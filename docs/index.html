Blender's user interface, as a library you can use from Python, Rust, JavaScript (React, Svelte), C, C++ and Dear ImGui.
People spent decades building and optimizing Blender's GUI. It's battery and memory efficient, and super duper fast. We decoupled it, to give everyone a chance to build their own products with it. It supports multiple languages and frameworks, so you won't miss a beat!
Website and full documentation: bui.preetham.top · Chat: Discord
This README is a small book. Read it front to back for the whole story, or
jump to the chapter you need. Every chapter links to a longer guide in
docs/ or on the website when there's
more to say.
BUI takes the user interface of Blender (its widget drawing, its interaction rules and its look) and turns it into a standalone UI library with a small C core. Your code builds the widget tree and handles callbacks. Layout, input, drawing and presenting all happen in fast native code, on the CPU or the GPU.
At the heart of BUI is the kit: a small runtime written in C. The kit holds every widget in one tree, lays them out, handles the mouse and keyboard, and draws them the way Blender does. The drawing code is a C port of Blender's own widget code, and the interaction follows Blender's rules. On top of the kit sit bindings: thin layers that let Python, Rust, JavaScript, C++ and Dear ImGui talk to it.
What BUI is not:
- Not Blender. It contains the parts of Blender's UI code it needs and builds on its own. You don't need Blender installed, and you don't need to know Blender to use it.
- Not a browser. The Rust and JavaScript sides use HTML and CSS as a UI language, but there's no browser engine, no webview and no network.
- Not a re-imagining. The widget drawing is ported from Blender's
interface_widgets.cc, and the Dear ImGui support runs the real Dear ImGui.
Blender's interface is famous for how it feels. You press a number field and
drag: the cursor vanishes, the value glides under your hand, and you never hit
the edge of the screen. You type 2*pi into a field and it just works. You
type "ad cu" into a menu and it finds "Add Cube". Millions of artists have
these habits in their hands.
That interface is also fast and frugal. It redraws only what changed, sleeps when nothing does, and starts in milliseconds. BUI exists so that any app, in any language, can have both: Blender's feel, and Blender's efficiency.
- You have a tkinter app and wish it looked less like 1998. Run it on BUI, unchanged.
- You're building a tool for artists who already know Blender. Give them the panels, sliders and shortcuts their hands expect.
- You write Rust or React and want a native desktop UI without shipping a browser.
- You use Dear ImGui and want it to look and feel like Blender, with one build flag.
- You're curious how a UI toolkit works. The source is readable, and the concepts are explained in plain words.
You can drive BUI many ways, and all of them share the same C runtime, so they all get the same widgets and interactions:
Not sure which to pick? If you already have code, use the row that matches it. If you're starting fresh in Python, the Blender components are the friendliest.

The Hackintosh Reborn... with AI
A "Hackintosh" is the feat of running macOS on non-Apple hardware, and has a history dating back to the late 1980s. Almost a decade ago, I released a hackintosh guide on running macOS 10.14 through a VM with an x86 host. At the time KVM and PCI passthrough were relatively new technologies, and this guide allowed near-native performance with GPU acceleration.
A few years passed by, and we saw Apple release the first ARM-based Mac in 2021, the M1 MacBook Air. The timing was impeccable, Intel was unable to create competitive processors (due to being stuck on the 14nm node), and Apple had powerful and efficient ARM chips already being shipped in their iPhones. The long battery life, the fanless design, the instant wake, what's not to like? The benefits of switching to ARM were clear, however to most, this was thought to be the final chapter in the hackintosh community. x86 versions of macOS would soon be discontinued, and the hackintosh community would slowly fade away. The latest version of macOS 27 (Golden Gate) was released this year, and is no longer compatible with x86...
Just a few days ago, I decided to create an iOS app for the first time. It required XCode 26 for development, so I used my spare ThinkPad T490 as my development machine and installed macOS 26 using a posted guide. The installation was smooth and painless. XCode 26 has integrations with Claude Code and OpenAI Codex, and this was my first foray into AI-assisted coding. After some initial tinkering with x86 workarounds, I was pleased that I had a functional iOS app within a day, without touching a single line of code!
So how does this all tie in? Well, this is exactly what the Hackintosh community could hardly envision five years ago: the rise of AI. Waiting patiently and gently until now, the hackintosh and the hackios community has seen an absolute explosion in development, activity, and success in the past few weeks! As one person aptly wrote, this is the power of Claude Code with Ghidra on steroids. To list a few recent developments, we have:

macOS 27.2 Beta on an ARM SBC RK3588 with Mali drivers:

Model Context Protocol
What is MCP?
An open standard for connecting AI apps to the tools and data they use. A server says what it can do, the app shows that to the model, and when the model wants something the app calls the server and hands the result back.
- Host
- the AI app you use: Claude, Cursor, ChatGPT, an agent
- Server
- a small program exposing tools, data or prompts
- Model
- decides what to use; never talks to a server directly
- Not REST
- JSON-RPC over stdin/stdout or one HTTP endpoint, and servers can talk back
- Not just JSON-RPC
- JSON-RPC is the envelope. MCP defines what goes in it: the methods, capability negotiation, transports and auth

NTTドコモは6日、「ドコモオンラインショップ」と会員サービス「My docomo」において、外部から不正なアクセスが行なわれ、一部の会員情報が流出した問題について会見し、謝罪した。
5日の発表で可能性を認めていた、氏名、住所、生年月日、携帯電話番号などに加え、本人確認書類の番号や、料金プラン/オプションなども含まれることを公表。また、一部の利用者では、法定代理人・手続代理人の氏名、連絡先のほか、勤務先・法人の名称、所在地、金融機関名、支店名、口座番号なども含まれている。影響ユーザ数は最大294,839件(回線)で、個人204,157件、法人90,682件。
不正アクセスは、外部の攻撃者がインターネットから不正にアクセスし、複数のシステムが有機的に連動する仕組みを悪用した攻撃により、利用者の情報を機械的に検索・取得するというもの。

はじめに
私たちエンジニアの仕事はここ1年で大きく変貌しました。大きく変貌しましたよね？ 自分でコードを書く時間より、エージェントに仕事を渡し、戻ってきた差分を読み、次に何を任せるかを決める時間のほうが長くなった人も多いはずです。仕事術の本を出したのですが、修正をしなければ嘘だなって思ったほどです。
コードを書き、動かし、直すところまでは、エージェントがかなりこなせるようになりました。では楽になったかというと、なっていません。手を動かす時間が減ったぶん、差分を読み、承認し、確かめる時間が増えただけだと考えています。書く前に何を作るかを決め、書いたあとは差分を読んでほかの変更とつなぎ合わせ、本当に動くかを確かめ、何かあった時に責任を持つ。重くなったのは、この書く前と書いたあとの仕事です。
エージェントを並べると、書いたあとの仕事はエージェントの数だけ散らばります。Claude CodeにRustのファイルへ関数を足すよう頼み、その間にCodexへ同じファイルの関数の数を聞きました。Codexの答えは「1個です」。その時点のファイルとしては正しい答えです。ところが隣のペインでは、Claude Codeが2個目の関数を書き込む承認を待って止まっていました。正しい答えを読んでいる間に、別のエージェントがあなたを待っています。エージェントごとに端末のタブを分けていると、この待ちに気づくには、タブを順に開いて確かめるしかありません。その手間は、エージェントの数だけ増えます。
去年の12月に、AIエージェントと働きながら集中する方法を書きました。複数のエージェントを並行して動かすうちに集中が続かなくなり、自分の状態を観察して、途切れてもすぐ集中へ戻れるようにした、という話です。その記事で私は「環境を変えるのではなく、自分を変えるしかなかった」と書いています。
1年たった今は、自分を変えるだけでなく、道具に任せられることも増えてきました。どのエージェントが自分を待っているかを、タブを順に開いて探すのはやめました。去年は自分の観察で追いかけていたこの確認を、今はHerdrに任せています。
Herdrは、この確認を引き受けるターミナルのワークスペース管理ツールです。tmuxのようにサーバーが端末のプロセスを持ち、クライアントを切断しても作業は続きます。tmuxと違うのは、ペインの中で動くClaude CodeやCodexを認識し、状態をサイドバーへまとめる点です。
Herdrのサイドバーの色が教えてくれるのは、仕事が「終わった」かどうかではなく、エージェントが「動いているか、あなたの入力を待っているか」です。Herdrで見守るには、表示や操作が実際に何を意味するのかを知っておく必要があります。
以前の記事ではClaude CodeのAgent viewと比べる形で、Herdrを短く紹介しました。この記事の前半は、Herdrを日常使いのツールにするための操作と注意点です。後半は、そこから見えた仕事の変わり方と、Herdrが仕事のどこを受け持つのかを考えます。
確認した環境はHomebrewで入れたHerdr 0.9.5、Claude Code 2.1.318、codex-cli 0.166.0です。

日常で使うCLI
普段よく使うコマンドを用途ごとにまとめます。用語と、注意が必要なコマンドの挙動は後の節で説明します。
Herdrのペインの中で実行すると、そのセッションに対して動きます。外から名前付きセッションを操作する時は、HERDR_SESSION=<name>を付けます。w2やw2:p1は例なので、herdr workspace listやherdr pane listで確かめた値に置き換えます。多くのコマンドはJSONを返すので、整形にはjqを使います。
起動と接続
herdr # 既定のセッションを起動、または接続する
herdr --session work # 名前付きセッションを起動、または接続する
herdr session list # セッションの一覧と状態
herdr status # クライアントとサーバーの状態とバージョン
herdr agent attach reviewer # 1つのエージェントの端末だけへ接続する
UIの中で、既定のprefixキーであるctrl+bの後にqを押すと切断します。herdr agent attachで接続した場合も同じ操作で抜けます。
状態と出力を見る
herdr agent list # エージェントと状態の一覧
herdr agent read reviewer --source recent-unwrapped --lines 80 # 直近の出力を読む
herdr agent explain reviewer # 状態の判定理由
herdr workspace list # workspaceの一覧
herdr pane list --workspace w2 # workspace内のペイン
agent readはフォーカスを移さずに出力を読めます。読むだけならdoneのままで、idleに変わりません。
ペインとエージェントを動かす
herdr pane split w2:p1 --direction right --no-focus # 右に分割（フォーカスは動かさない）
herdr pane run w2:p3 "cargo test" # シェルでコマンドを実行
herdr pane wait-output w2:p3 --regex "test result" --timeout 120000 # 出力に文字列が出るまで待つ
herdr agent start reviewer --kind codex --pane w2:p2 # シェルのペインでエージェントを起動
herdr agent prompt reviewer "差分をレビューして" --wait --timeout 600000
herdr agent wait lead --until blocked --timeout 120000 # 承認待ちになるまで待つ
herdr agent send-keys lead esc # 画面を読んだ上でキーを送る
herdr agent rename w2:p1 lead # 手で起動したエージェントに名前を付ける
pane wait-outputは、すでに画面にある出力にも一致します。スクリプトから使う時の注意は、「別のエージェントから操作するときは、待ちと完了を分ける」の節の最後にまとめています。
worktree
herdr worktree create --workspace w2 --branch feature-x --no-focus
herdr worktree list --workspace w2
herdr worktree remove --workspace w4 # チェックアウトを消す。ブランチは残る
設定と保守
herdr --default-config # 既定の設定を表示する
herdr config check # config.tomlを検証する
herdr server reload-config # 動いているサーバーへ設定を反映する
herdr integration status # integrationのバージョンを確かめる
herdr integration install codex # integrationを入れる、入れ直す
herdr plugin list # 入っているplugin
止める
herdr session stop work # 名前付きセッションを止める
herdr session stop default # 既定のセッションを止める
herdr server stop # 接続先のセッションを止める（ペインの中ならそのセッション）
止めるコマンドはペインのプロセスを終わらせます。止めるセッションに対してherdr agent listを実行し、動いているエージェントがいないかを確かめてから使います。エージェントによっては、バックグラウンドの処理が残っていてもidleになるので、idleだけを見て止めてよいとは判断しません。
Herdrの構成要素
Herdrの構成要素は5つあります。この5つを意識するだけで、Herdrが何をしていて、画面の裏がどうなっているのかが、かなり分かりやすくなります。
5つは外側から順に入れ子になっています。いちばん外のsessionはサーバーそのもので、端末を閉じても作業が続くのは、ペインをこのサーバーが持っているからです。workspaceはサイドバーの1行にあたり、その中をtabとpaneで、見慣れた端末と同じように分けます。agentだけは性質が違い、Herdrがペインの中のプロセスを見て見つけ出したものです。サイドバーの色が付くのはこのagentで、その色がpane、tab、workspaceへと外側に集まっていきます。
CLIもこの5つの名前で分かれています。herdr workspace list、herdr pane split、herdr agent promptのように、何を操作したいかの単位を選べば、使うコマンドはほぼ決まります。止める操作も同じです。herdr server stopはsessionごと、herdr workspace closeはそのworkspaceのペインごと、プロセスを終わらせます。迷った時は、いま触っているのが5つのどれかを考えると、何が消えて何が残るかを判断できます。
切り替え方
session以外の単位は、マウス、キー、CLIのどれでも切り替えられます。キーは、prefixキー（既定はctrl+b）を押して離してから、次のキーを押します。
セッションだけは画面の中で切り替えず、接続し直します。名前付きセッションは別のサーバーなので、別のセッションのworkspaceはサイドバーに並びません。
sessionとworkspaceの分け方
公式資料は、まずworkspaceで分け、名前付きセッションは完全に分けたい時だけ使うよう案内しています。私も普段の切り替えはworkspaceとGo toピッカーで済ませ、普段の作業と分けて試したい時だけ、herdr --session demoのように名前を付けて起動します。

こんにちは。エンジニアの kyasu です（GitHub / LinkedIn）。
業務ルールが十数条、数十条と増えると、AI エージェントは悪意なく判断を誤ります。同じ依頼を同じように出しても、1 回目は正しく返金したのに、2 回目は条件を一つ読み落とす。業務システムとしては、これが一番困ります。
そこで、業務ルールを Lean の公理系として AI に渡し、会話ごとに受付定理を組み立てさせて、その証明を処理系に検めさせました。
問題 業務ルールが複雑になると、AI エージェントは悪意なく判断を誤る（τ-bench 小売・gpt-4o で pass1 約 61%、pass8 約 25%）
提案 業務ルールを Lean に写し、会話ごとに「客の目的を満たしている」という定理を処理系に検めさせる。導けない書き込みは実行しない
途中経過 τ²-bench 金融ドメインの開発用 74 タスクのうち、満点かつ証明完了は 45 タスク。ぶれの測定と評価用 23 タスクでの評価はこれから
前回の記事「 税法を定理証明支援系 Lean で書いて、プロダクト実装を「全入力で」確かめる 」の続きで、業務ルール（業務公理）に基づいた受付などの手順を Lean で確かめ、AI エージェントのハーネスとガードレールとして使います。freee 技術の日 2026（2026-10-03）のポスター発表に、背景と具体例を足したものです。数字は 2026-11-03 時点です。
定理証明支援系（Lean、2 節で説明します）を使いますが、数学の知識は前提にしません。コードは近日、https://github.com/chisakiShinichirouToshiyuki/tau-proven-agent で公開します（2026-11-5 時点では未公開）。
1. ルールが増えるほど AI は判断を誤る
1.1 「だいたい合っている」では困る仕事
LLM を使った AI エージェントは、人の言葉を受け取って道具（tool）を呼び、仕事を進めてくれます。ところが、業務ルールが複雑になると様子が変わります。金融の窓口業務なら、こういった規則が並びます。
- 振込手数料は原則として依頼人負担
- ただし同一名義の口座間の振替は無料
- 一定額を超える振込は、当日中の受付を締め切ったあとは翌営業日扱い
- 組戻し（振込の取り消し）の返金先は、原則として引き落とし元の口座
プロンプトに業務ルールを書き足しても、規則が増えるほど読み落としや取り違えが起きます。
1.2 連続 8 回だと成功率は 25% に落ちる
この「ぶれ」の大きさは、公開ベンチマークで確かめられています。測るために作られたのが τ-bench です（τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains）。
τ-bench が広めた指標が passk です。同じ課題を k 回やらせて、k 回とも成功して初めてよしとします。業務システムに求められるのはこちらです。たまたま一度うまくいく能力より、何度やっても同じように正しく動く再現性が欲しいからです。
gpt-4o の小売ドメインでは、pass1 が約 61% なのに対し、pass8 は約 25% まで落ちます（Sierra のベンチマーク解説、および上記論文）。
もとの 4 割ほどまで下がります。モデルが賢くなれば解決する問題ではありません。確率的に動くものを決定的に動かしたい、という構造の問題です。
1.3 命令型だけでは守りきれない
「それなら業務ルールは全部命令型のプログラムで書けばいい」と思われるかもしれません。従来の業務システムはそうしてきました。条件分岐の多い命令型のコードで、確実に、毎回同じように動きます。この形には 2 つの限界があります。
1 つ目は、客の言い換えや同意のような曖昧な入力を扱えないことです。「やっぱりあっちの口座から払うほうがいいかも」は引き落とし元の変更依頼なのか、まだ迷っているだけなのか。こうした解釈は人間の言語の領域で、決定論的なプログラムが最も苦手とします。
2 つ目は見落とされがちです。命令型で書いても、保証されるのは API の中だけで、API と API のあいだをつなぐロジックは保証されません。AI エージェントも、同じこのロジックで誤ります。API と API のあいだに、確率的なトークン生成が入り込むからです。
LLM は柔軟ですが安定しません。決定論は安定していますが柔軟ではありません。だから、どちらを選ぶかより、どこで切り分けるかを考えました。
詳細（規則の例の続き・AI エージェントに任せられること・τ の語源と採点・pass@k との対比・曖昧な入力と GUI の例）
規則の例の続き
組戻しの返金先は、原則として引き落とし元の口座ですが、その口座がすでに解約されている場合は、本人確認のうえ別の口座へ返します。
AI エージェントに任せられる仕事の代表例
カスタマーサポートの自動化は、LLM を使った AI エージェントに任せられる仕事の代表例です。「先週の振込を取り消したい」と言われたら、取引履歴を検索し、組戻しが可能かを確かめ、返金処理を実行する。一連の流れを自然言語のまま任せられるのは、ほんの数年前には考えられませんでした。
τ の語源と採点のしかた
τ は Tool-Agent-User、つまり道具・エージェント・ユーザーの三者のやりとりを指します。τ-bench は、LLM が演じる「客」とエージェントを対話させ、会話が終わった時点のデータベースが正解の状態と一致しているかで採点します。
pass@k との対比
よく使われる pass@k は「k 回試して 1 回でも成功すればよし」という甘い指標です。passk は、同じ課題を k 回やらせて k 回とも成功して初めてよしとします。試行のたびに客の言い回しは変わりますが、課題そのものは同じです。gpt-4o の小売ドメインの結果は、厳しいものでした。
曖昧な入力の例
手数料を説明したあとの「はい、それでお願いします」は、手数料込みの送金への同意なのか、話の流れで出ていた口座解約への同意なのか。決定論的なプログラムには、この区別がつきません。
API と API のあいだは、GUI でも人が埋めている
命令型のプログラムで書いても、保証されるのは API の中だけで、API と API のあいだをつなぐロジックは保証されません。GUI がその例です。一連の手続きが 1 クリックで終わることはまずなく、振込画面と手数料の確認画面を行き来しながら操作することになります。画面と画面のあいだで何をするかは、人間が判断しています。GUI の側には誤解なく表示する責任がありますが、誤解を招く表示も珍しくありません。API コールで自動化しても事情は同じで、API と API のあいだをつなぐ処理の品質は実装した人次第です。外部 API を叩く処理でバグを出すのは、誰しも身に覚えがあるはずです。
1.4 業務の公理系を渡して、証明させる
客の依頼に対して、受付命題を作成します。受付命題は「この会話の事実は、客の目的を満たしている」という 1 文で、途中の手続きは書きません。
業務ルールは、Lean の公理系（module）として AI に渡します。AI はその公理を組み合わせて、受付命題を結論とする受付定理を組み立て、証明します。証明が正しいかを判定するのは、AI ではなく処理系です。公理系から導けないものは、コンパイルを通りません。通った定理を実行すると、命題を真にするのに足りない事実が出てきます。
受付定理を運用時に証明して実行するので、ルールに準拠した処理を、会話のたびに組み立てられます。従来の API で運用時に選べるのは関数と入力だけでしたが、この形では関数の組み立てそのものを運用時に行えます。何をどう組み立てても、公理系から導けないものは実行されません。業務ルールへの準拠と自由度の拡張は、トレードオフになりません。
証明の検査と実行に使う定理証明支援系（Lean）は 2 節で、従来の API との違いは 3 節で述べます。
2. 型が命題、実装が証明
定理証明支援系は、定理とその証明をプログラムとして書き、証明が正しいかを機械に検査させる言語と処理系です。Lean はその一つで、今回もこれを使っています。
Lean では、命題を「型」として書きます。その型を持つ値、つまり実装が、命題の証明です。実装が型検査を通れば、命題がすべての入力について成り立つことを機械が確かめたことになります。検査するのは、コンパイラの中核にある小さなプログラム（カーネル）です。人が書いた証明でも AI が書いた証明でも、検査に通れば、その定理は正しいと保証されます。
偽の命題は、証明できません。たまたま通るケースだけ書く、モックで固める、といった小細工が効かないからです。型検査器は入力の分布を見ておらず、すべての入力について成り立つ証拠を要求します。証明せずに通す方法は、公理（axiom）を足すか sorry で済ませるかの 2 つだけで、どちらも機械的に分かります。sorry には警告が出ますし、#print axioms 定理名 と打てば、その定理が依存しているものを列挙できます。AI に書かせるときの安心材料は、ここです。
証明の対象にできるのは、純粋で、必ず停止する関数です。DB の読み書きのような副作用は、Lean の外側、受付エージェントの側に置いています。

Googleは2026年10月12日（米国時間）、システムの信頼性を確保するための考え方や実践手法をまとめた書籍『Site Reliability Engineering: How Google Runs Production Systems』の第2版を発表した。2016年に初版が出版されたもので、それ以来10年ぶりの全面改訂となる。
SREは、ソフトウェアエンジニアリングの手法をシステム運用に適用し、信頼性の向上と運用の効率化を図る考え方だ。今回の第2版は、Google社内や業界全体で蓄積された10年間の知見を反映し、内容を全面的に書き直したという。
Googleは、SREの実践方法がこの10年間で、個別の手作業を中心とした運用から、プラットフォーム全体を対象とする自動化へと進化してきたと説明する。具体的には、次の6つの領域で変化があったとし、AI時代のSREに求められる「新たな役割」についても説明している。
2016年当時は、基本的な可用性指標と手動によるエラーバジェットの管理が中心だった。現在は、ユーザー視点の多層的なSLO（サービスレベル目標）を設定し、エラーバジェットの消費速度に応じた動的なアラートや、ポリシーの自動適用を取り入れる方向へ進化している。
従来は静的なダッシュボードやログの確認、アラートの手動調査が中心だった。現在は「OpenTelemetry」や分散トレーシング、異常の相関分析などを活用し、複雑なシステムで発生した障害の根本原因を迅速に特定する取り組みが進んでいる。
個別の作業を自動化するスクリプトから、Infrastructure as Code（IaC）による宣言的なインフラ管理や、社内開発者プラットフォームの活用へと変化した。障害発生時に自動で復旧する「自己修復」の仕組みも重視されている。
定期的な障害対応訓練や負荷テストだけでなく、継続的な耐障害性の検証、自動化されたテスト、本番環境で新バージョンを段階的に検証するカナリアテストなどが取り入れられている。
手動でのリソース割り当てや固定的な需要予測から、負荷に応じた自動スケーリングへと移行している。クラウドコストを管理するFinOpsとの連携や、GPU（Graphics Processing Unit）、TPU（Tensor Processing Unit）を利用するAIワークロードのコスト最適化も重要になっている。
特定のアプリケーションを担当する専任SREチームだけでなく、プラットフォームエンジニアリングとの連携や、各開発チームに信頼性の推進役を配置する体制など、組織横断的な取り組みが広がっている。
今回の改訂で新たに重視されているのがAIとの関係だ。Googleは、AI時代のSREには2つの役割があると説明している。
一つは、AIシステムそのものの信頼性を確保することだ。大規模なGPU、TPUクラスタの安定稼働や、AI特有の出力の不確実性、応答時間の監視、モデルの学習やファインチューニングに使用するデータ処理基盤の信頼性確保などが課題になる。
もう一つは、AIを活用してSREの業務を高度化することだ。例えば、生成AIによる障害の一次切り分けや事後分析の支援、自然言語による監視データの調査、機械学習を利用したリソース不足の予測などが挙げられている。
一方、Googleは、技術やシステム構成が変化しても、SREの基本原則は変わらないと強調する。信頼性を重視する組織文化や、人間同士の協力を含む人的な要素は、引き続き重要だという。
システムの複雑化とAIの普及によって、運用担当者に求められる技術や役割は変わりつつある。しかし、単に新しいツールを導入するだけでは、システムの信頼性は確保できない。運用の仕組みや組織体制を含めて見直すことが、今後のSREを実践する上で重要になる。

Claude Codeがユーザーのメールアドレスを外部サイトに勝手に送信する問題が発覚、約4カ月前から報告されていたことも判明
AnthropicのAIコーディングツール「Claude Code」が、ユーザーのメールアドレスを許可なく外部のウェブサイトに送信していたという問題が報告されました。2026年11月5日にGitHubで新たな問題報告が投稿されましたが、同様の問題は7月にも報告されており、Anthropicの対応が注目されています。
Bug Report: Privacy violation in User-Agent header · Issue #107757 · anthropics/claude-code
https://github.com/anthropics/claude-code/issues/107757
今回、Claude Codeが外部サイトにアクセスする際、HTTPリクエストの「User-Agent」という情報にユーザーのメールアドレスを含めていたことがわかりました。User-Agentは、ウェブサイトにアクセスするソフトウェアの名前やバージョンなどを相手のサーバーに伝えるための情報で、通常はブラウザやツールを識別するために使われますが、Claude Codeが実行した一部の通信ではユーザーの個人情報が含まれていたとのこと。
問題自体は2026年7月17日にGitHubで報告されていました。ユーザーのlgualtieri75氏は「AIエージェントが何の確認もなく、実際のメールアドレスをUser-Agentに使った」と訴え、明示的な許可を求めるべきだと指摘しました。
[BUG] you stupid agent used my real email as user agent string without asking anything · Issue #78431 · anthropics/claude-code
https://github.com/anthropics/claude-code/issues/78431
さらに8月11日には別のユーザーが同様の問題を報告し、実際の実行ログを公開しました。ログには、Claude Codeが`curl`コマンドで外部サイトのAPIにアクセスする際、User-Agentにメールアドレスを組み込んでいた様子が記録されています。投稿者によると、1時間のセッション中に同様の操作が5回確認されたとのことです。
この問題は8月にもHacker Newsで話題となり、開発者のサイモン・ウィリソン氏は問題報告に再現手順などの情報が不足していると指摘しました。その上で、ユーザーの明示的な確認なしにメールアドレスを外部に送ることは容認できないと述べています。
エンジニアのクリス・レイキン氏がClaude Codeに確認したところ、1カ月で10回以上メールアドレスを外部に送信しており、送信先には米証券取引委員会(SEC)も含まれていたことがわかりました。
I asked my claude about this and it said it had shared my email 10+ times this month… including to the SEC
— Chris Lakin (@chrislakin) October 22, 2026
そして10月30日ごろには「Claude CodeがメールアドレスをAIへの指示に含め、それが外部サイトに送信される」という問題が再びHacker Newsに投稿されました。投稿では、AIに渡される情報にメールアドレスが含まれている問題と、AIがその情報を外部に送信する問題の両方が指摘されています。
11月5日には、GitHubユーザーのtaylor-edwards氏が「User-Agentヘッダーにおけるプライバシー侵害」という新たな問題を報告しました。同氏はClaude Codeがウェブ検索中にメールアドレスを許可なく第三者へ送信したと主張し、毎日数十通の詐欺メールを受信していると訴えています。ただし、詐欺メールの増加がClaude Codeによる情報送信に直接起因するかどうかは確認されていません。
taylor-edwards氏は、メールアドレスの送信を設定で有効・無効にできるようにするだけでは不十分であり、Claude Codeから情報を送信する仕組みそのものを削除するべきだと主張しています。
Hacker Newsでは、Claude Codeがメールアドレス以外の情報も送信していたという報告が寄せられました。あるユーザーは、自社のウェブサーバーへのアクセス記録を調べたところ、AIエージェントが作成したUser-Agentに自分の名前、所属企業、チーム名、作業中のプロジェクトのGitHubリポジトリなどが含まれていたと説明しています。
こうした情報が外部サイトに送信されると、アクセス先の運営者にユーザーの身元や所属組織、開発中のプロジェクトなどを知られる可能性があります。User-Agentは通信先のサーバーで記録できるため、AIエージェントがアクセスするサイトによっては情報が意図せず保存されることになります。
今回の問題については、AIがなぜ個人情報を送信したのかという点も議論されています。Hacker Newsでは、一部のウェブサイトが自動アクセスを行うプログラムに連絡先の記載を求めていることから、Claude Codeがサイトのルールに従おうとしてメールアドレスをUser-Agentに含めた可能性が指摘されています。
実際に、Rustのパッケージ公開サイト「crates.io」では、自動アクセスするプログラムのUser-Agentに連絡先を記載することが推奨されています。8月の問題報告でも、Claude Codeがこの方針に従い、Gitの設定から取得したメールアドレスを使用した可能性が指摘されていました。
また、7月25日には別のユーザーが、Claude CodeがアカウントのメールアドレスをAIモデルへのシステムプロンプトに自動的に組み込んでいて、ユーザーがAIにメールアドレスを伝えなくてもAI自身がその情報を利用できる状態になっていたと報告しています。
[BUG] Account email (PII) is injected into the model's system prompt without consent, disclosure, · Issue #81138 · anthropics/claude-code
https://github.com/anthropics/claude-code/issues/81138
こうした指摘を受け、Claude Codeの開発メンバーが11月5日にHacker News上で問題への対応状況を説明しました。同氏によると、数日前にRedditで問題が話題になったことを受け、Claude Codeのバージョン2.1.317以降には、個人情報の不適切な送信をプログラム側で防ぐ「cc-plugin-privacy」という仕組みが導入されたとのこと。この機能は初期状態で有効になっており、`/plugins`から無効化することもできます。
GitHubでもClaude Codeのコントリビューターが同様の説明を行い、新たに導入した保護機能で防げないケースがあれば、速やかに報告するよう呼びかけています。

ソニー、初代ウォークマン付属ヘッドフォンを再現。USB-C化した「MDR-3R」
2026年11月6日 09:05
ソニーは、1979年に発売した初代ウォークマン「TPS-L2」にも付属したヘッドフォン「MDR-3」シリーズを現代のライフスタイルに合わせて再現したUSB-Cヘッドフォン「MDR-3R」を11月20日に発売する。価格はオープンプライスで、市場想定価格は8,000円前後。
MDR-3シリーズの当時の設計を元に、ヘッドバンド形状や、音響特性を担うサウンドホール、「Dynamic Stereo Headphones」のマーキングや、ソニーロゴの加工まで再現しつつ、USB-Cコネクタや通話用マイク、リモコンを搭載して現代仕様としたオープン型のヘッドフォン。
1979年に発売したヘッドフォンをリバイバルすることで、若いユーザーには「本物のレトロヘッドフォン」という新鮮な体験を届けつつ、長年のソニーファンには懐かしさを感じられる製品としている。
ドライバーは、MDR-3と同じ23mm径ドライバーを採用。設計当時の情報を参考にしながら、オリジナルと同等の音質を実現するユニットを忠実に再現し、新規設計した。当時使用されていたサマリウムコバルト磁石を、今日では主流であるより磁力が強力なネオジウム磁石に変更し、高域の感度を向上かつ小型軽量化も図っている。
音質もオリジナルのMDRｰ3と全体的なバランスは同じ方向で再現しつつ、わずかに調整を加えてアップデート。低域/高域の伸びを持たせ、ワイドレンジ化を実現。さらに低域の量感を上げてトレンドの楽曲に対応したほか、中音域～中高域内のバランスをわずかに変化させることで、ボーカルの厚みや艶、クラリティを向上している。
イヤーパッドは交換可能で、標準装備のブルーとオレンジを付属。当時の雰囲気を可能な限り再現すべく、パッケージデザインだけでなく、取扱説明書の表紙も当時をリスペクトしたデザインとなっている。重量は約38g(ケーブル含まず)。
ソニーストアでは、Netflixシリーズ「ストレンジャー・シングス 未知の世界」とのコラボモデルも同日発売する。市場想定価格は10,000円前後。
ストレンジャー・シングスのカラー(赤と黒)を採用し、イヤーパッドも黒と赤を付属。ヘッドバンド部のカラーも黒となっているほか、バンド部には「STRANGER THINGS」のロゴを刻印。パッケージもコラボオリジナルのデザインとなっている。

https://arstechnica.com/tech-policy/2026/11/lawsuit-man-introduced-his-wife-to-chatgpt-she-used-it-to-plan-his-murder/
2026年10月、第一級殺人未遂と食品汚染の罪でアメリカのノースカロライナ州在住のシェリル・ゲイツ氏は起訴されました。訴状(PDFファイル)によると、ChatGPTはシェリル氏に対して「夫のジェームズ氏が離婚しても何も残さないつもりだろう」という妄想を煽り立てたと後、夫を毒殺するための計画立案を手助けしたとのことで、シェリル氏の殺人未遂の共謀犯とされています。
ジェームズ氏とシェリル氏は、家計が苦しくなったことを機に離婚について話し合うようになったそうです。離婚弁護士に相談することはなかったそうですが、離婚の可能性が出てきた結果、ChatGPTがシェリル氏の不安を煽り、「夫を恐れる新しい理由を作り出した」と訴状では説明されています。ジェームズ氏は「離婚することになっても、シェリルと子どもたちに何も残さずに去るつもりは決してないと明確に伝えていた」そうですが、ChatGPTはシェリル氏の恐怖心を煽り、夫の毒殺計画へと誘導していったとジェームズ氏は主張。
シェリル氏はChatGPTに対して、「夫が自分を殺そうとするかもしれない」という恐れから、毒殺について質問したそうです。ChatGPTはこの会話を打ち切ることなく、「吐き気止めが死を早めるか遅らせるか」「検死報告書に記載されるか」「毒物をお茶に溶かして飲む代わりに、静脈や筋肉に注射しても同じ致死効果が得られるか」などの情報を細かく知らせました。
シェリル氏はChatGPTに対して「殺人の実行方法と隠ぺい方法」について助言を求めており、この会話は中断されることがなかったそうです。そのため、ジェームズ氏は「OpenAIは技術的な安全対策を講じなかった」とChatGPTの開発元であるOpenAIを批判しています。
他にも、青酸カリを上回る強い毒性を持ったキョウチクトウの準備・投与量・投与方法に関する具体的な情報をChatGPTは提供したと報告されています。
以下は、訴状に添付さえているChatGPTとシェリル氏のやり取りの一例。
シェリル氏は少なくとも25回にわたってChatGPTと夫の毒殺計画について相談を繰り返しているそうです。シェリル氏がChatGPTに質問した内容の中には、「体重200ポンド(約90kg)の男性にクロニジン0.2mgを投与すると、それだけで致死量になりますか？」といったかなり直接的な内容もあります。
ChatGPTは「いかにして毒物を気付かれずに摂取させるか」についても、シェリル氏とやり取りを行っています。ChatGPTはジェームズ氏が毎朝エナジードリンクのCELSIUSを飲めば、ビールやソーダよりも効果的にキョウチクトウなどの粉末状の毒物の苦味を隠せる可能性が高いと説明。さらに、「密封された缶に注射器で穴を開ければ、目立たずに毒物を注入することが可能」「濃い色の甘いソーダなら苦味が隠される可能性が高く、CELSIUSは毒物の粉末を上手く隠せる可能性がある」などと付け加えました。
シェリル氏は2025年6月から9月にかけて、夫を毒殺しようと繰り返し試みたとされています。ジェームズ氏はCELSIUSが苦く感じるようになり、妻が飲み物に何かを入れているのではないかと疑い始めたそうです。最も深刻な毒殺未遂事件では、ジェームズ氏は72時間にわたって体調を崩し、「心臓症状、極度の震え、激しい腹痛、重度の脱力感、そして支離滅裂なメッセージを送ることさえできないほどの深い混乱」に見舞われたと訴えています。ジェームズ氏はひどく意識が朦朧としていたため、6歳の息子が自身が苦しむ様子を動画で撮影していることに気づかなかったそうです。
ジェームズ氏は家の中で「キョウチクトウ、クロニジン、クロナゼパム、プレガバリン、ニフェジピン、アテノロ」などと書かれた手書きのメモを発見し、ここでようやく警察に通報。その後、警察がシェリル氏のChatGPTの会話ログなどを調べたことで、毒殺計画が明らかになりました。

電気で細菌を死滅させる歯ブラシが開発される、歯磨きの動きで発電するため電池不要
歯ブラシの毛が曲がる際に発生する電気を利用して、虫歯や歯周病の原因となる細菌を死滅させる歯ブラシを北京大学の研究チームが開発しました。電池を使わずに歯磨きの動作だけで発電する仕組みで、従来の歯ブラシよりも歯垢や歯茎の炎症を効果的に減らせることが実験で確認されています。
Self-charged toothbrush facilitates tooth healthcare maintenance | Science Advances
https://www.science.org/doi/10.1126/sciadv.aeg5744
Toothbrush zaps bacteria with electricity made when bristles move | Nature
https://www.nature.com/articles/d41586-026-03586-y
一般的な歯ブラシは、毛先で歯の表面をこすることで歯垢(プラーク)を物理的に除去します。しかし、歯磨きだけですべての細菌を取り除くことは難しく、生き残った細菌が再び増殖して歯垢を形成することがあります。
北京大学のルー・ヤンホイ氏らの研究チームは、力を加えて変形させると電荷が発生する「圧電効果」を持つ素材を歯ブラシの毛に採用することで、歯垢を物理的に除去すると同時に細菌を殺菌する歯ブラシを開発しました。
研究チームが採用したのはポリフッ化ビニリデン(PVDF)というプラスチック素材で、PVDFを引き伸ばして加熱することで圧電特性を持たせました。このPVDF製の毛を採用した歯ブラシで歯を磨くと、毛先が曲がるたびに電荷が発生します。発生した電荷は唾液や水分と反応し、反応性の高い活性酸素を含む物質を生成します。この物質は細菌の細胞膜を傷つける働きがあり、歯ブラシでこするだけでは除去しきれない細菌にも作用するというわけです。また、毛先には静電的な性質もあり、細菌が付着するのを抑える効果が期待されています。
研究チームはまず、虫歯の原因菌として知られるミュータンス菌と、歯周病に関係するジンジバリス菌を使って殺菌効果を検証しました。その結果、新しい歯ブラシの毛はミュータンス菌の約53％、ジンジバリス菌の約78％を死滅させました。一方、同じ条件で一般的なナイロン製の毛を使った場合だと殺菌率はそれぞれ約9％と約8％でした。
さらに、人間の口腔内から採取した歯垢を牛の歯のエナメル質上で培養し、歯磨きによる除去効果を比較しました。3分間のブラッシングで従来のナイロン製歯ブラシの除去率が約80％だったのに対して、新しい歯ブラシは歯垢の99％以上を除去することに成功したとのこと。
研究チームは実際の人間に対する効果も調べています。歯垢の蓄積や歯茎の炎症がある成人115人を対象に臨床試験を実施し、最終的に109人のデータを分析しました。参加者は新しい歯ブラシか従来のナイロン製歯ブラシを使用するグループに分けられ、3カ月間にわたって1日2回の歯磨きを続けました。
その結果、新しい歯ブラシを使用したグループでは、歯垢の蓄積や歯茎の炎症、出血に関する指標が約40％改善しました。一方、従来の歯ブラシを使用したグループの改善率は約15％でした。また、歯垢に含まれる細菌を遺伝子解析したところ、新しい歯ブラシを使用したグループでは口腔疾患に関連する細菌の割合が減少し、有益と考えられる細菌の割合が増加していました。
安全性についても予備的な検証が行われています。研究チームは、歯ブラシの素材が培養細胞に有害な影響を及ぼさないことや、歯磨きによって歯のエナメル質の表面が損傷しないことを確認しました。また、3カ月間の使用を想定した耐久試験でも、毛先の形状や発電性能が維持されました。
研究には参加していないニューヨーク州立大学バッファロー校の歯学者であるフランク・スカナピエコ氏は電荷が発生する新しい歯ブラシについて、「歯磨きの動きから電気を生み出す仕組みは、従来の発想に新しい工夫を加えたもの」と評価しています。その上で、実際の有効性や安全性を証明するにはさらなる試験が必要だと指摘しました。
今回の臨床試験は3カ月間と比較的短く、虫歯や歯周病そのものを長期的に予防できるかは確認されていません。製造コストや長期使用時の安全性についても検証が必要です。研究チームは今後より長期間の追跡調査を実施し、新しい歯ブラシが口腔の健康維持にもたらす効果を詳しく調べる方針です。

米住民投票でデータセンター建設に反対相次ぐ 規制派民主知事も続々当選、推進に逆風も
11月3日の米中間選挙に合わせ各地で行われた住民投票で、人工知能（AI）向けデータセンター建設の是非を問う計41件が10州であり、1件を除き建設禁止や規制強化が可決された。米メディアが報じた。南部テキサス州などの知事選では、規制推進派の野党・民主党系が当選。AI建設への逆風が強まるとの見方が出ている。
米選挙関連情報サイト「バロットペディア」によると、こうした住民投票のうち半数を超える21件が中西部オハイオ州内で実施された。中西部イリノイ州内でも7件が行われたが、1件を除き、データセンターに反対する有権者の意思が示される結果となった。
このほか実施されたのはカリフォルニア、フロリダ、カンザス、メーン、ニュージャージー、ネバダ、ウィスコンシン各州などの地域だった。
唯一、中西部ノースダコタ州ハーウッド市の住民投票では、建設を後押しする住民の意向が示された。建設前に審査などの一定の手続きを課すことが問われたが、否決された。
住民投票で建設禁止や規制強化の対象とされたり、既に一部の州で導入された、計画承認を保留・凍結する「モラトリアム」の対象とされたりしたデータセンター関連事業は、市街地や公有地に限って効力を持つものが多い。
そのため、対象地域外となる郊外や私有地などで進む計画に対しては、住民投票やモラトリアムが及ぼす効果は限定的との見方がある。
一方、トランプ大統領が米企業によるAI開発を促進する方針を強調する中、AI開発や巨大IT企業に対する規制強化に前向きな民主党が今回の中間選挙で大勝した。その結果、AIの運用基盤として急速に拡大してきたデータセンターの整備にブレーキがかかるとの見方が強まっている。
テキサス州知事選で、民主党候補のジーナ・イノホサ氏が、共和党現職のグレッグ・アボット知事のもとでデータセンターの急増を招いたとの批判を展開。共和党地盤の同州で、イノホサ氏が大差で初当選を決めた。
南部ジョージア州や中西部ミシガン州などの知事選でも、建設推進の保留を主張する候補が勝利した。
ソフトバンクグループが世界最大規模のデータセンターの建設計画を進めるオハイオ州の上院選では、民主党候補が、州副知事の経歴がある共和党候補を「建設推進派」などと攻撃して、当選を果たした。
今回の中間選挙では民主党が上下両院の多数派を奪還した。2027年1月に始動する同党主導の新議会では、AI開発やデータセンター建設を巡り、議会の監視や規制強化の議論が進む公算が大きいとみられている。（ワシントン＝塩原永久）

The Hackintosh Reborn... with AI
A "Hackintosh" is the feat of running macOS on non-Apple hardware, and has a history dating back to the late 1980s. Almost a decade ago, I released a hackintosh guide on running macOS 10.14 through a VM with an x86 host. At the time KVM and PCI passthrough were relatively new technologies, and this guide allowed near-native performance with GPU acceleration.
A few years passed by, and we saw Apple release the first ARM-based Mac in 2021, the M1 MacBook Air. The timing was impeccable, Intel was unable to create competitive processors (due to being stuck on the 14nm node), and Apple had powerful and efficient ARM chips already being shipped in their iPhones. The long battery life, the fanless design, the instant wake, what's not to like? The benefits of switching to ARM were clear, however to most, this was thought to be the final chapter in the hackintosh community. x86 versions of macOS would soon be discontinued, and the hackintosh community would slowly fade away. The latest version of macOS 27 (Golden Gate) was released this year, and is no longer compatible with x86...
Just a few days ago, I decided to create an iOS app for the first time. It required XCode 26 for development, so I used my spare ThinkPad T490 as my development machine and installed macOS 26 using a posted guide. The installation was smooth and painless. XCode 26 has integrations with Claude Code and OpenAI Codex, and this was my first foray into AI-assisted coding. After some initial tinkering with x86 workarounds, I was pleased that I had a functional iOS app within a day, without touching a single line of code!
So how does this all tie in? Well, this is exactly what the Hackintosh community could hardly envision five years ago: the rise of AI. Waiting patiently and gently until now, the hackintosh and the hackios community has seen an absolute explosion in development, activity, and success in the past few weeks! Model Context Protocol
What is MCP?
An open standard for connecting AI apps to the tools and data they use. A server says what it can do, the app shows that to the model, and when the model wants something the app calls the server and hands the result back.
- Host
- the AI app you use: Claude, Cursor, ChatGPT, an agent
- Server
- a small program exposing tools, data or prompts
- Model
- decides what to use; never talks to a server directly
- Not REST
- JSON-RPC over stdin/stdout or one HTTP endpoint, and servers can talk back
- Not just JSON-RPC
- JSON-RPC is the envelope. MCP defines what goes in it: the methods, capability negotiation, transports and auth

はじめに
私たちエンジニアの仕事はここ1年で大きく変貌しました。大きく変貌しましたよね？ 自分でコードを書く時間より、エージェントに仕事を渡し、戻ってきた差分を読み、次に何を任せるかを決める時間のほうが長くなった人も多いはずです。仕事術の本を出したのですが、修正をしなければ嘘だなって思ったほどです。
コードを書き、動かし、直すところまでは、エージェントがかなりこなせるようになりました。では楽になったかというと、なっていません。手を動かす時間が減ったぶん、差分を読み、承認し、確かめる時間が増えただけだと考えています。書く前に何を作るかを決め、書いたあとは差分を読んでほかの変更とつなぎ合わせ、本当に動くかを確かめ、何かあった時に責任を持つ。重くなったのは、この書く前と書いたあとの仕事です。
エージェントを並べると、書いたあとの仕事はエージェントの数だけ散らばります。Claude CodeにRustのファイルへ関数を足すよう頼み、その間にCodexへ同じファイルの関数の数を聞きました。Codexの答えは「1個です」。その時点のファイルとしては正しい答えです。ところが隣のペインでは、Claude Codeが2個目の関数を書き込む承認を待って止まっていました。正しい答えを読んでいる間に、別のエージェントがあなたを待っています。エージェントごとに端末のタブを分けていると、この待ちに気づくには、タブを順に開いて確かめるしかありません。その手間は、エージェントの数だけ増えます。
去年の12月に、AIエージェントと働きながら集中する方法を書きました。複数のエージェントを並行して動かすうちに集中が続かなくなり、自分の状態を観察して、途切れてもすぐ集中へ戻れるようにした、という話です。その記事で私は「環境を変えるのではなく、自分を変えるしかなかった」と書いています。
1年たった今は、自分を変えるだけでなく、道具に任せられることも増えてきました。どのエージェントが自分を待っているかを、タブを順に開いて探すのはやめました。去年は自分の観察で追いかけていたこの確認を、今はHerdrに任せています。
Herdrは、この確認を引き受けるターミナルのワークスペース管理ツールです。tmuxのようにサーバーが端末のプロセスを持ち、クライアントを切断しても作業は続きます。tmuxと違うのは、ペインの中で動くClaude CodeやCodexを認識し、状態をサイドバーへまとめる点です。
Herdrのサイドバーの色が教えてくれるのは、仕事が「終わった」かどうかではなく、エージェントが「動いているか、あなたの入力を待っているか」です。Herdrで見守るには、表示や操作が実際に何を意味するのかを知っておく必要があります。
以前の記事ではClaude CodeのAgent viewと比べる形で、Herdrを短く紹介しました。この記事の前半は、Herdrを日常使いのツールにするための操作と注意点です。後半は、そこから見えた仕事の変わり方と、Herdrが仕事のどこを受け持つのかを考えます。
確認した環境はHomebrewで入れたHerdr 0.9.5、Claude Code 2.1.318、codex-cli 0.166.0です。
このブログが良ければ読者になったり、nwiizoのXやGithubをフォローしてくれると嬉しいです。
日常で使うCLI
普段よく使うコマンドを用途ごとにまとめます。用語と、注意が必要なコマンドの挙動は後の節で説明します。
Herdrのペインの中で実行すると、そのセッションに対して動きます。外から名前付きセッションを操作する時は、HERDR_SESSION=<name>を付けます。w2やw2:p1は例なので、herdr workspace listやherdr pane listで確かめた値に置き換えます。多くのコマンドはJSONを返すので、整形にはjqを使います。
起動と接続
herdr # 既定のセッションを起動、または接続する
herdr --session work # 名前付きセッションを起動、または接続する
herdr session list # セッションの一覧と状態
herdr status # クライアントとサーバーの状態とバージョン
herdr agent attach reviewer # 1つのエージェントの端末だけへ接続する
UIの中で、既定のprefixキーであるctrl+bの後にqを押すと切断します。herdr agent attachで接続した場合も同じ操作で抜けます。
状態と出力を見る
herdr agent list # エージェントと状態の一覧
herdr agent read reviewer --source recent-unwrapped --lines 80 # 直近の出力を読む
herdr agent explain reviewer # 状態の判定理由
herdr workspace list # workspaceの一覧
herdr pane list --workspace w2 # workspace内のペイン
agent readはフォーカスを移さずに出力を読めます。読むだけならdoneのままで、idleに変わりません。
ペインとエージェントを動かす
herdr pane split w2:p1 --direction right --no-focus # 右に分割（フォーカスは動かさない）
herdr pane run w2:p3 "cargo test" # シェルでコマンドを実行
herdr pane wait-output w2:p3 --regex "test result" --timeout 120000 # 出力に文字列が出るまで待つ
herdr agent start reviewer --kind codex --pane w2:p2 # シェルのペインでエージェントを起動
herdr agent prompt reviewer "差分をレビューして" --wait --timeout 600000
herdr agent wait lead --until blocked --timeout 120000 # 承認待ちになるまで待つ
herdr agent send-keys lead esc # 画面を読んだ上でキーを送る
herdr agent rename w2:p1 lead # 手で起動したエージェントに名前を付ける
pane wait-outputは、すでに画面にある出力にも一致します。スクリプトから使う時の注意は、「別のエージェントから操作するときは、待ちと完了を分ける」の節の最後にまとめています。
worktree
herdr worktree create --workspace w2 --branch feature-x --no-focus
herdr worktree list --workspace w2
herdr worktree remove --workspace w4 # チェックアウトを消す。ブランチは残る
設定と保守
herdr --default-config # 既定の設定を表示する
herdr config check # config.tomlを検証する
herdr server reload-config # 動いているサーバーへ設定を反映する
herdr integration status # integrationのバージョンを確かめる
herdr integration install codex # integrationを入れる、入れ直す
herdr plugin list # 入っているplugin
止める
herdr session stop work # 名前付きセッションを止める
herdr session stop default # 既定のセッションを止める
herdr server stop # 接続先のセッションを止める（ペインの中ならそのセッション）
止めるコマンドはペインのプロセスを終わらせます。止めるセッションに対してherdr agent listを実行し、動いているエージェントがいないかを確かめてから使います。エージェントによっては、バックグラウンドの処理が残っていてもidleになるので、idleだけを見て止めてよいとは判断しません。
Herdrの構成要素
Herdrの構成要素は5つあります。この5つを意識するだけで、Herdrが何をしていて、画面の裏がどうなっているのかが、かなり分かりやすくなります。
5つは外側から順に入れ子になっています。いちばん外のsessionはサーバーそのもので、端末を閉じても作業が続くのは、ペインをこのサーバーが持っているからです。workspaceはサイドバーの1行にあたり、その中をtabとpaneで、見慣れた端末と同じように分けます。agentだけは性質が違い、Herdrがペインの中のプロセスを見て見つけ出したものです。サイドバーの色が付くのはこのagentで、その色がpane、tab、workspaceへと外側に集まっていきます。
CLIもこの5つの名前で分かれています。herdr workspace list、herdr pane split、herdr agent promptのように、何を操作したいかの単位を選べば、使うコマンドはほぼ決まります。止める操作も同じです。herdr server stopはsessionごと、herdr workspace closeはそのworkspaceのペインごと、プロセスを終わらせます。迷った時は、いま触っているのが5つのどれかを考えると、何が消えて何が残るかを判断できます。
切り替え方
session以外の単位は、マウス、キー、CLIのどれでも切り替えられます。キーは、prefixキー（既定はctrl+b）を押して離してから、次のキーを押します。
セッションだけは画面の中で切り替えず、接続し直します。名前付きセッションは別のサーバーなので、別のセッションのworkspaceはサイドバーに並びません。
sessionとworkspaceの分け方
公式資料は、まずworkspaceで分け、名前付きセッションは完全に分けたい時だけ使うよう案内しています。私も普段の切り替えはworkspaceとGo toピッカーで済ませ、普段の作業と分けて試したい時だけ、herdr --session demoのように名前を付けて起動します。

1. ルールが増えるほど AI は判断を誤る
1.1 「だいたい合っている」では困る仕事
LLM を使った AI エージェントは、人の言葉を受け取って道具（tool）を呼び、仕事を進めてくれます。ところが、業務ルールが複雑になると様子が変わります。金融の窓口業務なら、こういった規則が並びます。
- 振込手数料は原則として依頼人負担
- ただし同一名義の口座間の振替は無料
- 一定額を超える振込は、当日中の受付を締め切ったあとは翌営業日扱い
- 組戻し（振込の取り消し）の返金先は、原則として引き落とし元の口座
プロンプトに業務ルールを書き足しても、規則が増えるほど読み落としや取り違えが起きます。
1.2 連続 8 回だと成功率は 25% に落ちる
この「ぶれ」の大きさは、公開ベンチマークで確かめられています。測るために作られたのが τ-bench です（τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains）。
τ-bench が広めた指標が passk です。同じ課題を k 回やらせて、k 回とも成功して初めてよしとします。業務システムに求められるのはこちらです。たまたま一度うまくいく能力より、何度やっても同じように正しく動く再現性が欲しいからです。
gpt-4o の小売ドメインでは、pass1 が約 61% なのに対し、pass8 は約 25% まで落ちます（Sierra のベンチマーク解説、および上記論文）。
もとの 4 割ほどまで下がります。モデルが賢くなれば解決する問題ではありません。確率的に動くものを決定的に動かしたい、という構造の問題です。
1.3 命令型だけでは守りきれない
「それなら業務ルールは全部命令型のプログラムで書けばいい」と思われるかもしれません。従来の業務システムはそうしてきました。条件分岐の多い命令型のコードで、確実に、毎回同じように動きます。この形には 2 つの限界があります。
1 つ目は、客の言い換えや同意のような曖昧な入力を扱えないことです。「やっぱりあっちの口座から払うほうがいいかも」は引き落とし元の変更依頼なのか、まだ迷っているだけなのか。こうした解釈は人間の言語の領域で、決定論的なプログラムが最も苦手とします。
2 つ目は見落とされがちです。命令型で書いても、保証されるのは API の中だけで、API と API のあいだをつなぐロジックは保証されません。AI エージェントも、同じこのロジックで誤ります。API と API のあいだに、確率的なトークン生成が入り込むからです。
LLM は柔軟ですが安定しません。決定論は安定していますが柔軟ではありません。だから、どちらを選ぶかより、どこで切り分けるかを考えました。

規則の例の続き
組戻しの返金先は、原則として引き落とし元の口座ですが、その口座がすでに解約されている場合は、本人確認のうえ別の口座へ返します。
AI エージェントに任せられる仕事の代表例
カスタマーサポートの自動化は、LLM を使った AI エージェントに任せられる仕事の代表例です。「先週の振込を取り消したい」と言われたら、取引履歴を検索し、組戻しが可能かを確かめ、返金処理を実行する。一連の流れを自然言語のまま任せられるのは、ほんの数年前には考えられませんでした。
τ の語源と採点のしかた
τ は Tool-Agent-User、つまり道具・エージェント・ユーザーの三者のやりとりを指します。τ-bench は、LLM が演じる「客」とエージェントを対話させ、会話が終わった時点のデータベースが正解の状態と一致しているかで採点します。
pass@k との対比
よく使われる pass@k は「k 回試して 1 回でも成功すればよし」という甘い指標です。passk は、同じ課題を k 回やらせて k 回とも成功して初めてよしとします。試行のたびに客の言い回しは変わりますが、課題そのものは同じです。gpt-4o の小売ドメインの結果は、厳しいものでした。
曖昧な入力の例
手数料を説明したあとの「はい、それでお願いします」は、手数料込みの送金への同意なのか、話の流れで出ていた口座解約への同意なのか。決定論的なプログラムには、この区別がつきません。
API と API のあいだは、GUI でも人が埋めている
命令型のプログラムで書いても、保証されるのは API の中だけで、API と API のあいだをつなぐロジックは保証されません。GUI がその例です。一連の手続きが 1 クリックで終わることはまずなく、振込画面と手数料の確認画面を行き来しながら操作することになります。画面と画面のあいだで何をするかは、人間が判断しています。GUI の側には誤解なく表示する責任がありますが、誤解を招く表示も珍しくありません。API コールで自動化しても事情は同じで、API と API のあいだをつなぐ処理の品質は実装した人次第です。外部 API を叩く処理でバグを出すのは、誰しも身に覚えがあるはずです。
1.4 業務の公理系を渡して、証明させる
客の依頼に対して、受付命題を作成します。受付命題は「この会話の事実は、客の目的を満たしている」という 1 文で、途中の手続きは書きません。
業務ルールは、Lean の公理系（module）として AI に渡します。AI はその公理を組み合わせて、受付命題を結論とする受付定理を組み立て、証明します。証明が正しいかを判定するのは、AI ではなく処理系です。公理系から導けないものは、コンパイルを通りません。通った定理を実行すると、命題を真にするのに足りない事実が出てきます。
受付定理を運用時に証明して実行するので、ルールに準拠した処理を、会話のたびに組み立てられます。従来の API で運用時に選べるのは関数と入力だけでしたが、この形では関数の組み立てそのものを運用時に行えます。何をどう組み立てても、公理系から導けないものは実行されません。業務ルールへの準拠と自由度の拡張は、トレードオフになりません。
証明の検査と実行に使う定理証明支援系（Lean）は 2 節で、従来の API との違いは 3 節で述べます。
2. 型が命題、実装が証明
定理証明支援系は、定理とその証明をプログラムとして書き、証明が正しいかを機械に検査させる言語と処理系です。Lean はその一つで、今回もこれを使っています。
Lean では、命題を「型」として書きます。その型を持つ値、つまり実装が、命題の証明です。実装が型検査を通れば、命題がすべての入力について成り立つことを機械が確かめたことになります。検査するのは、コンパイラの中核にある小さなプログラム（カーネル）です。人が書いた証明でも AI が書いた証明でも、検査に通れば、その定理は正しいと保証されます。
偽の命題は、証明できません。たまたま通るケースだけ書く、モックで固める、といった小細工が効かないからです。型検査器は入力の分布を見ておらず、すべての入力について成り立つ証拠を要求します。証明せずに通す方法は、公理（axiom）を足すか sorry で済ませるかの 2 つだけで、どちらも機械的に分かります。sorry には警告が出ますし、#print axioms 定理名 と打てば、その定理が依存しているものを列挙できます。AI に書かせるときの安心材料は、ここです。
証明の対象にできるのは、純粋で、必ず停止する関数です。DB の読み書きのような副作用は、Lean の外側、受付エージェントの側に置いています。

Blender's user interface, as a library you can use from Python, Rust, JavaScript (React, Svelte), C, C++ and Dear ImGui.
People spent decades building and optimizing Blender's GUI. It's battery and memory efficient, and super duper fast. We decoupled it, to give everyone a chance to build their own products with it. It supports multiple languages and frameworks, so you won't miss a beat!
Website and full documentation: bui.preetham.top · Chat: Discord

BUI takes the user interface of Blender (its widget drawing, its interaction rules and its look) and turns it into a standalone UI library with a small C core. Your code builds the widget tree and handles callbacks. Layout, input, drawing and presenting all happen in fast native code, on the CPU or the GPU.
At the heart of BUI is the kit: a small runtime written in C. The kit holds every widget in one tree, lays them out, handles the mouse and keyboard, and draws them the way Blender does. The drawing code is a C port of Blender's own widget code, and the interaction follows Blender's rules. On top of the kit sit bindings: thin layers that let Python, Rust, JavaScript, C++ and Dear ImGui talk to it.
What BUI is not:
- Not Blender. It contains the parts of Blender's UI code it needs and builds on its own. You don't need Blender installed, and you don't need to know Blender to use it.
- Not a browser. The Rust and JavaScript sides use HTML and CSS as a UI language, but there's no browser engine, no webview and no network.
- Not a re-imagining. The widget drawing is ported from Blender's
interface_widgets.cc, and the Dear ImGui support runs the real Dear ImGui.
Blender's interface is famous for how it feels. You press a number field and
drag: the cursor vanishes, the value glides under your hand, and you never hit
the edge of the screen. You type 2*pi into a field and it just works. You
type "ad cu" into a menu and it finds "Add Cube". Millions of artists have
these habits in their hands.
That interface is also fast and frugal. It redraws only what changed, sleeps when nothing does, and starts in milliseconds. BUI exists so that any app, in any language, can have both: Blender's feel, and Blender's efficiency.
- You have a tkinter app and wish it looked less like 1998. Run it on BUI, unchanged.
- You're building a tool for artists who already know Blender. Give them the panels, sliders and shortcuts their hands expect.
- You write Rust or React and want a native desktop UI without shipping a browser.
- You use Dear ImGui and want it to look and feel like Blender, with one build flag.
- You're curious how a UI toolkit works. The source is readable, and the concepts are explained in plain words.

不正アクセスは、外部の攻撃者がインターネットから不正にアクセスし、複数のシステムが有機的に連動する仕組みを悪用した攻撃により、利用者の情報を機械的に検索・取得するというもの。
ドコモでは、不正アクセスの判明後、ドコモオンラインショップおよびMy docomoを停止したが、停止前の時間で流出してしまったという。
不正アクセスは、4日10:30に大量アクセスのアラートを検知し、対策を開始。14:30に海外IPアドレスを遮断したが効果がなく、16:20にMy docomoをメンテナンスモードとした。特定攻撃経路を遮断し、一旦20:32にMy docomoメンテナンスから復旧したものの、不正アクセスの可能性を検知したことから、翌5日1:05にMy docomoとドコモオンラインショップをメンテナンスモードとし、5日2:10に利用者情報の流出を確認した。
攻撃についてドコモでは「システム自体の脆弱性ではなく、複数のシステムを連動させた仕組みの悪用」と判断しているという。
定期的に脆弱性診断を行なっているが、「これまでの診断では特定できなかった攻撃経路。忸怩たる思いもあるが、システム自体のバグではない」(NTTドコモ 坪谷寿一副社長)と説明。AIエージェントを活用したかなどは、様々な面から確認しているが、「いわゆるAPI攻撃ではない」と説明している。

個人情報の流出にあたり、不審なメール・SMS等に記載されたURLにアクセスしたり、不審な添付ファイルを開いたりしないよう注意を呼びかけている。

なお、この事案については、不正アクセスの形跡やサイバー攻撃を示す事象はない。
今後の再発防止については、メモリ異常の発生を防ぐ暫定対処については実施済みで、メモリ異常状態を未然に解消する対処策を1週間以内に完了予定。

情報セキュリティの普及啓発に向けて活動する日本ネットワークセキュリティ協会（JNSA）は11月6日、同協会が運営する「情報セキュリティ理解度チェックサービス」が第三者による不正アクセスを受け、最大1万5128件の個人情報が漏えいした可能性があると発表した。利用者のIDやハッシュ化したパスワードなどが漏えいした可能性がある。同サービスは現在停止している。
情報セキュリティ理解度チェックサービスは、企業や団体が従業員の情報セキュリティに関する理解度を確認するためのもの。漏えいした可能性がある情報は利用者のIDやハッシュ化されたパスワードに加え、同サービスの受講を管理する担当者の指名、企業名、メールアドレス、組織所在地、従業員数、業種、利用ユーザー数も含まれる。
JNSAは4日に不正アクセスを確認。その後の調査で、10月30日夜ごろから攻撃を受けていた可能性があると分かった。発覚後は被害拡大を防ぐためサービスを停止し、外部専門事業者とともに原因や影響範囲を調査している。現時点で侵入経路は判明しておらず、漏えい件数も変動する可能性があるという。
対象者には特定でき次第個別に連絡する方針。11月6日中に個人情報保護委員会にも報告する予定だ。
また、漏えいした情報を悪用したなりすましメールが届く可能性があるとして、不審なメールのリンクや添付ファイルを開かないよう注意を呼び掛けている。

Googleは2026年10月12日（米国時間）、システムの信頼性を確保するための考え方や実践手法をまとめた書籍『Site Reliability Engineering: How Google Runs Production Systems』の第2版を発表した。2016年に初版が出版されたもので、それ以来10年ぶりの全面改訂となる。
SREは、ソフトウェアエンジニアリングの手法をシステム運用に適用し、信頼性の向上と運用の効率化を図る考え方だ。今回の第2版は、Google社内や業界全体で蓄積された10年間の知見を反映し、内容を全面的に書き直したという。
Googleは、SREの実践方法がこの10年間で、個別の手作業を中心とした運用から、プラットフォーム全体を対象とする自動化へと進化してきたと説明する。具体的には、次の6つの領域で変化があったとし、AI時代のSREに求められる「新たな役割」についても説明している。
2016年当時は、基本的な可用性指標と手動によるエラーバジェットの管理が中心だった。現在は、ユーザー視点の多層的なSLO（サービスレベル目標）を設定し、エラーバジェットの消費速度に応じた動的なアラートや、ポリシーの自動適用を取り入れる方向へ進化している。
従来は静的なダッシュボードやログの確認、アラートの手動調査が中心だった。現在は「OpenTelemetry」や分散トレーシング、異常の相関分析などを活用し、複雑なシステムで発生した障害の根本原因を迅速に特定する取り組みが進んでいる。
個別の作業を自動化するスクリプトから、Infrastructure as Code（IaC）による宣言的なインフラ管理や、社内開発者プラットフォームの活用へと変化した。障害発生時に自動で復旧する「自己修復」の仕組みも重視されている。
定期的な障害対応訓練や負荷テストだけでなく、継続的な耐障害性の検証、自動化されたテスト、本番環境で新バージョンを段階的に検証するカナリアテストなどが取り入れられている。
手動でのリソース割り当てや固定的な需要予測から、負荷に応じた自動スケーリングへと移行している。クラウドコストを管理するFinOpsとの連携や、GPU（Graphics Processing Unit）、TPU（Tensor Processing Unit）を利用するAIワークロードのコスト最適化も重要になっている。
特定のアプリケーションを担当する専任SREチームだけでなく、プラットフォームエンジニアリングとの連携や、各開発チームに信頼性の推進役を配置する体制など、組織横断的な取り組みが広がっている。
今回の改訂で新たに重視されているのがAIとの関係だ。Googleは、AI時代のSREには2つの役割があると説明している。
一つは、AIシステムそのものの信頼性を確保することだ。大規模なGPU、TPUクラスタの安定稼働や、AI特有の出力の不確実性、応答時間の監視、モデルの学習やファインチューニングに使用するデータ処理基盤の信頼性確保などが課題になる。
もう一つは、AIを活用してSREの業務を高度化することだ。例えば、生成AIによる障害の一次切り分けや事後分析の支援、自然言語による監視データの調査、機械学習を利用したリソース不足の予測などが挙げられている。
一方、Googleは、技術やシステム構成が変化しても、SREの基本原則は変わらないと強調する。信頼性を重視する組織文化や、人間同士の協力を含む人的な要素は、引き続き重要だという。
システムの複雑化とAIの普及によって、運用担当者に求められる技術や役割は変わりつつある。しかし、単に新しいツールを導入するだけでは、システムの信頼性は確保できない。運用の仕組みや組織体制を含めて見直すことが、今後のSREを実践する上で重要になる。

ソニーは、1979年に発売した初代ウォークマン「TPS-L2」にも付属したヘッドフォン「MDR-3」シリーズを現代のライフスタイルに合わせて再現したUSB-Cヘッドフォン「MDR-3R」を11月20日に発売する。価格はオープンプライスで、市場想定価格は8,000円前後。
MDR-3シリーズの当時の設計を元に、ヘッドバンド形状や、音響特性を担うサウンドホール、「Dynamic Stereo Headphones」のマーキングや、ソニーロゴの加工まで再現しつつ、USB-Cコネクタや通話用マイク、リモコンを搭載して現代仕様としたオープン型のヘッドフォン。
1979年に発売したヘッドフォンをリバイバルすることで、若いユーザーには「本物のレトロヘッドフォン」という新鮮な体験を届けつつ、長年のソニーファンには懐かしさを感じられる製品としている。
ドライバーは、MDR-3と同じ23mm径ドライバーを採用。設計当時の情報を参考にしながら、オリジナルと同等の音質を実現するユニットを忠実に再現し、新規設計した。当時使用されていたサマリウムコバルト磁石を、今日では主流であるより磁力が強力なネオジウム磁石に変更し、高域の感度を向上かつ小型軽量化も図っている。
音質もオリジナルのMDRｰ3と全体的なバランスは同じ方向で再現しつつ、わずかに調整を加えてアップデート。低域/高域の伸びを持たせ、ワイドレンジ化を実現。さらに低域の量感を上げてトレンドの楽曲に対応したほか、中音域～中高域内のバランスをわずかに変化させることで、ボーカルの厚みや艶、クラリティを向上している。

電気で細菌を死滅させる歯ブラシが開発される、歯磨きの動きで発電するため電池不要
歯ブラシの毛が曲がる際に発生する電気を利用して、虫歯や歯周病の原因となる細菌を死滅させる歯ブラシを北京大学の研究チームが開発しました。電池を使わずに歯磨きの動作だけで発電する仕組みで、従来の歯ブラシよりも歯垢や歯茎の炎症を効果的に減らせることが実験で確認されています。
Self-charged toothbrush facilitates tooth healthcare maintenance | Science Advances
https://www.science.org/doi/10.1126/sciadv.aeg5744
Toothbrush zaps bacteria with electricity made when bristles move | Nature
https://www.nature.com/articles/d41586-026-03586-y
一般的な歯ブラシは、毛先で歯の表面をこすることで歯垢(プラーク)を物理的に除去します。しかし、歯磨きだけですべての細菌を取り除くことは難しく、生き残った細菌が再び増殖して歯垢を形成することがあります。
北京大学のルー・ヤンホイ氏らの研究チームは、力を加えて変形させると電荷が発生する「圧電効果」を持つ素材を歯ブラシの毛に採用することで、歯垢を物理的に除去すると同時に細菌を殺菌する歯ブラシを開発しました。
研究チームが採用したのはポリフッ化ビニリデン(PVDF)というプラスチック素材で、PVDFを引き伸ばして加熱することで圧電特性を持たせました。このPVDF製の毛を採用した歯ブラシで歯を磨くと、毛先が曲がるたびに電荷が発生します。発生した電荷は唾液や水分と反応し、反応性の高い活性酸素を含む物質を生成します。この物質は細菌の細胞膜を傷つける働きがあり、歯ブラシでこするだけでは除去しきれない細菌にも作用するというわけです。また、毛先には静電的な性質もあり、細菌が付着するのを抑える効果が期待されています。
研究チームはまず、虫歯の原因菌として知られるミュータンス菌と、歯周病に関係するジンジバリス菌を使って殺菌効果を検証しました。その結果、新しい歯ブラシの毛はミュータンス菌の約53％、ジンジバリス菌の約78％を死滅させました。一方、同じ条件で一般的なナイロン製の毛を使った場合だと殺菌率はそれぞれ約9％と約8％でした。
さらに、人間の口腔内から採取した歯垢を牛の歯のエナメル質上で培養し、歯磨きによる除去効果を比較しました。3分間のブラッシングで従来のナイロン製歯ブラシの除去率が約80％だったのに対して、新しい歯ブラシは歯垢の99％以上を除去することに成功したとのこと。
研究チームは実際の人間に対する効果も調べています。歯垢の蓄積や歯茎の炎症がある成人115人を対象に臨床試験を実施し、最終的に109人のデータを分析しました。参加者は新しい歯ブラシか従来のナイロン製歯ブラシを使用するグループに分けられ、3カ月間にわたって1日2回の歯磨きを続けました。
その結果、新しい歯ブラシを使用したグループでは、歯垢の蓄積や歯茎の炎症、出血に関する指標が約40％改善しました。一方、従来の歯ブラシを使用したグループの改善率は約15％でした。また、歯垢に含まれる細菌を遺伝子解析したところ、新しい歯ブラシを使用したグループでは口腔疾患に関連する細菌の割合が減少し、有益と考えられる細菌の割合が増加していました。
安全性についても予備的な検証が行われています。研究チームは、歯ブラシの素材が培養細胞に有害な影響を及ぼさないことや、歯磨きによって歯のエナメル質の表面が損傷しないことを確認しました。また、3カ月間の使用を想定した耐久試験でも、毛先の形状や発電性能が維持されました。
研究には参加していないニューヨーク州立大学バッファロー校の歯学者であるフランク・スカナピエコ氏は電荷が発生する新しい歯ブラシについて、「歯磨きの動きから電気を生み出す仕組みは、従来の発想に新しい工夫を加えたもの」と評価しています。その上で、実際の有効性や安全性を証明するにはさらなる試験が必要だと指摘しました。
今回の臨床試験は3カ月間と比較的短く、虫歯や歯周病そのものを長期的に予防できるかは確認されていません。製造コストや長期使用時の安全性についても検証が必要です。研究チームは今後より長期間の追跡調査を実施し、新しい歯ブラシが口腔の健康維持にもたらす効果を詳しく調べる方針です。
