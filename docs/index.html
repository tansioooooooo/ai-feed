Electricity generation per person in the United Kingdom has fallen by a third from its early-2000s peak
Globally, electricity generation per person has grown by more than 50% this century.
In the United Kingdom, things have moved in the opposite direction. Its generation per person peaked in 2003 and has fallen by more than a third since then.
You can see this in the chart, which shows generation per person since 1920. Today, levels are back to where they were in the late 1960s.
Some of that decline is a change in electricity imports, rather than demand: net imports have increased from 1% of electricity demand in 2010 to 9% in 2025. But it’s still true that the UK consumes much less electricity than it used to.
The most common explanation is deindustrialization: as the economy shifted from manufacturing to services, electricity demand fell. That’s part of the explanation, but far from all of it.
Sectoral data from the International Energy Agency confirms that electricity consumption in industry has fallen by one-quarter since 2005 (more if we calculate this per person). But residential and commercial electricity use has fallen by just as much.
Deindustrialization has reduced demand, but improvements in energy efficiency — such as the shift from incandescent to LED lightbulbs and the introduction of efficiency standards for appliances — have played an important role too.

[BUG] bionic: wcscspn()/wcspbrk() treat every wchar_t >= 0x100 as a match (Android 17, CP3A.260905.009) #2260
Description
Description
On Android 17 builds from September 2026, wcscspn() and wcspbrk() stop at the first character of the string that is >= U+0100 whenever the reject set has two or more characters that are all < U+0100. The character is reported as a match even though it is not in the set. wcsspn(), wcschr(), wcsrchr(), wmemchr() and wcsstr() are correct.
Any code that scans wide strings for ASCII delimiters, for example newline or wildcard characters, breaks as soon as the text contains an emoji, CJK, Cyrillic, Greek or Latin Extended character.
Affected / unaffected
The public android17-release sources (android-17.0.0_r1, June 2026) build wcscspn/wcspbrk from external/llvm-libc, which is a plain nested loop over wchar_t and is correct. The code on the September builds is different (see "Mechanism"), so the regression was introduced between the June and September releases.
Reproducer
Build with the NDK (aarch64-linux-android30-clang), push to /data/local/tmp, run with adb shell:

Mechanism (from the shipped libc.so)
Disassembly of wcscspn in /apex/com.android.runtime/lib64/bionic/libc.so on CP3A.260905.009 shows three paths selected by the set:
- One character: a plain compare loop. Correct.
- Two or more characters: a 256-byte bool table on the stack is filled from the set while the set characters are in 1..0xFF. If a set character >= 0x100 is seen, the function falls back to calling wcschr() for each haystack character. Correct.
- Otherwise the haystack is scanned against the table:
a2564: ldrb w8, [x9, x8] ; table[c]
a2568: tbnz w8, #0, a2578 ; in set -> stop (correct)
a256c: ldr w8, [x22, #0x4]! ; next character
a2570: cmp w8, #0x100
a2574: b.lo a2564 ; c < 0x100 -> keep scanning
a2578: ... ; c >= 0x100 -> STOP, reported as a match
A character >= 0x100 cannot be in a set whose members are all < 0x100, so for wcscspn the scan must continue past it. The code stops instead. wcsspn has the same structure, and there stopping is the correct answer (the character is not in the keep set), which is why only the complement functions are wrong. wcspbrk is implemented on top of this scan and inherits the bug.
The existing bionic test TEST(wchar, wcspbrk) in tests/wchar_test.cpp only uses ASCII input, so it does not catch this. A test such as EXPECT_EQ(3u, wcscspn(L"aĀb\n", L"x\n")) would.
Real-world impact
Visual Pinball on Android (libwinevbs, a Unix build of Wine's vbscript engine) stopped loading any table whose VBScript source contains a comment with an emoji after the September update: the lexer uses wcspbrk(ptr, L"\n\r") to skip comments, got the position of the first emoji instead of the line end, and reported "Invalid character". FileSystem.MoveFolder likewise treated every path containing a character >= U+0100 as a wildcard pattern via wcspbrk(src, L"*?><").
Worked around downstream by replacing the calls with plain loops: vpinball/libwinevbs#41 (shipped in vpinball/vpinball@e7837322f4).

2026年10月12日、フランスのE. Leclerc、Intermarche、Cooperative Uといった複数のスーパーマーケットチェーンがサイバー攻撃を受け、冷蔵庫の温度を強制的に上げられるという事件が発生しました。サイバー攻撃の標的となったのは、ダンフォスの温度管理システムを搭載した冷蔵庫です。
ハッカーがサイバー攻撃でスーパーの冷蔵庫を50℃まで加熱 - GIGAZINE
Team82によると、今回のサイバー攻撃の標的となったのは多くのスーパーマーケットに設置されている冷凍庫および冷蔵庫を一元管理するための制御装置コントローラーの「AK-SM 800A」です。製造元のダンフォスは制御コントローラーの製造メーカーとしては世界最大手で、AK-SM 800Aはスーパーマーケットだけでなく商業施設などでも広く利用されているとのこと。
AK-SM 800Aでは、単一の管理画面から冷凍・冷蔵回路の監視を行ったり、温度のしきい値を設定したり、過去のアラーム履歴を確認したり、運転スケジュールを調整したり、通知について設定したり、ユーザー権限を管理したり、遠隔で保守作業を行ったりすることが可能です。
また、AK-SM 800Aにはウェブ上から接続機器を管理することが可能な組み込み型の管理インターフェースもあります。この管理インターフェースでは、ウェブ上から接続機器をコントロールできるため、ユーザー企業側は保守コストを大幅に削減することが可能です。
このウェブ管理インターフェースに複数の脆弱性が存在するとTeam82は指摘。Team82が発見した脆弱性は「CVE-2025-41450」「CVE-2025-41451」「CVE-2025-41452」の3つ。
CVE-2025-41450は、ウェブ管理インターフェースに日替わりでアクセス用のパスワードを自動生成する「check_code_of_day」というアルゴリズムが利用されていたというもの。管理者向けのパスワードを知らなくても、ユーザー名に「admin」、パスワードに「本日の日付」を入力するだけで、ウェブ管理インターフェースにアクセスできてしまいました。
CVE-2025-41451は、リモートコード実行につながる「コマンドインジェクションに関する脆弱性」です。AK-SM 800Aのウェブ管理インターフェースではシェルコマンドに埋め込まれるフィールドの値に、サニタイズ(危険な入力の除去や無害化)が行われていないため、OSのシェルへの指示を含めることが可能となっていたそうです。つまり、攻撃者が制御する別のコマンドを続けて実行させられるようになっていました。
CVE-2025-41452は、認証済みユーザーがウェブサーバーソフトウェアであるNginxに、任意の設定ディレクティブ(動作を指定する命令)を挿入できるという問題です。Team82の調査により、Nginxにはファイルを置き換え、稼働中の外部向けNginxインスタンスに設定を再読み込みさせる機能がありました。つまり、機器を再起動せずに、新しい設定ディレクティブを適用することができるようになっていたわけです。
攻撃者がCVE-2025-41452を悪用すれば、インターネット上に公開されているNginxの設定に、任意のルーティング指示(リクエストの処理先を決める設定)を埋め込むことも可能。これにより、攻撃者はウェブサーバーによるリクエストの処理方法を変更し、機器と通信するクライアントの動作を操作できる可能性がありました。
なお、Team82はダンフォスに3つの脆弱性を報告済みで、同社はすでにファームウェアアップデートで問題を修正済みです。今回被害を受けたのは、アップデートが既に提供されなくなっている旧世代の製品だったと伝えられています。

お絵描きアプリ「ibisPaint」（アイビスペイント）で知られる（株）アイビスは10月12日、オフィススイート「ibisOffice」を公開した。「GitHub」でホストされているオープンソースプロジェクトで、ライセンスは「AGPL-3.0」。
ibisPaintの姉妹製品ibisOfficeがリリースされました！無料オープンソースオフィススイートです。Windows, Macユーザーはお試しください👍️
— アイビスペイント ibisPaint (@ibisPaint)October 12, 2026
「ibisOffice」は「Word」（.docx）、「Excel」（.xlsx）、「PowerPoint」（.pptx）のドキュメントを表示・編集・保存できるフリーのオフィススイート。同日公開の初版v0.8.0はmacOS専用だったが、続くv0.8.1ではWindows版（64bit）を追加。Webブラウザーで体験できるプレイグラウンドも用意されている。
特徴は、すべて「Rust」言語で書かれていること。UIフレームワークには高速なエディター「Zed」のために開発された「GPUI」を採用しており、Windows環境では「DirectX」、macOS環境では「Metal」、Webブラウザーでは「WebGPU」を介して、レンダリングにGPUを活用する。
目標は「Microsoft Office」アプリで作成したドキュメントを開いても見た目が崩れないことだそうで、行の折り返しやページの区切り、表の罫線、グラフの目盛りまで、「Office」と同じ結果になるよう作られているという。これを支えるのは7万を超えるテストコードで、本物の「Word」「Excel」「PowerPoint」が書き出したPDFと「ibisOffice」の描画を画素単位で比べ続けることで実現されている。また、「ibisOffice」で保存したドキュメントを「Office」で修復なしに開けることも、テストで確かめているとのこと。
現時点で対応している機能としては、以下が挙げられている。
- 文書（.docx）：段落とスタイル、箇条書きと段落番号、表、段組み、縦書き、ルビ、脚注、ヘッダーとフッター、フィールド（ページ番号・目次）、図形・画像・グラフ、ページ設定
- 表計算（.xlsx）：数式と関数の計算、条件付き書式、オートフィルター、並べ替え、テーブル、ピボットテーブル、グラフ、スパークライン、入力規則、シートの保護、ゴールシークなど
- プレゼンテーション（.pptx）：図形・テキスト・表・グラフ・SmartArtの表示と編集、アニメーション、画面切り替え、スライドショーと発表者ビュー（2画面対応）、動画・音声、コメント
- マクロ付きのファイル（.docm/.xlsm/.pptm）：開いて保存できる。マクロは実行せず、そのまま残す
まだ未対応の機能も残されているが、今後の改善に期待したい。
そのほかにも、動作が高速であることも本ソフトの特徴と言えるだろう。開発元が公表したベンチマークでは、ファイルを開いて最初の画面が表示されるまでの時間が「Microsoft Office」「LibreOffice」「ONLYOFFICE」のいずれよりも短かったという。22シート・29グラフ・58万9,000個の数式を含むExcelのブック（13.7MB）の場合、「ibisOffice」は0.52秒で、「Microsoft Office」は14.07秒、「LibreOffice」は6.82秒、「ONLYOFFICE」は9.36秒だった。
お絵描きアプリの会社がなぜ突如オフィススイートを開発したのか不思議に感じられるが、同社はファイルの保存・共有サービス「ibisStorage」を提供しており、そこでオフィス文書をプレビューしたいというのがきっかけだったようだ。オンラインでのプレビューと編集を、速く、正確に、サーバーに負荷をかけずに行えるようにと試行錯誤した結果、「ibisOffice」が誕生したわけだ。
なお、「ibisOffice」は無償で利用できるが、製品やサービスに組み込む企業を対象に有償の商用ライセンスを用意しているとのこと。マネタイズはこの商用ライセンスで行う方針のようだ。

AIエージェントによるウェブサイトへの攻撃の注意喚起
AIエージェントによる攻撃を観測しました
皆様おそらくご存知のとおり、2026年9月頃からウェブサイトやウェブアプリケーションで立て続けに情報漏洩が報告されています。マクニカさんやJPCERT/CCから情報が出されています。
Scutumでは10月10日の夜より、これらの攻撃がAIエージェントによるものなのかを調べる仕組みを導入し、監視を実施しました。その結果、10月14日までに、少なくとも3つのIPアドレスからAIエージェントによる日本の企業のウェブサイトへの攻撃が実施されていることを確認しました。
AIエージェントによる攻撃を特定する手法
どのように「攻撃元がAIエージェントかどうかを見分けるのか」については公表してしまうと対策されてしまうため詳細についてはここではご説明できません。この点については申し訳ありません。
基本的には以下を踏まえ開発された手法です。
- AIエージェントはcurlやsqlmap、あるいは自身が生成したPython等のコードを使って攻撃してくる
- その際、それらの具体的なプロセスが実行された結果や出力(ウェブサーバ側の反応)を読み取り、必要に応じて次のアクションを軌道修正する
- AIエージェントは賢く柔軟性がある
- AIエージェントは目的を達成しようとする強いモチベーションがある
- AIエージェントの判断は速い
これらの点を逆手に取り、従来(AI以前)の「シンプルに決められたリクエストを単に連続して送ってくるタイプ」の攻撃ツールや単純にcurlやsqlmapを実行するだけの場合とは異なる流れが発生するよう、WAFの挙動を変更しました。
本番に投入する前に、手元の開発環境でこの仕組みでAIエージェントを検出できるかを確認したところ、試した8種類のモデルすべて（どれも最近リリースされた高性能のもの。Qwen 3.8 Flash NextやGLM-5.3 Flash Nextを含む)でうまく検出できました。モデルが賢いほど、今回の仕掛けはうまく動作するようになっています。攻撃者が実際に使っているモデルが何なのかという情報は取得できませんが、今回の仕組みが検知した場合、攻撃者がAIエージェントを使っていることは断定できる(false negativeはあるかもしれないが、false positiveはほぼない)ロジックになっています。つまり「漏れなくAIエージェントを列挙することはできないが、もし検知した場合は間違いなくAIエージェントである」という性質の仕組みです。

対策をどうするべきか
ウェブアプリケーションやウェブサイトにおけるセキュリティ対策は、攻撃者がAIエージェントを使っているかどうかによって大きく変わることはありません。事前に漏れなく(アプリケーションのバックエンドのAPIなども含めて)脆弱性がない状態にする。必要に応じてScutumのようなシグネチャのみに依存しない、分類の性能がよいWAFを導入することが有効です。株式会社セキュアスカイ・テクノロジーでは今回の一連の攻撃を踏まえこちらの実践ガイドを公開しておりますので、ぜひ参考にしてください。
また、筆者は2026年10月23日のSecurityDays 2026秋（東京）でAI時代のWAF論について講演させていただきますので、興味がある方はぜひ参加いただければと思います。

もっか線引きが問題となっているのは、ゲーム内のアート素材、物語やゲームデザイン、音声・音楽などの創作性に直結する領域です。

宇宙ヤバイ！ベランダでアンドロメダ星雲が撮れるスマート望遠鏡DWARF mini
2026年10月14日 06:14
宇宙はヤバイ。どんな美辞麗句を重ねようとも、宇宙の凄さを完全に表現できない。となると、やはり「ヤバイ」という言葉が最も適切なのではないだろうか？ これは皆さんにも共感していただけることと思う。
そんな私達を惹きつけてやまない宇宙の魅力、美しさに迫ることができるアイテムが天体望遠鏡だ。しかし、天体望遠鏡というと、非常に大きく、かさばるものをイメージするのではないだろうか？特に天体の自動追尾や長時間露光、複数の画像を重ね合わせるスタッキング処理などに対応した製品となれば、大きいだけでなく、非常に高価という印象がある。
そこで今回レビューするのが、 世界最小のスマート望遠鏡 をうたう「DWARF mini」だ。ポケットサイズというとやや誇張表現だとは思うが、冬物ジャケットの前ポケットであれば無理なく携帯できるサイズを実現している。それでいて天体の自動捕捉(自動導入)、自動追尾に対応し、35mm判換算で約1,016mm相当の超望遠撮影が可能だ。
直販価格は7万8,900円と決して安くはないが、最新のフラグシップスマホでも撮影が難しい天体写真を手軽に撮れるというのは大きな魅力だ。今回は本製品の実機を借用したので、主に使い勝手と、実際にどのような写真が撮れるのかにスポットを当てたミニレビューをお届けしよう。
重量840gのコンパクト筐体に望遠・広角カメラを搭載
DWARF miniの本体サイズは100.38×183.61×60.70mm、重量は840g。望遠カメラと広角カメラを搭載しており、35mm判換算の焦点距離はそれぞれ1,016mm、45mmだ。望遠カメラのレンズ口径は30mmで、イメージセンサーには約207万画素のソニー製CMOS「IMX662」(1/2.8型)を採用している。
本体には上下225度、左右360度に回転する電動機構を内蔵。スマートフォンとはWi-Fi、Bluetoothで接続し、専用アプリから操作する仕組みだ。また、64GBのストレージと7,000mAhのバッテリを内蔵しており、バッテリ駆動時間は最大約4時間とされている。USB Type-C端子から外部給電すれば、さらに長時間撮影することも可能だ。
実際に手にしてみると、個人的な感覚としては意外に大きく重い。筆者の身近なものでたとえると、M4のガスブローバックマガジン2個ぶん。皆さんの身近なものでたとえると、中身の入った800mL程度のシャンプーボトルといったところだろうか。
とはいえ、先ほどお伝えした通り、冬物ジャケットの前ポケットであれば十分収納できる。 これだけ小さな筐体に望遠・広角カメラ、電動回転機構、バッテリまで収めている のだから、携帯性は高いといえよう。
銀河や星雲から太陽、風景まで撮影できる5つのモードを用意
DWARF miniには「一般」「ディープスカイ」「太陽系」「天の川」「星の軌跡」という5つの撮影モードが用意されている。「一般」は風景や野鳥などの撮影用。「ディープスカイ」は銀河や星雲、星団などを撮影するモードで、露光した複数の写真を自動的に重ね合わせることで、肉眼では見えにくい淡い天体の姿を浮かび上がらせる。
「太陽系」は太陽や月などを撮影するモード、「天の川」は広角カメラで夜空に広がる天の川を撮影するモードだ。そして「星の軌跡」では、長時間にわたる星の動きを光の線として記録できる。 天体望遠鏡という名前からは想像できないほど、撮影できる被写体の幅は広い。 メーカーが「スマート望遠鏡」とうたうのも納得だ。
以下に、参考としてメーカー公式サイトに掲載されているサンプル画像をいくつか紹介しておこう。次の章では、筆者がこれらの作品にどこまで迫れるか試してみよう。
実際に筆者が撮影してみたらどうなった？
まずは練習ということで、昼間の望遠撮影を試してみた。35mm判換算で約1,016mm相当という焦点距離は、デジタルズームや超解像処理によるものではない。下記の望遠カメラと広角カメラの画角を見れば、超望遠の威力は一目瞭然だ。望遠カメラの解像感も高い。ただし、人工物の輪郭が不自然に歪んで見える箇所があった。
動画を撮影すると、その原因と思われる現象が確認できた。下記の動画を見ると、映像が全体的にゆらゆらと揺れている。この日は10月の快晴で、気温は24度。遠くの景色を超望遠で撮影したため、途中の大気の揺らぎ(陽炎)が目立ったと考えられる。バードウォッチングなどで遠くの被写体を撮影する際には、留意したい点だ。 天体撮影でも大気の状態は画質に影響するので、空気が安定した日を選びたい。
DWARF miniの望遠カメラで撮影した動画。大気の揺らぎと思われる映像のゆがみが確認できる
それではやっと本題。天体写真の撮影に挑戦しよう。今回は「アンドロメダ星雲(M31)」を狙ってみることにした。
撮影方法自体は想像以上に簡単だった。 専用アプリで「ディープスカイ」モードを選び、星図の検索欄から対象の天体を探して選択し、撮影を開始するだけ。本体の位置合わせ(キャリブレーション)、目標の天体への方向転換、自動追尾はすべて自動的に行なわれるので、撮影中は本体に触れる必要がない。操作はすべて専用アプリから行なえる。撮影時間は自由に決められるが、今回は約30分かけて撮影した。
ただし、今回1つ詰まった点がある。当初、露光時間を初期設定の15秒のままで撮影していたが、画像を重ね合わせる「スタッキング」に採用される画像が増えず、写真は暗く、周辺の星も線状に流れていた。そこで露光時間を5秒に短縮したところ、スタッキング採用率が大幅に改善。銀河の中心部だけでなく、周辺部分も見えてきた。

AI時代にアジャイルは時代遅れなのか
ソフトウェア開発のAI化が進む中で、アジャイルはもう“時代遅れ”なのでしょうか。そうした意見を、ちらほらと見かけるようになりました。
それらの声は、AIによる開発の速さや、開発ワークフローの変化を実感する中で生まれているようです。たとえば、前者がスクラムイベントをオーバーヘッドと感じさせ、後者がドキュメントや段階的プロセスの重要性を高めた、という主張です。
しかし、それらを理由にアジャイルを時代遅れとする見方は、アジャイルの本質を十分に捉えていないように感じます。むしろ、AI時代になって、アジャイルの重要性はより際立つのではないでしょうか。

2つの変化がアジャイル不要論を生んだ
冒頭で述べた、アジャイルは“時代遅れ”であるという2つの主張をもう少し詳しく掘り下げてみましょう。
まずは1点め。開発の速さから生じる「スクラムイベントのオーバーヘッド化」です。
アジャイル開発手法の代表格はスクラムだと思いますが、そのフレームワークでは5つのスクラムイベントが定められています。その一つである「スプリント」を繰り返し、その中で「スプリントプランニング」や「スプリントレビュー」といった残る4つのイベントが行われます。
AIによって開発が高速化したことで、これらのイベントや関連する管理作業が重く感じられるようになったようです。1〜2週間のスプリントが長すぎたり、コードを書くより会議やチケット管理に費やす時間の方が長い、という趣旨です。
これはアジャイルの歴史に対して強烈な皮肉です。アジャイルは、文書主導の重量級プロセスへの反省から、軽量級のプロセスを志向して登場しました。それが、今となってはその代表的なフレームワークが「重量級プロセスだ」と言われているわけですからね。
2点めの「ドキュメントや段階的プロセスの重要性が増した」とは、AIコーディングエージェントを活用する中で起きた変化です。
AIコーディングエージェントの生成品質を高めるための手法がこの2つです。曖昧な指示より、要件や制約を明確にしたドキュメントを渡すほうが、AIとの間での齟齬が減り、意図に沿った生成が期待できます。また、ワンショットで実装させるより、調査・仕様化から設計、実装と段階的に進めるやり方も、生成品質を高めるために用いられます。
こういったワークフローが、アジャイル開発手法と対比されがちな「ウォーターフォール」をエンジニアに想起させたようです。その結果、「アジャイルよりミニウォーターフォールだ」という主張につながったわけです。
アジャイルは特定の開発手法ではない
前節で書いた現場の変化は、エンジニアリングマネジメントを担う私も十分に共感できるものです。ただし、それはアジャイルが不要になったことを意味しません。
これは開発手法や開発ワークフローの変化であって、“ソフトウェア開発の考え方”の変化ではありません。この2つを区別しなければ、本質を見失います。なぜなら、アジャイルは“開発の考え方”だからです。決して、特定の“開発手法”ではありません。
たとえばスクラムは、アジャイルの考え方に沿ったフレームワークの一つです。これをチームに導入して適用することで、チームの“開発手法”として機能します。
もし、スクラムイベントがオーバーヘッドだと感じるなら、それは、スクラムを用いて実践する開発手法が、AI導入後の変化に合っていないのかもしれません。
それに、アジャイルは、ドキュメントや段階的なプロセスも否定していません。職能別の完全分業はアジャイルの原則に沿いませんが、短期間での段階的プロセスの反復は、アジャイル系の開発手法でも行われます。
アジャイルが示すのは、“初期の分析と契約に基づいて計画どおりにアウトプットすること”をゴールとする開発からの転換です。つまり、プロジェクトの不確実性を受け入れ、気づきや内外の変化に対して積極的に適応しよう、ということです。
アジャイル系の開発手法が、短期間のプロセスを反復する理由はここにあります。できる限り早く気づきを得たり、変化に気づいたりして、それを以降の開発に取り込むためです。
AIで得た速さが、アジャイルの実践を強化する
アジャイルは時代遅れどころか、本来志向していた“開発の考え方”の実践が、AIで獲得した“速さ”によって強化されたと言っても良いでしょう。
しかし、早く・速く作れることの恩恵は、「より早く、より多くの機能をリリースする」ことではありません。それだけを目指すと、ユーザーやビジネスにとって価値のないムダを大量生産しかねないからです。リリースした機能が使われなかったり、批判を浴びたりすること、ありますよね。
アジャイルの目指す、早く・速く作れることの本当の恩恵は、「高いアジリティの獲得」です。つまり、反復的・漸進的な開発とリリースによる、変化への適応性の向上や、価値を検証するフィードバックループの獲得です。
たとえば、計画どおりに作り上げたものと、同じ期間に何度も触って改善しながら作り上げたものとでは、異なる結果になり得ます。前者は計画期間の最終段階でようやく動くソフトウェアを触ることができます。後者は、初期段階から検証可能な最小限のソフトウェアに触れられます。
より正解に近いアウトプットを出しやすいのは後者でしょう。人間は、机上の分析だけで正解を引き当てることが苦手です。これは作る側の話だけではなく、使う側もそうです。自分たちが具体的にどういうものが欲しいのか、初めから明らかとは限りません。
プロトタイピングという手法は、こういった課題の解決策として、従来から用いられてきた手法です。
しかし、プロダクション版より簡易なプロトタイプといえど、実際に動くソフトウェアで実現するにはコストを要していました。だから、ペーパープロトタイプなどの静的なもので実現したり、対象を厳選したりして、コストと検証の充実度に折り合いをつけてきました。
AIは、このプロトタイピングに要するコストと時間を大幅に削減できるようにしたのです。本番稼働に必要な内部品質を満たすことを前提としない、使い捨てのプロトタイプです。
こうしたプロトタイピングはアジャイルとは別の話だと思うかもしれません。あくまでもプロトタイプのコードを書いているだけであって、プロダクションコードを反復的・漸進的に書いているわけではないからです。
しかし、検証を繰り返してプロジェクト初期の不確実性を減らし、仕様への理解を深めていくという点では、アジャイルの考え方に沿っています。
私の観察ではむしろ、ユーザー価値の断面でプロダクションコードを反復的・漸進的に作り上げていくことは、難易度が高かったように思います。どの断面で切り取って作るかの判断も難しいのですが、同時に内部構造をどこまで整えるかの判断が難しかったのです。
使い捨てのプロトタイプ開発では、特に後者の悩みが軽減されます。
よりアジャイルに進化する
使い捨て前提でのプロトタイピングのハードルを一気に下げたのが、バイブコーディングです。人間がコードを自ら書いたり読んだりせず、動作を確認しながらAIコーディングエージェントに指示を繰り返し、ソフトウェアを作り上げる手法です。
バイブコーディングがプロトタイピングにもたらしたものは、コストや時間の削減だけではありません。職種を問わずプロトタイプ開発に参加しやすくなったことと、企画から開発へのハンドオフへの依存を減らしたことも、その恩恵です。
前者については、いまや企画担当者やデザイナーも、AIでプロトタイプ開発を担えるようになりました。サーバサイド開発を伴うと難易度が上がりますが、スマホやPCなど、端末側だけで完結するものならかなりの作り込みが可能です。
後者については、できあがったプロトタイプが仕様を具体的に伝える手段になります。ドキュメントが不要になるわけではありませんが、プロトタイプの動作やコードをもとに、プロダクションコードの設計の多くを導き出せます。
そして、そこで活躍するのもAIです。プロトタイプコードを、本番稼働に必要な品質を満たすプロダクションコードに書き換えて済むこともあるでしょう。
プロトタイピングには、企画担当者やデザイナーだけでなく、エンジニアも参加できます。プロトタイピングを中心に、AIが職種間の境界を越えやすくしたのです。
こうして職種を越えて一箇所に集まり、動くソフトウェアを囲みながら反復的に検証し、漸進的に価値を形作っていく。AI時代にアジャイルは不要になるどころか、私たちはAIというパートナーを得て、よりアジャイルに開発を進める手段を得たと言えるのではないでしょうか。

AIエージェントによるウェブサイトへの攻撃の注意喚起
AIエージェントによる攻撃を観測しました
皆様おそらくご存知のとおり、2026年9月頃からウェブサイトやウェブアプリケーションで立て続けに情報漏洩が報告されています。マクニカさんやJPCERT/CCから情報が出されています。
Scutumでは10月10日の夜より、これらの攻撃がAIエージェントによるものなのかを調べる仕組みを導入し、監視を実施しました。その結果、10月14日までに、少なくとも3つのIPアドレスからAIエージェントによる日本の企業のウェブサイトへの攻撃が実施されていることを確認しました。
AIエージェントによる攻撃を特定する手法
どのように「攻撃元がAIエージェントかどうかを見分けるのか」については公表してしまうと対策されてしまうため詳細についてはここではご説明できません。この点については申し訳ありません。
基本的には以下を踏まえ開発された手法です。
- AIエージェントはcurlやsqlmap、あるいは自身が生成したPython等のコードを使って攻撃してくる
- その際、それらの具体的なプロセスが実行された結果や出力(ウェブサーバ側の反応)を読み取り、必要に応じて次のアクションを軌道修正する
- AIエージェントは賢く柔軟性がある
- AIエージェントは目的を達成しようとする強いモチベーションがある
- AIエージェントの判断は速い
これらの点を逆手に取り、従来(AI以前)の「シンプルに決められたリクエストを単に連続して送ってくるタイプ」の攻撃ツールや単純にcurlやsqlmapを実行するだけの場合とは異なる流れが発生するよう、WAFの挙動を変更しました。
本番に投入する前に、手元の開発環境でこの仕組みでAIエージェントを検出できるかを確認したところ、試した8種類のモデルすべて（どれも最近リリースされた高性能のもの。Qwen 3.8 Flash NextやGLM-5.3 Flash Nextを含む)でうまく検出できました。モデルが賢いほど、今回の仕掛けはうまく動作するようになっています。攻撃者が実際に使っているモデルが何なのかという情報は取得できませんが、今回の仕組みが検知した場合、攻撃者がAIエージェントを使っていることは断定できる(false negativeはあるかもしれないが、false positiveはほぼない)ロジックになっています。つまり「漏れなくAIエージェントを列挙することはできないが、もし検知した場合は間違いなくAIエージェントである」という性質の仕組みです。

対策をどうするべきか
ウェブアプリケーションやウェブサイトにおけるセキュリティ対策は、攻撃者がAIエージェントを使っているかどうかによって大きく変わることはありません。事前に漏れなく(アプリケーションのバックエンドのAPIなども含めて)脆弱性がない状態にする。必要に応じてScutumのようなシグネチャのみに依存しない、分類の性能がよいWAFを導入することが有効です。株式会社セキュアスカイ・テクノロジーでは今回の一連の攻撃を踏まえこちらの実践ガイドを公開しておりますので、ぜひ参考にしてください。

[BUG] bionic: wcscspn()/wcspbrk() treat every wchar_t >= 0x100 as a match (Android 17, CP3A.260905.009) #2260
Description
Description
On Android 17 builds from September 2026, wcscspn() and wcspbrk() stop at the first character of the string that is >= U+0100 whenever the reject set has two or more characters that are all < U+0100. The character is reported as a match even though it is not in the set. wcsspn(), wcschr(), wcsrchr(), wmemchr() and wcsstr() are correct.
Any code that scans wide strings for ASCII delimiters, for example newline or wildcard characters, breaks as soon as the text contains an emoji, CJK, Cyrillic, Greek or Latin Extended character.
Affected / unaffected
The public android17-release sources (android-17.0.0_r1, June 2026) build wcscspn/wcspbrk from external/llvm-libc, which is a plain nested loop over wchar_t and is correct. The code on the September builds is different (see "Mechanism"), so the regression was introduced between the June and September releases.
Reproducer
Build with the NDK (aarch64-linux-android30-clang), push to /data/local/tmp, run with adb shell:
#include <stdio.h>
#include <wchar.h>
int main(void)
{
wchar_t s[] = {'a', 0x1F680, 0x100, 'b', 'x', '\n', 0};
printf("wcscspn(s, L\"x\\n\") = %zu (expected 4)\n", wcscspn(s, L"x\n"));
printf("wcspbrk(s, L\"x\\n\") = index %ld (expected 4)\n", (long)(wcspbrk(s, L"x\n") - s));
printf("wcsspn(s, L\"a\\U0001F680\") = %zu (expected 2)\n", wcsspn(s, L"a\U0001F680"));
return 0;

wcscspn(s, L"x\n") = 1 (expected 4)
wcspbrk(s, L"x\n") = index 1 (expected 4)
wcsspn(s, L"a\U0001F680") = 2 (expected 2)
A sweep of every code point from U+0001 to U+10FFFF (skipping surrogates and the two set members) with wcscspn(L"<cp>\n", L"x\n") returns 0 instead of 1 for 1,111,808 code points: every one from U+0100 to U+10FFFF. U+0001 to U+00FF are correct.

Mechanism (from the shipped libc.so)
Disassembly of wcscspn in /apex/com.android.runtime/lib64/bionic/libc.so on CP3A.260905.009 shows three paths selected by the set:
- One character: a plain compare loop. Correct.
- Two or more characters: a 256-byte bool table on the stack is filled from the set while the set characters are in 1..0xFF. If a set character >= 0x100 is seen, the function falls back to calling wcschr() for each haystack character. Correct.
- Otherwise the haystack is scanned against the table:
a2564: ldrb w8, [x9, x8] ; table[c]
a2568: tbnz w8, #0, a2578 ; in set -> stop (correct)
a256c: ldr w8, [x22, #0x4]! ; next character
a2570: cmp w8, #0x100
a2574: b.lo a2564 ; c < 0x100 -> keep scanning
a2578: ... ; c >= 0x100 -> STOP, reported as a match
A character >= 0x100 cannot be in a set whose members are all < 0x100, so for wcscspn the scan must continue past it. The code stops instead. wcsspn has the same structure, and there stopping is the correct answer (the character is not in the keep set), which is why only the complement functions are wrong. wcspbrk is implemented on top of this scan and inherits the bug.
The existing bionic test TEST(wchar, wcspbrk) in tests/wchar_test.cpp only uses ASCII input, so it does not catch this. A test such as EXPECT_EQ(3u, wcscspn(L"aĀb\n", L"x\n")) would.
Real-world impact
Visual Pinball on Android (libwinevbs, a Unix build of Wine's vbscript engine) stopped loading any table whose VBScript source contains a comment with an emoji after the September update: the lexer uses wcspbrk(ptr, L"\n\r") to skip comments, got the position of the first emoji instead of the line end, and reported "Invalid character". FileSystem.MoveFolder likewise treated every path containing a character >= U+0100 as a wildcard pattern via wcspbrk(src, L"*?><").
Worked around downstream by replacing the calls with plain loops: vpinball/libwinevbs#41 (shipped in vpinball/vpinball@e7837322f4).

担保の株反映されず「保証金不足」と誤判定→ロスカット
FXは、預けた保証金の数倍の金額で外貨を売買できる取引。損失によって保証金が一定の水準まで減ると、証券会社はそれ以上損失が広がらないよう、まだ決済していない取引（ポジション）を自動で決済（ロスカット）する。
「株券担保サービス」は、証券口座で保有する株を現金の代わりに保証金として使えるものだが、今回、担保の株の評価額（代用評価額）が反映されない障害が発生。保証金が実際よりも少なく計算された結果、本来ロスカット対象にならない口座でも、保証金不足と誤って判定されてロスカットが行われた。
遅れて届いたファイルを再処理せず、評価額が反映されず

このウェブ管理インターフェースに複数の脆弱性が存在するとTeam82は指摘。Team82が発見した脆弱性は「CVE-2025-41450」「CVE-2025-41451」「CVE-2025-41452」の3つ。
CVE-2025-41450は、ウェブ管理インターフェースに日替わりでアクセス用のパスワードを自動生成する「check_code_of_day」というアルゴリズムが利用されていたというもの。管理者向けのパスワードを知らなくても、ユーザー名に「admin」、パスワードに「本日の日付」を入力するだけで、ウェブ管理インターフェースにアクセスできてしまいました。
CVE-2025-41451は、リモートコード実行につながる「コマンドインジェクションに関する脆弱性」です。AK-SM 800Aのウェブ管理インターフェースではシェルコマンドに埋め込まれるフィールドの値に、サニタイズ(危険な入力の除去や無害化)が行われていないため、OSのシェルへの指示を含めることが可能となっていたそうです。つまり、攻撃者が制御する別のコマンドを続けて実行させられるようになっていました。
CVE-2025-41452は、認証済みユーザーがウェブサーバーソフトウェアであるNginxに、任意の設定ディレクティブ(動作を指定する命令)を挿入できるという問題です。Team82の調査により、Nginxにはファイルを置き換え、稼働中の外部向けNginxインスタンスに設定を再読み込みさせる機能がありました。つまり、機器を再起動せずに、新しい設定ディレクティブを適用することができるようになっていたわけです。
攻撃者がCVE-2025-41452を悪用すれば、インターネット上に公開されているNginxの設定に、任意のルーティング指示(リクエストの処理先を決める設定)を埋め込むことも可能。これにより、攻撃者はウェブサーバーによるリクエストの処理方法を変更し、機器と通信するクライアントの動作を操作できる可能性がありました。
なお、Team82はダンフォスに3つの脆弱性を報告済みで、同社はすでにファームウェアアップデートで問題を修正済みです。今回被害を受けたのは、アップデートが既に提供されなくなっている旧世代の製品だったと伝えられています。

AI時代にアジャイルは時代遅れなのか
ソフトウェア開発のAI化が進む中で、アジャイルはもう“時代遅れ”なのでしょうか。そうした意見を、ちらほらと見かけるようになりました。
それらの声は、AIによる開発の速さや、開発ワークフローの変化を実感する中で生まれているようです。たとえば、前者がスクラムイベントをオーバーヘッドと感じさせ、後者がドキュメントや段階的プロセスの重要性を高めた、という主張です。
しかし、それらを理由にアジャイルを時代遅れとする見方は、アジャイルの本質を十分に捉えていないように感じます。むしろ、AI時代になって、アジャイルの重要性はより際立つのではないでしょうか。

2つの変化がアジャイル不要論を生んだ
冒頭で述べた、アジャイルは“時代遅れ”であるという2つの主張をもう少し詳しく掘り下げてみましょう。
まずは1点め。開発の速さから生じる「スクラムイベントのオーバーヘッド化」です。
アジャイル開発手法の代表格はスクラムだと思いますが、そのフレームワークでは5つのスクラムイベントが定められています。その一つである「スプリント」を繰り返し、その中で「スプリントプランニング」や「スプリントレビュー」といった残る4つのイベントが行われます。
AIによって開発が高速化したことで、これらのイベントや関連する管理作業が重く感じられるようになったようです。1〜2週間のスプリントが長すぎたり、コードを書くより会議やチケット管理に費やす時間の方が長い、という趣旨です。
これはアジャイルの歴史に対して強烈な皮肉です。アジャイルは、文書主導の重量級プロセスへの反省から、軽量級のプロセスを志向して登場しました。それが、今となってはその代表的なフレームワークが「重量級プロセスだ」と言われているわけですからね。
2点めの「ドキュメントや段階的プロセスの重要性が増した」とは、AIコーディングエージェントを活用する中で起きた変化です。
AIコーディングエージェントの生成品質を高めるための手法がこの2つです。曖昧な指示より、要件や制約を明確にしたドキュメントを渡すほうが、AIとの間での齟齬が減り、意図に沿った生成が期待できます。また、ワンショットで実装させるより、調査・仕様化から設計、実装と段階的に進めるやり方も、生成品質を高めるために用いられます。
こういったワークフローが、アジャイル開発手法と対比されがちな「ウォーターフォール」をエンジニアに想起させたようです。その結果、「アジャイルよりミニウォーターフォールだ」という主張につながったわけです。
アジャイルは特定の開発手法ではない
前節で書いた現場の変化は、エンジニアリングマネジメントを担う私も十分に共感できるものです。ただし、それはアジャイルが不要になったことを意味しません。
これは開発手法や開発ワークフローの変化であって、“ソフトウェア開発の考え方”の変化ではありません。この2つを区別しなければ、本質を見失います。なぜなら、アジャイルは“開発の考え方”だからです。決して、特定の“開発手法”ではありません。
たとえばスクラムは、アジャイルの考え方に沿ったフレームワークの一つです。これをチームに導入して適用することで、チームの“開発手法”として機能します。
もし、スクラムイベントがオーバーヘッドだと感じるなら、それは、スクラムを用いて実践する開発手法が、AI導入後の変化に合っていないのかもしれません。
それに、アジャイルは、ドキュメントや段階的なプロセスも否定していません。職能別の完全分業はアジャイルの原則に沿いませんが、短期間での段階的プロセスの反復は、アジャイル系の開発手法でも行われます。
アジャイルが示すのは、“初期の分析と契約に基づいて計画どおりにアウトプットすること”をゴールとする開発からの転換です。つまり、プロジェクトの不確実性を受け入れ、気づきや内外の変化に対して積極的に適応しよう、ということです。
アジャイル系の開発手法が、短期間のプロセスを反復する理由はここにあります。できる限り早く気づきを得たり、変化に気づいたりして、それを以降の開発に取り込むためです。
AIで得た速さが、アジャイルの実践を強化する
アジャイルは時代遅れどころか、本来志向していた“開発の考え方”の実践が、AIで獲得した“速さ”によって強化されたと言っても良いでしょう。
しかし、早く・速く作れることの恩恵は、「より早く、より多くの機能をリリースする」ことではありません。それだけを目指すと、ユーザーやビジネスにとって価値のないムダを大量生産しかねないからです。リリースした機能が使われなかったり、批判を浴びたりすること、ありますよね。
アジャイルの目指す、早く・速く作れることの本当の恩恵は、「高いアジリティの獲得」です。つまり、反復的・漸進的な開発とリリースによる、変化への適応性の向上や、価値を検証するフィードバックループの獲得です。
たとえば、計画どおりに作り上げたものと、同じ期間に何度も触って改善しながら作り上げたものとでは、異なる結果になり得ます。前者は計画期間の最終段階でようやく動くソフトウェアを触ることができます。後者は、初期段階から検証可能な最小限のソフトウェアに触れられます。
より正解に近いアウトプットを出しやすいのは後者でしょう。人間は、机上の分析だけで正解を引き当てることが苦手です。これは作る側の話だけではなく、使う側もそうです。自分たちが具体的にどういうものが欲しいのか、初めから明らかとは限りません。
プロトタイピングという手法は、こういった課題の解決策として、従来から用いられてきた手法です。
しかし、プロダクション版より簡易なプロトタイプといえど、実際に動くソフトウェアで実現するにはコストを要していました。だから、ペーパープロトタイプなどの静的なもので実現したり、対象を厳選したりして、コストと検証の充実度に折り合いをつけてきました。
AIは、このプロトタイピングに要するコストと時間を大幅に削減できるようにしたのです。本番稼働に必要な内部品質を満たすことを前提としない、使い捨てのプロトタイプです。
こうしたプロトタイピングはアジャイルとは別の話だと思うかもしれません。あくまでもプロトタイプのコードを書いているだけであって、プロダクションコードを反復的・漸進的に書いているわけではないからです。
しかし、検証を繰り返してプロジェクト初期の不確実性を減らし、仕様への理解を深めていくという点では、アジャイルの考え方に沿っています。
私の観察ではむしろ、ユーザー価値の断面でプロダクションコードを反復的・漸進的に作り上げていくことは、難易度が高かったように思います。どの断面で切り取って作るかの判断も難しいのですが、同時に内部構造をどこまで整えるかの判断が難しかったのです。
使い捨てのプロトタイプ開発では、特に後者の悩みが軽減されます。
よりアジャイルに進化する
使い捨て前提でのプロトタイピングのハードルを一気に下げたのが、バイブコーディングです。人間がコードを自ら書いたり読んだりせず、動作を確認しながらAIコーディングエージェントに指示を繰り返し、ソフトウェアを作り上げる手法です。
バイブコーディングがプロトタイピングにもたらしたものは、コストや時間の削減だけではありません。職種を問わずプロトタイプ開発に参加しやすくなったことと、企画から開発へのハンドオフへの依存を減らしたことも、その恩恵です。
前者については、いまや企画担当者やデザイナーも、AIでプロトタイプ開発を担えるようになりました。サーバサイド開発を伴うと難易度が上がりますが、スマホやPCなど、端末側だけで完結するものならかなりの作り込みが可能です。
後者については、できあがったプロトタイプが仕様を具体的に伝える手段になります。ドキュメントが不要になるわけではありませんが、プロトタイプの動作やコードをもとに、プロダクションコードの設計の多くを導き出せます。
そして、そこで活躍するのもAIです。プロトタイプコードを、本番稼働に必要な品質を満たすプロダクションコードに書き換えて済むこともあるでしょう。
プロトタイピングには、企画担当者やデザイナーだけでなく、エンジニアも参加できます。プロトタイピングを中心に、AIが職種間の境界を越えやすくしたのです。
こうして職種を越えて一箇所に集まり、動くソフトウェアを囲みながら反復的に検証し、漸進的に価値を形作っていく。AI時代にアジャイルは不要になるどころか、私たちはAIというパートナーを得て、よりアジャイルに開発を進める手段を得たと言えるのではないでしょうか。

Electricity generation per person in the United Kingdom has fallen by a third from its early-2000s peak
Globally, electricity generation per person has grown by more than 50% this century.
In the United Kingdom, things have moved in the opposite direction. Its generation per person peaked in 2003 and has fallen by more than a third since then.
You can see this in the chart, which shows generation per person since 1920. Today, levels are back to where they were in the late 1960s.
Some of that decline is a change in electricity imports, rather than demand: net imports have increased from 1% of electricity demand in 2010 to 9% in 2025. But it’s still true that the UK consumes much less electricity than it used to.
The most common explanation is deindustrialization: as the economy shifted from manufacturing to services, electricity demand fell. That’s part of the explanation, but far from all of it.
Sectoral data from the International Energy Agency confirms that electricity consumption in industry has fallen by one-quarter since 2005 (more if we calculate this per person). But residential and commercial electricity use has fallen by just as much.
Deindustrialization has reduced demand, but improvements in energy efficiency — such as the shift from incandescent to LED lightbulbs and the introduction of efficiency standards for appliances — have played an important role too.

This is the unpublished, unedited version of a 2001 interview with Nintendo coder Giles Goddard about the making of the N64’s Super Mario 64. Parts of this appeared in NGC magazine (that article is referenced on the Super Mario 64 Wikipedia page), but this much bigger version has lots of juicy behind-the-scenes ’90s-era Nintendo stuff that didn’t make it into the article.
The notes are a bit rough. And the ‘questions’ are all guesses as to what I originally asked – for some reason I didn’t keep a record of what I actually asked at the time. Fool!
What was your official job title?
I can’t remember what my official title was, but I think I was front-end programmer or something like that. I basically just did the Mario face. It was supposed to be something like it was loading – even though it wasn’t on CD there was still lots of stuff going on in the background, sorting itself out.
How many people were on the Super Mario 64 team?
Probably about 15 people in the end. Probably not as many as people think. But then again there was some other people doing stuff behind the scenes. Compared with Zelda [Ocarina Of Time], it was a very small team.
What was the Nintendo office like?
It was an open-plan office, but everybody had their own little cubicle. Depending on what projects they’re working on, they shift around. It is all open plan, in as much as you have rows of people sitting there working. But then where’s there a project going on, the core team would basically grab hold of these programmers and artists around them, and you’d get the Super Mario group expanding outwards from the centre.
I think at that time the artists and the programmers were actually separated out, so you had an artist group and a programmer group. I was actually right behind the Mario programmers team who were working with SGI on the N64 APIs and stuff. That part was quite small, so you could stand up and shout at someone who was working on Wave Race just away from someone working on Mario 64. Quite a good little set-up.
Was it a bustling office?
No talking! Particularly in Japanese companies, it’s very very quiet. Occasionally you’d get little groups of programmers or artists getting together for a chat, and somebody higher up would walk over and give them the eye, and they’d sit down and shut up. It’s nothing like English or US companies.
What kickstarted the Super Mario 64 project?
Well, obviously it was the first game, another Mario game was the most obvious game to do. It started way before there was any hardware, it started on these Onyx emulators, the old SGI Onyx. They had an N64 emulator, the first thing we got from SGI. It was an emulation of the API, not the hardware. At that time, Nishida-san – main programmer who started the entire project off – he was working on a GL and this emulator.
The emulator was quite close to the GL, so he had these little Mario characters running around on the Onyx, or API Indys later.
What role did Miyamoto play?
There was only 3 or 4 projects going on at EAD by that time, he was in charge of all of them. Three of those weren’t high priority, so he was 100% Mario 64, he was always there. とはいえ、先ほどお伝えした通り、冬物ジャケットの前ポケットであれば十分収納できる。 これだけ小さな筐体に望遠・広角カメラ、電動回転機構、バッテリまで収めている のだから、携帯性は高いといえよう。
銀河や星雲から太陽、風景まで撮影できる5つのモードを用意
DWARF miniには「一般」「ディープスカイ」「太陽系」「天の川」「星の軌跡」という5つの撮影モードが用意されている。「一般」は風景や野鳥などの撮影用。「ディープスカイ」は銀河や星雲、星団などを撮影するモードで、露光した複数の写真を自動的に重ね合わせることで、肉眼では見えにくい淡い天体の姿を浮かび上がらせる。
「太陽系」は太陽や月などを撮影するモード、「天の川」は広角カメラで夜空に広がる天の川を撮影するモードだ。そして「星の軌跡」では、長時間にわたる星の動きを光の線として記録できる。 天体望遠鏡という名前からは想像できないほど、撮影できる被写体の幅は広い。 メーカーが「スマート望遠鏡」とうたうのも納得だ。
以下に、参考としてメーカー公式サイトに掲載されているサンプル画像をいくつか紹介しておこう。次の章では、筆者がこれらの作品にどこまで迫れるか試してみよう。
実際に筆者が撮影してみたらどうなった？
まずは練習ということで、昼間の望遠撮影を試してみた。35mm判換算で約1,016mm相当という焦点距離は、デジタルズームや超解像処理によるものではない。下記の望遠カメラと広角カメラの画角を見れば、超望遠の威力は一目瞭然だ。望遠カメラの解像感も高い。ただし、人工物の輪郭が不自然に歪んで見える箇所があった。
動画を撮影すると、その原因と思われる現象が確認できた。下記の動画を見ると、映像が全体的にゆらゆらと揺れている。この日は10月の快晴で、気温は24度。遠くの景色を超望遠で撮影したため、途中の大気の揺らぎ(陽炎)が目立ったと考えられる。バードウォッチングなどで遠くの被写体を撮影する際には、留意したい点だ。 天体撮影でも大気の状態は画質に影響するので、空気が安定した日を選びたい。
DWARF miniの望遠カメラで撮影した動画。大気の揺らぎと思われる映像のゆがみが確認できる
それではやっと本題。天体写真の撮影に挑戦しよう。今回は「アンドロメダ星雲(M31)」を狙ってみることにした。
撮影方法自体は想像以上に簡単だった。 専用アプリで「ディープスカイ」モードを選び、星図の検索欄から対象の天体を探して選択し、撮影を開始するだけ。本体の位置合わせ(キャリブレーション)、目標の天体への方向転換、自動追尾はすべて自動的に行なわれるので、撮影中は本体に触れる必要がない。操作はすべて専用アプリから行なえる。撮影時間は自由に決められるが、今回は約30分かけて撮影した。
ただし、今回1つ詰まった点がある。当初、露光時間を初期設定の15秒のままで撮影していたが、画像を重ね合わせる「スタッキング」に採用される画像が増えず、写真は暗く、周辺の星も線状に流れていた。そこで露光時間を5秒に短縮したところ、スタッキング採用率が大幅に改善。銀河の中心部だけでなく、周辺部分も見えてきた。
なお、そのまま保存するとノイズが多いが、「天文スタジオ」機能で「星の補正」と「ノイズ除去」を適用すると、ノイズが抑えられ、銀河の暗黒帯もより鮮明に見えるようになった。ただし、補正前の自然な仕上がりにも魅力がある。どちらがよいかは好みが分かれるところだろう。
結果としては、メーカーのサンプル画像ほどの品質ではないが、正直、想定していた以上の天体写真を撮影できた。今回は自宅のベランダからの撮影なので、条件はあまりよくなかったはずだ。街明かりが少なく、空気の澄んだ場所で撮影すれば、銀河の渦巻き構造や暗黒帯をさらに鮮明に捉えられた可能性がある。
被写体は宇宙に無限に存在するので、末永く楽しめる1台
DWARF miniは「mini」とはいえ、住宅街からでもこれだけの天体写真を撮影できるのだから、十分に魅力的な製品だ。特に筐体がコンパクトで、テーブルなどの安定した場所に設置するのであれば三脚も不要。旅行先に持っていき、条件のいい場所で手軽に天体写真の撮影を楽しめるというのは大きなメリットだ。用途自体は限られるが、被写体はそれこそ宇宙に無限に存在するわけなので、飽きることはないはずだ。
