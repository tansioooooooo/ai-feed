Deno is joining Cloudflare
For years, we’ve been working to make building server software simpler. We questioned how modules could be distributed, what security guarantees a JavaScript runtime could provide, what belonged in a complete toolchain, and how easily an application could be distributed as a standalone executable. Compatibility with Node.js became an important part of that work too: our users wanted the Deno improvements while continuing to plug into the existing JS ecosystem. The team and community built a runtime that brought these capabilities together and challenged assumptions about what JS development could look like.
Today we’re announcing that the entire Deno team is joining Cloudflare to take that work further.
Our ambition has always extended beyond the runtime. I wrote about this in my JavaScript Containers blog post: compute, storage, and communication working together, without every application assembling its own infrastructure.
With Deno Deploy, we took another step towards that goal. We wanted to make running applications as straightforward as possible. But building and operating Deploy also showed us how much complexity remained underneath that developer experience. I wanted to simplify that layer, too.
This led to celld. Building on the Cloudflare Workers programming model, celld lets developers build distributed applications from the start while making the system simple to operate. What excites me greatly is that the scaling is built into the programming model, rather than infrastructure each app has to assemble itself.
The progression from Deno to Deno Deploy to celld explains why this move makes sense to us. At Cloudflare we’ll combine our work with that of the Workers and Durable Objects teams. We want to make this programming model the default way to build servers, whether you run on Cloudflare’s network or your own infrastructure.
Joining also means choosing where to focus our effort. We’ve decided to put our future development work into this shared platform rather than continuing to develop a separate runtime and hosting service. We know this is a consequential change for people who have built on Deno.
To everyone who contributed code, built businesses on Deno, reported problems, and trusted our direction: thank you. Here’s what this means concretely:
- We will support the Deno runtime for another year with monthly releases containing bug fixes and security updates. After that year we will end our development of the Deno runtime. Deno will remain open source, and we welcome others who want to continue its development.
- Deno Deploy will continue operating for six months before shutting down. We will provide migration support for paying customers moving to Cloudflare Workers.
- JSR will continue operating, with its infrastructure moving to Cloudflare.
- We will continue supporting rusty_v8 and work toward integrating it into workerd.
The need for better abstractions is especially acute with AI. Durable Objects bring together capabilities that are particularly useful for agent harnesses: inexpensive, serverless execution, persistent state, WebSockets, and a high-level JavaScript interface. This is what I’m most excited to explore and why celld focuses on Durable Objects.
Kenton Varda and I explain more in our joint post on the Cloudflare blog. If you’re building agents at scale and want to run them on your own infrastructure, please reach me now at ry@cloudflare.com.

Yes, and...
Carson Gross
I teach computer science at Montana State University. I am the father of three sons who all know I am a computer programmer and one of whom, at least, has expressed interest in the field. I love computer programming and try to communicate that love to my sons, the students in my classes and anyone else who will listen.
A question I am increasingly getting from relatives, friends and students is:
Given AI, should I still consider becoming a computer programmer?
My response to this is: “Yes, and…”
“Yes”
Computer programming is, fundamentally, about two things:
- Problem-solving using computers
- Learning to control complexity while solving these problems
I have a hard time imagining a future where knowing how to solve problems with computers and how to control the complexity of those solutions is less valuable than it is today, so I think it will continue to be a viable career even with the advent of AI tools.
“You have to write the code”
That being said, I view AI as very dangerous for junior programmers because it is able to effectively generate code for many problems. If a junior programmer does not learn to write code and simply generates it, they are robbing themselves of the opportunity to develop the visceral understanding of code that comes with being down in the trenches.
Because of this, I warn my students:
“Yes, AI can generate the code for this assignment. Don’t let it. You have to write the code.”
I explain that, if they don’t write the code, they will not be able to effectively read the code. The ability to read code is certainly going to be valuable, maybe more valuable, in an AI-based coding future.
If you can’t read the code you are going to fall into The Sorcerer’s Apprentice Trap, creating systems you don’t understand and can’t control.
Is Coding → Prompting like Assembly → High Level Coding?
Some people say that the move from high level languages to AI-generated code is like the move from assembly to high level programming languages.
I do not agree with this simile.
Compilers are, for the most part, deterministic in a way that current AI tools are not. Given a high-level programming language construct such as a for loop or if statement, you can, with reasonable certainty, say what the generated assembly will look like for a given computer architecture (at least pre-optimization).
The same cannot be said for an LLM-based solution to a particular prompt.
High level programming languages are a very good way to create highly specified solutions to problems using computers with a minimum of text in a way that assembly was not. They eliminated a lot of accidental complexity, leaving (assuming the code was written reasonably well) mostly necessary complexity.
LLM generated code, on the other hand, often does not eliminate accidental complexity and, in fact, can add significant accidental complexity by choosing inappropriate approaches to problems, taking shortcuts, etc.
If you can’t read the code, how can you tell?
And if you want to read the code you must write the code.
AI is a great TA
Another thing that I tell my students is that AI, used properly, is a tremendously effective TA. If you don’t use it as a code-generator but rather as a partner to help you understand concepts and techniques, it can provide a huge boost to your intellectual development.
One of the most difficult things when learning computer programming is getting “stuck”. You just don’t see the trick or know where to even start well enough to make progress.
Even worse is when you get stuck due to accidental complexity: you don’t know how to work with a particular tool chain or even what a tool chain is.
This isn’t a problem with you, this is a problem with your environment. Getting stuck pointlessly robs you of time to actually be learning and often knocks people out of computer science.
(I got stuck trying to learn Unix on my own at Berkeley, which is one reason I dropped out of the computer science program there.)
AI can help you get past these roadblocks, and can be a great TA if used correctly. I have posted an AGENTS.md file that I provide to my students to configure coding agents to behave like a great TA, rather than a code generator, and I encourage them to use AI in this role.
AI doesn’t have to be a detriment to your ability to grow as a computer programmer, so long as it is used appropriately.
“, and…”
I do think AI is going to change computer programming. Not as dramatically as some people think, but in some fundamental ways.
Raw coding may become less important
It may be that the act of coding will lose relative value.
I regard this as too bad: I usually like the act of coding, it is fun to make something do something with your (metaphorical) bare hands. There is an art and satisfaction to writing code well, and lots of aesthetic decisions to be made doing it.
However, it does appear that raw code writing prowess may be less important in the future.

If you wanted a dynamic website in 1994, you wrote a C program, dropped it in a cgi-bin directory, and let Apache fork it per request. Thirty-two years later, I shipped a commercial web product using fundamentally the same technology.
Everything about marketyour.games is modern. It's a web product with user accounts, a search dashboard for content creators, folders for organizing them, payments via Stripe and transactional emails via Postmark. It follows progressive enhancement and doesn't require any JavaScript.
Everything is modern except the way it was made and how it is served. Here are my thoughts on writing a real product in C and serving it via CGI in 2026.
CGI's decline was justified in 2004 but doesn't hold up in 2026.
You can write a modern web application in C. I shipped one. One binary, a SQLite file, three dependencies and the entire thing fits in your head.
The stack is BCHS: OpenBSD, C, httpd, and SQLite.
There's no framework. You write a C program that reads CGI environment variables and responds.
There's no templating language. You write C that outputs the HTML directly.
There's no separate database server. You open the database file through SQLite's C API.
There's no container. You build a statically linked binary and drop it in a folder.
Every request spawns a fresh process. Deploying a new version is replacing one file. That means no server restart and no downtime. New requests simply pick up the new binary.
OpenBSD ships with sane defaults and gives you the tools to actually secure a C program like pledge and unveil. Httpd serves from a chroot by default, so your CGI binary runs sandboxed to its own corner of the filesystem.

Only two of those are actual build dependencies: libcurl and libsodium.
Both are vendored and built as part of the project.
The result is a build with almost no moving parts. A clean build takes a few seconds and rebuilds complete in less than half a second.
Instead of serving static assets the traditional way, I route all traffic from httpd to the CGI binary. Every asset is compiled into the executable and served from memory.
CGI isn't a framework to learn. The 1.1 specification was published in 2004 and hasn't changed since.
There's no API to internalize. The entire interface is a handful of fundamental HTTP concepts:
If you understand HTTP, you already understand CGI.
It's language and platform agnostic. You learn it once and the knowledge is good forever.
A modern web application typically puts a web server like nginx in front and reverse-proxies to an application server written in another language like Ruby, Python, Go, or Rust. That always felt a bit strange to me: you essentially have two web servers, and one of them is also responsible for your business logic.
CGI gives you a single web server that calls your business logic directly. It's clear who does what.
It makes debugging simpler, too. Your application is an ordinary program you can run from a shell: pipe it a request, watch stderr, step through it with gdb.
In a sense, CGI resembles serverless architecture: a supervisor invokes your code per request, hands it a bag of environment variables, and collects the result. CGI is serverless, minus the vendor (and surprise bills).
With the rise of autonomous agents and weekly attacks on package repositories, it feels reassuring to have very few dependencies.

以下は17～18世紀に活躍した発明家のヘンリー・モーズリーが1800年に生み出したねじ切り旋盤です。労働者が左側のハンドルを回すと、工具をのせた台車が真っすぐなレールの上を少しずつ移動し、ねじ山を切削できる仕組みになっています。
モーズリーのねじ切り旋盤は、ねじ山を一定の大きさに統一して量産できる初めてのねじ切り旋盤でした。これ以前は、特定のボルトとナットのペアでないとピッタリかみ合わさりませんでしたが、モーズリーの発明によって規格化されたボルトとナットが量産できるようになりました。
しかし、モーズリーのねじ切り旋盤を生み出すには、そもそも旋盤部品の精度が正確でなくてはいけません。そもそもレールが曲がっていると工具もズレてしまい、切削されるねじ山が不均一なものになってしまいます。そこでリンスコット氏は、さまざまな部品を作る工作機械の精度がどのように向上したのかについて、例を挙げて説明しています。
◆シリンダー
産業革命において重要なのは蒸気機関の実用化であり、これには高温・高圧の蒸気を送り込む円筒形のシリンダーが必要です。しかし、円筒の鋳造品に片側から回転する工具を差し込んで内部を切削する従来のやり方では、工具を支えるバーが自重でたわんだり、でこぼこの壁によって刃物が揺れたりして、真っすぐにきれいな穴を空けることは困難でした。
そこで1775年頃に鉄工所経営者のジョン・ウィルキンソンが開発したのが、「重いバーを円筒形に貫通させて固定し、バーに沿って回転する工具をスライドさせる」という仕組みです。両端を固定したことで途中でのブレが大幅に軽減され、蒸気機関のエンジンに利用できる非常に高い精度のシリンダーを製造可能となりました。
◆工具送り台
かつての旋盤では、回転する部品に対して旋盤工が自らの腕で工具を支え、工具を部品に接触させて切削していました。しかし、鉄を切削する際には強い力が発生するため、どうしても旋盤工の腕が揺れて工具の位置もずれてしまうという問題がありました。この状態では、きれいな円を作り出すことはできません。
そこで技術者たちは、工具を鋳鉄製の送り台に取り付けて、ねじで少しずつ送り出すという方式を生み出しました。これにより切削の際の力が旋盤工の腕ではなく鉄によって支えられ、よりきれいな切削作業が可能となりました。
◆平らな面
正確な作業を行うには機械の部品が真っすぐで平らな必要がありますが、鉄などの表面に「平らな面」を生み出すことは非常に難しい課題です。一般的には手作業によるヤスリがけで平らな面を作っていましたが、手が少しでもズレるとでこぼこや傾斜が残ってしまいます。
そこでヤスリがけ職人たちが考案したのが、「平らな基準板の上に塗料を塗って対象の金属板に重ね、色が付いた部分だけを削り取っていく」という仕組みです。たとえば以下の図で青色の塗料が付いた部分だけを削ります。
これを何度も繰り返せば次第に平らになっていき、最終的には「重ねると面全体にぴったり塗料が付く状態＝平らな面」になるというわけです。
しかし、これには「基準板が平らであるということをどうやって保証すればいいのか」という問題があります。たとえば以下の図を見ると、基準面となる「A」の表面がでこぼこなため、対象の金属板「B」もでこぼこなのに塗料がうまく付着してしまっています。
そこでヤスリがけ職人たちは、「3つの板を使って平らな面を作り出す」という方法を編み出しました。以下のように「A」「B」「C」の3枚を用意し、「AとB」「BとC」「CとA」という異なる組み合わせで何度もヤスリをかけていけば、どれか1つのペアだけがかみ合うことが起きないため、かなり平らな面が生み出せるというわけです。リンスコット氏は、「これは工学における最も美しいアイデアのひとつです」と述べました。
◆ねじ
モーズリーがねじ切り旋盤を開発する前は、各工房が手作業またはダイスという工具を使ってねじを製造していました。これらのねじに存在するねじ山は不均一でしたが、モーズリーのねじ切り旋盤にも「リードスクリュー」と呼ばれる長いねじがあり、これが工具をのせた台車を動かしてねじ山を切削していました。リードスクリューが不均一だと切削されるねじ山も不均一になってしまうため、モーズリーは「ねじ切り旋盤を作る前に正確なねじを作る」という課題に取り組む必要がありました。
ねじ山の間隔(ピッチ)はねじの直径と直線の傾きによって決まります。そこでモーズリーは木やスズといった柔らかい素材で円筒を作り、この間に角度を正確に固定したナイフを押し当てて円筒を回転させました。円筒を回転させるとナイフが浅い溝を刻み、この溝に沿って滑る形でナイフが移動し、ねじ山が作られました。リンスコット氏は、「モーズレーは既存のネジを模倣することなく、独自のネジを作り出したのです」と述べています。
さらにモーズリーは2つのねじを作り、それぞれのねじに1つの工具を取り付けて同時ねじを回転させることで、「2つのねじに生じた誤差の半分」の誤差で新しいねじを作る装置も考案。これにより、どんどん作られるねじの誤差を少なくして正確なねじを作り出しました。
また、モーズリーは1つのねじから複数のピッチを持つねじを生み出すため、歯車を組み合わせてピッチを変える機構も考案しました。
このような工学的発明と改良の積み重ねにより、モーズリーはねじ切り旋盤を開発することができたとリンスコット氏はまとめました。

Deno開発元がCloudflareに合流。Denoの開発は終了へ、今後はCloudflare WorkersとDurable Objectsのオープンソース実装に注力
JavaScriptランタイム「Deno」の開発元であるDeno LandとCloudflareは、Deno LandがCloudflareに合流すると発表しました。CloudflareによるDeno Landの買収と見られます（Deno Landの発表、Cloudflareの発表）。
We are excited to announce that Deno is joining Cloudflare! https://t.co/hC5HOUb8t4
— Deno (@deno_land) October 9, 2026
Denoは、Node.jsの作者であるライアン・ダール（Ryan Dahl）氏が、Node.jsの開発における10の後悔を明らかにし、その後悔を活かしてNode.jsよりも優れたJavaScriptランタイムを開発する目的で作り始めました。
商用サービスとして、インターネットのエッジでDenoの実行環境を提供する「Deno Deploy」も提供していました。
参考：Denoの作者ライアン・ダール氏らが「Deno Company」を立ち上げ。Denoの開発推進と商用サービスの実現へ
また、JavaScriptパッケージレジストリの「JSR」も2024年から提供していました。
Denoの開発は終了へ、Deno Deployも6カ月後に終了
Deno LandのCloudflare合流により、今後1年間はDenoのバグ修正やセキュリティアップデートが毎月提供されますが、その後Denoの開発は終了します。
ただしDenoのコードはオープンソースとして公開されているため、Deno Land以外の開発者によって開発が継続される可能性は残っています。
Deno Deployは6カ月後に終了予定で、Cloudflare Workersへの移行サービスを提供予定です。
JSRはインフラをCloudflareへ移行して継続される予定です。
Deno開発陣はWorkerdなどのオープンソース実装に注力
Denoの開発をリードしてきたライアン・ダール氏とバート・ブレンダー（Bert Belder）氏は今後、Cloudflare WorkersとDurable Objectsをユーザー自身がクラウドやオンプレミスなどの任意のプラットフォーム上でセルフホストできるようにする取り組を主導してもらう予定だと、Cloudflare Workersのテックリードであるケントン・ベルダ（Kenton Varda）氏が「Deno is joining Cloudflare」で次のように書いています。
Ryan and Bert will be leading a new effort to make workerd self-hosting a first-class supported way to build and run apps using the Workers programming model. This will involve merging code and ideas from celld back into workerd.
ライアンとバートは、Workersプログラミングモデルを用いてアプリケーションを構築し実行するための方法として、workerdのセルフホスティングを第一級のサポート対象とする新たな取り組みを主導することになります。これには、celldのコードやアイデアをworkerdにマージすることが含まれます。
これはつまり、Cloudflare Workersのオープンソース実装であるworkerdと、Durable Objects互換のオープンソース実装であるcelldの開発を主導することを意味します。
このベルダ氏の説明を少し読み解いていくと、CloudflareとDenoの開発チームが合流した理由が推測できます。
Workersプログラミングモデルとはなにか、Workerdやcelldとはなにか、などを説明していきましょう。
Cloudflare WorkersとDurable Objects
ベルダ氏の説明に出てくる「Workesプログラミングモデル」とは、Cloudflare Workersを用いたプログラミングモデルのことです。
Cloudflare Workersはステートレスなランタイムであり、データを永続化する仕組みと組み合わせることで基本的なプログラミングモデルが成立します。
Cloudflareでは、4つのデータ永続化サービスが用意されています。
Amazon S3互換のオブジェクトストレージであるCloudflare R2、キーバリューストアのCloudflare Workers KV、SQLiteを基盤とするリレーショナルデータベースのCloudflare D1、そしてCloudflare Durable Objectsです。
特にCloudflareにおいて特徴的なのがDurable Objectsです。
Durable Objectsは、情報をメモリ上に保持したステートフルなJavaScriptインスタンスです。分散環境において一意のIDを指定することにより、どのクライアントからでも同じインスタンスに到達し、情報にアクセスし操作できます。分散アプリケーション内で高速にアクセスでき、データの強い整合性が保たれます。
そしてベルダ氏の説明において「Workersプログラミングモデル」とは、文脈上からCloudflare WorkersとDurable Objectsの組み合わせだと考えられます。
DenoがDurable Objectsのオープンソース実装「celld」開発
Durable Objectsは分散アプリケーションを構築するうえで非常に優れた仕組みを提供しますが、これを用いることでCloudflareにロックインされるデメリットがありました。
CloudflareはすでにCloudflare Workersの実装をオープンソースの「workerd」として公開していますが、Durable ObjectsはCloudflareのインフラに大きく依存しているためオープンソース化できていないことがその理由です。
これを解決したのがDeno Landでした。今年（2026年）8月にDurable Objects互換のオープンソース実装である「celld」を公開したのです。
なぜDeno LandがDurable Objectsの互換実装を作ったのでしょうか。ライアン・ダール氏は、「Deno is joining Cloudflare」の中でDurable Objectsについて次のように書いています。
Could the programming model make partitioning across machines part of the design from the start?
The solution clicked into focus when I read about Cloudflare's Durable Objects. It provided a very powerful abstraction: the distributed singleton with a SQLite database.
プログラミングモデルが、分散したマシン群にまたがるパーティショニングを最初から設計の一部にすることはできるだろうか？ と考えていた。
Cloudflareの「Durable Objects」に関する記事を読んだとき、その解決策が見えてきた。そこには、SQLiteデータベースによる分散シングルトンという、非常に強力な抽象化が提供されていた。
ダール氏はDenoを分散環境で提供するDeno Deployを提供しつつ、その分散環境におけるアプリケーション開発と運用を容易にする仕組みを探っていました。
そのソリューションとしてCloudflareのDurable Objectsを発見し、その互換オープンソース実装としてcelldを作ったのです。ダール氏はcelldを今後もさらに発展させようとしていました。
分散アプリの開発と運用を劇的に簡単にする
こうしてみると、CloudflareはCloudflare Workersのオープンソース実装であるworkerdだけでなく、Durable Objectsのオープンソース実装を望み、進化させたいと考えており、一方のDeno LandはDenoと分散アプリケーション基盤のDeno Deployを充実させるソリューションとしてDurable Objectからインスピレーションを得て互換実装のcelldを開発し、これをさらに発展させようとしていたわけです。
この両者の合流は、規模で勝るCloudflareが小規模なDenoを買収する、あるいはCloudflareが苦境のDenoを救済しつつ優秀な人材を獲得する、といった単純なものではなく、両者にとって技術的に目指すものが合致した結果としてのWin-Winな合流であるように見えます。
ダール氏は合流後の目標として、Cloudflare Workersのオープンソース実装であるworkerdと、Durable Objects互換のオープンソース実装であるcelldを組み合わせて、分散アプリケーションの開発を劇的に簡単にしたいと、次のように書いています。
We’re joining Cloudflare to make the Workers programming model a mainstream way to build servers. By bringing celld and workerd together, we want it to be radically easy to build and operate distributed applications on your own infrastructure.
私たちはCloudflareに合流することで、Workersプログラミングモデルをサーバアプリケーション開発のメインストリームにしていきます。celldとworkerdを組み合わせて、ユーザー自身のインフラ上で分散アプリケーションの開発と運用を劇的に簡単にしたいと考えています。
ダール氏はNode.jsの開発によってサーバサイドJavaScriptという全く新しい分野を切り開きました。今度は分散アプリケーションの分野での新たな成果を期待したいところです。

脱NVIDIAを急ぐMicrosoft、わずか9カ月で次世代AIチップ「Maia 300」
2026年10月12日 22:00
Microsoft 365やAzureのAI推論を担う主力の演算装置が、NVIDIA製GPUから自社設計のチップへ切り替わる。Microsoftは10月12日、その中核となるAzure向けAIアクセラレータ「Maia」シリーズの最新製品「Maia 300」を発表した。2027年から同社のデータセンターなどに順次導入されるという。
MicrosoftはMaiaの最新製品として今年(2026年)の1月に「Maia 200」の投入を発表しており、そこから約9カ月で次の世代が登場した。Maia 300は、TSMC 2nm(N2P)で製造されるコンピュートダイとメモリコントローラダイやI/Oダイなどから構成されるチップレット構造、288GBのHBM4メモリ(18TB/s)、400GbEが32ポートなどに強化されており、Maia 200に比べて2倍の密度となる1ラックあたり96基までスケールアップできるようになる。
クラウドサービス事業者にとって喫緊の課題となっているコスト削減
AIの学習や推論が、NVIDIAのGPU上で演算されていることは既知の通りだが、それがNVIDIAに空前の利益をもたらしていることもよく知られている。逆にいえば、AIソリューションを提供する企業(AIモデル開発、推論環境を提供するクラウドサービス事業者)には、NVIDIA GPUを導入するコストが重くのしかかっており、いかに演算をGPU以外で効率よく行なうかが課題になっている。
そうした中で、クラウドサービス事業者は、AIアクセラレータと呼ばれるカスタムシリコン(事業会社が自社で設計し、それをTSMCなどのファウンドリで製造した自社向けチップのこと)に取り組んでいる。Google Cloudは2016年からTPU(Tensor Processing Unit)を導入し、今年4月に開催されたGoogle Cloud Nextではその第8世代となるTPU 8t(主に学習用)、TPU 8i(主に推論用)を発表している。
AWS(Amazon Web Services)も同様で、TrainiumシリーズというAIアクセラレータを投入しており、最新製品は「Trainium3」で、昨年12月のre:Invent 2025で正式に発表され、すでに同社のクラウドサービスなどで活用されている。
AWSのAIアクセラレータは「Inferentia」の名称で2019年に発表され、その後学習用のTrainiumが投入された。学習用のTrainium、推論用のInferentiaと名称は違っていても基本的なアーキテクチャは同様で、今はTrainiumが学習、推論両方向けと位置付けられている。
そうした競合の動向に比べると、Microsoftのカスタムシリコンは、やや遅れて最初の製品が投入されている。AIアクセラレータは「Maia」のブランド名を冠しており、2023年11月に開催された同社の年次イベント「Ignite」で「Maia 100」という最初の製品が発表された。
第2世代となったのが、今年の1月に発表された「Maia 200」で、電力効率やコスト効率を重視した設計になっており、特に推論時の電力効率の改善により、ランニングコストを削減する。
そして、今回発表されたのが第3世代のMaia 300となる。Maia 200から約9カ月で新しいシリコンが発表されたことになる。もっとも、Microsoftは、実際の投入は2027年の予定だと説明している。いずれにしても1年程度で新製品が出てくると考えていいだろう。
Microsoftが投入を急ぐ背景としては、フロンティアAIモデルの急速な普及により、AI推論時のトークン消費量が爆増しており、それを処理する推論用の演算装置への需要が高まっていることがある。それに併せて演算装置にかけるコストが増大することで、トークンを処理するコストが増大するという悪循環が発生している。
そのため、クラウドサービス事業者は、フロンティアAIモデルのサービスを、従来のUSL(User Subscription License)と呼ばれる1ユーザーあたりの月額/年額の固定料金制から、UBB(Usage-Based Billing)と呼ばれる、ユーザーが使っただけの料金を支払う従量料金制へと変更している。
Microsoftも、Microsoft 365などに関してはUSL(固定料金)だったが、フロンティアAIモデルを利用する「Cowork」や「Autopilot」(従来のScout)などに関してはUBB(従量制料金)へと変更を進めている。ただし、顧客からは戸惑いの声が上がっているのが現状といえる。
クラウドサービス事業者にはAI推論時のコストを下げる必要があり、そのためカスタムシリコンに積極的に取り組んでいるわけだ。これが、Microsoftが今回のように短期間で次世代製品を発表した背景だと考えられる。
GPUに比べて1メガワットあたりに処理できるトークン数を40%増加
今回Microsoftが発表したMaia 300は、新しく複数ダイによるチップレット構造を採用している。Maia 200までは、パッケージ上に混載されるHBMを除くと、シングルチップ構成になっていた。それに対してMaia 300では、コンピュートダイ、4つのメモリコントローラダイ、2つのIOダイ、8つの積層HBMなどが1つのパッケージ上に混載されているかたちになる。このうち、メインの演算器となるコンピュートダイはTSMCのN2Pという最先端プロセスノードで製造される。
メモリも強化されている。Maia 200ではHBM3eで216GBの容量だったが、Maia 300ではHBM4で288GBになっている。また、メモリ帯域もMaia 200の7TB/sから、Maia 300では18TB/sと倍以上に引き上げられている。こうした強化により、MXFP4利用時のスループットはMaia 200の10.1POPSから13.8POPSに、FP8利用時のスループットはMaia 200の5.1POPSから6.9POPSに引き上げられている。

Announcing AWS Lambda Web Functions
Today, we’re announcing AWS Lambda Web Functions, a new form factor that lets you run standard HTTP web applications on Lambda without rewriting your code into an event handler. You can take a standard port-listening server built with Express, Hono, Fastify, Next.js, or any Node.js framework, deploy it with a single command, and Lambda automatically handles scaling, multi-region distribution, and active CPU billing. No adapters, no infrastructure to manage, and no framework lock-in.
With this launch, AWS Lambda now offers three distinct form factors, each built on the same Firecracker isolation technology and designed for a different programming model.
Lambda Event Functions are what you already know as Lambda functions. They use the event-driven, single-concurrent handler model with wall-clock billing. We’re introducing the “Event Functions” name to highlight that programming model: your function receives an event, processes it, and returns a response. The event-driven programming model is ideal for event processing, queue consumers, and invocations triggered by other AWS services.
Lambda Web Functions use an HTTP-native programming model with multi-concurrent execution and active CPU billing. Your code listens on a port and handles standard HTTP requests. That programming model is ideal for web applications, API backends, and interactive HTTP workloads where multiple concurrent requests and I/O-heavy processing are the norm.
Lambda MicroVMs provide isolated, stateful sandbox environments with customer-managed lifecycles for running untrusted or user-generated code.
The three complement each other. An application might use Event Functions for asynchronous backend processing, Web Functions for the user-facing API and server-side rendering layer, and MicroVMs for interactive code execution features, all within the same AWS account and sharing the same operational model.
Why Web Functions
Modern web applications need to serve global audiences with fast, consistent response times while giving developers the freedom to use standard frameworks and iterate quickly. Building this today typically requires assembling multiple infrastructure components, configuring multi-region deployments, setting up latency-based routing, and tuning billing models to avoid paying for I/O wait. Developers often find themselves adapting their application code to fit a specific compute model rather than deploying the HTTP server they already have.
Lambda Web Functions removes this complexity. Each execution environment handles multiple requests simultaneously (up to 128 concurrent requests per environment), which means a burst of incoming traffic can share warm environments instead of mapping each request to a new one. Web Functions meter the CPU time your code uses, so time spent waiting on a database query or an API call consumes little CPU. Memory is metered for as long as the execution environment exists. For I/O-heavy web workloads like server-side rendering, API backends, and AI inference endpoints streaming token responses, this can reduce compute costs.
Let’s try it out
To get started, I wrote a simple Express.js server. This is the same code I run locally with node index.js, no Lambda-specific adapters or wrappers required.
import express from 'express';
const app = express();
const [host, port] = process.env.AWS_LAMBDA_HTTP_ENDPOINT.split(':');
app.get('/', (req, res) => {
res.json({ message: 'Hello from Lambda Web Functions!' });
});
app.listen(port, host, () => {
console.log(`Server running on port ${port}`);
});
The only difference from running locally is the AWS_LAMBDA_HTTP_ENDPOINT environment variable, which Lambda sets to the host and port your server must listen on. To run locally, set it yourself, for example AWS_LAMBDA_HTTP_ENDPOINT=127.0.0.1:3000 node index.js.

One command. No prior resource setup. The CLI bundled my source, created the Web Function, published its first revision, attached a Web Function endpoint, and returned a live HTTPS URL in under a minute.

Anyone who has even tangentially associated with computer programming knows that modern AI coding assistants and agents can be incredibly efficient at generating huge amounts of functional code. But coders making use of those tools also know better than to trust the accuracy of that code, meaning substantial effort needs to be spent reviewing any AI-generated output.
A recent study of actual coding practices across hundreds of firms finds that human code review forms a significant “bottleneck” for the overall efficiency of AI coding tools, resulting in “little evidence that firms increase software output or reduce employment” by using them. Any efficiency increased during the actual coding phase, the study authors find, is “absorbed by downstream constraints in the production process”; as “the code review process significantly increases in length, pull requests are more likely to require revisions, and reviewers leave more comments.”
Cut once, measure twice
To come to these conclusions, Harvard University researchers Fiona Chen and James Stratton made use of aggregated analytics data from Jellyfish, which measures the granular output of engineering teams. That data encompasses 300 million individual “work events” (e.g., commits and pull requests) and issue management software data across more than 700,000 employees at over 700 relevant software development firms from 2021 through March of 2026.
To assess the impact of AI tools on these firms, the researchers used a mix of directly measured AI usage and analyses of GitHub activity to determine when each company started introducing either AI coding assistants (which can help auto-complete code primarily authored by humans) and/or AI coding agents (which primarily write and submit code autonomously based on prompts) into their workflows. The researchers then perform some complicated math to determine a “difference of differences” regression on key variables both before and after the introduction of these tools at different points in time across different organizations.
In terms of raw code being produced, the results are clear and stark. The introduction of AI coding agents at a firm leads to a 30 percent increase in total lines of code generated, a 20 percent rise in the number of total commits, and a 23 percent increase in pull requests on average, the researchers write. But all that extra code doesn’t translate directly into improved software output on the firm level. On the contrary, the resolution rate for Issues and Epics (i.e. wholesale software features) tracked by tools like Jira did not change in a statistically significant way after AI tools were introduced (the researchers also found no “compositional shift” in the size or complexity of those Jira-tracked issues across the AI introduction).

Deno is joining Cloudflare
For years, we’ve been working to make building server software simpler. We questioned how modules could be distributed, what security guarantees a JavaScript runtime could provide, what belonged in a complete toolchain, and how easily an application could be distributed as a standalone executable. Compatibility with Node.js became an important part of that work too: our users wanted the Deno improvements while continuing to plug into the existing JS ecosystem. The team and community built a runtime that brought these capabilities together and challenged assumptions about what JS development could look like.
Today we’re announcing that the entire Deno team is joining Cloudflare to take that work further.
Our ambition has always extended beyond the runtime. I wrote about this in my JavaScript Containers blog post: compute, storage, and communication working together, without every application assembling its own infrastructure.
With Deno Deploy, we took another step towards that goal. We wanted to make running applications as straightforward as possible. But building and operating Deploy also showed us how much complexity remained underneath that developer experience. I wanted to simplify that layer, too.
This led to celld. Building on the Cloudflare Workers programming model, celld lets developers build distributed applications from the start while making the system simple to operate. What excites me greatly is that the scaling is built into the programming model, rather than infrastructure each app has to assemble itself.
The progression from Deno to Deno Deploy to celld explains why this move makes sense to us. At Cloudflare we’ll combine our work with that of the Workers and Durable Objects teams. We want to make this programming model the default way to build servers, whether you run on Cloudflare’s network or your own infrastructure.
Joining also means choosing where to focus our effort. We’ve decided to put our future development work into this shared platform rather than continuing to develop a separate runtime and hosting service. We know this is a consequential change for people who have built on Deno.
To everyone who contributed code, built businesses on Deno, reported problems, and trusted our direction: thank you. Here’s what this means concretely:
- We will support the Deno runtime for another year with monthly releases containing bug fixes and security updates. After that year we will end our development of the Deno runtime. Deno will remain open source, and we welcome others who want to continue its development.
- Deno Deploy will continue operating for six months before shutting down. We will provide migration support for paying customers moving to Cloudflare Workers.
- JSR will continue operating, with its infrastructure moving to Cloudflare.
- We will continue supporting rusty_v8 and work toward integrating it into workerd.
The need for better abstractions is especially acute with AI. Durable Objects bring together capabilities that are particularly useful for agent harnesses: inexpensive, serverless execution, persistent state, WebSockets, and a high-level JavaScript interface. This is what I’m most excited to explore and why celld focuses on Durable Objects.
Kenton Varda and I explain more in our joint post on the Cloudflare blog. If you’re building agents at scale and want to run them on your own infrastructure, please reach me now at ry@cloudflare.com.

If you wanted a dynamic website in 1994, you wrote a C program, dropped it in a cgi-bin directory, and let Apache fork it per request. Thirty-two years later, I shipped a commercial web product using fundamentally the same technology.
Everything about marketyour.games is modern. It's a web product with user accounts, a search dashboard for content creators, folders for organizing them, payments via Stripe and transactional emails via Postmark. It follows progressive enhancement and doesn't require any JavaScript.
Everything is modern except the way it was made and how it is served. Here are my thoughts on writing a real product in C and serving it via CGI in 2026.
CGI's decline was justified in 2004 but doesn't hold up in 2026.
You can write a modern web application in C. I shipped one. One binary, a SQLite file, three dependencies and the entire thing fits in your head.
The stack is BCHS: OpenBSD, C, httpd, and SQLite.
There's no framework. You write a C program that reads CGI environment variables and responds.
There's no templating language. You write C that outputs the HTML directly.
There's no separate database server. You open the database file through SQLite's C API.
There's no container. You build a statically linked binary and drop it in a folder.
Every request spawns a fresh process. Deploying a new version is replacing one file. That means no server restart and no downtime. New requests simply pick up the new binary.
OpenBSD ships with sane defaults and gives you the tools to actually secure a C program like pledge and unveil. Httpd serves from a chroot by default, so your CGI binary runs sandboxed to its own corner of the filesystem.

Only two of those are actual build dependencies: libcurl and libsodium.
Both are vendored and built as part of the project.
The result is a build with almost no moving parts. A clean build takes a few seconds and rebuilds complete in less than half a second.
Instead of serving static assets the traditional way, I route all traffic from httpd to the CGI binary. Every asset is compiled into the executable and served from memory.
CGI isn't a framework to learn. The 1.1 specification was published in 2004 and hasn't changed since.
There's no API to internalize. The entire interface is a handful of fundamental HTTP concepts:
If you understand HTTP, you already understand CGI.
It's language and platform agnostic. You learn it once and the knowledge is good forever.
A modern web application typically puts a web server like nginx in front and reverse-proxies to an application server written in another language like Ruby, Python, Go, or Rust. That always felt a bit strange to me: you essentially have two web servers, and one of them is also responsible for your business logic.
CGI gives you a single web server that calls your business logic directly. It's clear who does what.
It makes debugging simpler, too. Your application is an ordinary program you can run from a shell: pipe it a request, watch stderr, step through it with gdb.
In a sense, CGI resembles serverless architecture: a supervisor invokes your code per request, hands it a bag of environment variables, and collects the result. CGI is serverless, minus the vendor (and surprise bills).
With the rise of autonomous agents and weekly attacks on package repositories, it feels reassuring to have very few dependencies.
Most modern tech stacks come with a package manager and an ecosystem to go along with it. It's convenient, but the dependency graph balloons. One or two direct dependencies can pull in hundreds of indirect ones, each maintained by somebody you've never heard of, with publish credentials protected by a password reused since 2015.
My supply chain is a C compiler and three libraries. Compromising it would require compromising libcurl... a project the entire internet watches, not a package with eleven weekly downloads and an owner who left in 2019.
I'm a minimalist at heart. I use classic Vim with zero plugins. That means no LSP, no autocomplete, no code formatters, and no AI.
Complex tech stacks demand complex tooling: they demand a language server to wade through the layers of abstraction. But this stack is simple enough a plain editor is all you need. The entire application is a directory of C files and a Makefile.
Open a file, read it, and you know what it does.
When you do want tooling, it's not far. Sanitizers, valgrind, gdb, ctags, cscope... these are mature (well, geriatric) tools that have been refined for decades and they're a package install away on any system that can compile C.
The maturity goes further than the tools themselves: integration is built into many editors. Vim ships with native support for ctags, cscope and has a graphical gdb frontend (see :h Termdebug).
I was hesitant to write the entire frontend in C, but it wasn't nearly as painful as I imagined.

Cloudflare WorkersとDurable Objects
ベルダ氏の説明に出てくる「Workesプログラミングモデル」とは、Cloudflare Workersを用いたプログラミングモデルのことです。
Cloudflare Workersはステートレスなランタイムであり、データを永続化する仕組みと組み合わせることで基本的なプログラミングモデルが成立します。
Cloudflareでは、4つのデータ永続化サービスが用意されています。
Amazon S3互換のオブジェクトストレージであるCloudflare R2、キーバリューストアのCloudflare Workers KV、SQLiteを基盤とするリレーショナルデータベースのCloudflare D1、そしてCloudflare Durable Objectsです。
特にCloudflareにおいて特徴的なのがDurable Objectsです。
Durable Objectsは、情報をメモリ上に保持したステートフルなJavaScriptインスタンスです。分散環境において一意のIDを指定することにより、どのクライアントからでも同じインスタンスに到達し、情報にアクセスし操作できます。分散アプリケーション内で高速にアクセスでき、データの強い整合性が保たれます。
そしてベルダ氏の説明において「Workersプログラミングモデル」とは、文脈上からCloudflare WorkersとDurable Objectsの組み合わせだと考えられます。

Durable Objectsは分散アプリケーションを構築するうえで非常に優れた仕組みを提供しますが、これを用いることでCloudflareにロックインされるデメリットがありました。

Announcing AWS Lambda Web Functions
Today, we’re announcing AWS Lambda Web Functions, a new form factor that lets you run standard HTTP web applications on Lambda without rewriting your code into an event handler. You can take a standard port-listening server built with Express, Hono, Fastify, Next.js, or any Node.js framework, deploy it with a single command, and Lambda automatically handles scaling, multi-region distribution, and active CPU billing. No adapters, no infrastructure to manage, and no framework lock-in.
With this launch, AWS Lambda now offers three distinct form factors, each built on the same Firecracker isolation technology and designed for a different programming model.
Lambda Event Functions are what you already know as Lambda functions. They use the event-driven, single-concurrent handler model with wall-clock billing. We’re introducing the “Event Functions” name to highlight that programming model: your function receives an event, processes it, and returns a response. The event-driven programming model is ideal for event processing, queue consumers, and invocations triggered by other AWS services.
Lambda Web Functions use an HTTP-native programming model with multi-concurrent execution and active CPU billing. Your code listens on a port and handles standard HTTP requests. That programming model is ideal for web applications, API backends, and interactive HTTP workloads where multiple concurrent requests and I/O-heavy processing are the norm.
Lambda MicroVMs provide isolated, stateful sandbox environments with customer-managed lifecycles for running untrusted or user-generated code.
The three complement each other. An application might use Event Functions for asynchronous backend processing, Web Functions for the user-facing API and server-side rendering layer, and MicroVMs for interactive code execution features, all within the same AWS account and sharing the same operational model.
Why Web Functions
Modern web applications need to serve global audiences with fast, consistent response times while giving developers the freedom to use standard frameworks and iterate quickly. Building this today typically requires assembling multiple infrastructure components, configuring multi-region deployments, setting up latency-based routing, and tuning billing models to avoid paying for I/O wait. Developers often find themselves adapting their application code to fit a specific compute model rather than deploying the HTTP server they already have.
Lambda Web Functions removes this complexity. Each execution environment handles multiple requests simultaneously (up to 128 concurrent requests per environment), which means a burst of incoming traffic can share warm environments instead of mapping each request to a new one. Web Functions meter the CPU time your code uses, so time spent waiting on a database query or an API call consumes little CPU. Memory is metered for as long as the execution environment exists. For I/O-heavy web workloads like server-side rendering, API backends, and AI inference endpoints streaming token responses, this can reduce compute costs.

Carson Gross
I teach computer science at Montana State University. I am the father of three sons who all know I am a computer programmer and one of whom, at least, has expressed interest in the field. I love computer programming and try to communicate that love to my sons, the students in my classes and anyone else who will listen.
A question I am increasingly getting from relatives, friends and students is:
Given AI, should I still consider becoming a computer programmer?
My response to this is: “Yes, and…”
“Yes”
Computer programming is, fundamentally, about two things:
- Problem-solving using computers
- Learning to control complexity while solving these problems
I have a hard time imagining a future where knowing how to solve problems with computers and how to control the complexity of those solutions is less valuable than it is today, so I think it will continue to be a viable career even with the advent of AI tools.
“You have to write the code”
That being said, I view AI as very dangerous for junior programmers because it is able to effectively generate code for many problems. If a junior programmer does not learn to write code and simply generates it, they are robbing themselves of the opportunity to develop the visceral understanding of code that comes with being down in the trenches.
Because of this, I warn my students:
“Yes, AI can generate the code for this assignment. Don’t let it. You have to write the code.”
I explain that, if they don’t write the code, they will not be able to effectively read the code. The ability to read code is certainly going to be valuable, maybe more valuable, in an AI-based coding future.
If you can’t read the code you are going to fall into The Sorcerer’s Apprentice Trap, creating systems you don’t understand and can’t control.
Is Coding → Prompting like Assembly → High Level Coding?
Some people say that the move from high level languages to AI-generated code is like the move from assembly to high level programming languages.
I do not agree with this simile.
Compilers are, for the most part, deterministic in a way that current AI tools are not. Given a high-level programming language construct such as a for loop or if statement, you can, with reasonable certainty, say what the generated assembly will look like for a given computer architecture (at least pre-optimization).
The same cannot be said for an LLM-based solution to a particular prompt.
High level programming languages are a very good way to create highly specified solutions to problems using computers with a minimum of text in a way that assembly was not. They eliminated a lot of accidental complexity, leaving (assuming the code was written reasonably well) mostly necessary complexity.
LLM generated code, on the other hand, often does not eliminate accidental complexity and, in fact, can add significant accidental complexity by choosing inappropriate approaches to problems, taking shortcuts, etc.
If you can’t read the code, how can you tell?
And if you want to read the code you must write the code.
AI is a great TA
Another thing that I tell my students is that AI, used properly, is a tremendously effective TA. If you don’t use it as a code-generator but rather as a partner to help you understand concepts and techniques, it can provide a huge boost to your intellectual development.
One of the most difficult things when learning computer programming is getting “stuck”. You just don’t see the trick or know where to even start well enough to make progress.
Even worse is when you get stuck due to accidental complexity: you don’t know how to work with a particular tool chain or even what a tool chain is.
This isn’t a problem with you, this is a problem with your environment. Getting stuck pointlessly robs you of time to actually be learning and often knocks people out of computer science.
(I got stuck trying to learn Unix on my own at Berkeley, which is one reason I dropped out of the computer science program there.)

AI doesn’t have to be a detriment to your ability to grow as a computer programmer, so long as it is used appropriately.
“, and…”
I do think AI is going to change computer programming. Not as dramatically as some people think, but in some fundamental ways.

How Machines Learned Precision
https://glinscott.github.io/how-machines-learned-precision/
以下は17～18世紀に活躍した発明家のヘンリー・モーズリーが1800年に生み出したねじ切り旋盤です。労働者が左側のハンドルを回すと、工具をのせた台車が真っすぐなレールの上を少しずつ移動し、ねじ山を切削できる仕組みになっています。
モーズリーのねじ切り旋盤は、ねじ山を一定の大きさに統一して量産できる初めてのねじ切り旋盤でした。これ以前は、特定のボルトとナットのペアでないとピッタリかみ合わさりませんでしたが、モーズリーの発明によって規格化されたボルトとナットが量産できるようになりました。
しかし、モーズリーのねじ切り旋盤を生み出すには、そもそも旋盤部品の精度が正確でなくてはいけません。そもそもレールが曲がっていると工具もズレてしまい、切削されるねじ山が不均一なものになってしまいます。そこでリンスコット氏は、さまざまな部品を作る工作機械の精度がどのように向上したのかについて、例を挙げて説明しています。
◆シリンダー
産業革命において重要なのは蒸気機関の実用化であり、これには高温・高圧の蒸気を送り込む円筒形のシリンダーが必要です。しかし、円筒の鋳造品に片側から回転する工具を差し込んで内部を切削する従来のやり方では、工具を支えるバーが自重でたわんだり、でこぼこの壁によって刃物が揺れたりして、真っすぐにきれいな穴を空けることは困難でした。
そこで1775年頃に鉄工所経営者のジョン・ウィルキンソンが開発したのが、「重いバーを円筒形に貫通させて固定し、バーに沿って回転する工具をスライドさせる」という仕組みです。両端を固定したことで途中でのブレが大幅に軽減され、蒸気機関のエンジンに利用できる非常に高い精度のシリンダーを製造可能となりました。
◆工具送り台
かつての旋盤では、回転する部品に対して旋盤工が自らの腕で工具を支え、工具を部品に接触させて切削していました。しかし、鉄を切削する際には強い力が発生するため、どうしても旋盤工の腕が揺れて工具の位置もずれてしまうという問題がありました。この状態では、きれいな円を作り出すことはできません。
そこで技術者たちは、工具を鋳鉄製の送り台に取り付けて、ねじで少しずつ送り出すという方式を生み出しました。これにより切削の際の力が旋盤工の腕ではなく鉄によって支えられ、よりきれいな切削作業が可能となりました。
◆平らな面
正確な作業を行うには機械の部品が真っすぐで平らな必要がありますが、鉄などの表面に「平らな面」を生み出すことは非常に難しい課題です。一般的には手作業によるヤスリがけで平らな面を作っていましたが、手が少しでもズレるとでこぼこや傾斜が残ってしまいます。
そこでヤスリがけ職人たちが考案したのが、「平らな基準板の上に塗料を塗って対象の金属板に重ね、色が付いた部分だけを削り取っていく」という仕組みです。たとえば以下の図で青色の塗料が付いた部分だけを削ります。
これを何度も繰り返せば次第に平らになっていき、最終的には「重ねると面全体にぴったり塗料が付く状態＝平らな面」になるというわけです。
しかし、これには「基準板が平らであるということをどうやって保証すればいいのか」という問題があります。たとえば以下の図を見ると、基準面となる「A」の表面がでこぼこなため、対象の金属板「B」もでこぼこなのに塗料がうまく付着してしまっています。
そこでヤスリがけ職人たちは、「3つの板を使って平らな面を作り出す」という方法を編み出しました。以下のように「A」「B」「C」の3枚を用意し、「AとB」「BとC」「CとA」という異なる組み合わせで何度もヤスリをかけていけば、どれか1つのペアだけがかみ合うことが起きないため、かなり平らな面が生み出せるというわけです。リンスコット氏は、「これは工学における最も美しいアイデアのひとつです」と述べました。
◆ねじ
モーズリーがねじ切り旋盤を開発する前は、各工房が手作業またはダイスという工具を使ってねじを製造していました。これらのねじに存在するねじ山は不均一でしたが、モーズリーのねじ切り旋盤にも「リードスクリュー」と呼ばれる長いねじがあり、これが工具をのせた台車を動かしてねじ山を切削していました。リードスクリューが不均一だと切削されるねじ山も不均一になってしまうため、モーズリーは「ねじ切り旋盤を作る前に正確なねじを作る」という課題に取り組む必要がありました。
ねじ山の間隔(ピッチ)はねじの直径と直線の傾きによって決まります。そこでモーズリーは木やスズといった柔らかい素材で円筒を作り、この間に角度を正確に固定したナイフを押し当てて円筒を回転させました。円筒を回転させるとナイフが浅い溝を刻み、この溝に沿って滑る形でナイフが移動し、ねじ山が作られました。リンスコット氏は、「モーズレーは既存のネジを模倣することなく、独自のネジを作り出したのです」と述べています。
さらにモーズリーは2つのねじを作り、それぞれのねじに1つの工具を取り付けて同時ねじを回転させることで、「2つのねじに生じた誤差の半分」の誤差で新しいねじを作る装置も考案。これにより、どんどん作られるねじの誤差を少なくして正確なねじを作り出しました。
また、モーズリーは1つのねじから複数のピッチを持つねじを生み出すため、歯車を組み合わせてピッチを変える機構も考案しました。

AI時代のサイバー攻撃、度重なる情報漏洩からの守りを固めるための政府への7つの提言私案
個人情報の漏洩事案が過去に例をみないペースで公表されている。現在見えている事案はあくまで氷山の一角で、公表や検知すらされていない事案も数多く存在すると思われる。また、サイバー攻撃能力の高いAIの拡散によって今後さらに状況が悪くなる可能性が高い。ライフラインに関わる領域が攻撃されれば産業や人命にも関わる。そのような重大事案が発生する前に一刻も早く動かなければならない。一方で、具体的な打ち手に関する議論は国会の内外でまだまだ足りていない。そこで本記事では具体的に政府がとるべき打ち手を7つ提案したい。
今回の提言にあたり、多くの当事者、有識者に協力をいただいた。漏洩を経験したり不安を感じたりしている方々とは1,251件、セキュリティの専門家や事業者の方々とは278件のAIによる匿名インタビューセッションを実施した。また、セキュリティの専門家の方（大企業のCISO、政府系機関の専門職、セキュリティ企業のエンジニア、セキュリティ系スタートアップの経営者、AI安全性の研究者等）にオンライン/オフラインのインタビューも7件実施した。
下記に示す見解は党を代表するものではなく、安野個人としての提言である。ゆえに、積極的にまだ粗いアイデアも入れているしやや総花的である。本記事はオープンβ版のような立ち位置のものであり、是非、有識者の方にはツッコミをいただきたい。記事末尾にはコメント用のGoogle Docsへのリンクもある。引き続き党内外での議論を通じて磨き込んだ上で、可能であれば党として正式に諮った上で、関係各所に働きかけていこうと考えている。
状況認識
過去最悪ペースで情報漏洩事案が公表されているが、これはまだ氷山の一角である
国内におけるサイバー攻撃の被害は、2026年に入って急激に拡大している。民間の集計(humanhacker.ai)によれば、国内で公表されたサイバー事案は1月の29件から8月に67件、9月には75件へと増えた。別の集計(トレンドマイクロ)でも、企業や自治体が今年公表した不正アクセスなどの被害は9月末で600件に達し、2025年通年の593件をすでに上回っている。
漏洩の規模も大きい。東京商工リサーチの調査によると、100万件以上の個人情報漏洩は、2026年10月5日時点で10件に達した。2025年通年の6件をすでに上回り、1,000万件以上の漏洩に限っても、2012年から2025年までの14年間で3回だったものが、2026年だけですでに3回起きている。
守りが固い組織でも被害は相次いでいる。政府機関のデジタル庁、金融機関の大和証券、クラウド基盤を提供するIDCフロンティアなどが相次いで被害を受けた。IDCフロンティアの事例では、契約する495の企業・自治体に影響が及んだ。
ここまで挙げただけでも過去最悪のペースだが、重要なのは、公表されている漏洩が氷山の一角にすぎないということである。
行政への報告件数と、企業が自主的に公表する件数との間には、極めて大きな隔たりがある。英国政府のCyber Security Breaches Survey 2025/2026によれば、侵害を経験した企業のうち、最も影響の大きかった侵害を組織外へ報告したのは40%で、外部へ報告した企業の中でも警察へ届け出たのは6%にすぎない。米国では2023年1月にFBIがランサムウェア集団Hiveを摘発した際、長官は被害者のうち法執行機関に届け出たのは約20%だったと述べている。日本には公的統計が存在しないが、英米の報告率を踏まえれば、公表されている事案の背後により多くの侵害事案が起きている可能性が高い。
高いサイバー攻撃能力を持つAIが誰でも手に入るようになり、今後状況はさらに悪くなる可能性が高い
8月28日、中国のZ.aiは新しいモデル「GLM-5.3」をオープンウェイトとして一般公開した。Anthropicが公表した検証では、既知の脆弱性を対象にしたベンチマークにおいて、GLM-5.3は410回の試行中50回、動作する攻撃コードを完成させたという。2026年4月に提供された「Claude Mythos Preview」は、同じ評価で56回であり、GLM-5.3の性能はほぼMythos並みと言える。
GLM-5.3には悪用されないように安全装置がついているものの、比較的容易に回避が可能である。公開から数日のうちに、安全装置を外した改変版が複数の開発者によってインターネット上で配布された。Abliterationと呼ばれる手法を使うと、大規模なファインチューニングをしなくても、計算コスト70万円程度で、モデルの能力をほぼ保ったまま有害な要求への拒否を大幅に弱められる。
筆者は2026年4月15日の参議院デジタル社会・AI特別委員会で、米国企業以外も含む他社がMythos Preview相当の能力を持つモデルを開発できるまで早くて数か月、遅くても1年以内であり、AIを使った攻撃能力は早期に拡散する恐れがあるため対策を急ぐ必要があると申し上げていた。実際にこれが実現し、高い攻撃能力を持つオープンウェイトモデルがMythosの登場から5か月ほどで世界中に拡散してしまった形となる。
悪用から検知、公表までにかかるリードタイムを踏まえると、10月初旬までに公表されている漏洩の多くは、まだこのレベルのAIによるものではないと考えるべきだ。侵入から検知までにかかる時間の中央値は14日(Mandiant M-Trends 2026)、国内の不正アクセス事案で発生から公表までの中央値は56日、発覚から公表までは平均77日であり、技術の拡散から実際の公表までは時間差がある。これまでの事案でもAIは活用されているが、一世代以上前のモデルである可能性が高い。

AI時代のサイバー攻撃から守りを固める7つの提言
1) AIにはAIを: 人間が守るという前提を捨て、AIで継続的に守りを固める
AIによってさまざまな前提が変わった。脆弱性の公表から悪用までの時間は年々短くなり、脆弱性公表以前に悪用されるケースも増えた。つまり、パッチを素早く適用したとしてもシステムは守れない。既製ソフトウェアの欠陥だけでなく、個別企業が独自に構築したアプリケーション固有の欠陥も、AI が見つけ出すようになっている。攻撃はますます安価になり、2026 年 9 月に報告された事例では、攻撃者が標的 1 社に費やした AI モデルの利用料は平均4,000円前後であったという。攻撃対象を慎重に選ぶのではなく、脆弱性があれば無作為に誰であれ攻撃されるようになった。この事態に対応するためには人間だけでは限界がある。だからこそ、防御側もAIを最大限活用しなければならない。
具体的には下記を行う。
- AIによる継続的な脆弱性チェックを推奨する。専門家インタビューにおいても「資産の棚卸しやリスクアセスメント、監査は年1回が基準で、環境の変化に追いついていない」という意見があった。ISMSやプライバシーマークなどの認証においても年に一度のチェックが標準的である。これを見直し、年に一度ではなく、継続的に検証と修正を繰り返す運用を標準にする。米国FedRAMPという認証では、エクセルやPDFでチェックシートに回答する従来の形式ではなく、jsonで検証項目が連携され、AIエージェント向けの指示がAgents.mdによって整備され、数日に一度自動的に監査をする仕組みが実装されている。米Vanta社はAPIで企業のシステム群（クラウド、社内ツールなど）に直接つないで、セキュリティ監視とコンプライアンス対応を自動化するツールを提供している。人間の介在を前提としない(Human in the loopではない)チェック体制として参考にするべきである。
- 国内の防御側が継続的にフロンティアモデルを使えるよう、外交で確保する。米CISAは2026年6月にMythos Previewへのフルアクセスを得たと報じられた。Anthropicは10月6日に審査を通過した専門家・組織向けのCyber Verification Programを3段階に拡大し、最上位モデルへのアクセスを広げた。日本においてもYATA-Shieldなどの枠組みがあるが、政府は継続的に複数のフロンティアラボと交渉を続け、日本の機関、企業がアクセスを得られるようにすべきである。
- 国が高度なオープンウェイトモデルの検証環境を用意し、計算資源の支援をする。セキュリティ企業が今後はプライベートモデルだけではなく、オープンウェイトモデルを活用するケースが増える可能性がある。これに備え、ABCI等の既存の公的計算基盤に、自己ホスト型モデル(GLM-5.3などのオープンウェイトモデル)の検証環境を置き、審査制・利用ログ付きで認定事業者や企業に貸し出す。
- 企業に補助金ならぬ「補助トークン」を配る。セキュリティ検証用のAI推論のトークンを、用途・金額上限・成果指標を定めて配布し、より多くの企業が安価にシステムの守りを固められるようにする。既存のサイバーセキュリティお助け隊サービスや、デジタル化・AI導入補助金のセキュリティ対策推進枠を拡張する形を想定。補助金だけではなく補助トークンとして現物支援も行うことで、直接的にAIによる守りを届けることができる。
- 国産のサイバーセキュリティ専門モデルの開発を支援する。機密情報を国外に送らずに防御の検証を行えること、国内の業務システムに対応できること、海外事業者の提供方針が変わっても防御を継続できることを中長期で目指す。国産であることだけで安全と判断せず、モデルや運用環境の検証もあわせて行い、国内に開発・評価・運用の技術と人材を蓄積するべきである。
