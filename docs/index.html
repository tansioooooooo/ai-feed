DeepInfer is the high-performance inference framework that powers DeepSeek's large-scale production services. This open-source release provides offline inference with the core features needed for serving at scale.
Supported models:
- DeepSeek-V4.1-Flash
Supported features:
- Optimized kernels, model and sampler runtime
- Parallelism: Attention DP / balanced CP, MoE EP + EPLB
- DSpark and confidence-scheduled verification
- SWA bounded replay
- Asynchronous scheduling (zero-overhead batch scheduler)
- Batch-invariant inference
- Deterministic sampling
- Structured outputs
Feature details and configuration
- Optimized kernels: FlashMLA, DeepGEMM, DeepEP, TileKernels, DeepSelect, and custom TileLang kernels.
- DSpark and confidence-scheduled verification: accelerate decoding with draft tokens and use confidence estimates to schedule verification. Set DEEPINFER_ENABLE_MTP_VARLEN=1; DEEPINFER_USE_NEXTN_DECODE controls the maximum draft length (default: 5).
- Decoder SWA bounded replay: reduce decoder prefill work by replaying only a bounded suffix. Set DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact and DEEPINFER_YOCO_PREFILL_KEEP_TOKENS=140 for the default V4.1 settings; the retained suffix must cover the SWA window plus the maximum backtracking length.
- Asynchronous scheduling: overlap CPU batch scheduling with device execution. Enabled by default.
- Batch-invariant inference: keep model results identical across different batch compositions. Enable with DEEPINFER_BATCH_INVARIANT=1 (NVIDIA only).
- Deterministic sampling: produce identical outputs for identical input tokens and sampling parameters. Set DEEPINFER_BATCH_INVARIANT=1 DEEPINFER_ENABLE_MTP_VARLEN=0 and pass a fixed seq_seed to SamplingParams (NVIDIA only).
- Structured outputs: constrain generation to a regex, JSON schema, or EBNF grammar. Pass so_args={"schema_type": ..., "schema": ...} to SamplingParams; see examples.

- Load balancing across data-parallel replicas for both prefill and decode
- Linux

The private keys of eight eMudhra intermediate CA certificates have been compromised. They chain to roots trusted by the Mozilla, Microsoft, Apple and Chrome root programs and by many downstream trust stores.
Root programs are run by operating system and browser vendors to vet certificate authorities and decide which ones their products trust. Trust stores are the lists of trusted root certificates that operating systems, browsers, language runtimes, libraries and applications use to verify certificates, and many are based on the root programs' lists.
To demonstrate that the keys are compromised, the original reporter Wayne signed the following message with the private key of each of the eight intermediate CAs and reported it to the Root Program Teams on the 17th of October:
We have a problem here - Wayne
proof.zip contains the message, and for each intermediate the certificate, its public key and a signature on the message. To verify with OpenSSL:
openssl x509 -in EM-DV-TLS-CA-G3B.crt.pem -noout -pubkey | diff - EM-DV-TLS-CA-G3B.pub.pem
openssl dgst -sha384 -verify EM-DV-TLS-CA-G3B.pub.pem -signature EM-DV-TLS-CA-G3B.sig message.txt
The root programs and many downstream trust stores have taken action to protect their users. The certificates have been blocked in Firefox and Chrome since the 17th of October, on Microsoft platforms since the 20th and on Apple products since the 22nd.
The issue was responsibly disclosed to downstream trust stores on the 19th of October. Many have already released updates or are in the process of releasing updates.
An attacker with the private key of any of the compromised intermediate CAs could impersonate any website or service.
This has already been remediated by Mozilla, Microsoft, Apple, and Chrome for their users through their tools for distributing revocation information such as OneCRL, CRLite and CRLSets.
The CA has also revoked the compromised intermediate certificates. However, many other clients do not consume revocation information and require software updates to ensure they no longer trust the compromised intermediates. These include applications and libraries that ship their own CA bundle, and apps built on Electron, such as Slack and Discord. Electron apps only pick up Electron's fix once they are updated to a version built on a patched Electron release. Updating the operating system or browser may not be enough for these clients.
A ✅ only means that the connection failed. Browsers do not tell the page why, so a network problem looks the same as a rejected certificate. To double-check, open the link in that row: if it loads without a warning page, the browser is vulnerable.
On 22nd October 2026, two chains marked No CT were added. Their leaf certificates were never logged to Certificate Transparency (CT), so clients that enforce CT reject them even if they still trust the intermediate. A successful connection to these hosts means the client trusts the compromised intermediates and does not enforce CT. As described below, these are the clients that can be attacked without anyone noticing.
To check curl or other command-line clients, run:
curl https://dv-g3b-emudhra.we-have-a-problem.com/
curl https://dv-g3b-aaa-emudhra.we-have-a-problem.com/
A certificate error means the client does not trust the compromised intermediates. To check whether the client also accepts certificates that were never logged to CT, run:
curl https://dv-g3b-noct-emudhra.we-have-a-problem.com/
curl https://dv-g3b-aaa-noct-emudhra.we-have-a-problem.com/
Most browsers enforce CT, but many non-browser clients, including curl, do not which places them at greater risk.
To check a trust store offline, chains.zip contains the certificate chain served by each of the fourteen hosts above in PEM format, with instructions for verifying them with OpenSSL.
The private keys for the intermediate certificates were incorrectly generated by the CA. This means that anyone can recover them from the certificates.
This would have been possible since the certificates were created in April 2025. There are no entries in the certificate transparency logs for these intermediates in that period, indicating that CT-enforcing clients like Firefox, Chrome, Edge and Safari could not have been attacked.
However, many clients outside of the browser ecosystem do not enforce Certificate Transparency. We do not know if attackers exploited the flawed key generation to target these clients.

How I got over 300 Tor exit nodes removed
On Friday Oct 2, 09:35am, 333 infected exit nodes started a coordinated campaign to intercept SSH connections and gather as much unencrypted data as possible.
To give you a sense of scale, all of Tor has around 3000 exit relays, so roughly 10% were under their control.
The attackers had gained access to the servers two months earlier, in August, and quietly deployed their Ebury 1.8.3 payload (an OpenSSH backdoor and credential stealer for Linux).
The Attack
The attack appears to have had two primary goals:
- Gather as much unencrypted mail traffic as possible
- Intercept SSH connections (MITM)
By blocking certain ports, they made their exit nodes handle only unencrypted mail traffic. An interesting writeup by one of the victims (a veteran Tor operator) goes into great detail about that: lists.torproject.org/mailman3
In this post I'll focus on the second attack, the SSH MITM. If you happen to get a circuit that exits over one of those 333 infected exit nodes, you won't notice anything at first. Encrypted web traffic is forwarded as usual, but if you attempt an SSH connection over Port 22, you're unknowingly redirected to one of 12 SSH interception servers.
That's exactly what happened to me on Friday morning. My SSH connection got redirected, and I was greeted with this warning:
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@ WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED! @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
IT IS POSSIBLE THAT SOMEONE IS DOING SOMETHING NASTY!
Someone could be eavesdropping on you right now (man-in-the-middle attack)!
It is also possible that a host key has just been changed.
The fingerprint for the ED25519 key sent by the remote host is
SHA256:6baCZCPsl+AfQuujUS81fMEE/C7UeJ+AwjrImqmDB3E.
Please contact your system administrator.
But if you ignore the warning and go ahead with the login, the attacker does three things:
- Steals your password
- Opens a connection to your server and observes each command you type (MITM)
- Opens a second connection to your server and infects it with Ebury
Getting them taken down
On Friday evening I contacted the Tor Project's network health team with my findings. They confirmed this was something new and got to work by contacting the affected relay operators.
"We've not seen an attack like that before."
- Tor Network Health Team
- Fri Oct 2: Interception started.
- Sun Oct 4: The Tor network health team made an announcement to the operators, who began shutting their exit nodes down.
- Sun Oct 4: The relays were marked BadExit, so clients would no longer use them to exit traffic.
- Mon Oct 5: The attackers restarted many of the relays, but since they were already flagged they could only serve as middle relays.
- Mon Oct 5: All infected servers were shut down, partly by the operators and partly by the attackers.
In their announcement, the health team described the pattern:
"It seems the attacker is gaining access to Linux based hosts and when these machines are running non-exits they are editing the torrc file and turning them into exits to be able to carry out the SSH attack."
- Tor Network Health in the announcement

Consider running a relay: community.torproject.org/relay/setup/
The technical part: how I found them
In this part I'll go into detail about how I found all the infected exit nodes.
Using exitmap, I built a simple script that did the following: it pinned an exit node, then opened an SSH connection from my server A to my server B.
- Server A checked whether it received the correct SSH fingerprint from server B.
- Server B checked whether the connection came from the pinned exit node or from one of the 12 SSH interception servers.
I ran the script against every single one of the ~3000 exit relays. Around a dozen served a fake fingerprint, and over 300 didn't intercept anything but redirected through those same interception servers. Redirecting alone was enough to confirm the exit was infected.
In some further analysis I used sshesame as a honeypot. Tricking the MITM into logging into the honeypot showed that they used paramiko (a Python SSH library) and also how they attempted to install Ebury using Perl.

> sudo bash -c 'echo <base64> | base64 -d | perl'

Checking for permissions first, then executing a base64-encoded command.

アップデートを終えたあとに、多くの人が気になるのが「すでに攻撃されていないか？」という点だと思います。
実際に、Datadog Security Labsの解説記事によると、10月21日の時点で悪用の報告が複数あり、公開の4日前にあたる10月17日には攻撃の試みが観測されていたとされています。
つまり、修正版を入れた日より前に、攻撃を受けていた可能性があるということです。
PHPをアップデートしても、すでに置かれた不正なファイルや、起動された不正なプログラムは消えません。この記事では、サーバーに残る痕跡をどこで、どう確認するかを整理します。
調べる期間を決めておく¶
調査を始める前に、まず「いつからいつまでのログを見るか」を決めます。
今回は、公開の4日前にあたる10月17日には攻撃の試みが観測されています。そのため、少なくとも10月17日から、自分のサーバーでPHPのアップデートが完了した時刻までが調査の対象になります。
ここで困るのが、ログが残っていないケースです。ログローテーションの設定によっては、1週間ほどで古いログが削除されてしまいます。
# ローテーションされた古いログが残っているか確認する
ls -l /var/log/nginx/ /var/log/apache2/
調査が終わるまでは、ログを別の場所へコピーして保管しておくと安心です。
攻撃の痕跡は「3つの場所」で探す¶
php2shellの攻撃を調べるときは、次の3つの場所を見ます。
大切なのは、1つの痕跡だけで「攻撃された」「攻撃されていない」と判断しないことです。
例えばメモリ不足のエラーは、普段の大きなアップロードでも起きます。反対に、攻撃が成功した場合でも、エラーが出ずに正常な応答（HTTP 200）が返ることがあります。
3つの場所の記録を、時刻を合わせて突き合わせることが調査の基本になります。
① 不審なフォーム送信がないか確認する¶
攻撃リクエストの特徴¶
Datadogが検証した攻撃では、普通のWebフォームと同じ形式（application/x-www-form-urlencoded）のPOSTリクエストが使われていました。
見た目はただのフォーム送信ですが、中身には次のような特徴があります。
- 約3.5MBもある、異常に長いフィールド名が含まれる
- 名前が空のフィールドに、制御文字（ヌルバイトなど）を含むバイナリデータが入っている
ログインフォームのような通常の入力欄で、数MBの項目名が送られてくることはまずありません。
アクセスログで大きなPOSTを探す¶
まずは、Webサーバーのアクセスログから、PHPへのPOSTリクエストを確認します。
# POSTリクエストの多い送信元IPを数える（Nginxの例）
sudo grep '"POST ' /var/log/nginx/access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head
標準的なログ形式では、リクエストの大きさ（ボディのサイズ）は記録されません。Nginxなら$request_length、Apacheならmod_logioの%Iをログ形式に加えておくと、受け取ったバイト数を残せます。
今回のような事態に備えて、普段からリクエストサイズを記録しておくと、あとの調査がずっと楽になります。
WAFやリバースプロキシでの対策¶
WAF（Web Application Firewall）やリバースプロキシを使っている場合は、次のようなリクエストを検知・遮断するルールを検討します。
- フォームのフィールド名が異常に長い
- フォームの値に、想定しない制御文字が含まれる
制限値は、自分のアプリケーションの正常な通信を基準に決めます。いきなり厳しくすると、正規のアップロードまで止めてしまうからです。
WAFが大きなリクエストを途中までしか検査しない設定になっていると、検査されなかった部分に攻撃の中身があっても見逃します。WAFの検査上限と、アプリケーションが受け付ける上限が合っているかも確認しましょう。
② PHPのエラーログを確認する¶
「Unknown on line 0」のメモリ不足エラー¶
攻撃の試行では、PHPのエラーログに次のような致命的エラーが記録されていました。
PHP Fatal error: Allowed memory size of 16777216 bytes exhausted
(tried to allocate 3500032 bytes) in Unknown on line 0
注目したいのはUnknown on line 0の部分です。
通常のメモリ不足なら、どのPHPファイルの何行目で起きたかが記録されます。Unknown on line 0は、スクリプトが動き出す前、リクエストを受け取って準備している途中でメモリが足りなくなったことを示しています。
ログは次のように検索できます。
# PHP-FPMのログから探す（パスは環境に合わせて変更）
sudo grep -n "Unknown on line 0" /var/log/php*-fpm.log
# Apache（mod_php）の場合はエラーログに出る
sudo grep -n "Allowed memory size" /var/log/apache2/error.log
ログの保存場所が分からない場合は、Apacheのログの保存場所や、PHP-FPMの設定ファイル（error_logの項目）を確認してください。
ワーカーの異常終了¶
攻撃者がメモリの位置を推測し損ねると、Webサーバーのワーカーが異常終了することがあります。Apacheでは次のようなログが残ります。
AH00052: child pid ... exit signal Segmentation fault (11)
sudo grep -n "Segmentation fault" /var/log/apache2/error.log
Segmentation faultは、プログラムが不正なメモリにアクセスして強制終了したことを表します。
NginxとPHP-FPMの構成では、ワーカーの異常終了はPHP-FPMのログに記録されます。あわせて、Nginxのエラーログに上流（PHP-FPM）との接続が切れた記録が残ることもあります。
# PHP-FPMのワーカーがシグナルで終了した記録
sudo grep -n "exited on signal" /var/log/php*-fpm.log
# Nginx側で上流との接続が途中で切れた記録
sudo grep -n "upstream prematurely closed" /var/log/nginx/error.log
どちらも、普段から一定数は出ることがあるログです。件数が急に増えた日時がないかに注目すると、いつもとの違いに気づきやすくなります。
これらのエラーが、①の大きなPOSTリクエストや、上流の接続リセットと同じ時刻に集中していないかを確認します。
ただし、メモリ不足もワーカーの異常終了も、正当な処理で起きることがあります。それだけで攻撃と断定はできません。
CVE-2026-109619で見るポイント¶
もう1つの脆弱性（CVE-2026-109619）については、外部からアクセスできるURLで、次のようなログが増えていないかを確認します。
- 起動直後の設定に関する警告
- 終了処理（シャットダウン）中の診断メッセージ
- 致命的なエラー
- 実行時間の上限超え（タイムアウト）
PHPの公式アドバイザリでは、こうしたイベントが、前のリクエストの内部状態が残ってしまう経路と関係している可能性が示されています。
③ Webサーバーが起動したプロセスを確認する¶
もっとも直接的な証拠は「シェルの起動」¶
3つの中で、攻撃の成功をもっとも直接的に示すのが、Webサーバーのワーカーがシェルを起動しているという痕跡です。
Datadogの検証では、Apacheのワーカーがシェルを起動し、そのシェルが攻撃者のサーバーへ外向きの通信を張っていました。
apache2 (www-data)
└── sh -c <リバースシェルのコマンド>
└── bash [外部サーバーへの通信]
本来、WebサーバーはHTTPリクエストを処理するだけで、シェルを起動する必要はほとんどありません。
Linuxで確認するコマンド¶
まず、Webサーバーの実行ユーザー（Ubuntuならwww-data、RHEL系ならapacheやnginx）が動かしているプロセスを確認します。
# プロセスの親子関係をツリーで表示する
ps -ef --forest | less
# www-data が実行しているプロセスだけを見る
ps -u www-data -o pid,ppid,lstart,cmd
apache2やphp-fpmの下に、shやbash、見覚えのないプログラムがぶら下がっていないかを確認します。
あわせて、外部への通信も確認します。
# 確立している通信と、それを持つプロセスを表示する
sudo ss -tnp state established
Webサーバーの実行ユーザーのプロセスが、見覚えのない外部のIPアドレスへ接続している場合は要注意です。
「普段の動き」を知っておく¶
アプリケーションによっては、画像変換などのために、意図して外部コマンドを実行するものもあります。
そのため、普段どんなプロセスが起動しているか（ベースライン）を把握しておくことが大切です。普段の動きが分かっていれば、いつもと違う動きにすぐ気づけます。
攻撃の検知を、特定のコマンド名やHTTPのステータスコード、ワーカーの異常終了に頼らないようにしてください。改良された攻撃では、リクエストは正常な応答を返し、ワーカーも動き続けます。
不審なファイルや自動実行の設定も確認する¶
攻撃者がシェルを手に入れると、次にアクセスするための仕掛けを残すことがあります。代表的なのは、Webから実行できる不正なPHPファイル（Webシェル）や、定期的に動く不正なプログラムです。
ドキュメントルートの中で、調査期間に新しく作られたり変更されたりしたファイルを探します。
# 10月17日以降に変更されたPHPファイルを探す（パスは環境に合わせて変更）
sudo find /var/www -type f -name '*.php' -newermt '2026-10-17' -ls
# 一時ディレクトリに置かれた実行ファイルも確認する
sudo find /tmp /var/tmp /dev/shm -type f -newermt '2026-10-17' -ls
デプロイやプラグインの更新でも変更日時は新しくなるため、見つかったファイルが自分たちの作業によるものかを照らし合わせます。
あわせて、Webサーバーの実行ユーザーに定期実行の設定が追加されていないかも確認します。
sudo crontab -u www-data -l
ls -l /etc/cron.d/

スイッチングハブは使いこなしの宝庫。AV向けのハブ選びやポートの使い方
2026年10月23日 09:00
今回からは家庭内LANによる音楽配信や動画配信にまつわるお話にしよう。
特に昔気質のオーディオ愛好家ならば、音源としてもっぱら各種の音盤を回し、各機器の組み合わせやケーブル類の選択、さらにはスピーカーの「ミリ単位」の微調整を要する設置法の問題などに汗を流してきたことだろう。
しかし、デジタルネットワーク系のオーディオ再生となると勝手が違うかも。LANとかルーターとか、スイッチングハブとかにまつわる耳慣れない用語や機器に戸惑う向きも多いことと思う。かくいう私も同様ではあった。
まずはオーディオ系について。デジタルファイル化された音声データが地球上を駆け巡るネットワークを通じて自分の家にまで届き、ハイレゾの高音質データまで再生可能になったことは朗報に違いない。その代わり、音楽ディスクの売れ行きは衰退傾向になってきたけれど。
接続や設定については、光回線関係の回線業者、設置業者に頼めば、ONU(光回線端末)からWi-Fiルーターまでは施設してくれるので問題はない。現場でのチェックは手持ちのパソコンにて、LANケーブルを使う有線や無線のWi-Fi接続においてインターネット回線が使えるかどうかで済む話だ。
そこから先、LANのスイッチングハブを用意して音声デコード用機器の近くに設置し、必要な機器を有線LANで接続することになる。音楽配信ならネットワークプレーヤーの単体機、あるいはCDプレーヤー、D/Aコンバーター、AVアンプなどに備わっているネットワークプレーヤーの機能を使って再生することになる。もちろん、ストリーミング再生だけでなく音楽データをメモリーにストレージすることも可能であり、そのためにはPC経由にしたり、ストレージを重視する専用機器を用意すればいい。
スイッチングハブの音質対策
ともあれ、ここで紹介するのは、音楽配信のストリーミング再生をする最小限のシステムの末端近くにおける音質対策となる。
そもそもルーターから導いたLANケーブルはスイッチングハブなど経由せずとも、ネットワークプレーヤーに接続するだけで、ただちに音楽を再生できるようになっている。ならば、なぜスイッチングハブが必要になるのかというと、ハブを介すると音質がいいからだ。これは筆者が各所で何度も確認していることだし、オーディオファンにも広く普及している対策方法だ。
しかし、音質優先で考えるとむやみに分岐すると複雑なノイズのループを生じるし、そもそもそこに接続される機器はほとんど例外なくスイッチング電源を使用しているだろう。つまり強いノイズの発生装置を多数ぶら下げたところに、AV機器を接続すると、ノイズの影響を受けてしまうわけだ。
映像バッファーの効用
それで理想としては多数のポート(端子)を備えているスイッチングハブを使っていても、余計な機器を接続せず、ルーターとプレーヤー機器のみを接続し、データの流れをシンプルにしたほうが望ましいのである。
こういうことについて自信をもって言えるのは、実機で実験したことがあるからだし、さかのぼればホームシアターにおける映像機器の「セレクター」あたりから続いているお題だ。
というのは、映像セレクターを経由させると、画質音質が改善される、と言い続けてきたのはこの私だからだ。しかし当時はほとんど理解されなかった。ピュアイムズがオーディオの世界を席巻する中で、ただの中継機能とはいえ、映像バッファー(ビデオアンプ)や音声バッファー(音声アンプ)という“余分なもの”を経由させれば、必ず画質、音質の劣化を招く、と固く信じられていたからだ。
しかし、実際は注意深く配線し、電源ラインを整えると、映像セレクターを経由させた方が画質、音質が向上することが確認できたのだ。ノイズのループが遮断されるからだ。信号伝送の途中におけるわずかな劣化よりも、方々を自在に駆け巡るループノイズの方が悪さをするのである。
さらには、なつかしや、MUSE(ミューズ)方式のハイビジョン放送やMUSE LD(レーザーディスク)が登場したころ、より鮮明な映像の変化としてそれを体験できたのだ。
それは、従来映像と同じように通常の映像セレクターにMUSE信号を経由させることで試すことができた次第。これを意外なことという向きもあるだろうけど、MUSEといっても1フレームを4分割してそれが4回で1フレームを完成させるという簡易型の時分割式アナログ情報圧縮だったので可能だったわけだ。
それでも信じないお堅い面々には、手製の汎用ビデオアンプを電池駆動する仕掛けをこさえて先方でデモすると、さすがに納得されたり称賛されたりもした。ただしMUSE方式はあまりに短命であったために、画質音質を改善するビデオバッファーの発想がメーカー製品に反映されることはかなわないまま終わってしまった。
唯一、某メーカーの視聴室にて、2in/1outのゲーム機割り込み用のHDMIセレクターをプロジェクターへの配線の途中に介在させると画質、音質が改善されるということが認められ、常設されることになった。その際、電池電源ではないがノイズ対策した電源を用いたことも好結果につながった次第。
LANポートは低価格でも堅牢なものを選ぶ
というわけで、スイッチングハブの電源は付属のACアダプター、その大部分はスイッチング電源になっているけれど、それにノイズ対策したり、さらには電池電源にしてみると、画質、音質が改善したのだ。
これを基本としつつ、ここでは、スイッチングハブの“ポートの使い方”でどう変化するかを試してみたい。
筆者が現用しているスイッチングハブは高級品ではなく、量販店で＜売れてます＞とかの惹句付きで吊るし売りされていたものだ。数千円で購入したが、最近検索するとその後継機と思しき製品がさらに低価格で通販されていた。
LANポート(端子)は5口のみ。選択の際重視したのは、まずは金属筐体(鉄)であること。内部に飛び交うノイズを吸い取るのに効果が期待できるし、今後紹介する予定の筆者独自の「床アース」の処理をしやすいからだ。それと外付け電源であり、DC入力端子はUSB系などではなくDC用端子であること。ここでは5Vの汎用端子なので、他のDC電源を使いやすい。
ポートの使い方
次に、実際にどのポートをどう使うのか、というあまり話題になってこなかった課題に取り組んでみよう。
スイッチングハブにおいて、原理的にはすべてのポート間の信号のやりとりは対等のはずだが、実際にはポートの組み合わせで音質が変わる。ポートの距離は数cmしかなく、内部でスイッチングICも経由するのでどのポートを使っても同じと思われるかもしれないが、実際にポートを変えながら試聴すると違いがある。オーディオ用ハブのメーカーによっては「ポートノイズ」対策を重視すると説明しているところもある。また私見を言えば、回路基板のパターン設計において、信号系が電源系やクリーンアースに近いか、遠いかということでも音質に影響する可能性はあるだろう。もちろん各ポートからの信号パターンが完全に等長、同一条件かどうかという問題も関係するだろう。
ただし、闇雲に音声データの入力や出力の組み合わせを試すのは得策ではない。膨大な組み合わせの中で原則を打ち立ててから手順を経て正解を探る手法が現実的だろう。
そこで筆者の試みでは、隣同士とそうでない場合をいくつか試すと、ポートの1番と2番、3番と4番のように隣同士で接続した方が、間を置いた接続よりも音質上有利だと判明した。
その上でどの組み合わせがいいのかを判断すると、ポート群の両端、つまり5ポートあった場合、“1番と2番”、“4番と5番”を使うのが音質的に良かった。実機では最終的に“4番と5番”で使うことにした次第。
ちなみに、私が複数のスイッチングハブを比較テストする場合は、おそらくどのメーカーも確認するだろう“1番と2番”の接続で統一している。ただし個々の製品が優先順位を指定している場合はそれに従っている。
差し替えるだけで簡単に試せるので、既にスイッチングハブを使っている人は、自分で色々な組み合わせを試してみるといい。すくなくとも端子の選択は結構な音質要素だということは間違いない。
なお、ハブから出るLANケーブルが交差する場合の、“交差のさせ方”は、私は＜出力が下、入力が上＞を鉄則としている。アナログ信号でもそうだ。
電源については、基本としてLAN関係の各機器の電源は絶縁トランス経由かリニア電源(アナログ電源)としている。その効用は、写真のように充電池パックのDC5V電源を付属のスイッチング電源の代わりに用いるだけで明らかだ。特に画質には著効がある。音質についても改善効果はあるのだが、少々ドライな音、熟成感が乏しい音になるかもしれない。いわゆる電池臭い音だ。ならば乾電池にすればいいのだが、そこまではしていない。
それと、空いている3つのポートについてだが、これはターミネート(終端)した方がいい。LANポートは終端しなくても問題ないものだが、実際に試してみると効果がある。
といっても高価な音質改善用アクセサリーを何本も用意する必要はない。とりあえずは使っていない、あるいは故障しているスイッチングハブを用意して、短いLANケーブルをそれぞれ接続すれば試せる。その際、ターミネートする側は通電しない。電源OFFのハブをつないでも、当然リンクは確立しないわけだが、効果はある。
また、一端子置きに接続するほうが効果がよろしいようなのでお試しあれ。受ける側にてノイズを消耗させる余裕があった方がいい、ということだろうか？
そして、音声の再生を受け持つネットワークプレーヤーとの接続は、できたらLANケーブルを「半径ずらし」するといい。
ところが、こうした地道な改善努力をあざ笑うような代物が登場している。スイッチングハブを不要にする強力な光絶縁型中継器のことだ。それについては次回お話しよう。

GMO、「能動的サイバー防御」適用を政府に要請 不正アクセス問題
GMOインターネットグループは24日、外国為替証拠金取引（FX）サービスへの不正アクセスを受け、サイバー攻撃に先手を打って被害を防ぐ「能動的サイバー防御」の適用を政府に緊急要請したと発表した。被害の拡大を見越し国に異例の支援を求める。
GMOは民間事業者が単独で高度なサイバー攻撃を防御することは難しいと主張。10月施行した能動的サイバー防御法に基づき、国主導で攻撃の無害化などの措置を講じるよう要請した。GMOは「政府関係機関に対する『発動第1号』の緊急要請」になるとしている。
政府は国家サイバー統括室（NCO）や関係省庁を通じてGMOから被害状況の報告や相談内容を聞き取り、対応を検討する。無害化措置の制度は個別企業の要請で発動することを想定していない。重大性や緊急性などの要件に照らして政府が主体的に判断する。
GMOから提供された攻撃の痕跡や通信記録を警察などと共有し、攻撃元サーバーを特定できるか分析する。無害化措置を実施する場合でも措置の内容や対象、個別案件への対応の有無は明らかにしない可能性が高い。

Over the past year, we’ve published lots of data that shows that frontier AI models are more than capable of discovering and exploiting security vulnerabilities. Showing how previously unknown vulnerabilities might be exploited is, however, only the start of what frontier AI models can do for cyber defense. In this post, we summarize some of our initial research into automated attack surface analysis and reduction: the process of using AI models to map the code that is reachable, then removing or restricting access to anything than a given deployment doesn’t need to expose.
Automated attack surface analysis and reduction can meaningfully improve the security of deployed software in the near term. Securing software by finding and fixing individual vulnerabilities alone scales poorly: fixing even a critical vulnerability tells you nothing about the vulnerabilities that remain. By contrast, reducing code reachability can reduce the severity of unknown vulnerabilities, including the ones that might be under active exploitation. These techniques don’t remove the unknown vulnerabilities in the code, but they do make the vulnerabilities harder to reach, and thereby reduce their severity. Minimizing codebases’ attack surface results in better security without ever having to find or fix an individual vulnerability.
Below, we preview some of the data we’ve collected from applying attack surface reduction techniques to large open-source codebases using Claude. Our aim in doing so is to show that Claude can meaningfully, and economically, improve software security through the methods we outline. Specifically, we ran Claude over 25 projects (in a variety of languages), and it discovered 493 issues. With these results in mind, we discuss how developers can apply similar techniques to their own code.
Methods for reducing codebases’ attack surface
Over time, software has a tendency to become more complicated, with new layers of abstractions, new dependencies, and new features slowly piling on top of one-another. This can often cause it to function very differently to how its original developers intended. And it is a big part of why attackers are often so successful: they study exactly how a piece of code behaves in practice, rather than how its developers intended or designed it to work.
Automated attack surface analysis and reduction techniques aim to discover unnecessary attack surfaces, then move that code behind an appropriate gate. This might involve moving code from pre-authentication to post-authentication, from 0-click to 1-click, from on-by-default to explicit opt-in, or from the first message of a protocol to deeper in the session state machine. Some code is meant to be reachable before these stages, but a lot it is not, and, given the complexity that comes with code churn across thousands or millions of lines of code, unnecessary exposure of features often goes unnoticed.
There are numerous ways to reduce the attack surface of code. In our own research efforts, we focused on three methods in particular:
- Default configuration. We identified code that was reachable in its shipped default configuration but wasn’t intended to be used by any default functionality.
- Configuration interaction. We found pairs of options that looked reasonable on their own, but which caused issues when configured together (for instance, by silently disabling a security control, or leaving a features behavior undefined while its code remains reachable).
- Early reachability. We identified security sensitive and complex code that runs either before an appropriate security control (such as authentication), without victim interaction, or before a protocol state transition.

This package provides a standalone sandbox implementation that can be used as both a CLI tool and a library. It's designed with a secure-by-default philosophy tailored for common developer use cases: processes start with minimal access, and you explicitly poke only the holes you need.
Key capabilities:
- Network restrictions: Control which hosts/domains can be accessed via HTTP/HTTPS and other protocols
- Filesystem restrictions: Control which files/directories can be read/written
- Unix socket restrictions: Control access to local IPC sockets
- Violation monitoring: On macOS, tap into the system's sandbox violation log store for real-time alerts
A key use case is sandboxing Model Context Protocol (MCP) servers to restrict their capabilities. For example, to sandbox the filesystem MCP server:
Without sandboxing (.mcp.json):
{
"mcpServers": {
"filesystem": {
"command": "npx",
"args": ["-y", "@modelcontextprotocol/server-filesystem"]
}
}
}
With sandboxing (.mcp.json):
{
"mcpServers": {
"filesystem": {
"command": "srt",
"args": ["npx", "-y", "@modelcontextprotocol/server-filesystem"]
}
}
}
Then configure restrictions in ~/.srt-settings.json:
{
"filesystem": {
"denyRead": [],
"allowWrite": ["."],
"denyWrite": ["~/sensitive-folder"]
},
"network": {
"allowedDomains": [],
"deniedDomains": []
}
}
Now the MCP server will be blocked from writing to the denied path:
> Write a file to ~/sensitive-folder
✗ Error: EPERM: operation not permitted, open '/Users/ollie/sensitive-folder/test.txt'
The sandbox uses OS-level primitives to enforce restrictions that apply to the entire process tree:
- macOS: Uses sandbox-exec with dynamically generated Seatbelt profiles
- Linux: Uses bubblewrap for containerization with network namespace isolation
- Windows: Runs the sandboxed process under a dedicated srt-sandbox local user account, with a Windows Filtering Platform egress fence keyed on that account's SID, a write-restricted token, and explicit ACEs on the working tree
Both filesystem and network isolation are required for effective sandboxing. Without file isolation, a compromised process could exfiltrate SSH keys or other sensitive files. Without network isolation, a process could escape the sandbox and gain unrestricted network access.
Filesystem Isolation enforces read and write restrictions:
- Read (deny-then-allow pattern): By default, read access is allowed everywhere. You can deny broad regions (e.g., /Users) and then re-allow specific paths within them (e.g., .). allowRead takes precedence over denyRead — the opposite of write, where denyWrite takes precedence over allowWrite. A denyRead entry that is more specific than the allowRead region it falls inside (e.g. denyRead: ["**/.env"] or ["./secrets"] with allowRead: ["."]) still stays denied.
- Write (allow-only pattern): By default, write access is denied everywhere. You must explicitly allow paths (e.g., ., /tmp). An empty allow list means no write access.

Automated attack surface analysis and reduction can meaningfully improve the security of deployed software in the near term. Securing software by finding and fixing individual vulnerabilities alone scales poorly: fixing even a critical vulnerability tells you nothing about the vulnerabilities that remain. By contrast, reducing code reachability can reduce the severity of unknown vulnerabilities, including the ones that might be under active exploitation. These techniques don’t remove the unknown vulnerabilities in the code, but they do make the vulnerabilities harder to reach, and thereby reduce their severity. This package provides a standalone sandbox implementation that can be used as both a CLI tool and a library. It's designed with a secure-by-default philosophy tailored for common developer use cases: processes start with minimal access, and you explicitly poke only the holes you need.
Key capabilities:
- Network restrictions: Control which hosts/domains can be accessed via HTTP/HTTPS and other protocols
- Filesystem restrictions: Control which files/directories can be read/written
- Unix socket restrictions: Control access to local IPC sockets
- Violation monitoring: On macOS, tap into the system's sandbox violation log store for real-time alerts

The sandbox uses OS-level primitives to enforce restrictions that apply to the entire process tree:
- macOS: Uses sandbox-exec with dynamically generated Seatbelt profiles
- Linux: Uses bubblewrap for containerization with network namespace isolation
- Windows: Runs the sandboxed process under a dedicated srt-sandbox local user account, with a Windows Filtering Platform egress fence keyed on that account's SID, a write-restricted token, and explicit ACEs on the working tree
Both filesystem and network isolation are required for effective sandboxing. Without file isolation, a compromised process could exfiltrate SSH keys or other sensitive files. Without network isolation, a process could escape the sandbox and gain unrestricted network access.
Filesystem Isolation enforces read and write restrictions:

On Friday Oct 2, 09:35am, 333 infected exit nodes started a coordinated campaign to intercept SSH connections and gather as much unencrypted data as possible.
To give you a sense of scale, all of Tor has around 3000 exit relays, so roughly 10% were under their control.

こんにちは、インフラエンジニアのryuです。
前回の記事「PHPの緊急脆弱性「php2shell」とは？」では、2026年10月21日に公開されたPHPの脆弱性の仕組みと、アップデートの進め方を解説しました。
今回はその続きです。
アップデートを終えたあとに、多くの人が気になるのが「すでに攻撃されていないか？」という点だと思います。
実際に、Datadog Security Labsの解説記事によると、10月21日の時点で悪用の報告が複数あり、公開の4日前にあたる10月17日には攻撃の試みが観測されていたとされています。
つまり、修正版を入れた日より前に、攻撃を受けていた可能性があるということです。
PHPをアップデートしても、すでに置かれた不正なファイルや、起動された不正なプログラムは消えません。この記事では、サーバーに残る痕跡をどこで、どう確認するかを整理します。
調べる期間を決めておく¶
調査を始める前に、まず「いつからいつまでのログを見るか」を決めます。
今回は、公開の4日前にあたる10月17日には攻撃の試みが観測されています。そのため、少なくとも10月17日から、自分のサーバーでPHPのアップデートが完了した時刻までが調査の対象になります。
ここで困るのが、ログが残っていないケースです。ログローテーションの設定によっては、1週間ほどで古いログが削除されてしまいます。
# ローテーションされた古いログが残っているか確認する
ls -l /var/log/nginx/ /var/log/apache2/
調査が終わるまでは、ログを別の場所へコピーして保管しておくと安心です。
攻撃の痕跡は「3つの場所」で探す¶
php2shellの攻撃を調べるときは、次の3つの場所を見ます。
大切なのは、1つの痕跡だけで「攻撃された」「攻撃されていない」と判断しないことです。
例えばメモリ不足のエラーは、普段の大きなアップロードでも起きます。反対に、攻撃が成功した場合でも、エラーが出ずに正常な応答（HTTP 200）が返ることがあります。
3つの場所の記録を、時刻を合わせて突き合わせることが調査の基本になります。
① 不審なフォーム送信がないか確認する¶
攻撃リクエストの特徴¶
Datadogが検証した攻撃では、普通のWebフォームと同じ形式（application/x-www-form-urlencoded）のPOSTリクエストが使われていました。
見た目はただのフォーム送信ですが、中身には次のような特徴があります。
- 約3.5MBもある、異常に長いフィールド名が含まれる
- 名前が空のフィールドに、制御文字（ヌルバイトなど）を含むバイナリデータが入っている
ログインフォームのような通常の入力欄で、数MBの項目名が送られてくることはまずありません。
アクセスログで大きなPOSTを探す¶
まずは、Webサーバーのアクセスログから、PHPへのPOSTリクエストを確認します。
# POSTリクエストの多い送信元IPを数える（Nginxの例）
sudo grep '"POST ' /var/log/nginx/access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head
標準的なログ形式では、リクエストの大きさ（ボディのサイズ）は記録されません。Nginxなら$request_length、Apacheならmod_logioの%Iをログ形式に加えておくと、受け取ったバイト数を残せます。
今回のような事態に備えて、普段からリクエストサイズを記録しておくと、あとの調査がずっと楽になります。
WAFやリバースプロキシでの対策¶
WAF（Web Application Firewall）やリバースプロキシを使っている場合は、次のようなリクエストを検知・遮断するルールを検討します。
- フォームのフィールド名が異常に長い
- フォームの値に、想定しない制御文字が含まれる
制限値は、自分のアプリケーションの正常な通信を基準に決めます。いきなり厳しくすると、正規のアップロードまで止めてしまうからです。
WAFが大きなリクエストを途中までしか検査しない設定になっていると、検査されなかった部分に攻撃の中身があっても見逃します。WAFの検査上限と、アプリケーションが受け付ける上限が合っているかも確認しましょう。
② PHPのエラーログを確認する¶
「Unknown on line 0」のメモリ不足エラー¶
攻撃の試行では、PHPのエラーログに次のような致命的エラーが記録されていました。
PHP Fatal error: Allowed memory size of 16777216 bytes exhausted
(tried to allocate 3500032 bytes) in Unknown on line 0
注目したいのはUnknown on line 0の部分です。
通常のメモリ不足なら、どのPHPファイルの何行目で起きたかが記録されます。Unknown on line 0は、スクリプトが動き出す前、リクエストを受け取って準備している途中でメモリが足りなくなったことを示しています。
ログは次のように検索できます。
# PHP-FPMのログから探す（パスは環境に合わせて変更）
sudo grep -n "Unknown on line 0" /var/log/php*-fpm.log
# Apache（mod_php）の場合はエラーログに出る
sudo grep -n "Allowed memory size" /var/log/apache2/error.log
ログの保存場所が分からない場合は、Apacheのログの保存場所や、PHP-FPMの設定ファイル（error_logの項目）を確認してください。
ワーカーの異常終了¶
攻撃者がメモリの位置を推測し損ねると、Webサーバーのワーカーが異常終了することがあります。Apacheでは次のようなログが残ります。
AH00052: child pid ... exit signal Segmentation fault (11)
sudo grep -n "Segmentation fault" /var/log/apache2/error.log
Segmentation faultは、プログラムが不正なメモリにアクセスして強制終了したことを表します。
NginxとPHP-FPMの構成では、ワーカーの異常終了はPHP-FPMのログに記録されます。あわせて、Nginxのエラーログに上流（PHP-FPM）との接続が切れた記録が残ることもあります。
# PHP-FPMのワーカーがシグナルで終了した記録
sudo grep -n "exited on signal" /var/log/php*-fpm.log
# Nginx側で上流との接続が途中で切れた記録
sudo grep -n "upstream prematurely closed" /var/log/nginx/error.log
どちらも、普段から一定数は出ることがあるログです。件数が急に増えた日時がないかに注目すると、いつもとの違いに気づきやすくなります。
これらのエラーが、①の大きなPOSTリクエストや、上流の接続リセットと同じ時刻に集中していないかを確認します。
ただし、メモリ不足もワーカーの異常終了も、正当な処理で起きることがあります。それだけで攻撃と断定はできません。
CVE-2026-109619で見るポイント¶
もう1つの脆弱性（CVE-2026-109619）については、外部からアクセスできるURLで、次のようなログが増えていないかを確認します。
- 起動直後の設定に関する警告
- 終了処理（シャットダウン）中の診断メッセージ
- 致命的なエラー
- 実行時間の上限超え（タイムアウト）
PHPの公式アドバイザリでは、こうしたイベントが、前のリクエストの内部状態が残ってしまう経路と関係している可能性が示されています。
③ Webサーバーが起動したプロセスを確認する¶
もっとも直接的な証拠は「シェルの起動」¶
3つの中で、攻撃の成功をもっとも直接的に示すのが、Webサーバーのワーカーがシェルを起動しているという痕跡です。
Datadogの検証では、Apacheのワーカーがシェルを起動し、そのシェルが攻撃者のサーバーへ外向きの通信を張っていました。
apache2 (www-data)
└── sh -c <リバースシェルのコマンド>
└── bash [外部サーバーへの通信]
本来、WebサーバーはHTTPリクエストを処理するだけで、シェルを起動する必要はほとんどありません。
Linuxで確認するコマンド¶
まず、Webサーバーの実行ユーザー（Ubuntuならwww-data、RHEL系ならapacheやnginx）が動かしているプロセスを確認します。
# プロセスの親子関係をツリーで表示する
ps -ef --forest | less
# www-data が実行しているプロセスだけを見る
ps -u www-data -o pid,ppid,lstart,cmd
apache2やphp-fpmの下に、shやbash、見覚えのないプログラムがぶら下がっていないかを確認します。
あわせて、外部への通信も確認します。
# 確立している通信と、それを持つプロセスを表示する
sudo ss -tnp state established
Webサーバーの実行ユーザーのプロセスが、見覚えのない外部のIPアドレスへ接続している場合は要注意です。
「普段の動き」を知っておく¶
アプリケーションによっては、画像変換などのために、意図して外部コマンドを実行するものもあります。
そのため、普段どんなプロセスが起動しているか（ベースライン）を把握しておくことが大切です。普段の動きが分かっていれば、いつもと違う動きにすぐ気づけます。
攻撃の検知を、特定のコマンド名やHTTPのステータスコード、ワーカーの異常終了に頼らないようにしてください。改良された攻撃では、リクエストは正常な応答を返し、ワーカーも動き続けます。
不審なファイルや自動実行の設定も確認する¶
攻撃者がシェルを手に入れると、次にアクセスするための仕掛けを残すことがあります。代表的なのは、Webから実行できる不正なPHPファイル（Webシェル）や、定期的に動く不正なプログラムです。
ドキュメントルートの中で、調査期間に新しく作られたり変更されたりしたファイルを探します。
# 10月17日以降に変更されたPHPファイルを探す（パスは環境に合わせて変更）
sudo find /var/www -type f -name '*.php' -newermt '2026-10-17' -ls
# 一時ディレクトリに置かれた実行ファイルも確認する
sudo find /tmp /var/tmp /dev/shm -type f -newermt '2026-10-17' -ls
デプロイやプラグインの更新でも変更日時は新しくなるため、見つかったファイルが自分たちの作業によるものかを照らし合わせます。
あわせて、Webサーバーの実行ユーザーに定期実行の設定が追加されていないかも確認します。
sudo crontab -u www-data -l
ls -l /etc/cron.d/

スイッチングハブは使いこなしの宝庫。AV向けのハブ選びやポートの使い方
2026年10月23日 09:00
今回からは家庭内LANによる音楽配信や動画配信にまつわるお話にしよう。
特に昔気質のオーディオ愛好家ならば、音源としてもっぱら各種の音盤を回し、各機器の組み合わせやケーブル類の選択、さらにはスピーカーの「ミリ単位」の微調整を要する設置法の問題などに汗を流してきたことだろう。
しかし、デジタルネットワーク系のオーディオ再生となると勝手が違うかも。LANとかルーターとか、スイッチングハブとかにまつわる耳慣れない用語や機器に戸惑う向きも多いことと思う。かくいう私も同様ではあった。
まずはオーディオ系について。デジタルファイル化された音声データが地球上を駆け巡るネットワークを通じて自分の家にまで届き、ハイレゾの高音質データまで再生可能になったことは朗報に違いない。その代わり、音楽ディスクの売れ行きは衰退傾向になってきたけれど。
接続や設定については、光回線関係の回線業者、設置業者に頼めば、ONU(光回線端末)からWi-Fiルーターまでは施設してくれるので問題はない。現場でのチェックは手持ちのパソコンにて、LANケーブルを使う有線や無線のWi-Fi接続においてインターネット回線が使えるかどうかで済む話だ。
そこから先、LANのスイッチングハブを用意して音声デコード用機器の近くに設置し、必要な機器を有線LANで接続することになる。音楽配信ならネットワークプレーヤーの単体機、あるいはCDプレーヤー、D/Aコンバーター、AVアンプなどに備わっているネットワークプレーヤーの機能を使って再生することになる。もちろん、ストリーミング再生だけでなく音楽データをメモリーにストレージすることも可能であり、そのためにはPC経由にしたり、ストレージを重視する専用機器を用意すればいい。
スイッチングハブの音質対策
ともあれ、ここで紹介するのは、音楽配信のストリーミング再生をする最小限のシステムの末端近くにおける音質対策となる。
そもそもルーターから導いたLANケーブルはスイッチングハブなど経由せずとも、ネットワークプレーヤーに接続するだけで、ただちに音楽を再生できるようになっている。ならば、なぜスイッチングハブが必要になるのかというと、ハブを介すると音質がいいからだ。これは筆者が各所で何度も確認していることだし、オーディオファンにも広く普及している対策方法だ。
しかし、音質優先で考えるとむやみに分岐すると複雑なノイズのループを生じるし、そもそもそこに接続される機器はほとんど例外なくスイッチング電源を使用しているだろう。つまり強いノイズの発生装置を多数ぶら下げたところに、AV機器を接続すると、ノイズの影響を受けてしまうわけだ。
映像バッファーの効用
それで理想としては多数のポート(端子)を備えているスイッチングハブを使っていても、余計な機器を接続せず、ルーターとプレーヤー機器のみを接続し、データの流れをシンプルにしたほうが望ましいのである。
こういうことについて自信をもって言えるのは、実機で実験したことがあるからだし、さかのぼればホームシアターにおける映像機器の「セレクター」あたりから続いているお題だ。
というのは、映像セレクターを経由させると、画質音質が改善される、と言い続けてきたのはこの私だからだ。しかし当時はほとんど理解されなかった。ピュアイムズがオーディオの世界を席巻する中で、ただの中継機能とはいえ、映像バッファー(ビデオアンプ)や音声バッファー(音声アンプ)という“余分なもの”を経由させれば、必ず画質、音質の劣化を招く、と固く信じられていたからだ。
しかし、実際は注意深く配線し、電源ラインを整えると、映像セレクターを経由させた方が画質、音質が向上することが確認できたのだ。ノイズのループが遮断されるからだ。信号伝送の途中におけるわずかな劣化よりも、方々を自在に駆け巡るループノイズの方が悪さをするのである。
さらには、なつかしや、MUSE(ミューズ)方式のハイビジョン放送やMUSE LD(レーザーディスク)が登場したころ、より鮮明な映像の変化としてそれを体験できたのだ。
それは、従来映像と同じように通常の映像セレクターにMUSE信号を経由させることで試すことができた次第。これを意外なことという向きもあるだろうけど、MUSEといっても1フレームを4分割してそれが4回で1フレームを完成させるという簡易型の時分割式アナログ情報圧縮だったので可能だったわけだ。
それでも信じないお堅い面々には、手製の汎用ビデオアンプを電池駆動する仕掛けをこさえて先方でデモすると、さすがに納得されたり称賛されたりもした。ただしMUSE方式はあまりに短命であったために、画質音質を改善するビデオバッファーの発想がメーカー製品に反映されることはかなわないまま終わってしまった。
唯一、某メーカーの視聴室にて、2in/1outのゲーム機割り込み用のHDMIセレクターをプロジェクターへの配線の途中に介在させると画質、音質が改善されるということが認められ、常設されることになった。その際、電池電源ではないがノイズ対策した電源を用いたことも好結果につながった次第。
LANポートは低価格でも堅牢なものを選ぶ
というわけで、スイッチングハブの電源は付属のACアダプター、その大部分はスイッチング電源になっているけれど、それにノイズ対策したり、さらには電池電源にしてみると、画質、音質が改善したのだ。
これを基本としつつ、ここでは、スイッチングハブの“ポートの使い方”でどう変化するかを試してみたい。
筆者が現用しているスイッチングハブは高級品ではなく、量販店で＜売れてます＞とかの惹句付きで吊るし売りされていたものだ。数千円で購入したが、最近検索するとその後継機と思しき製品がさらに低価格で通販されていた。
LANポート(端子)は5口のみ。選択の際重視したのは、まずは金属筐体(鉄)であること。内部に飛び交うノイズを吸い取るのに効果が期待できるし、今後紹介する予定の筆者独自の「床アース」の処理をしやすいからだ。それと外付け電源であり、DC入力端子はUSB系などではなくDC用端子であること。ここでは5Vの汎用端子なので、他のDC電源を使いやすい。
ポートの使い方
次に、実際にどのポートをどう使うのか、というあまり話題になってこなかった課題に取り組んでみよう。
スイッチングハブにおいて、原理的にはすべてのポート間の信号のやりとりは対等のはずだが、実際にはポートの組み合わせで音質が変わる。ポートの距離は数cmしかなく、内部でスイッチングICも経由するのでどのポートを使っても同じと思われるかもしれないが、実際にポートを変えながら試聴すると違いがある。オーディオ用ハブのメーカーによっては「ポートノイズ」対策を重視すると説明しているところもある。また私見を言えば、回路基板のパターン設計において、信号系が電源系やクリーンアースに近いか、遠いかということでも音質に影響する可能性はあるだろう。もちろん各ポートからの信号パターンが完全に等長、同一条件かどうかという問題も関係するだろう。
ただし、闇雲に音声データの入力や出力の組み合わせを試すのは得策ではない。膨大な組み合わせの中で原則を打ち立ててから手順を経て正解を探る手法が現実的だろう。
そこで筆者の試みでは、隣同士とそうでない場合をいくつか試すと、ポートの1番と2番、3番と4番のように隣同士で接続した方が、間を置いた接続よりも音質上有利だと判明した。
その上でどの組み合わせがいいのかを判断すると、ポート群の両端、つまり5ポートあった場合、“1番と2番”、“4番と5番”を使うのが音質的に良かった。実機では最終的に“4番と5番”で使うことにした次第。
ちなみに、私が複数のスイッチングハブを比較テストする場合は、おそらくどのメーカーも確認するだろう“1番と2番”の接続で統一している。ただし個々の製品が優先順位を指定している場合はそれに従っている。
差し替えるだけで簡単に試せるので、既にスイッチングハブを使っている人は、自分で色々な組み合わせを試してみるといい。すくなくとも端子の選択は結構な音質要素だということは間違いない。
なお、ハブから出るLANケーブルが交差する場合の、“交差のさせ方”は、私は＜出力が下、入力が上＞を鉄則としている。アナログ信号でもそうだ。
電源については、基本としてLAN関係の各機器の電源は絶縁トランス経由かリニア電源(アナログ電源)としている。その効用は、写真のように充電池パックのDC5V電源を付属のスイッチング電源の代わりに用いるだけで明らかだ。特に画質には著効がある。音質についても改善効果はあるのだが、少々ドライな音、熟成感が乏しい音になるかもしれない。いわゆる電池臭い音だ。ならば乾電池にすればいいのだが、そこまではしていない。
それと、空いている3つのポートについてだが、これはターミネート(終端)した方がいい。LANポートは終端しなくても問題ないものだが、実際に試してみると効果がある。
といっても高価な音質改善用アクセサリーを何本も用意する必要はない。とりあえずは使っていない、あるいは故障しているスイッチングハブを用意して、短いLANケーブルをそれぞれ接続すれば試せる。その際、ターミネートする側は通電しない。電源OFFのハブをつないでも、当然リンクは確立しないわけだが、効果はある。
また、一端子置きに接続するほうが効果がよろしいようなのでお試しあれ。受ける側にてノイズを消耗させる余裕があった方がいい、ということだろうか？
そして、音声の再生を受け持つネットワークプレーヤーとの接続は、できたらLANケーブルを「半径ずらし」するといい。
ところが、こうした地道な改善努力をあざ笑うような代物が登場している。スイッチングハブを不要にする強力な光絶縁型中継器のことだ。それについては次回お話しよう。

GMO、「能動的サイバー防御」適用を政府に要請 不正アクセス問題
GMOインターネットグループは24日、外国為替証拠金取引（FX）サービスへの不正アクセスを受け、サイバー攻撃に先手を打って被害を防ぐ「能動的サイバー防御」の適用を政府に緊急要請したと発表した。被害の拡大を見越し国に異例の支援を求める。
GMOは民間事業者が単独で高度なサイバー攻撃を防御することは難しいと主張。10月施行した能動的サイバー防御法に基づき、国主導で攻撃の無害化などの措置を講じるよう要請した。GMOは「政府関係機関に対する『発動第1号』の緊急要請」になるとしている。
政府は国家サイバー統括室（NCO）や関係省庁を通じてGMOから被害状況の報告や相談内容を聞き取り、対応を検討する。無害化措置の制度は個別企業の要請で発動することを想定していない。重大性や緊急性などの要件に照らして政府が主体的に判断する。
