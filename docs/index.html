Deno is joining Cloudflare
For years, we’ve been working to make building server software simpler. We questioned how modules could be distributed, what security guarantees a JavaScript runtime could provide, what belonged in a complete toolchain, and how easily an application could be distributed as a standalone executable. Compatibility with Node.js became an important part of that work too: our users wanted the Deno improvements while continuing to plug into the existing JS ecosystem. The team and community built a runtime that brought these capabilities together and challenged assumptions about what JS development could look like.
Today we’re announcing that the entire Deno team is joining Cloudflare to take that work further.
Our ambition has always extended beyond the runtime. I wrote about this in my JavaScript Containers blog post: compute, storage, and communication working together, without every application assembling its own infrastructure.
With Deno Deploy, we took another step towards that goal. We wanted to make running applications as straightforward as possible. But building and operating Deploy also showed us how much complexity remained underneath that developer experience. I wanted to simplify that layer, too.
This led to celld. Building on the Cloudflare Workers programming model, celld lets developers build distributed applications from the start while making the system simple to operate. What excites me greatly is that the scaling is built into the programming model, rather than infrastructure each app has to assemble itself.
The progression from Deno to Deno Deploy to celld explains why this move makes sense to us. At Cloudflare we’ll combine our work with that of the Workers and Durable Objects teams. We want to make this programming model the default way to build servers, whether you run on Cloudflare’s network or your own infrastructure.
Joining also means choosing where to focus our effort. We’ve decided to put our future development work into this shared platform rather than continuing to develop a separate runtime and hosting service. We know this is a consequential change for people who have built on Deno.
To everyone who contributed code, built businesses on Deno, reported problems, and trusted our direction: thank you. Here’s what this means concretely:
- We will support the Deno runtime for another year with monthly releases containing bug fixes and security updates. After that year we will end our development of the Deno runtime. Deno will remain open source, and we welcome others who want to continue its development.
- Deno Deploy will continue operating for six months before shutting down. We will provide migration support for paying customers moving to Cloudflare Workers.
- JSR will continue operating, with its infrastructure moving to Cloudflare.
- We will continue supporting rusty_v8 and work toward integrating it into workerd.
The need for better abstractions is especially acute with AI. Durable Objects bring together capabilities that are particularly useful for agent harnesses: inexpensive, serverless execution, persistent state, WebSockets, and a high-level JavaScript interface. This is what I’m most excited to explore and why celld focuses on Durable Objects.
Kenton Varda and I explain more in our joint post on the Cloudflare blog. If you’re building agents at scale and want to run them on your own infrastructure, please reach me now at ry@cloudflare.com.

Yes, and...
Carson Gross
I teach computer science at Montana State University. I am the father of three sons who all know I am a computer programmer and one of whom, at least, has expressed interest in the field. I love computer programming and try to communicate that love to my sons, the students in my classes and anyone else who will listen.
A question I am increasingly getting from relatives, friends and students is:
Given AI, should I still consider becoming a computer programmer?
My response to this is: “Yes, and…”
“Yes”
Computer programming is, fundamentally, about two things:
- Problem-solving using computers
- Learning to control complexity while solving these problems
I have a hard time imagining a future where knowing how to solve problems with computers and how to control the complexity of those solutions is less valuable than it is today, so I think it will continue to be a viable career even with the advent of AI tools.
“You have to write the code”
That being said, I view AI as very dangerous for junior programmers because it is able to effectively generate code for many problems. If a junior programmer does not learn to write code and simply generates it, they are robbing themselves of the opportunity to develop the visceral understanding of code that comes with being down in the trenches.
Because of this, I warn my students:
“Yes, AI can generate the code for this assignment. Don’t let it. You have to write the code.”
I explain that, if they don’t write the code, they will not be able to effectively read the code. The ability to read code is certainly going to be valuable, maybe more valuable, in an AI-based coding future.
If you can’t read the code you are going to fall into The Sorcerer’s Apprentice Trap, creating systems you don’t understand and can’t control.
Is Coding → Prompting like Assembly → High Level Coding?
Some people say that the move from high level languages to AI-generated code is like the move from assembly to high level programming languages.
I do not agree with this simile.
Compilers are, for the most part, deterministic in a way that current AI tools are not. Given a high-level programming language construct such as a for loop or if statement, you can, with reasonable certainty, say what the generated assembly will look like for a given computer architecture (at least pre-optimization).
The same cannot be said for an LLM-based solution to a particular prompt.
High level programming languages are a very good way to create highly specified solutions to problems using computers with a minimum of text in a way that assembly was not. They eliminated a lot of accidental complexity, leaving (assuming the code was written reasonably well) mostly necessary complexity.
LLM generated code, on the other hand, often does not eliminate accidental complexity and, in fact, can add significant accidental complexity by choosing inappropriate approaches to problems, taking shortcuts, etc.
If you can’t read the code, how can you tell?
And if you want to read the code you must write the code.
AI is a great TA
Another thing that I tell my students is that AI, used properly, is a tremendously effective TA. If you don’t use it as a code-generator but rather as a partner to help you understand concepts and techniques, it can provide a huge boost to your intellectual development.
One of the most difficult things when learning computer programming is getting “stuck”. You just don’t see the trick or know where to even start well enough to make progress.
Even worse is when you get stuck due to accidental complexity: you don’t know how to work with a particular tool chain or even what a tool chain is.
This isn’t a problem with you, this is a problem with your environment. Getting stuck pointlessly robs you of time to actually be learning and often knocks people out of computer science.
(I got stuck trying to learn Unix on my own at Berkeley, which is one reason I dropped out of the computer science program there.)
AI can help you get past these roadblocks, and can be a great TA if used correctly. I have posted an AGENTS.md file that I provide to my students to configure coding agents to behave like a great TA, rather than a code generator, and I encourage them to use AI in this role.
AI doesn’t have to be a detriment to your ability to grow as a computer programmer, so long as it is used appropriately.
“, and…”
I do think AI is going to change computer programming. Not as dramatically as some people think, but in some fundamental ways.
Raw coding may become less important
It may be that the act of coding will lose relative value.
I regard this as too bad: I usually like the act of coding, it is fun to make something do something with your (metaphorical) bare hands. There is an art and satisfaction to writing code well, and lots of aesthetic decisions to be made doing it.
However, it does appear that raw code writing prowess may be less important in the future.

Deeper dive: Keyboard differences between Windows and Macs
Over the years, I learned about many gotchas and strange differences between keyboard handling on Mac and Windows – pertinent especially to web apps, which use the same codebase to cater to both. I thought it might be helpful to someone if I compile them all in one place.
This post is meant to be a reference, and there aren’t any cute or riveting stories hiding inside – if this seems boring to you, feel free to skip to the next one!
Different names for keys
What Windows calls Backspace, Mac calls Delete. What Windows calls Delete, Macs call Forward Delete. (This means saying “Delete” without specifying the platform might actually be confusing.)
What Windows calls ⏎ Enter, Mac calls ⏎ Return. However, Macs also have an ⌤ Enter, although only on a numeric keypad (previously, it was even there on laptops!). On keyboards without the physical Enter key, you can simulate it via Fn+Return.
In most Mac software, Enter and Return do the same thing. There are a few exceptions – for example, Photoshop adds a new line on Return but commits on Enter, and some classic pro apps like Cubase or Pro Tools do different things, too – but it seems to be a dying tradition. (If you are curious about the history of Return and Enter, I wrote about it once.)
Windows customarily calls the secondary key Numpad Enter. I don’t believe Fn+Enter works to simulate it.
Generally, third-party keyboards use Windows verbiage – so, Backspace and Enter. If a keyboard offers Mac conventions at all, they usually only extend to modifier keys.
Modifier keys
⌃ Control on Windows is the equivalent to ⌘ Command on a Mac. (Paste, for example, is ⌃V on Windows and ⌘V on a Mac.) But, confusingly, Apple devices still have a Control key, too. This was originally meant for terminal applications, but these days many GUI apps use it as an extra modifier key of much lesser significance than Control on Windows.
This means that for apps, Windows devices offer Ctrl, Alt, and Shift – and Macs offer ⌘ Command, ⌥ Option, ⌃ Control, and ⇧ Shift. That’s one more modifier key, and thus more space to breathe. (We’re not counting the Windows key or the 🌐 Globe/Fn key since those are technically reserved by the operating system.)

Words vs. symbols
Apple devices rely more on symbols on their keys and in their menus, although they don’t do so consistently. Here are all of them:
- ⇧ Shift
- ⌃ Control
- ⌥ Option
- ⌘ Command
- ⏎ Return
- ⌤ Enter
- 🌐 Globe/Fn
- ⇥ Tab
- ⎋ Esc (not printed on keyboards, for some reason)
- ⌫ Delete
- ⌦ Forward Delete
- ⌧ Clear
- ≣ Contextual Menu (only on full-size keyboards)
- ⇞ Page Up (only on full-size keyboards)
- ⇟ Page Down (only on full-size keyboards)
- ↖ Home (only on full-size keyboards)
- ↘ End (only on full-size keyboards)
Actually, I lied about the last four. On modern Apple keyboards, they are:
- ↑ Page Up
- ↓ Page Down
- ⤒ Home
- ⤓ End

概要
直近において、国内の金融機関や通信事業者等の幅広い事業者から、不正アクセスの被害による情報漏えい事案の公表が相次いで行われています。特に、大量の個人情報を取り扱うオンラインサービス・アカウントサービス等に関するシステムが不正侵入され、個人情報を含むデータが窃取される事案が相次いでいるところです。
その様な大量の情報資産を保有する事業者や機微な情報を取り扱う事業者等の経営者におかれては、サイバーセキュリティリスクが自社のリスクマネジメントにおける重要課題であることを認識し、自らのリーダーシップのもとで対策を進めることが必要です。経営責任として情報漏えいを起こさないためのサイバーセキュリティ対策の点検や見直しを至急実施願います。

速やかに行うべき点検
現段階では、特定のプロダクトやサービスの脆弱性を狙った攻撃とは断定されておらず、公表事例の傾向から、外部公開しているアプリケーションやサービスの侵害、アカウントの侵害が起点となっていることがうかがえます。これらを踏まえた、速やかに行うべき点検は以下の通りです。
外部に公開しているアプリケーションの精査
- ・自組織が独自に構築・運用している外部公開アプリケーションやサービスがあるかどうかを確認してください。
- ・各アプリケーション、サービス単位で直近のログに異常が記録されていないか確認してください。
- 異常の見わけ方としては、たとえばエラーの出力量、平時との差異等が挙げられます。また、直近１ヵ月、その後３ヵ月といったように、段階的に対象範囲を広げて確認してください。さらに、今後複数回調査を行う可能性も踏まえ、誰がどのように調査できるかについても把握しておいてください。
- ・各アプリケーション、サービスの構成要素に現在未適用の脆弱性対応パッチがないか確認してください。
- 未適用のものがあった場合はできるだけ速やかに適用してください。
自組織が利用している外部サービスの洗い出し
- ・自組織が利用している外部サービスをすべて洗い出してください。
- クラウドサービス、VPNサービス等様々な分類があること、また組織全体、部署単位での利用がありうることを踏まえ、できる限り網羅的に把握してください。
- ・サービス単位のログに異常が記録されていないか確認してください。
- サービス単位でログの保有期間はそれぞれ異なることが想定されますので、その整理も必要です。また、サービス提供者と利用者で確認できるログにも違いがある可能性があります。誰がいつどのように確認できるかについて整理してください。異常な点については、ログイン失敗の量など比較的わかりやすいものから、ログイン元IPアドレス、ログイン時間等といった平時の情報との比較が必要なものがありますので、自組織の運用を考慮して異常または不審な点がないかを確認してください。
- ・サービス単位のアカウントに異常がないか確認してください。
- 作ったはずのないアカウントが存在しないか、削除・無効化されているはずのアカウントが有効化されていないか等の異常を確認してください。このような操作が記録されるログについての確認も並行しておこなうとより有効です。
外部に公開しているアプリケーション、自組織が利用している外部サービスのいずれにおいても、異常なログやアカウントの発見があった場合は、速やかにセキュリティインシデントと判定し、インシデント対応を進めてください。情報漏えいの可能性を考慮し、専門のセキュリティベンダーに詳細調査を依頼することを強く推奨します。
保有データの再点検
今回の多くの事案は情報漏えいにつながっています。情報を窃取されてしまうと、情報の悪用はもとより、「窃取した情報を公開する」と脅迫されたり、不正売買されるなど、情報を悪用した二次被害が拡大する傾向が強まっていますので、不要な情報は持たない、という基本原則のもと、自らが保有する情報資産を正確に把握し、必要最小限にする等、保有情報の再点検も必要です。これらの点検作業についても、速やかにおこなってください。
なお、今後各公的機関やセキュリティベンダー等から不審なIPアドレスやログの痕跡等、調査に活用できる情報が公表される可能性がありますので、当面情報収集を強化してください。

We questioned how modules could be distributed, what security guarantees a JavaScript runtime could provide, what belonged in a complete toolchain, and how easily an application could be distributed as a standalone executable. Today we’re announcing that the entire Deno team is joining Cloudflare to take that work further.
Our ambition has always extended beyond the runtime. I wrote about this in my JavaScript Containers blog post: compute, storage, and communication working together, without every application assembling its own infrastructure.
With Deno Deploy, we took another step towards that goal. We wanted to make running applications as straightforward as possible. But building and operating Deploy also showed us how much complexity remained underneath that developer experience. I wanted to simplify that layer, too.
This led to celld. Building on the Cloudflare Workers programming model, celld lets developers build distributed applications from the start while making the system simple to operate. What excites me greatly is that the scaling is built into the programming model, rather than infrastructure each app has to assemble itself.
The progression from Deno to Deno Deploy to celld explains why this move makes sense to us. At Cloudflare we’ll combine our work with that of the Workers and Durable Objects teams. - We will continue supporting rusty_v8 and work toward integrating it into workerd.

This is what I’m most excited to explore and why celld focuses on Durable Objects.

できること
すべてこのページ上で実際に組まれています。文字にマウスを乗せると赤くなるのは、1文字ずつがSVGの要素になっているからです。
縦書きと縦中横
2 桁以下の数字は正体で並べ、3 桁以上の数字と英字は 90 度回転します。句読点や括弧は縦組み用のグリフに置き換わります。
コードを見る
<StoneText direction="tbRl" height={280} fontSize={18} lineHeightScale={1.9}>
{"令和6年12月31日、Ver.2.0を公開した。数字は2桁まで縦中横、3桁以上の123と英字は回転する。"}
</StoneText>
禁則処理
句読点や閉じ括弧を行頭に、開き括弧を行末に置きません。「ー」や小書きの仮名、全角の「！」「・」も行頭に置かない強い禁則（CSS の line-break: strict 相当）で、「……」「——」の途中でも改行しません。
コードを見る
// 比べやすいように 1 文字単位で折り返す（dividesByWords={false}）
<StoneText width={220} dividesByWords={false} kinsoku>{text}</StoneText>
<StoneText width={220} dividesByWords={false} kinsoku={false}>{text}</StoneText>
約物の詰め
句読点や括弧の連続を半角にします。stone モードは前後の文字を見て、自然に見えるところだけ詰めます。
コードを見る
<StoneText punctuationMode="whole">{text}</StoneText> // 常に全角
<StoneText punctuationMode="half">{text}</StoneText> // 常に半角
<StoneText punctuationMode="stone">{text}</StoneText> // 前後関係で判断（既定）

Anthropicは10月8日、Build live dashboards and animate explainers with Claude において、生成AI「Claude」の新機能「Claude Dashboards」と「Claude Motion」をベータ版として公開した。
Claude Dashboardsは、企業のデータ分析を支援する新機能。データウェアハウスや業務アプリケーションをClaudeに接続し、分析したい内容を自然言語で指示すると、Claudeがデータを取得・分析してダッシュボードを作成する。
従来、データを分析するにはSQLなどの知識が必要になる場合があったが、Claude Dashboardsでは、ユーザーがSQLを記述することなくデータを分析できる。
SnowflakeやDatabricksに接続、自然言語からダッシュボードを生成
Claude Dashboardsは、Amazon Redshift、BigQuery、ClickHouse、Databricks、Snowflakeなどのデータ基盤に対応する。Salesforceなど、Claudeの既存のコネクタを利用したデータ分析も可能だ。
例えば、「今四半期の地域別売上高を表示して」「今週の新規登録者数を先月と比較して」といった指示を入力すると、Claudeが必要なデータを取得し、グラフなどを使ったダッシュボードを生成する。
作成したダッシュボードは、接続先のデータが変化すると更新される。各グラフにはデータの最終更新時刻が表示され、利用者は情報がいつ更新されたかを確認できる。
また、グラフ内の数値をクリックすると、その数値の算出に使用されたSQLクエリを確認できる。Claudeにクエリの内容を説明させることも可能で、分析結果の根拠を確認できる仕組みとなっている。
作成したダッシュボードはAmplitude、Grafana、Hex、Mixpanel、Omni、PostHog、Sigmaなどの分析ツールに引き継ぐこともできる。LookerやTableauなどへの対応も予定されている。
Claude DashboardsはPro、Max、Team、Enterpriseの各有料プランを対象にベータ版として提供される。Enterpriseプランでは初期状態で無効になっており、管理者による有効化が必要となる。
Claude Motion、レポートやグラフからアニメーションを生成

筆者が工具にハマり始めた30年近く前だと、Weraはまだ知名度は高くなかったと思う。当時、千葉県にファクトリーギアという工具専門店ができて、それまで高級工具はガラスケースの中にしまわれているのが普通だったところ、ここのお店では直接触れるというので、クルマ好きの仲間と訪れたのは懐かしい思い出だ。

PB SWISS TOOLS vs Wera vs アネックスで比較!!
ということで今回比較するのは、筆者が長らく愛用しているPBの最新モデル スイスグリップEVOと、Weraからは、読者から推す声が多かったレーザーチップ、加えてWeraのもう1種類のカムアウト防止機能であるダイヤモンドドライバー、そして最後に国内メーカーからアネックスの差替式ダイヤモンドドライバーを用意してみた。
まずは製品の説明から。
PB SWISS TOOLS スイスグリップEVO
2025年に登場した新モデル。マルチクラフトグリップ、スイスグリップと継承してきた樽形のグリップをベースに、ゆるやかに三角形に近づけたような形状で、従来の形状より手になじみやすく、約25％高いトルクがかけられるという。
刃先は特別なカムアウト防止加工はされておらず、とにかく精度を追求している。刃先が黒っぽいのはメッキをしていないため。これも精度を求めた結果で、メッキの厚みで精度が落ちるのを嫌ったのが理由。といっても最近のドライバーは先端にメッキしていないものがほとんどだが。あとは軸にバネ鋼ベースの特殊素材を使うことで弾性に優れるというのもポイントだろう。
Wera レーザーチップドライバー
読者からなめにくいと推す声が多かったドライバー。Weraはかなりバリエーションが多くて、ステンレスタイプなどもあるが、今回はスタンダードなレーザーチップを選んでいる。
Weraの特長の1つがそのグリップ形状。上下が細く、真ん中が太い変わった形状だが、これは柔らかいボールをグッと握りしめたときの手のひらの内側の形状に合うように作られているのだという。ただ、他にボールグリップタイプも用意されていて、これは日本市場に向けて開発されたものだそうだ（日本では人気のボールグリップだが、世界的にはマイナーなのだ）。
そして刃先だが、レーザーチップでは、レーザー加工によるギザ歯が施してあって、その凹凸でネジに食いつくことでカムアウトをしにくくしている。先端に凹凸を持たせたドライバーはこれまでにもあったが、レーザーでというのがポイントなのだろう。
Wera ダイヤモンドドライバー
グリップはレーザーチップと同じWera特有の形状だが、色が青になる。刃先はレーザーによる加工は無く、代わりに人工ダイヤの粒子をコーティングしているというもの。レーザーチップより耐久性に優れるが、価格としてもレーザーチップより少しお高め。
シャフトの根本が六角になっていて、レンチをかけて大トルクで回すこともできる。
アネックス 差替式ダイヤモンドドライバー
国内メーカーのアネックスの製品。その名のとおり差し替え式のビットを装着して使うタイプで、付属のビットはプラスの1と2の両頭タイプとなっている。
グリップ形状はボールグリップタイプ。ラチェット機構などは持たないが、同社からはラチェット機構付きのグリップも出ているので、それらと組み合わせてもいいかもしれない。ちなみにビット単体でも販売されているが、Amazonだとセットの方が実売価格が安い。
ダイヤモンドの粒子で食いつきをよくするというのはWeraと同じ発想だが、こちらはダイヤモンド粒子入りのメッキをしているような形。そのため刃先だけでなく全体がダイヤモンド粒子入りということになる。刃先にメッキというと精度の心配があるが、無電解ニッケルメッキという非常に薄いメッキを採用。そしてなにより安い。これでどこまで他のドライバーに太刀打ちできるのか、気になるところだ。
フィリップスプラスドライバーとJIS規格のドライバーは違う？
さて比較する前に、しばしばドライバーの話題で語られる、日本はJIS規格なので、海外製のドライバーだと合わない、という説について掘り下げたい。筆者自身、長らくスイス製のPBのドライバーを使っていて全く問題を感じていないので、実感として気にしたことがなかったのだが、せっかくならと調べてみた。
実は世界にはドライバーの規格がいろいろある。
プラスドライバーの元祖は1932年、アメリカのジョン P. トンプソンが発明した十字のシンプルな溝を持つスクリュードライバー。その特許がヘンリー F. フィリップスに譲渡され、1936年に現在まで繋がるフィリップスプラスドライバーが登場する。ドライバーのサイズをPH1、PH2などと表記するが、PHとはPhilipsのことを指す。
そして1949年、日本では、JIS規格で定めた独自のプラスドライバーが作られる。
日本のJIS規格とアメリカ生まれのフィリップスドライバーは、同じように見えて微妙に違いがある……らしい。というのも、海外のユーザーの間では、日本車やシマノの変速機をイジるならJIS規格のドライバーを使わないとなめる、という声が散見される。
で、そこで語られる違いというのが、まず、先端の徐々に細くなっていくところの角度。フィリップスのほうが鋭角で先端が長く、それと比べるとJISのほうが鈍角で短い。また、十字の交差する部分の形状も、JISが純粋な十字に近いのに対して、フィリップスのほうは交差部分に丸みを持たせたような形になっている、というのがよく語られる話だ。
要は、JISドライバーのほうが先端が短く、そしてJISネジも、それに合わせて浅く作られているので、そこに先の長いフィリップスドライバーを挿すと、奥まで入らず掛かりが甘くなってカムアウトしやすくなる、ということだ。
逆にフィリップスネジにJISドライバーを挿した場合は、底までは届かなくても力のかかる外周部分がちゃんとハマるのでほとんど問題にはならないという。つまり日本で普通に売られているJIS規格対応のドライバーを使っていれば、ネジの規格を意識させられる機会はないというわけだ（そういえば昔スナップオンのドライバーはアメリカのASME規格なので合わないという話を聞いたことがあった）。
ただし、ドライバーの規格については、調べれば調べるほどにいろいろな説が出てきて、真偽の分からない情報も多い。
前回の記事のコメントで、プラスドライバーがカムアウトするのは、過大トルクがかかった時に締めすぎを防ぐための正常な機能だ、というコメントがあった。
確かにフィリップスドライバーに関して、過大トルク時にカムアウトするように設計されている（対してJIS規格にはその機能がないのでカムアウトしにくい）、といった解説はあちこちで見られた。
ただ、フィリップスの特許にそういった記述はなく、カムアウトしやすいのは単なる設計上の問題（ミス）だ、という説もある。工具メーカーでも言うことが違うので、本当のところは分からない。他にもこういった真偽不明の情報があふれていたので、いろいろ調べてみたものの、本稿では深追いするのは避けておきたい。
だが、実は工具の規格も時代で少しずつ変わる（おかげでまたややこしくなるのだが）。というわけで、現在の状況を紹介したい。

スタメンでCTOしております、@tnir (X: @takuya_stmn, note: @takuya_stmn) です。
2023年9月、スタメン技術ブログで次の記事を公開しました。
記事では、TUNAG の技術的負債解消に向けてドメイン駆動設計（DDD）の導入を検討している、と書きました。その後の対外的な印象として、「スタメンは DDD を積極導入している」と読まれる場面がありました。
本記事の目的は二つです。
- 当時の検討表明と、いまの実装実態のあいだにある差分を正確に共有すること
- その後に行った小規模な試験導入（PoC）から得た、Rails 文脈での技術的・組織的な学びを共有すること
結論を先に述べます。私たちの設計の軸は ActiveRecord で、DDD はバックエンドのごく小さな範囲で試しました。その結果、ActiveRecord を軸にする方針を選んでいます。ただしこれは DDD全般の評価ではなく、私たちの文脈での記録です。小さく試し、合うものを残し、合わないものを手放すプロセス自体は、今でも有効なエンジニアリング判断だと考えています。
2023年の記事が書いていたこと
当時の記事の冒頭は、次のとおりです。
株式会社スタメンでは、企業エンゲージメント構築サービス TUNAG（ツナグ）の技術的負債解消と今後の持続的成長のため、ドメイン駆動設計(DDD)の導入を検討しています。
記事は実装報告ではなく、コアドメインを軸に「DDD が何を解決する手法なのか」を整理する解説でした。実装詳細は扱わない、とも明記しています。締めは、将来に向けた表明です。
つまり本文の事実は「導入を検討している」までであり、「すでに積極導入している」ではありません。ただし、解説の熱量や「邁進していきます」という結びが重なると、読後印象としては積極導入企業のように残りやすい面もありました。このギャップを、いま実装と検証結果に基づいて補正します。
当時の課題提起がなければ、机上の議論で終わっていた可能性もあります。検討を公開し、その後に実コードで検証まで進めたからこそ、本記事で共有するトレードオフが見えました。
何を、どこまで試したか
私たちのプロダクトは、大きくバックエンド（API）とフロントエンドに分かれます。
本記事では前者を 業務DXサービスA API、後者を 業務DXサービスB API と呼びます。どちらも TUNAG 本体から独立した形で実装されたグリーンフィールドサービスのバックエンドです。
業務DXサービスA API は、MVC でくくると Model がおおよそ 2,000 LoC 前後、View + Controller がおおよそ数百 LoC 規模でした。期間は 2023年12月からの約3ヶ月です。ここでの DDD は、Evans 流の戦術パターンを全面適用したものではなく、不変条件が重要な箇所に限定した実用主義的な導入（DDD-lite としても呼ばれることがある）でした。設問・選択肢・合格判定・受験セッションなど、「壊れると困るルール」が比較的はっきりしている領域だったため、試験対象として適していました。
実コードでは、たとえば次が確認できます。
- ドメイン層を ActiveRecord から分離した pure Ruby のオブジェクトがある
- 選択肢数・重複・合格ラインなどの不変条件を、生成時や操作時に検証する実装がある
- 一部の更新経路では、リポジトリ経由で集約を再構成してから永続化する
一方で、次の限界もありました。
- 単純更新・複製・一部セッション更新は ActiveRecord 直叩きのまま残り、層を迂回した
- 一部のドメインオブジェクトは、振る舞いに乏しいデータホルダーに近い
- ドメインイベントや、依存逆転を徹底した古典的構成までは採っていない
つまり「DDD を名乗るに足る部分実装はあった」が、「プロダクト全体の標準アーキテクチャになった」わけではありません。
時系列は次のとおりです。
業務DXサービスB API は「DDD 導入の第2弾」ではありません。振り返りの結果、採らないと決めたあとの開発です。境界の分離や外部モデルの漏洩防止など、マイクロサービスとして当然の設計はありますが、それを DDD の戦術導入とは数えません。
なぜ本格採用を見送ったか — 技術的・組織的な理由
ここが本記事の本題です。「やらなければよかった」ではなく、「何が効き、何が合わなかったか」を残します。
1. 本来の課題と手法がずれた
2023年の検討の出発点は、TUNAG の技術的負債解消でした。ところが検証が進むにつれ、手法の導入そのものが目的化しやすい 局面がありました。
負債解消で本当に解きたかったのは、たとえば次のようなことだと考えています。
- 変更影響の見通しを良くすること
- ドメイン知識をコード上で追跡しやすくすること
- チームが安全に改修できる速度を保つこと
一方で、層分け・用語・パターンの整備が進むと、「DDD らしく書けているか」が評価軸になりやすい。すると、負債解消や変更容易性への寄与より、導入の完成度が議論の中心になります。業務DXサービスA API での試験は、この目的化を本体から切り離して観測するためにも有用でした。振り返りの結論は明確で、その時点のスタメンの文脈では、DDD の本格導入は TUNAG の技術的負債解消に適していない、でした。
2. Rails / ActiveRecord との摩擦コストが高かった
業務DXサービスA API は Rails API です。ActiveRecord は永続化だけでなく、クエリ・バリデーション・ライフサイクル・関連の中心でもあります。ここに戦術的 DDD（集約の再構成、リポジトリ、pure ドメインモデル）を部分導入すると、少なくとも次のコストが発生しました。
- 二重モデル化: DB 行としての AR と、ドメイン上のオブジェクトを往復させる変換が必要になる
- 経路の分岐: 不変条件が強い操作だけドメイン経由、単純 CRUD は AR 直叩き、という二系統が同居する
- 認知負荷: 「この変更はどの層に書くべきか」の判断自体が、機能追加のたびに発生する
複雑な採点や、正式版の訂正ルールのように、壊れ方が高い箇所では、pure なドメインオブジェクトに寄せる利点はありました。逆に、大半の更新が CRUD に近い画面・API では、変換と層分けのコストが、得られる安全性を上回りやすかった、というのが率直な感触です。
Rails way（責務を散らさない Model、明確な UseCase、必要なら concern）を主軸にした方が、少人数チームでの変更速度と学習コストのバランスが良かった、というのが本格採用見送りの技術的な中核です。
3. 効く範囲が、プロダクト全体のボトルネックと一致しなかった
DDD が相対的に効きやすいのは、ルールが複雑で、不変条件の破壊がそのまま障害になる領域です。業務DXサービスA API でも、設問制約や採点のようにその種の箇所には部分適用の合理性がありました。
しかし TUNAG 本体を含むプロダクト全体の負債の主因が、「集約境界が無いこと」だけだったわけではありません。認証委譲、サービス分割、スキーマ契約、運用、データ整合、画面を含む変更伝播など、別種の複雑性の方が大きい局面も多い。戦術 DDD を局所に厚くしても、プロダクト全体の変更容易性が線形に改善するとは限らない、というのが PoC 後の整理です。
4. 小さく試せたから、大きく間違わずに済んだ
見送り自体を失敗とは捉えていません。新規の小さい API で約3ヶ月試し、振り返り、次の新規 API では使わないと決めた。この切れ方の方が、本体へ先に全面適用するより健全でした。
組織として得られた整理は、次です。
- DDD は銀の弾丸ではない
- 導入を目的化すると、負債解消から離れる
- Rails 中心のプロダクトでは、戦術 DDD の全面適用より、ActiveRecord を軸に複雑箇所だけ設計を厚くする方が現実的なことが多い
- 手法の採否は、流行や完成度ではなく、事業成長と開発生産性（保守性・変更容易性を含む）で見る
いまの設計方針
PoC 後の標準は、ActiveRecord を軸に置いています。UseCase（アプリケーションサービス）でユースケースの流れとトランザクション境界を担保しつつ、永続化モデル側は ActiveRecord 本来の表現力を活かす。そのうえで、モデルを無秩序に太らせないために、関心事ごとに concern へ閉じる、という形です。
これは「Fat Model に戻した」という意味ではありません。ドメイン層と AR を二重に持つコストを下げつつ、ユースケースのオーケストレーションは UseCase に残し、モデルに散らばりがちな関心事だけを concern で分割する、という選択です。Concern の濫用が神オブジェクトの隠蔽になりうることは認識したうえで、DDD-lite の二重モデルより、この分割の方がチームの認知負荷と変更速度に合う、と判断しています。
対外的な事実関係は、次で足ります。
- 2023年の記事は導入検討の表明であり、全面採用の報告ではない
- フロントエンドでは DDD を導入していない
- バックエンドでも、LoC ベースで全体の 1% を大きく下回る範囲での部分的・実践的な試験にとどまる
- 主例は業務DXサービスA API（2023年12月〜約3ヶ月）
- 2024年3〜4月の振り返りで本格採用を見送り、業務DXサービスB API（2024年5月〜約3ヶ月）では非採用前提で開発した
- 現在のスタメンを「DDD積極導入企業」と呼ぶのは実態に合わない
- 小さく検証し、合わなければ採用しない、という判断は今後も取りうる
手法の是非を好みで決めず、小さく試し、事業成長と変更容易性を含む生産性、および本来の課題（技術的負債解消）への寄与で採否を決める。業務DXサービスA API での試験と、業務DXサービスB API での見送りは、その一例です。
おわりに
この記事は、過去のチャレンジ計画ブログ記事を消すためのものではありません。当時の検討や、その後の試験を否定するものでもありません。むしろ、2023年の記事が課題を言語化し、仮説を外に出したからこそ、机上の空論で終わらせず実コードでトレードオフを検証できました。話題の手法をスローガンで終わらせず、小さなプロダクトに落として確かめ、本格採用を見送った記録です。
エンジニアリングにおいて重要なのは、流行を追うことでも、一度選んだ手法に固執することでもありません。自社のプロダクト特性、フレームワークの前提、チームの認知負荷に照らして、効く設計を残し、効かない設計を手放せることです。今回の PoC は、その判断をコードと振り返りで一度通した事例だと考えています。
設計の話をするときも、採用の話をするときも、「スタメンは DDD を積極導入している」ではなく、「小さく試し、Rails / ActiveRecord を軸に UseCase と concern で整理する設計を主軸として選び直した」と読んでいただけると、実態に近いです。

- 攻撃者は約40分間で326のIPアドレスを使い分けていました。同一の識別子が使い回されていたことから、同一の攻撃者によるものと判断しています。
- これらのIPアドレスから、約40分間に1,200件を超えるアクセスが行われる攻撃が複数回確認されました。
- このサイトへの攻撃に関してのアクセス量は人手とは考えにくい一方、ツール特有の機械的な規則性はなく、応答を見ながら手を変えていました。こうした特徴から、応答に応じて判断できる仕組み、たとえばAIなどが使われている可能性があります。

■ 調査の概要
JPCERT/CCおよび株式会社マクニカ（以下、マクニカ社）は2026年10月、国内組織で相次ぐ不正アクセス・情報漏えい事案について、攻撃手法や確認すべきアクセス元の情報を公開しました（※1）（※2）。当社では、マクニカ社が「重点的に確認するIPアドレス」として公開した2件のIPアドレスを起点に、当社が観測した通信を調査しました。
※保存されているログの範囲がサービスや環境によって異なるため、観測期間全体のデータを網羅したものではありません。特に9月18日～28日は、一部の環境のデータに限られます。
■ 観測された攻撃の流れ
観測した攻撃の一例では、攻撃者はまずSQLインジェクション（入力欄などに不正なデータベース命令を紛れ込ませる攻撃）によって、ログイン認証の回避や情報の窃取ができないかを探っていました。認証を回避できないことを確認すると、攻撃者があらかじめ作成していたとみられるアカウントでログインし、ログイン後の画面や機能の中で改めてSQLインジェクションが可能かを探索していました。
これらが成功しないことが分かると、サイトの機能そのものに狙いを移す動きが見られました。たとえば、ポイントが貯まる仕組みを持つサイトでは、他の利用者のポイントを窃取できないかを探る動きを確認しています。

■ 約40分間で326のIPアドレスを使い分け
この攻撃では、攻撃者が複数のIPアドレスを使い分けていることが分かりました。その数は、約40分間で326にのぼります。IPアドレスは異なっていても、リクエストの中で同一の識別子が使い回されていたことから、当社ではこれらを同一の攻撃者によるものと判断しています。
さらに、これらのIPアドレスから約40分間に1,200件を超えるアクセスが行われる攻撃を、複数回確認しています。人の手による操作とは考えにくい規模です。一方で、攻撃ツールで見られるような短時間の大量アクセスや、一定の規則に沿った機械的な動きは見られませんでした。
また、複数のサイトを横断して調査したところ、同じIPアドレスが当社の観測範囲で同時に複数のサイトを攻撃している様子は見受けられませんでした。このことから、一連の攻撃は単一の攻撃者によるものである可能性が高いと考えられます。
■ サイトごとに異なる攻撃手法
同一の攻撃者とみられる一方で、攻撃の仕方はサイトによって大きく異なっていました。SQLインジェクションの自動検査ツールとして知られる「sqlmap」を使う場合もあれば、コマンドラインからHTTPリクエストを送る「curl」や、スマートフォンアプリの開発に使われるプログラミング言語「Dart」の通信機能を使った攻撃の試行も観測しています。
観測されたUser-Agent（通信元のソフトウェアを示す情報）には、Windows上のブラウザやAndroid端末、スマートフォンアプリを装うものも含まれていました。標的のサイトやその提供形態（Webサイト、スマートフォンアプリ向けAPIなど）に合わせて、手段を切り替えている可能性が示唆されます。観測されたUser-Agentの例は「■ 観測された指標」に掲載しています。
■ 数値では測りにくい点
AIエージェントによる攻撃の可能性
今回の攻撃で特徴的なのは、一つひとつのレスポンスを判断しながら次の手を選んでいるような動きです。人の手では難しい量のアクセスでありながら、ツールのような規則性がなく、認証回避が失敗すればログインを試み、それも失敗すれば機能の悪用に切り替えるなど、状況に応じて行動を変えています。こうした特徴から、当社ではAIエージェントまたはそれに近い仕組みによる攻撃である可能性があると考えています。
なお、これは観測された振る舞いからの推測であり、AIの利用を直接示す痕跡を確認したものではありません。マクニカ社も、AIが使われたことを示すログや痕跡は確認されていないとしつつ、AIによって攻撃者の調査が高速化することへの懸念を示しています（※2）。
アクセス数の多さだけでは気づきにくい
今回の攻撃は、1つのIPアドレスあたりのアクセス数が少なく、短時間で一通り試すと引き上げられ、同じサイトに日を改めて現れる動きも確認されていません。そのため、特定のIPアドレスからのアクセス数や、ツール特有のパターンに頼った監視だけでは見逃すおそれがあります。
■ 攻撃者の目的
認証の回避や情報窃取の探索に加え、ポイントのように金銭的な価値に直結する機能やAPI（システム間で機能やデータをやり取りする窓口）の脆弱性を探っていたことから、情報窃取と金銭的な利益の獲得が主な狙いであると推測しています。
■ 相次ぐ不正アクセス事案について
JPCERT/CCは2026年10月8日、2026年9月前後から国内組織で不正アクセスによる個人情報などの漏えいが相次いでいるとして注意喚起を公開しました（※1）。確認されている攻撃手法として、既知の脆弱性の探索・悪用、公開されているスマートフォンアプリの解析などを通じたAPI経由の不正操作、BIツール「Metabase」の脆弱性（CVE-2026-72898）の悪用を挙げています。
マクニカ社も2026年10月7日、WEBシステムからの情報漏えい事案に関する分析を公開しました（※2）。国内法人のWEBシステムからの個人情報漏えいの公表件数は、2026年は10月6日時点で119件にのぼり、特定の企業を狙ったものではなく、公開されているWEBシステムへの無差別な攻撃の可能性が高いとしています。今回当社が観測した攻撃も、認証やAPIの不備を広く探る点で、両者が示す傾向と共通しています。
■ 推奨する対応
- 通常と異なるHTTPレスポンスコードの偏りを確認する
攻撃者はさまざまなリクエストを試すため、正常応答（200）以外の4xx系・5xx系のレスポンスが普段より増えることがあります。こうしたレスポンスが頻出している時間帯がないかを調べ、当たりをつけて重点的に確認することが、調査の最初の一歩として有効です。たとえば、アクセス過多を示す429を返しているリクエストがどのような内容かも、調査の観点の一つになります。
- レスポンスサイズの違いに注目する
認証APIなどでは、成功時・失敗時に決まったサイズのレスポンスが返ることがあります。それと異なるサイズのレスポンスが返っているリクエストは、攻撃の影響を受けている可能性があります。また、通常ではありえない大きさのレスポンスが返っている場合も、情報が引き出されている可能性があるため、より詳細な調査をお勧めします。
- 公開された指標とログを照合する
本レポートやJPCERT/CC、マクニカ社が公開しているIPアドレス・User-Agent・JA4 fingerprintなどを、自組織のアクセスログと照合してください。ただし、これらは正規の利用者と重なる場合もあるため、該当するアクセスがあったことだけで被害を判断せず、前後のリクエストやレスポンスとあわせて確認することが重要です。
- API・認証機能のアクセス制御と回数制限を点検する
ログイン後の機能も含め、すべてのAPIでサーバー側の権限確認が行われているか、ポイントの付与・移動など金銭的価値に関わる機能で他の利用者のデータを操作できないかを点検してください。単位時間あたりのリクエスト数の上限設定も、短時間の大量アクセスへの備えとして有効です（※1）。
- 脆弱性の解消とWAFによる防御を組み合わせる
SQLインジェクションの根本的な対策は、アプリケーション側で入力値を安全に扱う実装にすることです。あわせて、脆弱性診断（公開されない管理機能を含む）や既知の脆弱性へのパッチ適用を行い、WAFで攻撃リクエストを遮断する多層的な対策をとることが推奨されます。

内閣官房国家サイバー統括室（NCO）は10月9日、不正アクセスによる漏えいなどの事案を踏まえた対応についての注意喚起を発表した。
NCOは、大量の個人情報を取り扱う事業者や機微な情報を取り扱う事業者などに向けて、以下3点の対策ポイントを示し、「より一層の対策の徹底を速やかに検討いただくようお願いいたします」としている。
1.ウェブシステムなどの適切な管理
インターネットに公開されているシステムは特に攻撃の対象となりやすいため、「いつ攻撃を受けてもおかしくない」という前提で対策を講じることが重要となる。
具体的には、脆弱性の適切な管理として、ソフトウェアのアップデートを速やかに適用することやサポートが終了した製品やバージョンを使用しないことなどを挙げている。
2.サプライチェーンを通じた侵害への対策
サイバー攻撃への対策は、自社システムのみを対象として考えるのではなく、個人情報や業務情報を預ける委託先企業などを含むサプライチェーン全体で安全性を確保する観点で取り組む必要がある。

Deeper dive: Keyboard differences between Windows and Macs
Over the years, I learned about many gotchas and strange differences between keyboard handling on Mac and Windows – pertinent especially to web apps, which use the same codebase to cater to both. I thought it might be helpful to someone if I compile them all in one place.
This post is meant to be a reference, and there aren’t any cute or riveting stories hiding inside – if this seems boring to you, feel free to skip to the next one!
Different names for keys
What Windows calls Backspace, Mac calls Delete. What Windows calls Delete, Macs call Forward Delete. (This means saying “Delete” without specifying the platform might actually be confusing.)
What Windows calls ⏎ Enter, Mac calls ⏎ Return. However, Macs also have an ⌤ Enter, although only on a numeric keypad (previously, it was even there on laptops!). On keyboards without the physical Enter key, you can simulate it via Fn+Return.
In most Mac software, Enter and Return do the same thing. There are a few exceptions – for example, Photoshop adds a new line on Return but commits on Enter, and some classic pro apps like Cubase or Pro Tools do different things, too – but it seems to be a dying tradition. (If you are curious about the history of Return and Enter, I wrote about it once.)
Windows customarily calls the secondary key Numpad Enter. I don’t believe Fn+Enter works to simulate it.
Generally, third-party keyboards use Windows verbiage – so, Backspace and Enter. If a keyboard offers Mac conventions at all, they usually only extend to modifier keys.
Modifier keys
⌃ Control on Windows is the equivalent to ⌘ Command on a Mac. (Paste, for example, is ⌃V on Windows and ⌘V on a Mac.) But, confusingly, Apple devices still have a Control key, too. This was originally meant for terminal applications, but these days many GUI apps use it as an extra modifier key of much lesser significance than Control on Windows.
This means that for apps, Windows devices offer Ctrl, Alt, and Shift – and Macs offer ⌘ Command, ⌥ Option, ⌃ Control, and ⇧ Shift. That’s one more modifier key, and thus more space to breathe. (We’re not counting the Windows key or the 🌐 Globe/Fn key since those are technically reserved by the operating system.)

- ・サービス単位のアカウントに異常がないか確認してください。
- 作ったはずのないアカウントが存在しないか、削除・無効化されているはずのアカウントが有効化されていないか等の異常を確認してください。このような操作が記録されるログについての確認も並行しておこなうとより有効です。
外部に公開しているアプリケーション、自組織が利用している外部サービスのいずれにおいても、異常なログやアカウントの発見があった場合は、速やかにセキュリティインシデントと判定し、インシデント対応を進めてください。情報漏えいの可能性を考慮し、専門のセキュリティベンダーに詳細調査を依頼することを強く推奨します。
保有データの再点検
今回の多くの事案は情報漏えいにつながっています。情報を窃取されてしまうと、情報の悪用はもとより、「窃取した情報を公開する」と脅迫されたり、不正売買されるなど、情報を悪用した二次被害が拡大する傾向が強まっていますので、不要な情報は持たない、という基本原則のもと、自らが保有する情報資産を正確に把握し、必要最小限にする等、保有情報の再点検も必要です。これらの点検作業についても、速やかにおこなってください。

Deno is joining Cloudflare
For years, we’ve been working to make building server software simpler. We questioned how modules could be distributed, what security guarantees a JavaScript runtime could provide, what belonged in a complete toolchain, and how easily an application could be distributed as a standalone executable. Compatibility with Node.js became an important part of that work too: our users wanted the Deno improvements while continuing to plug into the existing JS ecosystem. The team and community built a runtime that brought these capabilities together and challenged assumptions about what JS development could look like.
Today we’re announcing that the entire Deno team is joining Cloudflare to take that work further.
Our ambition has always extended beyond the runtime. I wrote about this in my JavaScript Containers blog post: compute, storage, and communication working together, without every application assembling its own infrastructure.
With Deno Deploy, we took another step towards that goal. We wanted to make running applications as straightforward as possible. But building and operating Deploy also showed us how much complexity remained underneath that developer experience. I wanted to simplify that layer, too.
This led to celld. Building on the Cloudflare Workers programming model, celld lets developers build distributed applications from the start while making the system simple to operate. What excites me greatly is that the scaling is built into the programming model, rather than infrastructure each app has to assemble itself.
The progression from Deno to Deno Deploy to celld explains why this move makes sense to us. At Cloudflare we’ll combine our work with that of the Workers and Durable Objects teams. - We will continue supporting rusty_v8 and work toward integrating it into workerd.

This is what I’m most excited to explore and why celld focuses on Durable Objects.

印刷物基準の文字組みをウェブの世界で。日本デザインセンター様から生まれたiOS用文字組みエンジンをJavaScriptに移植しました。
私たちの会社では株式会社日本デザインセンター様から公開されている書く気分を高めるエディタ「stone」から生まれたオープンソースのiOS用文字組エンジン「stone engine」を、広くWebの世界で利用できるように「stone-engine.js」としてJavaScriptに移植しました。
これにより、モダンJSフレームワークを使ったウェブの世界でも、印刷物水準の日本語組版、縦書き、禁則処理、文字詰めが可能になります。
日本デザインセンター様より許可をいただき、本日よりオープンソースで無償で公開しています。一行のコマンドで導入できるので、ぜひご利用ください。
すでにこのサイトと自社サービス「atelier yori.so」に利用されています。
できること
すべてこのページ上で実際に組まれています。文字にマウスを乗せると赤くなるのは、1文字ずつがSVGの要素になっているからです。
縦書きと縦中横
2 桁以下の数字は正体で並べ、3 桁以上の数字と英字は 90 度回転します。句読点や括弧は縦組み用のグリフに置き換わります。
コードを見る
<StoneText direction="tbRl" height={280} fontSize={18} lineHeightScale={1.9}>
{"令和6年12月31日、Ver.2.0を公開した。数字は2桁まで縦中横、3桁以上の123と英字は回転する。"}
</StoneText>
禁則処理
句読点や閉じ括弧を行頭に、開き括弧を行末に置きません。「ー」や小書きの仮名、全角の「！」「・」も行頭に置かない強い禁則（CSS の line-break: strict 相当）で、「……」「——」の途中でも改行しません。
コードを見る
// 比べやすいように 1 文字単位で折り返す（dividesByWords={false}）
<StoneText width={220} dividesByWords={false} kinsoku>{text}</StoneText>
<StoneText width={220} dividesByWords={false} kinsoku={false}>{text}</StoneText>
約物の詰め
句読点や括弧の連続を半角にします。stone モードは前後の文字を見て、自然に見えるところだけ詰めます。
コードを見る
<StoneText punctuationMode="whole">{text}</StoneText> // 常に全角
<StoneText punctuationMode="half">{text}</StoneText> // 常に半角
<StoneText punctuationMode="stone">{text}</StoneText> // 前後関係で判断（既定）

和文・欧文・絵文字ごとにフォントとスケールを指定できます。ここでは欧文を Georgia にし、0.9 倍にしています。
コードを見る
<StoneText

japanese: { family: '"Noto Serif JP", serif' },
latin: { family: "Georgia, serif", scale: 0.9 },
}}
>
{"日本語の中に English や 2024 を混ぜても、文字種ごとにフォントとスケールを選べる。"}
</StoneText>

行頭・中央・行末・均等。均等配置は最終行と改行で終わる行を除き、余白を文字間に均等に配ります。欧文の単語の途中と「……」「——」の間は空けません。
コードを見る
// 余白は文字間に均等に配る。欧文の単語の途中と「……」「——」の間は空けない
<StoneText textAlign="justify" width={300}>{text}</StoneText>

スタメンでCTOしております、@tnir (X: @takuya_stmn, note: @takuya_stmn) です。
2023年9月、スタメン技術ブログで次の記事を公開しました。
記事では、TUNAG の技術的負債解消に向けてドメイン駆動設計（DDD）の導入を検討している、と書きました。その後の対外的な印象として、「スタメンは DDD を積極導入している」と読まれる場面がありました。
本記事の目的は二つです。
- 当時の検討表明と、いまの実装実態のあいだにある差分を正確に共有すること
- その後に行った小規模な試験導入（PoC）から得た、Rails 文脈での技術的・組織的な学びを共有すること
結論を先に述べます。私たちの設計の軸は ActiveRecord で、DDD はバックエンドのごく小さな範囲で試しました。その結果、ActiveRecord を軸にする方針を選んでいます。ただしこれは DDD全般の評価ではなく、私たちの文脈での記録です。小さく試し、合うものを残し、合わないものを手放すプロセス自体は、今でも有効なエンジニアリング判断だと考えています。
2023年の記事が書いていたこと
当時の記事の冒頭は、次のとおりです。
株式会社スタメンでは、企業エンゲージメント構築サービス TUNAG（ツナグ）の技術的負債解消と今後の持続的成長のため、ドメイン駆動設計(DDD)の導入を検討しています。
記事は実装報告ではなく、コアドメインを軸に「DDD が何を解決する手法なのか」を整理する解説でした。実装詳細は扱わない、とも明記しています。締めは、将来に向けた表明です。
つまり本文の事実は「導入を検討している」までであり、「すでに積極導入している」ではありません。ただし、解説の熱量や「邁進していきます」という結びが重なると、読後印象としては積極導入企業のように残りやすい面もありました。このギャップを、いま実装と検証結果に基づいて補正します。
当時の課題提起がなければ、机上の議論で終わっていた可能性もあります。検討を公開し、その後に実コードで検証まで進めたからこそ、本記事で共有するトレードオフが見えました。
何を、どこまで試したか
私たちのプロダクトは、大きくバックエンド（API）とフロントエンドに分かれます。
本記事では前者を 業務DXサービスA API、後者を 業務DXサービスB API と呼びます。どちらも TUNAG 本体から独立した形で実装されたグリーンフィールドサービスのバックエンドです。
業務DXサービスA API は、MVC でくくると Model がおおよそ 2,000 LoC 前後、View + Controller がおおよそ数百 LoC 規模でした。期間は 2023年12月からの約3ヶ月です。ここでの DDD は、Evans 流の戦術パターンを全面適用したものではなく、不変条件が重要な箇所に限定した実用主義的な導入（DDD-lite としても呼ばれることがある）でした。設問・選択肢・合格判定・受験セッションなど、「壊れると困るルール」が比較的はっきりしている領域だったため、試験対象として適していました。
実コードでは、たとえば次が確認できます。
- ドメイン層を ActiveRecord から分離した pure Ruby のオブジェクトがある
- 選択肢数・重複・合格ラインなどの不変条件を、生成時や操作時に検証する実装がある
- 一部の更新経路では、リポジトリ経由で集約を再構成してから永続化する
一方で、次の限界もありました。
- 単純更新・複製・一部セッション更新は ActiveRecord 直叩きのまま残り、層を迂回した
- 一部のドメインオブジェクトは、振る舞いに乏しいデータホルダーに近い
- ドメインイベントや、依存逆転を徹底した古典的構成までは採っていない
つまり「DDD を名乗るに足る部分実装はあった」が、「プロダクト全体の標準アーキテクチャになった」わけではありません。
時系列は次のとおりです。
業務DXサービスB API は「DDD 導入の第2弾」ではありません。振り返りの結果、採らないと決めたあとの開発です。境界の分離や外部モデルの漏洩防止など、マイクロサービスとして当然の設計はありますが、それを DDD の戦術導入とは数えません。
なぜ本格採用を見送ったか — 技術的・組織的な理由
ここが本記事の本題です。「やらなければよかった」ではなく、「何が効き、何が合わなかったか」を残します。
1. 本来の課題と手法がずれた
2023年の検討の出発点は、TUNAG の技術的負債解消でした。ところが検証が進むにつれ、手法の導入そのものが目的化しやすい 局面がありました。
負債解消で本当に解きたかったのは、たとえば次のようなことだと考えています。
- 変更影響の見通しを良くすること
- ドメイン知識をコード上で追跡しやすくすること
- チームが安全に改修できる速度を保つこと
一方で、層分け・用語・パターンの整備が進むと、「DDD らしく書けているか」が評価軸になりやすい。すると、負債解消や変更容易性への寄与より、導入の完成度が議論の中心になります。業務DXサービスA API での試験は、この目的化を本体から切り離して観測するためにも有用でした。振り返りの結論は明確で、その時点のスタメンの文脈では、DDD の本格導入は TUNAG の技術的負債解消に適していない、でした。
2. Rails / ActiveRecord との摩擦コストが高かった
業務DXサービスA API は Rails API です。ActiveRecord は永続化だけでなく、クエリ・バリデーション・ライフサイクル・関連の中心でもあります。ここに戦術的 DDD（集約の再構成、リポジトリ、pure ドメインモデル）を部分導入すると、少なくとも次のコストが発生しました。
- 二重モデル化: DB 行としての AR と、ドメイン上のオブジェクトを往復させる変換が必要になる
- 経路の分岐: 不変条件が強い操作だけドメイン経由、単純 CRUD は AR 直叩き、という二系統が同居する
- 認知負荷: 「この変更はどの層に書くべきか」の判断自体が、機能追加のたびに発生する
複雑な採点や、正式版の訂正ルールのように、壊れ方が高い箇所では、pure なドメインオブジェクトに寄せる利点はありました。逆に、大半の更新が CRUD に近い画面・API では、変換と層分けのコストが、得られる安全性を上回りやすかった、というのが率直な感触です。
Rails way（責務を散らさない Model、明確な UseCase、必要なら concern）を主軸にした方が、少人数チームでの変更速度と学習コストのバランスが良かった、というのが本格採用見送りの技術的な中核です。
3. 効く範囲が、プロダクト全体のボトルネックと一致しなかった
DDD が相対的に効きやすいのは、ルールが複雑で、不変条件の破壊がそのまま障害になる領域です。業務DXサービスA API でも、設問制約や採点のようにその種の箇所には部分適用の合理性がありました。
しかし TUNAG 本体を含むプロダクト全体の負債の主因が、「集約境界が無いこと」だけだったわけではありません。認証委譲、サービス分割、スキーマ契約、運用、データ整合、画面を含む変更伝播など、別種の複雑性の方が大きい局面も多い。戦術 DDD を局所に厚くしても、プロダクト全体の変更容易性が線形に改善するとは限らない、というのが PoC 後の整理です。
4. 小さく試せたから、大きく間違わずに済んだ
見送り自体を失敗とは捉えていません。新規の小さい API で約3ヶ月試し、振り返り、次の新規 API では使わないと決めた。この切れ方の方が、本体へ先に全面適用するより健全でした。
組織として得られた整理は、次です。
- DDD は銀の弾丸ではない
- 導入を目的化すると、負債解消から離れる
- Rails 中心のプロダクトでは、戦術 DDD の全面適用より、ActiveRecord を軸に複雑箇所だけ設計を厚くする方が現実的なことが多い
- 手法の採否は、流行や完成度ではなく、事業成長と開発生産性（保守性・変更容易性を含む）で見る
いまの設計方針
PoC 後の標準は、ActiveRecord を軸に置いています。UseCase（アプリケーションサービス）でユースケースの流れとトランザクション境界を担保しつつ、永続化モデル側は ActiveRecord 本来の表現力を活かす。そのうえで、モデルを無秩序に太らせないために、関心事ごとに concern へ閉じる、という形です。
これは「Fat Model に戻した」という意味ではありません。ドメイン層と AR を二重に持つコストを下げつつ、ユースケースのオーケストレーションは UseCase に残し、モデルに散らばりがちな関心事だけを concern で分割する、という選択です。Concern の濫用が神オブジェクトの隠蔽になりうることは認識したうえで、DDD-lite の二重モデルより、この分割の方がチームの認知負荷と変更速度に合う、と判断しています。
対外的な事実関係は、次で足ります。
- 2023年の記事は導入検討の表明であり、全面採用の報告ではない
- フロントエンドでは DDD を導入していない
- バックエンドでも、LoC ベースで全体の 1% を大きく下回る範囲での部分的・実践的な試験にとどまる
- 主例は業務DXサービスA API（2023年12月〜約3ヶ月）
- 2024年3〜4月の振り返りで本格採用を見送り、業務DXサービスB API（2024年5月〜約3ヶ月）では非採用前提で開発した
- 現在のスタメンを「DDD積極導入企業」と呼ぶのは実態に合わない
- 小さく検証し、合わなければ採用しない、という判断は今後も取りうる
手法の是非を好みで決めず、小さく試し、事業成長と変更容易性を含む生産性、および本来の課題（技術的負債解消）への寄与で採否を決める。業務DXサービスA API での試験と、業務DXサービスB API での見送りは、その一例です。
おわりに
この記事は、過去のチャレンジ計画ブログ記事を消すためのものではありません。当時の検討や、その後の試験を否定するものでもありません。むしろ、2023年の記事が課題を言語化し、仮説を外に出したからこそ、机上の空論で終わらせず実コードでトレードオフを検証できました。話題の手法をスローガンで終わらせず、小さなプロダクトに落として確かめ、本格採用を見送った記録です。
エンジニアリングにおいて重要なのは、流行を追うことでも、一度選んだ手法に固執することでもありません。自社のプロダクト特性、フレームワークの前提、チームの認知負荷に照らして、効く設計を残し、効かない設計を手放せることです。今回の PoC は、その判断をコードと振り返りで一度通した事例だと考えています。
設計の話をするときも、採用の話をするときも、「スタメンは DDD を積極導入している」ではなく、「小さく試し、Rails / ActiveRecord を軸に UseCase と concern で整理する設計を主軸として選び直した」と読んでいただけると、実態に近いです。
今現在、主に採用しているシンプルな Rails Way に準じたアーキテクチャに関しては別の記事でコメントできればと思います。

- 攻撃者は約40分間で326のIPアドレスを使い分けていました。同一の識別子が使い回されていたことから、同一の攻撃者によるものと判断しています。
- これらのIPアドレスから、約40分間に1,200件を超えるアクセスが行われる攻撃が複数回確認されました。
- このサイトへの攻撃に関してのアクセス量は人手とは考えにくい一方、ツール特有の機械的な規則性はなく、応答を見ながら手を変えていました。こうした特徴から、応答に応じて判断できる仕組み、たとえばAIなどが使われている可能性があります。

■ 調査の概要
JPCERT/CCおよび株式会社マクニカ（以下、マクニカ社）は2026年10月、国内組織で相次ぐ不正アクセス・情報漏えい事案について、攻撃手法や確認すべきアクセス元の情報を公開しました（※1）（※2）。当社では、マクニカ社が「重点的に確認するIPアドレス」として公開した2件のIPアドレスを起点に、当社が観測した通信を調査しました。
※保存されているログの範囲がサービスや環境によって異なるため、観測期間全体のデータを網羅したものではありません。特に9月18日～28日は、一部の環境のデータに限られます。
■ 観測された攻撃の流れ
観測した攻撃の一例では、攻撃者はまずSQLインジェクション（入力欄などに不正なデータベース命令を紛れ込ませる攻撃）によって、ログイン認証の回避や情報の窃取ができないかを探っていました。認証を回避できないことを確認すると、攻撃者があらかじめ作成していたとみられるアカウントでログインし、ログイン後の画面や機能の中で改めてSQLインジェクションが可能かを探索していました。
これらが成功しないことが分かると、サイトの機能そのものに狙いを移す動きが見られました。たとえば、ポイントが貯まる仕組みを持つサイトでは、他の利用者のポイントを窃取できないかを探る動きを確認しています。

■ 約40分間で326のIPアドレスを使い分け
この攻撃では、攻撃者が複数のIPアドレスを使い分けていることが分かりました。その数は、約40分間で326にのぼります。IPアドレスは異なっていても、リクエストの中で同一の識別子が使い回されていたことから、当社ではこれらを同一の攻撃者によるものと判断しています。
さらに、これらのIPアドレスから約40分間に1,200件を超えるアクセスが行われる攻撃を、複数回確認しています。人の手による操作とは考えにくい規模です。一方で、攻撃ツールで見られるような短時間の大量アクセスや、一定の規則に沿った機械的な動きは見られませんでした。
また、複数のサイトを横断して調査したところ、同じIPアドレスが当社の観測範囲で同時に複数のサイトを攻撃している様子は見受けられませんでした。このことから、一連の攻撃は単一の攻撃者によるものである可能性が高いと考えられます。
■ サイトごとに異なる攻撃手法
同一の攻撃者とみられる一方で、攻撃の仕方はサイトによって大きく異なっていました。SQLインジェクションの自動検査ツールとして知られる「sqlmap」を使う場合もあれば、コマンドラインからHTTPリクエストを送る「curl」や、スマートフォンアプリの開発に使われるプログラミング言語「Dart」の通信機能を使った攻撃の試行も観測しています。
観測されたUser-Agent（通信元のソフトウェアを示す情報）には、Windows上のブラウザやAndroid端末、スマートフォンアプリを装うものも含まれていました。標的のサイトやその提供形態（Webサイト、スマートフォンアプリ向けAPIなど）に合わせて、手段を切り替えている可能性が示唆されます。観測されたUser-Agentの例は「■ 観測された指標」に掲載しています。
■ 数値では測りにくい点
AIエージェントによる攻撃の可能性
今回の攻撃で特徴的なのは、一つひとつのレスポンスを判断しながら次の手を選んでいるような動きです。人の手では難しい量のアクセスでありながら、ツールのような規則性がなく、認証回避が失敗すればログインを試み、それも失敗すれば機能の悪用に切り替えるなど、状況に応じて行動を変えています。こうした特徴から、当社ではAIエージェントまたはそれに近い仕組みによる攻撃である可能性があると考えています。
なお、これは観測された振る舞いからの推測であり、AIの利用を直接示す痕跡を確認したものではありません。マクニカ社も、AIが使われたことを示すログや痕跡は確認されていないとしつつ、AIによって攻撃者の調査が高速化することへの懸念を示しています（※2）。
アクセス数の多さだけでは気づきにくい
今回の攻撃は、1つのIPアドレスあたりのアクセス数が少なく、短時間で一通り試すと引き上げられ、同じサイトに日を改めて現れる動きも確認されていません。そのため、特定のIPアドレスからのアクセス数や、ツール特有のパターンに頼った監視だけでは見逃すおそれがあります。
■ 攻撃者の目的
認証の回避や情報窃取の探索に加え、ポイントのように金銭的な価値に直結する機能やAPI（システム間で機能やデータをやり取りする窓口）の脆弱性を探っていたことから、情報窃取と金銭的な利益の獲得が主な狙いであると推測しています。
■ 相次ぐ不正アクセス事案について
JPCERT/CCは2026年10月8日、2026年9月前後から国内組織で不正アクセスによる個人情報などの漏えいが相次いでいるとして注意喚起を公開しました（※1）。確認されている攻撃手法として、既知の脆弱性の探索・悪用、公開されているスマートフォンアプリの解析などを通じたAPI経由の不正操作、BIツール「Metabase」の脆弱性（CVE-2026-72898）の悪用を挙げています。
マクニカ社も2026年10月7日、WEBシステムからの情報漏えい事案に関する分析を公開しました（※2）。国内法人のWEBシステムからの個人情報漏えいの公表件数は、2026年は10月6日時点で119件にのぼり、特定の企業を狙ったものではなく、公開されているWEBシステムへの無差別な攻撃の可能性が高いとしています。今回当社が観測した攻撃も、認証やAPIの不備を広く探る点で、両者が示す傾向と共通しています。
■ 推奨する対応
- 通常と異なるHTTPレスポンスコードの偏りを確認する
攻撃者はさまざまなリクエストを試すため、正常応答（200）以外の4xx系・5xx系のレスポンスが普段より増えることがあります。こうしたレスポンスが頻出している時間帯がないかを調べ、当たりをつけて重点的に確認することが、調査の最初の一歩として有効です。たとえば、アクセス過多を示す429を返しているリクエストがどのような内容かも、調査の観点の一つになります。
- レスポンスサイズの違いに注目する
認証APIなどでは、成功時・失敗時に決まったサイズのレスポンスが返ることがあります。それと異なるサイズのレスポンスが返っているリクエストは、攻撃の影響を受けている可能性があります。また、通常ではありえない大きさのレスポンスが返っている場合も、情報が引き出されている可能性があるため、より詳細な調査をお勧めします。
- 公開された指標とログを照合する
本レポートやJPCERT/CC、マクニカ社が公開しているIPアドレス・User-Agent・JA4 fingerprintなどを、自組織のアクセスログと照合してください。ただし、これらは正規の利用者と重なる場合もあるため、該当するアクセスがあったことだけで被害を判断せず、前後のリクエストやレスポンスとあわせて確認することが重要です。
- API・認証機能のアクセス制御と回数制限を点検する
ログイン後の機能も含め、すべてのAPIでサーバー側の権限確認が行われているか、ポイントの付与・移動など金銭的価値に関わる機能で他の利用者のデータを操作できないかを点検してください。単位時間あたりのリクエスト数の上限設定も、短時間の大量アクセスへの備えとして有効です（※1）。
- 脆弱性の解消とWAFによる防御を組み合わせる
SQLインジェクションの根本的な対策は、アプリケーション側で入力値を安全に扱う実装にすることです。あわせて、脆弱性診断（公開されない管理機能を含む）や既知の脆弱性へのパッチ適用を行い、WAFで攻撃リクエストを遮断する多層的な対策をとることが推奨されます。

JR東日本、「えきねっと」「ビューカード」などで漏えいか メルアドなど最大609万件 IDCFへの不正アクセスで【追記あり】
JR東日本とグループ会社のビューカードは10月9日、列車予約サービス「えきねっと」や会員制サービス「大人の休日倶楽部」、ビューカードの会員サイト「VIEW's NET」において、合計約609万件の利用者情報が漏えいした可能性があると発表した。7日にIDCフロンティアが公表した不正アクセスが原因で、メール配信用の外部サービスに保存していた利用者の情報が第三者に閲覧・取得された恐れがあるという。
JR東日本で漏えいした可能性があるのは、えきねっと会員の約167万件と、大人の休日倶楽部会員の約39万件。えきねっとではメールアドレスのみが対象で、法人向けの「ビジネスえきねっと」会員は含まれない。大人の休日倶楽部では、メールアドレスに加え、会員番号、クレジットカードの有効期限、生年月日が漏えいした可能性があるという。
ビューカードでは、会員サイト「VIEW's NET」に登録する会員のメールアドレス約403万件が漏えいした可能性がある。対象者の特定は現在も調査中という。「iiマーク」のあるカードやビュー法人カードは対象に含まれない。なお、JR東日本とビューカードはいずれも、氏名、住所、電話番号、クレジットカード番号などが漏えいした可能性はないとしている。
両社によると、現時点では一部顧客のメールアドレスなどが第三者に閲覧・取得された可能性を否定できないという。また、不正アクセスの影響により、3サービスでは会員向けのメール配信に一部支障が生じている。情報が漏えいした可能性のある利用者には、準備が整い次第、個別にメールで通知し、謝罪する方針だ。
IDCFクラウドの障害は7日午前3時40分ごろから発生しており、福島県白河市のデータセンターにある「東日本リージョン1」の一部が影響を受けた。IDCフロンティアによると、495の企業や自治体が影響を受けており、対象となる一部の仮想サーバではデータの取り出しや復元が困難な見通しという。

Carson Gross
I teach computer science at Montana State University. I am the father of three sons who all know I am a computer programmer and one of whom, at least, has expressed interest in the field. I love computer programming and try to communicate that love to my sons, the students in my classes and anyone else who will listen.
A question I am increasingly getting from relatives, friends and students is:
Given AI, should I still consider becoming a computer programmer?
My response to this is: “Yes, and…”
“Yes”
Computer programming is, fundamentally, about two things:
- Problem-solving using computers
- Learning to control complexity while solving these problems
I have a hard time imagining a future where knowing how to solve problems with computers and how to control the complexity of those solutions is less valuable than it is today, so I think it will continue to be a viable career even with the advent of AI tools.
“You have to write the code”
That being said, I view AI as very dangerous for junior programmers because it is able to effectively generate code for many problems. If a junior programmer does not learn to write code and simply generates it, they are robbing themselves of the opportunity to develop the visceral understanding of code that comes with being down in the trenches.
Because of this, I warn my students:
“Yes, AI can generate the code for this assignment. Don’t let it. You have to write the code.”
I explain that, if they don’t write the code, they will not be able to effectively read the code. The ability to read code is certainly going to be valuable, maybe more valuable, in an AI-based coding future.
If you can’t read the code you are going to fall into The Sorcerer’s Apprentice Trap, creating systems you don’t understand and can’t control.
Is Coding → Prompting like Assembly → High Level Coding?
Some people say that the move from high level languages to AI-generated code is like the move from assembly to high level programming languages.
I do not agree with this simile.
Compilers are, for the most part, deterministic in a way that current AI tools are not. Given a high-level programming language construct such as a for loop or if statement, you can, with reasonable certainty, say what the generated assembly will look like for a given computer architecture (at least pre-optimization).
The same cannot be said for an LLM-based solution to a particular prompt.
High level programming languages are a very good way to create highly specified solutions to problems using computers with a minimum of text in a way that assembly was not. They eliminated a lot of accidental complexity, leaving (assuming the code was written reasonably well) mostly necessary complexity.
LLM generated code, on the other hand, often does not eliminate accidental complexity and, in fact, can add significant accidental complexity by choosing inappropriate approaches to problems, taking shortcuts, etc.
If you can’t read the code, how can you tell?
And if you want to read the code you must write the code.
AI is a great TA
Another thing that I tell my students is that AI, used properly, is a tremendously effective TA. If you don’t use it as a code-generator but rather as a partner to help you understand concepts and techniques, it can provide a huge boost to your intellectual development.
One of the most difficult things when learning computer programming is getting “stuck”. You just don’t see the trick or know where to even start well enough to make progress.
Even worse is when you get stuck due to accidental complexity: you don’t know how to work with a particular tool chain or even what a tool chain is.
This isn’t a problem with you, this is a problem with your environment. Getting stuck pointlessly robs you of time to actually be learning and often knocks people out of computer science.
(I got stuck trying to learn Unix on my own at Berkeley, which is one reason I dropped out of the computer science program there.)
AI can help you get past these roadblocks, and can be a great TA if used correctly. I have posted an AGENTS.md file that I provide to my students to configure coding agents to behave like a great TA, rather than a code generator, and I encourage them to use AI in this role.
AI doesn’t have to be a detriment to your ability to grow as a computer programmer, so long as it is used appropriately.
“, and…”
I do think AI is going to change computer programming. Not as dramatically as some people think, but in some fundamental ways.
Raw coding may become less important
It may be that the act of coding will lose relative value.
I regard this as too bad: I usually like the act of coding, it is fun to make something do something with your (metaphorical) bare hands. There is an art and satisfaction to writing code well, and lots of aesthetic decisions to be made doing it.
However, it does appear that raw code writing prowess may be less important in the future.

中でもドライバーは最初にファクトリーギアで買った工具だと思う。いくら一流工具はいいと言われてもなかなか高価で手が出しにくい中、せっかくだしドライバー1本ぐらいはと買って帰った。当時は高級ドライバーといえばPBが人気で、使用頻度の高いプラスの2番を1本だけ購入して帰ったが、これが工具沼にハマる第一歩となった。
それまではドライバーでネジをなめることはときどきあったし、なめるとドライバーの刃先がダメージを受けて、ますますカムアウトしやすくなる、という悪循環。ところがPBはネジにピッタリフィットしてカムアウトする気配がない。カムアウトしないから刃先も痩せないし、だからいつまでも使える、と結局20年ぐらい使い続けた。その間、国内メーカーからもカムアウト防止機能付きのドライバーなどが出て、いろいろ試したこともあったが、結局PBが一番気に入っていて、次もPBに買い換えた。
そんなわけで、Weraはいいという話は聞いたことはあったものの、自分で使う機会がなかった。加えて、昔のカムアウト防止機能にあまりよい印象が無かったのもあって、食わず嫌いだった、というのもある。
ただ、先日アネックスのダイヤモンド龍靱ビットを使って、ちょっと見方が変わった。今時のカムアウト防止機能は結構スゴいかも、という気がしてきた。がぜんWeraのカムアウト防止機能付きドライバーにも興味が沸いてきたのだ。
PB SWISS TOOLS vs Wera vs アネックスで比較!!
ということで今回比較するのは、筆者が長らく愛用しているPBの最新モデル スイスグリップEVOと、Weraからは、読者から推す声が多かったレーザーチップ、加えてWeraのもう1種類のカムアウト防止機能であるダイヤモンドドライバー、そして最後に国内メーカーからアネックスの差替式ダイヤモンドドライバーを用意してみた。
まずは製品の説明から。
PB SWISS TOOLS スイスグリップEVO
2025年に登場した新モデル。マルチクラフトグリップ、スイスグリップと継承してきた樽形のグリップをベースに、ゆるやかに三角形に近づけたような形状で、従来の形状より手になじみやすく、約25％高いトルクがかけられるという。
刃先は特別なカムアウト防止加工はされておらず、とにかく精度を追求している。刃先が黒っぽいのはメッキをしていないため。これも精度を求めた結果で、メッキの厚みで精度が落ちるのを嫌ったのが理由。といっても最近のドライバーは先端にメッキしていないものがほとんどだが。あとは軸にバネ鋼ベースの特殊素材を使うことで弾性に優れるというのもポイントだろう。
Wera レーザーチップドライバー
読者からなめにくいと推す声が多かったドライバー。Weraはかなりバリエーションが多くて、ステンレスタイプなどもあるが、今回はスタンダードなレーザーチップを選んでいる。
Weraの特長の1つがそのグリップ形状。上下が細く、真ん中が太い変わった形状だが、これは柔らかいボールをグッと握りしめたときの手のひらの内側の形状に合うように作られているのだという。ただ、他にボールグリップタイプも用意されていて、これは日本市場に向けて開発されたものだそうだ（日本では人気のボールグリップだが、世界的にはマイナーなのだ）。
そして刃先だが、レーザーチップでは、レーザー加工によるギザ歯が施してあって、その凹凸でネジに食いつくことでカムアウトをしにくくしている。先端に凹凸を持たせたドライバーはこれまでにもあったが、レーザーでというのがポイントなのだろう。
Wera ダイヤモンドドライバー
グリップはレーザーチップと同じWera特有の形状だが、色が青になる。刃先はレーザーによる加工は無く、代わりに人工ダイヤの粒子をコーティングしているというもの。レーザーチップより耐久性に優れるが、価格としてもレーザーチップより少しお高め。
シャフトの根本が六角になっていて、レンチをかけて大トルクで回すこともできる。
アネックス 差替式ダイヤモンドドライバー
国内メーカーのアネックスの製品。その名のとおり差し替え式のビットを装着して使うタイプで、付属のビットはプラスの1と2の両頭タイプとなっている。
グリップ形状はボールグリップタイプ。ラチェット機構などは持たないが、同社からはラチェット機構付きのグリップも出ているので、それらと組み合わせてもいいかもしれない。ちなみにビット単体でも販売されているが、Amazonだとセットの方が実売価格が安い。
ダイヤモンドの粒子で食いつきをよくするというのはWeraと同じ発想だが、こちらはダイヤモンド粒子入りのメッキをしているような形。そのため刃先だけでなく全体がダイヤモンド粒子入りということになる。刃先にメッキというと精度の心配があるが、無電解ニッケルメッキという非常に薄いメッキを採用。そしてなにより安い。これでどこまで他のドライバーに太刀打ちできるのか、気になるところだ。
フィリップスプラスドライバーとJIS規格のドライバーは違う？
さて比較する前に、しばしばドライバーの話題で語られる、日本はJIS規格なので、海外製のドライバーだと合わない、という説について掘り下げたい。筆者自身、長らくスイス製のPBのドライバーを使っていて全く問題を感じていないので、実感として気にしたことがなかったのだが、せっかくならと調べてみた。
実は世界にはドライバーの規格がいろいろある。
プラスドライバーの元祖は1932年、アメリカのジョン P. トンプソンが発明した十字のシンプルな溝を持つスクリュードライバー。その特許がヘンリー F. フィリップスに譲渡され、1936年に現在まで繋がるフィリップスプラスドライバーが登場する。ドライバーのサイズをPH1、PH2などと表記するが、PHとはPhilipsのことを指す。
そして1949年、日本では、JIS規格で定めた独自のプラスドライバーが作られる。
日本のJIS規格とアメリカ生まれのフィリップスドライバーは、同じように見えて微妙に違いがある……らしい。というのも、海外のユーザーの間では、日本車やシマノの変速機をイジるならJIS規格のドライバーを使わないとなめる、という声が散見される。
で、そこで語られる違いというのが、まず、先端の徐々に細くなっていくところの角度。フィリップスのほうが鋭角で先端が長く、それと比べるとJISのほうが鈍角で短い。また、十字の交差する部分の形状も、JISが純粋な十字に近いのに対して、フィリップスのほうは交差部分に丸みを持たせたような形になっている、というのがよく語られる話だ。
要は、JISドライバーのほうが先端が短く、そしてJISネジも、それに合わせて浅く作られているので、そこに先の長いフィリップスドライバーを挿すと、奥まで入らず掛かりが甘くなってカムアウトしやすくなる、ということだ。
逆にフィリップスネジにJISドライバーを挿した場合は、底までは届かなくても力のかかる外周部分がちゃんとハマるのでほとんど問題にはならないという。つまり日本で普通に売られているJIS規格対応のドライバーを使っていれば、ネジの規格を意識させられる機会はないというわけだ（そういえば昔スナップオンのドライバーはアメリカのASME規格なので合わないという話を聞いたことがあった）。
ただし、ドライバーの規格については、調べれば調べるほどにいろいろな説が出てきて、真偽の分からない情報も多い。
前回の記事のコメントで、プラスドライバーがカムアウトするのは、過大トルクがかかった時に締めすぎを防ぐための正常な機能だ、というコメントがあった。
確かにフィリップスドライバーに関して、過大トルク時にカムアウトするように設計されている（対してJIS規格にはその機能がないのでカムアウトしにくい）、といった解説はあちこちで見られた。
ただ、フィリップスの特許にそういった記述はなく、カムアウトしやすいのは単なる設計上の問題（ミス）だ、という説もある。工具メーカーでも言うことが違うので、本当のところは分からない。他にもこういった真偽不明の情報があふれていたので、いろいろ調べてみたものの、本稿では深追いするのは避けておきたい。
だが、実は工具の規格も時代で少しずつ変わる（おかげでまたややこしくなるのだが）。というわけで、現在の状況を紹介したい。
工具メーカーTEKTONのウェブサイトにまとめられた情報が分かりやすいので以下に引用させていただくと、現在のプラスドライバーの規格は、国際的に統一される傾向にあって、フィリップスドライバーの生まれたアメリカのASME規格（ASME B107.600-2016）も、国際規格のISO（ISO 8764-1：2004）も、日本のJIS規格（JIS B 4633：1998）とほとんど同じになっている（主な違いは公差の幅で、規格の古いJISが一番広い）。
ちなみに明確な違いとしては、先端の部分の処理だ。プラスドライバーは先に行くほど細くなっているが、先端の部分は尖っているわけではなく、角度を落とした緩やかな円錐になっている。そしてこの角度がJISだと17～19°とされているのに対して、ISOやASMEでは0～19°となっている。0°でもいいということは、つまりここを平坦にしてしまってもいい、というのがISOとASMEの規格だ。
また、十字の羽根の部分、ネジに引っかかる部分が刃先から何㎜まで平坦である必要があるか、というのも、JISは3.7mm以上という基準なのに対してISOが4.37mm以上、ASMEが4.83mm以上と、ISOやASMEのほうが基準が厳しくなっている。
刃先の形はどれだけ違うのか、写真で比較
ということで、海外メーカーのPBやWeraとJISのアネックスで刃先の形状はどれほど違うのか、刃先の部分を比較してみたい。そこで、角度をできるだけそろうようにして撮影したものを横並びで比較したのが以下の写真だ。ただし手作業なので多少のずれはご了承いただきたい。
