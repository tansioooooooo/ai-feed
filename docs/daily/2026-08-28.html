Everything I own, owned
Over the past couple weeks I’ve been doing agent-driven reverse engineering of peripherals that happen to be within arm’s reach. From those devices, I’ve come away with a full plaintext command shell inside my microphone, a webcam whose activity LED I can switch off while it records, and a key light that hands out memory writes to anyone on the WiFi. Peripherals have proven to be an ideal target for agentic RE - they’re tiny computers attached to my computer, with a data connection to the host and usually a firmware update mechanism, so an agent has something to iterate against. The net outcome is better control and understanding of my machine.
My process was pretty much the same for each of these devices: grab a copy of the device’s firmware and associated update tool from the manufacturer, throw it into my reverse engineering environment, tell Claude Opus 5 what my goals are, and let it churn. Depending on the device, the goals were somewhat different, but they usually looked something like:
In this directory is the firmware and update utility for ___. The device is also attached to this computer, and you may interact with it in non-mutating ways. Exhaustively document and cross-validate the entire firmware, including the following goals:
* reverse engineer the firmware update format and update protocol
* implement our own update utility
* determine the security properties of the update protocol, including checksums, signature validation, secure boot
* use static and dynamic analysis to determine all protocol surfaces and completely enumerate functionality
* find any hidden or debug functionality in the product and how to access it
Depending on the results, there were different directions of follow-up, but you should get the general idea. Let’s run through the list - each device links to a GitHub repo full of generated-slop docs and scripts, most of which have been validated live against real hardware. I’ve also included the effort each device took, pulled out of the Claude Code session transcripts. “Churn” is the time Claude was actually working, with the long idle gaps removed. “Prompts from me” is every message I typed, including the one-word ones telling it to keep going. All five devices together came out to about 13 hours of churn and 98 prompts, spread across two weeks of evenings.
I’ve shared everything in this post with the vendors involved.

GitHub repo - 3.7 hours of Claude churn, 33 prompts from me
I use an Insta360 Link webcam, which is a nice gimbaled pan-tilt-zoom camera that does face tracking for automatically framing the shot. I wanted to know if it was possible to subvert the activity LED, like in the classic iSeeYou exploit.
Interestingly, it was immediately obvious that this camera has a lot going on inside it. It turns out that it runs a whole RTOS (ThreadX) sourced from the upstream SoC vendor, Ambarella. The RTOS hosts several small vision models that provide things like the aforementioned face tracking, as well as gesture detection for controlling settings. Pretty amazing complexity inside a tiny webcam, but it also means there’s some exciting attack surface here.
Over the USB Video Class interface, there’s an XU (Extension Unit) command that kicks the device into “mass storage” mode. This then lets us transfer a staged firmware update to the device’s internal FAT filesystem, which the device then applies to itself on reboot. This route does require user intervention to reboot with a replug, but there’s actually another command channel that exposes arbitrary read/write of files and a reboot command over the USB vendor class. With this, we can fully flash the device without any user interaction. Once the firmware is in the right place, there’s effectively no anti-tamper, just an appended MD5 hash to ensure integrity.
The indicator LED turns out to have a well-structured set of “patterns” in the firmware that dictate color, blink pattern, etc. that are indexed into for various device states. I had Claude write a tool to patch out the table entry for camera activity, fix up the integrity hash, and flash it to the camera. A quick test showed that the green LED that normally illuminates while recording no longer turned on. Horrifying! On this device, the gimbal itself also deflects down when not recording, so it’s not completely stealth, but it still doesn’t feel great.

How we saved 100 terabytes of memory by optimizing 1.1.1.1’s DNS cache
Big Pineapple, the platform behind 1.1.1.1, Gateway DNS, DNS Firewall, AS112, and several other Cloudflare DNS services, stores over 250 billion DNS cache entries at any given time. At that scale, wasting a single byte per entry costs more than 250 gigabytes of memory across our fleet.
Five successive changes to how cache entries are stored in memory cut the per-entry footprint by over 50%. Across our fleet, these changes freed up roughly 100 terabytes of memory, equivalent to the amount of RAM in 130 of our Gen 13 servers. The cache also got faster. Insert throughput rose 43% and lookup latency dropped 19%, as fewer allocations and better memory locality meant we did not trade speed for space.
What we cache
On cold start, Big Pineapple starts out with an empty cache. As DNS queries arrive, the cache fills until it hits its maximum entry count, at which point we evict older or less popular items to make room.
The exact cache size varies by data center. When EDNS Client Subnet (ECS) is in use, authoritative servers return different answers depending on the client's network, so we cache multiple versions of the same query. This increases both the number of entries and the memory each one consumes, making the optimizations in this post especially impactful for ECS-heavy locations.
Each item in the cache is a key-value pair. The key identifies what was queried:
pub struct CacheKey {
qname: Name,
qtype: Rtype,
authenticated: bool,
tag: Vec<u8>,
}
The value stores the DNS response itself: the answer, authority, and additional record sections, along with metadata like the creation time, a hit counter, and the Time-to-Live (TTL).
pub struct CacheEntry {
timestamp: UnixTimeStamp,
pub inception: Instant,
pub ttl: Ttl,
pub hits: u32,
pub answers: Vec<Record>,
pub authority: Vec<Record>,
pub additional: Vec<Record>,
pub errors: Vec<ExtendedError>,
...
}
Both structs have room for improvement. Several fields use types that carry overhead we don't need once the entry is stored.
Benchmarking memory usage
To measure the impact of each change, we benchmark by filling the cache with randomly generated entries that roughly match the traffic distribution we see in production: 56% A records, 25% AAAA, and 19% TXT. Each entry contains between one and four records.
TXT records serve as a stand-in for all non-A/AAAA record types in the benchmark. Their size is randomized between 64 and 224 bytes, close to the average response size we see for variable-length record types.
We track memory usage using a custom allocator that wraps Rust’s System allocator and records the number and size of allocations per cache entry. Alongside memory, we measure insert throughput and lookup latency across the full cache flow to make sure memory savings don’t come at the cost of performance.
These inputs approximate production rather than reproduce it exactly. Process memory also depends on traffic mix, cache occupancy, allocator state, and memory used outside the cache. We therefore measured resident memory across production instances during the rollout.
The cost of capacity
Vec<T> stores three fields: a pointer to heap-allocated data, the current length, and the total capacity. When you push an item, Vec checks whether the length exceeds the capacity and reallocates if needed. If there’s room, it just appends the item and increments the length.
Once we store a DNS response in the cache, however, we never modify it again. The capacity field serves no purpose, but still costs 8 bytes per Vec. The over-allocated heap space is wasted as well, as a Vec with capacity for eight items but only five stored leaves three slots unused on the heap.
Using Box<[T]> solves both problems. It can’t grow after creation, so it doesn’t need a capacity field or reserve space for future elements. The same applies to String, which also carries a capacity field. Box<str> drops it.
Each cache entry stores 8 Vec and String fields. Replacing them with Box<[T]> and Box<str> saves 8 bytes per field, 64 bytes per entry. It also eliminates the excess heap memory that Vec reserves for future growth. The combined savings add up to over 15 terabytes with over 250 billion cache entries.
Fewer lists, fewer pointers
Rather than storing the answer, authority, and additional sections in separate lists, we can store a single list with offsets to the start of each section. Since DNS record counts per section fit in a u16, we can use a u16 (2 bytes) for each offset, compared to the 8-byte pointer and 8-byte length that each separate Box<[T]> requires.
This removes two lists, each with an 8-byte pointer and 8-byte length, and replaces them with two 2-byte offsets, saving 28 bytes per entry.

Small Models Have Arrived
For the past few weeks, I've been playing with gpt-5.6-luna. It is shockingly capable, fast, and smart. I regularly see it do ~100 tps, and rip around my codebase, email, and knowledge base.
Of course, the biggest thing with luna is the cost. I've tried running some fairly complicated research threads, and it's pretty tough to run up a large bill. Even having it search across thousands of emails, I end up with an API cost in the tens of cents.
With GLM 5.3, we even have a new option at the Pareto frontier.
When doing coding work, I almost always reach for the most expensive and capable models (Fable 5, 5.6 Sol). So it's been easy to miss the progress the small fast models have made.
One thing a few investors I've talked with have mentioned: "It's weird we're not seeing more consumer AI companies. Why is that?"
There's a straightforward answer: token costs.
In the times before AI, the playbook for big consumer apps looked like this...
- create some sort of compelling website which is fairly cheap to run
- attract a bunch of users (typically with some virality)
- raise money, scale to more users
- create an ads marketplace
This roughly describes most of the big consumer companies (Google, Facebook, Snapchat, etc.).1
But what if you want to add AI to your product? Well, now you have some real inference costs on every request! Suddenly the amount of capital required increases dramatically.
A pet eval of mine is to build a daily news site, personalized to me:
research @calvinfo on the internet. figure out what news they might like. build a micro-site with today's top stories, personalized for them. search hn, reddit, twitter, etc.
With the previous generation of models (Sonnet class), you'd spend ~$1 to get anywhere. Charging $30/mo is untenable for a consumer app. There's obviously a lot we can optimize here, but if you're charging what the WSJ or The Economist charges, you'd better be delivering similar value.
But looking at luna, the results are pretty decent, and the average cost is ~$0.10. Now we're talking!
Where I think this gets even more interesting is in the world of business.
My Segment co-founder Peter and I were recently comparing notes on a hike. Across his various startups, Peter has seen two kinds of work:
- the "IQ 180" work. some mad scientist genius type comes up with some crazy solution you've never thought of.
- the "token spewer" work. being ultra responsive, pushing the ball forward across dozens of different fronts.
Peter runs multiple companies. Beyond Segment, he's raised $100m+ for Charm Industrial, and just recently closed a Series A for Revoy. He's incredibly organized and efficient with his time.
And yet, Peter mentioned that ~95% of the work he does falls into bucket 2. It's hopping on calls. Nudging people. Blocking and tackling.
To be clear, Peter says his companies would be dead-in-the-water today without an IQ 180 technical mind solving the deep problems. Just that most of his work falls in bucket 2.2
I think demand for "frontier-level" models is going to keep compounding. Especially for fields that require novel breakthroughs or discovery (engineering, hard science, model training).
But I also think the demand for "fast/cheap/good-enough" models is just about to take off.
Think of the people you interact with on a daily basis: coworkers, vendors, and customers. Nine times out of ten, you want someone who is super responsive, and just handles things for you. Most of the "human tokens" at companies today are spent this way — hiring skews heavily toward the fast/cheap/good-enough archetype.
There's a lot of work that needs to happen to make fast/cheap/good-enough models a reality for business. New harnesses, prompt injection safety, roles, and permissions. But I'm confident we'll figure that out.
If you're also experimenting with making small models useful, please drop me a line.

石川温の「スマホ業界 Watch」
なぜ「povo 5G SAで圏外」に "端末非対応”ではなくKDDIの設定ミス
2026年8月28日 00:00
KDDIのオンライン専用ブランド「povo」がついに5G SAに対応した。しかし、5G SA開始直後、思わぬ騒動が勃発している。SNS上で「5G SAに切り替えようとしたら、圏外になってしまった」という声が相次いでいるのだ。
その声の主はほとんどがSIMフリーのAndroidで5G SAを開通させようとした人たちだった。
povoではauが取り扱っていないSIMフリーのAndroidは5G SAの対応機種に入れていない。しかし、人柱的にSIMフリーのAndroidで5G SAを入れてみようとした人が、予想通りつながらなくなってしまった。
しかも、デュアルSIMで使っていた場合、もう片方の、別キャリアのSIMカードも使えなくなるという。
復活させるには、翌日、5G SAから5G NSAに戻す作業が必要となる。ただ、SIMカードの切り替えという作業が発生するため、本人確認に時間がかかるという、なんとも厄介な状況となっている。
povoの対応機種を紹介するページでは
【5G SA対応SIMのお申し込みをご検討中のお客さまへのご案内】
5G SA対応端末以外では、通信ができなくなる可能性があります。
※Android端末については、SIMフリー端末を含む他社が販売する端末等は5G SA通信に対応していない場合があります。
※iPhone端末については、iPhone 13シリーズ以前およびiPhone SEは対応しておりません。
5G SA対応端末であっても、端末のソフトウェアが最新でない場合、通信ができなくなる可能性があります。

というアナウンスをするようになった。
SNS上の有志の間で、ネットワークの挙動に関して、検証が進められている。それらによれば、povoのネットワーク側で、非対応機種が接続してこようとした際に、拒否するような仕組みが入っているという。
実際に、KDDIに確認したところ「povo2.0での5G SAについては、意図せずに誤った設定をしておりました。そのため、一部の端末で予期せぬ挙動が発生することも確認しており、今般、設定変更を行うため準備しております」とのことであった。
本来、povoの5G SAはauやUQモバイルと同じ仕様のはずだった。しかし、「意図せず誤った設定」をしてしまったことで、今回のような混乱が起きたようだ。設定の変更が完了すれば、povoの5G SAはauやUQモバイルと同じ仕様になるようだ。
ちなみにpovo側で設定を変えることで「5G SAに対応した端末では接続できる可能性があります。ただ、動作確認済みの端末以外では、正常に通信できない可能性があるため、引き続き動作検証を進め、対応端末についてはWebサイトで公開していきます」（KDDI）とのことであった。自分の端末が対応機種かどうかをきちんと確認した方が良いだろう。
5G SAはすでにauだけでなく、ソフトバンクやNTTドコモでも提供されている（残念ながら楽天モバイルは現時点で提供されていない）。
5G SA関連で、こういったトラブルが発生したのはpovoが初めてだ。端末側で5G SAの仕様を満たせば、どのキャリアでも使えるように感じるが実際はそうではないらしい。
SIMフリースマートフォンが5G SAにつなぐのは、これまでとは異なる技術や規格への対応が必要なのだろうか。
SIMフリースマートフォンに強いメーカー関係者によれば「5G SAと一言でいっても、実は微妙に各社ごとに仕様が異なる。キャリアモデルとして納入する際には当然、5G SAへ対応するが、SIMフリーの場合はそうはいかない。とはいっても、5G SAはこれからの技術と言えるので、次第にこなれてくるのではないか」という。
まさに今回はpovoが「こなれていない」ために起こったと言えそうだ。
そもそも、povoはこれまでのキャリアにないスタンスで「オンラインでSIMのみを手に入れられる」という点が魅力だ。しかし、今回の5G SA騒動は、「auで販売されているスマートフォンのみ5G SAにつなげられる」という条件であり、幅広い端末を受け入れてきた、これまでのpovoとは大きく異なる。
KDDIは「povoは、SIMのみを提供するブランドとして、従来から通信キャリアで販売された端末やSIMフリー端末を問わず、広くpovoの通信を提供してきました。その考えのもと、幅広い端末の動作検証も実施してきており、5G SAについてもその考え方は変わっておりません」としている。
5G SAの設定変更などは早急に実施される見込みで、混乱もすぐに収まる可能性が高い。
ただ、一度、5G SAに接続できなかった契約を5G NSAに戻す際にも本人確認が必要で、さらに5G SAにしようと思えば、また本人確認が必要となる。
KDDIでは「想定以上のお申し込みを多数いただいており、通常よりも本人確認の対応にお時間をいただいています。お客さまにはご不便をおかけして申し訳ございませんが、確認後、順次お客さまにはご案内を行っておりますので、お待ちいただきますようお願いいたします」としている。

ローカル AWS エミュレータで Terraform を検証する
はじめに
Zenn 読者のみなさん、こんにちは。e-dash VPoE の伊藤です。
e-dash ではアプリケーションインフラとして多くのプロダクトで AWS を採用しており、IaC として Terraform でインフラリソースを全面的に管理しています。
最近はインフラ構築・運用も全面的に AI にお任せするようになってきました。AI 登場前はあまり気にならなかったのですが、インフラも AI に任せるようになったことで、ローカルで迅速にフィードバックループが回せる環境がほしくなってきました。
今回は、Terraform から使えるローカル AWS エミュレータを取り上げ、何が評価できて何が評価できないのか、を検証していきます。
Terraform で利用可能なローカル AWS エミュレータ
ローカル AWS エミュレータは、AWS の API と同じレスポンスを手元のプロセスで返すことで、実アカウントなしに SDK・CLI・Terraform を動かせるようにするツールです。
2026年7月現在、Terraform から使える主なエミュレータは以下の3つです。
- LocalStack：最も普及しているエミュレータで、110 以上のサービスに対応。ただし無償の Community Edition で使えるのは Lambda・S3・DynamoDB・SQS・SNS・IAM などのコアサービスに限られ、RDS や API Gateway、Step Functions などは有償プランが必要になる。2026年3月以降は無償利用でも認証トークンの登録が必須になった。
-
Floci：2026年に登場した新興エミュレータで、68 サービス程度に対応する。MIT ライセンスの OSS で、アカウント登録も認証トークンも不要。Quarkus Native 製で起動が速く（公称で約 24 ミリ秒、アイドル時のメモリが約 13 MiB）、docker compose up だけで立ち上がる。LocalStack と同じ4566 番ポートで待ち受けるため、既存の LocalStack 向け設定をそのまま流用できる。
-
moto：もともと Python のテストで AWS 呼び出しをモックするライブラリだが、moto_server としてスタンドアロンのエンドポイントを立てれば Terraform からも利用できる。Python のテストコードと組み合わせる場面に向いている。
今回は、無償のまま RDS のようなサービスまで触れる Floci を利用して検証を進めていきます。

Floci は docker compose で起動し、http://localhost:4566 でアクセスできます。
Terraform からは、AWS プロバイダのエンドポイントをこのアドレスに向ければOKです。
具体的には、プロバイダ設定で endpoints ブロックでサービスごとに指定します。
資格情報の検証やアカウント ID の問い合わせは実 AWS に飛んでしまうため、あわせて無効化します。

技術的な制約
Floci の公式サイトは、対応サービス数（AWS で 68 サービス）と「実エンジンで動く」点（Lambda は実 Docker コンテナ、RDS は実 PostgreSQL / MySQL、ElastiCache は実 Redis）をアピールしています。
制約を一覧したページはありませんが、サービスごとのドキュメントを読むと、何が再現されないのかは個別に書かれています。以下は、その記述と実際に触れて確認した挙動をあわせて整理したものです。
具体的には、次のような制約があります。
- API カバレッジは完全ではない：全 API・全パラメータが実装されているわけではない。サービス一覧では Bedrock Runtime がスタブ実装（ストリーミングは 501 を返す）と明記されている。使いたいサービスの必要な操作が対応しているかは、事前に確認する必要がある。
-
IAM の認可は既定で評価されない：IAM のドキュメントは「By default Floci accepts any credentials without enforcing IAM policies」と述べており、test /test のような固定値で何でも通る。ただしFLOCI_SERVICES_IAM_ENFORCEMENT_ENABLED を有効にすると、リクエストごとに呼び出し元のポリシーが評価され、許可がなければ 403 のAccessDeniedException が返る。
-
ECS の secrets は解決されない：タスク定義のsecrets （valueFrom ）で指定した環境変数はコンテナに注入されない。通常のenvironment は注入される。公式ドキュメントに記載はなく、Case 5 で確認した挙動である。
- ネットワーク制御は再現されない：EC2 のドキュメントはセキュリティグループについて「not enforced as a firewall (Docker bridge networking handles routing)」と述べている。ルートテーブルや NACL も同様に、リソースとして保存されるだけで通信の可否を決めない。
- 料金・クォータ・レイテンシは対象外：課金額やサービスクォータ、実 AWS のネットワーク遅延といった非機能面は再現されない。
-
サービスを選んで起動できない：LocalStack からの移行ガイドによれば、SERVICES 環境変数による絞り込みはなく、全サービスが起動する。
エミュレータが再現するのは、あくまで API のレスポンス（コントロールプレーン）です。
実際にパケットを流したり権限を評価したりする挙動（データプレーン）は、再現されないか、部分的な再現にとどまります。
一方で、RDS や ElastiCache などのステートフルなサービスを、モックではなく実際の Docker コンテナ（PostgreSQL や MySQL など）で動かします。このためデータベースについては、本物のエンジンに対して SQL を流して挙動を確かめられます。

DataRobot Japanの小川です。日本法人の立ち上げ期から、現場でのAI導入支援とCoE（Center of Excellence／AI推進組織）の立ち上げ伴走をずっとやってきました。

つまり、「AIの民主化」は約8年前に自分たちで打ち出し、その1年半後には自分たちで軌道修正した言葉です。そして私は、そこから7年近くCoEの話をし続けてきました。それを踏まえた上で、いま改めて申し上げたいことがあります。

1. AutoML時代の「民主化」が成立していた前提
批判から入る前に、なぜ当時の機械学習（AutoML）では民主化が一定の合理性を持っていたのかを整理しておきます。感情ではなく前提条件の話なので、ここは冷静に振り返る必要があります。
前提1：生産性の差が「1対5」程度だった
AutoMLを装備した市民データサイエンティストの生産性を「1」、専門家の生産性を「5」と仮定します。ここが重要なところで、素手の非専門家の話ではありません。AutoMLというツールが差をかなり圧縮してくれた上での「1」です。
この比率であれば、算数が成り立ちます。現場に10人分のライセンスを配れば、トータルのアウトプットは 1×10＝10。専門家2人分（5×2＝10）と並びます。20人に配れば専門家4人分です。専門家を2人採用するより、現場の20人にツールを配るほうが速いし安い、という判断は当時それなりに合理的でした。
前提2：リスクの低い領域から広げる、という設計だった
もうひとつ、当時の民主化とセットで語っていたのが「どの領域から広げるか」でした。
いきなり与信審査や品質保証の最終判定を市民データサイエンティストに作らせる、という話ではありません。リード優先順位づけのような、外しても業務が即座に壊れない領域から広げていく。専門家が作れば90〜100点のところ、70点のモデルでも十分に価値が出る、という割り切りが成立したのは、そもそも70点で許される領域を選んでいたからです。
（以下、本記事で使う点数は「他人に業務で使わせられる水準を100点」とした私の体感値です。統一の物差しとして読んでください。）
リードのスコアリング精度が数ポイント落ちても、それまで担当者の勘と経験だけで決めていた優先順位が数字ベースになるなら、価値は出ます。外れたところで、営業が架電する順番が少し変わるだけです。逆に言えば、リスクの高い領域には最初から民主化を持ち込んでいませんでした。
「多少精度が落ちても、リスクの低いところで数の力でカバーできる」。この算数が成り立っていたからこそ、ツールを広く配る民主化には意味があったわけです。逆に言えば、この2つの前提が崩れたら民主化は成立しません。
余談：それでもAutoMLは「Excel」にはならなかった
当時、社内やお客様先でよく話していたのは、「AutoMLはExcelにはならない」ということでした。
Excelは事実上、全社員が使えます。ただ、AutoMLで意味のあるモデルを作ろうと思ったら、データの持ち方を理解していて、リーケージに気づけて、AUCやLogloss、RMSEが何を言っているかがわかる必要がある。この時点でだいぶ人を選びます。
感覚的には、どれだけうまく広げてもExcel VBAが書ける層くらいまでが受け取り手側のスキルの限界だろう、という話をしていました。そして実際、おおむねその通りになりました。「誰でも」と言いながら、AutoMLの民主化にも最初から天井があったわけです。この話は、あとの章にそのまま効いてきます。
2. AIエージェント時代の算数：1対100〜1000の世界
そして、いまのAIエージェントでは、この前提がどちらも崩れています。
AIエージェントは、プロンプトを少し書けば誰でも「30点のもの」を一瞬で作れます。動くプロトタイプがその日のうちにできる。これが「誰でも作れる＝民主化だ」という感覚を生みます。
なぜ非専門家の点数が70点から30点に落ちるのか
ここで、「1章は70点なのに、こっちは30点？ タイポか？」と思われた方がいるかもしれません。タイポではありません。私の体感として、エージェントで非専門家が70点を出すのは難しいです。
では、なぜ同じ「素人が作ったもの」なのに、点数が半分以下になるのか。
理由はシンプルで、ツールが肩代わりしてくれる範囲が違うからです。
AutoMLは、専門家と非専門家の差そのものをツール側が埋める設計でした。アルゴリズムの選択も、特徴量生成も、ハイパーパラメータの調整も、精度検証の作法も、押せば全部やってくれる。だから素人がボタンを押しても70点のモデルが出てきたわけです。1章で「1」をAutoMLを装備した市民データサイエンティストと定義したのは、まさにこの意味でした。
一方、エージェント開発で下がったのは入口の敷居だけです。プロンプトを書けば何かが動く、そこまでは一瞬でたどり着けます。しかし、そこから先の例外処理も、評価設計も、権限管理も、コスト設計も、ツールは肩代わりしてくれません。入口が広がっただけで、入口から実務水準までの距離は、むしろAutoML時代より伸びています。
もちろん、腰を据えて教育し続ければ70点に到達する人は出てきます。そこは否定しません。ただ、それでも算数は好転しないのです。理由は3つあります。
- 合格ラインが上がっている：AutoML時代は70点で合格でしたが、他人に業務で使わせるエージェントは80点以上ないと使えません。70点まで来ても、まだ届かない。
- 初期値が下がっている：70点スタートと30点スタートでは、埋めるべき差が倍以上違います。
- 埋めるコストが桁違い：しかもその差を埋める中身が、ソフトウェア工学の広い知識です。ツールの操作研修とデータサイエンス基礎知識のような単一科目だけでは埋まりません。
かつては「合格ラインが70点で、非専門家が最初から70点を出せた」から民主化が成立していました。いまは、合格ラインが上がり、初期値が下がり、その差を埋めるコストが跳ね上がっている。三重に悪化しています。
具体的に、何が足りないのか
「自分の手元で動かす30点」と「他人に業務で使わせる実用レベル（80点以上）」の間にあるギャップを、具体的に並べてみます。
- 例外処理とハルシネーションの制御
- 既存システム・APIとの堅牢な連携
- セキュリティ、権限管理、データ漏洩対策
- 評価基盤の設計（そもそも「良くなった」をどう測るのか）
- 運用保守と、エラー時のフォールバック設計
- トークンコストの設計
最後のトークンコストは、AutoML時代にはあまり存在しなかった軸です。手元で10回動かす分にはフラッグシップモデルを富豪的に使えばいい。しかし全社の業務で毎日回すとなると、そのままではコストが見合いません。
そうなると「安いモデルに寄せる」という話になりますが、ここで問題が一段複雑になります。安いモデルに落とした上で、ハルシネーションや指示追従の品質を落とさずに運用できるのか。モデルを落としても壊れないようにコンテキストとワークフローを設計し直せるのか。 「動くか」ではなく「いくらで、どの品質で、動き続けるか」 という問いに答える必要があり、これはプロトタイプを作った人が最も想像しにくい部分でもあります。
効くのはドメイン知識よりソフトウェア工学の知識
このリストを見ていただくとわかる通り、どれもプロンプトの上手さとは別の領域の話です。例外処理、疎結合、テスト、可観測性、コスト設計。要するに、ソフトウェア工学の広大な知識を持っている人が圧倒的に強いという結論になります。
ここがAutoML時代との決定的な違いです。AutoMLは、ドメイン知識を持っている人に装備させたときのシナジーが非常に大きいツールでした。業務を知っている人が自分でモデルを回せることに、はっきりした意味があった。
一方でエージェントは、ドメイン知識よりもソフトウェアの知識のほうが効きます。しかもその知識がないまま作ると、単に品質が低いものができるのではなく、リスクのあるものができてしまう。この非対称性が、「現場に作らせる」という発想の前提を壊しています。
余談：30点で構わない領域も、ちゃんとある
念のため補足しておくと、30点のものに価値がない、という話ではまったくありません。 自己責任の範囲 なら、30点で十分です。
メールの英文化、自分用の議事録の要約、企画を詰めるときの壁打ち相手。この手の使い方に合格ラインはありません。おかしければ自分で気づいて、自分で捨てられるからです。10回投げて3回使えれば得。むしろ30点のものをどんどん作って、どんどん捨てるのが正しい使い方だと思っています。ここは大いに民主化すべきですし、実際そうなりつつあります。

AI への指示書は自然言語で書きます。
書いた本人には明確に見えますし、AI も分かったという顔をして実装を始めます。
その結果、できあがったものが思っていたものではないことがあります。
なぜなら、自然言語は解釈が揺れるからです。
私が開発している OSS の TAKT では、この揺れを実行前の対話で潰しています。
具体的には、アシスタントとタスクを詰めて合意した内容を、指示書にまとめてからエージェント群に渡すようにしています。
この指示書の受け入れ条件はこれまで Gherkin で書かせてきました。
v0.61.0 でここに形式仕様モードという設定を足しました。
有効にすると、指示書の要件を Quint と Alloy という記法でも表現するようになります。
形式手法は正しさが欲しい場面で昔から使われてきた道具です。
ただ実務で常用するには仕様を書いて維持するコストが高く、採用できないという結論になりがちの代物でした。
有効であることは間違いないが運用するのが重い。
そんな形式手法ですが、昨今は AI の時代です。
書く手間を AI が引き受けられるなら、実用可能ではないだろうか。
これが、この手法に取組むきっかけになったのです。
TAKT の形式仕様モードの仕組み
TAKT では TUI を開くとデフォルトで形式手法を利用するかを確認されます。
なお、この設定は config.yaml に assistant.formal_spec として設定もできます。
# ~/.takt/config.yaml（プロジェクトの .takt/config.yaml でも可）
assistant:

type Outcome = Proceed | ExitNonZero
// パスが同じなら衝突、という判定
pure def collides(globalReal: str, projectReal: str): bool =

// パスが衝突していたらエラー終了、それ以外は続行
pure def startupOutcome(isMetaOnly: bool, globalReal: str, projectReal: str): Outcome =
if (isMetaOnly) Proceed
else if (collides(globalReal, projectReal)) ExitNonZero
else Proceed
// ここから下は、このルールを3つのケースで確かめるテスト
// --help はパスが衝突していても続行する
run metaOnlyAlwaysProceedsTest =

}

-- sig は「登場するもの」の宣言。Path はパスを表す
sig Path {}
-- 起動の結果は「続行」か「エラー終了」のどちらか
abstract sig Outcome {}
one sig Proceed, ExitNonZero extends Outcome {}
-- takt の起動1回。3つの値を持つ
sig Invocation {
globalReal: one Path, -- グローバル設定のパス（解決後）
projectReal: one Path, -- プロジェクト設定のパス（解決後）
outcome: one Outcome -- その起動がどうなったか
}
-- 起動のうち --help / --version だったもの
sig MetaOnly in Invocation {}
-- fact はいつでも成り立つルール。ここがガード本体
-- エラー終了するのは「--help / --version ではない」かつ「パスが一致」のとき
-- それ以外でエラー終了することはない。iff はこの両方をまとめて言う
fact Guard {
all i: Invocation |
i.outcome = ExitNonZero iff
(i not in MetaOnly and i.globalReal = i.projectReal)
}
-- assert は上のルールから当然こうなるはず、という主張
-- 検証器はこれが破れる例（反例）を探す
-- --help / --version は必ず続行する
assert MetaAlwaysProceeds { all i: MetaOnly | i.outcome = Proceed }
-- パスが違えば必ず続行する
assert DistinctPathsProceed {
all i: Invocation | i.globalReal != i.projectReal implies i.outcome = Proceed
}
-- 登場するものが4個までの組み合わせを全部試して反例を探せ、という指示
check MetaAlwaysProceeds for 4
check DistinctPathsProceed for 4

Webアプリケーションセキュリティの定番『徳丸本』が8年ぶりに改訂するという。2026年7月に開催された「Hack Fes. 2026」で、第3版の改訂ポイントを著者・徳丸浩氏が解説した。

Webアプリケーションの開発やセキュリティに携わるITエンジニア必携の書と言ってもいい『徳丸本』こと、『体系的に学ぶ 安全なWebアプリケーションの作り方』は、2011年に初版が発行され、2018年には、Web API関連を中心に200ページ近く記述が加わった「第2版」が刊行された。
しかし、Web技術の進化と複雑化に伴い、新たなリスクや脆弱（ぜいじゃく）性が浮上している。こうした背景から2026年現在、「第3版」への改訂に向けた執筆が進められているという。
2026年7月に一般社団法人日本ハッカー協会が開催した「Hack Fes. 2026」に、筆者である徳丸浩氏が登壇。「徳丸本アップデート2026」と題して講演・ワークショップを実施した。同氏は第2版以降の大きな変化を「個人情報漏えいから事業被害へのシフト」と捉えており、その最新動向と第3版の改訂ポイントを2部に分けて解説した。
もともとWebアプリケーション開発者向けに書かれた徳丸本だが、脆弱性診断に携わる診断員にとっても「必携の書」となっている。そんな同書が初版から貫いてきた方針の一つは、手を動かしながら勉強できること。
もう一つは「実務に即したバランスの良い記述を心掛けていること」（徳丸氏）だ。「セキュリティのためなら会社が潰れてもいい」といった極端な主張ではなく、事業を守るためのセキュリティという点を重視して書かれてきた。
Webを取り巻く技術の進化は速く、Webブラウザに搭載される機能も増えている。それに伴って脅威も変化し、対応が求められる基準やガイドラインも更新されてきた。
第3版では、そうした新たな状況に対応した記述を追加するとともに、構成も見直し、実用性の高い項目から順に紹介する方針とした。「クロスオリジンリソースシェアリング」（CORS）を理解するには「クロスサイトリクエストフォージェリ」（CSRF）の知識が前提になるといった具合に、順序立てての理解が必要なものについては、その通りに読み進められるように整理しているという。
構成面での大きなポイントは、脆弱性やWebセキュリティに関する基礎知識、主要な脆弱性に続いて、丸々一章を割いて「セキュリティ要件」を記述していることだ。「第2版まであまり書いてこなかったセキュリティ要件とは何か、どう組み立てるかといった事柄をしっかり入れようとしています」（徳丸氏）
そして「ブラウザセキュリティと技術的な基礎」として同一オリジンポリシーやCORS、CSP（Content Security Policy）、TLS（Transport Layer Security）、DNS（Domain Name System）、さらに文字コードに関する説明をまとめる他、前半の章で触れられなかったレースコンディション（TOCTOU脆弱性）やHTTPリクエストスマグリング（HRS）といった高度な脆弱性に言及するという。一方で、クリックジャッキングやOSコマンドインジェクションといった、時間がたちながらも現役の脆弱性については、9章で「古典的（レガシー）な脆弱性」としてまとめていく。
8章では「セキュア開発プロセス」について言及し、CI/CD（継続的インテグレーション／継続的デリバリー）環境を前提としたツールやリスク分析のフレームワークなどを解説する他、昨今話題となっているソフトウェアサプライチェーンの問題にも触れていく。
徳丸本の特徴である実習環境もアップデートされる。Docker Composeベースの実習環境を用意し、従来利用してきたPHPの他、Node.jsやLaravelなど、現在の開発環境に即したフレームワークを題材に取り、「OWASP ZAP」に代えてWebアプリケーションセキュリティツール「Burp Suite」を用いた実習環境を用意していく。
また「『OWASP ASVS』（OWASP Application Security Verification Standard）がだいぶこなれてきたこともあり、『ASVS 5.0』や『NIST SP 800-63 Rev.4』といった最新のグローバルスタンダードに合わせています」（徳丸氏）という。
講演では、徳丸本第3版で網羅するトピックの中から、レースコンディション、HTTPリクエストスマグリング（HRS）、JWTによるセッション管理とそれに対する攻撃の3つについて、深掘りした説明が行われた。
レースコンディション（競合状態）は昔から存在する問題で、徳丸本でも初版から言及されていた。「他人の個人情報が見えてしまう、あるいはECサイトに在庫が1つしかないのに2人以上に販売できてしまう、というのが典型例で、割とよく見つかっていた問題です」（徳丸氏）
では、なぜ第3版でこのトピックを取り上げる予定なのか。
背景にあるのが、厚生労働省をはじめ複数省庁のWebサイトでレースコンディションに起因するセキュリティ問題が顕在化したことだ。デジタル庁の「政府情報システムにおける脆弱性診断ガイドライン」においても、Webアプリケーションの実装に起因する脆弱性の冒頭に「レースコンディションによるデータの不整合」という項目が挙げられている。
「『脆弱性診断員の友』としての徳丸本を考えますと、レースコンディションもしっかり書いておこうという考えです」（徳丸氏）
レースコンディションに起因する問題は幾つかあるが、中でも厄介なのが「TOCTOU（Time-of-check to time-of-use）競合」だ。
if文を用いた「もし在庫が1以上あれば、在庫を減らして注文を記録する」といった処理はWebアプリケーションでよく見掛ける実装だ。だが、if文でのチェックからthenで記述された処理を実行するまでの間にはわずかなギャップがある。「この時間的ギャップを狙った事象がTOCTOU競合です」（徳丸氏）
TOCTOU競合が発生すると、重要な同一ファイルが上書きされて他人の情報が見えてしまったり、前述のようにデータベースでは在庫が1つしかないのに複数人に販売してしまったりする事態が生じてしまう。
徳丸本第3版では、Burp Suiteを用いてTOCTOU競合の動きを確認できる実習環境が用意されており、「『もしも在庫があったら購入できる』という実に自然なif・then文の処理によって、TOCTOU競合が起きることを再現できる」（徳丸氏）と、講演ではデモも披露された。
「原因は、SELECT文による確認と、UPDATEによる操作が不可分（アトミック）ではなく、別々に実行されていることにあります。違和感があるかもしれませんが、いきなりUPDATEする、もしくは行ロックをかけて排他制御をすることが重要です」（徳丸氏）
このような対策を済ませれば適切な結果が返ってくることも、実習環境で確認できるという。
次に言及した「HRS」は、Burp Suiteを用いた脆弱性診断で時折検出される問題だという。端的に言えば、2つ以上のリクエストを、1つに見えるような形で細工して送信することで、リバースプロキシなどによるリクエストの検査をかいくぐる手法だ。
HRSを理解するためには「HTTP/1.1」の仕様を知る必要がある。HTTPリクエストにおいて、コンテンツ本体の「ボディーの長さ」を伝える手段には、長さを直接指定する「Content-Length」（CL）と、データを「チャンク」単位で分割送信する「Transfer-Encoding」（TE）の2種類が存在する。
RFCにおいては「両方が記述されている場合はTransfer-Encodingが優先される」と明記されている。しかし徳丸氏によると、仕様に反してContent-Lengthを優先してしまう実装が存在するという。
この解釈の不一致がHRSを引き起こす。実務的には、フロントエンドがCLで解釈し、バックエンドがTEで解釈する「CL-TE」のパターンが圧倒的に多いという。
Nginxをリバースプロキシに用いた場合、TEを優先するだけでなく転送時に不要なCLヘッダを削除するため、構造上HRSは起こり得ない。一方で、判定やヘッダの扱いが緩いリバースプロキシを挟んでいる場合に、HRSが発生することになる。
徳丸氏は「根本対策は『脆弱性のない（仕様に準拠し、適切にヘッダを処理する）リバースプロキシを使う』というだけですので、診断時にHRSというキーワードが出てきたらこのことを思い出してください」と述べた。
続けて徳丸氏が言及したのが「JWT」（JSON Webトークン）だ。
JWTは、OpenID ConnectでIDトークンを用いるための形式だ。扱いやすいことから、セッション管理に広く用いられるようになったが、「有効期間中は即時取り消しができないという欠点もあるため、結論としてはあまりお勧めできません」と徳丸氏は述べた。
辞書攻撃や「alg=none」攻撃、アルゴリズム交換攻撃といった「非常に素朴な、基本的な攻撃」（徳丸氏）が存在しており、徳丸本第3版では、HRSと同様に実習環境で試しながら学ぶことができるという。

MCPの新ロードマップ公開、今後はAIエージェント対応、HTTP通信への統一、アイデンティティ、よりよいデベロッパー体験などに注力
Linux Foundation傘下でMCP（Model Context Protocol）の仕様策定を行っている「Agentic AI Foundation（AAIF）」は、今後のMCPの進化について、その方向性を示す新たなロードマップを発表しました。
MCPはAIツールとサービスを接続するための事実上の業界標準となっている通信プロトコルです。
もともと2024年11月にAnthropicが自社のAIサービスであるClaudeと外部のデータソースを接続するために提唱したプロトコルです。2025年12月にLinux Foundationに移管され、オープンな業界標準としてアップデートされてきました。
今年（2026年）7月にはエンタープライズ向けにアクセスを一括管理できる「Enterprise-Managed Authorization（EMA）extension」が安定版となり、またステートレスな接続になったことで容易にスケールできる大型のアップデートが行われました。
- MCPにエンタープライズ向け新機能、アクセスを一括管理できる「Enterprise-Managed Authorization（EMA）extension」が安定版として利用可能に
- MCP仕様が明日アップデート、7月28日版MCPからはステートレスな接続が正式仕様に。GitHub MCPサーバが早くも対応発表
5つの優先事項を発表
今回発表されたのは、今後のMCPの進化に関するロードマップです。5つの優先分野が示されています。
それぞれの概要を紹介しましょう。
Agentic messaging primitives
（AIエージェント向けのメッセージング）
MCPの登場当初、AIの主な使い方はチャットで質問し、その答えが返ってくるというものでした。しかしその後のAIがエージェントへと進化したことで、AIがバックグラウンドで長時間タスクを処理し続けることが増えてきました。
こうした状況に対応するため、サーバがストリーミングで結果をプッシュできたり、クライアントがポーリングすることなくサーバ発のイベントを取得できたりするように、サーバー主導イベント（server-initiated events）の実現、AgentsワークグループとTransportsワークグループとTriggers＆Eventsワークグループが協力してメッセージング構成を見直すことなどを進めていくとしています。
HTTP-native transport unification and hardening
（トランスポートをHTTPネイティブに統一へ）
MCP はもともとWebSocket、stdio、ローカル接続などの複数の通信方式が混在していましたが、最新の2026-07-28仕様でリモートMCPサーバーもHTTP経由で接続できるようになりました。
今後この方向性を推し進め、MCPの通信方式を完全にHTTP ベースに統一し強化していくとしています。
Agent identity and enterprise-ready security
（AIエージェントのアイデンティティとエンタープライズ向けセキュリティ）
現在のMCP認証は、ブラウザ上で人間が承認することを前提に構築されています。
しかし今後はAIエージェントが独自のアイデンティティを持ち、ユーザーの代理として処理を行い、サブエージェントに権限の一部を委譲して処理を任せることが期待されています。
今後は人間による承認に依存せずに安全に権限を管理できるように、エンタープライズ環境で本番運用できるAIエージェントのアイデンティティ管理をMCPに組み込もうとしています。
具体的には、AIエージェントが必要な権限だけを安全に取得するための 標準的なトークン交換プロトコルの実装および監査、権限分離などの仕組みなどを実装するとしています。
Improved primitives
（基本ツールの改善）
MCPにおけるツールの呼び出しやツールの発見の際の複雑さを軽減し、より一貫性があり、扱いやすい形式にする。
例えばツールの発見では段階的に、例えばまずカテゴリを示し、カテゴリを選択すると関連ツールの一覧を表示する、などの分かりやすい仕組みを取り入れる。
Improved SDK developer experience
（SDKでの開発者体験の改善）
MCPのクライアントやサーバを実装するためのSDKは多くの人間だけでなく多くのAIも使い始めている。そうなるとAPIが直感的であること、ドキュメントが正確であることがより重要となる。そのため、さらに使いやすく、仕様に忠実なものへ改善するように取り組む。

2025年にはMetaの最高データ責任者であるアレックス・シュルツ氏や製品責任者のナオミ・グライト氏を含む幹部らがアジアを訪問し、スタートアップがAI中心で組織を構築していることに感銘を受けたそうです。幹部らはAIスタートアップの組織構造に関する独自の調査を依頼し、「AIネイティブ」の可能性を判断するためのパイロットプロジェクトを立ち上げたと、社内の事情に詳しい関係者がロイターに語っています。
そしてザッカーバーグ氏や一部の側近らは2026年1月、ハワイにある別荘で合宿を行い、MetaをよりAIネイティブにする「Project OT」を練り上げました。ロイターが入手した内部文書や関係者によると、Project OTは数千人以上の従業員が行っている仕事をAIに引き継ぎ、多くの社内チームの規模を最大60％削減するシナリオも検討されていたとのこと。

DuckDBはシングルバイナリの高速なOLAPデータベース
DuckDBは、従来のクライアント／サーバ型の複雑なOLAPデータベースサーバとは異なり、SQLiteのようにシングルバイナリあるいはアプリケーションに容易に組み込んでローカルマシン上で非常に高速にデータ分析が実行できるOLAPデータベースソフトウェアです。
単一ファイルとして扱える独自フォーマットのデータベースファイルに加えて、CSV、Parquet、JSON形式などのファイルの読み書きに対応し、また拡張機能によってMySQLやPostgreSQL、SQLiteデータベースの読み書きも可能です。
この秋に登場予定のDuckDB 2.0では手元のDuckDBからリモートマシンで実行中のDuckDBインスタンスに接続して操作できるクライアント／サーバ型にも対応するなど、大型のアップデートが行われる予定であり、注目度が非常に高まっています。
参考：シングルバイナリなOLAP DBの次期版「DuckDB 2.0」プレビュー。クライアント／サーバ機能が安定版に、スキーマレスのVARIANT型、トリガー、非同期I/Oなど新機能
DuckDBは引き続きMITラインセスのオープンソースを維持
DuckDBおよび関連プロジェクトであるDuckLakeは、現在は独立した非営利団体であるDuckDB Foundationの下でMITラインセンスのオープンソースとして開発が進められています。
DuckLabsがAWSの子会社になった後も、ライセンスや開発体制、ガバナンス体制、ロードマップなども含めて引き続き維持されると説明されています。
AWSはなぜDuckLabsを買収するのか？
AWSはなぜDuckLabsを買収するのでしょうか？ それはAWSが顧客のデータを預けるためのクラウドとして優れたポジションを維持し続けるためだと考えられます。
AWSは以前から、顧客のデータを預ける優れたクラウドとしての優位性を築くことに積極的なベンダでした。顧客が大規模なデータをクラウドに保存すればするほど、顧客はそのクラウドから別のサービスに移行することが難しくなるためです。
そのためにAWSは、大規模高信頼かつ安価なデータストアであるAmazon S3を中心に、データ分析サービスとしてAmazon Redshift、Amazon S3のデータを直接分析できるAmazon S3 Tables、さまざまなデータを容易に分析可能にするゼロETL統合戦略などを展開しています。
一方で、DuckDBは手軽かつ高速なOLAPデータベースであり、代表的なユースケースの1つとしてAmazon S3などのクラウド上に保存された大規模なCSVやParquetファイルを読み込んで高速に分析することが挙げられます。こうしたユースケースは従来のAWSのデータ戦略を補完するものです。
そのため今回の買収は、このDuckDBの特徴やユースケースがAWSのデータベース戦略を強化するピースとして大きな将来性を持つと評価して行われたものと考えられます。
と同時にこの将来有望なDuckDBがAWSのデータベース戦略のライバル、例えばSnowflakeやDatabricksやGoogle BigQueryを提供するGoogle Cloudなどと接近したり子会社化される前に、自社陣営にしておきたかったという事情もあるでしょう。
DuckDBは今後、おそらくAWSからの積極的な支援と資金提供によって今後さらに機能強化のペースが早まると同時に、AWSの各種サービスとの統合を容易にするような機能も追加されていくのではないかと思われます。

LINEヤフーでは、ユーザーの目的に応じてさまざまなサービスや機能をつなぐAIエージェントサービス「Agent i」の開発を進めています。
Agent iで多様なニーズに応えるには、現場のアイデアを素早くAIエージェントとして形にできることに加え、作られたエージェントを安全かつ安定的に本番環境で動かせることが必要です。
そこで私たちは、エンジニアでなくてもノーコードでワークフローを構築できる「Agent Builder」と、公開されたワークフローをサービスの負荷に応じて実行する「Agent Runtime」を内製化しました。
本記事では、当初目指していたマルチエージェント構想から、なぜ「まずエージェントを作れる基盤が必要だ」という結論に至ったのか、そして作りやすさと本番運用の要件をどのような設計で両立したのかを紹介します。
AIエージェント領域への方針転換
私たちのチームはもともと別のAI領域で開発に取り組んでいました。そうした中、LLM (Large Language Model)の急速な進歩によって、AIエージェントを活用したサービス開発の可能性が大きく広がりました。より大きな事業成長を見込み、AIエージェント領域への新たなチャレンジをすることになりました。
方針を転換した時点では、具体的に何を作り、どのように進めるかまでは決まっていませんでした。最初に取り組んだのはAIエージェントの普及によって生じる課題の整理です。
当初はAIエージェントが今後急速に増え、エージェント同士の連携が課題になると考えていました。その見立てから「マルチエージェント」を軸に据え、エージェント間連携を最初に解くべきテーマとして検討を進めました。
エージェントを増やせない理由
検討を進めるとマルチエージェントの前に解くべき課題が見えてきました。エージェント同士を連携させる以前に、一つひとつのエージェントを作ること自体が、まだ難しかったのです。
一つのエージェントを作るにはコードを書く必要があり、担い手がエンジニアに限られていました。加えて、処理の分岐や実行経路も把握しにくいため、設計の見通しが立ちにくくなります。作った後も、デプロイして動かすまでには手間がかかります。
エージェントを量産し、試行錯誤を高速に繰り返せる状態には至っていません。連携させるエージェントそのものを増やせなければ、マルチエージェントの活用も広がりません。
こうした状況を踏まえ、エージェント同士の連携はその先に取り組むものだと判断しました。先に作るべきだったのは、エージェントそのものを手軽に作ってすぐに試せる環境だったのです。
アイデアをエージェントとして形にするツール
私たちが目指したのは、AIエージェント開発に関われる人の幅を広げることです。現場で生まれたアイデアを自分たちですぐ試せれば、エンドユーザーに近い場所で検証と改善を重ねられます。この考えから、エンジニアだけでなく、ユーザーや事業に近い企画職や営業職も自らアイデアを形にできる環境を作ることにしました。
アイデアを試すたびにコードによる実装が必要になると、試行錯誤の速度を上げにくくなります。そのため、利用者自身がエージェントを構築できるノーコードのツールを目指しました。
そのうえで、使いやすさを優先するため、ツールが扱うユースケースを絞りました。複雑な制御や高度なカスタマイズは、引き続きエンジニアが担う設計としています。アイデアをまずは小さく動かせる形にし、汎用的な処理はほかのケースにも再利用しやすい設計を目指しました。
利用者の範囲とあわせて、このツールでどのようなエージェントを構築できるようにするかも検討しました。単一のエージェントにすべてを任せるのではなく、人が複数の処理を組み合わせて設計するワークフロー方式を採用しました。
利用者自身が処理の実行順序や条件を確認し、動作を制御しながら改善を重ねられることも大きな利点です。
この方式を実現するにあたり、類似サービスを参考に開発基盤に必要な要件を整理しました。その中で重視したのが、社内データへ安全に接続できることと、自社サービスの要件に合わせて継続的に拡張できることです。既存ツールをそのまま利用するだけでは両立が難しいと判断し、設計から実行までを自社で制御できるノーコードの開発基盤を内製化する方針としました。
エージェント開発基盤の仕組み
開発基盤は、エージェント開発ツールのAgent Builderと、エージェント実行基盤のAgent Runtimeで構成されています。
Agent Builderでは、社内の利用者がワークフローを定義します。Agent Runtimeでは、定義されたワークフローを読み込み、処理量に応じてスケールしながら実行します。
Agent Builderの仕組み
Agent Builderでは、ノードとエッジを配置・接続し、ワークフローをノーコードで組み立てられるグラフ形式の編集画面を提供しています。LLMの処理や分岐、繰り返しを画面上で組み合わせ、テストから公開・デプロイまでを一貫して進められます。
編集画面にはReact Flowを採用し、ノードの配置や接続に加えて処理ごとの表示・設定画面も柔軟に組み込んでいます。
作成したワークフローから、後述する独自の中間表現（IR: Intermediate Representation）を生成し、構造や設定を検証したうえで保存します。検証では、到達可能性や接続関係をグラフ理論に基づいて確認します。問題があれば公開前に利用者へフィードバックし、構造上の不整合による実行時エラーを未然に防ぎます。さらに、Agent Builderでは、高度なLLM機能を画面上の操作に落とし込み、専門的な仕様を意識せず使えるようにしています。
リリース後は利用者からさまざまな改善要望が寄せられましたが、そのまますべてを機能に加えるわけではありません。幅広い利用者にとって意味がわかりやすく、誤った設定が起きにくいかを見極め、専門知識が必要な機能はユーザーインターフェースだけで設定できる形に落とし込んでいます。例えば、VerbosityやReasoning EffortといったLLMのAPIパラメータのうち、効果を理解しやすい項目は見つけやすい場所に配置し、モデル選択とあわせて処理ごとに調整できます。一方、Structured Outputsでは、画面上で設定した出力項目からJSON Schemaを自動生成し、専門的な記述なしで利用できるよう工夫しました。
Agent Runtimeの仕組み
Agent Runtimeには、公開されたワークフローをサービスの負荷に応じて安定して実行できるようにする役割があります。そのため、Kubernetes上でスケールし、高負荷時の安定性とリソース効率の両立を目指した構成です。
設計を実行へつなぐIR
ワークフローの設計時と実行時のデータ表現の違いは、共通モデルとなるIRで吸収します。Agent Runtimeは実行リクエストを受けると、Agent Builderで生成・検証されたIRを読み込み、LangGraphの実行グラフへ変換・コンパイルして実行します。LangGraphは条件分岐や繰り返し、ノード間の状態管理に対応しており、IRを実行グラフへ落とし込みやすいことから採用しました。
実行環境を分離するサンドボックス設計
また、Agent Runtimeの特徴の一つはKubernetes Namespaceを実行環境ごとに分離し、論理的なサンドボックスとして扱う構成です。
各環境では、ネットワークACL (Access Control List)で通信先を絞り、MCP (Model Context Protocol) Serverやドキュメント、内部APIなどへのアクセス可否も実行時に検証します。また、認証情報やAPIキーはワークフロー定義に含めず、必要なタイミングで取得し、社内データや外部サービスへ接続します。
さらに、Namespaceの分離によって、負荷も実行環境ごとに局所化できます。特定のワークフロー群にアクセスが集中しても影響をほかの環境へ広げにくくし、必要な範囲だけレプリカ数やリソース量を調整できます。これにより、負荷への耐性と平常時のコスト効率の両立を図っています。

こうした構成を整える過程では、ファーストリリースに向けたQA (Quality Assurance)で安定性に関する課題が次々と見つかり、想定する最大負荷に耐えられるよう負荷試験を繰り返しました。検証を進める中で、CPUとメモリを見直した後、同時実行数に対応するためレプリカ数を増やすと、今度はネットワーク帯域がボトルネックになりました。この経験から、実行基盤全体を継続的に監視し、ボトルネックに応じてリソースをすぐに調整できる仕組みが必要だとわかりました。
問題の原因を特定するため、メトリクスの確認と仮説検証を短いサイクルで繰り返し、再現条件を絞り込みました。また、短期間で検証サイクルを回すため、検証用スタブの作成からログやコードの調査、原因分析、修正案とテスト観点の洗い出しまでをコーディングエージェントに任せました。設計・検証の方針と最終確認は人が担い、コーディングエージェントとの分担で原因特定から修正・再検証までを一気に進められたのは良い経験でした。

Small Models Have Arrived
For the past few weeks, I've been playing with gpt-5.6-luna. It is shockingly capable, fast, and smart. I regularly see it do ~100 tps, and rip around my codebase, email, and knowledge base.
Of course, the biggest thing with luna is the cost. I've tried running some fairly complicated research threads, and it's pretty tough to run up a large bill. Even having it search across thousands of emails, I end up with an API cost in the tens of cents.
With GLM 5.3, we even have a new option at the Pareto frontier.
When doing coding work, I almost always reach for the most expensive and capable models (Fable 5, 5.6 Sol). So it's been easy to miss the progress the small fast models have made.
One thing a few investors I've talked with have mentioned: "It's weird we're not seeing more consumer AI companies. Why is that?"
There's a straightforward answer: token costs.
In the times before AI, the playbook for big consumer apps looked like this...
- create some sort of compelling website which is fairly cheap to run
- attract a bunch of users (typically with some virality)
- raise money, scale to more users
- create an ads marketplace
This roughly describes most of the big consumer companies (Google, Facebook, Snapchat, etc.).1
But what if you want to add AI to your product? Well, now you have some real inference costs on every request! Suddenly the amount of capital required increases dramatically.
A pet eval of mine is to build a daily news site, personalized to me:
research @calvinfo on the internet. figure out what news they might like. build a micro-site with today's top stories, personalized for them. search hn, reddit, twitter, etc.
With the previous generation of models (Sonnet class), you'd spend ~$1 to get anywhere. Charging $30/mo is untenable for a consumer app. There's obviously a lot we can optimize here, but if you're charging what the WSJ or The Economist charges, you'd better be delivering similar value.
But looking at luna, the results are pretty decent, and the average cost is ~$0.10. Now we're talking!
Where I think this gets even more interesting is in the world of business.
My Segment co-founder Peter and I were recently comparing notes on a hike. Across his various startups, Peter has seen two kinds of work:
- the "IQ 180" work. some mad scientist genius type comes up with some crazy solution you've never thought of.
- the "token spewer" work. being ultra responsive, pushing the ball forward across dozens of different fronts.
Peter runs multiple companies. Beyond Segment, he's raised $100m+ for Charm Industrial, and just recently closed a Series A for Revoy. He's incredibly organized and efficient with his time.
And yet, Peter mentioned that ~95% of the work he does falls into bucket 2. It's hopping on calls. Nudging people. Blocking and tackling.
To be clear, Peter says his companies would be dead-in-the-water today without an IQ 180 technical mind solving the deep problems. Just that most of his work falls in bucket 2.2
I think demand for "frontier-level" models is going to keep compounding. Especially for fields that require novel breakthroughs or discovery (engineering, hard science, model training).
But I also think the demand for "fast/cheap/good-enough" models is just about to take off.
Think of the people you interact with on a daily basis: coworkers, vendors, and customers. Nine times out of ten, you want someone who is super responsive, and just handles things for you. Most of the "human tokens" at companies today are spent this way — hiring skews heavily toward the fast/cheap/good-enough archetype.
There's a lot of work that needs to happen to make fast/cheap/good-enough models a reality for business. New harnesses, prompt injection safety, roles, and permissions. But I'm confident we'll figure that out.
If you're also experimenting with making small models useful, please drop me a line.

私が開発している OSS の TAKT では、この揺れを実行前の対話で潰しています。
具体的には、アシスタントとタスクを詰めて合意した内容を、指示書にまとめてからエージェント群に渡すようにしています。
この指示書の受け入れ条件はこれまで Gherkin で書かせてきました。
v0.61.0 でここに形式仕様モードという設定を足しました。
有効にすると、指示書の要件を Quint と Alloy という記法でも表現するようになります。
形式手法は正しさが欲しい場面で昔から使われてきた道具です。
ただ実務で常用するには仕様を書いて維持するコストが高く、採用できないという結論になりがちの代物でした。
有効であることは間違いないが運用するのが重い。
そんな形式手法ですが、昨今は AI の時代です。
書く手間を AI が引き受けられるなら、実用可能ではないだろうか。
これが、この手法に取組むきっかけになったのです。
TAKT の形式仕様モードの仕組み
TAKT では TUI を開くとデフォルトで形式手法を利用するかを確認されます。
なお、この設定は config.yaml に assistant.formal_spec として設定もできます。
# ~/.takt/config.yaml（プロジェクトの .takt/config.yaml でも可）
assistant:
formal_spec: 'Y/n' # true / false / 'Y/n' / 'y/N'（既定は 'y/N'）
'Y/n' と 'y/N' は既定回答つきの質問で、対話セッションの最初に一度だけ「形式仕様モード（Alloy, Quint）を有効にしますか？」と聞かれます。
true と false は質問なしでそのまま使われます。
有効にしたときの記法の分担はこうなります。
Gherkin には観測可能な振る舞い、つまり外から見える挙動を Given/When/Then の具体的なシナリオで書きます（これは形式仕様モードと関係なく、開発タスクなら常時出力されます）。
ただしシナリオは代表例を挙げる書き方で、全ケースを網羅する保証はありません。
Quint が受け持つのは振る舞いの一般則です。
システムをステートマシンとして捉え、すべての入力と状態遷移に対する規則を書きます。
元になっているのは、AWS などが分散システムの設計検証に使ってきた TLA+ という言語で、その考え方をプログラマになじみやすい構文で書けるようにしてあります。
Alloy はデータ構造を受け持ちます。
何が登場してどう関係するかを定義して、常に成り立つべき制約を宣言します。
こちらは MIT で作られた、ソフトウェア設計をモデル化するための言語です。
どちらも本来は検証器とセットで使う道具ですが、TAKT では記法として使います（後述）。

というか読みたくない。

Given 設定パスが衝突している

| --version |

type Outcome = Proceed | ExitNonZero

pure def startupOutcome(isMetaOnly: bool, globalReal: str, projectReal: str): Outcome =
if (isMetaOnly) Proceed
else if (collides(globalReal, projectReal)) ExitNonZero
else Proceed

-- sig は「登場するもの」の宣言。Path はパスを表す
sig Path {}
-- 起動の結果は「続行」か「エラー終了」のどちらか
abstract sig Outcome {}
one sig Proceed, ExitNonZero extends Outcome {}
-- takt の起動1回。3つの値を持つ
sig Invocation {
globalReal: one Path, -- グローバル設定のパス（解決後）
projectReal: one Path, -- プロジェクト設定のパス（解決後）
outcome: one Outcome -- その起動がどうなったか
}
-- 起動のうち --help / --version だったもの
sig MetaOnly in Invocation {}
-- fact はいつでも成り立つルール。ここがガード本体
-- エラー終了するのは「--help / --version ではない」かつ「パスが一致」のとき
-- それ以外でエラー終了することはない。iff はこの両方をまとめて言う
fact Guard {
all i: Invocation |
i.outcome = ExitNonZero iff
(i not in MetaOnly and i.globalReal = i.projectReal)
}
-- assert は上のルールから当然こうなるはず、という主張
-- 検証器はこれが破れる例（反例）を探す
-- --help / --version は必ず続行する
assert MetaAlwaysProceeds { all i: MetaOnly | i.outcome = Proceed }
-- パスが違えば必ず続行する
assert DistinctPathsProceed {
all i: Invocation | i.globalReal != i.projectReal implies i.outcome = Proceed
}
-- 登場するものが4個までの組み合わせを全部試して反例を探せ、という指示
check MetaAlwaysProceeds for 4
check DistinctPathsProceed for 4

MCPの新ロードマップ公開、今後はAIエージェント対応、HTTP通信への統一、アイデンティティ、よりよいデベロッパー体験などに注力
Linux Foundation傘下でMCP（Model Context Protocol）の仕様策定を行っている「Agentic AI Foundation（AAIF）」は、今後のMCPの進化について、その方向性を示す新たなロードマップを発表しました。
MCPはAIツールとサービスを接続するための事実上の業界標準となっている通信プロトコルです。
もともと2024年11月にAnthropicが自社のAIサービスであるClaudeと外部のデータソースを接続するために提唱したプロトコルです。2025年12月にLinux Foundationに移管され、オープンな業界標準としてアップデートされてきました。
今年（2026年）7月にはエンタープライズ向けにアクセスを一括管理できる「Enterprise-Managed Authorization（EMA）extension」が安定版となり、またステートレスな接続になったことで容易にスケールできる大型のアップデートが行われました。
- MCPにエンタープライズ向け新機能、アクセスを一括管理できる「Enterprise-Managed Authorization（EMA）extension」が安定版として利用可能に
- MCP仕様が明日アップデート、7月28日版MCPからはステートレスな接続が正式仕様に。GitHub MCPサーバが早くも対応発表
5つの優先事項を発表
今回発表されたのは、今後のMCPの進化に関するロードマップです。5つの優先分野が示されています。
それぞれの概要を紹介しましょう。
Agentic messaging primitives
（AIエージェント向けのメッセージング）
MCPの登場当初、AIの主な使い方はチャットで質問し、その答えが返ってくるというものでした。しかしその後のAIがエージェントへと進化したことで、AIがバックグラウンドで長時間タスクを処理し続けることが増えてきました。
こうした状況に対応するため、サーバがストリーミングで結果をプッシュできたり、クライアントがポーリングすることなくサーバ発のイベントを取得できたりするように、サーバー主導イベント（server-initiated events）の実現、AgentsワークグループとTransportsワークグループとTriggers＆Eventsワークグループが協力してメッセージング構成を見直すことなどを進めていくとしています。
HTTP-native transport unification and hardening
（トランスポートをHTTPネイティブに統一へ）
MCP はもともとWebSocket、stdio、ローカル接続などの複数の通信方式が混在していましたが、最新の2026-07-28仕様でリモートMCPサーバーもHTTP経由で接続できるようになりました。
今後この方向性を推し進め、MCPの通信方式を完全にHTTP ベースに統一し強化していくとしています。
Agent identity and enterprise-ready security
（AIエージェントのアイデンティティとエンタープライズ向けセキュリティ）

LINEヤフーでは、ユーザーの目的に応じてさまざまなサービスや機能をつなぐAIエージェントサービス「Agent i」の開発を進めています。
Agent iで多様なニーズに応えるには、現場のアイデアを素早くAIエージェントとして形にできることに加え、作られたエージェントを安全かつ安定的に本番環境で動かせることが必要です。
そこで私たちは、エンジニアでなくてもノーコードでワークフローを構築できる「Agent Builder」と、公開されたワークフローをサービスの負荷に応じて実行する「Agent Runtime」を内製化しました。
本記事では、当初目指していたマルチエージェント構想から、なぜ「まずエージェントを作れる基盤が必要だ」という結論に至ったのか、そして作りやすさと本番運用の要件をどのような設計で両立したのかを紹介します。
AIエージェント領域への方針転換
私たちのチームはもともと別のAI領域で開発に取り組んでいました。そうした中、LLM (Large Language Model)の急速な進歩によって、AIエージェントを活用したサービス開発の可能性が大きく広がりました。より大きな事業成長を見込み、AIエージェント領域への新たなチャレンジをすることになりました。
方針を転換した時点では、具体的に何を作り、どのように進めるかまでは決まっていませんでした。最初に取り組んだのはAIエージェントの普及によって生じる課題の整理です。
当初はAIエージェントが今後急速に増え、エージェント同士の連携が課題になると考えていました。その見立てから「マルチエージェント」を軸に据え、エージェント間連携を最初に解くべきテーマとして検討を進めました。
エージェントを増やせない理由
検討を進めるとマルチエージェントの前に解くべき課題が見えてきました。エージェント同士を連携させる以前に、一つひとつのエージェントを作ること自体が、まだ難しかったのです。
一つのエージェントを作るにはコードを書く必要があり、担い手がエンジニアに限られていました。加えて、処理の分岐や実行経路も把握しにくいため、設計の見通しが立ちにくくなります。作った後も、デプロイして動かすまでには手間がかかります。
エージェントを量産し、試行錯誤を高速に繰り返せる状態には至っていません。連携させるエージェントそのものを増やせなければ、マルチエージェントの活用も広がりません。
こうした状況を踏まえ、エージェント同士の連携はその先に取り組むものだと判断しました。先に作るべきだったのは、エージェントそのものを手軽に作ってすぐに試せる環境だったのです。
アイデアをエージェントとして形にするツール
私たちが目指したのは、AIエージェント開発に関われる人の幅を広げることです。現場で生まれたアイデアを自分たちですぐ試せれば、エンドユーザーに近い場所で検証と改善を重ねられます。この考えから、エンジニアだけでなく、ユーザーや事業に近い企画職や営業職も自らアイデアを形にできる環境を作ることにしました。
アイデアを試すたびにコードによる実装が必要になると、試行錯誤の速度を上げにくくなります。そのため、利用者自身がエージェントを構築できるノーコードのツールを目指しました。
そのうえで、使いやすさを優先するため、ツールが扱うユースケースを絞りました。複雑な制御や高度なカスタマイズは、引き続きエンジニアが担う設計としています。アイデアをまずは小さく動かせる形にし、汎用的な処理はほかのケースにも再利用しやすい設計を目指しました。
利用者の範囲とあわせて、このツールでどのようなエージェントを構築できるようにするかも検討しました。単一のエージェントにすべてを任せるのではなく、人が複数の処理を組み合わせて設計するワークフロー方式を採用しました。
利用者自身が処理の実行順序や条件を確認し、動作を制御しながら改善を重ねられることも大きな利点です。
この方式を実現するにあたり、類似サービスを参考に開発基盤に必要な要件を整理しました。その中で重視したのが、社内データへ安全に接続できることと、自社サービスの要件に合わせて継続的に拡張できることです。既存ツールをそのまま利用するだけでは両立が難しいと判断し、設計から実行までを自社で制御できるノーコードの開発基盤を内製化する方針としました。
エージェント開発基盤の仕組み
開発基盤は、エージェント開発ツールのAgent Builderと、エージェント実行基盤のAgent Runtimeで構成されています。
Agent Builderでは、社内の利用者がワークフローを定義します。Agent Runtimeでは、定義されたワークフローを読み込み、処理量に応じてスケールしながら実行します。
Agent Builderの仕組み
Agent Builderでは、ノードとエッジを配置・接続し、ワークフローをノーコードで組み立てられるグラフ形式の編集画面を提供しています。LLMの処理や分岐、繰り返しを画面上で組み合わせ、テストから公開・デプロイまでを一貫して進められます。
編集画面にはReact Flowを採用し、ノードの配置や接続に加えて処理ごとの表示・設定画面も柔軟に組み込んでいます。
作成したワークフローから、後述する独自の中間表現（IR: Intermediate Representation）を生成し、構造や設定を検証したうえで保存します。検証では、到達可能性や接続関係をグラフ理論に基づいて確認します。問題があれば公開前に利用者へフィードバックし、構造上の不整合による実行時エラーを未然に防ぎます。さらに、Agent Builderでは、高度なLLM機能を画面上の操作に落とし込み、専門的な仕様を意識せず使えるようにしています。
リリース後は利用者からさまざまな改善要望が寄せられましたが、そのまますべてを機能に加えるわけではありません。幅広い利用者にとって意味がわかりやすく、誤った設定が起きにくいかを見極め、専門知識が必要な機能はユーザーインターフェースだけで設定できる形に落とし込んでいます。例えば、VerbosityやReasoning EffortといったLLMのAPIパラメータのうち、効果を理解しやすい項目は見つけやすい場所に配置し、モデル選択とあわせて処理ごとに調整できます。一方、Structured Outputsでは、画面上で設定した出力項目からJSON Schemaを自動生成し、専門的な記述なしで利用できるよう工夫しました。
Agent Runtimeの仕組み
Agent Runtimeには、公開されたワークフローをサービスの負荷に応じて安定して実行できるようにする役割があります。そのため、Kubernetes上でスケールし、高負荷時の安定性とリソース効率の両立を目指した構成です。
設計を実行へつなぐIR
ワークフローの設計時と実行時のデータ表現の違いは、共通モデルとなるIRで吸収します。Agent Runtimeは実行リクエストを受けると、Agent Builderで生成・検証されたIRを読み込み、LangGraphの実行グラフへ変換・コンパイルして実行します。LangGraphは条件分岐や繰り返し、ノード間の状態管理に対応しており、IRを実行グラフへ落とし込みやすいことから採用しました。
実行環境を分離するサンドボックス設計
また、Agent Runtimeの特徴の一つはKubernetes Namespaceを実行環境ごとに分離し、論理的なサンドボックスとして扱う構成です。
各環境では、ネットワークACL (Access Control List)で通信先を絞り、MCP (Model Context Protocol) Serverやドキュメント、内部APIなどへのアクセス可否も実行時に検証します。また、認証情報やAPIキーはワークフロー定義に含めず、必要なタイミングで取得し、社内データや外部サービスへ接続します。
さらに、Namespaceの分離によって、負荷も実行環境ごとに局所化できます。特定のワークフロー群にアクセスが集中しても影響をほかの環境へ広げにくくし、必要な範囲だけレプリカ数やリソース量を調整できます。これにより、負荷への耐性と平常時のコスト効率の両立を図っています。

How we saved 100 terabytes of memory by optimizing 1.1.1.1’s DNS cache
Big Pineapple, the platform behind 1.1.1.1, Gateway DNS, DNS Firewall, AS112, and several other Cloudflare DNS services, stores over 250 billion DNS cache entries at any given time. At that scale, wasting a single byte per entry costs more than 250 gigabytes of memory across our fleet.
Five successive changes to how cache entries are stored in memory cut the per-entry footprint by over 50%. Across our fleet, these changes freed up roughly 100 terabytes of memory, equivalent to the amount of RAM in 130 of our Gen 13 servers. The cache also got faster. Insert throughput rose 43% and lookup latency dropped 19%, as fewer allocations and better memory locality meant we did not trade speed for space.
What we cache
On cold start, Big Pineapple starts out with an empty cache. As DNS queries arrive, the cache fills until it hits its maximum entry count, at which point we evict older or less popular items to make room.
The exact cache size varies by data center. When EDNS Client Subnet (ECS) is in use, authoritative servers return different answers depending on the client's network, so we cache multiple versions of the same query. This increases both the number of entries and the memory each one consumes, making the optimizations in this post especially impactful for ECS-heavy locations.
Each item in the cache is a key-value pair. The key identifies what was queried:

qname: Name,
qtype: Rtype,
authenticated: bool,
tag: Vec<u8>,
}
The value stores the DNS response itself: the answer, authority, and additional record sections, along with metadata like the creation time, a hit counter, and the Time-to-Live (TTL).

timestamp: UnixTimeStamp,
pub inception: Instant,
pub ttl: Ttl,
pub hits: u32,

pub authority: Vec<Record>,

Both structs have room for improvement. Several fields use types that carry overhead we don't need once the entry is stored.
Benchmarking memory usage
To measure the impact of each change, we benchmark by filling the cache with randomly generated entries that roughly match the traffic distribution we see in production: 56% A records, 25% AAAA, and 19% TXT. Each entry contains between one and four records.
TXT records serve as a stand-in for all non-A/AAAA record types in the benchmark. Their size is randomized between 64 and 224 bytes, close to the average response size we see for variable-length record types.
We track memory usage using a custom allocator that wraps Rust’s System allocator and records the number and size of allocations per cache entry. Alongside memory, we measure insert throughput and lookup latency across the full cache flow to make sure memory savings don’t come at the cost of performance.
These inputs approximate production rather than reproduce it exactly. Process memory also depends on traffic mix, cache occupancy, allocator state, and memory used outside the cache. We therefore measured resident memory across production instances during the rollout.
The cost of capacity
Vec<T> stores three fields: a pointer to heap-allocated data, the current length, and the total capacity. When you push an item, Vec checks whether the length exceeds the capacity and reallocates if needed. If there’s room, it just appends the item and increments the length.
Once we store a DNS response in the cache, however, we never modify it again. The capacity field serves no purpose, but still costs 8 bytes per Vec. The over-allocated heap space is wasted as well, as a Vec with capacity for eight items but only five stored leaves three slots unused on the heap.
Using Box<[T]> solves both problems. It can’t grow after creation, so it doesn’t need a capacity field or reserve space for future elements. The same applies to String, which also carries a capacity field. Box<str> drops it.
Each cache entry stores 8 Vec and String fields. Replacing them with Box<[T]> and Box<str> saves 8 bytes per field, 64 bytes per entry. It also eliminates the excess heap memory that Vec reserves for future growth. The combined savings add up to over 15 terabytes with over 250 billion cache entries.
Fewer lists, fewer pointers
Rather than storing the answer, authority, and additional sections in separate lists, we can store a single list with offsets to the start of each section. Since DNS record counts per section fit in a u16, we can use a u16 (2 bytes) for each offset, compared to the 8-byte pointer and 8-byte length that each separate Box<[T]> requires.

Terraform で利用可能なローカル AWS エミュレータ
ローカル AWS エミュレータは、AWS の API と同じレスポンスを手元のプロセスで返すことで、実アカウントなしに SDK・CLI・Terraform を動かせるようにするツールです。
2026年7月現在、Terraform から使える主なエミュレータは以下の3つです。

- API カバレッジは完全ではない：全 API・全パラメータが実装されているわけではない。サービス一覧では Bedrock Runtime がスタブ実装（ストリーミングは 501 を返す）と明記されている。使いたいサービスの必要な操作が対応しているかは、事前に確認する必要がある。
-
IAM の認可は既定で評価されない：IAM のドキュメントは「By default Floci accepts any credentials without enforcing IAM policies」と述べており、test /test のような固定値で何でも通る。ただしFLOCI_SERVICES_IAM_ENFORCEMENT_ENABLED を有効にすると、リクエストごとに呼び出し元のポリシーが評価され、許可がなければ 403 のAccessDeniedException が返る。
-
ECS の secrets は解決されない：タスク定義のsecrets （valueFrom ）で指定した環境変数はコンテナに注入されない。通常のenvironment は注入される。公式ドキュメントに記載はなく、Case 5 で確認した挙動である。
- ネットワーク制御は再現されない：EC2 のドキュメントはセキュリティグループについて「not enforced as a firewall (Docker bridge networking handles routing)」と述べている。ルートテーブルや NACL も同様に、リソースとして保存されるだけで通信の可否を決めない。
- 料金・クォータ・レイテンシは対象外：課金額やサービスクォータ、実 AWS のネットワーク遅延といった非機能面は再現されない。
-
サービスを選んで起動できない：LocalStack からの移行ガイドによれば、SERVICES 環境変数による絞り込みはなく、全サービスが起動する。
エミュレータが再現するのは、あくまで API のレスポンス（コントロールプレーン）です。
実際にパケットを流したり権限を評価したりする挙動（データプレーン）は、再現されないか、部分的な再現にとどまります。
一方で、RDS や ElastiCache などのステートフルなサービスを、モックではなく実際の Docker コンテナ（PostgreSQL や MySQL など）で動かします。このためデータベースについては、本物のエンジンに対して SQL を流して挙動を確かめられます。

Webアプリケーションの開発やセキュリティに携わるITエンジニア必携の書と言ってもいい『徳丸本』こと、『体系的に学ぶ 安全なWebアプリケーションの作り方』は、2011年に初版が発行され、2018年には、Web API関連を中心に200ページ近く記述が加わった「第2版」が刊行された。
しかし、Web技術の進化と複雑化に伴い、新たなリスクや脆弱（ぜいじゃく）性が浮上している。こうした背景から2026年現在、「第3版」への改訂に向けた執筆が進められているという。
2026年7月に一般社団法人日本ハッカー協会が開催した「Hack Fes. 2026」に、筆者である徳丸浩氏が登壇。「徳丸本アップデート2026」と題して講演・ワークショップを実施した。同氏は第2版以降の大きな変化を「個人情報漏えいから事業被害へのシフト」と捉えており、その最新動向と第3版の改訂ポイントを2部に分けて解説した。
もともとWebアプリケーション開発者向けに書かれた徳丸本だが、脆弱性診断に携わる診断員にとっても「必携の書」となっている。そんな同書が初版から貫いてきた方針の一つは、手を動かしながら勉強できること。
もう一つは「実務に即したバランスの良い記述を心掛けていること」（徳丸氏）だ。「セキュリティのためなら会社が潰れてもいい」といった極端な主張ではなく、事業を守るためのセキュリティという点を重視して書かれてきた。
Webを取り巻く技術の進化は速く、Webブラウザに搭載される機能も増えている。それに伴って脅威も変化し、対応が求められる基準やガイドラインも更新されてきた。
第3版では、そうした新たな状況に対応した記述を追加するとともに、構成も見直し、実用性の高い項目から順に紹介する方針とした。「クロスオリジンリソースシェアリング」（CORS）を理解するには「クロスサイトリクエストフォージェリ」（CSRF）の知識が前提になるといった具合に、順序立てての理解が必要なものについては、その通りに読み進められるように整理しているという。
構成面での大きなポイントは、脆弱性やWebセキュリティに関する基礎知識、主要な脆弱性に続いて、丸々一章を割いて「セキュリティ要件」を記述していることだ。「第2版まであまり書いてこなかったセキュリティ要件とは何か、どう組み立てるかといった事柄をしっかり入れようとしています」（徳丸氏）
そして「ブラウザセキュリティと技術的な基礎」として同一オリジンポリシーやCORS、CSP（Content Security Policy）、TLS（Transport Layer Security）、DNS（Domain Name System）、さらに文字コードに関する説明をまとめる他、前半の章で触れられなかったレースコンディション（TOCTOU脆弱性）やHTTPリクエストスマグリング（HRS）といった高度な脆弱性に言及するという。一方で、クリックジャッキングやOSコマンドインジェクションといった、時間がたちながらも現役の脆弱性については、9章で「古典的（レガシー）な脆弱性」としてまとめていく。
8章では「セキュア開発プロセス」について言及し、CI/CD（継続的インテグレーション／継続的デリバリー）環境を前提としたツールやリスク分析のフレームワークなどを解説する他、昨今話題となっているソフトウェアサプライチェーンの問題にも触れていく。
徳丸本の特徴である実習環境もアップデートされる。Docker Composeベースの実習環境を用意し、従来利用してきたPHPの他、Node.jsやLaravelなど、現在の開発環境に即したフレームワークを題材に取り、「OWASP ZAP」に代えてWebアプリケーションセキュリティツール「Burp Suite」を用いた実習環境を用意していく。
また「『OWASP ASVS』（OWASP Application Security Verification Standard）がだいぶこなれてきたこともあり、『ASVS 5.0』や『NIST SP 800-63 Rev.4』といった最新のグローバルスタンダードに合わせています」（徳丸氏）という。
講演では、徳丸本第3版で網羅するトピックの中から、レースコンディション、HTTPリクエストスマグリング（HRS）、JWTによるセッション管理とそれに対する攻撃の3つについて、深掘りした説明が行われた。
レースコンディション（競合状態）は昔から存在する問題で、徳丸本でも初版から言及されていた。「他人の個人情報が見えてしまう、あるいはECサイトに在庫が1つしかないのに2人以上に販売できてしまう、というのが典型例で、割とよく見つかっていた問題です」（徳丸氏）
では、なぜ第3版でこのトピックを取り上げる予定なのか。
背景にあるのが、厚生労働省をはじめ複数省庁のWebサイトでレースコンディションに起因するセキュリティ問題が顕在化したことだ。デジタル庁の「政府情報システムにおける脆弱性診断ガイドライン」においても、Webアプリケーションの実装に起因する脆弱性の冒頭に「レースコンディションによるデータの不整合」という項目が挙げられている。
「『脆弱性診断員の友』としての徳丸本を考えますと、レースコンディションもしっかり書いておこうという考えです」（徳丸氏）
レースコンディションに起因する問題は幾つかあるが、中でも厄介なのが「TOCTOU（Time-of-check to time-of-use）競合」だ。
if文を用いた「もし在庫が1以上あれば、在庫を減らして注文を記録する」といった処理はWebアプリケーションでよく見掛ける実装だ。だが、if文でのチェックからthenで記述された処理を実行するまでの間にはわずかなギャップがある。「この時間的ギャップを狙った事象がTOCTOU競合です」（徳丸氏）
TOCTOU競合が発生すると、重要な同一ファイルが上書きされて他人の情報が見えてしまったり、前述のようにデータベースでは在庫が1つしかないのに複数人に販売してしまったりする事態が生じてしまう。
徳丸本第3版では、Burp Suiteを用いてTOCTOU競合の動きを確認できる実習環境が用意されており、「『もしも在庫があったら購入できる』という実に自然なif・then文の処理によって、TOCTOU競合が起きることを再現できる」（徳丸氏）と、講演ではデモも披露された。
「原因は、SELECT文による確認と、UPDATEによる操作が不可分（アトミック）ではなく、別々に実行されていることにあります。違和感があるかもしれませんが、いきなりUPDATEする、もしくは行ロックをかけて排他制御をすることが重要です」（徳丸氏）
このような対策を済ませれば適切な結果が返ってくることも、実習環境で確認できるという。
次に言及した「HRS」は、Burp Suiteを用いた脆弱性診断で時折検出される問題だという。端的に言えば、2つ以上のリクエストを、1つに見えるような形で細工して送信することで、リバースプロキシなどによるリクエストの検査をかいくぐる手法だ。
HRSを理解するためには「HTTP/1.1」の仕様を知る必要がある。HTTPリクエストにおいて、コンテンツ本体の「ボディーの長さ」を伝える手段には、長さを直接指定する「Content-Length」（CL）と、データを「チャンク」単位で分割送信する「Transfer-Encoding」（TE）の2種類が存在する。
RFCにおいては「両方が記述されている場合はTransfer-Encodingが優先される」と明記されている。しかし徳丸氏によると、仕様に反してContent-Lengthを優先してしまう実装が存在するという。
この解釈の不一致がHRSを引き起こす。実務的には、フロントエンドがCLで解釈し、バックエンドがTEで解釈する「CL-TE」のパターンが圧倒的に多いという。
Nginxをリバースプロキシに用いた場合、TEを優先するだけでなく転送時に不要なCLヘッダを削除するため、構造上HRSは起こり得ない。一方で、判定やヘッダの扱いが緩いリバースプロキシを挟んでいる場合に、HRSが発生することになる。
徳丸氏は「根本対策は『脆弱性のない（仕様に準拠し、適切にヘッダを処理する）リバースプロキシを使う』というだけですので、診断時にHRSというキーワードが出てきたらこのことを思い出してください」と述べた。
続けて徳丸氏が言及したのが「JWT」（JSON Webトークン）だ。
JWTは、OpenID ConnectでIDトークンを用いるための形式だ。扱いやすいことから、セッション管理に広く用いられるようになったが、「有効期間中は即時取り消しができないという欠点もあるため、結論としてはあまりお勧めできません」と徳丸氏は述べた。
辞書攻撃や「alg=none」攻撃、アルゴリズム交換攻撃といった「非常に素朴な、基本的な攻撃」（徳丸氏）が存在しており、徳丸本第3版では、HRSと同様に実習環境で試しながら学ぶことができるという。

米CNETの検証では、マップの広告は一部の検索結果の横にのみ表示された。また、「Googleマップ」で見られるようなスポンサー付きのピンは、今のところ確認できなかった。ニューヨーク市やサンフランシスコのような人口の多い地域でも、検索結果に毎回広告が出るわけではなかった。そのため、少なくとも導入当初は、デザインが大きく変わったと感じないユーザーもいるだろう。

私自身は、この時期から「AI推進CoE」という考え方の発信を始めました。2019年後半、金融機関を中心にお話ししていた内容です。ツールを配ることではなく、AIを組織にどう定着させるかという実行方法のほうに答えがある、という主張でした。
つまり、「AIの民主化」は約8年前に自分たちで打ち出し、その1年半後には自分たちで軌道修正した言葉です。そして私は、そこから7年近くCoEの話をし続けてきました。それを踏まえた上で、いま改めて申し上げたいことがあります。
「AIの民主化」というスローガンは、そろそろ本当に終わりにしたほうがいいと考えています。
生成AIとAIエージェントの登場で、「AIの民主化」「誰もが自分のエージェントを作る時代」という言説がまた盛り上がっています。言葉としては前回とほぼ同じです。ただ、AutoML時代の民主化が成立していた前提条件と、いまのAIエージェントの特性を並べて比べてみると、成立条件が明確に壊れていることがわかります。
この記事では、私が対外的に話している内容をそのまま文章にしておこうと思います。AutoML時代とエージェント時代の「算数の違い」、そして動画プラットフォームの歴史を補助線に、これからのAI組織論について考えていることを共有します。
先に断っておくと、本記事の結論は7年前と同じ「CoE」です。単語としては目新しくありません。ただ、なぜ民主化を閉じるべきかの理由も、CoEに求められる中身も、当時とはまったく別物になっています。そこが本題です。
1. AutoML時代の「民主化」が成立していた前提
批判から入る前に、なぜ当時の機械学習（AutoML）では民主化が一定の合理性を持っていたのかを整理しておきます。感情ではなく前提条件の話なので、ここは冷静に振り返る必要があります。
前提1：生産性の差が「1対5」程度だった
AutoMLを装備した市民データサイエンティストの生産性を「1」、専門家の生産性を「5」と仮定します。ここが重要なところで、素手の非専門家の話ではありません。AutoMLというツールが差をかなり圧縮してくれた上での「1」です。
この比率であれば、算数が成り立ちます。現場に10人分のライセンスを配れば、トータルのアウトプットは 1×10＝10。専門家2人分（5×2＝10）と並びます。20人に配れば専門家4人分です。専門家を2人採用するより、現場の20人にツールを配るほうが速いし安い、という判断は当時それなりに合理的でした。
前提2：リスクの低い領域から広げる、という設計だった
もうひとつ、当時の民主化とセットで語っていたのが「どの領域から広げるか」でした。
いきなり与信審査や品質保証の最終判定を市民データサイエンティストに作らせる、という話ではありません。リード優先順位づけのような、外しても業務が即座に壊れない領域から広げていく。専門家が作れば90〜100点のところ、70点のモデルでも十分に価値が出る、という割り切りが成立したのは、そもそも70点で許される領域を選んでいたからです。
（以下、本記事で使う点数は「他人に業務で使わせられる水準を100点」とした私の体感値です。統一の物差しとして読んでください。）
リードのスコアリング精度が数ポイント落ちても、それまで担当者の勘と経験だけで決めていた優先順位が数字ベースになるなら、価値は出ます。外れたところで、営業が架電する順番が少し変わるだけです。逆に言えば、リスクの高い領域には最初から民主化を持ち込んでいませんでした。
「多少精度が落ちても、リスクの低いところで数の力でカバーできる」。この算数が成り立っていたからこそ、ツールを広く配る民主化には意味があったわけです。逆に言えば、この2つの前提が崩れたら民主化は成立しません。
余談：それでもAutoMLは「Excel」にはならなかった
当時、社内やお客様先でよく話していたのは、「AutoMLはExcelにはならない」ということでした。
Excelは事実上、全社員が使えます。ただ、AutoMLで意味のあるモデルを作ろうと思ったら、データの持ち方を理解していて、リーケージに気づけて、AUCやLogloss、RMSEが何を言っているかがわかる必要がある。この時点でだいぶ人を選びます。
感覚的には、どれだけうまく広げてもExcel VBAが書ける層くらいまでが受け取り手側のスキルの限界だろう、という話をしていました。そして実際、おおむねその通りになりました。「誰でも」と言いながら、AutoMLの民主化にも最初から天井があったわけです。この話は、あとの章にそのまま効いてきます。
2. AIエージェント時代の算数：1対100〜1000の世界
そして、いまのAIエージェントでは、この前提がどちらも崩れています。
AIエージェントは、プロンプトを少し書けば誰でも「30点のもの」を一瞬で作れます。動くプロトタイプがその日のうちにできる。これが「誰でも作れる＝民主化だ」という感覚を生みます。
なぜ非専門家の点数が70点から30点に落ちるのか
ここで、「1章は70点なのに、こっちは30点？ タイポか？」と思われた方がいるかもしれません。タイポではありません。私の体感として、エージェントで非専門家が70点を出すのは難しいです。
では、なぜ同じ「素人が作ったもの」なのに、点数が半分以下になるのか。
理由はシンプルで、ツールが肩代わりしてくれる範囲が違うからです。
AutoMLは、専門家と非専門家の差そのものをツール側が埋める設計でした。アルゴリズムの選択も、特徴量生成も、ハイパーパラメータの調整も、精度検証の作法も、押せば全部やってくれる。だから素人がボタンを押しても70点のモデルが出てきたわけです。1章で「1」をAutoMLを装備した市民データサイエンティストと定義したのは、まさにこの意味でした。
一方、エージェント開発で下がったのは入口の敷居だけです。プロンプトを書けば何かが動く、そこまでは一瞬でたどり着けます。しかし、そこから先の例外処理も、評価設計も、権限管理も、コスト設計も、ツールは肩代わりしてくれません。入口が広がっただけで、入口から実務水準までの距離は、むしろAutoML時代より伸びています。
もちろん、腰を据えて教育し続ければ70点に到達する人は出てきます。そこは否定しません。ただ、それでも算数は好転しないのです。理由は3つあります。
- 合格ラインが上がっている：AutoML時代は70点で合格でしたが、他人に業務で使わせるエージェントは80点以上ないと使えません。70点まで来ても、まだ届かない。
- 初期値が下がっている：70点スタートと30点スタートでは、埋めるべき差が倍以上違います。
- 埋めるコストが桁違い：しかもその差を埋める中身が、ソフトウェア工学の広い知識です。ツールの操作研修とデータサイエンス基礎知識のような単一科目だけでは埋まりません。
かつては「合格ラインが70点で、非専門家が最初から70点を出せた」から民主化が成立していました。いまは、合格ラインが上がり、初期値が下がり、その差を埋めるコストが跳ね上がっている。三重に悪化しています。
具体的に、何が足りないのか
「自分の手元で動かす30点」と「他人に業務で使わせる実用レベル（80点以上）」の間にあるギャップを、具体的に並べてみます。
- 例外処理とハルシネーションの制御
- 既存システム・APIとの堅牢な連携
- セキュリティ、権限管理、データ漏洩対策
- 評価基盤の設計（そもそも「良くなった」をどう測るのか）
- 運用保守と、エラー時のフォールバック設計
- トークンコストの設計
最後のトークンコストは、AutoML時代にはあまり存在しなかった軸です。手元で10回動かす分にはフラッグシップモデルを富豪的に使えばいい。しかし全社の業務で毎日回すとなると、そのままではコストが見合いません。
そうなると「安いモデルに寄せる」という話になりますが、ここで問題が一段複雑になります。安いモデルに落とした上で、ハルシネーションや指示追従の品質を落とさずに運用できるのか。モデルを落としても壊れないようにコンテキストとワークフローを設計し直せるのか。 「動くか」ではなく「いくらで、どの品質で、動き続けるか」 という問いに答える必要があり、これはプロトタイプを作った人が最も想像しにくい部分でもあります。
効くのはドメイン知識よりソフトウェア工学の知識
このリストを見ていただくとわかる通り、どれもプロンプトの上手さとは別の領域の話です。例外処理、疎結合、テスト、可観測性、コスト設計。要するに、ソフトウェア工学の広大な知識を持っている人が圧倒的に強いという結論になります。
ここがAutoML時代との決定的な違いです。AutoMLは、ドメイン知識を持っている人に装備させたときのシナジーが非常に大きいツールでした。業務を知っている人が自分でモデルを回せることに、はっきりした意味があった。
一方でエージェントは、ドメイン知識よりもソフトウェアの知識のほうが効きます。しかもその知識がないまま作ると、単に品質が低いものができるのではなく、リスクのあるものができてしまう。この非対称性が、「現場に作らせる」という発想の前提を壊しています。
余談：30点で構わない領域も、ちゃんとある
念のため補足しておくと、30点のものに価値がない、という話ではまったくありません。 自己責任の範囲 なら、30点で十分です。
メールの英文化、自分用の議事録の要約、企画を詰めるときの壁打ち相手。この手の使い方に合格ラインはありません。おかしければ自分で気づいて、自分で捨てられるからです。10回投げて3回使えれば得。むしろ30点のものをどんどん作って、どんどん捨てるのが正しい使い方だと思っています。ここは大いに民主化すべきですし、実際そうなりつつあります。
ただ、お気づきの通り、これらは生成AIの利用であって、エージェントではありません。人が毎回結果を見て、人が使うかどうかを決めている。
点数が問題になるのは、他人に使わせた瞬間からです。自分で捨てられなくなり
