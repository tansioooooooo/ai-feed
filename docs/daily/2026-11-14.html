TLDR; Every core smart device in my house does not depend on a vendor’s server. If the internet goes down, everything works (downgraded experience perhaps). It has been my rule for 10 years and it has been challenging to follow. I’ve given two talks about it. Check out each slide by slide.
Why local
My Nest integration worked one day until it didn’t. They had changed the api (around the same time Google acquired them). I have a few more examples in these talks that show a samsung fridge and a grill controller that needs wifi to show temperature. I don’t/shouldn’t need wifi and/or vendor service to interact with hardware.
So everything that matters runs on hardware I own. Mostly on Tasmota on esp8266/esp32 boards, MQTT broker, and Node-RED on a Raspberry Pi. I do use some cloud services for enhancements like Alexa and a few AWS ones BUT those are secondary. If the internet is down, the switches all work like normal.
The rules
From the first talk:
- No internet, no problem. Core stuff has to work with the internet unplugged.
- Don’t remove the old way while adding the new one.
- Be agile.
- Check your automations.
- Exceptions must be exceptional.
Added after year five, once more people lived in the house:
- A cloud device needs an API with logs or it doesn’t get installed. I don’t want a black box in the house.
- Configuration lives in one place instead of five vendor apps.
- More than one way to do something. An app, Alexa, a QR code, or an NFC tag.
- If I keep doing the same steps, it becomes routine (node red or on the tasmota device itself).
- Devices talk pub/sub over MQTT instead of point to point.
- No batteries unless they last a year or more between changes.
I get asked about the the Tasmota sprinkler controller the most as well as the garage door setup. Both have been running for years with no real changes.

Introducing AlphaProof Code: a breakthrough in verifying complex software at depth
How Google DeepMind researchers built a new agentic framework that formally verified the code of Signal’s cryptographic protocol — long considered to be a grand security challenge
Today, we’re sharing a milestone in software security long considered to be a grand challenge: Google DeepMind researchers guided AI agents to mathematically prove key security properties of the actual code underlying the Signal protocol, the technology that protects billions of private conversations in apps like Signal and Google Messages.
This breakthrough discovery was made using AlphaProof Code, a novel agentic framework for formal verification at unprecedented depth that combines human expertise with AI agents. Formal verification—mathematically proving code runs correctly without flaws—is the highest standard of security assurance; however, it is difficult and often labor-intensive.
Our work marks the first time AI has been used to formally verify a widely deployed cryptographic protocol at this depth. It's also the first time the implementation of a widely deployed protocol like this has been formally verified by any method, with or without AI.
How we verified Signal
AlphaProof Code is a multi-LLM agentic framework that splits the work of formal verification the way a research team would: human experts work with AI to decide what to prove, and a group of AI agents does it.
First, our researchers collaborated with a mix of models to translate Signal’s security goals into formal mathematical specifications, with human experts reviewing every one. From there, agents powered by Gemini Carbon did the proofs, generating over six million lines of Lean, a computer language that mathematically proves the accuracy of code.
Next, the agents audited the proof and highlighted areas that needed a second look by a human – just one percent of the codebase, a massive time savings. Because Lean automatically checks the rest, our experts could focus their review where human judgment matters most.
Cryptographic protocols underpin nearly all digital communication, from online banking to web browsing, and a single flaw can expose millions of people at once. That's why experts have spent decades formally analyzing them.
But most protocol verification stops at the design level. Our agents went further, proving that the compiled code fulfills the key security properties – such as keeping messages protected before and after a device is temporarily compromised – down to the exact code running on devices. Because real-world vulnerabilities often hide in the gap between design and implementation, bridging this gap makes these proofs vastly more complex.
Even at this complexity, our verification process took just four weeks – a task that historically takes expert teams years – proving that Signal's core cryptographic code delivers the security protections our experts specified.
To confirm that AlphaProof Code can tell correct code from buggy code, we reintroduced two real, previously fixed bugs into an isolated version of Signal's code. In both cases, the system produced a machine-checked proof that the buggy version was insecure.
While prior formal verification work has necessarily focused on smaller scopes, this new approach enables a significant expansion. Traditionally, verifying that production code strictly matches its cryptographic design required extensive manual effort, making the use of AI agents to automatically translate live code into valid Lean theorems a great breakthrough. As AI-driven security threats grow, having the core Signal protocol rigorously verified with automated theorem proving gives us even greater confidence that our code delivers on its privacy guarantees.
The future of security
Achieving this long-standing challenge demonstrates how AI can bring elite security assurance to businesses, governments, and critical infrastructure, helping defend against agent-driven cyber threats.
Verifying Signal's core cryptography lays the groundwork to secure other vital systems, from medical device firmware to power grid software.
Scaling these techniques requires continued research. Paired with automated defense agents like CodeMender, formal verification can help counter the speed and scale of modern cyber threats to create software with mathematical proof that its protections work.

LLM を使った検索というと RAG を思い浮かべる方が多いと思いますが、まずそれ以前に文脈詰込み (context stuffing) という手法があります。本書では検索に特化したものとして全文プロンプトと呼んでいます。RAG は検索で引っかかった文章をプロンプトに入れて質問に答えさせますが、全文プロンプトはすべての文書をプロンプトに詰め込んで質問に答えさせます。
2～3 年前は LLM の文脈長が 512 や 1024 などが主流だったので RAG が有効でしたが、最近は文脈長が 100 万トークンあるモデルも珍しくありません。日本国憲法全文（全百三条）は GPT-5 のトークナイザーだと 8334 トークンなので、その程度であれば余裕で全文詰め込めますし、社内のマニュアルをすべて詰めても 100 万トークンに入りきるというのはあり得る話です。そのような時代背景をふまえながら、どのような場合に RAG が適切で、どのような場合に全文プロンプトが適切かを詳しく議論しています。
ここですべてをお話すると肝心の本を買ってもらえなくなるのであまり深入りはしませんが、大まかにいうと RAG と全文プロンプトは適合率 (precision) と再現率 (recall) のような関係にあります。全文プロンプトは再現率が高く、情報の拾い逃しが少ないと言えますが、文脈が多いとこじつけ的に間違った情報を出力する可能性が増えます。逆に RAG は拾い逃す可能性がありますが、拾えたときには事実に基づいて回答しやすくなります。また、もちろん使う LLM の基礎能力にもより、基礎能力が弱いとたとえ文脈長が足りても全文プロンプトをうまく処理しきれません。

Amazon, YouTube, X, Netflix などの巨大テック企業の成功は推薦システムなしで語ることはできません。当初は不満の声が多かった X のおすすめ欄ですが、今では確実に浸透して X の利用時間を増やしていますし、YouTube でも推薦がなければ動画を見ている時間ははるかに少なかったはずです。自分からキーワードを入力して動画を見つけにいかなければいけないようなサービスだったら、気づいたら 2 時間 YouTube を見ていた、なんていう体験は起こらなかったでしょう。

The Home Repo Pattern
One repo for your skills, AGENTS.md and shared docs, with pointers to your other repos. A reference, with a setup prompt you can copy.
On this page
A Home Repo is one repository that holds your skills, your AGENTS.md and your shared docs. You run your agent in the Home Repo. Its AGENTS.md holds a navigation pointer to each of your other repos, so the agent can open or clone them as it needs to.
The problem it solves
When a project spans several repos, an agent started in one of them sees only that repo. Each repo ends up with its own copy of the skills and the agent setup, and planning a feature that crosses repos means working without the whole overview.
A Home Repo gives you:
- One place for your steering files and tooling
- One place to run all your agents
- Sweeping changes across multiple repos from a single session
Set one up
Paste this prompt into a new session with your coding agent, started in the folder that holds your repos. The agent finds your repos and their skills itself, grills you about the decisions in rounds, and changes nothing until you approve its plan.

FAQ
Contents
What goes in a Home Repo? Skills you use across repos, AGENTS.md with its pointers, steering files, and shared docs such as coding standards, a glossary, and decisions that affect the whole system. Coding standards are the first doc worth sharing: one universal set transfers across projects. A Home Repo can also hold a small wiki of Markdown files, and tooling.
What stays in each repo? Anything true of that repo alone: its own AGENTS.md, its build and test commands, its repo-specific docs. The Home Repo points at it. Code stays where it is, and each repo keeps its history, remote and issue tracker.
Why a repo, and not ~/.claude/skills?
The ideal end state is that everyone uses the same skills, kept in the project. A user folder is the stopgap until then. A Home Repo is a project: its skills are versioned with git, and a team can share it.

データセンターの排熱でエビ養殖、NTT系が実験 育ったら食べられる？ 担当者に聞いてみた
NTTドコモビジネスなど4社は11月13日、データセンターの排熱を活用してエビを養殖する実証実験を発表した。2026年度中に養殖に適した排熱の回収方法を模索し、2027年度には回収した熱を使ってクルマエビ科の一種「バナメイエビ」を育てる計画だ。なぜエビの養殖を選んだのか、育てたエビはどうするのか。担当者に話を聞いた。
実証では、データセンターの冷却設備から排熱を回収し、エビの飼育水を温める。26年度は排熱の温度や熱量などを調べ、養殖に適した回収方法を検証。27年度には実際にエビを飼育し、排熱による水温維持や加温エネルギーの削減効果、データセンターの運用への影響などを調べる。
同実験は東京都の「スタートアップによる未利用熱活用促進事業」に採択されたもので、4社が参加する。NTTドコモビジネスは都内近郊の自社データセンターを実証場所として提供し、設備への影響を評価。IMTエンジニアリング（静岡県磐田市）は養殖システムの設計と飼育の運営、日比谷総合設備（東京都港区）は排熱回収・熱供給設備の設計・施工、NTTグリーン&フード（東京都千代田区）は飼育環境の監視と事業性の評価を担う。
背景には、データセンターの排熱と陸上養殖が抱える課題がある。生成AIの普及などでデータセンターの電力消費が増える一方、排熱は比較的低温のため、活用先が限られていた。一方、陸上養殖では飼育水の温度を一定に保つためのエネルギーが負担になっている。4社は排熱を養殖に利用することで、双方の課題解決を目指す。
なぜバナメイエビ？ 担当者に聞いた
バナメイエビは、成長すると体長15～20cmほどになるクルマエビ科の食用エビ。東南アジアなどで盛んに養殖されており、日本でもエビチリや炒め物などに使われている。
NTTドコモビジネスの担当者に選定理由を聞いたところ、「バナメイエビは陸上養殖の研究が進んでおり、16～18週間という非常に短い期間で育成できる技術が確立している」という。短期間での育成が可能なことから、養殖対象に選んだと答えた。
育てたエビの用途については「実証終了後に出荷可能な状態であれば、出荷を検討する」と担当者。ただし、出荷先や具体的なスケジュールは決まっておらず、「できればそういった状態に持っていけると良いなと考えている段階」という。
実証期間は28年3月まで。4社は実証結果を踏まえ、他のデータセンターにも展開できる事業モデルの確立を目指す。

劇場版アニメ「楽園追放 -Expelled from Paradise-」の続編「楽園追放 心のレゾナンス」。前作が公開された2014年11月から約12年、続編が11月13日に公開された。水島精二監督、脚本の虚淵玄さん、キャラクターデザインの齋藤将嗣さん、音楽のNARASAKIさんら豪華スタッフが再集結した。人類が肉体や地球を捨て、電脳世界ディーヴァで暮らすようになった西暦2400年を舞台とした作品で、骨太なSF、フル3DCGのハイクオリティーな映像が話題になり、ヒットを記録した。約12年ぶりの続編ということもあり、大きな期待が高まるが、水島監督はいかに作品に向き合ったのだろうか。制作の裏側を聞いた。
あなたにオススメ
「LOST10」「波うららかに、めおと日和」……「VIVANT」だけじゃない！ 話題作いっぱいの秋ドラマ特集
「楽園追放 -Expelled from Paradise-」は、ヒットが期待されていた作品というわけではなかった。公開された2014年、日本のアニメ業界は、手描きが主流で、フル3DCGアニメは受け入れられているとは言えなかった。3DCGでありながら手描きのような質感と表現を目指したセルルックという表現で制作され、3DCGならではのダイナミックなアクションと、手描きのようなキャラクターを両立させたことが話題になった。人類が肉体を捨て、AIとシステムによって完璧に管理された電脳世界ディーヴァで暮らしているという設定は、近年の仮想現実やAIの急激な発展を予見していたようにも見える。わずか13館の上映という静かなスタートだったが、11万人以上を動員し、ブルーレイディスク＆DVDは7万本以上の売り上げを記録した。
ヒットした作品ということもあって、早い段階から続編の企画は進行していた。
「前作の制作時、ラストでアンジェラとディンゴがトレーラーの中で笑っているカットを作った際、野口（光一）プロデューサーから『続編を匂わせているように見えるから外してほしい』と言われたんです。しかし、『アンジェラが最終的に楽園を追放された、あるいは捨てた状態で地上で生きていく、ディンゴと一緒になるかどうかは別としても、彼女がその覚悟を持っているシーンなのだから映画として絶対に必要だ』と主張し、残すことになりました。最初から続編を想定したわけではないのですが、『続編を』という企画自体はすぐに持ち上がりました。前作がきれいに終わっていたため、続編で一体何をやればいいのか、という根本的な疑問から始まりました。私としては『やるのであれば、虚淵さんに脚本を書いてもらうことが絶対条件』と伝えていました」
「Fate/Zero」「魔法少女まどか☆マギカ」などでも知られる虚淵さんは“超”が付くほどの人気脚本家、小説家だ。続編は、水島監督、虚淵さんありきで進められていた。
「虚淵さんとは個人的にも交流があるので意向を聞いたのですが、彼からも『続編って何をやればいいんですか』と返されてしまって。『だよね』と納得しつつも、『作りたい』という意志自体はずっと受け止めていました。そのため、野口さんとも数年に一度会っては『どうですかね』といったやり取りが長く続いていました。企画が具体的に動いたのは約6年前です。ある時、虚淵さんがひらめいて『これならいけるかも』というアイデアが出てきて、一同で集まって『とりあえず一度進めてみよう』とスタートを切ることになりました。それまでの間は、いつ動くか先が見えず、仕事の予定としてもあてにできない状態でした」
「水島精二×虚淵玄」の名タッグが再び動き出した。
「『なるほどね』と腑（ふ）に落ちました。打ち合わせを経て変化した部分は当然ありますが、芯の部分は現在の形とほぼ変わりません。前作は実験的な要素が多く、実質的にはOVA規模の予算でした。今回は、東映が全国配給する映画としてしっかりと予算も確保されています。その条件のもと、12年たった今、我々が何をやるべきか。虚淵さんのアイデアには、前作では表現できなかった要素もしっかりと盛り込まれていました。映像にするには、難度の高い要素ばかりでしたが、『これを形にしていくのはワクワクするな』とも感じました。虚淵さんは『水島さんだったら、シナリオを読み込んで真面目に取り扱ってくれると思ったので』と最初からあてにされていまして（笑）。信頼の裏返しとはいえプレッシャーを感じながら取り組みました」
虚淵さんから委ねられた水島監督は、試行錯誤を繰り返した。
「虚淵さんのシナリオはあまり書きすぎない。クリエーターに委ねる部分が大きいんです。任せてもらえるのであれば最大限に応えたいですし、そのためのアイデアをこちらで考えなければなりません。ただ、私自身はとっぴなアイデアを次々と生み出すタイプではなく、過去に触れてきた映像の蓄積やお客さんの目線を大切にして作っていくタイプです。お客さんも何だか分からないものをいきなり見せられても面食らってしまいますから、パッと見て判断していただけるラインを意識しています。今回で言えば、リビルダー（スライムのような正体不明の物体）の開発を一緒に担当してくれたクリエーターの多家正樹さんらと密にキャッチボールを重ね、このカット数で一番面白くできる表現を突き詰めていきました。シークエンスの構成としては、カットの連続性をあえて断ち、形状を厳密につなぎ続ける無理な設計を避けています。形状の変化が激しいリビルダーだからこそ、カットの合間にカットを挟むなど演出的な工夫を凝らすことで、異様さをコントロールしながら表現できるようにしました。長回しで見せるカットと、短く刻むカットを計算して配置しつつ、編集のリズムやテンポを意識してカット運びを構築していきました。アニメーターが面白い動きを取り込んでくれたら、臨機応変にリズムを変えて再構築しています」
前作は、フル3DCGアニメのヒットは難しいというそれまでの常識を覆した。それから約12年、日本国内のフル3DCGアニメが増え、受け入れられるようになった。
「12年前は、3Dで劇場版アニメを一本丸々制作すること自体が大きな挑戦でした。当時、ポリゴン・ピクチュアズが制作したテレビシリーズ『シドニアの騎士』の抑制の利いたセルルック表現に強い刺激を受け、我々は映画なのだから、さらにその先をいかなければならないと考えていました。当時グラフィニカにいらした板野一郎さんの指導のもと、絵コンテをものすごく膨らませてくれたこともあり、高いクオリティーに到達できました。では、この12年でエポックメーキングな技術革新があったかというと、実はそうではありません。セルルックにこだわり、アニメーターの手作業でモデルを変形させて表情やニュアンスを作る手法自体は、過去と大きく変わっていないのです。ツールは進化しているものの、求められるハードルも上がっているため、作業の大変さは変わりません。3D制作はレンダリングに膨大な時間がかかります。予期せぬエラーが出ればやり直すしかなく、作画のように、直前まで粘って手直しするのが難しい。煙や爆発といったエフェクトも、3Dで作画のように成立させるのは非常に難しく、3Dだから実現できた表現が数多くある一方で、時間の面などでも非常に厳しい戦いがありました」
新作では、3DCGで背景美術を表現するという挑戦もあった。
「野口プロデューサーがCG畑の出身ということもあり、『アニメーションではなぜか背景を3Dでやらないことが多いが、今回は背景も3Dで構築したい』という提案がありました。当初は『全編3D背景で』という勢いだったのですが、コストを考慮すると現実的ではないため、いくつかのシーンを選定して行う形に落ち着きました。その際、私から『今後の3Dアニメーション制作の指標となるデータを取るためにも、屋内の狭い場所ではなく、あえて空間的に広いところで挑戦しなければ意味がないだろう』と提案し、広大な縦穴の空間などを選んだのですが、結果としてそれが自分たちの首を絞めることになりました。リビルダーが食い荒らしてできた穴の特殊性をどう表現するか悩んでいた際、美術設定を担当してくれたスタッフから『ビスマスはどうでしょうか』というアイデアが出ました」
ビスマスは、階段状の幾何学的な結晶、玉虫色に輝く虹色の表面が美しい。大きな見どころになっているが、苦難の連続だった。

Introducing AlphaProof Code: a breakthrough in verifying complex software at depth
How Google DeepMind researchers built a new agentic framework that formally verified the code of Signal’s cryptographic protocol — long considered to be a grand security challenge
Today, we’re sharing a milestone in software security long considered to be a grand challenge: Google DeepMind researchers guided AI agents to mathematically prove key security properties of the actual code underlying the Signal protocol, the technology that protects billions of private conversations in apps like Signal and Google Messages.
This breakthrough discovery was made using AlphaProof Code, a novel agentic framework for formal verification at unprecedented depth that combines human expertise with AI agents. Formal verification—mathematically proving code runs correctly without flaws—is the highest standard of security assurance; however, it is difficult and often labor-intensive.
Our work marks the first time AI has been used to formally verify a widely deployed cryptographic protocol at this depth. It's also the first time the implementation of a widely deployed protocol like this has been formally verified by any method, with or without AI.
How we verified Signal
AlphaProof Code is a multi-LLM agentic framework that splits the work of formal verification the way a research team would: human experts work with AI to decide what to prove, and a group of AI agents does it.
First, our researchers collaborated with a mix of models to translate Signal’s security goals into formal mathematical specifications, with human experts reviewing every one. From there, agents powered by Gemini Carbon did the proofs, generating over six million lines of Lean, a computer language that mathematically proves the accuracy of code.
Next, the agents audited the proof and highlighted areas that needed a second look by a human – just one percent of the codebase, a massive time savings. Because Lean automatically checks the rest, our experts could focus their review where human judgment matters most.
Cryptographic protocols underpin nearly all digital communication, from online banking to web browsing, and a single flaw can expose millions of people at once. That's why experts have spent decades formally analyzing them.
But most protocol verification stops at the design level. Our agents went further, proving that the compiled code fulfills the key security properties – such as keeping messages protected before and after a device is temporarily compromised – down to the exact code running on devices. Because real-world vulnerabilities often hide in the gap between design and implementation, bridging this gap makes these proofs vastly more complex.
Even at this complexity, our verification process took just four weeks – a task that historically takes expert teams years – proving that Signal's core cryptographic code delivers the security protections our experts specified.
To confirm that AlphaProof Code can tell correct code from buggy code, we reintroduced two real, previously fixed bugs into an isolated version of Signal's code. In both cases, the system produced a machine-checked proof that the buggy version was insecure.
While prior formal verification work has necessarily focused on smaller scopes, this new approach enables a significant expansion. Traditionally, verifying that production code strictly matches its cryptographic design required extensive manual effort, making the use of AI agents to automatically translate live code into valid Lean theorems a great breakthrough. As AI-driven security threats grow, having the core Signal protocol rigorously verified with automated theorem proving gives us even greater confidence that our code delivers on its privacy guarantees.
The future of security
Achieving this long-standing challenge demonstrates how AI can bring elite security assurance to businesses, governments, and critical infrastructure, helping defend against agent-driven cyber threats.
Verifying Signal's core cryptography lays the groundwork to secure other vital systems, from medical device firmware to power grid software.
Scaling these techniques requires continued research. Paired with automated defense agents like CodeMender, formal verification can help counter the speed and scale of modern cyber threats to create software with mathematical proof that its protections work.

これらはその名の通り検索システムと推薦システムの教科書です。LLM 時代の新基準になることを目指して執筆しました。すべてのログデータをプロンプトに入れて「これを前提に何を推薦すればいいか」と LLM に訊くという投げやりな推薦アルゴリズムすらあるような時代です。この教科書では、そのようなものからエージェントベースの手の込んだ手法まで、LLM 時代の手法を詳しく解説しました。もちろん、転置インデックスや行列分解などの古典的な手法も丁寧に解説し、またそれだけでなく、古典的な手法と LLM 時代の手法のシナジー効果を生む手法や、それぞれの使い分け場面についても解説し、骨太の解説になるように心がけました。それぞれ 320 ページと 288 ページで、合わせて 600 ページ以上あり、両方読めば情報検索分野の全体を一通り学べると言ってもよいかと思います。
『検索システム』では第 5 章「生成検索」で LLM 時代の手法を数多く紹介しています。
LLM を使った検索というと RAG を思い浮かべる方が多いと思いますが、まずそれ以前に文脈詰込み (context stuffing) という手法があります。本書では検索に特化したものとして全文プロンプトと呼んでいます。RAG は検索で引っかかった文章をプロンプトに入れて質問に答えさせますが、全文プロンプトはすべての文書をプロンプトに詰め込んで質問に答えさせます。
2～3 年前は LLM の文脈長が 512 や 1024 などが主流だったので RAG が有効でしたが、最近は文脈長が 100 万トークンあるモデルも珍しくありません。日本国憲法全文（全百三条）は GPT-5 のトークナイザーだと 8334 トークンなので、その程度であれば余裕で全文詰め込めますし、社内のマニュアルをすべて詰めても 100 万トークンに入りきるというのはあり得る話です。そのような時代背景をふまえながら、どのような場合に RAG が適切で、どのような場合に全文プロンプトが適切かを詳しく議論しています。
ここですべてをお話すると肝心の本を買ってもらえなくなるのであまり深入りはしませんが、大まかにいうと RAG と全文プロンプトは適合率 (precision) と再現率 (recall) のような関係にあります。全文プロンプトは再現率が高く、情報の拾い逃しが少ないと言えますが、文脈が多いとこじつけ的に間違った情報を出力する可能性が増えます。逆に RAG は拾い逃す可能性がありますが、拾えたときには事実に基づいて回答しやすくなります。また、もちろん使う LLM の基礎能力にもより、基礎能力が弱いとたとえ文脈長が足りても全文プロンプトをうまく処理しきれません。
『検索システム』ではそのあたりも含めて実用的な話を数多く収録しているので、興味のある方はぜひ読んでみてくださいね。
『推薦システム』は LLM を使った手法を 10 以上掲載！というのを一つの売り文句にしています。前述のようなすべてを LLM に任せる手法もありますし、なにより従来の推薦システムは商品をポンと出して終わりだったのに対して、LLM を使えばなぜそれがあなたに合っているのかを言葉で説明できます。さらにはセールスや説得のようなことまでできてしまいます。もちろんやりすぎるとユーザーにウザがられますが、それでも推薦システムの応用範囲が LLM の登場でとても広がったように感じています。
Amazon, YouTube, X, Netflix などの巨大テック企業の成功は推薦システムなしで語ることはできません。当初は不満の声が多かった X のおすすめ欄ですが、今では確実に浸透して X の利用時間を増やしていますし、YouTube でも推薦がなければ動画を見ている時間ははるかに少なかったはずです。自分からキーワードを入力して動画を見つけにいかなければいけないようなサービスだったら、気づいたら 2 時間 YouTube を見ていた、なんていう体験は起こらなかったでしょう。
今後、推薦システムは LLM の登場でますますその威力を増して、LLM × 推薦システムをビジネスのドライバーにする企業が多く登場するのではないかと思います。
もう少し技術的な話としては、LLM の登場で推薦システムにおける内容フィルタリングと協調フィルタリングの役割が変容したように思います。内容フィルタリングはアイテムや商品自身の性質をもとに推薦するアプローチで、協調フィルタリングは他のユーザーがどう行動したかをもとに推薦するアプローチです。従来の推薦アルゴリズムは「この商品を買った他のユーザーはこの商品も購入しています」に代表されるように、他のユーザーの行動を使う協調フィルタリングが一般的でした。
しかし近年、LLM の登場で内容フィルタリングの力が増しています。単に私にどの内容が合っている？と ChatGPT に訊くだけで ChatGPT は内容に基づいておすすめを教えてくれます。LLM は内容に基づく推薦が得意であり、時には協調フィルタリングを上回るようなシンデレラフィットを提案してくれます。
このことはこれまで推薦システムを導入できなかった企業やクリエイターにとって追い風になります。協調フィルタリングは数多くのユーザーが存在するサービスではじめて効果を発揮するので、小さなサービスでは機能しませんでした。極端な話、ユーザーが 1 人では協調フィルタリングは原理的に成立しません。それに対して、LLM を使った内容フィルタリングはデータが乏しくても、極端にはユーザーが 1 人だけ、自分だけでも機能します。
これにより、推薦システムが使える範囲が劇的に増えました。サービスを作るとき、これまでは人が来ないからデータが集まらない、データが集まらないから推薦がうまくいかない、推薦がうまくいかないとサービスに滞留してくれないという悪循環がありましたが、これからはサービスの初期では LLM ベースの内容フィルタリングで推薦システムを作り、それで人とデータが集まると徐々に協調フィルタリングも導入していくというブートストラップができるようになりました。

Secondary note: From HN, I know you don’t like AI written content so I’ve reworked most of this post to be written in my own words. The slide decks are the most interesting, LLMs were used to add context. I’m making those available as downloads for first talk and then second talk.
TLDR; Every core smart device in my house does not depend on a vendor’s server. If the internet goes down, everything works (downgraded experience perhaps). It has been my rule for 10 years and it has been challenging to follow. I’ve given two talks about it. Check out each slide by slide.
Why local
My Nest integration worked one day until it didn’t. They had changed the api (around the same time Google acquired them). I have a few more examples in these talks that show a samsung fridge and a grill controller that needs wifi to show temperature. I don’t/shouldn’t need wifi and/or vendor service to interact with hardware.
So everything that matters runs on hardware I own. Mostly on Tasmota on esp8266/esp32 boards, MQTT broker, and Node-RED on a Raspberry Pi. I do use some cloud services for enhancements like Alexa and a few AWS ones BUT those are secondary. If the internet is down, the switches all work like normal.
The rules
From the first talk:
- No internet, no problem. Core stuff has to work with the internet unplugged.
- Don’t remove the old way while adding the new one.
- Be agile.
- Check your automations.
- Exceptions must be exceptional.
Added after year five, once more people lived in the house:
- A cloud device needs an API with logs or it doesn’t get installed. I don’t want a black box in the house.
- Configuration lives in one place instead of five vendor apps.
- More than one way to do something. An app, Alexa, a QR code, or an NFC tag.
- If I keep doing the same steps, it becomes routine (node red or on the tasmota device itself).
- Devices talk pub/sub over MQTT instead of point to point.
- No batteries unless they last a year or more between changes.
I get asked about the the Tasmota sprinkler controller the most as well as the garage door setup. Both have been running for years with no real changes.

It’s an overpriced box fan with a HEPA filter and an air quality sensor. It has some controls for the fan speed, and it can also automatically ramp up if the air quality is bad. It’s ugly, but they’re so ubiquitous around here that I feel like no one even notices them anymore. Also, FWIW, the device works. It really does improve air quality.
This device became a staple item in our household when my wife eventually started cranking up the fan at night for white noise (a dual purpose!). Over time, I have become accustomed to it and now also require it to sleep.
The Good Night button
Our home also has smart lighting, and it’s all integrated with Apple Home. At night, I always press the “Good Night” button, which shuts off all the lights. I really wanted to tie the fan into that. I’d press Good Night, the lights would shut off, and the fan would crank up to my wife’s preferred white noise volume.
The old Airmega didn’t have Wi-Fi, so there was no easy way to integrate it with Apple Home. When it eventually broke, I bought the now-discontinued Coway Airmega IconS (for non-discontinued Wi-Fi models, check out the Airmega 250S or Airmega MightyS). It’s still just a box fan with a HEPA filter, but it’s considerably more expensive, aims to look like a piece of fancy mid-century furniture, and most importantly, can be controlled over Wi-Fi (sort of).
The existing Home Assistant integration
Coway’s iPhone app is an absolutely classic IoT affair. It takes forever to load, and it asks me to change my password nearly every time I launch it. Thankfully, a brave soul reverse-engineered the app and wrote an integration for Home Assistant. The integration more or less pretends to be the phone app. It polls the Coway cloud service for status updates and sends commands through it to control the fan. Home Assistant bridges that to Apple Home and… voilà!
Why ditch the cloud?
The downside of this approach is that you’re still at the mercy (or lack thereof) of the Coway cloud service. It seems like at least once or twice a year, it breaks.
Here are some of the reasons I have seen it break:
- Coway didn’t like the integration hammering their servers and banned it. After a protracted argument with the community, they eventually settled on allowing it.
- Coway rewrote their phone app and rebranded it from IoCare to IoCare+, so the integration had to be rewritten as well.
- Coway made minor changes to the layout of the HTML that the integration scrapes, which broke it.
- Coway’s servers were periodically offline, which prevented any remote control of the device.
- Coway banned my account at one point for running an old version of the integration. I couldn’t control the fan remotely for weeks while I waited for their support team to reverse the ban.
On top of this, it seems unlikely that Coway will maintain this service forever. I suspect that eventually, like all IoT manufacturers, they’ll either charge for this service or discontinue it. My fan model is already discontinued (though there are other Wi-Fi enabled models, so… who knows).

The Home Repo Pattern
One repo for your skills, AGENTS.md and shared docs, with pointers to your other repos. A reference, with a setup prompt you can copy.
On this page
A Home Repo is one repository that holds your skills, your AGENTS.md and your shared docs. You run your agent in the Home Repo. Its AGENTS.md holds a navigation pointer to each of your other repos, so the agent can open or clone them as it needs to.
The problem it solves
When a project spans several repos, an agent started in one of them sees only that repo. Each repo ends up with its own copy of the skills and the agent setup, and planning a feature that crosses repos means working without the whole overview.
A Home Repo gives you:
- One place for your steering files and tooling
- One place to run all your agents
- Sweeping changes across multiple repos from a single session
Set one up
Paste this prompt into a new session with your coding agent, started in the folder that holds your repos. The agent finds your repos and their skills itself, grills you about the decisions in rounds, and changes nothing until you approve its plan.
Set up a Home Repo with me: one git repo that holds my shared skills,AGENTS.md and shared docs, and points at my other repos. データセンターの排熱でエビ養殖、NTT系が実験 育ったら食べられる？ 担当者に聞いてみた
NTTドコモビジネスなど4社は11月13日、データセンターの排熱を活用してエビを養殖する実証実験を発表した。2026年度中に養殖に適した排熱の回収方法を模索し、2027年度には回収した熱を使ってクルマエビ科の一種「バナメイエビ」を育てる計画だ。なぜエビの養殖を選んだのか、育てたエビはどうするのか。担当者に話を聞いた。
実証では、データセンターの冷却設備から排熱を回収し、エビの飼育水を温める。26年度は排熱の温度や熱量などを調べ、養殖に適した回収方法を検証。27年度には実際にエビを飼育し、排熱による水温維持や加温エネルギーの削減効果、データセンターの運用への影響などを調べる。
同実験は東京都の「スタートアップによる未利用熱活用促進事業」に採択されたもので、4社が参加する。NTTドコモビジネスは都内近郊の自社データセンターを実証場所として提供し、設備への影響を評価。IMTエンジニアリング（静岡県磐田市）は養殖システムの設計と飼育の運営、日比谷総合設備（東京都港区）は排熱回収・熱供給設備の設計・施工、NTTグリーン&フード（東京都千代田区）は飼育環境の監視と事業性の評価を担う。
背景には、データセンターの排熱と陸上養殖が抱える課題がある。生成AIの普及などでデータセンターの電力消費が増える一方、排熱は比較的低温のため、活用先が限られていた。一方、陸上養殖では飼育水の温度を一定に保つためのエネルギーが負担になっている。4社は排熱を養殖に利用することで、双方の課題解決を目指す。
なぜバナメイエビ？ 担当者に聞いた
バナメイエビは、成長すると体長15～20cmほどになるクルマエビ科の食用エビ。東南アジアなどで盛んに養殖されており、日本でもエビチリや炒め物などに使われている。
NTTドコモビジネスの担当者に選定理由を聞いたところ、「バナメイエビは陸上養殖の研究が進んでおり、16～18週間という非常に短い期間で育成できる技術が確立している」という。短期間での育成が可能なことから、養殖対象に選んだと答えた。
育てたエビの用途については「実証終了後に出荷可能な状態であれば、出荷を検討する」と担当者。ただし、出荷先や具体的なスケジュールは決まっておらず、「できればそういった状態に持っていけると良いなと考えている段階」という。

ヒットした作品ということもあって、早い段階から続編の企画は進行していた。
「前作の制作時、ラストでアンジェラとディンゴがトレーラーの中で笑っているカットを作った際、野口（光一）プロデューサーから『続編を匂わせているように見えるから外してほしい』と言われたんです。しかし、『アンジェラが最終的に楽園を追放された、あるいは捨てた状態で地上で生きていく、ディンゴと一緒になるかどうかは別としても、彼女がその覚悟を持っているシーンなのだから映画として絶対に必要だ』と主張し、残すことになりました。最初から続編を想定したわけではないのですが、『続編を』という企画自体はすぐに持ち上がりました。前作がきれいに終わっていたため、続編で一体何をやればいいのか、という根本的な疑問から始まりました。私としては『やるのであれば、虚淵さんに脚本を書いてもらうことが絶対条件』と伝えていました」
「Fate/Zero」「魔法少女まどか☆マギカ」などでも知られる虚淵さんは“超”が付くほどの人気脚本家、小説家だ。続編は、水島監督、虚淵さんありきで進められていた。
「虚淵さんとは個人的にも交流があるので意向を聞いたのですが、彼からも『続編って何をやればいいんですか』と返されてしまって。『だよね』と納得しつつも、『作りたい』という意志自体はずっと受け止めていました。そのため、野口さんとも数年に一度会っては『どうですかね』といったやり取りが長く続いていました。企画が具体的に動いたのは約6年前です。ある時、虚淵さんがひらめいて『これならいけるかも』というアイデアが出てきて、一同で集まって『とりあえず一度進めてみよう』とスタートを切ることになりました。それまでの間は、いつ動くか先が見えず、仕事の予定としてもあてにできない状態でした」
「水島精二×虚淵玄」の名タッグが再び動き出した。
「『なるほどね』と腑（ふ）に落ちました。打ち合わせを経て変化した部分は当然ありますが、芯の部分は現在の形とほぼ変わりません。前作は実験的な要素が多く、実質的にはOVA規模の予算でした。今回は、東映が全国配給する映画としてしっかりと予算も確保されています。その条件のもと、12年たった今、我々が何をやるべきか。虚淵さんのアイデアには、前作では表現できなかった要素もしっかりと盛り込まれていました。映像にするには、難度の高い要素ばかりでしたが、『これを形にしていくのはワクワクするな』とも感じました。虚淵さんは『水島さんだったら、シナリオを読み込んで真面目に取り扱ってくれると思ったので』と最初からあてにされていまして（笑）。信頼の裏返しとはいえプレッシャーを感じながら取り組みました」
虚淵さんから委ねられた水島監督は、試行錯誤を繰り返した。
「虚淵さんのシナリオはあまり書きすぎない。クリエーターに委ねる部分が大きいんです。任せてもらえるのであれば最大限に応えたいですし、そのためのアイデアをこちらで考えなければなりません。ただ、私自身はとっぴなアイデアを次々と生み出すタイプではなく、過去に触れてきた映像の蓄積やお客さんの目線を大切にして作っていくタイプです。お客さんも何だか分からないものをいきなり見せられても面食らってしまいますから、パッと見て判断していただけるラインを意識しています。今回で言えば、リビルダー（スライムのような正体不明の物体）の開発を一緒に担当してくれたクリエーターの多家正樹さんらと密にキャッチボールを重ね、このカット数で一番面白くできる表現を突き詰めていきました。シークエンスの構成としては、カットの連続性をあえて断ち、形状を厳密につなぎ続ける無理な設計を避けています。形状の変化が激しいリビルダーだからこそ、カットの合間にカットを挟むなど演出的な工夫を凝らすことで、異様さをコントロールしながら表現できるようにしました。長回しで見せるカットと、短く刻むカットを計算して配置しつつ、編集のリズムやテンポを意識してカット運びを構築していきました。アニメーターが面白い動きを取り込んでくれたら、臨機応変にリズムを変えて再構築しています」
前作は、フル3DCGアニメのヒットは難しいというそれまでの常識を覆した。それから約12年、日本国内のフル3DCGアニメが増え、受け入れられるようになった。
「12年前は、3Dで劇場版アニメを一本丸々制作すること自体が大きな挑戦でした。当時、ポリゴン・ピクチュアズが制作したテレビシリーズ『シドニアの騎士』の抑制の利いたセルルック表現に強い刺激を受け、我々は映画なのだから、さらにその先をいかなければならないと考えていました。当時グラフィニカにいらした板野一郎さんの指導のもと、絵コンテをものすごく膨らませてくれたこともあり、高いクオリティーに到達できました。では、この12年でエポックメーキングな技術革新があったかというと、実はそうではありません。セルルックにこだわり、アニメーターの手作業でモデルを変形させて表情やニュアンスを作る手法自体は、過去と大きく変わっていないのです。ツールは進化しているものの、求められるハードルも上がっているため、作業の大変さは変わりません。3D制作はレンダリングに膨大な時間がかかります。予期せぬエラーが出ればやり直すしかなく、作画のように、直前まで粘って手直しするのが難しい。煙や爆発といったエフェクトも、3Dで作画のように成立させるのは非常に難しく、3Dだから実現できた表現が数多くある一方で、時間の面などでも非常に厳しい戦いがありました」
新作では、3DCGで背景美術を表現するという挑戦もあった。
「野口プロデューサーがCG畑の出身ということもあり、『アニメーションではなぜか背景を3Dでやらないことが多いが、今回は背景も3Dで構築したい』という提案がありました。当初は『全編3D背景で』という勢いだったのですが、コストを考慮すると現実的ではないため、いくつかのシーンを選定して行う形に落ち着きました。その際、私から『今後の3Dアニメーション制作の指標となるデータを取るためにも、屋内の狭い場所ではなく、あえて空間的に広いところで挑戦しなければ意味がないだろう』と提案し、広大な縦穴の空間などを選んだのですが、結果としてそれが自分たちの首を絞めることになりました。リビルダーが食い荒らしてできた穴の特殊性をどう表現するか悩んでいた際、美術設定を担当してくれたスタッフから『ビスマスはどうでしょうか』というアイデアが出ました」
ビスマスは、階段状の幾何学的な結晶、玉虫色に輝く虹色の表面が美しい。大きな見どころになっているが、苦難の連続だった。
「何より難しかったのは、設定上のスケール感です。この縦穴は直径5キロメートルという途方もない大きさなのですが、そんなスケールのビスマス空間に足を踏み入れた人間など世界中に一人もいません。そのため、作り手側も何が視覚的な正解なのかが分からない状態からのスタートでした。さらに、映画のスクリーンに耐えうる解像度で巨大空間を丸ごと構築しようとすると、データ量が膨大になりすぎる。そこで、カットごとに必要な範囲を切り取り、複数パターンの素材を組み合わせて構築する手法を採りました。その手法を採ると、3D本来の強みが崩れてしまいます。最終的に目指す絵作りのために素材を合成、再配置していくため、作業者個人のセンスに依存するところが極めて大きくなってしまったのです。3Dで背景を作っている以上、形状や対比自体は極めて正確に表現できるのですが、その正確さが逆に仇（あだ）となる場面もありました。直径5キロの縦穴の中にキャラクターを置き、上から注ぐ光量や影の落ち方を厳密にシミュレーションすると、深さがあるため底や奥は真っ暗になってしまい、そもそも絵として成立しません。 ただただ暗くて広い空間の中だと、望遠でキャラを捉えて動かしても奥の空間の変化が乏しく、意図したダイナミックなアクションになりません。奥を暗く落としすぎるとキャラクターの移動や距離感が分からなくなるため、物理的な正しさと、映像としての見やすさ、伝わりやすさをどう両立させるか、足し算と引き算を繰り返しながら最後まで調整に頭を悩ませました」
前作の公開から約12年、AIを取り巻く状況は大きく変化した。「楽園追放」で描かれるAIによる管理社会は約12年前よりも現実味を帯びてきた。
「SF作品に深く関わってきた人間からすると、人造人間など『人と同じ役割を果たす人ではない存在』には数多く触れてきているため、現実が追いついてきたという感覚はあっても、AIに対する意識そのものが劇的に変わったわけではありません。『BEATLESS』というアニメを手掛けた際にもAIの現状をリサーチしたのですが、炊飯器や券売機といった特定分野を制御するAIが日常に溶け込んでいる一方で、人間に取って代わるような存在はまだ空想の域にあります。原作者の長谷敏司先生とも当時議論したのですが、長谷先生が『AIはプログラムで動く機械であり、魂はない。人間に代わるものではない』という立場だったのに対し、私はピノキオのように『器が人間で、思考も人間と同じものをトレースして動くのであれば、人間として扱ってもいいのではないか』と考えるタイプです。長谷先生はその感覚の違いを『多様性』として容認してくださいました。今回もそうした『魂の器としての在り方』という根本的なスタンスは変えずに描いています」
「楽園追放」は、管理社会の中で喪失しつつある“人間らしさ”や“人間のアイデンティティー”についても考えさせられる。
「なぜかそうしたテーマを内包した企画が自分のところへ巡ってくるんです（笑）。會川昇さんや黒田洋介さん、虚淵さんといった同世代の脚本家と組むと、この社会で作品として何を提示すべきかという問題意識が自然と共有されます。20歳ほど離れた若いライターと組む場合でも、打ち合わせの中で私がそうした話をしているからか、自然とテーマに入ってきます。私は何かに極端に偏った物語よりも普遍性を重視したいと考えています。他者を拒絶するのではなく、どうすればよいバランスで共生できるのかという視点は、どうしても作品ににじみ出ます」
