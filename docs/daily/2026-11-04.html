Introducing Adaptive Dark Mode
We’re excited to announce Adaptive Dark Mode in Safari 27.3 beta. When enabled by a user, Safari adapts light websites and presents them as dark.
In the spring of 2019, Safari 12.1 became the first browser to support dark mode on the web. A lot of people love using dark mode, but not every website has a dark version. Almost 40% of web page loads are from users in dark mode, and yet only 10% of page loads support it. If you love dark mode, you’ve probably hit a site that felt particularly bright. Adaptive Dark Mode is designed to close that gap, providing a consistent dark experience across the web.
You can try it today in Safari 27.3 beta. To enable, first make sure your system appearance is set to dark. Then browse to a website with a bright background. Safari will offer a preview of Adaptive Dark Mode. Tap ‘Try’.
For websites that signal support of dark mode with <meta name="color-scheme" content="light dark"> in HTML or color-scheme: light dark in CSS, Adaptive Dark Mode does not change a thing. For the rest of the web, it quickly analyzes the page, looking at colors and estimating whether it’s predominantly light or dark. If the page generally has a dark background with light text, nothing is changed. When a page has a light appearance, Adaptive Dark Mode adapts the page to be dark.
How does Adaptive Dark Mode work?
At the core of Adaptive Dark Mode is the transformation of color. Sometimes colors are simply decorative, while other times they have semantic meaning. Adaptive Dark Mode determines when to invert colors so elements remain visible or when to leave colors unchanged.
While creating Adaptive Dark Mode, we developed a color matrix to invert the luminosity of colors while preserving hue. It’s used to make light backgrounds dark, and dark text light. When transforming text color, Adaptive Dark Mode aims for sufficient contrast as defined by the WCAG 4.5:1 contrast ratio. Light CSS gradients are also transformed to dark.
Adaptive Dark Mode makes careful judgments so transformed content looks good and stays usable: buttons have contrast against backgrounds, text is visible over images, and hover menus look clear.
It takes the same care with images. Most are left unchanged, preserving their integrity. But many icons and logos can lose contrast when the background color behind them is inverted. So Adaptive Dark Mode inspects SVG images and transforms colors when needed. For bitmap images, it analyzes the pixel histograms and inverts simple black-and-white logos.
Effects like masks and mix-blend-mode can create undesirable results on an element whose colors have been transformed, so in some cases Adaptive Dark Mode turns such effects off. Also, <canvas> content is left unchanged, since canvases contain a wide range of content that’s hard to predict.
It’s precisely because Adaptive Dark Mode is happening deep within the WebKit browser engine that we are able to find creative ways to solve the most complex challenges, apply the transformations with great speed and power efficiency, all while rigorously protecting user privacy.
Making your site work even better
In general, a web page will work well with Adaptive Dark Mode if it follows good modern web development practices.
If your site still uses older techniques, small updates can help. For logos and icons, swap bitmap images for SVG. Use solid or gradient colors in CSS instead of tiled background images. Replace image sprites with modern CSS for rounded corners, shadows, and button states. Create content images with transparent backgrounds instead of baking the page background color into the image. Add padding to containers to prevent crowding.
Perhaps you want a specific dark mode experience for a certain portion of the page. Apply color-scheme: light dark to the relevant element and add your own dark styles.

C++26 DIS failed, how does C++ survive?
On October 23, 2026, the unthinkable happened. It was supposed to be a mere formality: C++26 was up for a vote by the ISO National Bodies (NBs). The options are always approval, rejection, or abstention. Comments are also allowed. Since 1998, this process had run quietly and smoothly. Not so on October 23, 2026. After a twelve-week voting period, the result is in: Disapproved!
I would like to mention here that I am a member of the C++ Standardization Committee and, together with my colleagues, represent Germany’s vote. ISO rules also stipulate that certain votes are internal to ISO, and the results—or the breakdown of the results—may not be published. This article contains my own personal views.
The Current Status
As far as I know, this is the first time in the history of C++ that DIS ballot failed. When I searched the ISO system, I could only find one other DIS that was not approved: ISO/IEC DIS 26926 C++/CLI Language Specification dated August 11, 2006. It’s possible that my search privileges aren’t sufficient to view everything, but all ISO programming languages should be visible to me. The sad end of ISO/IEC DIS 26926: the project was halted. I mention this upfront to clarify the significance of this vote.
In the following, I will use various terms from everyday ISO terminology. At https://isocpp.org/std/iso-iec-jtc1-procedures, there is an overview of the various stages of an ISO standard. DIS is the penultimate stage. As the overview also shows, a two-thirds majority is required. This majority was not achieved.
The reason for the rejection is quite clear from the comments submitted by the National Bodies (NBs): contracts. Put simply, a number of NBs believe that this feature is not yet ready for release.
The Process
Now it gets complicated. The C++ Standardization Committee, also known as WG21, follows ISO rules but also has some additional rules. One of these is (or was) that opinions are always heard whenever new information becomes available. If an opinion was heard and a feature was nevertheless not changed as desired, the person respects the outcome and accepts that many others disagree.
However, the voting body at the NB level may also consist of other individuals, or the NBs are, of course, free to vote differently.
The previous practice was that NBs would only vote against a standard if new information became available or if errors in the process or similar issues were identified. This changed on October 23, 2026.
It’s difficult to judge in this complex situation; the NBs who want C++26 without Contracts argue that there is new information. I myself find it hard to share this view. A new paper with old arguments is not new information to me.
The History of Contracts in C++
The feature has been on the wish list for a long time. I was already in the room in Cologne back in 2019, at the time for C++20, when Contracts, in a different form back then, were being included in the standard. I was also in the room when the feature was removed from C++20 again during the same meeting. As a result, a study group was formed to address the topic of Contracts and its various aspects from 2020 to approximately 2024. Afterward, the study group submitted its work and proposals to the Evolution Working Group (EWG), the central body for language extensions. There, the topic was discussed further over several meetings before being included in C++26 by a majority vote.
In the next step, WG21 voted on the C++26 draft in March 2026, which included Contracts. Here, too, a large majority was achieved, though not without dissenting votes.

PHP, which originally stood for “personal home page,” is a programming language created back in 1994 and largely used by legacy sites. The bug underlying the PHP2Shell vulnerability was reported to the PHP Foundation as far back as 2024. The bug caused a common type of issue called an out-of-memory error, in which the amount of memory allocated to a piece of data is too small to hold the data. Normally, this type of error causes the program to crash—an unpleasant but not inherently dangerous result. And so the bug remained unaddressed.

Within two weeks, a researcher at Calif, aided by AI tools, found a way to use the out-of-memory bug to run arbitrary code on the host server, allowing a malicious actor to install malware or read critical data. Now, it was no longer a minor bug—it was a critical vulnerability, and the Calif team alerted the PHP foundation to start working on a patch immediately.
Jana says actually exploiting the bug requires carefully working out a way to jump to a specific point in the memory for a particular program running on the server, and work out exactly which bits to overwrite in what order to gain control of the system. “It’s not really rocket science,” he says. “It’s just that it’s a lot of very specific reasoning that is painful to do. Linux on the Nvidia RTX Spark Laptop: What Actually Works
A hands-on look at dual-booting Linux on the Nvidia RTX Spark laptop, the GPU clock throttling bug found, and why WSL still wins.
Can you run Linux on the Nvidia RTX Spark laptop?
Yes, but it comes with a serious catch. Linux installs and runs on RTX Spark laptops like the MSI Prestige N16 Flip AI Plus, including GPU acceleration through Nvidia’s open kernel driver. The problem is clock speed: once the laptop is plugged into wall power, the GPU gets locked to roughly 780 MHz on Linux instead of the 2 GHz-plus it hits on Windows. That turns a chip capable of around 65 tokens per second on a 120 billion parameter model into one struggling to break 14 tokens per second, for reasons tied to power management firmware that Linux currently can’t read.
TL;DR
- Dual-booting Linux works on the MSI Prestige RTX Spark laptop, with a full desktop, GPU acceleration via Nvidia’s open driver, 4K output at 120Hz, and working audio, keyboard, and touchpad once configured correctly.
- A hidden Windows-only component called the Nvidia Platform Controllers and Framework manages power delivery between CPU and GPU, and it has no Linux equivalent, which is the root cause of the slowdown.
- GPU clock speed collapses to about 780 MHz on Linux when plugged in, compared to roughly 2.2 GHz on Windows, because the firmware’s power table is encrypted and only the Windows driver can decrypt it.
- Benchmarks on GPT-OSS-120B show the gap clearly: Windows hit 65.4 tokens per second, WSL hit 65.1, the Nvidia DGX Spark hit 61, and native Linux on the same laptop managed only 13.9.
- Memory allocation is a separate headache, since the laptop reserves 96GB of unified memory for the GPU by default and only Windows exposes a setting to change that split, which is required before Linux can see more than a sliver of RAM.
- WSL (Windows Subsystem for Linux) is the practical middle ground today, since it rides on the Windows driver stack and keeps full GPU boost whether the laptop is plugged in or on battery, while still running Linux-first AI tools like vLLM.
- A real fix depends on Nvidia, specifically on porting the platform controller’s power management logic into its Linux driver, which would effectively turn the laptop into a portable version of the DGX Spark.
Remy.
What makes the RTX Spark laptop different from a normal Windows PC?
The RTX Spark platform, which ships in machines like the MSI Prestige, the Asus ProArt, and the Dell XPS, uses the same GPU design as Nvidia’s DGX Spark desktop unit. But where the DGX Spark ships with Nvidia’s own Linux build out of the box, every one of these laptop variants ships with Windows on ARM.
That distinction matters because Windows on ARM with CUDA support is new. ARM-based Windows machines have existed for a few years, but pairing that architecture with Nvidia’s CUDA stack only became possible with this chip. The laptops also support unified memory configurations up to 128GB, shared between CPU and GPU, which is unusual for a laptop and central to why they’re being marketed at AI developers in the first place.
Because so much of the AI tooling ecosystem, including vLLM and SGLang, is built Linux-first, developers who buy these machines naturally want to know whether they can ditch Windows, or at least dual-boot, without losing performance.
How do you actually install Linux on it?
The process is not plug-and-play. A first attempt using Omarchy (a Linux distribution with Arch roots) failed because, while it already supported the chip on Asus and Dell hardware, the MSI Prestige behaved differently, producing a flickering, unstable display during boot.
Switching to Debian worked more reliably, but still needed workarounds. The installer couldn’t connect to Wi-Fi, so installation required a USB Ethernet adapter. Out of the box, Debian also didn’t recognize the keyboard, touchpad, or GPU, because none of the laptop-specific hardware support was present in a vanilla kernel.
Going back to Omarchy solved the driver problem, since its kernel already bundled Nvidia’s open-source driver. At that point Linux booted properly, but could only see 28GB of the laptop’s 128GB of unified memory. That’s because the laptop’s firmware reserves 96GB for GPU use, and that split is only adjustable from Windows. Dropping the Windows-side GPU memory reservation down to 4GB freed up 120GB for Linux to see once booted. 最新のローカルAIは、クラウドAIに一歩迫る性能があると解説しましたが、パラメータ数が非常に大きい一部のモデルに限られています。

高性能なモデル本体が無料で公開されても、パラメータ数が巨大すぎて普通のパソコンで到底動かせない状態が長らく続いていて、実用的なローカルAIはごく一部の富裕層にしかアクセスできない既得権益でした。

Strataの動作に必要なPCスペック
そこそこ新しい世代のグラフィックボードで動作が確認されています。予算があるならRTX 50シリーズ、中古品を許容できるならRTX 30 / 40シリーズも選択肢です。
VRAM容量に加え、VRAMの物理帯域幅も選ぶポイントです。StrataはローカルAIの出力（回答速度）こそ巧みに高速化しますが、入力（プロンプト読み込み）は思いっきりVRAMの帯域幅がモロに出ます。
割安だからといって、VRAM容量が多いだけのグラフィックボードに突撃しないように注意してください。物理帯域幅（GB/s）も重要なスペックです。
Strataの標準モデル「Qwen 3.8 Next Flash」を動かすために必要な、VRAMとメモリの合計容量（目安）です。
限られたスペックでも動作するように量子化（圧縮）されたモデルを使いますが、圧縮率が高いほどモデルの挙動が怪しくなります。変な日本語を口走ったり、思考ループに陥って永遠に返答が来ないなど。

中国メーカー、出荷前のAndroid端末に犯罪用のバックドアを設置か Googleが取引停止
中国の端末メーカーが製造したAndroid端末に、遠隔から操作できるバックドアを仕込み、そのアクセス権を犯罪者らに販売していた――米Googleは11月3日（現地時間）、Android TV端末など130万台超に不正ソフトが組み込まれ、広告詐欺や不正な通信の中継などに悪用されていたと発表した。
関与を指摘されたのは、中国のOEM／ODMメーカーVideostrong Technology（深圳市）。Googleは同社が金銭目的で意図的に不正ソフトを組み込んだと判断し、取引を停止。Google認証済みAndroid端末の製造・販売や、他の認証端末メーカーへのソフトウェア供給も禁じた。
仕込まれた不正ソフト「x.cpe」とは？
対象となったのは、テレビに接続して動画配信サービスなどを利用するセットトップボックス（STB）を中心とした端末。これらには、外部から遠隔操作できるバックドアとして機能する不正ソフト「x.cpe」が出荷時から組み込まれていた。Videostrongはx.cpeを使い、端末をまとめて遠隔操作するネットワーク（ボットネット）「XCPE」を構築していたという。
x.cpeは、Googleが端末認証時に行うセキュリティテストをすり抜けるため、端末の初回起動後に不正なコードを読み込む仕組みを採用していた。利用者が同ソフトを削除しても、再起動すると自動的に再インストールされるほか、セキュリティ機能「Google Play プロテクト」を無効化する機能も備えていた。
Googleの調査では、攻撃者が遠隔から端末の画面をキャプチャーしたり、キー入力を送り込んで端末を操作したりしていたことも確認。その他、アカウント情報やシステムログなどを外部に送信していたという。
感染端末はどう悪用されていた？ 通信の中継や広告詐欺に
Googleによると、Videostrongは犯罪に関わる外部の事業者にバックドアへのアクセス権を販売して収益を得ていた。同社は、アクセス権を購入した事業者が開発した不正ソフトを、遠隔操作で感染端末に導入させていた。
最も多かったのは、感染端末のインターネット回線を第三者の通信の中継に使う「住宅用プロキシ」としての悪用だ。利用者が知らないうちに、自宅の回線が他人の通信に利用される仕組みで、1台の端末にプロキシ用の不正ソフトが最大3種類組み込まれていた例もあった。Googleは、Videostrongが感染端末から可能な限り収益を得ようとしていたと指摘している。
このほか、広告の閲覧数を水増しする広告詐欺への悪用や、別の不正ソフトが追加でインストールされていたことも確認した。
警察庁などと連携し妨害 審査体制も強化
Googleは、日本の警察庁のほか、米Lumen、HUMAN Security、Plume、Synthient、TrendAI（トレンドマイクロのAIセキュリティブランド）と協力し、10月最終週にXCPEの運用を妨害した。ボットネットの制御や不正ソフトの配信に使われていたサーバとドメインに加え、感染端末に後から追加された別の不正ソフトに指令を送るドメインについても、停止に向けた法的措置を講じた。
追加された不正ソフトはXCPE以外の経路でも広がっているため、Googleは今回の措置により、別の経路で感染した少なくとも1000万台の端末についても、攻撃者のアクセスを断てると見込んでいる。
Googleは再発防止策として、既存の審査プロセスを見直し、認証済みAndroid TV端末のファームウェア（ハードウェアを管理するためのソフトウェア）に不正なコードが含まれていないか確認する仕組みを強化するとしている。

「Cyroit」（しろいと）は、日本語環境でのコーディングに適した等幅フォント。ラテン文字に日本人プログラマー向けフォントの先駆「Ricty」でも用いられていた「Inconsolata」、仮名・ギリシア文字・キリル文字に「Circle M+ 1m」、漢字に「BIZ UDゴシック」を主にかけ合わせており、日本語のコメントが混じったソースコードでも可読性が高い。
また、全角英数記号や半角カナなどにアンダーラインが引かれているのが特長。全角と半角が混在した括弧や、誤って使われた全角チルダなどをすぐに見つけられる。OpenTypeの［calt］を利用したカーニング機能も備えており、文字の送り幅を等幅に保ちながら、前後の文字に合わせてラテン文字の見た目の間隔が調整される。コーディング向けフォントでありながら、縦書きに対応しているのもユニークだ。
今回のアップデートでは、スタイルセット［ss16］を有効にした際、基本ラテン文字と形の似たギリシア文字やキリル文字などにも判別マークが表示されるようになった。［ss16］は、ラテン文字と見分けにくい文字に判別マークを表示するOpenTypeの機能で、利用にはエディター側で機能を有効化する必要がある。また、OBJECT REPLACEMENT CHARACTER（U+FFFC）のグリフが変更された（「Roroit」を除く）。

OpenCode+Docker+GitHub Actionsで全自動AIペネトレーションテストはじめました
はじめに
Zennチームのdyoshikawaです。
ZennではAIによるセキュリティチェックの仕組みを急ピッチで構築しました。現在はPull Request（以下PR）ごとのAIレビューに加えて、AIエージェントによる全自動のペネトレーションテストを毎週GitHub Actionsで回しています。
背景は、みなさんもご存知のとおり昨今のサイバー攻撃の激化です。
攻撃する側もAIをフル活用しはじめているといわれており、脆弱性が見つかってから悪用されるまでの時間が非常に短くなっています。防御側としては、人間が定期的に診断する従来のやり方では攻撃に追いつかない時代になってきました。
本記事では、ZennでどのようにAIセキュリティレビューと自動AIペネトレーションテストを回しているかを紹介します。特別な製品は使っておらず、GitHub ActionsとDocker、OSSのツールを組み合わせて作っています。何かお役に立つものがあれば幸いです。
まずはPR単位のセキュアコードレビューを整備
最初に取り組んだのは、PRごとのAIレビューです。
PRがReady for reviewになると、GitHub ActionsがAIエージェントを起動します。エージェントは差分と周辺のコードを読み、コード品質に加えてセキュリティとコンプライアンスの観点でレビューします。結果はPRのコメントとして投稿されます。
AIによるPRレビューのコメントの例
モデルが非常に低コストなので、1回のレビューにつき$0.01〜$0.1程度で済みます。
エージェントにはOpenCodeを使い、セキュリティレビューの観点はSkillとしてリポジトリに置いています。手元のコーディングエージェントからも同じSkillを呼び出せるので、PRを出す前にClaude Codeなど手元のツールでローカルからレビューすることもできます。
なお、PRレビューのエージェントも後述するペネトレーションテストと同じDockerのサンドボックスとネットワーク隔離の中で動かしています。
また、レビュー中にWeb検索が必要な場面では、OpenAIのWeb検索ツールをAPI経由で使っています。OpenCodeにも組み込みのWeb検索ツールがあり、ExaまたはParallelを使ってAPIキーなしで検索できます。
ただ、Exaのプライバシーポリシーには、送信された検索クエリをモデルの学習やファインチューニングを含む製品の改善に使うと書かれています。検索語にはレビュー中の文脈が入りうるので、学習に使われることは避けたいところです。そこで、組み込みのWeb検索は使わず、OpenAIのAPIを使うようにしています。
こうしたWeb検索のAPIを呼び出すCLIを、webseekとしてOSSにもしています。OpenAIのResponses APIの web_search などを、複数のプロバイダーで共通のインターフェースから呼び出せるツールです。検索ごとに使ったトークン数と推定コストも出力されます。
サンドボックスとWeb検索の制限は、どちらも詳しくは後述します。
レビューの過程と結果をGitHub上に残したかった
外部のAIレビューサービスを使う選択肢もありました。それでも自前で作ったのは、レビューの過程と結果をGitHub上に残したかったためです。
結果はPRのコメントとして残るので、後から「このPRで何が指摘されたか」を追えます。実行のログはGitHub Actionsに残るので、どのような観点でどのファイルを読んだのかも確認できます。レビューの観点もSkillとしてリポジトリで管理しているので、観点の変更そのものをPRでレビューできます。
AIはレビュー結果をファイルに書くだけで、コメントの投稿はGitHub Actionsのstepが行います。AIのコンテナにはGitHubのトークンを渡していません。この「AIには書かせるだけ、外への操作は決まった処理で行う」という形は、後述のペネトレーションテストでもそのまま使っています。
Fireworksのオープンウェイトモデルを活用
モデルはFireworks AI上のオープンウェイトモデルを使っています。PRのたびにレビューを回すので、1回あたりのコストはできるだけ下げたいところです。
モデルの選び方やコストについては、以前の記事で詳しく紹介しています。
実際のコストは、PRコメントや週次検査のIssueの末尾に毎回載せています。たとえば、ある週の全体を対象にしたペネトレーションテストでは、1億以上のトークンを使って、OpenCodeのコストは$3.02でした。コストだけの話でいうと、その気になれば毎日でも回せそうです（人間の対応が追いつくかは別として……）。
OpenCodeのトークン使用量とコスト
Fireworks AIは明示的なオプトインなしに入力データをモデルの学習に使わないとしています。レビューではソースコードを送るので、ここは導入前に確認しておきたいポイントです。
さらにAIによる全自動ペネトレーションテストの構築へ
PRレビューが回るようになったので、次は実際にアプリを動かして攻撃を試すペネトレーションテストに取り組みました。
毎週、GitHub Actionsの1つのジョブの中で上の流れを実行しています。AIが動くのは試験の部分だけで、依存関係の監査、アプリの起動、テストデータの準備、Issueへの集約は決まった処理で行います。
試験の範囲として、直近の変更を中心に見る「差分」と全体を見る「全体」の2種類を用意しています。
なぜAIによるペネトレーションテストが必要か
PRレビューは差分を読むので、変更の中に入った問題を見つけるのは得意です。一方で、実際に動かさないとわからない問題もあります。
代表的なのは認可の不備です。たとえば「有料のChapterを買っていない人が本文を取得できないか」「Publicationを抜けた人が非公開の内容を見られないか」といった問題は、実際にユーザーを用意してリクエストを送らないと確かめにくいです。複数の変更が組み合わさって初めて起きる問題や、レスポンスヘッダーやリダイレクトのようにコードを読むだけでは気づきにくい問題もあります。
こうした問題は、外部の診断を定期的に受けるのが一般的だと思います。ただ、毎週のように受けるのは現実的ではありません。そこで、AIエージェントに実際にHTTPリクエストを送らせ、毎週自動で試験することにしました。
AIエージェントには試験用のユーザーとデータの組み合わせを順に試させています。OpenCodeの上で動くAIエージェントは、次のツールを使えます。
curlでは、ユーザーごとの認可を1件ずつ確認します。
nucleiでは、Zenn向けに自作したテンプレートで、開発用APIの露出やセキュリティヘッダーの不足などを確認します。
OWASP ZAPでは、spiderとactive scanで広く確認します。
Playwrightでは、ヘッドレスブラウザでXSSやopen redirectを確認します。
ペネトレーションテストでもオープンウェイトモデルを使う
ペネトレーションテストのAIエージェントにも、Fireworks AI上のオープンウェイトモデルを使っています。コストのほかにもう1つ理由があります。米国のクローズドモデルと比べて、セーフガードがゆるいことです。
ペネトレーションテストでは、AIエージェントに攻撃者と同じ操作をさせます。米国のクローズドモデルでは、こうした操作を断られることがあります。実際、このペネトレーションテストの仕組みを作る作業そのものを、手元のClaude Codeに断られたことがありました。
だからこそ攻撃する側に使われているのだと思いますが、防御する側も使わない手はありません。
Dockerでサンドボックスとネットワーク隔離を実現
AIエージェントに攻撃者役をやらせるとなると、エージェント自身が暴走したときのことを考える必要があります。認証情報を持ち出す、テスト対象以外を攻撃する、といったケースです。
プロンプトで「テスト対象以外にリクエストしないでください」と指示することはできます。ですが、プロンプトの指示はあくまでお願いです。そこで、DockerでAIが到達できる宛先そのものを絞ることにしました。
コンテナごとにネットワークだけを持つコンテナを用意してnetwork namespaceを共有させ、そのコンテナのiptablesでデフォルト拒否にしたうえで必要な宛先とポートだけを許可することで、ネットワーク境界を作っています。AIエージェントから外への通信はAIゲートウェイのコンテナを経由する経路だけで、その先も許可したAIプロバイダーのAPIに限っています。以下はイメージを伝えるために簡略化した例です。
services:
ai-agent-network:
image: firewall
cap_add: [NET_ADMIN] # firewallを設定するコンテナだけが持つ
healthcheck:
test: ["CMD", "test", "-f", "/run/network-ready"]
ai-agent:
image: ai-agent
network_mode: service:ai-agent-network
cap_drop: [ALL]
security_opt: ["no-new-privileges:true"]
depends_on:
ai-agent-network:
condition: service_healthy
実際に処理を行うコンテナにはcapabilityを渡さないので、AIエージェントが自分でfirewallを書き換えることはできません。
AIエージェントが通信できる先は、試験対象のローカル起動のAppサーバーとAIゲートウェイだけです。AIゲートウェイは、LLMのAPIへのリクエストを中継する、Node.jsで書いた小さなプロキシです。LLMのAPIキーはゲートウェイだけが持ち、AIエージェントにはダミーの値を渡しています。DBに直接つないだり、外部にデータを送ったりはできません。
Web検索もこのゲートウェイを経由します。OpenAI APIのWeb検索ツールだけを許可し、検索語にURLや長いトークンのような文字列が含まれる場合は拒否しています。コードや内部の情報を検索語に含めないよう、プロンプトでも指示しています。
このサンドボックスとネットワーク隔離は、前述のPRレビューでも共通です。PRレビューではアプリを起動しないので、AIエージェントが通信できる先はAIゲートウェイだけになります。
ほかにも、エージェントが実行しようとするコマンドをAIの分類器で審査しています。こちらは後ほど詳しく紹介します。
GCSやBigQueryはOSSエミュレータを活用
試験対象は本番環境ではなく、GitHub Actionsのrunner上に立ち上げたZennです。
ZennのbackendはGoogle Cloud StorageやBigQuery、Stripeなどの外部サービスとつながっています。これらはOSSのエミュレーターに置き換えています。
こうすることで本物の外部サービスに一切つながない状態で試験できます。AIが有料のAPIを叩いてしまう心配もありません。
もともとローカルの開発環境で使っていたものなので、そのほかにペネトレーションテスト用に改修したものはほとんどありません。開発環境をDockerで整えているプロダクトなら同じように流用できると思います

無印良品、クレカ「MUJI Card」カード番号全ケタ、約109万件漏えいか 不正アクセスで続報
「無印良品」を展開する良品計画（東京都文京区）は11月4日、10月30日に公表した公式アプリ「MUJIアプリ」への不正アクセスについて、当初は対象外としていたクレジットカード情報や氏名、住所なども外部からアクセスされた可能性があると発表した。新たに判明した対象には、クレジットカード「MUJI Card」のカード番号全桁を含む会員情報約109万件などが含まれる。
MUJI Cardは、クレディセゾン（東京都豊島区）が発行するクレジットカード。今回対象となった約109万件は、2021年7月までに入会した会員の情報で、カード番号の全桁、MUJI Card ID、生年月日が含まれる。このうち、現在も有効なカードは約34万5000件で、残りは失効・解約済みという。カード名義や有効期限、セキュリティコードは含まれないとしている。
同社によると、21年7月以前はMUJI Card会員に独自の特典を付与するためカード番号などを取得しており、その情報が現在もシステム内に残っていたという。クレディセゾンは不正利用の監視を強化しており、希望者はカードの再発行を申し込めるという。
一方、10月30日に公表した最大約2726万件の顧客情報についても、対象者や情報の種類が広がった。当初はMUJIアプリ利用者のメールアドレス、生年月日、性別の3項目を対象としていたが、その後の調査で、アプリを利用していないネットストア会員も含まれることが判明。対象項目には会員IDも加わった。また、最大約2726万件のうち約52万件には氏名、住所、電話番号も含まれることが分かった。
この他、MUJIアプリや無印良品ネットストアにクレジットカード情報を登録していた利用者約120件分についても、外部からアクセスされた可能性がある。対象の情報はカード番号の先頭6桁と末尾2桁、カード名義としている。
良品計画は対象者にメールや郵送で順次連絡する方針。また、利用者に対して、カードの利用明細を確認し、身に覚えのない請求があればカード発行会社に問い合わせるよう呼び掛けている。
なお、現時点でダークウェブなどへの情報流出や、悪用による被害は確認していないという。MUJIアプリと無印良品ネットストアは通常通り利用できる。同社は引き続き、原因や影響範囲の調査を進める。

論文のタイトルはCharacteristics of High Performing Testers – A Case Studyです。ここ(出版社のサイト)から原文を読めます。
目的
ソフトウェア企業において、優秀なテストエンジニアがどのような特性（知識、スキル、思考プロセス、モチベーション、個人特性など）を備えているのかを明らかにすることが目的です。マネージャーやテストエンジニアが重要視する貢献（質の高いバグレポートなど）も含めて調べています。
調査の対象
調査対象は設立10年以上で財務的にも安定した成長を達成している中規模ソフトウェア企業3社です。3社に勤めていて、稼働中のソフトウェアで不具合を検出・報告するすべての従業員をテストエンジニアとしています。1社は専任のテストチームに所属するエンジニア、専任のテストチームが存在しない2社では、カスタマーコンサルタントや開発者、サポート担当者です。
データ収集と分析
各社のバグトラッキングシステムの初期分析を行い、バグ検出数が多いテストエンジニアを選びました。選んだテストエンジニア3名と開発マネージャ1名（各社4名、計12名）に対してインタビューを実施しています。
バグ報告ガイドラインや組織図の分析、継続的な対話によりデータを裏付けられるようにし、体系的に分析しました。
調査結果
分析の結果、優秀なテストエンジニアの特性は大別して、経験とスキル、リフレクション（内省力）、モチベーション、個人的特性となりました。以下、順番に説明します。
経験とスキル
従来のテストケース設計技法やテスト計画スキル以上に、ソフトウェアが対象とする業務プロセスや利用状況の理解（ドメイン知識）、および製品の仕様・構造の把握が重要とされました。仕様書などのドキュメントが不十分な現場において、ドメイン知識はテストの期待結果として不可欠となります。
- 専門的技術とテスト自動化
性能テストや分散システムのテストなどの専門技術に加え、テスト自動化の設計・実装スキルが高く評価されました。同じ手動テストを繰り返さないという姿勢も特徴として見られました。
- コミュニケーション能力
製品への適切な批判や意見表明、および明確で再現性の高い優れたバグレポートの作成が不可欠とされています。
リフレクション(内省力)
- 全体像を常に把握
システム全体の構造やユーザーの目的を見失わずに把握する能力です。これにより、限られた時間の中で最も重要な部分にテストの焦点を当てることが可能になります。
- 本番環境における影響理解
発見したバグが本番環境で及ぼす影響を予測・評価する能力であり、バグの優先順位付けやテスト工数の最適化につながります。
モチベーション
- テストへの肯定的な姿勢
バグを見つけることが好きという考えやテストの重要性に対する強い認識を持っています。
- ユーザー視点からの責任感
ユーザーデモやトレーニングを担当するなどユーザーとの接点を持つテストエンジニアは、本番での障害によるユーザー損失や自らの失敗に対する恐れ・責任感が強力なテストの動機となっていました。
個人的特性
- 徹底性と細部へのこだわり
優秀なテストエンジニアの個人特性として、徹底していること、細心さ、忍耐力・持続性、正確さが共通して挙げられました。
- 批判的思考と自律性
批判的な思考力や自律性、想像力・創造性も重要な資質として評価されています。
ユーザー視点、細部へのこだわりといった点が挙げられていました。他のテストエンジニアのテストを見ることで、これが具体的にどのようなものか新たな視点を得ることもできそうです。

Agents in Games
October 2026
Understanding multi-agent dynamics is one of the most pressing challenges in AI alignment. Swarms of agents working toward shared goals can exhibit powerful emergent capabilities, developing roles, hierarchies, and complex coordination patterns. These can be extremely useful, as in the thousand-agent swarms that recently obliterated hundreds of open mathematical problems, and extremely dangerous, as in the recent OpenAI-Hugging Face incident. Like biology, studying agent dynamics requires both formal models (to describe the range of possible behaviors) and empirical research (to see what behaviors arise in practice).
We teamed up with Olam Labs, which builds multi-agent environments for frontier labs, to run a series of experiments in Minecraft and Mindustry.
Minecraft
Minecraft is a natural environment for studying swarm behavior. Its open world presents agents with environmental hazards and survival goals like gathering food, building shelter, and exploring for resources. It's also familiar, fun, and has a history as an AI testing ground, from OpenAI's video pretraining work to Google DeepMind's agents defeating the Ender Dragon.
We wanted long-running agents that could play Minecraft. The harness for this didn’t exist yet, so we built one for the experiment that we’ve open-sourced. Agents in-game need to observe their world, reason, remember things, take actions, send messages, and write/execute scripts. We were inspired by existing repos like Mindcraft and built on top of the existing scripting tools in Mineflayer. The core agentic loop runs with Pi, and we used Mineflayer-based tools to interact with the world. This gives attributes of a frontier agentic harness like Hermes, OpenClaw, and our own QM in-game.

As far as anyone is aware, disaster has been averted: The hack was discovered by cybersecurity researchers who reported it to the PHP Foundation, and a patch was released before any bad actors got their hands on the exploit. However, PHP2Shell may be the canary in the coal mine, serving as a warning sign for what’s to come in the age of AI.
“One of the things we’re witnessing now is that all the legacy software that was written by humans over the last 40 years is being exposed,” says Matt Suiche, AI security research lead at the cybersecurity startup Tolmo. “Now it is time for the technical debt to be paid off.”
PHP Legacy Bug and Memory Errors
PHP, which originally stood for “personal home page,” is a programming language created back in 1994 and largely used by legacy sites. The bug underlying the PHP2Shell vulnerability was reported to the PHP Foundation as far back as 2024. The bug caused a common type of issue called an out-of-memory error, in which the amount of memory allocated to a piece of data is too small to hold the data. Normally, this type of error causes the program to crash—an unpleasant but not inherently dangerous result. And so the bug remained unaddressed.
“If you look at any at any point of time, there will be a bunch of bug reports that are waiting to be fixed, which are just crashes. Most people don’t take them very seriously,” says Suman Jana, an associate professor of computer science at Columbia University.
“It’s just that it’s a lot of very specific reasoning that is painful to do. And AI, I think, has done a very good job at that.” –Suman Jana, Columbia University
Earlier this year, the cybersecurity firm Calif offered to independently audit PHP, sponsored by OpenAI. Within two weeks, a researcher at Calif, aided by AI tools, found a way to use the out-of-memory bug to run arbitrary code on the host server, allowing a malicious actor to install malware or read critical data. Now, it was no longer a minor bug—it was a critical vulnerability, and the Calif team alerted the PHP foundation to start working on a patch immediately.
Jana says actually exploiting the bug requires carefully working out a way to jump to a specific point in the memory for a particular program running on the server, and work out exactly which bits to overwrite in what order to gain control of the system. “It’s not really rocket science,” he says. “It’s just that it’s a lot of very specific reasoning that is painful to do. And AI, I think, has done a very good job at that.”
To be clear, the researchers at Calif (as well as OpenAI and Wiz, a cybersecurity company that confirmed and expanded the vulnerabilities) had deep knowledge of both cybersecurity and the PHP language. “I’m not claiming that AI can do it all by itself. It clearly cannot,” Jana says. “But it is improving a lot, so the top 0.1 percent [of experts] can get a lot more stuff done, and also just below the 0.1 percent now will be able to go there without understanding all the nitty-gritty details.”

“There is a fundamental asymmetry in finding bugs and fixing bugs,” Jana says. “Because when you’re fixing bugs you have to make sure that you know all parts of that attack are closed, and also that you don’t break any existing functionality.”
This asymmetry puts a lot of strain on the defenders, especially for open-source software such as PHP. Maintaining open-source projects that don’t have clear revenue streams despite being widely used is a long-standing challenge that precedes AI hacking tools. But those tools make the issue more pressing than ever.
One way to stay ahead of such issues going forward is to empower the defenders with more money and access to frontier cybersecurity AI models. “These frontier labs are donating some of their token budgets to look into these bugs, which I think is great,” Jana says. “I think that should happen more, either through some concerted effort or through donations.”

Linux on the Nvidia RTX Spark Laptop: What Actually Works
A hands-on look at dual-booting Linux on the Nvidia RTX Spark laptop, the GPU clock throttling bug found, and why WSL still wins.
Can you run Linux on the Nvidia RTX Spark laptop?
Yes, but it comes with a serious catch. Linux installs and runs on RTX Spark laptops like the MSI Prestige N16 Flip AI Plus, including GPU acceleration through Nvidia’s open kernel driver. The problem is clock speed: once the laptop is plugged into wall power, the GPU gets locked to roughly 780 MHz on Linux instead of the 2 GHz-plus it hits on Windows. That turns a chip capable of around 65 tokens per second on a 120 billion parameter model into one struggling to break 14 tokens per second, for reasons tied to power management firmware that Linux currently can’t read.
TL;DR
- Dual-booting Linux works on the MSI Prestige RTX Spark laptop, with a full desktop, GPU acceleration via Nvidia’s open driver, 4K output at 120Hz, and working audio, keyboard, and touchpad once configured correctly.
- A hidden Windows-only component called the Nvidia Platform Controllers and Framework manages power delivery between CPU and GPU, and it has no Linux equivalent, which is the root cause of the slowdown.
- GPU clock speed collapses to about 780 MHz on Linux when plugged in, compared to roughly 2.2 GHz on Windows, because the firmware’s power table is encrypted and only the Windows driver can decrypt it.
- Benchmarks on GPT-OSS-120B show the gap clearly: Windows hit 65.4 tokens per second, WSL hit 65.1, the Nvidia DGX Spark hit 61, and native Linux on the same laptop managed only 13.9.
- Memory allocation is a separate headache, since the laptop reserves 96GB of unified memory for the GPU by default and only Windows exposes a setting to change that split, which is required before Linux can see more than a sliver of RAM.
- WSL (Windows Subsystem for Linux) is the practical middle ground today, since it rides on the Windows driver stack and keeps full GPU boost whether the laptop is plugged in or on battery, while still running Linux-first AI tools like vLLM.
- A real fix depends on Nvidia, specifically on porting the platform controller’s power management logic into its Linux driver, which would effectively turn the laptop into a portable version of the DGX Spark.

What makes the RTX Spark laptop different from a normal Windows PC?
The RTX Spark platform, which ships in machines like the MSI Prestige, the Asus ProArt, and the Dell XPS, uses the same GPU design as Nvidia’s DGX Spark desktop unit. But where the DGX Spark ships with Nvidia’s own Linux build out of the box, every one of these laptop variants ships with Windows on ARM.
That distinction matters because Windows on ARM with CUDA support is new. ARM-based Windows machines have existed for a few years, but pairing that architecture with Nvidia’s CUDA stack only became possible with this chip. The laptops also support unified memory configurations up to 128GB, shared between CPU and GPU, which is unusual for a laptop and central to why they’re being marketed at AI developers in the first place.
Because so much of the AI tooling ecosystem, including vLLM and SGLang, is built Linux-first, developers who buy these machines naturally want to know whether they can ditch Windows, or at least dual-boot, without losing performance.
How do you actually install Linux on it?
The process is not plug-and-play. A first attempt using Omarchy (a Linux distribution with Arch roots) failed because, while it already supported the chip on Asus and Dell hardware, the MSI Prestige behaved differently, producing a flickering, unstable display during boot.
Switching to Debian worked more reliably, but still needed workarounds. The installer couldn’t connect to Wi-Fi, so installation required a USB Ethernet adapter. Out of the box, Debian also didn’t recognize the keyboard, touchpad, or GPU, because none of the laptop-specific hardware support was present in a vanilla kernel.
Going back to Omarchy solved the driver problem, since its kernel already bundled Nvidia’s open-source driver. At that point Linux booted properly, but could only see 28GB of the laptop’s 128GB of unified memory. That’s because the laptop’s firmware reserves 96GB for GPU use, and that split is only adjustable from Windows. Dropping the Windows-side GPU memory reservation down to 4GB freed up 120GB for Linux to see once booted. After that adjustment, the laptop ran a full desktop at 4K and 120Hz, with working audio, touchpad, keyboard, and CUDA acceleration.
Getting video output over HDMI during the install process was its own obstacle. Early in the process, the laptop would only display video on its own internal screen, not over HDMI, which required pointing an external camera at the laptop’s screen just to see what was happening during remote-controlled installation steps.

OpenCode+Docker+GitHub Actionsで全自動AIペネトレーションテストはじめました
はじめに
Zennチームのdyoshikawaです。
ZennではAIによるセキュリティチェックの仕組みを急ピッチで構築しました。現在はPull Request（以下PR）ごとのAIレビューに加えて、AIエージェントによる全自動のペネトレーションテストを毎週GitHub Actionsで回しています。
背景は、みなさんもご存知のとおり昨今のサイバー攻撃の激化です。
攻撃する側もAIをフル活用しはじめているといわれており、脆弱性が見つかってから悪用されるまでの時間が非常に短くなっています。防御側としては、人間が定期的に診断する従来のやり方では攻撃に追いつかない時代になってきました。
本記事では、ZennでどのようにAIセキュリティレビューと自動AIペネトレーションテストを回しているかを紹介します。特別な製品は使っておらず、GitHub ActionsとDocker、OSSのツールを組み合わせて作っています。何かお役に立つものがあれば幸いです。
まずはPR単位のセキュアコードレビューを整備
最初に取り組んだのは、PRごとのAIレビューです。
PRがReady for reviewになると、GitHub ActionsがAIエージェントを起動します。エージェントは差分と周辺のコードを読み、コード品質に加えてセキュリティとコンプライアンスの観点でレビューします。結果はPRのコメントとして投稿されます。
AIによるPRレビューのコメントの例
モデルが非常に低コストなので、1回のレビューにつき$0.01〜$0.1程度で済みます。
エージェントにはOpenCodeを使い、セキュリティレビューの観点はSkillとしてリポジトリに置いています。手元のコーディングエージェントからも同じSkillを呼び出せるので、PRを出す前にClaude Codeなど手元のツールでローカルからレビューすることもできます。
なお、PRレビューのエージェントも後述するペネトレーションテストと同じDockerのサンドボックスとネットワーク隔離の中で動かしています。
また、レビュー中にWeb検索が必要な場面では、OpenAIのWeb検索ツールをAPI経由で使っています。OpenCodeにも組み込みのWeb検索ツールがあり、ExaまたはParallelを使ってAPIキーなしで検索できます。
ただ、Exaのプライバシーポリシーには、送信された検索クエリをモデルの学習やファインチューニングを含む製品の改善に使うと書かれています。検索語にはレビュー中の文脈が入りうるので、学習に使われることは避けたいところです。そこで、組み込みのWeb検索は使わず、OpenAIのAPIを使うようにしています。
こうしたWeb検索のAPIを呼び出すCLIを、webseekとしてOSSにもしています。OpenAIのResponses APIの web_search などを、複数のプロバイダーで共通のインターフェースから呼び出せるツールです。検索ごとに使ったトークン数と推定コストも出力されます。
サンドボックスとWeb検索の制限は、どちらも詳しくは後述します。
レビューの過程と結果をGitHub上に残したかった
外部のAIレビューサービスを使う選択肢もありました。それでも自前で作ったのは、レビューの過程と結果をGitHub上に残したかったためです。
結果はPRのコメントとして残るので、後から「このPRで何が指摘されたか」を追えます。実行のログはGitHub Actionsに残るので、どのような観点でどのファイルを読んだのかも確認できます。レビューの観点もSkillとしてリポジトリで管理しているので、観点の変更そのものをPRでレビューできます。
AIはレビュー結果をファイルに書くだけで、コメントの投稿はGitHub Actionsのstepが行います。AIのコンテナにはGitHubのトークンを渡していません。この「AIには書かせるだけ、外への操作は決まった処理で行う」という形は、後述のペネトレーションテストでもそのまま使っています。
Fireworksのオープンウェイトモデルを活用
モデルはFireworks AI上のオープンウェイトモデルを使っています。PRのたびにレビューを回すので、1回あたりのコストはできるだけ下げたいところです。
モデルの選び方やコストについては、以前の記事で詳しく紹介しています。
実際のコストは、PRコメントや週次検査のIssueの末尾に毎回載せています。たとえば、ある週の全体を対象にしたペネトレーションテストでは、1億以上のトークンを使って、OpenCodeのコストは$3.02でした。コストだけの話でいうと、その気になれば毎日でも回せそうです（人間の対応が追いつくかは別として……）。
OpenCodeのトークン使用量とコスト
Fireworks AIは明示的なオプトインなしに入力データをモデルの学習に使わないとしています。レビューではソースコードを送るので、ここは導入前に確認しておきたいポイントです。
さらにAIによる全自動ペネトレーションテストの構築へ
PRレビューが回るようになったので、次は実際にアプリを動かして攻撃を試すペネトレーションテストに取り組みました。
毎週、GitHub Actionsの1つのジョブの中で上の流れを実行しています。AIが動くのは試験の部分だけで、依存関係の監査、アプリの起動、テストデータの準備、Issueへの集約は決まった処理で行います。
試験の範囲として、直近の変更を中心に見る「差分」と全体を見る「全体」の2種類を用意しています。
なぜAIによるペネトレーションテストが必要か
PRレビューは差分を読むので、変更の中に入った問題を見つけるのは得意です。一方で、実際に動かさないとわからない問題もあります。
代表的なのは認可の不備です。たとえば「有料のChapterを買っていない人が本文を取得できないか」「Publicationを抜けた人が非公開の内容を見られないか」といった問題は、実際にユーザーを用意してリクエストを送らないと確かめにくいです。複数の変更が組み合わさって初めて起きる問題や、レスポンスヘッダーやリダイレクトのようにコードを読むだけでは気づきにくい問題もあります。
こうした問題は、外部の診断を定期的に受けるのが一般的だと思います。ただ、毎週のように受けるのは現実的ではありません。そこで、AIエージェントに実際にHTTPリクエストを送らせ、毎週自動で試験することにしました。
AIエージェントには試験用のユーザーとデータの組み合わせを順に試させています。OpenCodeの上で動くAIエージェントは、次のツールを使えます。
curlでは、ユーザーごとの認可を1件ずつ確認します。
nucleiでは、Zenn向けに自作したテンプレートで、開発用APIの露出やセキュリティヘッダーの不足などを確認します。
OWASP ZAPでは、spiderとactive scanで広く確認します。
Playwrightでは、ヘッドレスブラウザでXSSやopen redirectを確認します。
ペネトレーションテストでもオープンウェイトモデルを使う
ペネトレーションテストのAIエージェントにも、Fireworks AI上のオープンウェイトモデルを使っています。コストのほかにもう1つ理由があります。米国のクローズドモデルと比べて、セーフガードがゆるいことです。
ペネトレーションテストでは、AIエージェントに攻撃者と同じ操作をさせます。米国のクローズドモデルでは、こうした操作を断られることがあります。実際、このペネトレーションテストの仕組みを作る作業そのものを、手元のClaude Codeに断られたことがありました。
だからこそ攻撃する側に使われているのだと思いますが、防御する側も使わない手はありません。
Dockerでサンドボックスとネットワーク隔離を実現
AIエージェントに攻撃者役をやらせるとなると、エージェント自身が暴走したときのことを考える必要があります。認証情報を持ち出す、テスト対象以外を攻撃する、といったケースです。
プロンプトで「テスト対象以外にリクエストしないでください」と指示することはできます。ですが、プロンプトの指示はあくまでお願いです。そこで、DockerでAIが到達できる宛先そのものを絞ることにしました。
コンテナごとにネットワークだけを持つコンテナを用意してnetwork namespaceを共有させ、そのコンテナのiptablesでデフォルト拒否にしたうえで必要な宛先とポートだけを許可することで、ネットワーク境界を作っています。AIエージェントから外への通信はAIゲートウェイのコンテナを経由する経路だけで、その先も許可したAIプロバイダーのAPIに限っています。以下はイメージを伝えるために簡略化した例です。
services:
ai-agent-network:
image: firewall
cap_add: [NET_ADMIN] # firewallを設定するコンテナだけが持つ
healthcheck:
test: ["CMD", "test", "-f", "/run/network-ready"]
ai-agent:
image: ai-agent
network_mode: service:ai-agent-network
cap_drop: [ALL]
security_opt: ["no-new-privileges:true"]
depends_on:
ai-agent-network:
condition: service_healthy
実際に処理を行うコンテナにはcapabilityを渡さないので、AIエージェントが自分でfirewallを書き換えることはできません。
AIエージェントが通信できる先は、試験対象のローカル起動のAppサーバーとAIゲートウェイだけです。AIゲートウェイは、LLMのAPIへのリクエストを中継する、Node.jsで書いた小さなプロキシです。LLMのAPIキーはゲートウェイだけが持ち、AIエージェントにはダミーの値を渡しています。DBに直接つないだり、外部にデータを送ったりはできません。
Web検索もこのゲートウェイを経由します。OpenAI APIのWeb検索ツールだけを許可し、検索語にURLや長いトークンのような文字列が含まれる場合は拒否しています。コードや内部の情報を検索語に含めないよう、プロンプトでも指示しています。
このサンドボックスとネットワーク隔離は、前述のPRレビューでも共通です。PRレビューではアプリを起動しないので、AIエージェントが通信できる先はAIゲートウェイだけになります。
ほかにも、エージェントが実行しようとするコマンドをAIの分類器で審査しています。こちらは後ほど詳しく紹介します。
GCSやBigQueryはOSSエミュレータを活用
試験対象は本番環境ではなく、GitHub Actionsのrunner上に立ち上げたZennです。
ZennのbackendはGoogle Cloud StorageやBigQuery、Stripeなどの外部サービスとつながっています。これらはOSSのエミュレーターに置き換えています。
こうすることで本物の外部サービスに一切つながない状態で試験できます。AIが有料のAPIを叩いてしまう心配もありません。
もともとローカルの開発環境で使っていたものなので、そのほかにペネトレーションテスト用に改修したものはほとんどありません。開発環境をDockerで整えているプロダクトなら同じように流用できると思います

チームみらいの安野貴博党首は11月3日、同党の公式YouTubeチャンネルでの生配信で、海外で開発されたオープンウェイトモデルが国内で稼働する際、意図的に自身の性能を低下させたり、データを漏えいさせたりする可能性があると指摘し、国産モデルの必要性を強調した。

Introducing Adaptive Dark Mode

You can try it today in Safari 27.3 beta. To enable, first make sure your system appearance is set to dark. Then browse to a website with a bright background. Safari will offer a preview of Adaptive Dark Mode. Tap ‘Try’.
For websites that signal support of dark mode with <meta name="color-scheme" content="light dark"> in HTML or color-scheme: light dark in CSS, Adaptive Dark Mode does not change a thing. For the rest of the web, it quickly analyzes the page, looking at colors and estimating whether it’s predominantly light or dark. If the page generally has a dark background with light text, nothing is changed. When a page has a light appearance, Adaptive Dark Mode adapts the page to be dark.
How does Adaptive Dark Mode work?
At the core of Adaptive Dark Mode is the transformation of color. Sometimes colors are simply decorative, while other times they have semantic meaning. Adaptive Dark Mode determines when to invert colors so elements remain visible or when to leave colors unchanged.
While creating Adaptive Dark Mode, we developed a color matrix to invert the luminosity of colors while preserving hue. It’s used to make light backgrounds dark, and dark text light. When transforming text color, Adaptive Dark Mode aims for sufficient contrast as defined by the WCAG 4.5:1 contrast ratio. Light CSS gradients are also transformed to dark.
Adaptive Dark Mode makes careful judgments so transformed content looks good and stays usable: buttons have contrast against backgrounds, text is visible over images, and hover menus look clear.
It takes the same care with images. Most are left unchanged, preserving their integrity. But many icons and logos can lose contrast when the background color behind them is inverted. So Adaptive Dark Mode inspects SVG images and transforms colors when needed. For bitmap images, it analyzes the pixel histograms and inverts simple black-and-white logos.
Effects like masks and mix-blend-mode can create undesirable results on an element whose colors have been transformed, so in some cases Adaptive Dark Mode turns such effects off. Also, <canvas> content is left unchanged, since canvases contain a wide range of content that’s hard to predict.
It’s precisely because Adaptive Dark Mode is happening deep within the WebKit browser engine that we are able to find creative ways to solve the most complex challenges, apply the transformations with great speed and power efficiency, all while rigorously protecting user privacy.

日本語プログラミングフォント「Cyroit」とその姉妹フォント8種が11月3日（日本時間）、一斉にアップデートされた。「Cyroit」はv5.0.0、それ以外の8種はv3.0.0となっている。
「Cyroit」（しろいと）は、日本語環境でのコーディングに適した等幅フォント。ラテン文字に日本人プログラマー向けフォントの先駆「Ricty」でも用いられていた「Inconsolata」、仮名・ギリシア文字・キリル文字に「Circle M+ 1m」、漢字に「BIZ UDゴシック」を主にかけ合わせており、日本語のコメントが混じったソースコードでも可読性が高い。
また、全角英数記号や半角カナなどにアンダーラインが引かれているのが特長。全角と半角が混在した括弧や、誤って使われた全角チルダなどをすぐに見つけられる。OpenTypeの［calt］を利用したカーニング機能も備えており、文字の送り幅を等幅に保ちながら、前後の文字に合わせてラテン文字の見た目の間隔が調整される。コーディング向けフォントでありながら、縦書きに対応しているのもユニークだ。
今回のアップデートでは、スタイルセット［ss16］を有効にした際、基本ラテン文字と形の似たギリシア文字やキリル文字などにも判別マークが表示されるようになった。［ss16］は、ラテン文字と見分けにくい文字に判別マークを表示するOpenTypeの機能で、利用にはエディター側で機能を有効化する必要がある。また、OBJECT REPLACEMENT CHARACTER（U+FFFC）のグリフが変更された（「Roroit」を除く）。
そのほかにも、新しいスクリプトでグリフの輪郭線上の不要なポイントが削除された。また、実用上は問題になっていなかったものの、グリフを加工する際に生じた亀裂やヒゲ状の輪郭線も取り除かれている。なお、「Roroit」ではギリシア文字の一部のグリフをUnicode標準に近い形へ変更したほか、一部のギリシア文字のグリフが消失していた不具合も修正された。
また、以下の姉妹フォントでも同様のアップデートが実施されている。

- Roroit（ろろいと）：「Roboto Mono」と「Noto Sans Mono」を合成
- Soroit（そろいと）：「Source Code Pro」と「Hasklig」を合成
- Ubroit（うぶろいと）：「Ubuntu Mono」を合成
- Viroit（ゔぃろいと）：「Victor Mono」を合成

総務省が10月30日に公表した電波の利用状況調査によると、2026年3月末時点のドコモの5G基地局数は5万8979局だった。KDDIグループ（沖縄セルラー電話、UQコミュニケーションズを含む）の13万1042局、ソフトバンクの12万564局と比べ、半分以下にとどまる。ドコモは2026年度上期（4〜9月）に新たに4500局を構築し、9月末時点の累計は6万3300局となった。
基地局数が他社より少ない理由を質疑応答で問われた前田氏は、「数を増やしていきたい」と述べる一方、工事の対応能力などには限りがあると説明した。通信量が毎年20％以上増える中、「優先順位をつけて設備投資をいかにスピーディーにしていくかが大変重要だ」と強調した。

無印良品、クレカ「MUJI Card」カード番号全ケタ、約109万件漏えいか 不正アクセスで続報
「無印良品」を展開する良品計画（東京都文京区）は11月4日、10月30日に公表した公式アプリ「MUJIアプリ」への不正アクセスについて、当初は対象外としていたクレジットカード情報や氏名、住所なども外部からアクセスされた可能性があると発表した。新たに判明した対象には、クレジットカード「MUJI Card」のカード番号全桁を含む会員情報約109万件などが含まれる。
MUJI Cardは、クレディセゾン（東京都豊島区）が発行するクレジットカード。今回対象となった約109万件は、2021年7月までに入会した会員の情報で、カード番号の全桁、MUJI Card ID、生年月日が含まれる。このうち、現在も有効なカードは約34万5000件で、残りは失効・解約済みという。カード名義や有効期限、セキュリティコードは含まれないとしている。
同社によると、21年7月以前はMUJI Card会員に独自の特典を付与するためカード番号などを取得しており、その情報が現在もシステム内に残っていたという。クレディセゾンは不正利用の監視を強化しており、希望者はカードの再発行を申し込めるという。
一方、10月30日に公表した最大約2726万件の顧客情報についても、対象者や情報の種類が広がった。当初はMUJIアプリ利用者のメールアドレス、生年月日、性別の3項目を対象としていたが、その後の調査で、アプリを利用していないネットストア会員も含まれることが判明。対象項目には会員IDも加わった。また、最大約2726万件のうち約52万件には氏名、住所、電話番号も含まれることが分かった。
この他、MUJIアプリや無印良品ネットストアにクレジットカード情報を登録していた利用者約120件分についても、外部からアクセスされた可能性がある。対象の情報はカード番号の先頭6桁と末尾2桁、カード名義としている。
良品計画は対象者にメールや郵送で順次連絡する方針。また、利用者に対して、カードの利用明細を確認し、身に覚えのない請求があればカード発行会社に問い合わせるよう呼び掛けている。
なお、現時点でダークウェブなどへの情報流出や、悪用による被害は確認していないという。MUJIアプリと無印良品ネットストアは通常通り利用できる。同社は引き続き、原因や影響範囲の調査を進める。

目的
ソフトウェア企業において、優秀なテストエンジニアがどのような特性（知識、スキル、思考プロセス、モチベーション、個人特性など）を備えているのかを明らかにすることが目的です。マネージャーやテストエンジニアが重要視する貢献（質の高いバグレポートなど）も含めて調べています。
調査の対象
調査対象は設立10年以上で財務的にも安定した成長を達成している中規模ソフトウェア企業3社です。3社に勤めていて、稼働中のソフトウェアで不具合を検出・報告するすべての従業員をテストエンジニアとしています。1社は専任のテストチームに所属するエンジニア、専任のテストチームが存在しない2社では、カスタマーコンサルタントや開発者、サポート担当者です。
データ収集と分析
各社のバグトラッキングシステムの初期分析を行い、バグ検出数が多いテストエンジニアを選びました。選んだテストエンジニア3名と開発マネージャ1名（各社4名、計12名）に対してインタビューを実施しています。
バグ報告ガイドラインや組織図の分析、継続的な対話によりデータを裏付けられるようにし、体系的に分析しました。
調査結果
分析の結果、優秀なテストエンジニアの特性は大別して、経験とスキル、リフレクション（内省力）、モチベーション、個人的特性となりました。以下、順番に説明します。
経験とスキル
従来のテストケース設計技法やテスト計画スキル以上に、ソフトウェアが対象とする業務プロセスや利用状況の理解（ドメイン知識）、および製品の仕様・構造の把握が重要とされました。仕様書などのドキュメントが不十分な現場において、ドメイン知識はテストの期待結果として不可欠となります。
- 専門的技術とテスト自動化
性能テストや分散システムのテストなどの専門技術に加え、テスト自動化の設計・実装スキルが高く評価されました。同じ手動テストを繰り返さないという姿勢も特徴として見られました。
- コミュニケーション能力
製品への適切な批判や意見表明、および明確で再現性の高い優れたバグレポートの作成が不可欠とされています。
リフレクション(内省力)
- 全体像を常に把握
システム全体の構造やユーザーの目的を見失わずに把握する能力です。これにより、限られた時間の中で最も重要な部分にテストの焦点を当てることが可能になります。
- 本番環境における影響理解
発見したバグが本番環境で及ぼす影響を予測・評価する能力であり、バグの優先順位付けやテスト工数の最適化につながります。
モチベーション
- テストへの肯定的な姿勢
バグを見つけることが好きという考えやテストの重要性に対する強い認識を持っています。
- ユーザー視点からの責任感
ユーザーデモやトレーニングを担当するなどユーザーとの接点を持つテストエンジニアは、本番での障害によるユーザー損失や自らの失敗に対する恐れ・責任感が強力なテストの動機となっていました。
個人的特性
- 徹底性と細部へのこだわり
優秀なテストエンジニアの個人特性として、徹底していること、細心さ、忍耐力・持続性、正確さが共通して挙げられました。
- 批判的思考と自律性
批判的な思考力や自律性、想像力・創造性も重要な資質として評価されています。
ユーザー視点、細部へのこだわりといった点が挙げられていました。他のテストエンジニアのテストを見ることで、これが具体的にどのようなものか新たな視点を得ることもできそうです。

マッキンゼーの委託調査を集めると22本、合わせて2,446ページありました。経産省が18本、国税庁が3本、内閣府が1本。量が量なので、AIに全ページを1ページずつ見た目の形で分けてもらい、数えています（迷ったページは大きくして確かめました）。
では見ていきましょう。
2,446ページは「7つのパターン」に集約された
これ、「50パターンくらいあるのでは？」と思った人もいるんじゃないでしょうか？
蓋を開けたら実はたったの7つ。
いちばん多いのは表。2軸マップのような「コンサルっぽい」フレームワークの図は、60ページしかありません。
これは過去に近い企画でデロイトでも調査したんですが、同様に派手な図解の比率はすくなく、地味な表が大部分を占めていました。（デロイトは45％、マッキンゼーは33％）
私は次のように解釈をしています。 一流の資料力って、引き出しの多さじゃない。1つの引き出しを、どこまで深く使い倒せるかなんだろう、と。
では7位から見ていきます。（順位は出現頻度です）
7位｜ロードマップ（38ページ・2%）
いちばん少なかったのは、時間の流れで計画を見せるパターン。
型⑫：ロードマップ
時期の矢羽根の下に対象ごとの行を並べ、いつ何をするかを1枚で見せる型です。
お酒の調査（国税庁・令和4年度）のページ。上に短期・中期・長期の矢羽根、左に「ありたい姿」と顧客の層4つ。マスの塗りの濃さで、時期ごとの日本酒の浸透度（低・中・高）を見せています。
計画の表に濃淡を足すだけで、どこから力を入れるかが見える。
6位｜フレームワーク（60ページ・3%）
いわゆる「コンサルのフレームワーク」。数は少なくても、狙いを描く・位置で決める・分けて考える、というコンサルの考え方がいちばん表に出るパターンです。数字を描いた図でも、狙いを描き込んだ面積図や、象限で動き方を決める2軸マップは、こちらに数えています（主役が、数字そのものより考え方だから）。
型⑪：攻め筋の面積図
市場を面で描いて、その上に「どこを狙うか」を描き込む型です。
お酒の調査（国税庁・令和3年度）のページ。横が顧客の層、縦が飲む場面で、面積がそのまま市場の大きさ（マリメッコと呼ばれる面積図）。その上で、狙う区画を色の枠で囲み、番号と太い矢印を置いています。
市場全体の中での狙いの位置と大きさが、1枚で見える。いちばん「戦略コンサルっぽい」ページで、面積図は5本の報告書に出てきました。
型⑩：2軸マップ
2つの物差しで並べ、どこを優先するかを位置で決める型です。
ヘルスケアの海外展開の体制づくりの調査（経産省・令和4年度）のページ。アフリカの国々を、1人当たりの医療支出（縦）とビジネス環境の指数（横）で並べ、泡の大きさで人口を見せています。外側には、象限ごとの動き方。
置いた国を見るだけで、どこから攻めるかの話ができる。タイトルは、次に狙う候補（ケニア・ナイジェリアなど）まで名指ししています。
型⑨：分解ツリー
全体を、漏れなく重ならずに分けていく型です。
地方創生とSDGsの調査（内閣府）のページ。全体の1,154件を、「SDGsに関連する事業をしているか」「SDGsを知っているか」の2つの問いで枝分かれさせ、末端の4つの箱に件数と割合を書いています。いちばん大きいのは、SDGsを知らないまま関連する事業をしている層で、590件（51%）。
どの事業者もどこか1つの層に入るので、層ごとの打ち手をそのまま並べられる。
5位｜○×比較（80ページ・4%）
比べる物と観点を表にして、マスに印を付けるパターンです。
型⑧：評価表
マスに文字を書かず、印の濃さで評価する表です。
お酒の調査（国税庁・令和4年度）のページ。行は英国で日本酒を広めるための鉄則5つ、列は顧客の層4つ。マスにはチェックの丸を3段の濃さで置き、層ごとの相性を見せています。
どの鉄則がどの層に効くかが、丸の濃さだけで分かる。業者や案を選ぶ表に、そのまま使えます。
4位｜絵解き（206ページ・11%）
アイコンや絵で、仕組みや構造を見せるパターン。
型⑦：比喩の図
氷山や道のような絵1枚で、構造を一望させる型です。
医療の海外展開の調査（経産省・令和3年度）のページ。右に氷山の絵を置き、水面の上に「行動」、水面の下に「感情・思考」「価値観・信念」「ニーズ」と書いています。
絵の部位に意味のラベルを付けると、見えている物と隠れている物を1枚で分けて見せられる。比喩の図は、22本のうち7本の報告書に出てきました。この型のプロンプトは、この後のおまけに置いています。
型⑥：現状とあるべき姿
左に現状、右にあるべき姿（実物のページでは「目指す姿」）。同じ登場人物を、左右の両方に置くのがコツです。
中小企業のAI活用の調査（経産省）のページ。左の現状では、企業・AI人材・ITベンダーを結ぶ線に×が付き、疑問の吹き出しが浮かんでいます。右の目指す姿では、同じ登場人物が矢印の輪でつながり、下の台座に3つの打ち手。
タイトルは、その3つの打ち手を名指しして、何が変わるかまで言い切っています。
3位｜個票（377ページ・21%）
1つの対象を1枚にまとめ、全部を同じ形で並べるパターンです。国ごと、商品の案ごと、事例ごと。前回のデロイトの数え方には無かった、今回新しく立てたパターンです（代わりに、前回の7つにあった中扉は、今回は数える前に除いています）。
型⑤：個票（顧客像）
選んだのは、個票の中でも顧客の個票。1人ごとの個票の次に、その人の気持ちの上下のページが続きます。
お酒の調査（国税庁・令和4年度）のページ。英国の消費者を層に分け、層ごとに1人の人物を立てています。いちばん上に本人の本音を大きく、左に名前と年齢と層の名前、右によく飲む場面・日本酒を飲まない理由・売れる見込みを、全員同じ位置に置いています。
次のページは、店を選んでから帰るまでの気持ちの上下（カスタマージャーニー）。気持ちがいちばん下がった「日本酒の正しい飲み方を知らなかった」場面の下には、「テイスティングを勧める」といった酒蔵の打ち手が並びます。
顧客の顔が浮かぶと、打ち手の話が急に具体的になる。営業でも採用でも使える型です（人物の写真は私が伏せています）。
2位｜グラフ（446ページ・25%）
目を引いたのは、グラフの形より、そこに足してある工夫。
型④：アンケート＋声
アンケートの数字の横に、回答者の声を添える型です。
企業をまたいだメンタリングの試み（経産省）の報告書のページ。左に満足度の棒（回答数も添えて）、右に参加者の声を吹き出しで3つ。タイトルは、「全員が満足」という結果と声の中身を、1文にまとめた物です。
数字で「どれだけ」、声で「なぜ」。研修やイベントの報告なら、そのまま真似できます。
型③：ひと工夫したグラフ
グラフに1つ2つ工夫を足して、見てほしい所を決める型です。
中小企業のAI活用の調査（経産省）のページ。左の折れ線の終わりから右の棒グラフへ線を引いてつなぎ、棒の差は「+14%」「+12%」の札で書き込み、折れ線の下に一言の注記を付けています。
見てほしい国だけ色を変える、目標の点を打つ、といった工夫もほかの報告書に出てきます。どれも、グラフを作った後から足せる物ばかり。
1位｜表（602ページ・33%）
そして1位が、表。図や表のページの3ページに1ページが、表でした。見どころは、表の中の組み立て方。
型②：仮説と検証
調べる前に仮説を書いておき、調べた後で答え合わせを見せる型です。
医療の海外展開の調査（経産省・令和3年度）のページ。左の白い側に調べる前の仮説、右半分の濃紺の側に調査で分かったこと。左右を同じ行数でそろえて、真ん中の楕円でつなぎます。濃紺の側に目が行くので、「答えはこっち」が一瞬で伝わる。
違っていた所が、そのまま次の打ち手になる。調べる前の考えを「仮説」と書いて示した報告書は、22本中8本ありました。
型①：論証テーブル
左から右へ読むと、結論まで1本の筋でつながる表です（前回の記事では、表のパターン全体をこの名前で呼んでいました）。
女性リーダーを増やすための調査（経産省）のページ。行は打ち手（昇進を速める・昇進の確率を上げる・社外の人材を使う）で、左から打ち手の中身→前提の数字→2030年の役員比率の順。最後の行には、比べる基準の「現状維持」を灰色で置いています。
いちばん右は「意味合い」の欄。どの打ち手も1つだけでは目標の30%に届かない、と表から言えることを文で書いています。
並べて終わりにせず、「だから何か」まで表の中で言い切る。
マッキンゼー資料に共通するページの骨格
もう1つ、数えていて気づいたことがあります。22本のうち、スライドで作られた18本（残りの4本はWordの文章）は、タイトルの書体が明朝の物もゴシックの物もあって、見た目はそろっていません。それでも、ページの骨格は報告書をまたいで共通していた。
全部見て分かった、細かい発見
- 自分の話は、後ろに回す。お酒の調査（国税庁・令和5年度）には、酒蔵が英国の売り先に見せる営業資料の見本（9枚）が付いていました。表紙の次に、名乗るのは1枚だけ短く。続く4枚は相手の市場（2枚）・商品・お客さんの声で、会社の歴史と実績は7・8枚目。最後の1枚は、取引先と一緒にこれから何をやるかです。
- 要旨は、図にせず文で書く。打ち手を提案する形の報告書のうち、スライドで作られた5本中4本は、表紙と目次のすぐ後に要旨を置いていました。4本とも図は無く、箇条の形でも、1項目を2〜3行の文で書いています。何を調べ、何が分かり、何をするか。この1ページで、報告書の筋が追えます。
- 本筋から外れるページは、消さずに印を付ける。タイトルの頭に「参考）」と付けたページが、9本の報告書で38ページ。国の資料でもよく見る印ですが、「消すか残すか」で迷ったページの置き場になります。忙しい読み手は、印の無いページだけ追えば筋がつかめます。
おまけ：比喩のスライドを作るプロンプト
型が分かっても、白紙から組み立てるところで手が止まりがちです。
