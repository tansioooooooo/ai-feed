Our Residential Proxy Observatory, launched earlier this week, is a first-of-its-kind interface that gives researchers a global view of residential proxy and anonymized internet activity.
While our team was looking through it, we noticed residential proxy exit activity on AS2650. AS2650 is registered to the Executive Office of the President, the federal agency that hosts the White House network. Residential proxy services sell access to everyday devices, letting customers send traffic through them so it appears to come from that device's network.
What we observed
From October 5 to November 3:
- Our residential proxy enumeration pipeline exited through the White House network 236 separate times.
- Those exits came from 6 addresses, on 26 of the 30 days.
- 28 separate residential proxy services were able to exit through this network.
To make sure this was not a fluke, we checked these addresses against other residential proxy detection services, such as Spur and Synthient. Their public IP context pages independently identify these addresses as residential proxy exits.
This is public access. Anybody can obtain it by signing up to a public residential proxy service, paying a few dollars and sending requests through it. We did not selectively target this network or try to make our probes exit from it. We caught this by chance, simply by requesting global rotating access through these services.
Why this is concerning
Most of the activity happens in the evening, Eastern time: about half of it falls between 5 p.m. and midnight, and almost none happens in the early morning. That pattern suggests a person rather than a public guest Wi-Fi network: someone regularly on the White House network late into the evening, whose device is infected with a proxy SDK. Our data shows the exits, not the device or the person behind them.
Past research has shown that poorly secured proxy SDKs can allow internal network access and lateral movement. This is how past botnets have spread. In A Broken System Fueling Botnets, the researchers at Synthient documented how the Kimwolf botnet reached at least 2 million devices, mostly Android devices with an exposed ADB service, through residential proxy networks. If an SDK on this network has the same kind of flaw, anyone buying proxy access could use it to reach internal systems.
No place is too remote
The White House is not the only surprise in the observatory. Residential proxies also reach some of the most isolated places on the planet.
Saint Helena, Ascension and Tristan da Cunha is the South Atlantic territory that includes the most remote inhabited island in the world. We recorded 413 addresses and more than 32,000 observations there, split between Starlink and the island's local internet provider, Sure Saint Helena.
We also recorded three observations from Antarctica. All of them come from a Cloudflare WARP address that points to McMurdo Station.
Other remote places with activity:
- Pitcairn: 1 Starlink address, 1 observation.
- Norfolk Island: 1 Norfolk Telecom address, 4 observations.
- Svalbard: 1 Starlink address in Longyearbyen, 3 observations.
- Also seen: the Falklands (388 addresses), the Chagos Islands (43), Tokelau (21) and South Georgia (7).
Residential proxies have infected every corner of the world, and it looks like there is no place they cannot reach. Layer3 Intel tracks residential proxy and anonymization infrastructure worldwide. Even when the proxies hide in networks on the farthest corners of the planet, we can still observe them, leaving threat actors no place to hide.

Security advisory: openssh-server password authentication bypass
If you run sshd on Alpine Linux, update openssh now and restart sshd.
Upgrading the package alone does not replace the running daemon.
If you cannot update yet, at least disable password logins: set
PasswordAuthentication no in your sshd configuration and restart sshd.
Either one closes the hole.
What is the problem?
An attacker who can reach your SSH port can log in without knowing any password. It takes one connection, works every time, and needs no retries.
The attacker needs the name of an account whose password field is *
(an account with no password set, which is normal for key-only accounts), and
needs the machine to have at least one other account with a $5$ or $6$
password hash. The attacker then sends a very long password (257 to 1024
bytes). One user with a password is enough: it makes every account without
one reachable.
Details are in the OpenSSH 10.6p2 release notes. No CVE identifier had been assigned at the time of writing.
Who is affected?
You are affected if all of the following are true:
- You run the Alpine openssh-server package, which is built without PAM, or
you run openssh-server-pam with UsePAM no. (openssh-server-pam with UsePAM yes is not affected.)
- PasswordAuthentication is yes (the OpenSSH default, unless you changed it).
- The machine has an account whose password field is *. This includes:
- root, which ships as root:* in the base image since about Alpine 3.16.
OpenSSH’s default PermitRootLogin prohibit-password protects root, so
root is only reachable if PermitRootLogin yes is set. That does not help if
another account that can log in is able to become root, for example
through doas.
- Any key-only user created with adduser without a password, or with usermod -p '*'.
- Users coming from a directory service through musl-nscd (nslcd, winbind, sssd), since they have no shadow entry.
- The alpine user in the official tiny-cloud images (see below).
- At least one local account has a $5$ or $6$ password hash.
Affected releases: every Alpine release we checked, 3.21 through 3.24 and edge, and the older releases that no longer receive regular updates (3.16 to 3.20).
Who is not affected?
- Docker and other container users that do not run sshd in the
container.
- Systems with PasswordAuthentication no.
- Systems using openssh-server-pam with UsePAM yes (with UsePAM no you are affected).
- Locked accounts: those with ! as the password field in /etc/shadow (a line starting user:!:). They cannot log in with a password or a key.
- Systems where no account has a $-style password hash.
- Cloud images configured through cloud-init, which writes
PasswordAuthentication no.
How can I fix it?
1. Update
apk upgrade -U -a
Alpine 3.21.10, 3.22.8, 3.23.8 and 3.24.4 contain the fixed package (see the release announcement). The fixed package versions are:
Restart sshd after upgrading (rc-service sshd restart). Upgrading the
package does not restart a running sshd, so you must do it after.
2. If you cannot update: disable password authentication
Before you start, make sure your SSH key login works, and keep your current session open until you have tested a new login.
Run these as root. The first two commands create a drop-in file. Alpine’s
default sshd_config reads that directory from 3.19 onward; older releases
ignore it. The sed command changes yes to no on every
PasswordAuthentication line in /etc/ssh/sshd_config, whatever the spacing,
including lines inside a Match block. It also adds PasswordAuthentication no at the top of the file, for the case where there was no such line, and
saves the original as /etc/ssh/sshd_config.bak. The last two commands check
the configuration, restart the daemon, and show the result:
mkdir -p /etc/ssh/sshd_config.d
echo 'PasswordAuthentication no' > /etc/ssh/sshd_config.d/00-no-passwords.conf
sed -i.bak -e '1i PasswordAuthentication no' \
-e 's/^\(\s*PasswordAuthentication[^y#]*\)yes/\1no/i' \
/etc/ssh/sshd_config
sshd -t && rc-service sshd restart
sshd -T | grep -i passwordauthentication
The last command should print passwordauthentication no. To undo, delete
/etc/ssh/sshd_config.d/00-no-passwords.conf and copy
/etc/ssh/sshd_config.bak back over /etc/ssh/sshd_config.
Cloud images (tiny-cloud)
The official tiny-cloud images (the qcow2, VHD and AMI artifacts) from

Introduction
JavaScript Object Notation (JSON) is a simple data interchange format, the most popular data format used on the internet, and widely read and written by Go programs. Go has included support for JSON in the standard library since well before Go 1.0. We first wrote about support for JSON in Go more than 15 years ago!
Over time, packages evolve with the needs of their users, and encoding/json is no exception.
Last year, we wrote about a new experimental API for JSON designed to bring long-awaited improvements and fixes.
After additional feedback and refinement, the new encoding/json/v2 and encoding/json/jsontext packages are stable and generally available in Go 1.27!
This post is an updated version of the article introducing the experiment, describing the problems with encoding/json and introducing the new packages.
Problems with encoding/json
Overall, encoding/json has held up well.
The idea of marshaling and unmarshaling arbitrary Go types
with some default representation in JSON, combined with the ability to
customize the representation, has proven to be highly flexible.
However, in the years since its introduction,
various users have identified numerous shortcomings.
Behavior flaws
There are various behavioral flaws in encoding/json:
- Imprecise handling of JSON syntax: Over the years, JSON has seen increased standardization in order for programs to properly communicate. Generally, decoders have become stricter at rejecting ambiguous inputs, to reduce the chance that two implementations will have different (successful) interpretations of a particular JSON value.
- encoding/json currently accepts invalid UTF-8,
whereas the latest Internet Standard (RFC 8259) requires valid UTF-8.
The default behavior should report an error in the presence of invalid UTF-8,
instead of introducing silent data corruption,
which may cause problems downstream.
- encoding/json currently accepts objects with duplicate member names.
RFC 8259 does not specify how to handle duplicate names,
so an implementation is free to choose an arbitrary value,
merge the values, discard the values, or report an error.
The presence of a duplicate name results in a JSON value
without a universally agreed upon meaning.
This could be exploited by attackers in security applications
and has been exploited before (as in CVE-2017-12635).
The default behavior should err on the side of safety and reject duplicate names.
- Leaking nilness of slices and maps: JSON is often used to communicate with
programs using JSON implementations that do not allow null to be unmarshaled
into a data type expected to be a JSON array or object.
Since encoding/json marshals a nil slice or map as a JSON null,
this may lead to errors when unmarshaling by other implementations.
A survey
indicated that most Go users prefer that nil slices and maps
are marshaled as an empty JSON array or object by default.
- Case-insensitive unmarshaling: When unmarshaling, a JSON object member name is resolved to a Go struct field name using a case-insensitive match. This is a surprising default, a potential security vulnerability, and a performance limitation.
- Inconsistent calling of methods: Due to an implementation detail,
MarshalJSON methods declared on a pointer receiver
are inconsistently called by encoding/json. While regarded as a bug,
this cannot be fixed as too many applications depend on the current behavior.
API deficiencies
The API of encoding/json can be tricky or restrictive:
- It is difficult to correctly unmarshal from an io.Reader.
Users often write json.NewDecoder(r).Decode(v),
which fails to reject trailing junk at the end of the input.
- Options can be set on the Encoder and Decoder types,
but cannot be used with the Marshal and Unmarshal functions.
Similarly, types implementing the Marshaler and Unmarshaler interfaces
cannot make use of the options and there is no way to plumb options down the call stack.
For example, the Decoder.DisallowUnknownFields option loses its effect
when calling a custom UnmarshalJSON method.
- The Compact, Indent, and HTMLEscape functions write to a bytes.Buffer instead of something more flexible like a []byte or io.Writer.
This limits the usability of those functions.

Mozillaの開発陣は、ウェブブラウザーの「Firefox」を市場で最も実用的なブラウザーにすべく、機能改善を重ねている。その一環として追加された新機能が、現在ベータ段階にある「Mini Window」だ。筆者は同機能がFirefox Nightlyに搭載されてから試用しているが、その動作や完成度には大いに満足している。
ミニウィンドウ機能とは何か
Mini Window機能のコンセプトは極めてシンプルだ。現在開いているタブ全体、あるいはページ内の特定部分を切り離し、独立した小さな別ウィンドウへと移行できる。タブのウィンドウをウェブアプリのようなものへ切り替えるようなイメージだ。つまり、ブラウザーの要素を除いた純粋なウェブページやその一部のみを表示するウィンドウへ移せる。一見すると、アドレスバーや各種操作ボタン、スクロールバーなど、通常のFirefoxが備えるインターフェースは一切見当たらない。あたかもウェブアプリを構築したかのような表示を実現する。
ただし、カーソルをMini Windowの内部に移動させると、アドレスバーをはじめ、「戻る」「進む」「再読み込み」の各ボタンやウィンドウを閉じるボタンが現れる。必要な操作部だけが表示され、それ以外の要素は非表示に保たれるため、利用者はコンテンツの閲覧に専念できる。
さらに、Mini Windowは他のFirefoxのウィンドウよりも常に前面に表示される。そのため、別の作業を進めながら切り離したコンテンツを常に視界に収めておくことが可能だ。ノートPCをはじめとする画面スペースが限られた環境下で、別の作業をしながら資料ページを常時参照したい場面や、マルチタスクを効率化したい場面で大いに重宝する。
Mini Windowの使い方
Mini Windowの使い方は非常に簡単だが、正式提供まではFirefox Nightlyでのみ利用可能だ。筆者はすでにLinuxとMacOSの双方でFirefox Nightlyを既定のブラウザーとして常用しており、これまでのところ動作上の問題には遭遇していない。もちろん、動作環境によって挙動が異なる可能性はある。

Androidも正式スタート！ スマホとマイナンバーカードがますます近づく
2026年10月20日、Android端末にマイナンバーカードの電子証明書機能と属性証明機能が実装できる「Androidのマイナンバーカード」機能の提供が始まりました。これまでも電子証明書機能は組み込めましたが、属性証明機能の実装により、コンビニでの証明書の取得や、マイナ保険証として医療機関の窓口での提示に利用できるようになります。対応機種はデジタル庁のサイトで確認できます。
なお、iPhoneでは2025年6月からマイナンバーカードの両機能が使える環境が提供されています。利用者の数は、2026年9月時点でマイナンバーカード保有数全体の約9%にあたる980万人強。Androidでの実装により、今後この数字は伸びていくと予想されます。
マイナンバーカードという個人情報の塊がどんどんスマホに組み込まれているわけです。しかし、スマホはその高いセキュリティ環境ゆえに、持ち主が亡くなったときにロックが解除できずに相続や引継ぎに欠かせない情報を閉じ込めてしまう、という困った側面があります。
マイナンバーカードを実装したスマホの持ち主が亡くなったとき、どんな対応をするべきでしょうか。下取りに出すにしても、しばらく保管するにしても、正しい処理方法を知っておくに越したことはないはず。デジタル遺品を扱う当連載ではそこに注目しないわけにはいきません。
3年前の「第12回 マイナンバーカード機能を付けたスマホを手放すときは要注意！ デジタル庁に詳しく聞いてきた」でも同じテーマを扱いましたが、当時とはマイナンバーカード周りの整備のレベルが異なります。改めて追いかけていきましょう（iPhoneに関しては「第32回 マイナンバーカードを実装した故人のiPhone、スムーズに解約する方法は？ 確認してみた」を参照してください）。
基本は何もしなくてOKに……けれど
前提として掴んでおきたいのは、「スマホのマイナンバーカード」情報の保存場所です。
スマホのマイナンバーカードは「マイナアプリ」を通して、カード型マイナンバーカードとスマホを紐付けることで設定します。紐付けられたスマホには固有の「スマホ用電子証明書」が保存されるのですが、保存場所は一般的なストレージの中ではありません。「おサイフケータイ」等で使われる専用チップ（Androidの場合はFeliCa-SEチップ）という別のハードウェアに格納されます。
注意したいのはこの領域はスマホの一般的な初期化操作の対象外ということです。スマホの標準メニューでシンプルに初期化してしまうとデータが残存してしまうので、専用チップ内を消去したうえでスマホ全体を初期化しなければなりません。消去といえば、最近のAndroid端末では「おサイフケータイ」アプリ内でFeliCa-SEチップのデータをまとめて削除できます。しかし、この機能でもスマホ用電子証明書は検知されず、対象外の扱いとなっています。スマホ用電子証明書はいろいろと例外的な存在なのです。iPhoneでも基本的には同様です。
それでいて、手放す際はきちんと失効させなければなりません。デジタル庁は「法律上、機種変更や下取り・売却、廃棄、故障などによって、スマホ用電子証明書を登録しているスマートフォンの利用をやめるときは、利用者ご自身で電子証明書を失効（削除）させることが義務づけられています」と公式サイトに明記しています。では、どう消せばいいのでしょうか？
同庁が推奨するのは「死亡届による自動失効を待つこと」です。
マイナンバーカードの有効性は、同カードの開発と運営を担っているJ-LIS（地方公共団体情報システム機構）が管理しています。遺族や葬儀社等により死亡届が提出されると、48時間以内に故人のマイナンバーカードとマイナアプリは有効性を失い、専用チップ内のスマホ用電子証明書も自動で消失する仕組みです。
つまり、死亡届さえ提出されれば後は何もしなくてもよいということです。3年前の取材時には確立しきれていなかった部分がしっかり整備されたといえるでしょう。

3行まとめ
- 分析エージェントを開発するのはやめて、分析 MCP として作り直した
- AI エージェントの全てを開発するのは手間がかかりすぎる
- 良い分析体験のキモはエージェントが動く手前にある
分析エージェントから分析 MCP へ
もともと作ろうとしていたエージェントは、チャット UI で分析を依頼するとデータ取得・考察・結果の可視化までを担うものだった。
ところが AI エージェント全体を作ろうとすると自作しなければいけない構成要素が多すぎる。全てに注力するには時間がかかるし、限られた時間で多くのものを作ろうとすると一つひとつのクオリティは下がってしまう。
そこで今年の7月からは心機一転 MCP を作ることにした。事前集計されたデータを返したり、各データについての知識を的確に返すような MCP だ。
私たちの用途では MCP を作り込むので充分だという感触を得ている。汎用エージェント (Claude.ai など) に MCP を接続するだけで、基礎的なデータ分析を担うエージェントとして使えそうだ。
自作エージェントの守備範囲
分析エージェントは Google Agent Developer Kit (ADK) を使って作っていた。
ADK はマルチエージェントシステムを構築・デプロイするためのフレームワークで。サブエージェントを定義してタスク分担・オーケストレーションといったことを手軽にできるようになる。
とはいえ AI エージェントを自作するとなると賄わなければいけない領域は多岐にわたる。
- UI
- 認証基盤
- セッション管理
- メモリー
- サブエージェントのオーケストレーションルール
- アセットアップロード
- アップロードされたアセット管理
- スキルシステム
ざっと挙げただけでも、これらは自作する必要がある。
UI 以外は無くても分析エージェントとして成り立つものの。普段使っている Claude.ai, ChatGPT, Gemini などと比較してしまうと物足りないものになる。
メモリーという難所
特にメモリーが難しい。セッションをまたいでユーザーの関心事ややりとりの注意点を記憶させておく仕組み。
仕組み自体はシンプルだ、
- ユーザーとの会話から覚えておくべきことを抽出する
- なんらかのデータベースに情報を永続化する
- しかるべきタイミングでデータベースを検索し、適切に参照させる。
これだけ。
しかし「覚えておくべきことを抽出」「しかるべきタイミングで検索」「適切に参照させる」これらが奥深すぎる。
一応、 mem0 などのサードパーティ製の API を使って楽をすることはできる。が、開発者側でやるべきことはいくらか残る。
- 過去のメモリーを訂正する
- 過去のメモリーを忘却させる
などは実装側で工夫する必要がある。
最大の欠点は、ユーザーが普段使っている AI エージェントとの間でメモリーが共有されないことかもしれない。どれだけ良い AI エージェントを自作してもメモリーが引き継がれないことが乗り換えの障壁になりうる。
汎用エージェントに任せられること

一方で必要な部分だけ MCP 化して、残りを汎用エージェントにお任せするのは現実的なんだろうか。
私の場合、とてもうまく機能している。作り直した分析 MCP を接続することで、汎用エージェントが "分析エージェント化" した感覚だ。
データを表示する UI は手放しでも改善されていく。最近の Claude.ai は Claude Artifacts でインタラクティブな可視化もしてくれる。
認証基盤・メモリー・アセット管理・スキルシステムなども言わずもがな、普段の使い慣れた仕組みをそのまま分析業務にも活用できる。
これらの "備え付けられた" 便利な仕組みを捨ててまで自作エージェントをゼロから作る動機を私は見出せなかった。
分析の手応えとデータ基盤
では自作の分析エージェント作りは全くの無駄骨だったのか。実はそうでもない。
分析エージェントを作るなかで、分析業務に本質的に重要な部分と汎用の仕組みを活用するべき部分が見分けられるようになったからだ。
最初は『BigQuery の execute_sql ツールを AI に繋げば良い感じの洞察を語ってくれるのかな？』などと思っていた。
が、これは全然違った。当たり前のデータを渡すだけでは当たり前のことしか言わないのが AI だ。何の工夫もしなければ「朝晩は電車が混むようです」「冬はおでんが売れるようです」などのわかりきったことしか言わない。
むしろ、分析エージェントとして前進している感覚が得られたのは、
- 注目するべき指標をしっかり定義し、チームで合意したとき
- 注目するべき指標が日々事前集計されるよう仕組み化したとき
- 注目するべき指標が正確になるようにデータの収集方法を見直したとき
だった。
これらどれも AI 以前の工程であり、データ基盤として当たり前のことをコツコツやる類のアクションだ。
つまり有用な分析エージェントを作るためには有用なデータ基盤が必要で。エージェントなんか作ってる場合ではなかったのだ。
引き算で進んだ MCP への移行
そんなわけで分析エージェントはやめて分析 MCP を作った。
コードの多くは分析エージェント時代のものを流用できている。リライトにあたって整理整頓できたのも良かった。
MCP のベースには FastMCP を使っている。Google ADK も FastMCP もベースには FastAPI があるのでコードがとても似通ったものになる。
ドメインモデルの面でも実装の面でも移行は難しくなかった。
使ってもらえる場所に届ける
先日チーム内で MCP を共有し、Claude.ai のコネクタとして接続して使ってもらった。
普段使っている Claude.ai が突然 分析エージェントとして振る舞いだすのはみんなにとっても面白かったらしく。「こんな感じで使ってみました」と活用例がシェアされてきた。
私がずっと自作分析エージェントを作っていたとしても、このような驚きとクオリティを提供できていなかったと思う。技術を使うべき正しい場所をようやっと見つけ出したような気分になっている。
まとめ
分析エージェントをやめて、分析 MCP を作り動かし始めた。
少し遠回りだった気もするが。作って、手放して、分かったことも多かった。

Popover API
popover 属性を付けた要素を、ポップオーバーとして表示できる機能です。開く・閉じる処理や重なり順の調整を、JavaScript を書かずにブラウザに任せられます。

- 最前面（top layer）に表示されるので、z-index の調整がいらない
- 外側のクリックや Esc キーで自動的に閉じる
- popover="manual" にすると自動では閉じなくなる（トーストなど、開閉を自分で制御したいとき向け）
<button popovertarget="menu">メニュー</button>
<div id="menu" popover>
<a href="/settings">設定</a>
</div>
Invoker Commands（commandfor / command）

標準のコマンドとして、ダイアログ用の show-modal / close / request-close と、ポップオーバー用の show-popover / hide-popover / toggle-popover が用意されています。

fetchpriority
画像やスクリプトなどの読み込みの優先度を、ブラウザに伝える属性です。
主な目的は Core Web Vitals の LCP（Largest Contentful Paint） の改善です。LCP は画面に見えている中で一番大きな画像やテキストが表示されるまでの時間で、2.5 秒以内が「良い」とされます。一番大きな要素はたいていメインの画像や本文なので、「ページを開いてから、メインのコンテンツが表示されるまでの時間」を表す指標になっています。
ブラウザはページの一番上の大きな画像が重要だと気づくのが遅れがちで、そのぶん LCP も悪くなります。fetchpriority="high" で最初から優先度を伝えておくと、早く表示されます。
- 値は high / low / auto（初期値）の 3 つ
- <img>、<script>、<link rel="preload"> などに付けられる
- JavaScript の fetch() でも、priority オプションで同じ指定ができる
- あくまで「ヒント」なので、ブラウザが必ずその通りに読み込むとは限らない
たとえば、次のような場面で使います。
- トップページのメインビジュアル: ページを開いて最初に見える大きな画像を high にして、LCP を短くする
- EC サイトの商品詳細ページ: 商品のメイン画像を high にする
- カルーセル: 最初に見える 1 枚目を high、2 枚目以降を low にして、1 枚目の読み込みを先に終わらせる
- 重要度の低いスクリプト: 分析タグなど、急がないスクリプトを low にして、ほかの読み込みを邪魔しないようにする
<img src="hero.jpg" fetchpriority="high" alt="">
<img src="slide-2.jpg" fetchpriority="low" alt="">

指定したリソースを読み込み終えるまで、ページの描画を待たせる属性です。テーマの切り替えやログイン状態による出し分けのスクリプトを読み込む前に画面が出てしまい、一瞬だけ違う見た目がちらつく、という問題を防げます。
- <script>、<link> に付けられる（<link> は rel が stylesheet か expect のときだけ）
- <style> にも付けられるが、<head> の CSS はもともと描画を止めるので、使う場面はあまりない
- どの要素でも、描画を止められるのは <head> の中にあるものだけ
- 読み込みに失敗したら（404 など）ブロックは解除され、そのまま描画される

<head> に async なしで書いた普通の <script> も描画を止めますが、こちらは HTML の解析そのものを止めます。そのスクリプトを実行し終えるまで、下の HTML は読まれません。
一方、async に blocking="render" を付けた場合は、HTML の解析は止めずに、描画だけを止めます。待っているあいだにも、下の HTML の解析や、画像やほかのスクリプトの読み込みが進むので、描画が始まるのが早くなりやすいです。

「NIKKE」PCランチャー改ざん、9月27日以降の起動で不正プログラム侵入のおそれ
2026年11月5日 17:35
SHIFT UPおよびLevel Infiniteの提供するシューティングゲーム「勝利の女神: NIKKE」において、PC版ランチャーがダウンロードするスクリプトファイルが第三者によって改ざんされていたことが分かった。運営チームが11月5日に明らかにしたもので、ランチャーの起動時に不正プログラムが実行された可能性があるという。9月27日15時41分以降にPC版ランチャーを1回以上起動したユーザーが対象で、運営チームはPCとアカウントのセキュリティ確認を呼びかけている。なお、モバイル版への影響はないとしている。
説明によると、9月27日10時59分にゲームサービスの一部で利用していたドメイン「insightjs.com」が第三者に乗っ取られた。同日15時41分から42分にかけて、ランチャーがダウンロードする公式CDNスクリプトファイル4件が改ざんされた。改ざんされたファイルには、特定のドメインへ接続する不正なコードが挿入されていたという。その後、10月30日3時52分から、このスクリプトを通じてユーザーのPCへの不正プログラムの配布が始まった。
運営チームでは11月4日0時頃にスクリプトファイルの異常を確認し、調査と対応を開始。第一次対応として、同日2時4分から23分にかけて不正なスクリプトファイル3件を差し替え、不正プログラムの追加配布を遮断した。続く第二次対応として、同日12時9分に残り1件の不正なスクリプトファイルに関連するCDNキャッシュを更新し、正常なファイルを順次反映していったとしている。現在も被害範囲の調査を続けているほか、改ざんの経路を特定するため、CDNを含むネットワークのセキュリティ環境を確認している。
対象のユーザーは、不正プログラムを削除する必要がある。方法は2通りで、11月5日8時から公開された、検査/削除機能を追加した最新版ランチャーでチェックするか、自身でログファイルの確認やレジストリ項目/ファイルの削除を実施する。
ランチャーのチェック機能を使用する場合は、起動中のWebブラウザをすべて終了してから、PC版ランチャーを起動する。不正プログラムが検出された場合はポップアップが表示され、削除に同意すると、不正プログラムに関連するログやDLLファイル、レジストリ情報がすべて削除される。不正プログラムが検出されなかった場合、ポップアップは表示されず、そのままゲームが起動する。なお、Webブラウザが完全に終了していない場合、一部のDLLファイルが残ってしまう可能性があるが、そのファイルが実行されることはなく、追加のセキュリティリスクは生じないとしている。
PC版ランチャーをインストールしていない場合や、ランチャーを使わずにチェックしたい場合は、インストール先のログファイル(debug.log)内に「k2f_chan registered」の文字列があるかどうかを確認する。ある場合は不正プログラムが実行された可能性がある。その際は、レジストリ項目や、Chromeのユーザーデータフォルダー内に置かれた不正なDLLファイル、ランチャーのキャッシュなどの削除が必要となる(詳細はサポートページを参照のこと)。
文字列が見つからなかった場合でもリスクは完全には排除できないとして、手順の最後にはウイルス対策ソフトによるフルスキャンと、Microsoft Defenderのオフラインスキャンの実施も求めている。
不正プログラムの削除に加えて、影響を受けていた可能性がある場合はアカウント保護の対応を実施するよう呼びかけている。具体的には、当該PCで利用したことのあるアカウントのパスワードの変更、APIキーやアクセストークンの破棄/再発行などを挙げている。これらの対応は、不正プログラムの影響を受けていない別のデバイスか、セキュリティチェックの完了後に実施することを推奨している。また、本件はゲーム外のアカウントや資産にも影響を及ぼす可能性があるとして、アカウントに異常が生じた場合や金銭的被害を受けた場合は、公式カスタマーサポートで受け付けるとしている。
本事案を受け運営チームでは、セキュリティ全般の管理体制を再点検するほか、不正を早期に検知し対応できるよう、監視体制の強化を図ると説明。あわせて、改ざんの検知やリスクの低減に向け、PC版ランチャーが読み込む外部リソースの完全性検証の仕組みを構築するほか、権限周りの見直しなども実施するとしている。

Either one closes the hole.
What is the problem?
An attacker who can reach your SSH port can log in without knowing any password. It takes one connection, works every time, and needs no retries.
The attacker needs the name of an account whose password field is *
(an account with no password set, which is normal for key-only accounts), and
needs the machine to have at least one other account with a $5$ or $6$
password hash. The attacker then sends a very long password (257 to 1024
bytes). One user with a password is enough: it makes every account without
one reachable.
Details are in the OpenSSH 10.6p2 release notes. No CVE identifier had been assigned at the time of writing.

You are affected if all of the following are true:
- You run the Alpine openssh-server package, which is built without PAM, or

another account that can log in is able to become root, for example
through doas.

- Users coming from a directory service through musl-nscd (nslcd, winbind, sssd), since they have no shadow entry.

A new Go API for JSON
Introduction
JavaScript Object Notation (JSON) is a simple data interchange format, the most popular data format used on the internet, and widely read and written by Go programs. Go has included support for JSON in the standard library since well before Go 1.0. We first wrote about support for JSON in Go more than 15 years ago!
Over time, packages evolve with the needs of their users, and encoding/json is no exception.
Last year, we wrote about a new experimental API for JSON designed to bring long-awaited improvements and fixes.
After additional feedback and refinement, the new encoding/json/v2 and encoding/json/jsontext packages are stable and generally available in Go 1.27!
This post is an updated version of the article introducing the experiment, describing the problems with encoding/json and introducing the new packages.
Problems with encoding/json
Overall, encoding/json has held up well.
The idea of marshaling and unmarshaling arbitrary Go types
with some default representation in JSON, combined with the ability to
customize the representation, has proven to be highly flexible.
However, in the years since its introduction,
various users have identified numerous shortcomings.
Behavior flaws
There are various behavioral flaws in encoding/json:
- Imprecise handling of JSON syntax: Over the years, JSON has seen increased standardization in order for programs to properly communicate. Generally, decoders have become stricter at rejecting ambiguous inputs, to reduce the chance that two implementations will have different (successful) interpretations of a particular JSON value.
- encoding/json currently accepts invalid UTF-8,
whereas the latest Internet Standard (RFC 8259) requires valid UTF-8.
The default behavior should report an error in the presence of invalid UTF-8,
instead of introducing silent data corruption,
which may cause problems downstream.
- encoding/json currently accepts objects with duplicate member names.
RFC 8259 does not specify how to handle duplicate names,
so an implementation is free to choose an arbitrary value,
merge the values, discard the values, or report an error.
The presence of a duplicate name results in a JSON value
without a universally agreed upon meaning.
This could be exploited by attackers in security applications
and has been exploited before (as in CVE-2017-12635).
The default behavior should err on the side of safety and reject duplicate names.
- Leaking nilness of slices and maps: JSON is often used to communicate with
programs using JSON implementations that do not allow null to be unmarshaled
into a data type expected to be a JSON array or object.
Since encoding/json marshals a nil slice or map as a JSON null,
this may lead to errors when unmarshaling by other implementations.
A survey
indicated that most Go users prefer that nil slices and maps
are marshaled as an empty JSON array or object by default.
- Case-insensitive unmarshaling: When unmarshaling, a JSON object member name is resolved to a Go struct field name using a case-insensitive match. This is a surprising default, a potential security vulnerability, and a performance limitation.
- Inconsistent calling of methods: Due to an implementation detail,
MarshalJSON methods declared on a pointer receiver
are inconsistently called by encoding/json. While regarded as a bug,
this cannot be fixed as too many applications depend on the current behavior.
API deficiencies
The API of encoding/json can be tricky or restrictive:
- It is difficult to correctly unmarshal from an io.Reader.
Users often write json.NewDecoder(r).Decode(v),
which fails to reject trailing junk at the end of the input.
- Options can be set on the Encoder and Decoder types,
but cannot be used with the Marshal and Unmarshal functions.
Similarly, types implementing the Marshaler and Unmarshaler interfaces
cannot make use of the options and there is no way to plumb options down the call stack.
For example, the Decoder.DisallowUnknownFields option loses its effect
when calling a custom UnmarshalJSON method.
- The Compact, Indent, and HTMLEscape functions write to a bytes.Buffer instead of something more flexible like a []byte or io.Writer.
This limits the usability of those functions.

We no longer need to care about syntax and variable names, or how to construct a for loop. The agents are more than capable of making these kinds of simple decisions at warp speed. This means we’re spending way less time on implementation.
The important work is now everything that happens before and after code gets written: planning and review. These are not solved problems.
Planning is the more critical piece because everything else is downstream of it. It’s what will make or break your feature. And it’s also where having a seasoned developer driving the plan makes a big difference. Handing a coding agent a poorly specified, rough idea of a feature with no clear validation requirements is how you end up with vibe-coded slop.
All of today’s AI agents have a well-established “plan mode.” It was one of the early, immensely popular breakout features of Claude Code back in ye olde June 2025. Claude was not the first to do this; improving agent results by getting them to think and plan before acting was first proposed by the 2022 ReAct paper and implemented by lesser known agent harnesses like Cline.
Combining plan mode with skills like Matt Pocock’s infamous grill-me, which exhaustively quizzes you on what you want to make, helps you develop a thorough understanding of the task at hand and explore possible directions first, before jumping into building anything. You and the agent discuss the problem space and come to clear, opinionated solutions together.
The plan then becomes a clear touchpoint in the development process; both an artifact that you can hand off to a coding agent to implement, and record of the original intention to compare against during the review phase.
This planning part isn’t drastically different to how we used to plan in the pre-agentic era. Developers, product managers, designers, and other stakeholders spent plenty of time and effort writing up design specs, PRDs, RFCs, and other acronym-laden documents in order to guide and drive the work of engineering teams. The difference now is that humans are not involved in the implementation process. We can’t adjust and redirect decisions once the work begins, making planning well up front much more critical.
The Problem with our Planning Tools
Our current planning tools have plenty of limitations, but four major ones stick out to us: interactivity, team collaboration, decision ownership, and visual explanations.
1. Lack of Interactivity
If you’re using a CLI tool in the terminal, the plan is, at best, a wall of uneditable, static text. Even when it displays inline Markdown syntax, it still renders as a flat, unstyled, hard-to-read document.
If you’re part of the more enlightened crowd who have upgraded to a desktop app GUI, you get a much richer view of plans and documents with nice markdown formatting. But you still can’t directly edit the plan. Some interfaces make it hard to read the plan in full, partially hiding it in a preview. And most offer a binary option: would you like to accept or reject this plan?
This does not offer us a way to engage with the details of the plan and understand what we’re agreeing it. Making small changes and progressively iterating on a large, long, 3000 word plan is difficult. In most of our current tools it is hard or impossible to point at a section and say “Can you expand on this point?” or “Please delete this suggestion” or “I don’t agree with this approach, why are you recommending it?”
You have to instead hold many, complex threads and separate ideas in your head as you read the plan and then dump all of your feedback into one chat box. Then hope the agent remembers to address all of your points.
Answering 37 different questions during the grilling session does not guarantee all of your decisions will be reflected in the final plan. This is a very primitive interface compared to what is possible.
It makes the final plan feel detached from the process of creating it. “Writing” a plan with an agent does not feel like an interactive experience. The plan appears fully formed, rather than being co-written. What would it take for a human to feel they have fully understood, digested, and been part of every key decision in that plan?

関係のある機能は続けて並べているので、上から順に読むとつながりが分かりやすいと思います。
Popover API
popover 属性を付けた要素を、ポップオーバーとして表示できる機能です。開く・閉じる処理や重なり順の調整を、JavaScript を書かずにブラウザに任せられます。
- popovertarget を付けたボタンで開閉できる
- 最前面（top layer）に表示されるので、z-index の調整がいらない
- 外側のクリックや Esc キーで自動的に閉じる
- popover="manual" にすると自動では閉じなくなる（トーストなど、開閉を自分で制御したいとき向け）
<button popovertarget="menu">メニュー</button>
<div id="menu" popover>
<a href="/settings">設定</a>
</div>
Invoker Commands（commandfor / command）
popovertarget を、ポップオーバー以外にも使えるように広げた機能です。<button> に commandfor（操作する要素の id）と command（何をするか）を付けて使います。
標準のコマンドとして、ダイアログ用の show-modal / close / request-close と、ポップオーバー用の show-popover / hide-popover / toggle-popover が用意されています。
<button commandfor="confirm" command="show-modal">削除する</button>
<dialog id="confirm">
<p>本当に削除しますか？</p>
<button commandfor="confirm" command="close">キャンセル</button>
</dialog>
-- で始まる名前にすると、独自のコマンドも作れます。独自のコマンドは操作される側の要素に届く command イベントで受け取ります。イベントの command にはコマンド名が、source には押されたボタンが入っています。
<button commandfor="counter" command="--increment">+1</button>
<output id="counter">0</output>
// 独自コマンドは、操作される側の要素で受け取る
counter.addEventListener('command', (event) => {
if (event.command === '--increment') counter.value = Number(counter.value) + 1;
});
参考: Invoker Commands API - MDN
Interest Invokers（interestfor）
Invoker Commands がボタンを押したとき（クリックやキーボードの Enter / Space など）に反応するのに対して、こちらはホバー、フォーカス、長押しといった「ユーザーが関心を示した」ときに反応します。ツールチップやリンクのプレビューを、JavaScript なしで出せます。
- interestfor に対象の id を書き、対象に popover を付けて使う
- ホバーした瞬間に開かないよう、ブラウザが少し待ってから表示する（待ち時間は CSS の interest-delay で調整できる）
- 対象の要素で interest / loseinterest イベントが発生する（表示に合わせて中身を読み込む、などに使える）
- まだ Chromium 系のブラウザ（Chrome 142 以降）だけの機能で、ほかのブラウザでは polyfill が必要
<a href="/profile" interestfor="profile-card">ユーザー名</a>
<div id="profile-card" popover="hint">プロフィールのプレビュー</div>

<dialog closedby>
ダイアログをどう閉じられるようにするかを、属性で決められる機能です。外側のクリックで閉じたいときに、クリック位置がダイアログの外かどうかを JavaScript で判定する必要がなくなります。
- any: 外側のクリックでも Esc キーでも閉じる
- closerequest: Esc キーでだけ閉じる
- none: どちらでも閉じない

<dialog closedby="any">外側をクリックしても閉じる</dialog>

inert

- スクリーンリーダーなどの支援技術からも見えなくなる

fetchpriority
画像やスクリプトなどの読み込みの優先度を、ブラウザに伝える属性です。
主な目的は Core Web Vitals の LCP（Largest Contentful Paint） の改善です。LCP は画面に見えている中で一番大きな画像やテキストが表示されるまでの時間で、2.5 秒以内が「良い」とされます。一番大きな要素はたいていメインの画像や本文なので、「ページを開いてから、メインのコンテンツが表示されるまでの時間」を表す指標になっています。
ブラウザはページの一番上の大きな画像が重要だと気づくのが遅れがちで、そのぶん LCP も悪くなります。fetchpriority="high" で最初から優先度を伝えておくと、早く表示されます。
- 値は high / low / auto（初期値）の 3 つ
- <img>、<script>、<link rel="preload"> などに付けられる
- JavaScript の fetch() でも、priority オプションで同じ指定ができる
- あくまで「ヒント」なので、ブラウザが必ずその通りに読み込むとは限らない
たとえば、次のような場面で使います。
- トップページのメインビジュアル: ページを開いて最初に見える大きな画像を high にして、LCP を短くする
- EC サイトの商品詳細ページ: 商品のメイン画像を high にする
- カルーセル: 最初に見える 1 枚目を high、2 枚目以降を low にして、1 枚目の読み込みを先に終わらせる
- 重要度の低いスクリプト: 分析タグなど、急がないスクリプトを low にして、ほかの読み込みを邪魔しないようにする
<img src="hero.jpg" fetchpriority="high" alt="">
<img src="slide-2.jpg" fetchpriority="low" alt="">
参考: Optimize resource loading with the Fetch Priority API - web.dev
blocking="render"
指定したリソースを読み込み終えるまで、ページの描画を待たせる属性です。テーマの切り替えやログイン状態による出し分けのスクリプトを読み込む前に画面が出てしまい、一瞬だけ違う見た目がちらつく、という問題を防げます。

- <style> にも付けられるが、<head> の CSS はもともと描画を止めるので、使う場面はあまりない
- どの要素でも、描画を止められるのは <head> の中にあるものだけ
- 読み込みに失敗したら（404 など）ブロックは解除され、そのまま描画される
<script src="theme.js" async blocking="render"></script>
<head> に async なしで書いた普通の <script> も描画を止めますが、こちらは HTML の解析そのものを止めます。そのスクリプトを実行し終えるまで、下の HTML は読まれません。
一方、async に blocking="render" を付けた場合は、HTML の解析は止めずに、描画だけを止めます。待っているあいだにも、下の HTML の解析や、画像やほかのスクリプトの読み込みが進むので、描画が始まるのが早くなりやすいです。

SHIFT UPおよびLevel Infiniteの提供するシューティングゲーム「勝利の女神: NIKKE」において、PC版ランチャーがダウンロードするスクリプトファイルが第三者によって改ざんされていたことが分かった。運営チームが11月5日に明らかにしたもので、ランチャーの起動時に不正プログラムが実行された可能性があるという。9月27日15時41分以降にPC版ランチャーを1回以上起動したユーザーが対象で、運営チームはPCとアカウントのセキュリティ確認を呼びかけている。なお、モバイル版への影響はないとしている。
説明によると、9月27日10時59分にゲームサービスの一部で利用していたドメイン「insightjs.com」が第三者に乗っ取られた。同日15時41分から42分にかけて、ランチャーがダウンロードする公式CDNスクリプトファイル4件が改ざんされた。改ざんされたファイルには、特定のドメインへ接続する不正なコードが挿入されていたという。その後、10月30日3時52分から、このスクリプトを通じてユーザーのPCへの不正プログラムの配布が始まった。
運営チームでは11月4日0時頃にスクリプトファイルの異常を確認し、調査と対応を開始。第一次対応として、同日2時4分から23分にかけて不正なスクリプトファイル3件を差し替え、不正プログラムの追加配布を遮断した。続く第二次対応として、同日12時9分に残り1件の不正なスクリプトファイルに関連するCDNキャッシュを更新し、正常なファイルを順次反映していったとしている。現在も被害範囲の調査を続けているほか、改ざんの経路を特定するため、CDNを含むネットワークのセキュリティ環境を確認している。
対象のユーザーは、不正プログラムを削除する必要がある。方法は2通りで、11月5日8時から公開された、検査/削除機能を追加した最新版ランチャーでチェックするか、自身でログファイルの確認やレジストリ項目/ファイルの削除を実施する。
ランチャーのチェック機能を使用する場合は、起動中のWebブラウザをすべて終了してから、PC版ランチャーを起動する。不正プログラムが検出された場合はポップアップが表示され、削除に同意すると、不正プログラムに関連するログやDLLファイル、レジストリ情報がすべて削除される。不正プログラムが検出されなかった場合、ポップアップは表示されず、そのままゲームが起動する。なお、Webブラウザが完全に終了していない場合、一部のDLLファイルが残ってしまう可能性があるが、そのファイルが実行されることはなく、追加のセキュリティリスクは生じないとしている。
PC版ランチャーをインストールしていない場合や、ランチャーを使わずにチェックしたい場合は、インストール先のログファイル(debug.log)内に「k2f_chan registered」の文字列があるかどうかを確認する。ある場合は不正プログラムが実行された可能性がある。その際は、レジストリ項目や、Chromeのユーザーデータフォルダー内に置かれた不正なDLLファイル、ランチャーのキャッシュなどの削除が必要となる(詳細はサポートページを参照のこと)。
文字列が見つからなかった場合でもリスクは完全には排除できないとして、手順の最後にはウイルス対策ソフトによるフルスキャンと、Microsoft Defenderのオフラインスキャンの実施も求めている。
不正プログラムの削除に加えて、影響を受けていた可能性がある場合はアカウント保護の対応を実施するよう呼びかけている。具体的には、当該PCで利用したことのあるアカウントのパスワードの変更、APIキーやアクセストークンの破棄/再発行などを挙げている。これらの対応は、不正プログラムの影響を受けていない別のデバイスか、セキュリティチェックの完了後に実施することを推奨している。また、本件はゲーム外のアカウントや資産にも影響を及ぼす可能性があるとして、アカウントに異常が生じた場合や金銭的被害を受けた場合は、公式カスタマーサポートで受け付けるとしている。

マイナンバーカードを実装したスマホの持ち主が亡くなったとき、どんな対応をするべきでしょうか。下取りに出すにしても、しばらく保管するにしても、正しい処理方法を知っておくに越したことはないはず。デジタル遺品を扱う当連載ではそこに注目しないわけにはいきません。

基本は何もしなくてOKに……けれど
前提として掴んでおきたいのは、「スマホのマイナンバーカード」情報の保存場所です。
スマホのマイナンバーカードは「マイナアプリ」を通して、カード型マイナンバーカードとスマホを紐付けることで設定します。紐付けられたスマホには固有の「スマホ用電子証明書」が保存されるのですが、保存場所は一般的なストレージの中ではありません。「おサイフケータイ」等で使われる専用チップ（Androidの場合はFeliCa-SEチップ）という別のハードウェアに格納されます。
注意したいのはこの領域はスマホの一般的な初期化操作の対象外ということです。スマホの標準メニューでシンプルに初期化してしまうとデータが残存してしまうので、専用チップ内を消去したうえでスマホ全体を初期化しなければなりません。消去といえば、最近のAndroid端末では「おサイフケータイ」アプリ内でFeliCa-SEチップのデータをまとめて削除できます。しかし、この機能でもスマホ用電子証明書は検知されず、対象外の扱いとなっています。スマホ用電子証明書はいろいろと例外的な存在なのです。iPhoneでも基本的には同様です。

今年の6月まで、データ分析用途の AI エージェント (以下、分析エージェント) をスクラッチで開発していた。
が、思うところがあり開発をスッパリとやめた。この記事でいろいろと振り返ってみようと思う。
3行まとめ
- 分析エージェントを開発するのはやめて、分析 MCP として作り直した
- AI エージェントの全てを開発するのは手間がかかりすぎる
- 良い分析体験のキモはエージェントが動く手前にある
分析エージェントから分析 MCP へ
もともと作ろうとしていたエージェントは、チャット UI で分析を依頼するとデータ取得・考察・結果の可視化までを担うものだった。
ところが AI エージェント全体を作ろうとすると自作しなければいけない構成要素が多すぎる。全てに注力するには時間がかかるし、限られた時間で多くのものを作ろうとすると一つひとつのクオリティは下がってしまう。
そこで今年の7月からは心機一転 MCP を作ることにした。事前集計されたデータを返したり、各データについての知識を的確に返すような MCP だ。
私たちの用途では MCP を作り込むので充分だという感触を得ている。汎用エージェント (Claude.ai など) に MCP を接続するだけで、基礎的なデータ分析を担うエージェントとして使えそうだ。
自作エージェントの守備範囲
分析エージェントは Google Agent Developer Kit (ADK) を使って作っていた。
ADK はマルチエージェントシステムを構築・デプロイするためのフレームワークで。サブエージェントを定義してタスク分担・オーケストレーションといったことを手軽にできるようになる。
とはいえ AI エージェントを自作するとなると賄わなければいけない領域は多岐にわたる。
- UI
- 認証基盤
- セッション管理
- メモリー
- サブエージェントのオーケストレーションルール
- アセットアップロード
- アップロードされたアセット管理
- スキルシステム
ざっと挙げただけでも、これらは自作する必要がある。
UI 以外は無くても分析エージェントとして成り立つものの。普段使っている Claude.ai, ChatGPT, Gemini などと比較してしまうと物足りないものになる。
メモリーという難所
特にメモリーが難しい。セッションをまたいでユーザーの関心事ややりとりの注意点を記憶させておく仕組み。
仕組み自体はシンプルだ、
- ユーザーとの会話から覚えておくべきことを抽出する
- なんらかのデータベースに情報を永続化する
- しかるべきタイミングでデータベースを検索し、適切に参照させる。
これだけ。
しかし「覚えておくべきことを抽出」「しかるべきタイミングで検索」「適切に参照させる」これらが奥深すぎる。
一応、 mem0 などのサードパーティ製の API を使って楽をすることはできる。が、開発者側でやるべきことはいくらか残る。
- 過去のメモリーを訂正する
- 過去のメモリーを忘却させる
などは実装側で工夫する必要がある。
最大の欠点は、ユーザーが普段使っている AI エージェントとの間でメモリーが共有されないことかもしれない。どれだけ良い AI エージェントを自作してもメモリーが引き継がれないことが乗り換えの障壁になりうる。
汎用エージェントに任せられること
このように自作エージェントには本質的なタスク (例えばデータ分析) でない部分で実装コストがかかりすぎる。
一方で必要な部分だけ MCP 化して、残りを汎用エージェントにお任せするのは現実的なんだろうか。
私の場合、とてもうまく機能している。作り直した分析 MCP を接続することで、汎用エージェントが "分析エージェント化" した感覚だ。
データを表示する UI は手放しでも改善されていく。最近の Claude.ai は Claude Artifacts でインタラクティブな可視化もしてくれる。
認証基盤・メモリー・アセット管理・スキルシステムなども言わずもがな、普段の使い慣れた仕組みをそのまま分析業務にも活用できる。
これらの "備え付けられた" 便利な仕組みを捨ててまで自作エージェントをゼロから作る動機を私は見出せなかった。
分析の手応えとデータ基盤
では自作の分析エージェント作りは全くの無駄骨だったのか。実はそうでもない。
分析エージェントを作るなかで、分析業務に本質的に重要な部分と汎用の仕組みを活用するべき部分が見分けられるようになったからだ。
最初は『BigQuery の execute_sql ツールを AI に繋げば良い感じの洞察を語ってくれるのかな？』などと思っていた。
が、これは全然違った。当たり前のデータを渡すだけでは当たり前のことしか言わないのが AI だ。何の工夫もしなければ「朝晩は電車が混むようです」「冬はおでんが売れるようです」などのわかりきったことしか言わない。
むしろ、分析エージェントとして前進している感覚が得られたのは、
- 注目するべき指標をしっかり定義し、チームで合意したとき
- 注目するべき指標が日々事前集計されるよう仕組み化したとき
- 注目するべき指標が正確になるようにデータの収集方法を見直したとき
だった。
これらどれも AI 以前の工程であり、データ基盤として当たり前のことをコツコツやる類のアクションだ。
つまり有用な分析エージェントを作るためには有用なデータ基盤が必要で。エージェントなんか作ってる場合ではなかったのだ。
引き算で進んだ MCP への移行
そんなわけで分析エージェントはやめて分析 MCP を作った。
コードの多くは分析エージェント時代のものを流用できている。リライトにあたって整理整頓できたのも良かった。
MCP のベースには FastMCP を使っている。Google ADK も FastMCP もベースには FastAPI があるのでコードがとても似通ったものになる。
ドメインモデルの面でも実装の面でも移行は難しくなかった。
使ってもらえる場所に届ける
先日チーム内で MCP を共有し、Claude.ai のコネクタとして接続して使ってもらった。
普段使っている Claude.ai が突然 分析エージェントとして振る舞いだすのはみんなにとっても面白かったらしく。「こんな感じで使ってみました」と活用例がシェアされてきた。
私がずっと自作分析エージェントを作っていたとしても、このような驚きとクオリティを提供できていなかったと思う。技術を使うべき正しい場所をようやっと見つけ出したような気分になっている。
まとめ
分析エージェントをやめて、分析 MCP を作り動かし始めた。
少し遠回りだった気もするが。作って、手放して、分かったことも多かった。
私からは以上です。
