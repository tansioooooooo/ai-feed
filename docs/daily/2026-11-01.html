28th October 2026
Apple was notified of the eMudhra incident on 17th October. As of 28th October, the developer tools Apple ships with macOS, including git, curl and python3, still trust the compromised certificates.
Worse, macOS 27.2, released on 26th October, did not fix the issue and undid the workaround that users had applied by hand, leaving them vulnerable again.
Meanwhile, dozens of other projects, many run by volunteers, shipped fixes days ago.
Anyone can intercept any HTTPS connection these tools make.
For git, that means clones and pulls from https:// remotes can deliver attacker-chosen code, pushes can be altered in transit, and your credentials, such as GitHub tokens, can be intercepted.
To check whether your git is affected, run:
git ls-remote https://git-emudhra.we-have-a-problem.com/check.git
A certificate error means your git is protected. If git lists a commit, your git is affected. Your connections to GitHub, or any other https:// git remote, can be intercepted and tampered with.
To see an attack end to end, run the command below in a temporary directory. It clones a repository from a test server impersonating GitHub. The -c option redirects github.com to our test server for this one command only. The server presents a github.com certificate issued by one of the compromised eMudhra intermediates.
git -c http.curloptResolve=github.com:443:15.235.19.186 clone https://fake-user@github.com/galadran/emudhra-git-test
A patched git will refuse with a certificate error. If the clone succeeds, you'll see a README.md starting with INTERCEPTED.
A real attacker would not need the extra option. Anyone on the network path between you and GitHub can redirect your traffic themselves.
You can replace the demo repository with any other, public or private. Keep the fake-user@ prefix. Without it, git would send your GitHub credentials to the test server. For example:
git -c http.curloptResolve=github.com:443:15.235.19.186 clone https://fake-user@github.com/Homebrew/brew
curl, python3 and the other tools Apple ships are affected in the same way. To check curl, run:
curl https://dv-g3b-noct-emudhra.we-have-a-problem.com/
curl https://dv-g3b-aaa-noct-emudhra.we-have-a-problem.com/
A certificate error means curl is protected.
Apple has already protected Safari and other apps built on its networking framework.
Apple needs to ship a fix for macOS developers as soon as possible, for example by removing the affected roots from /etc/ssl/cert.pem.
The affected roots can be removed by hand. The macOS workaround on the main page walks through the steps. Apple's guidance states that macOS updates may revert the fix, so developers need to repeat the checks above and the workaround after every update until Apple ships a fix.
Security teams should also consider whether macOS runners are used in their CI or other build infrastructure and evaluate the supply chain risk.

Overview
Linux's stable kernels shipped a fix on October 11 and 15, 2026 for CVE-2026-98432, a use-after-free in the IPv4 TCP handshake that a remote, unauthenticated peer can reach. The kernel's own CVE Numbering Authority (CNA) scores it CVSS 3.1 9.8, Critical. The fixed releases are 5.10.272, 5.15.223, 6.1.190, 6.6.159, 6.12.113, 6.18.56, 7.2.10, and 7.3, and the bug goes back to Linux 4.4. The upstream fix is a four-line change, but most servers run a distribution's kernel, and as of 5:15 PM CDT, October 31, Ubuntu's tracker still reads "Vulnerable" for its kernel on every release, and Red Hat, which now rates the bug Critical too, lists RHEL 8, 9, and 10 as affected with no fix.
Why it's urgent: the bug sits in code every Linux server runs when it accepts an IPv4 TCP connection, before any application sees the connection. Anthropic, whose researcher reported it, says its Claude model wrote a working proof-of-concept exploit that runs commands as root on "Linux servers with a multipath TCP listener," with no credentials. Go programs open those listeners by default, per the Go Security Team. See the timeline.

Any Linux kernel from 4.4 on that lacks the fix, whether it serves the network directly or hosts containers: a container runs on the host's kernel, so a new image doesn't change anything. IPv6 connections aren't affected by the main issue; the commit says "IPv6 is not affected by the first issue."

How the vulnerability works
When a Linux server accepts a TCP connection, the kernel tracks the half-open handshake in a lightweight "request socket," then creates a full socket once the handshake completes. If the connecting peer's IPv4 header carried options, the kernel keeps them to echo in its replies. The bug: the kernel handed those saved options from the request socket to the new connection without copying them, then freed them immediately when the connection went away, while another CPU could still be reading them to build a handshake reply. Reading freed kernel memory is a use-after-free.
The peer needs no login, and it all happens inside the kernel's handshake handling, before any application code runs. The CNA's scoring notes say the stale data can leak kernel heap memory back to the peer, steer kernel writes out of bounds, or crash the machine. Anthropic says a lost race "only fails the handshake without crashing the whole system, so a determined attacker can retry indefinitely until they succeed."

1 Background
Modern applications often spread state across a variety of systems: databases, caches, queues, data warehouses, search indices, and so on. Coordinating these systems is challenging: caches are often stale, the analytics platform might lag days behind the primary database, the search index might lose data, and transactional updates across disparate systems remains an open research problem.
ParticleDB1 aims to unify these workloads in a single engine with a special focus on AI agents and applications. It offers transactional SQL, a key-value store, vector search, live analytics, and user-defined functions called Particles.2 To integrate with existing systems, clients can connect through a variety of interfaces, including the Postgres and Redis protocols, as well as its own gRPC and HTTP2 APIs. Written from the ground up in Rust, ParticleDB claims to be orders of magnitude faster than Postgres while preserving the same safety characteristics.
ParticleDB was built by Orkes to support their workflow orchestration platform, Conductor. Conductor was initially built to store data in Redis and Postgres, but to improve performance, Orkes opted to write their own database. ParticleDB 1.0.0 offered a limited feature set specifically for Conductor’s queries, and was deployed as the backing database for some of their Conductor clusters. A few Orkes customers followed suit. In preparation for a broader release, Orkes undertook a major refactoring of ParticleDB, adding a custom wire protocol, more datatypes, additional OLAP queries, and more. While Orkes and their customers continued to run 1.0.0, they soft launched the refactored versions on particledb.ai. Orkes engaged Jepsen to test these versions of ParticleDB, beginning with 1.1.4.
While ParticleDB could run as a single node, it also offered a replicated cluster using the Raft consensus protocol. This replication feature was available only in enterprise cloud deployments. The builds Orkes provided did not support replication, so this report covers only single-node behavior.

風音屋（@Kazaneya_PR）のゆずたそ（@yuzutas0）です。 この記事では、AIエージェント向けの業務手順書「Agent Skills」の設計方法を紹介します。 実際に私が使っている「ミーティング日程調整」スキルを題材にして、8つのコツを解説します。
はじめに
AIに「日程調整をやっておいて」と頼むと、たいていはどちらかの反応が返ってきます。 ひとつは「何時間の打ち合わせですか」「相手はどなたですか」「候補は何日分ほしいですか」と質問攻めにされて、こちらが全部答えるまで動いてくれないパターン。 もうひとつは、聞かずに勝手に候補を並べてくるものの、いざ見てみると、集中作業のために空けている曜日や祝日、ランチ時間にまたがる時間帯が平気で混じっているパターンです。
この違いを生んでいるのは、AIの性能ではありません。 「業務手順」と「ドメイン知識」を渡していないことです。 新入社員に日程調整を任せる場面を思い浮かべると分かりやすいでしょう。 その業務を担当していた先輩は、口には出さない判断基準を無数に持っています。 「水曜はノー会議デーなので入れない」「ランチの時間帯には打ち合わせを入れない」「候補は少なくとも3日分を並べる」といった具合です。 この暗黙知を渡さないまま「よろしく」と頼むと、新入社員はいちいち質問しに来るか、聞かずに独自解釈で進めて事故を起こすかのどちらかになります。
AIに対して、この「新入社員に渡す業務手順書」の役割を担うのが「Agent Skills」（以下、スキル）です。
スキルとは、AIに読ませる前提で書かれた業務手順書のことです。
たとえばClaude Codeでは、スキルのフォルダを .claude/skills/ に置くだけで、依頼内容に応じてAIが自動で読み込んでくれます。
さらに、スキル自身をAIに改修させることもできます。
新入社員がマニュアルの不備を見つけたら、その場で直してもらうのと同じ感覚です。
画像はメール返信業務の例ですが、日程調整のスキルも同じ体裁で書けます。 本記事の画像は技術カンファレンス「Data Engineering Summit 2026」の登壇資料から引用しています。
日程調整という題材を選んだ理由は、暗黙知が多く、判断が細かく、失敗パターンも豊富で、スキル設計の勘所が全部詰まっているためです。 同じ考え方は「経理データからの月次コスト集計」「会議録画からのロードマップ更新」など、バックオフィスを含むあらゆる業務にそのまま応用できます。

こんにちは。TVerのAutomationチームで、テストや開発業務の効率化・自動化を担当している城間です。
TVerの開発組織では、2025年からリリースサイクルの短縮に取り組み、リリーストレイン（複数チームが同期して決められたサイクルでリリースを行う運用）を導入しています。
いま現在、Web、iOS、Androidの各プラットフォームはおおむね隔週でのリリースを実現できており、その背景や経緯の詳細は弊社の「計測から始める品質とスピードの両立 - TVerの開発組織改革2年間の記録」で紹介しています。
リリースサイクルを短縮するためには、リリースのたびに行うリグレッションテストを短時間かつ確実に回せる仕組みが重要になります。
しかしながら、2025年の春先まで、TVerのリグレッションテストはすべて手動で行われていました。 リリースサイクルを短縮しようとすればするほど、テスト工数が線形に積み上がっていく構造で、これを解消しない限りリリーストレインの持続的な運用はできません。
リリーストレインの運用をはじめるにあたり、迅速かつ安定して検証ができる自動テスト基盤を構築することは、私たちAutomationチームの重大なミッションでした。
本稿では、私たちが約1年間、戦略策定から運用に至るまで、段階を踏んでテストの自動化を進めてきた過程とその取り組みを紹介したいと思います。
抱えていた課題
2025年の初頭、リリース前に実施していたリグレッションテストの所要工数は、概算で以下のとおりでした。
これは、UIのリグレッションや、動画・ライブの目視確認、広告配信の検証など、複数のテストスイートにまたがる総工数の見積もりです。 継続的な機能改善とリリースを必要とするTVerサービスにおいて、毎回リリース前に数日分の検証工数を割き続ける運用には、いくつかの構造的な限界がありました。
- テストの実行に一定の工数を要し、短サイクルでのリリース対応が困難
- テスト実行の一部が属人化しており、チーム全体の生産性に波が出やすい
- 人的ミスによる軽微な不具合の取りこぼしが発生しうる
また、TVerのテストには「動いて見える」だけでは検証できない領域があります。
ユーザーの操作の裏で送信されるTVerタグ（行動ログ）、視聴データの計測用ビーコン、広告に関連するURLパラメータ置換処理といったログ系の整合性確認です。
これらはTVerの主要KPI、ひいては放送局・広告主に対する説明責任に直結する重要な検証項目ですが、マニュアルではHTTPプロキシで通信ログを目視確認するしかなく、QAチームへの負荷も再現性も大きな課題でした。
戦略の策定から始める
私たちはテストの自動化を導入するにあたり、フレームワークの選定よりも前に、まずリグレッションテストの戦略を明文化することから始めました。
自動テストを持続可能なものにするためには、何を、どこまで、どのように自動化するのかを最初に定義しておく必要があります。
スコープの定義
戦略ドキュメントでは、テストピラミッドの考え方を参考に、リグレッションテストを正常系のユーザーシナリオに絞ることに決めました。
細かな分岐や例外は単体・結合テストに任せ、リグレッションテストでは主要導線がend-to-endで機能していること、ユーザー操作によって生じるCRUD処理（作成・読み取り・更新・削除）が正しく動くことを確認する。ピラミッドの頂点に置くべき範囲に限定する、という方針です。
加えて、前述したログ系の整合性確認も、主要KPIへの影響度が高いことからリグレッションテストのスコープに含めました。
ユーザー操作の裏で送信されるログまで含めて回帰を担保する、TVerのサービス特性を反映した判断です。
実行契機の整理
次に自動テストを「いつ、どのトリガーで、何のために回すか」を整理しました。 いまは主に次の3つの実行契機で回しています。
自動テストを導入する目的は単一ではなく、同じテストアセットでも、走らせるタイミングを変えれば狙えるリスクが変わります。
この前提を最初に揃えることで、後から個別の運用設計をブレずに進められました。
E2Eテスト環境を独立して用意する
戦略の次に着手したのは、E2Eテスト専用の検証環境を各プラットフォームで揃えて用意することでした。
通常の開発環境やステージング環境を流用すると、開発作業や手動テストの副作用が自動テストの結果に影響してしまい、再現性が大きく損なわれます。 テストごとに「いまの環境はどんな状態か」を気にしないと結果を信頼できない状況は、自動化の前提を崩します。
私たちはWeb/iOS/AndroidのそれぞれのOSで、E2Eテスト専用の環境を共通で見るようにしました。実装方法はOSごとに異なりますが、テストが実行されるバックエンドは同じ独立した環境を指しています。
データの独立性とテストの再現性、この2つを早い段階で担保することが、後の運用フェーズで「テストを信じてリリース判断する」という文化を作るうえで重要でした。
リグレッションテストそのものを見直す
戦略と環境が用意できた後、私たちは自動化の実装に進む前に、もうひとつ大きな工程を挟みました。 既存のリグレッションテスト自体の作り直しです。
既存のリグレッションテストは、長らく画面の要素単位で書かれていました。
たとえば「シリーズ名が表示されていること」「エピソード名が表示されていること」「制作局が表示されていること」「配信終了日時が表示されていること」のように、画面のパーツがひとつずつ列挙され、それぞれを確認していくテストです。
このスタイルは、確認漏れを防ぐという観点では一定の意味がありましたが、自動化を視野に入れると、以下のような問題が見えてきました。
- テストの単位がユーザーの目的と乖離している：「要素Aの表示確認」「要素Bの表示確認」と並んでいても、それが何のユーザーシナリオを担保しているのかが不明瞭
- 項目数が膨らみやすい：同じ画面の要素を画面ごとに繰り返し確認することになり、機械的な確認項目が無限に増えていく
- 自動化したときの価値が見えにくい：1要素1アサーションのテストを大量に走らせても、ユーザー体験のリスクをどこまで担保できているかが定量化しにくい
そこで私たちは、リグレッションテストをユーザーシナリオに沿ったend-to-endのテストに書き直しました。
「ユーザーが何をしようとしていて、そのために画面をどう操作し、結果として何が起きるべきか」を一つのシナリオにまとめ、その流れの中で要素の表示や挙動を検証する形に変えていきました。
書き直しに合わせて、テストスイートそのものの最適化も同時に進めました。
検証デバイスの精査、テストファイルの命名規則の整理、テストデータの記述ルール化、不具合があっても次回対応となるケースの除外といった、自動化と独立しても価値のある手動テストの整理も、自動化準備と並行して進めました。
テストケースの書き直しと最適化による効果は2つありました。
- テストの意義そのものが明確になった：1つのテストケースが「ユーザーがこれを達成できる」という保証単位になり、優先度づけやスコープの取捨選択が判断しやすくなった
- 自動化との相性が大幅に上がった：E2Eテストフレームワークは、もともとユーザー操作を起点としたシナリオの記述に最適化されており、書き直し後のテストはほぼそのまま自動化のテンプレートに乗せられる形になった
「既存のテストをそのまま自動化する」のではなく、自動化を視野に入れてテストそのものを再設計する。 この順序が、その後の実装フェーズの速度と質を大きく押し上げました。
ツールの選定
自動化ツールには、大きく分けてコード型OSS（Playwright/Cypress/Seleniumなど）とローコードSaaS（Autify/MagicPod/mablなど）の2系統があります。 私たちは双方を比較したうえで、最終的にコード型OSS（Web: Playwright、iOS: XCUITest、Android: Espresso）を選定しました。
選定にあたって特に重視したのは、プロダクトの開発サイクルとの親和性とメンテナンス性です。
- ランニングコストを抑えられる：実行回数やシナリオ数に制限がなく、追加コストなしでスケールできる
- プロダクトの開発プロセスに乗せやすい：各プラットフォームの開発言語と同じ言語でテストを書ける。Page ObjectモデルやCI/CDへの組み込みも、エンジニアが普段使うワークフローに載せやすい
- 柔軟性が高い：HTTPリクエストの傍受やフィクスチャの差し替えなど、TVer特有の検証要件にあわせて拡張できる
SaaSにはレコーディングによるテスト量産しやすさという強みがある一方、メンテナンス性や実行制限、ランニングコストの面で、私たちが向かいたい方向とはトレードオフが大きいと判断しました。

AI学習への利用拒否をrobots.txtで一括指定へ OpenAIやGoogleなどが対応表明
米OpenAI、米Google、米Microsoftは10月30日（現地時間）、Webサイト運営者がAI学習へのコンテンツ利用に関する意向を複数のAI企業にまとめて伝えられる共通の仕組みに対応する方針をそれぞれ発表した。米Anthropicも実装を進めている。この仕組みは、Anthropicの標準化担当者、ケビン・ケリー氏が同日付で標準化団体IETF（Internet Engineering Task Force）に提出したInternet-Draft（インターネット標準の草案）で提案されている。
これまでWebサイト運営者は、AI企業ごとにクローラーを識別し、それぞれに合わせてルールを書き分ける必要があった。新しい仕組みでは、Webサイトへのクローラーのアクセスを制御する「robots.txt」に共通のシグナルを記述することで、複数のAI企業に学習への利用を拒否または許可する意向を一括して伝えられる。IETFのAI Preferences（AIPREF）ワーキンググループでの議論を基にしたもので、OpenAIは、各社が共通のシグナルに対応することで運営者の負担を軽減できるとしている。
ドラフト「Machine-Readable Training Preference Signal」では、robots.txtの「User-Agent」行に「__usage_ai-training」というポリシートークンを指定する。このトークンの下で「Disallow」はAI学習への利用を拒否する意向、「Allow」は許可する意向を示す。例えば「User-Agent: __usage_ai-training」の下に「Disallow: /」と「Allow: /press-kit/」と記述すれば、/press-kit/以下を除く全てのパスについて、学習に使わないよう求める意思表示になる。
この指定は従来のクロール制御とは独立しており、コンテンツのクロール自体を禁止するものではない。クロールを制限したい場合は、引き続き各クローラー向けのルールを使う。共通トークンを指定しなければ、AI学習について特に意向を表明していないと解釈される。新しいディレクティブや文法を導入しないため、既存の解析プログラム（パーサー）の動作には影響しないという。
対象とする「AI学習」は、生成AIモデルの学習済みパラメータを変更するためにコンテンツを利用することと定義されており、生成以外の用途だけに使うモデルの学習は含まない。また、各企業が独自に提供する制御手段を共通シグナルより優先させたり、個別契約に基づいて異なる取り扱いをしたりすることも認めている。なお、このドラフトは個人名義で提出されたもので、現時点ではIETFの標準化プロセス上の正式な地位を持たない。
各社の対応予定時期は異なる。OpenAIは今後数カ月以内の対応を目指し、実装時に詳細を改めて公表するとしている。robots.txtによる既存のクローラー制御は引き続き適用する。同社は他のAI企業にも共通シグナルを尊重するよう呼び掛けた。
Googleは、他のAI企業とともに2027年の対応を目指す。Webサイトが共通シグナルでAI学習への利用を拒否し、かつ同社独自の制御手段「Google-Extended」を明示的に指定していない場合は、Google-Extendedによる利用も拒否したものとして扱う方針だ。Google-Extendedは、同社が2023年から提供しているAI学習向けの制御手段で、共通シグナルの導入後も引き続き利用できる。
Google-Extendedによる利用を明示的に許可したサイトは、GeminiアプリがWebコンテンツを参照して回答を生成する「グラウンディング」の対象となり、回答内で紹介されてクリックを得る可能性があるという。
Googleは今回の提案について、AI学習に関する業界共通の制御を求めてきたパブリッシャーや市民団体、規制当局などの声を反映したものだと説明している。また、robots.txtを機械可読な意思表示の主要な手段として認める、欧州連合（EU）のAI規制法「EU AI Act」に基づく汎用AIモデル提供者向け行動規範とも整合するとしている。
Microsoftは2027年2月1日から、Webページをクロールする際に新しい設定を読み取り、適用を開始する。共通シグナルに加え、AI学習への利用の可否をmetaタグやHTTPヘッダでページ単位でも指定できるようにし、これらをrobots.txtの設定より優先させる。

Computer use for AI agents: read and operate desktop apps through the OS accessibility tree.
A CLI and C library for macOS, Windows and Linux. A snapshot returns JSON with a ref for every element an agent can act on. The agent acts on a ref and snapshots again to check, with no pixel matching; the loop stays in your agent.
On macOS, CLI calls reuse a private command host for each snapshot namespace and binary build. It retains native accessibility objects so a removed row cannot silently resolve to a surviving row with the same identifier. The host exits after 15 idle minutes. TMPDIR must be owned by the current user with mode 0700; the standard macOS per-user temporary directory satisfies this requirement. Headless calls still prohibit foreground activation and synthesized input.
Snapshots, clipboard reads, screenshots, command output and debug artifacts can contain private desktop content. Keep them out of public logs and uploads. 月額課金型MMORPG『ファイナルファンタジーXIV』（以下、FF14）が、ゲームの根幹に関わる大きな変更を進めている。
2026年10月31日、幕張メッセで開催された「FINAL FANTASY XIV FAN FESTIVAL 2026 in TOKYO」。プロデューサー兼ディレクターの吉田直樹さんは、次期拡張パッケージで導入する新システムについて説明した。
その中心にあるのは、プレイヤーが毎日ゲームを遊ばなくても、自分の生活に合わせて楽しめる仕組みだ。
日々のプレイを前提とした進行システムの見直し。長時間の拘束が避けられなかったコンテンツの分割。そして、わずか5分の空き時間でも楽しめる新コンテンツの導入。
長く遊んでもらうことが重要なオンラインゲームが、なぜ「毎日遊ばなくてもいい」方向へ進むのか。
基調講演で発表された変更から、そのゲームデザインの思想を読み解く。
「毎日遊ぶ」から「遊べる日に遊ぶ」へ
「最も大きなゲームデザインの進化が、このデイリーからウィークリーへ、という変化になります」
基調講演で吉田さんがそう強調したのは、プレイヤーのゲームの進め方に関わる変更だった。
これまでオンラインゲームでは、毎日のログインや日課となるコンテンツの消化を通じて、報酬や成長に必要なポイントを獲得する仕組みが広く採用されてきた。
継続して遊ぶ動機になる一方、忙しくてプレイできない日が続けば、報酬を取り逃したり、ほかのプレイヤーから遅れたりすることへの焦りにもつながる。
FF14が目指すのは、そうした日々のプレイを前提とした仕組みからの転換だ。
「毎日遊ぶから、一週間単位で遊べるタイミングでまとめて遊ぶ」
吉田さんは新たな方向性をこう説明した。
もちろん、毎日少しずつ遊ぶこともできる。ただし、平日は忙しいから週末にまとめて遊ぶ、といったプレイスタイルでも進行できるようにする。
そのための仕組みの一つが、さまざまなゲーム内活動で獲得できる「アクティビティポイント」だ。
対象となる活動は細かく設定され、メインクエストやサブクエストも、クエスト一つをクリアするごとにポイントを得られる。繰り返し達成できるミッションも用意されるため、必ずしも多種多様なコンテンツを消化する必要はない。
「これもやらなきゃ、あれもやらなきゃ、そっちもこっちもじゃなくて、好きなことを繰り返してもいい」
「ミッションには多数の項目があります。シナリオ、バトル、ギャザラー、クラフター、PVP。あまり項目を気にせず、どんどん遊んでもらいたい」
「とにかくFF14を楽しく遊んでいれば、何かしらポイントが得られるというところを目指しています」
吉田さんが説明したのは、そんな遊び方だ。
さらに興味深いのは、前週に獲得しきれなかったポイントを、翌週に取り戻せる仕組みも用意されていること。
当週分のポイントを獲得し終えた後、前週に取り残したポイントがあれば、さかのぼって獲得できるという。
先週は仕事が忙しかった。でも、今週は時間がある。そんなとき、まとめて遊んで進行を取り戻せる。
毎日ログインすることを求めるのではなく、プレイヤー自身が、いつ、何を、どれだけ遊ぶかを決められるようにする。
今回の変更には、そんな考え方が表れている。
「20〜35分は長い」24人レイドを前後半に分割
こうした方向性は、日々の進行システムだけにとどまらない。
今回、吉田さんが大きな変更を発表したのが、24人のプレイヤーで協力して挑む「アライアンスレイド」だ。
従来のアライアンスレイドは、複数のボス戦や道中の戦闘を経て、最後まで攻略する構造になっている。
吉田さんによれば、所要時間はおおむね20〜35分。途中で全滅すれば、さらに時間がかかる。
長年採用してきた方式だが、現在は大きな課題を抱えているという。
「現状のやっぱり最大の問題点は、コンテンツ完了までの時間が長いということです」
吉田さんは、忙しい現代のプレイヤーにとって、アライアンスレイドの拘束時間が長くなっていると指摘する。
「時間というものが今よりどんどんもっと貴重なものになっていってる」
時間の価値が高まるなかで、プレイに要する時間に見合った報酬を設定することも難しくなっているという。
さらに、欲しい報酬を得るために何度も挑戦する際には、コンテンツの長さがモチベーションを下げる原因になる。短く、比較的攻略しやすいレイドにプレイヤーが集中し、マッチングが偏る問題も生じていた。
そこでFF14が選んだのは、報酬を増やすだけでも、攻略を簡単にするだけでもない。
アライアンスレイドそのものを、前半と後半の二つに分割するという変更だ。
24人で協力して攻略するというコンセプトは維持しつつ、前半と後半でそれぞれ独立してマッチングできるようにする。
例えば、今日は前半だけ遊び、後半は明日挑戦する、といったことが可能になる。初回はストーリーの進行に沿って前半から後半へ進む必要があるものの、それぞれを別のコンテンツとして遊べる設計だ。
さらに、報酬の獲得方法も見直される。
従来は、欲しい装備が出現しても、ほかのプレイヤーとの抽選（ロット）に負ければ入手できなかった。吉田さんによれば、こうした仕組みも変更されるという。具体的な新方式については、今後説明する予定だ。
注目したいのは、プレイヤーの時間的負担を減らすために、長年続けてきたコンテンツの構造にまで手を入れていることだ。
遊ぶ時間が限られているユーザーに対して、「まとまった時間を確保してほしい」と求めるのではない。
限られた時間でも楽しめるように、コンテンツの側を変える。
それは、単なる利便性の改善以上の意味を持つ変更といえるだろう。
5分だけでも遊べる。しかも、長く遊ばなければ損をするわけではない
もう一つ、今回の発表で象徴的だったのが、新コンテンツ「Gauntlet of Power」だ。
これは4人のプレイヤーで、インスタンスダンジョンのボスと連続して戦うコンテンツ。
特徴の一つは、これまでに登場した200体以上のボスから、ランダムに対戦相手が選ばれることだ。新しいダンジョンが追加されれば、そのボスも対象に加わっていくという。
ただし、参加者がまだ開放していないダンジョンのボスは選ばれない。ストーリーのネタバレを避けるための配慮だ。
また、新たに導入されるレベル調整の仕組みにより、レベルの異なるプレイヤー同士でも、それぞれが習得済みのアクションを使って一緒に戦える。
そして、このコンテンツの設計思想を最もよく表しているのが、ボスを1体倒すたびに、続けるかどうかを投票で決めるという仕組みだ。
全員が続行を希望すれば次の戦闘へ進む。一方、1人でも終了を希望すれば、その時点で終了となる。
「ほんと一瞬空いた時間5分でやりたいとか、たっぷり5戦分やりたいとか、そんな目的に合わせて」
吉田さんは、短時間だけ遊びたい人も、じっくり連戦したい人も、それぞれの目的に合わせて楽しめるようにしたと説明した。
さらに、5戦を最後までクリアしなければ得られないような、特別に大きなボーナスは設けないという。
ここが重要だ。
5分だけ遊べる仕組みをつくっても、最後まで遊んだ方が圧倒的に得をする報酬設計になっていれば、結局は長時間のプレイを促すことになる。
しかし、Gauntlet of Powerでは、短時間で切り上げること自体が不利になりすぎないよう配慮されている。
プレイヤーに選択肢を与えるだけでなく、その選択を報酬によって事実上制限しない。
今回発表された仕様からは、そうした意図が読み取れる。
オンラインサービスにとって、ユーザーに継続して利用してもらうことは重要だ。
毎日アクセスしてもらうこと。できるだけ長くサービスを使ってもらうこと。それらがプロダクトの成長を測る指標になることもある。
しかし、ユーザーがサービスに費やす時間と、そこから得られる価値は、必ずしも比例しない。
FF14が今回示したのは、プレイヤーがゲームに生活を合わせるのではなく、ゲームの方がプレイヤーの生活に歩み寄るという変化だ。
毎日遊ばなくてもいい。好きなことを繰り返してもいい。まとまった時間がなければ、途中で区切ってもいい。
もちろん、こうした変更が実際のプレイ体験にどう作用するかは、実装後の評価を待つ必要がある。
それでも、長く愛されるサービスをつくるために、ユーザーの時間をどこまで求めるべきなのか。
吉田さんが示した一連の変更は、ゲームの外でプロダクトをつくるエンジニアにとっても、考えるきっかけになりそうだ。

- 2026年10月29日にセキュリティ修正版「Contact Form 7 6.2.4」を公開しました。
- 脆弱性が確認された対象はバージョン6.2～6.2.3です。
- 複数の欠陥を組み合わせると、認証不要で本来許可されないファイルをアップロードし、一時ファイルを削除せず残せる場合があります。

- 問題はShinya Murakami氏とJakub Herman氏が発見し、WPScanを通じて報告しました。
- セキュリティ強化は旧系列の利用者にも有効なため、開発元はすべての利用者に6.2.4への更新を推奨しています。

streamAppendHTML() で AI の回答を HTML のままストリーミング描画する
LLM の回答を逐次描画するとき、届いた文字列全体を毎回パースして DOM を置き換える実装では、要素が作り直され続けてテキストの選択状態が失われたりします。streamAppendHTML() は WritableStream を返し、届いた HTML を要素の末尾へ順にパースします。この記事では streamAppendHTML() の使い方とサニタイズの挙動について紹介します。
LLM の回答を画面に少しずつ表示するチャット UI では、未完成の回答を描画し続ける必要があります。最も単純な実装は、届いた内容全体をチャンクごとにパースして要素を置き換える方法です。この方法では回答が長くなるほどパースし直す量が増え、更新のたびに要素が作り直されます。その結果、テキストの選択状態が失われたり、1 度開いた <details> が閉じてしまったりします。そのため実際のチャット UI では、Markdown ライブラリが完成した部分を処理し直さない工夫をしています。
streamAppendHTML() を使うと、この処理の一部をブラウザに任せられます。HTML を文字列のまま要素の末尾へストリーミングでき、すでに描画した要素は作り直されません。
この記事では streamAppendHTML() の使い方とサニタイズの挙動について紹介します。
Warning
2026 年 10 月 31 日時点の手元の確認では、Chrome 158 Beta 以降でフラグなしで streamAppendHTML() が使えます。Chrome と Edge の 148 以降は chrome://flags/#enable-experimental-web-platform-features を有効にすると試せます。Safari と Firefox は未対応です。
従来の実装で起きること
LLM の回答を逐次描画する最も単純な実装方法は次のようになります。届いた文字列を連結し、そのたびに全体を要素へ設定します。
textStream() はレスポンスボディを文字列のストリームとして読み出すメソッドです。setHTML() は Sanitizer API の一部で、HTML をサニタイズしてから要素の内容を置き換えます。
このコードは write() が呼ばれるたびに、回答の先頭からパースし直して子要素をすべて置き換えます。その結果、次の問題が起きます。
- 回答が長くなるほど、1 回の更新でパースする文字列が長くなる
- 開いた <details>、テキストの選択範囲など、要素に結びついた状態が失われる
- CSS アニメーションが更新のたびに最初から再生される
実際のチャット UI で使われている工夫
Chrome の公式ガイドも、蓄積した全文を innerHTML に代入する方法は安全でなく遅いと説明しています。実際のチャット UI で使われるライブラリは、Markdown の回答を前提に次のような工夫をしています。
- 回答をブロックに分けてメモ化する: Streamdown は段落やコードブロックなどの単位で結果を保持し、トークンが届くと影響を受けたブロックだけを再レンダリングする
- ストリーミング対応のパーサーを使う: streaming-markdown はチャンクごとに処理して新しい要素を追加するだけなので、表示済みの要素を変更しない
- 未完成の記法を補う: Streamdown が使う remend は **bold text を **bold text** に補ってから描画する
Markdown では * が 1 つ届いただけでは、リストなのか強調なのかが確定しません。streaming-markdown は記号を見た時点で楽観的に要素を作り、remend は足りない記号を補うことで、途中の状態でも描画できるようにしています。
streamAppendHTML() は、タグが完成するまでの保持と要素の追加をブラウザの HTML パーサーが行う API です。メモ化の仕組みがなくても、完成した部分を処理し直さずに描画できます。
Note
LLM に HTML を出力させる必要があります。回答を Markdown のまま扱う場合は、上記のライブラリが引き続き選択肢になります。
streamAppendHTML() の基本
streamAppendHTML() は HTML 文字列を受け取らず、WritableStream を返します。fetch のレスポンスをこのストリームへ接続すると、チャンクが届くたびに要素の末尾へ HTML がパースされます。
Note
response.body はバイト列のストリームなので、直接接続しないでください。Uint8Array が文字列に変換され、60,112,62 のような数字の並びが描画されます。textStream() を使うと、UTF-8 のテキストとして受け取れます。
Note
チャンクが <a hr のようにタグの途中で切れても、呼び出し側で待つ必要はありません。パーサーが内部に保持し、タグが完成してから DOM に反映します。未完成のタグが文字列として表示されることはありません。
streamAppendHTML() 以外にも、挿入位置ごとにメソッドが用意されています。
Safe 版と Unsafe 版の違いは、サニタイズの有無です。Unsafe 版はデフォルトではサニタイズを行わず、HTML をそのままパースします。Safe 版はデフォルトでサニタイズを行い、XSS 攻撃につながる要素や属性を除去します。チャットの回答は既存の要素の末尾へ追加していくので、この記事では streamAppendHTML() を使います。

実際に streamAppendHTML() を使った描画を試してみましょう。比較用に、前述の setHTML() で全体を置き換える最も単純な実装も用意しました。次のコードは、/api/answer から回答を取得し streamAppendHTML() で描画します。sanitizer の設定については後述します。

どちらも回答は同じ速さで表示されますが、setHTML() 版で開いた <details> は次のチャンクで閉じてしまっていることがわかります。streamAppendHTML() 版の <details> は次のチャンクが届いても開いたままです。
LLM の出力は信頼できない入力として扱う
ストリーミング描画には、LLM の出力をそのまま DOM に入れるという危険があります。LLM は検索結果や Web ページ、ユーザーが添付した文書を入力として読みます。それらに埋め込まれた指示に従って、LLM が悪意のある HTML を出力する可能性があります。この攻撃はプロンプトインジェクションと呼ばれます。
外部のコンテンツに誘導された LLM が、次の HTML を回答に混ぜた場合を再現します。<img> の URL には会話中の情報を含め、別オリジンの攻撃者のサーバーへ送信します。攻撃者のサーバーは 404 を返すので onerror が発火し、ページの DOM を書き換えます。
左は streamAppendHTMLUnsafe()、右は streamAppendHTML() で同じ回答を描画します。
streamAppendHTML() を使用した場合は <img> と <script> が除去され、回答のテキストだけが描画されていることがわかります。一方で streamAppendHTMLUnsafe() を使用した場合は <img> が描画され、onerror が実行されて DOM が書き換えられてしまいました。
streamAppendHTMLUnsafe() 版においても <script> は実行されていないことに注目してください。Unsafe 版の runScripts オプションがデフォルトで false だからです。
デフォルトのサニタイザが除去するもの
Safe 版の sanitizer オプションのデフォルトは "default" で、ブラウザに組み込まれた設定が使われます。この設定は XSS を防ぐだけでなく、許可リスト方式で多くの要素と属性を除去します。Chrome 158 Beta と Chrome 159 で実際の結果を確認すると、以下のようになりました。
new Sanitizer().get() を実行すると、許可されている要素と属性の一覧を取得できます。
許可する要素を絞る
チャットの回答で使う要素が決まっているなら、Sanitizer で許可する要素を列挙するほうが、攻撃者が使える要素を減らせます。実際に比較のデモでも次の設定を使っています。<details> はデフォルトでは除去されてしまうので、明示的に許可しています。
Safe 版は、設定で許可しても XSS につながるものを通しません。例えば elements に "script" を指定しても <script> は除去されます。
Warning
サニタイザが防ぐのは XSS であり、外部への情報送信は防ぎません。例えば <img> の src を許可すると、URL へのリクエストは送信されます。画像を許可する場合は、CSP の img-src などで送信先を制限してください。
回答の生成を止める
チャット UI の「生成を停止」ボタンは AbortController で実装できます。同じ signal を fetch() と pipeTo() に渡します。
中断すると pipeTo() の Promise は AbortError で拒否されます。<p>one<ul><li>two まで届いた時点で中断した場合、DOM は中断前と同じ <p>one</p><ul><li>two</li></ul> のまま残りました。閉じタグが届いていなくても、それまでに描画した部分が崩れることはありません。
次の動画では、回答の途中で「生成を停止」をクリックして AbortError が発生する様子を示しています。回答の続きは描画されませんが、途中まで描画した内容はそのまま残っています。
まとめ
- streamAppendHTML() は WritableStream を返し、response.textStream().pipeTo(element.streamAppendHTML()) で HTML を要素の末尾へ逐次パースする
- 全置換の課題に対して Markdown ライブラリはブロックのメモ化やストリーミングパーサーで対処しており、streamAppendHTML() は同様の処理を HTML についてブラウザが担う
- タグの途中で切れたチャンクはパーサーが保持するので、未完成のタグは DOM に現れない
- LLM の出力はプロンプトインジェクションの影響を受けるので、信頼できない入力として Safe 版で描画する
- streamAppendHTMLUnsafe() はデフォルトではサニタイズを行わないので、onerror などのイベントハンドラ属性が実行される。<script> は runScripts がデフォルトで false のため実行されない
- デフォルトのサニタイザは <img>、<details>、class も除去するので、必要な要素は Sanitizer の許可リストに指定する

2026年11月1日 09:00
OpenAIやGoogle、Microsoft、Anthropicは、Webサイトの運営者がrobots.txtを使って、AIの学習可否などを指定可能にする共通仕様の策定を進めると発表した。2027年の導入を目指す。
robots.txtは、Webサイトにおいて検索エンジン等のクローラー(サイトから情報収集する仕組み)へのアクセス可否を示すファイル。robots.txtを指定することで、検索サービスやAIサービスに対し、対象となるページやWebサイトの情報収集を許可する、もしくは拒否するなどを、Webサイトの運営者側が決める仕組みとなっている。しかし、AIサービスにおいては、robots.txtを無視して情報収集するケースも多く、日本においても新聞協会らが問題視している。
そのため、Webサイト運営者はクローラーを個別に識別し、企業ごとにルールを管理する必要があった。今回の取り組みでは、業界で共通のシグナルに対応することで、運営者の負担軽減などを図る狙い。
Googleによれば、Webサイト所有者が、robots.txt内で共有の「ポリシートークン」を使用することで、参加しているAIプロバイダー全体にわたる設定を指定できるようにする。
Googleの例では、Webサイト事業者やパブリッシャーは、「Google-Extended」という仕組みを使うことで、検索でのクロールを許可しながら、Geminiによる学習を拒否するなどの設定は可能となっている。こうした設定をrobots.txtにおける共通の仕組みとして整備することが今回の取り組みだ。
この取り組みは、Internet Engineering Task Force(IETF)のAI Preferencesワーキンググループにおいて協議して策定し、27年に各社導入予定。Googleは27年の導入を予定しているほか、OpenAIは今後数カ月以内での導入を目指すとしている。また、Microsoftは27年2月から適用する方針。
共通仕様を策定したうえで、各社の独自のクローラー制御などは継続。Googleでも、より細かな設定はGoogle-Extendedを活用するという。また、Microsoftはページ単位での学習設定や独立したグラウンディング設定なども追加する。

風音屋（@Kazaneya_PR）のゆずたそ（@yuzutas0）です。 この記事では、AIエージェント向けの業務手順書「Agent Skills」の設計方法を紹介します。 実際に私が使っている「ミーティング日程調整」スキルを題材にして、8つのコツを解説します。
はじめに
AIに「日程調整をやっておいて」と頼むと、たいていはどちらかの反応が返ってきます。 ひとつは「何時間の打ち合わせですか」「相手はどなたですか」「候補は何日分ほしいですか」と質問攻めにされて、こちらが全部答えるまで動いてくれないパターン。 もうひとつは、聞かずに勝手に候補を並べてくるものの、いざ見てみると、集中作業のために空けている曜日や祝日、ランチ時間にまたがる時間帯が平気で混じっているパターンです。
この違いを生んでいるのは、AIの性能ではありません。 「業務手順」と「ドメイン知識」を渡していないことです。 新入社員に日程調整を任せる場面を思い浮かべると分かりやすいでしょう。 その業務を担当していた先輩は、口には出さない判断基準を無数に持っています。 「水曜はノー会議デーなので入れない」「ランチの時間帯には打ち合わせを入れない」「候補は少なくとも3日分を並べる」といった具合です。 この暗黙知を渡さないまま「よろしく」と頼むと、新入社員はいちいち質問しに来るか、聞かずに独自解釈で進めて事故を起こすかのどちらかになります。
AIに対して、この「新入社員に渡す業務手順書」の役割を担うのが「Agent Skills」（以下、スキル）です。
スキルとは、AIに読ませる前提で書かれた業務手順書のことです。
たとえばClaude Codeでは、スキルのフォルダを .claude/skills/ に置くだけで、依頼内容に応じてAIが自動で読み込んでくれます。
さらに、スキル自身をAIに改修させることもできます。
新入社員がマニュアルの不備を見つけたら、その場で直してもらうのと同じ感覚です。
画像はメール返信業務の例ですが、日程調整のスキルも同じ体裁で書けます。 本記事の画像は技術カンファレンス「Data Engineering Summit 2026」の登壇資料から引用しています。
日程調整という題材を選んだ理由は、暗黙知が多く、判断が細かく、失敗パターンも豊富で、スキル設計の勘所が全部詰まっているためです。 同じ考え方は「経理データからの月次コスト集計」「会議録画からのロードマップ更新」など、バックオフィスを含むあらゆる業務にそのまま応用できます。
スキルのサンプルを見る
言葉で説明する前に、スキルのサンプルを見ていただきます。 といっても、そのままの転載は難しいため、社内の情報を伏せて架空の業務設定に書き起こし、全体から一部を抜粋しています。
このスキルは複数のファイルでできています。 ファイル構成は以下のとおりで、それぞれの役割は後述します。

description: |
What: 日程調整に関わる2つの業務手順を配下に持つ。
(1) 単発のミーティング設定・リスケ: 相手・目的・所要時間・希望期間を確認し、空き枠から候補を提示して依頼文のドラフトを作る。
(2) 月次のカレンダー衝突チェック: 今後の予定を巡回し、祝日・ダブルブッキングなどの衝突を検出してリスケ候補と依頼文ドラフトを提示する。
Why: 「気付いたら会議当日」を避けるため。早く手を打つほど相手の負担が小さく、こちらも日程を確保しやすい。
When: (1) ユーザーが「◯◯さんとミーティング設定して」等で依頼した時。
(2) 月初・週初の予定棚卸し時、または明示的に呼び出された時。
Where: ローカル開発環境。書き込みはユーザー承認後の共有チャットへの投稿のみ、カレンダーへの書き込みは行わない。
allowed-tools: Bash, Read, Edit, Write, Grep, Glob, Task

# 業務手順（1）単発のミーティング設定・リスケ
## Step 1: 依頼内容の確認（未指定ならヒアリング）
以下の必須項目のうち、依頼に含まれていないものはユーザーに聞く。
デフォルト値を持たない項目を勝手に決めない。
| 項目 | 内容 |
| ---- | ---- |
| 相手 | 先方の社名・氏名。社外か社内かの判別に使う |
| 目的 | 何のためのミーティングか。予定タイトルにも使う |
| 所要時間 | デフォルトなし。必ず聞く（例: 30分・60分・90分） |
| 希望期間 | デフォルトなし。必ず聞く（例:「来週中で」「今月中で」） |
## Step 2: 空き枠の計算（スクリプトに委ねる）
自分のカレンダーを取得したうえで、以下をスクリプト（analyze.py）で計算する。
AI側での判断は入れない。
- 空き枠の候補時間帯を◯△✕のゾーンで分類する
- 前後30分のバッファが取れない候補は◯から△に降格する
- 候補が同じ日に偏らないよう、日付を分散して5日分を目標に選ぶ
## Step 3: 候補の提示と依頼文の作成
Step 2の結果を読み、以下の2つを整形する。
- 候補提示（ユーザー向け、ラベルと補足を含む）
- 依頼文ドラフト（取引先向け、ラベルと補足を含まない自然な文章）
依頼文の宛先は「（宛先：〇〇様）」のプレースホルダにする（誤送信防止）。
## Step 4: 送信前の承認（人間の判断を待つ）
取引先向けの依頼文は、AIが自動で送らない。文面をユーザーに提示し、承認を得てから送信する。
# 判断基準
## 予定の3分類
| 分類 | 説明 |
| ---- | ---- |
| 重複してもよい | 自分は出なくても成立する社内イベント（並行で他予定を入れてよい） |
| 相談すれば動かせる | 社内1on1・任意参加の会（相手と調整すれば動く） |
| 動かせない | 取引先との打ち合わせ・採用面接（動かさない前提） |
## 時間帯ポリシー
- 業務時間: 月・火・木・金の10:00〜19:00
- ノー会議デー: 水曜（打ち合わせを入れない曜日を1日確保し、集中作業や突発対応に充てるため）
- ランチ枠: 11:30〜13:00
- ◯ゾーン: 13:30〜18:00
- △ゾーン: 10:00〜11:30、13:00〜13:30、18:00〜19:00
- ✕ゾーン: それ以外、および祝日・年末年始・お盆

- OK: スクリプトが候補件数を確定し、AIは文面の言い回しだけを担う

- ヘッダー：「何をするか」「いつ使うか」「どこまで書き込んでよいか」の要約

「シェル実行」「ファイルの読み書き」「検索」「別のAIへの作業依頼」といった、AIが作業に使う道具の名前を並べます。
このスキルの場合、空き枠計算スクリプトをBashで実行し、計算の中間結果をReadやWriteで読み書きするために使います。
人間が読みやすい業務手順は、AIにとっても読みやすい業務手順になります。
以降の章では、このサンプルに加えて、同じスキル配下のもう1つの業務手順である月次のカレンダー衝突チェックからも素材を引きながら、そこに込めた8つのコツを見ていきます。 各節で挟むスキル断片は、いずれも手順書・仕様書・テストを含むこのスキルの一式から切り出したものです。 並び順は「書く（①〜④）→ 守る（⑤）→ 確かめる（⑥〜⑦）→ 育てる（⑧）」の順で、スキル作りの時系列に沿っています。

# 判断基準
## 予定の3分類
| 分類 | 説明 |
| ---- | ---- |
| 重複してもよい | 自分は出なくても成立する社内イベント（並行で他予定を入れてよい） |
| 相談すれば動かせる | 社内1on1・任意参加の会（相手と調整すれば動く） |
| 動かせない | 取引先との打ち合わせ・採用面接（動かさない前提） |
## 時間帯ポリシー
- 業務時間: 月・火・木・金の10:00〜19:00
- ノー会議デー: 水曜（打ち合わせを入れない曜日を1日確保し、集中作業や突発対応に充てるため）
- ランチ枠: 11:30〜13:00
## 空き枠のゾーン
- ◯ゾーン（推奨）: 13:30〜18:00
- △ゾーン（許容、優先度低い）: 10:00〜11:30、13:00〜13:30、18:00〜19:00
- ✕ゾーン（候補から除外）: 上記以外、および祝日・年末年始・お盆
## 候補の並べ方
- 5日以上のユニーク日付を目標とし、確保できなければ3日まで妥協する
- 同じ日に候補が偏らないよう、日付を分散して選ぶ
3分類がないと、AIは既存の予定をすべて同じ重みで扱い、「社内イベントがあるので候補が出せません」と言い出します。 分類を書き出しておけば、社内イベントと並行する枠も候補にでき、取引先との打ち合わせと重なる枠は候補から外す、という当たり前の判断を任せられます。
時間帯ポリシーの「水曜は入れない」は、規則だけでなく「打ち合わせを入れない曜日を1日確保し、集中作業や突発対応に充てる」という背景をセットで書きます。 背景が書いてあると、AI側でも例外の相談を返せるようになります。 たとえば4月、期初を迎えたお得意様の役員と1年間の方針を決めるような会議は、優先する価値がありそうです。 そうした打診が来たとき、背景を知っているAIは「水曜ですが例外にしますか」と相談できます。 ◯△✕のゾーン化も、時間帯を推奨・許容・除外という意味で整理できるので、後で見直すときに「どの帯を何に使う想定だったか」を復元しやすくなります。
祝日の考慮や、候補日を同じ日に固めないための日付分散も、ここに書いておきた

AI学習への利用拒否をrobots.txtで一括指定へ OpenAIやGoogleなどが対応表明
米OpenAI、米Google、米Microsoftは10月30日（現地時間）、Webサイト運営者がAI学習へのコンテンツ利用に関する意向を複数のAI企業にまとめて伝えられる共通の仕組みに対応する方針をそれぞれ発表した。米Anthropicも実装を進めている。この仕組みは、Anthropicの標準化担当者、ケビン・ケリー氏が同日付で標準化団体IETF（Internet Engineering Task Force）に提出したInternet-Draft（インターネット標準の草案）で提案されている。
これまでWebサイト運営者は、AI企業ごとにクローラーを識別し、それぞれに合わせてルールを書き分ける必要があった。新しい仕組みでは、Webサイトへのクローラーのアクセスを制御する「robots.txt」に共通のシグナルを記述することで、複数のAI企業に学習への利用を拒否または許可する意向を一括して伝えられる。IETFのAI Preferences（AIPREF）ワーキンググループでの議論を基にしたもので、OpenAIは、各社が共通のシグナルに対応することで運営者の負担を軽減できるとしている。
ドラフト「Machine-Readable Training Preference Signal」では、robots.txtの「User-Agent」行に「__usage_ai-training」というポリシートークンを指定する。このトークンの下で「Disallow」はAI学習への利用を拒否する意向、「Allow」は許可する意向を示す。例えば「User-Agent: __usage_ai-training」の下に「Disallow: /」と「Allow: /press-kit/」と記述すれば、/press-kit/以下を除く全てのパスについて、学習に使わないよう求める意思表示になる。
この指定は従来のクロール制御とは独立しており、コンテンツのクロール自体を禁止するものではない。クロールを制限したい場合は、引き続き各クローラー向けのルールを使う。共通トークンを指定しなければ、AI学習について特に意向を表明していないと解釈される。新しいディレクティブや文法を導入しないため、既存の解析プログラム（パーサー）の動作には影響しないという。
対象とする「AI学習」は、生成AIモデルの学習済みパラメータを変更するためにコンテンツを利用することと定義されており、生成以外の用途だけに使うモデルの学習は含まない。また、各企業が独自に提供する制御手段を共通シグナルより優先させたり、個別契約に基づいて異なる取り扱いをしたりすることも認めている。なお、このドラフトは個人名義で提出されたもので、現時点ではIETFの標準化プロセス上の正式な地位を持たない。
各社の対応予定時期は異なる。OpenAIは今後数カ月以内の対応を目指し、実装時に詳細を改めて公表するとしている。robots.txtによる既存のクローラー制御は引き続き適用する。同社は他のAI企業にも共通シグナルを尊重するよう呼び掛けた。
Googleは、他のAI企業とともに2027年の対応を目指す。Webサイトが共通シグナルでAI学習への利用を拒否し、かつ同社独自の制御手段「Google-Extended」を明示的に指定していない場合は、Google-Extendedによる利用も拒否したものとして扱う方針だ。Google-Extendedは、同社が2023年から提供しているAI学習向けの制御手段で、共通シグナルの導入後も引き続き利用できる。
Google-Extendedによる利用を明示的に許可したサイトは、GeminiアプリがWebコンテンツを参照して回答を生成する「グラウンディング」の対象となり、回答内で紹介されてクリックを得る可能性があるという。
Googleは今回の提案について、AI学習に関する業界共通の制御を求めてきたパブリッシャーや市民団体、規制当局などの声を反映したものだと説明している。また、robots.txtを機械可読な意思表示の主要な手段として認める、欧州連合（EU）のAI規制法「EU AI Act」に基づく汎用AIモデル提供者向け行動規範とも整合するとしている。
Microsoftは2027年2月1日から、Webページをクロールする際に新しい設定を読み取り、適用を開始する。共通シグナルに加え、AI学習への利用の可否をmetaタグやHTTPヘッダでページ単位でも指定できるようにし、これらをrobots.txtの設定より優先させる。
さらに、AIの回答生成時にWebコンテンツを参照するグラウンディングについても、独自のページ単位の制御を導入する。「Disallow」で利用を拒否できるほか、「DisallowExtended」も指定できる。後者は、CopilotやMicrosoft 365などMicrosoft自身が提供するサービスでの利用は認めながら、同社が外部企業向けに提供する「Web IQ」やMicrosoft FoundryのAPIを通じたグラウンディングでの利用を拒否する設定だ。これらの設定は、Bingの検索結果への掲載には影響しないという。
新設定は従来の「NoArchive」「NoCache」に代わるもので、Microsoftはこれらを利用しているサイトに対し、2027年3月1日までに新しい設定へ移行するよう求めている。グラウンディングの制限を維持する場合は、再クロールまでの経過措置として、Bing Webmaster Toolsでの暫定設定も必要になる。
Anthropicについては、ケリー氏がAIPREFのメーリングリストで、同社が既にドラフトへの対応実装を始めたと報告した。ただし、Anthropicのサービス全体に対応を広げるには時間がかかるとしている。
AI企業によるWebコンテンツの利用を巡っては、パブリッシャーによる訴訟が相次いでいる。米Cloudflareは7月、AI関連のクローラーを「検索」「エージェント」「学習」の用途別に管理できる機能を全顧客に開放した。Googleも6月、AI検索機能へのコンテンツ利用をオプトアウトできるトグルをSearch Consoleで提供すると発表している。

Computer use for AI agents: read and operate desktop apps through the OS accessibility tree.
A CLI and C library for macOS, Windows and Linux. A snapshot returns JSON with a ref for every element an agent can act on. The agent acts on a ref and snapshots again to check, with no pixel matching; the loop stays in your agent.
On macOS, CLI calls reuse a private command host for each snapshot namespace and binary build. It retains native accessibility objects so a removed row cannot silently resolve to a surviving row with the same identifier. The host exits after 15 idle minutes. TMPDIR must be owned by the current user with mode 0700; the standard macOS per-user temporary directory satisfies this requirement. Headless calls still prohibit foreground activation and synthesized input.
Snapshots, clipboard reads, screenshots, command output and debug artifacts can contain private desktop content. Keep them out of public logs and uploads. The optional JEV helper sends screen descriptions to a configured model provider; it is separate from the native CLI. See privacy and data handling.
Install on macOS, Windows or Linux with npm:
npm install -g agent-desktop
agent-desktop version
Bun, Yarn and pnpm can install the same package. It includes native binaries and platform helpers for x64 and ARM64. For direct execution without a JavaScript launcher, download the matching native archive from GitHub Releases and keep its helper beside the executable.
Official Homebrew and Scoop packages are being submitted; they are not yet available in the default catalogs. The repository no longer maintains a custom Homebrew tap or Scoop bucket.
- macOS needs Accessibility permission: agent-desktop permissions --guide.
- Windows needs no grant for apps at your terminal's integrity level.
- Linux needs the user's graphical session with at-spi2-core.
See installation and permissions for package-manager behavior, release archives, and building from source.

Apple was notified of the eMudhra incident on 17th October. As of 28th October, the developer tools Apple ships with macOS, including git, curl and python3, still trust the compromised certificates.
Worse, macOS 27.2, released on 26th October, did not fix the issue and undid the workaround that users had applied by hand, leaving them vulnerable again.
Meanwhile, dozens of other projects, many run by volunteers, shipped fixes days ago.
Anyone can intercept any HTTPS connection these tools make.
For git, that means clones and pulls from https:// remotes can deliver attacker-chosen code, pushes can be altered in transit, and your credentials, such as GitHub tokens, can be intercepted.
To check whether your git is affected, run:
git ls-remote https://git-emudhra.we-have-a-problem.com/check.git
A certificate error means your git is protected. If git lists a commit, your git is affected. Your connections to GitHub, or any other https:// git remote, can be intercepted and tampered with.
To see an attack end to end, run the command below in a temporary directory. It clones a repository from a test server impersonating GitHub. The -c option redirects github.com to our test server for this one command only. The server presents a github.com certificate issued by one of the compromised eMudhra intermediates.
git -c http.curloptResolve=github.com:443:15.235.19.186 clone https://fake-user@github.com/galadran/emudhra-git-test
A patched git will refuse with a certificate error. If the clone succeeds, you'll see a README.md starting with INTERCEPTED.
A real attacker would not need the extra option. Anyone on the network path between you and GitHub can redirect your traffic themselves.
You can replace the demo repository with any other, public or private. Keep the fake-user@ prefix. Without it, git would send your GitHub credentials to the test server. For example:
git -c http.curloptResolve=github.com:443:15.235.19.186 clone https://fake-user@github.com/Homebrew/brew

How the vulnerability works
When a Linux server accepts a TCP connection, the kernel tracks the half-open handshake in a lightweight "request socket," then creates a full socket once the handshake completes. If the connecting peer's IPv4 header carried options, the kernel keeps them to echo in its replies. The bug: the kernel handed those saved options from the request socket to the new connection without copying them, then freed them immediately when the connection went away, while another CPU could still be reading them to build a handshake reply. Reading freed kernel memory is a use-after-free.
The peer needs no login, and it all happens inside the kernel's handshake handling, before any application code runs. The CNA's scoring notes say the stale data can leak kernel heap memory back to the peer, steer kernel writes out of bounds, or crash the machine. Anthropic says a lost race "only fails the handshake without crashing the whole system, so a determined attacker can retry indefinitely until they succeed."

1 Background
Modern applications often spread state across a variety of systems: databases, caches, queues, data warehouses, search indices, and so on. Coordinating these systems is challenging: caches are often stale, the analytics platform might lag days behind the primary database, the search index might lose data, and transactional updates across disparate systems remains an open research problem.
ParticleDB1 aims to unify these workloads in a single engine with a special focus on AI agents and applications. It offers transactional SQL, a key-value store, vector search, live analytics, and user-defined functions called Particles.2 To integrate with existing systems, clients can connect through a variety of interfaces, including the Postgres and Redis protocols, as well as its own gRPC and HTTP2 APIs. Written from the ground up in Rust, ParticleDB claims to be orders of magnitude faster than Postgres while preserving the same safety characteristics.
ParticleDB was built by Orkes to support their workflow orchestration platform, Conductor. Conductor was initially built to store data in Redis and Postgres, but to improve performance, Orkes opted to write their own database. ParticleDB 1.0.0 offered a limited feature set specifically for Conductor’s queries, and was deployed as the backing database for some of their Conductor clusters. A few Orkes customers followed suit. In preparation for a broader release, Orkes undertook a major refactoring of ParticleDB, adding a custom wire protocol, more datatypes, additional OLAP queries, and more. While Orkes and their customers continued to run 1.0.0, they soft launched the refactored versions on particledb.ai. Orkes engaged Jepsen to test these versions of ParticleDB, beginning with 1.1.4.

こんにちは。TVerのAutomationチームで、テストや開発業務の効率化・自動化を担当している城間です。
TVerの開発組織では、2025年からリリースサイクルの短縮に取り組み、リリーストレイン（複数チームが同期して決められたサイクルでリリースを行う運用）を導入しています。
いま現在、Web、iOS、Androidの各プラットフォームはおおむね隔週でのリリースを実現できており、その背景や経緯の詳細は弊社の「計測から始める品質とスピードの両立 - TVerの開発組織改革2年間の記録」で紹介しています。
リリースサイクルを短縮するためには、リリースのたびに行うリグレッションテストを短時間かつ確実に回せる仕組みが重要になります。
しかしながら、2025年の春先まで、TVerのリグレッションテストはすべて手動で行われていました。 リリースサイクルを短縮しようとすればするほど、テスト工数が線形に積み上がっていく構造で、これを解消しない限りリリーストレインの持続的な運用はできません。
リリーストレインの運用をはじめるにあたり、迅速かつ安定して検証ができる自動テスト基盤を構築することは、私たちAutomationチームの重大なミッションでした。
本稿では、私たちが約1年間、戦略策定から運用に至るまで、段階を踏んでテストの自動化を進めてきた過程とその取り組みを紹介したいと思います。
抱えていた課題
2025年の初頭、リリース前に実施していたリグレッションテストの所要工数は、概算で以下のとおりでした。
これは、UIのリグレッションや、動画・ライブの目視確認、広告配信の検証など、複数のテストスイートにまたがる総工数の見積もりです。 継続的な機能改善とリリースを必要とするTVerサービスにおいて、毎回リリース前に数日分の検証工数を割き続ける運用には、いくつかの構造的な限界がありました。
- テストの実行に一定の工数を要し、短サイクルでのリリース対応が困難
- テスト実行の一部が属人化しており、チーム全体の生産性に波が出やすい
- 人的ミスによる軽微な不具合の取りこぼしが発生しうる
また、TVerのテストには「動いて見える」だけでは検証できない領域があります。
ユーザーの操作の裏で送信されるTVerタグ（行動ログ）、視聴データの計測用ビーコン、広告に関連するURLパラメータ置換処理といったログ系の整合性確認です。
これらはTVerの主要KPI、ひいては放送局・広告主に対する説明責任に直結する重要な検証項目ですが、マニュアルではHTTPプロキシで通信ログを目視確認するしかなく、QAチームへの負荷も再現性も大きな課題でした。
戦略の策定から始める
私たちはテストの自動化を導入するにあたり、フレームワークの選定よりも前に、まずリグレッションテストの戦略を明文化することから始めました。
自動テストを持続可能なものにするためには、何を、どこまで、どのように自動化するのかを最初に定義しておく必要があります。
スコープの定義
戦略ドキュメントでは、テストピラミッドの考え方を参考に、リグレッションテストを正常系のユーザーシナリオに絞ることに決めました。
細かな分岐や例外は単体・結合テストに任せ、リグレッションテストでは主要導線がend-to-endで機能していること、ユーザー操作によって生じるCRUD処理（作成・読み取り・更新・削除）が正しく動くことを確認する。ピラミッドの頂点に置くべき範囲に限定する、という方針です。
加えて、前述したログ系の整合性確認も、主要KPIへの影響度が高いことからリグレッションテストのスコープに含めました。
ユーザー操作の裏で送信されるログまで含めて回帰を担保する、TVerのサービス特性を反映した判断です。
実行契機の整理
次に自動テストを「いつ、どのトリガーで、何のために回すか」を整理しました。 いまは主に次の3つの実行契機で回しています。
自動テストを導入する目的は単一ではなく、同じテストアセットでも、走らせるタイミングを変えれば狙えるリスクが変わります。
この前提を最初に揃えることで、後から個別の運用設計をブレずに進められました。
E2Eテスト環境を独立して用意する
戦略の次に着手したのは、E2Eテスト専用の検証環境を各プラットフォームで揃えて用意することでした。
通常の開発環境やステージング環境を流用すると、開発作業や手動テストの副作用が自動テストの結果に影響してしまい、再現性が大きく損なわれます。 テストごとに「いまの環境はどんな状態か」を気にしないと結果を信頼できない状況は、自動化の前提を崩します。
私たちはWeb/iOS/AndroidのそれぞれのOSで、E2Eテスト専用の環境を共通で見るようにしました。実装方法はOSごとに異なりますが、テストが実行されるバックエンドは同じ独立した環境を指しています。
データの独立性とテストの再現性、この2つを早い段階で担保することが、後の運用フェーズで「テストを信じてリリース判断する」という文化を作るうえで重要でした。
リグレッションテストそのものを見直す
戦略と環境が用意できた後、私たちは自動化の実装に進む前に、もうひとつ大きな工程を挟みました。 既存のリグレッションテスト自体の作り直しです。
既存のリグレッションテストは、長らく画面の要素単位で書かれていました。
たとえば「シリーズ名が表示されていること」「エピソード名が表示されていること」「制作局が表示されていること」「配信終了日時が表示されていること」のように、画面のパーツがひとつずつ列挙され、それぞれを確認していくテストです。
このスタイルは、確認漏れを防ぐという観点では一定の意味がありましたが、自動化を視野に入れると、以下のような問題が見えてきました。
- テストの単位がユーザーの目的と乖離している：「要素Aの表示確認」「要素Bの表示確認」と並んでいても、それが何のユーザーシナリオを担保しているのかが不明瞭
- 項目数が膨らみやすい：同じ画面の要素を画面ごとに繰り返し確認することになり、機械的な確認項目が無限に増えていく
- 自動化したときの価値が見えにくい：1要素1アサーションのテストを大量に走らせても、ユーザー体験のリスクをどこまで担保できているかが定量化しにくい
そこで私たちは、リグレッションテストをユーザーシナリオに沿ったend-to-endのテストに書き直しました。
「ユーザーが何をしようとしていて、そのために画面をどう操作し、結果として何が起きるべきか」を一つのシナリオにまとめ、その流れの中で要素の表示や挙動を検証する形に変えていきました。
書き直しに合わせて、テストスイートそのものの最適化も同時に進めました。
検証デバイスの精査、テストファイルの命名規則の整理、テストデータの記述ルール化、不具合があっても次回対応となるケースの除外といった、自動化と独立しても価値のある手動テストの整理も、自動化準備と並行して進めました。
テストケースの書き直しと最適化による効果は2つありました。
- テストの意義そのものが明確になった：1つのテストケースが「ユーザーがこれを達成できる」という保証単位になり、優先度づけやスコープの取捨選択が判断しやすくなった
- 自動化との相性が大幅に上がった：E2Eテストフレームワークは、もともとユーザー操作を起点としたシナリオの記述に最適化されており、書き直し後のテストはほぼそのまま自動化のテンプレートに乗せられる形になった
「既存のテストをそのまま自動化する」のではなく、自動化を視野に入れてテストそのものを再設計する。 この順序が、その後の実装フェーズの速度と質を大きく押し上げました。

Contact Form 7 6.2.4のセキュリティ修正の概要
- 2026年10月29日にセキュリティ修正版「Contact Form 7 6.2.4」を公開しました。
- 脆弱性が確認された対象はバージョン6.2～6.2.3です。
- 複数の欠陥を組み合わせると、認証不要で本来許可されないファイルをアップロードし、一時ファイルを削除せず残せる場合があります。
- 開発元は、ファイルアップロード欄があるフォームと、ディレクトリの内容を公開する設定のHTTPサーバーとの組み合わせを攻撃対象になり得る条件として挙げています。
- 問題はShinya Murakami氏とJakub Herman氏が発見し、WPScanを通じて報告しました。
- セキュリティ強化は旧系列の利用者にも有効なため、開発元はすべての利用者に6.2.4への更新を推奨しています。
- WordPress.orgでは追加更新版6.2.4.1が公開されており、現在は同版以降への更新を推奨します。
- 6.2系にはWordPress 7.1以上、PHP 8.3以上が必要です。更新前に稼働環境との互換性を確認してください。
ファイル検証を回避し、アップロードされたファイルを残せる問題
開発元によると、Contact Form 7 6.2～6.2.3には、ファイルアップロード時の検証と送信後の一時ファイル削除に関係する複数の欠陥があります。攻撃者がこれらを組み合わせて悪用すると、通常は受け付けないファイルをアップロードできるほか、送信直後に削除されるべきファイルをサーバー上に保持できる可能性があります。
公式告知は、理論上の攻撃対象として「ファイルアップロード項目を持つフォーム」と「ディレクトリの内容を一覧表示するHTTPサーバー設定」の組み合わせを明示しています。ただし、すべてのContact Form 7導入サイトで直ちに任意のPHPコードが実行できると公表されたわけではありません。ファイルの公開範囲やサーバー上での実行可否は、運用環境の構成にも左右されます。
開発元の6.2.4告知には、この問題のCVE番号、CVSS評価、実際の攻撃による被害確認についての記載はありません。

独自に取り扱うファイル形式がある場合、開発元は`wpcf7_file_extension_safelist`フィルターフックでセーフリストを調整できると案内しています。ただし、業務上必要な拡張子だけを追加し、サーバーで実行可能なスクリプト形式を安易に許可しない運用が必要です。
また、`wpcf7_unship_uploaded_file()`の第2引数`$options`が必須となり、第3引数`$uploaded_files`が追加されました。テーマや独自プラグインでこの関数を直接呼び出している場合は、更新後の互換性を確認する必要があります。
そのほか、Functions-PHP、FormDataTree-PHP、SWV-PHPなどの依存ライブラリ更新や、UTF-8文字列の処理改善も含まれます。追加版の6.2.4.1では、WordPress.orgの変更履歴によるとFormDataTree-PHPが2.0.10に更新されています。

streamAppendHTML() で AI の回答を HTML のままストリーミング描画する
LLM の回答を逐次描画するとき、届いた文字列全体を毎回パースして DOM を置き換える実装では、要素が作り直され続けてテキストの選択状態が失われたりします。streamAppendHTML() は WritableStream を返し、届いた HTML を要素の末尾へ順にパースします。この記事では streamAppendHTML() の使い方とサニタイズの挙動について紹介します。
LLM の回答を画面に少しずつ表示するチャット UI では、未完成の回答を描画し続ける必要があります。最も単純な実装は、届いた内容全体をチャンクごとにパースして要素を置き換える方法です。この方法では回答が長くなるほどパースし直す量が増え、更新のたびに要素が作り直されます。その結果、テキストの選択状態が失われたり、1 度開いた <details> が閉じてしまったりします。そのため実際のチャット UI では、Markdown ライブラリが完成した部分を処理し直さない工夫をしています。
streamAppendHTML() を使うと、この処理の一部をブラウザに任せられます。HTML を文字列のまま要素の末尾へストリーミングでき、すでに描画した要素は作り直されません。
この記事では streamAppendHTML() の使い方とサニタイズの挙動について紹介します。
Warning
2026 年 10 月 31 日時点の手元の確認では、Chrome 158 Beta 以降でフラグなしで streamAppendHTML() が使えます。Chrome と Edge の 148 以降は chrome://flags/#enable-experimental-web-platform-features を有効にすると試せます。Safari と Firefox は未対応です。
従来の実装で起きること
LLM の回答を逐次描画する最も単純な実装方法は次のようになります。届いた文字列を連結し、そのたびに全体を要素へ設定します。
textStream() はレスポンスボディを文字列のストリームとして読み出すメソッドです。setHTML() は Sanitizer API の一部で、HTML をサニタイズしてから要素の内容を置き換えます。
このコードは write() が呼ばれるたびに、回答の先頭からパースし直して子要素をすべて置き換えます。その結果、次の問題が起きます。
- 回答が長くなるほど、1 回の更新でパースする文字列が長くなる
- 開いた <details>、テキストの選択範囲など、要素に結びついた状態が失われる
- CSS アニメーションが更新のたびに最初から再生される
実際のチャット UI で使われている工夫
Chrome の公式ガイドも、蓄積した全文を innerHTML に代入する方法は安全でなく遅いと説明しています。実際のチャット UI で使われるライブラリは、Markdown の回答を前提に次のような工夫をしています。
- 回答をブロックに分けてメモ化する: Streamdown は段落やコードブロックなどの単位で結果を保持し、トークンが届くと影響を受けたブロックだけを再レンダリングする
- ストリーミング対応のパーサーを使う: streaming-markdown はチャンクごとに処理して新しい要素を追加するだけなので、表示済みの要素を変更しない
- 未完成の記法を補う: Streamdown が使う remend は **bold text を **bold text** に補ってから描画する
Markdown では * が 1 つ届いただけでは、リストなのか強調なのかが確定しません。streaming-markdown は記号を見た時点で楽観的に要素を作り、remend は足りない記号を補うことで、途中の状態でも描画できるようにしています。
streamAppendHTML() は、タグが完成するまでの保持と要素の追加をブラウザの HTML パーサーが行う API です。メモ化の仕組みがなくても、完成した部分を処理し直さずに描画できます。
Note
LLM に HTML を出力させる必要があります。回答を Markdown のまま扱う場合は、上記のライブラリが引き続き選択肢になります。
streamAppendHTML() の基本
streamAppendHTML() は HTML 文字列を受け取らず、WritableStream を返します。fetch のレスポンスをこのストリームへ接続すると、チャンクが届くたびに要素の末尾へ HTML がパースされます。
Note
response.body はバイト列のストリームなので、直接接続しないでください。Uint8Array が文字列に変換され、60,112,62 のような数字の並びが描画されます。textStream() を使うと、UTF-8 のテキストとして受け取れます。
Note
チャンクが <a hr のようにタグの途中で切れても、呼び出し側で待つ必要はありません。パーサーが内部に保持し、タグが完成してから DOM に反映します。未完成のタグが文字列として表示されることはありません。
streamAppendHTML() 以外にも、挿入位置ごとにメソッドが用意されています。
Safe 版と Unsafe 版の違いは、サニタイズの有無です。Unsafe 版はデフォルトではサニタイズを行わず、HTML をそのままパースします。Safe 版はデフォルトでサニタイズを行い、XSS 攻撃につながる要素や属性を除去します。チャットの回答は既存の要素の末尾へ追加していくので、この記事では streamAppendHTML() を使います。

LLM の出力は信頼できない入力として扱う
ストリーミング描画には、LLM の出力をそのまま DOM に入れるという危険があります。LLM は検索結果や Web ページ、ユーザーが添付した文書を入力として読みます。それらに埋め込まれた指示に従って、LLM が悪意のある HTML を出力する可能性があります。この攻撃はプロンプトインジェクションと呼ばれます。

Sometime in the early 1990s, Claudio Grossi, a 40-year-old farmer in Parma, in northern Italy, was cleaning his attic when he turned up an old sack full of seeds that he couldn’t identify. The bag, he was sure, had been left by his late great-grandfather, who’d started the farmstead around 1915. Grossi had no idea how long the seeds had been sitting there, deprived of water, soil and sun. Dry and cracked, the kernels looked so old in the palm of his hand that he doubted anything would ever sprout from them. He carried the bag down the stairs, shook the seeds out into a pile of manure and then forgot about them.
To his surprise, the seeds soon sprouted a few different types of wheat. One was particularly striking: At six feet high, its plants were about twice as tall as commercial wheat. But the most remarkable feature came when it developed ears—the grain-studded parts at the top of the plant. All of the wheat types Grossi had previously seen grew only one such ear. But the tall wheat grew a full seven ears, always in the same pattern: a long one with six shorties bunched up around it like little fingers. Even the kernels themselves were bigger than those of average wheat. And unlike the typical pale-yellow wheat kernels, they came in a rainbow of colors—yellow, black, red, white and even green, sometimes all on the same stem. Grossi, a grain farmer his whole life, had never seen anything like it. “I thought it was a freak of nature,” he says. He couldn’t find a mention of it in agricultural books.
For Grossi, a practicing Catholic, the next insight came from a different book altogether. Leafing through a Bible at church one Sunday, he found a passage in the Book of Genesis describing a stalk with seven ears, in a dream that Joseph interprets for the Pharaoh: “And he slept and dreamed the second time: And, behold, seven ears of grain came up upon one stalk, rank and good. And, behold, seven thin ears and blasted with the east wind sprung up after them. And the seven thin ears devoured the seven rank and full ears.” To Grossi, that sounded just like the mysterious crop in his manure pile.
“I connected the dots,” Grossi says. That grain must be really ancient, he thought. And if people were farming this odd-looking wheat in biblical times, why does no one today?
Back on his farm, Grossi harvested the grain, milled it into flour and baked a loaf of bread in his kitchen. FF14が「毎日ログイン前提」を見直す。吉田直樹が挑む、プレイヤーの時間を奪わないゲーム設計
NEW! ITニュース
ゲームは、ユーザーに毎日遊んでもらうべきなのか。
月額課金型MMORPG『ファイナルファンタジーXIV』（以下、FF14）が、ゲームの根幹に関わる大きな変更を進めている。
2026年10月31日、幕張メッセで開催された「FINAL FANTASY XIV FAN FESTIVAL 2026 in TOKYO」。プロデューサー兼ディレクターの吉田直樹さんは、次期拡張パッケージで導入する新システムについて説明した。
その中心にあるのは、プレイヤーが毎日ゲームを遊ばなくても、自分の生活に合わせて楽しめる仕組みだ。
日々のプレイを前提とした進行システムの見直し。長時間の拘束が避けられなかったコンテンツの分割。そして、わずか5分の空き時間でも楽しめる新コンテンツの導入。
長く遊んでもらうことが重要なオンラインゲームが、なぜ「毎日遊ばなくてもいい」方向へ進むのか。
基調講演で発表された変更から、そのゲームデザインの思想を読み解く。
「毎日遊ぶ」から「遊べる日に遊ぶ」へ
「最も大きなゲームデザインの進化が、このデイリーからウィークリーへ、という変化になります」
基調講演で吉田さんがそう強調したのは、プレイヤーのゲームの進め方に関わる変更だった。
これまでオンラインゲームでは、毎日のログインや日課となるコンテンツの消化を通じて、報酬や成長に必要なポイントを獲得する仕組みが広く採用されてきた。
継続して遊ぶ動機になる一方、忙しくてプレイできない日が続けば、報酬を取り逃したり、ほかのプレイヤーから遅れたりすることへの焦りにもつながる。
FF14が目指すのは、そうした日々のプレイを前提とした仕組みからの転換だ。
「毎日遊ぶから、一週間単位で遊べるタイミングでまとめて遊ぶ」
吉田さんは新たな方向性をこう説明した。
もちろん、毎日少しずつ遊ぶこともできる。ただし、平日は忙しいから週末にまとめて遊ぶ、といったプレイスタイルでも進行できるようにする。
そのための仕組みの一つが、さまざまなゲーム内活動で獲得できる「アクティビティポイント」だ。
対象となる活動は細かく設定され、メインクエストやサブクエストも、クエスト一つをクリアするごとにポイントを得られる。繰り返し達成できるミッションも用意されるため、必ずしも多種多様なコンテンツを消化する必要はない。
「これもやらなきゃ、あれもやらなきゃ、そっちもこっちもじゃなくて、好きなことを繰り返してもいい」
「ミッションには多数の項目があります。シナリオ、バトル、ギャザラー、クラフター、PVP。あまり項目を気にせず、どんどん遊んでもらいたい」
「とにかくFF14を楽しく遊んでいれば、何かしらポイントが得られるというところを目指しています」
吉田さんが説明したのは、そんな遊び方だ。
さらに興味深いのは、前週に獲得しきれなかったポイントを、翌週に取り戻せる仕組みも用意されていること。
当週分のポイントを獲得し終えた後、前週に取り残したポイントがあれば、さかのぼって獲得できるという。
先週は仕事が忙しかった。でも、今週は時間がある。そんなとき、まとめて遊んで進行を取り戻せる。
毎日ログインすることを求めるのではなく、プレイヤー自身が、いつ、何を、どれだけ遊ぶかを決められるようにする。
今回の変更には、そんな考え方が表れている。
「20〜35分は長い」24人レイドを前後半に分割
こうした方向性は、日々の進行システムだけにとどまらない。
今回、吉田さんが大きな変更を発表したのが、24人のプレイヤーで協力して挑む「アライアンスレイド」だ。
従来のアライアンスレイドは、複数のボス戦や道中の戦闘を経て、最後まで攻略する構造になっている。
吉田さんによれば、所要時間はおおむね20〜35分。途中で全滅すれば、さらに時間がかかる。
長年採用してきた方式だが、現在は大きな課題を抱えているという。
「現状のやっぱり最大の問題点は、コンテンツ完了までの時間が長いということです」
吉田さんは、忙しい現代のプレイヤーにとって、アライアンスレイドの拘束時間が長くなっていると指摘する。
「時間というものが今よりどんどんもっと貴重なものになっていってる」
時間の価値が高まるなかで、プレイに要する時間に見合った報酬を設定することも難しくなっているという。
さらに、欲しい報酬を得るために何度も挑戦する際には、コンテンツの長さがモチベーションを下げる原因になる。短く、比較的攻略しやすいレイドにプレイヤーが集中し、マッチングが偏る問題も生じていた。
そこでFF14が選んだのは、報酬を増やすだけでも、攻略を簡単にするだけでもない。
アライアンスレイドそのものを、前半と後半の二つに分割するという変更だ。
24人で協力して攻略するというコンセプトは維持しつつ、前半と後半でそれぞれ独立してマッチングできるようにする。
例えば、今日は前半だけ遊び、後半は明日挑戦する、といったことが可能になる。初回はストーリーの進行に沿って前半から後半へ進む必要があるものの、それぞれを別のコンテンツとして遊べる設計だ。
さらに、報酬の獲得方法も見直される。
従来は、欲しい装備が出現しても、ほかのプレイヤーとの抽選（ロット）に負ければ入手できなかった。吉田さんによれば、こうした仕組みも変更されるという。具体的な新方式については、今後説明する予定だ。
注目したいのは、プレイヤーの時間的負担を減らすために、長年続けてきたコンテンツの構造にまで手を入れていることだ。
遊ぶ時間が限られているユーザーに対して、「まとまった時間を確保してほしい」と求めるのではない。
限られた時間でも楽しめるように、コンテンツの側を変える。
それは、単なる利便性の改善以上の意味を持つ変更といえるだろう。
5分だけでも遊べる。しかも、長く遊ばなければ損をするわけではない
もう一つ、今回の発表で象徴的だったのが、新コンテンツ「Gauntlet of Power」だ。
これは4人のプレイヤーで、インスタンスダンジョンのボスと連続して戦うコンテンツ。
特徴の一つは、これまでに登場した200体以上のボスから、ランダムに対戦相手が選ばれることだ。新しいダンジョンが追加されれば、そのボスも対象に加わっていくという。
ただし、参加者がまだ開放していないダンジョンのボスは選ばれない。ストーリーのネタバレを避けるための配慮だ。
また、新たに導入されるレベル調整の仕組みにより、レベルの異なるプレイヤー同士でも、それぞれが習得済みのアクションを使って一緒に戦える。
そして、このコンテンツの設計思想を最もよく表しているのが、ボスを1体倒すたびに、続けるかどうかを投票で決めるという仕組みだ。
全員が続行を希望すれば次の戦闘へ進む。一方、1人でも終了を希望すれば、その時点で終了となる。
「ほんと一瞬空いた時間5分でやりたいとか、たっぷり5戦分やりたいとか、そんな目的に合わせて」
吉田さんは、短時間だけ遊びたい人も、じっくり連戦したい人も、それぞれの目的に合わせて楽しめるようにしたと説明した。
さらに、5戦を最後までクリアしなければ得られないような、特別に大きなボーナスは設けないという。
ここが重要だ。
5分だけ遊べる仕組みをつくっても、最後まで遊んだ方が圧倒的に得をする報酬設計になっていれば、結局は長時間のプレイを促すことになる。
しかし、Gauntlet of Powerでは、短時間で切り上げること自体が不利になりすぎないよう配慮されている。
プレイヤーに選択肢を与えるだけでなく、その選択を報酬によって事実上制限しない。
今回発表された仕様からは、そうした意図が読み取れる。
オンラインサービスにとって、ユーザーに継続して利用してもらうことは重要だ。
毎日アクセスしてもらうこと。できるだけ長くサービスを使ってもらうこと。それらがプロダクトの成長を測る指標になることもある。
しかし、ユーザーがサービスに費やす時間と、そこから得られる価値は、必ずしも比例しない。
FF14が今回示したのは、プレイヤーがゲームに生活を合わせるのではなく、ゲームの方がプレイヤーの生活に歩み寄るという変化だ。
毎日遊ばなくてもいい。好きなことを繰り返してもいい。まとまった時間がなければ、途中で区切ってもいい。
もちろん、こうした変更が実際のプレイ体験にどう作用するかは、実装後の評価を待つ必要がある。
それでも、長く愛されるサービスをつくるために、ユーザーの時間をどこまで求めるべきなのか。
吉田さんが示した一連の変更は、ゲームの外でプロダクトをつくるエンジニアにとっても、考えるきっかけになりそうだ。
