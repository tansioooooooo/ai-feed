Stage magicians often do the same trick multiple ways. One iteration uses a gimmick prop, the next one shows you the prop isn’t gimmick but that one palms the object, the third time was a forced choice etc. When you watch the performance you assume there’s only one technique, so each time they do it they seem to debunk your hypothesis about how it must be working.
This is pretty much how the experiments in the ‘Astra can read and write weights to improve Qwen’ post work. The post’s abstract says:
Just by looking at the raw weights, GPT-6 Astra can tell what a network was trained to do. And without any environment feedback, it has no trouble writing, from scratch, small game-playing networks that outplay networks trained with PPO for 100 million steps.
Likewise, asked to make Qwen3.5-0.8B better at math without gradients, Astra identifies an issue in its weights causing reasoning loops that Qwen’s own model card warns about, and fixes this by natively editing 0.016% of the weights. With the same sampling settings, this weight correction raises MATH-500 from 7.9% to 48.1% and generalizes out of the box to instruction following, raising IFEval by 3x.
If you read that, would you assume that the Qwen experiment worked ‘just by looking at the raw weights’? Well it doesn’t. There’s experiments that look at raw weights, and experiments that improve a game-playing network, and an experiment that improves Qwen at maths. But those latter two aren’t just working with raw weights, they write Python programs.
Here’s a summary of what the post actually does and how the techniques work.
The “just by looking at the raw weights” setting (raw floats in context, no tools, no running the network) only appears in experiments 1, 2 and 4, on networks of 17K–172K weights. Every experiment involving a real language model uses Python, and the Qwen result, which is the headline one, also gets to run the model on up to 50 batches of practice problems.
What the Qwen result actually shows is that Astra can be prompted to devise and perform tasks that a human ML engineer could do. Human ML engineers write snippets of code that analyse or even modify network weights “directly” all the time. Figuring out how to do this productively is not nothing, and AI models of a year or two ago would have failed at all these tasks.
But to me the Qwen result and the other experiments that use Python don’t belong in the same post or paper as the experiments that read the weights directly. A single technique that could achieve both, “Author weights for a small game from scratch” and “Improve the performance of a large model on a sample task” would imply a deep capability. If you test a single technique that way you’ve demonstrated a sort of ‘gestalt’ of the weights (it can write them out from scratch) and also that it understands a large existing network. But that’s not at all true here, because it’s not a single technique.

Libghostty 1.0
libghostty-vt 1.0 is here. libghostty is a
portable, high-performance C library for terminal emulation, extracted
directly from the core of Ghostty. The 1.0 release means both the library
itself and the C ABI are now stable.
A little over a year ago, I wrote that libghostty is coming. At the time, the Zig module had just been merged, the C API didn't exist, and nobody but Ghostty was a consumer. Today, the C API is a complete terminal emulator, it runs in production for millions of people across hundreds of products, both free and commercial, and it has a real, enforced ABI stability policy.
This post is about how we got here and what 1.0 actually means.1
Who Is Already Using It
Since starting the Ghostty project in 2022, the most common question I've been asked is "why?". I already answered this in the libghostty is coming post, so feel free to read that if you wish. Today, I'd rather answer this by showing the broad industry impact libghostty has already had. I believe this strongly validates its existence.
A year ago, I used a bug in JediTerm, the terminal emulator in JetBrains IDEs, as an example of why terminal emulation is hard to get right. A year later, the terminal in JetBrains IDEs now runs on libghostty. Every IntelliJ, PyCharm, GoLand, etc. user now has a libghostty-powered terminal. Based on a report by JetBrains, that's over 12.5 million active users.
Neovim has an approved pull request
replacing libvterm with libghostty-vt. Among other things, it closes a
10-year-old issue
about reflowing scrollback on resize. The maintainers are waiting on a
tagged release before merging so that distributions can package the
dependency separately, and the release today should enable that.
KDE developers are experimenting with a Konsole replacement built on it. Vercel's Turborepo uses it to render task output in its TUI. devenv uses it to drive shells. Antithesis used it to fuzz TUI programs and found real bugs in btop and others. Ghostel brings it to Emacs. ghostty-web is the WASM build with an Xterm.js-compatible API. Commercial products like OrbStack embed it. And a whole wave of new terminals and "agentic" coding tools, such as herdr and cmux, have been built on it rather than writing yet another emulator.
There are community bindings for Rust, Go, JavaScript, Swift, Python, .NET, Elixir, Dart, Java, and more, and the awesome-libghostty list tracks well over a hundred projects.
More people today use a terminal powered by libghostty than use Ghostty the application, by a very large multiple. And libghostty is having a much larger impact than being "just" a terminal emulator.2
ABI Stability
1.0 means libghostty-vt follows semantic versioning and has strict
ABI compatibility
promises so that packagers across distributions and operating systems
can be confident packaging libghostty-vt and program developers can be
confident dynamically linking against it.
Beyond providing useful features, I believe the hallmark of a high-quality and enduring C library is ABI stability. So from the start, I took inspiration from C libraries I enjoyed working with and designed the API to have a strong, stable ABI that allows for future additions.
Every object is an opaque handle. The hundreds of values you might read or
write go through a small set of enum-keyed getters and setters, so we
can add new values easily without introducing a new symbol. Programs with
newer headers linked against an older libghostty get GHOSTTY_UNSUPPORTED
results instead of crashes or undefined behavior. The few non-opaque structs
we have carry their size so that fields can be appended later, or contain
reserved padding. Enums are pinned to int on every compiler, as much as
the C standard allows.
Our CI enforces our ABI policy. Every change is checked with libabigail against a committed baseline on Linux, and against golden type manifests on macOS and WebAssembly.
On ELF platforms, every exported symbol is also versioned, so the dynamic loader refuses to load a mismatched library by name rather than failing in some mysterious way later.
Packaging
In addition to ABI stability, the 1.0 release brings along the proper
build tooling, tarballs, dependency licensing manifests, documentation,
and more to enable every major operating system and distribution to
package libghostty-vt through standard official tooling.
Libghostty has its own release cycle, separate from Ghostty the application. And it has its own tarballs with only the files and dependencies libghostty needs, resulting in smaller sizes and simpler licensing verification and compatibility.
Each release publishes a signed source tarball along with a companion
dependencies tarball containing every Zig package in Zig's own cache
layout, so a distribution can build the library completely offline. The
build installs the shared and static libraries with a proper SONAME,
headers, pkg-config files, and a CMake package config, and it honors
--prefix, DESTDIR, and lib64.

This post discusses a public METR report on AI R&D acceleration at Anthropic. I did not work on this project or see the unredacted report.1 All opinions are my own and do not represent METR or the report authors.
Thanks to Ryan Greenblatt for discussion, feedback, and help with modeling, and Daniel Kokotajlo, Eli Lifland, and Hjalmar Wjik for comments.
Earlier this week, Anthropic stated in their S1 that they “may imminently meet” the threshold of “dramatically accelerated progress due to AI” as defined in their Responsible Scaling Policy. In their latest RSP (effective July 2026), say this threshold will be met when:
- They observe or expect overall capabilities progress to be going twice as fast as the fastest sustained rate before AI was contributing much to AI R&D.2
- This is plausibly attributable to AI automating AI R&D, rather than acceleration in compute or other inputs.3
For the last few months, some of my colleagues at METR have been working on a deep-access investigation to understand how much Anthropic is being accelerated by its AI systems. From my reading of their report and Anthropic’s RSP, it looks like the “dramatic acceleration” threshold has already been crossed.4
The report authors found that:
- Between October 2025 and October 2026, capabilities progress at Anthropic has been going about twice as fast as it had been over the previous twelve months. The measurement they report is an internal version of the Epoch Capabilities Index called AECI; a wide range of other supporting evidence for acceleration has been redacted. They said that this redacted evidence was "a majority of the evidence [they] found most informative."
- While the pace may have initially started picking up for a mix of reasons, AI automation is probably the large majority of the reason why capabilities are still improving at this faster pace today. Their reasons for believing this have been redacted.
This is a much bigger deal than it might sound at first. I think this report is the most important update we have gotten about AI risk in the last couple of years — much bigger than the Hugging Face attack. Naively, it points toward much shorter timelines than most external researchers (including the AI 2027 team) have projected.
Researchers must be sped up a whole lot
Importantly, if AI is roughly doubling capabilities progress overall, it must be speeding up human researchers by much more than that.
Researchers work on improving algorithms and architectures; Anthropic has sometimes referred to these innovations as “compute multipliers.”5 Overall AI capabilities (“effective compute”) is the product of compute multipliers and training compute. Because the compute multipliers are only one input into capabilities, this means that if AI capabilities are advancing twice as fast overall because of software progress, the rate of growth in compute multipliers would need to be more than twice as fast: perhaps ~2.5-3x faster based on reasonable assumptions.6 Since there’s uncertainty about the size of speedup and how much of it comes from AI, I’ll go with ~2-3x.
Similarly, researcher labor is only one input to discovering these compute multipliers: they need to test their ideas, which requires compute for experiments. If we assume a very simple Cobb-Douglas model where experiment compute and labor are similarly important, that means the uplift to labor roughly needs to be the square of the acceleration in compute multipliers.7 This would imply that we would need a (~2-3x)^2 = ~4-9x speed up in labor to make overall AI capabilities go twice as fast.8
However, once capabilities start speeding up significantly, this also means that low-hanging fruit is plucked at a correspondingly faster rate. Each new compute multiplier takes more and more work to discover and implement (i.e., “ideas are getting harder to find”). Before there was much acceleration from AI, labor roughly grew at some roughly fixed exponential rate from hiring more humans. Combined with growth in compute, this compensated for diminishing returns enough to maintain the baseline rate of capabilities progress. But to maintain a new faster rate of capabilities progress without scaling compute faster, we would need a new faster rate of growth in overall labor.
Since the human labor force is stuck growing at more or less the old rate, the uplift from AI would need to get larger and larger over time just to sustain capabilities progress at its new rate. That means the uplift today, after several months of accelerated progress from AI,9 needs to be even higher than ~4-9x, the estimate for what it would take to double progress at the start: maybe the necessary labor uplift is ~10x. This is very uncertain, and substantially more or less is plausible. But it lines up surprisingly well with informal self-reports from Anthropic staff, who say they are now getting a ~12x uplift from the use of internal models.

同じような考え方で、AIが使うんだから人間用に設計されたインターフェースは最初から取っ払ってしまってもいいのでは、という思想もある。Elixir作者のJosé Valimがブログに書いていたAI向けのプログラミング言語という話もそうだし、マルチエージェントオーケストレーション系のツールには、エージェント間の会話を謎に暗号化されたJSONでやりとりする、ReactFlightでイルカ同士が話しているようなアーキテクチャがある。LLMがコード生成の代わりに機械語を出すというのはちょっと飛躍があるけど、人間は読まないけどLLM間だけでメッセージングが完結するというのは結構想像できる。現に、パーソナルアシスタント系も人間のインターフェイスは一つだけど、バックグラウンドで小人さんのようにマルチセッションがせっせと作業していることがある。
モデル自身が解決策を考えて、人間はゴールを指すだけの方がうまくいくっていうパターンは、ISUCONのような評価が明確なプロジェクトにはかなり効いているというのは、インタビューで本人たちも語っていた。明確な定義に落とし込める証明記述や型化の分野に、最近熱心に取り組んでいる人たちもいるのも、その流れだろう。SoEなアプリケーション開発にもそれが適用できるかはちょっとわからないが。
私たちの開発でも、最近はAIが視覚情報なしにビューを構築できることを利用したUIプログラミングができるのではないかと考えている。ちょうどShopifyが、一つの契約から複数のモバイルアプリのビューを作るっていう記事を出していたところだった。
ただ、準備期間の検証と評価が重要だなと思ったが、対象の内容を理解することもまだ地道に有効なのではないか。優勝スコアの決定打となった構成要素はいくつかあって、Postgresを廃止して、過去データはダンプしてmmapで読み込み、書き込みは変更イベントを代表のサーバーが順序付けてファイルに永続化し、全台のメモリへ同じ順序で適用するイベントソーシング的な設計にする。nginxの機能をGoのアプリケーション側に移して外す。画像の署名検証のボトルネックを、事前計算で潰す。などは、結構古典的な回答だと思った（抽象的に見ると、負荷分散の定石の疎結合アーキテクチャを結合してジェンガが崩壊しないよう密を維持するAIロボコンと言える）。
あとは、レイテンシーから来るベンチマーカーのスループットを上げる最適化は、AIが仮説を立てて自動で解いていくっていうので、結構面白いと思った。スコア履歴と残り時間から期待値を計算して、閾値を超えた走行で自動停止させる停止判定ツールまで事前に用意していたっていうのも、かなりやり込んでる人の発想だと思った。

毎朝のセキュリティ確認をAIに任せたら、判定の基準が「人が動く必要があるか」に変わった
本番環境に攻撃の兆候が来ていないかを、AIエージェントが平日の朝に確認して、判定付きのレポートを作るルーティンを動かしています。
動かし始めて1週間で、判定の基準を3回変えました。最初は「何かが起きたら赤」でしたが、それだと社員の普段の作業でも毎週赤になります。最後は、何が起きたかではなく、人が動く必要があるかで色を決める形に落ち着きました。
仕組みそのものより、この基準の変わり方の方が、同じことをやろうとしている人の役に立つと思います。
ダッシュボードで足りるかを、先に棚卸しした
ルーティンを作る前に、既にあるダッシュボードとアラームで何が見えていて、何が見えていないかを一覧にしました。
結論は「見えていない範囲がある」でした。ダッシュボードはクエリを書いた攻撃しか拾えません。想定していない種類の攻撃は、そもそも画面に出てきません。アラームも、鳴った後に誰かが実行者や送信元を引きに行かなければ、何が起きたのかは分かりません。
足りない部分は、毎朝AIに取りに行かせることにしました。見るものは次の4系統です。
- 入口（WAF・ロードバランサー）の遮断数と、国別の通信量
- アプリケーションへのログイン失敗とロック
- クラウドのアカウントの乗っ取りの兆候（証跡の停止、権限の変更、外部への開放）
- 既存のアラームの状態遷移
このとき同時に決めたのが、ルーティンでは直さない、ということです。棚卸しの途中で、外に開いている設定の是正をAIが提案してきましたが、それは保留にしました。このセッションの目的はあくまで攻撃の状況把握で、是正は別の判断だからです。保留した事項は「既知の事項」として毎朝の確認に渡し、増えていないかだけを見させています。
構成は、読み取り専用の許可リストとスケジュール実行だけ
ルーティンの実体は、スケジュール実行されるエージェントへの指示書（プロンプト）1枚です。
平日の朝に起動
├─ 観測窓: 前回の実行時刻から今回まで（月曜は金曜の実行から72時間）
├─ 許可リストにある読み取り専用のコマンドだけを実行
│ cloudwatch get-metric-data / describe-alarm-history
│ logs start-query / get-query-results
│ cloudtrail lookup-events（呼び出しの間を空ける）
│ ec2 describe-security-groups ほか
├─ 技術レポートをローカルに保存
└─ 社内向けの共有ノートを1件作る（書き込みはこれだけ）
指示書の先頭に安全ガードを置き、許可リストに無い操作（作成・更新・削除・コンテナへの接続・DBへの接続・権限の変更）は実行せず、レポートの「要判断」に書くようにしています。書き込みの権限は、共有ノートの作成1件だけに使うキーを別に持たせました。
起動時刻は、最初に決めた時刻から後ろにずらしました。手元のPCで動くスケジュール実行なので、PCが開いていない時間には走りません。監視の時刻を、監視する人の出社時刻に合わせることになったのは少し皮肉ですが、ここは割り切っています。
細かいところで2つ、最初から指示書に書いておいて良かったものがあります。
1つはタイムゾーンです。CLIの返すタイムスタンプはJSTで、Logs Insights の @timestamp はUTCです。AIはこの2つを平気で混ぜます。「レポートの時刻はJSTで書く」と明記しておかないと、深夜の出来事が朝の出来事として報告されます。
もう1つはスキャン量です。Logs Insights はスキャンした量で課金されるので、毎回 statistics.bytesScanned を合計してレポートに書かせ、1回の実行で上限を超えそうなら残りのクエリを止めて「未確認」にさせています。
固定の閾値をやめて、7日中央値と比べる
最初に捨てたのは固定の閾値です。
ログイン失敗が何件を超えたら異常、という決め方をすると、曜日やキャンペーンの有無で平常値そのものが動きます。そこで比較の基準を「同じ長さの窓の、直近7日分の中央値」に置きました。平均ではなく中央値にしたのは、1日だけ大きな攻撃があった週に、基準が引きずられて翌週の異常を見逃さないためです。
固定の閾値は補助に回しました。たとえば、証跡の停止は中央値と比べるまでもなく1件で赤です。
社員の作業でも鳴るので、毎週赤になった
運用を始めてすぐ、アカウントの変更を検知するアラームが、社員の通常の作業でも鳴ることが分かりました。権限の付け替えも、新しいバケットの作成も、正規の作業です。最初の基準ではこれが全部赤になり、毎週赤のレポートが出る状態になりました。
毎週赤だと、誰も赤を読まなくなります。
そこで、アラームが鳴ったら、該当するイベントの実行者・送信元・MFAの有無まで引かせ、全部が「社員のIAMユーザー」「社内の回線」「MFAあり」なら緑、それ以外が1件でもあれば赤、という形に変えました。証跡の停止のように、誰がやっても赤のままにするものは例外として列挙しています。
翌週、さらに一段緩めています。在宅や出張では社内の回線から外れるので、社外の回線からでも、社員の想定内の作業（リリース、調査のための読み取り、MFAありのコンソールログイン）は緑にしました。黄色にするのは、社外の回線からで、内容が想定外のもの（権限の変更、秘密情報の読み出し、外部への開放、実行者や目的が分からないもの）に限っています。
色の意味を「人が動く必要があるか」に揃えた
レポートは、技術職ではない社員も読む共有ノートとしても出しています。そうなると、色の意味が「何が起きたか」では伝わりません。遮断が急増した日に赤を出すと、読んだ人は「何か被害があったのか」と受け取ります。実際には防げているのに、です。
そこで判定を4段階と「未確認」に作り直しました。
基準を一言で言うと、防げているもの、原因が分かっているものは黄色にしない、です。
似た2つで差を書くと分かりやすいと思います。入口で遮断された通信が急増したなら、それは緑です。遮断できているからです。遮断されずにアプリまで届いて、エラーや失敗が増えていて、送信元か原因が分からないなら、それは黄色です。量は前者の方が多くても、人が動く必要があるのは後者だけです。
⚪は共有ノートには書かず、技術レポートにだけ残しています。技術職以外の人が「確認できていない」を読むと、確認できていないものの中身を想像して不安になるからです。
公開を「塞ぐ」操作で、公開のアラームが鳴った
基準を作り直している間に、外部への開放を検知するアラームが鳴りました。調べると、鳴らしたのはバケットの公開ブロックを有効にする操作、つまり公開を「塞ぐ」操作でした。社員が新しいバケットを作ったときの初期設定です。
仕組みは単純で、メトリクスフィルタがAPI名だけを数えていました。
{ $.eventName = "PutBucketPublicAccessBlock" }
PutBucketPublicAccessBlock は、公開ブロックの4項目を true にする呼び出しにも false にする呼び出しにも使われます。API名だけを見ると、塞いだのか開けたのかが区別できません。バケットを新しく作るたびに鳴ります。
この種の監視を作るとほぼ必ず起きることなので、直し方の一般形を置いておきます。設定値が false のときだけ数え、ブロックそのものの削除は常に数えます。
{ ($.eventName = "DeletePublicAccessBlock") ||
($.eventName = "DeleteBucketPublicAccessBlock") ||
(($.eventName = "PutBucketPublicAccessBlock") &&
(($.requestParameters.PublicAccessBlockConfiguration.BlockPublicAcls IS FALSE) ||
($.requestParameters.PublicAccessBlockConfiguration.IgnorePublicAcls IS FALSE) ||
($.requestParameters.PublicAccessBlockConfiguration.BlockPublicPolicy IS FALSE) ||
($.requestParameters.PublicAccessBlockConfiguration.RestrictPublicBuckets IS FALSE))) }
requestParameters の下の構造は、自分の環境で実際に記録されたイベントを1件取り出して確かめてください。フィールドのパスが1段ずれると、今度は何も数えない監視になります。鳴らない監視は鳴りすぎる監視より気づきにくいので、直した後に一度わざと false の設定を検証環境で入れて、鳴ることを見ておくのが安全です。
調べる側の教訓は1つです。外部への開放のアラームが鳴ったら、最初に「開けた操作か、塞いだ操作か」を見る。いまはこれを指示書の調べ方に入れています。
AIが「ログが無い」と言い、それを前提に課題を起票した
もう1つ、AI側の誤りがありました。
WAFのログを調べる流れで、AIが「WAFのログが無い」と書き、それを前提に、ログを出す設定を足す課題まで起票しました。実際には、どちらの本番環境でも、ログは別の保存先に既に出力されていました。後で調べ直したAI自身が、課題の前提が誤りだったと訂正しています。
AIの「無い」は、AIが見た範囲に無かった、という意味でしかありません。この話は長くなるので、別の記事で扱います。
ただ、このときの調べ直しで判断材料が1つ増えました。WAFのログを全件ログの集約サービスに入れる場合と、遮断とカウントに絞ってストレージに直接出す場合とで、月額が2桁以上違いました。調べるときに必要な分だけあればよいので、後者にしています。
国で絞る案も出ましたが、採りませんでした。ログを国で絞るには、通信に国のラベルを付けるルールを足す必要があり、そのルールには評価するリクエスト数に応じた課金が全通信にかかります。調べるときにしか使わないログのために、平常時の全通信に費用を払うことになるので、割に合わないと判断しました。
想定される反論
「社外の回線からの操作でも緑にするのは、緩すぎるのでは」
緩めたのは色だけで、記録は緩めていません。社外の回線からでも、MFAありで、リリースや調査のための読み取りといった想定内の作業なら緑にしています。一方で、社外の回線からの権限の変更、秘密情報の読み出し、外部への開放は、MFAがあっても黄色のままです。
緩めた理由は、在宅や出張の日に毎回黄色が出ると、黄色が「いつものこと」になるからです。黄色の数を、人が本当に見る数に保つ方を優先しました。
緑にしたものも、技術レポートには実行者と操作を全件残しています。後から「あの日のあの操作は誰だったか」は引けます。
「本番環境の読み取りを、AIに毎朝渡してよいのか」

AWSでWebリクエストを受ける8パターンと「オリジンを裸にしない」設定プラクティス
はじめに
先日、X（旧Twitter）でこんな趣旨の話題が流れてきました。
- CloudFront + WAF → ALB の構成では、ALB の SG に CloudFront のプレフィックスリストを入れて直接アクセスを防ぐ
- ただし ALB のドメインが知られると、第三者が作った CloudFront 経由で WAF を迂回される。そのため秘密ヘッダーでの照合が必要
- さらに、CT Log が知られるようになってから、Host ヘッダー付きの攻撃が増えた
元の投稿はこちらです。
どちらも重要な指摘です。一方で、2024年11月に CloudFront VPC オリジン が登場してから、選べる構成はかなり変わっています。
この記事では、AWS で Web リクエストを受ける代表的な 8 パターンを、公式ドキュメントの根拠付きで、構成図と設定プラクティスにまとめます。
TL;DR
- 公式ドキュメントから読み取れる優先順位は 「VPC オリジン / OAC（マネージド）→ 使えない場合のみ プレフィックスリスト＋秘密ヘッダー」
- プレフィックスリストだけでは不十分です。他人の CloudFront も同じ IP 帯から来るため、本体は秘密ヘッダーの照合です
- CT Log にはオリジン用に取った証明書のホスト名が載るので、「ホスト名は知られる前提」で設計します
- 新規構築なら VPC オリジン＋CloudFront-VPCOrigins-Service-SG 限定 が第一候補です。名前を知られても、そもそも到達できません
- WAF は「中身を検査する層」、VPC オリジン / OAC / SG は「届く経路を絞る層」 です。役割が違うので両方必要で、WAF の主戦場はエッジ（CloudFront）です
以前のプラクティスと、いまのプラクティス
私自身、2015〜2017 年頃から「ELB（のちに ALB）をインターネットに公開し、その前に CloudFront を置く」構成を何度も作ってきました。当時はそれが一般的な作り方で、SG で CloudFront の IP に絞る、秘密ヘッダーで照合する、といった対策をプラクティスとして実装していました。
ALB をインターネットに公開する構成は今もよく見かけますし、それ自体が間違いというわけではありません。ただ、ここ数年でオリジンを閉じるためのマネージドな仕組みがそろい、同じ要件をよりセキュアに、しかも運用負荷を下げて作れるようになっています。
AWS 自身も、VPC オリジンの発表で「これまで VPC 内のオリジンはパブリックサブネットに置く必要があった」と書いています。つまり、10 年近く定番だった「ALB を公開して IP 制限と秘密ヘッダーで守る」方式は、今ではVPC オリジンが使えない場合のフォールバックという位置付けになりました。
この記事は、そうした変化を踏まえて「いま新しく作るなら、あるいは見直すなら、どう作るか」を整理したものです。
前提知識
プレフィックスリストだけではダメな理由
com.amazonaws.global.cloudfront.origin-facing は「CloudFront 全体」の IP 帯です。自社のディストリビューションに限った IP 帯ではありません。攻撃者が自分の AWS アカウントで CloudFront を作り、オリジンにあなたの ALB を指定すれば、SG は素通りします。WAF は「あなたの CloudFront」に付いているので、当然かかりません。
そのため公式ドキュメントでも、プレフィックスリストは Optional（追加の防御層） という位置付けです。本体は、カスタムヘッダーを ALB のリスナールールで照合する仕組みです。
CT Log（Certificate Transparency：証明書の透明性）とは
CT は、公的な CA（Certificate Authority：認証局）が発行した TLS 証明書を、誰でも検索できる公開ログにすべて記録する仕組みです。ブラウザが CT を必須にしているため、ACM で発行した証明書も必ず記録され、オプトアウトできません。
そのため crt.sh などで検索すれば、origin.example.com のように証明書を取ったホスト名を誰でも一覧できます。攻撃者はこれを偵察に使い、証明書の発行から数分でスキャンが来ることも観測されています。
DNS を公開していなくても、公的な証明書を取った時点でホスト名は知られる と考えておきましょう。ワイルドカード証明書で個別のホスト名を隠すことはできますが、それは推測しにくくするだけの隠蔽策です。本筋は「名前を知られても届かない」構成にすることです。
CA と CT の仕組み（構成・発行・検証・監視）は、図解付きで別の記事にまとめました。
選定フロー
DDoS 耐性のホワイトペーパーでは、CloudFront の背後に VPC 内のオリジンを置く場合、VPC オリジンが最新かつ推奨の方法 とされています。S3・AWS Elemental・Lambda 関数 URL については、引き続き OAC が推奨 です。
CloudFront の FAQ でも、マネージドな仕組みで要件を満たせない場合の代替として、カスタムオリジンヘッダーが挙げられています。
① CloudFront + VPC オリジン（内部 ALB）★第一候補
プライベートサブネットにある ALB / NLB / EC2 を、CloudFront のオリジンとして直接使えます。ALB にパブリック IP がないため、CT Log でホスト名を知られても、Host ヘッダーを付けても、インターネットから届く経路自体がありません。VPC オリジンの利用に追加料金はかかりません。

最初にやるべきことは課題点・問題点の洗い出しです。
対応開始当初はそもそも60FPS達成もままならない状況でした。
そこで、最初の関門は60FPS達成であると考えました。このときは全プラットフォームで60FPSなんてそんな…。という状況でしたので、まずはスペックが一番高いPCで60FPS達成を実現し、そこからパフォーマンスバジェットの割り当てを決定し、それを1/2にスケールすれば120FPS達成が可能ではないか？と考えました。
そのため、120FPSのパフォーマンスバジェットを決めるためにPC版で60FPS達成を最初の目標として取り組むことにしました。
PC版 60FPS達成まで
PCは処理速度がかなり速いので、明らかにおかしいボトルネックを解消すれば、比較的に60FPSは達成しやすいです。
そのため、PC版 60FPS達成では明らかなボトルネック、そもそもレンダリングパスの組み方がおかしい箇所などを大きな問題点を取り除く作業をすることになりました。
過去の経験から60FPS達成に問題になる点はある程度絞ることができます。大まかに分けて次の3点だと思います。
- モデル描画が重い。
- ライティングが重い。
- ポストプロセスが重い。
これ以外で、重い点が見つかるようであれば、まずその箇所の最適化を優先的に行います。
次のその最適化を施した状態でも重い場合は，非同期コンピュートに逃がすことを考え、処理時間を隠蔽すること考えます。
当時では、デカール処理などが若干重かったので、デカール処理時間を隠蔽するようにレンダリングパスの入れ替えなどを行い、ボトルネックの解消を行いました。
次に、モデル描画です。モデル描画は重いものの、まぁ許容できる処理時間ではあったのですが、GPUでオクルージョンカリングを行っており、そちらの方が処理時間を1,2ms程度喰っていて問題となっていました。そのため、GPUでオクルージョンカリングをやめて，CPUでオクルージョンカリングを実行する方針へと変更しました。
こちらのCPUオクルージョンカリングが入って、これでモデル描画はいったん解決としました。

縮小バッファ対応などがすでにされているのであれば、あとはやることは決まっています。
「どのポストプロセスを残すか？」を決めるだけです。
基本的に絵作りに重要な要素は外せないと思うので，BloomやTAAは残します。
それ以外は基本的に不要と考え、SSAOやSSRなど縮小バッファで乗り切れるものは残し，DOFやモーションブラーなど乗り切れない機能は大胆に削るという判断をします。

ここからエンジニアとしてはハードモードに突入します。…というのもの60FPS達成である程度最適化できるところはしてしまったので、大きなボトルネックがもうない状態になっています。
120FPS達成するには、8.3ms以内，理想的には7ms台に抑える必要が必要があります。

画面の全体
左が司令塔の Claude Code で、右が Orca の右サイドバーに出している「確認待ち」のパネルです。パネルは Orca のプラグインとして自作していて、エージェントの状態が変わるたびに読み直すので、司令塔が確認待ちを出すとすぐに並びます。

確認待ちができるまで
/coordinator で司令塔のスキルを起動すると、司令塔は GitHub と Notion のタスクを見比べて今抱えているものを組み立て直し、人間の判断が要るものを確認待ちに入れていきます。
- GitHub でレビュワーにアサインされた PR や、自分に割り当てられた Issue は、まず Notion のタスクにします。
- タスクの Next や前提のタスクを見て、着手できる条件がそろったものは作業役に渡し、設計の判断や本番への変更のように選択肢があるものは着手前の確認待ちにします。
- 着手する順番も司令塔が決めます。誰かが自分を待っているもの、期限の近いもの、ほかのタスクの前提になっているものの順です。
- 承認がそろってマージできる PR は、マージの確認待ちにします。
作業が始まってからのルールは、「人に見せる前」を意識して組みました。作業役の PR をほかのレビュワーに見せる前や、人の PR にレビューを投稿する前のように、自分以外の人の目に触れる手前で止まるようにしていて、そこまでは作業役と司令塔に任せています。ほかに、作業役が方針に迷ったときと、自分の手作業が要るときにも確認待ちが増えます。

ロート製薬（大阪市）は11月6日、9月11日に公表した通信販売システムへの不正アクセスについて、顧客279万7545人分の個人情報が漏えいしたと発表した。調査の結果、9715人分のクレジットカード情報も不正に取得されていたことが分かったという。

クラウドで動くリモートエージェント
リモートエージェントは、エージェントのセッションとツールを、ローカル PC ではなく Google が管理する隔離されたリモート環境で実行する機能です。
ブラウザを閉じたり PC をスリープにしたり、デスクトップとモバイルを切り替えたりしても、長時間のタスクを続けられることが特長です。
リモートプロジェクトは、アプリの左サイドバーにある「Projects」横の [+] から「New Remote Project」を選ぶか、メッセージ入力欄のプロジェクト選択から [Remote] > [GitHub Repositories] を選んで作成します。
GitHub のリポジトリは OAuth で認可すると複数接続でき、会話の中で自動的にクローンされてリモートワークスペースにマウントされます。ただし、同じプロジェクト内のプライベートリポジトリは、同じ GitHub ユーザーまたは組織のオーナーに属している必要があります。

クラウドプロジェクトの会話は antigravity.google.com/remote から開けます。
リモートエージェントを利用するには、個人の Google アカウントで Google AI Pro または Google AI Ultra の有料プランに加入している必要があり、無料プラン、Google AI Plus、Google Workspace や Google Cloud のビジネスアカウントは対象外です。

音声モードは、Gemini Live を利用して Antigravity に話しかけ、依頼を音声で渡せる機能です。メッセージ入力欄が空のときに表示されるボタンから開始できます。
現時点では音声モードは段階的に提供されており、まだ表示されない場合があります。
会話ページのデザインを刷新
新しい会話ページでは、上部に挨拶が表示され、メッセージ入力欄が画面下部に固定されます。単一リポジトリのプロジェクトでは、ブランチと Git ワークツリーの選択が 1 つのメニューにまとまり、エージェントの選択はモデルのメニュー内に移りました。
設定を変更していない場合のテーマは Onyx、フォントは Google Sans になります。どちらも [Settings] > [Appearance] から変更できます。
Automations ページと内蔵ブラウザの更新
Automations ページは、自動化を「Scheduled」、「Always on」、「Paused」の一覧に分けて表示する構成になり、次回実行と前回実行の時刻も確認できます。

- アドレスバー: 接続の安全性の表示を見直し、読み込み状況を上端の細いバーで表示、サイトがテキスト入力を求めるとページ内ダイアログを表示
- サイドパネル: 新規タブページから URL を開いたり Google 検索を実行したりでき、リンクのドラッグ操作と左側のタブをまとめて閉じる操作にも対応
また、キーボードショートカットを [Settings] > [Shortcuts] で変更でき、既定に戻すこともできます。
起動も速くなり、サイドバーとサイドパネルの開閉はなめらかなアニメーションで表示されます。

Stage magicians often do the same trick multiple ways. One iteration uses a gimmick prop, the next one shows you the prop isn’t gimmick but that one palms the object, the third time was a forced choice etc. When you watch the performance you assume there’s only one technique, so each time they do it they seem to debunk your hypothesis about how it must be working.
This is pretty much how the experiments in the ‘Astra can read and write weights to improve Qwen’ post work. The post’s abstract says:
Just by looking at the raw weights, GPT-6 Astra can tell what a network was trained to do. And without any environment feedback, it has no trouble writing, from scratch, small game-playing networks that outplay networks trained with PPO for 100 million steps.
Likewise, asked to make Qwen3.5-0.8B better at math without gradients, Astra identifies an issue in its weights causing reasoning loops that Qwen’s own model card warns about, and fixes this by natively editing 0.016% of the weights. With the same sampling settings, this weight correction raises MATH-500 from 7.9% to 48.1% and generalizes out of the box to instruction following, raising IFEval by 3x.
If you read that, would you assume that the Qwen experiment worked ‘just by looking at the raw weights’? Well it doesn’t. There’s experiments that look at raw weights, and experiments that improve a game-playing network, and an experiment that improves Qwen at maths. But those latter two aren’t just working with raw weights, they write Python programs.
Here’s a summary of what the post actually does and how the techniques work.
The “just by looking at the raw weights” setting (raw floats in context, no tools, no running the network) only appears in experiments 1, 2 and 4, on networks of 17K–172K weights. Every experiment involving a real language model uses Python, and the Qwen result, which is the headline one, also gets to run the model on up to 50 batches of practice problems.
What the Qwen result actually shows is that Astra can be prompted to devise and perform tasks that a human ML engineer could do. Human ML engineers write snippets of code that analyse or even modify network weights “directly” all the time. Figuring out how to do this productively is not nothing, and AI models of a year or two ago would have failed at all these tasks.
But to me the Qwen result and the other experiments that use Python don’t belong in the same post or paper as the experiments that read the weights directly. A single technique that could achieve both, “Author weights for a small game from scratch” and “Improve the performance of a large model on a sample task” would imply a deep capability. If you test a single technique that way you’ve demonstrated a sort of ‘gestalt’ of the weights (it can write them out from scratch) and also that it understands a large existing network. But that’s not at all true here, because it’s not a single technique.

動かし始めて1週間で、判定の基準を3回変えました。最初は「何かが起きたら赤」でしたが、それだと社員の普段の作業でも毎週赤になります。最後は、何が起きたかではなく、人が動く必要があるかで色を決める形に落ち着きました。
仕組みそのものより、この基準の変わり方の方が、同じことをやろうとしている人の役に立つと思います。
ダッシュボードで足りるかを、先に棚卸しした
ルーティンを作る前に、既にあるダッシュボードとアラームで何が見えていて、何が見えていないかを一覧にしました。
結論は「見えていない範囲がある」でした。ダッシュボードはクエリを書いた攻撃しか拾えません。想定していない種類の攻撃は、そもそも画面に出てきません。アラームも、鳴った後に誰かが実行者や送信元を引きに行かなければ、何が起きたのかは分かりません。
足りない部分は、毎朝AIに取りに行かせることにしました。見るものは次の4系統です。
- 入口（WAF・ロードバランサー）の遮断数と、国別の通信量
- アプリケーションへのログイン失敗とロック
- クラウドのアカウントの乗っ取りの兆候（証跡の停止、権限の変更、外部への開放）
- 既存のアラームの状態遷移
このとき同時に決めたのが、ルーティンでは直さない、ということです。棚卸しの途中で、外に開いている設定の是正をAIが提案してきましたが、それは保留にしました。このセッションの目的はあくまで攻撃の状況把握で、是正は別の判断だからです。保留した事項は「既知の事項」として毎朝の確認に渡し、増えていないかだけを見させています。
構成は、読み取り専用の許可リストとスケジュール実行だけ
ルーティンの実体は、スケジュール実行されるエージェントへの指示書（プロンプト）1枚です。
平日の朝に起動
├─ 観測窓: 前回の実行時刻から今回まで（月曜は金曜の実行から72時間）
├─ 許可リストにある読み取り専用のコマンドだけを実行
│ cloudwatch get-metric-data / describe-alarm-history
│ logs start-query / get-query-results
│ cloudtrail lookup-events（呼び出しの間を空ける）
│ ec2 describe-security-groups ほか
├─ 技術レポートをローカルに保存
└─ 社内向けの共有ノートを1件作る（書き込みはこれだけ）
指示書の先頭に安全ガードを置き、許可リストに無い操作（作成・更新・削除・コンテナへの接続・DBへの接続・権限の変更）は実行せず、レポートの「要判断」に書くようにしています。書き込みの権限は、共有ノートの作成1件だけに使うキーを別に持たせました。
起動時刻は、最初に決めた時刻から後ろにずらしました。手元のPCで動くスケジュール実行なので、PCが開いていない時間には走りません。監視の時刻を、監視する人の出社時刻に合わせることになったのは少し皮肉ですが、ここは割り切っています。
細かいところで2つ、最初から指示書に書いておいて良かったものがあります。
1つはタイムゾーンです。CLIの返すタイムスタンプはJSTで、Logs Insights の @timestamp はUTCです。AIはこの2つを平気で混ぜます。「レポートの時刻はJSTで書く」と明記しておかないと、深夜の出来事が朝の出来事として報告されます。
もう1つはスキャン量です。Logs Insights はスキャンした量で課金されるので、毎回 statistics.bytesScanned を合計してレポートに書かせ、1回の実行で上限を超えそうなら残りのクエリを止めて「未確認」にさせています。
固定の閾値をやめて、7日中央値と比べる
最初に捨てたのは固定の閾値です。
ログイン失敗が何件を超えたら異常、という決め方をすると、曜日やキャンペーンの有無で平常値そのものが動きます。そこで比較の基準を「同じ長さの窓の、直近7日分の中央値」に置きました。平均ではなく中央値にしたのは、1日だけ大きな攻撃があった週に、基準が引きずられて翌週の異常を見逃さないためです。
固定の閾値は補助に回しました。たとえば、証跡の停止は中央値と比べるまでもなく1件で赤です。
社員の作業でも鳴るので、毎週赤になった
運用を始めてすぐ、アカウントの変更を検知するアラームが、社員の通常の作業でも鳴ることが分かりました。権限の付け替えも、新しいバケットの作成も、正規の作業です。最初の基準ではこれが全部赤になり、毎週赤のレポートが出る状態になりました。
毎週赤だと、誰も赤を読まなくなります。
そこで、アラームが鳴ったら、該当するイベントの実行者・送信元・MFAの有無まで引かせ、全部が「社員のIAMユーザー」「社内の回線」「MFAあり」なら緑、それ以外が1件でもあれば赤、という形に変えました。証跡の停止のように、誰がやっても赤のままにするものは例外として列挙しています。
翌週、さらに一段緩めています。在宅や出張では社内の回線から外れるので、社外の回線からでも、社員の想定内の作業（リリース、調査のための読み取り、MFAありのコンソールログイン）は緑にしました。黄色にするのは、社外の回線からで、内容が想定外のもの（権限の変更、秘密情報の読み出し、外部への開放、実行者や目的が分からないもの）に限っています。
色の意味を「人が動く必要があるか」に揃えた
レポートは、技術職ではない社員も読む共有ノートとしても出しています。そうなると、色の意味が「何が起きたか」では伝わりません。遮断が急増した日に赤を出すと、読んだ人は「何か被害があったのか」と受け取ります。実際には防げているのに、です。
そこで判定を4段階と「未確認」に作り直しました。
基準を一言で言うと、防げているもの、原因が分かっているものは黄色にしない、です。
似た2つで差を書くと分かりやすいと思います。入口で遮断された通信が急増したなら、それは緑です。遮断できているからです。遮断されずにアプリまで届いて、エラーや失敗が増えていて、送信元か原因が分からないなら、それは黄色です。量は前者の方が多くても、人が動く必要があるのは後者だけです。
⚪は共有ノートには書かず、技術レポートにだけ残しています。技術職以外の人が「確認できていない」を読むと、確認できていないものの中身を想像して不安になるからです。
公開を「塞ぐ」操作で、公開のアラームが鳴った
基準を作り直している間に、外部への開放を検知するアラームが鳴りました。調べると、鳴らしたのはバケットの公開ブロックを有効にする操作、つまり公開を「塞ぐ」操作でした。社員が新しいバケットを作ったときの初期設定です。
仕組みは単純で、メトリクスフィルタがAPI名だけを数えていました。
{ $.eventName = "PutBucketPublicAccessBlock" }
PutBucketPublicAccessBlock は、公開ブロックの4項目を true にする呼び出しにも false にする呼び出しにも使われます。API名だけを見ると、塞いだのか開けたのかが区別できません。バケットを新しく作るたびに鳴ります。
この種の監視を作るとほぼ必ず起きることなので、直し方の一般形を置いておきます。設定値が false のときだけ数え、ブロックそのものの削除は常に数えます。
{ ($.eventName = "DeletePublicAccessBlock") ||
($.eventName = "DeleteBucketPublicAccessBlock") ||
(($.eventName = "PutBucketPublicAccessBlock") &&
(($.requestParameters.PublicAccessBlockConfiguration.BlockPublicAcls IS FALSE) ||
($.requestParameters.PublicAccessBlockConfiguration.IgnorePublicAcls IS FALSE) ||
($.requestParameters.PublicAccessBlockConfiguration.BlockPublicPolicy IS FALSE) ||
($.requestParameters.PublicAccessBlockConfiguration.RestrictPublicBuckets IS FALSE))) }
requestParameters の下の構造は、自分の環境で実際に記録されたイベントを1件取り出して確かめてください。フィールドのパスが1段ずれると、今度は何も数えない監視になります。鳴らない監視は鳴りすぎる監視より気づきにくいので、直した後に一度わざと false の設定を検証環境で入れて、鳴ることを見ておくのが安全です。
調べる側の教訓は1つです。外部への開放のアラームが鳴ったら、最初に「開けた操作か、塞いだ操作か」を見る。いまはこれを指示書の調べ方に入れています。
AIが「ログが無い」と言い、それを前提に課題を起票した
もう1つ、AI側の誤りがありました。
WAFのログを調べる流れで、AIが「WAFのログが無い」と書き、それを前提に、ログを出す設定を足す課題まで起票しました。実際には、どちらの本番環境でも、ログは別の保存先に既に出力されていました。後で調べ直したAI自身が、課題の前提が誤りだったと訂正しています。
AIの「無い」は、AIが見た範囲に無かった、という意味でしかありません。この話は長くなるので、別の記事で扱います。
ただ、このときの調べ直しで判断材料が1つ増えました。WAFのログを全件ログの集約サービスに入れる場合と、遮断とカウントに絞ってストレージに直接出す場合とで、月額が2桁以上違いました。調べるときに必要な分だけあればよいので、後者にしています。
国で絞る案も出ましたが、採りませんでした。ログを国で絞るには、通信に国のラベルを付けるルールを足す必要があり、そのルールには評価するリクエスト数に応じた課金が全通信にかかります。調べるときにしか使わないログのために、平常時の全通信に費用を払うことになるので、割に合わないと判断しました。
想定される反論
「社外の回線からの操作でも緑にするのは、緩すぎるのでは」
緩めたのは色だけで、記録は緩めていません。社外の回線からでも、MFAありで、リリースや調査のための読み取りといった想定内の作業なら緑にしています。一方で、社外の回線からの権限の変更、秘密情報の読み出し、外部への開放は、MFAがあっても黄色のままです。
緩めた理由は、在宅や出張の日に毎回黄色が出ると、黄色が「いつものこと」になるからです。黄色の数を、人が本当に見る数に保つ方を優先しました。
緑にしたものも、技術レポートには実行者と操作を全件残しています。後から「あの日のあの操作は誰だったか」は引けます。
「本番環境の読み取りを、AIに毎朝渡してよいのか」
渡しているのは読み取りだけで、それも許可リストで絞っています。作成・更新・削除、コンテナやDBへの接続、権限の変更は許可リストに無く、必要なら「要判断」に書いて止まります。書き込みは共有ノートを1件作ることだけで、そのためのキーは別に持たせています。
読み取りでも漏れうるものはあります。ログには送信元のIPや利用者の識別子が入ります。共有ノートにはそれを書かせず、件数と判定だけにしています。

AI時代の要求管理ハンドブック ～経営・現場・開発がともに描く、問いから実現への道筋～
公開日：2026年11月5日
デジタル＆AIシステムズ・デザインセンター
独立行政法人情報処理推進機構（IPA）は、AIが社会や産業の基盤となる時代に求められる要求管理の考え方と実践を解説した「AI時代の要求管理ハンドブック」を公開しました。
AIやデータ、ソフトウェアの活用が広がり、ビジネス環境や技術が急速に変化する中、組織や社会が「何を実現したいのか」を明確にし、その目的を要求・要件として具体化するとともに、業務、データ、システム、ルール、評価、運用・改善へと一貫してつなげていくことが重要になっています。
そのためには、要求・要件を一度定義して終わりにするのではなく、関係者間で共通理解を形成し、変化に応じて継続的に管理していくことが求められます。
本書は、こうしたAI時代の要求管理を実践するために必要な基本的な考え方、手法、留意点等を体系的に整理したものです。

本書の特徴
1. 「何を実現したいか」を起点に考える
要求管理をシステム開発の上流工程に限定せず、組織や社会が実現したい価値を要求・要件へと結び付け、具体的な実現手段や評価・運用につなぐ継続的な活動として捉えて解説しています。
2. AI時代における要求管理の変化を捉える
AIシステム特有の不確実性やデータ品質、人とAIの役割分担等について、要求・要件として明確にするための考え方を解説します。また、AIを活用した要求の抽出、分析、文書化、整合性確認等の支援についても取り上げます。
3. 要求管理を継続的な組織活動につなげる
要求・要件と設計・実装・評価・運用を関連付け、変更に伴う影響を把握するためのモデル化やトレーサビリティの考え方を解説します。また、法令・規則等との接続や、要求管理を組織へ段階的に導入・定着させるための考え方も紹介します。
想定読者・活用場面
- 本書は、情報システムの開発者だけでなく、経営、事業、業務改革、AI・データ活用、法務、調達等に関わる幅広い関係者を対象としています。
例えば、次のような場面での活用を想定しています。
- 経営層・事業部門・業務改革担当者：事業上の目的や課題を関係者間で共有し、業務改革やAI活用の方向性を要求・要件へとつなげたい場合
- IT・システム開発・AI・データ担当者：要求・要件の品質を高め、設計・実装・評価・運用まで一貫して管理したい場合
- 法務・コンプライアンス・調達・行政機関の担当者：法令・規則・契約等で求められる事項を、業務やシステムで実現すべき要件として整理したい場合
- 組織の管理者・プロジェクト責任者：要求管理を特定の担当者に依存させず、組織的な活動として導入・定着させたい場合
本書のすべての内容を一律に適用する必要はなく、読者の役割やプロジェクトの特性、課題に応じて必要な内容を参照することができます。
本書の主な内容
本書は、次の5部で構成しています。
- 第1部 要求管理の基礎
- 「要望」「要求」「要件」の違いや要求工学の基本プロセスを整理し、要求管理の意義や、経営・事業活動との関係を解説します。
- 第2部 AI時代に要求管理はどう変わるか
- AIシステムに求められる要求・要件、AIによる要求管理支援、AI時代における要求管理プロセス等を解説します。
- 第3部 モデリングとトレーサビリティ
- 要求の可視化・モデル化、ビルディングブロックやサービスを活用したシステムの実現、要求・要件と実装等の追跡可能性の確保について解説します。
- 第4部 ルール・制度・コンプライアンスと要求管
- 法令・規制・標準や社内規則等を、業務やシステムで実現すべき要求・要件につなげるための考え方を解説します。
- 第5部 AI時代の要求管理プロセスの組織への定着
- 要求管理を組織に導入し、継続的に実践するための役割分担、導入ステップ、成熟度及び代表的な成果物について解説します。

タスク管理までAIエージェントに任せたら、確認待ちに答えるだけになった
はじめに
こんにちは、しもちです。
前回の「2026年自分流AIエージェント環境構築の秋」では、司令塔のエージェントに作業役を回してもらう仕組みを紹介しました。司令塔には作業だけでなく、抱えているタスク全体の管理も任せていて、どれに手を付けるか、どの順で進めるかも司令塔が決めます。自分でタスクの一覧を見て回ることはなくなり、司令塔が出してくる確認待ちに答えるのが主な仕事になりました。
今回は画面を中心に、その確認待ちを普段どう捌いているかを紹介します。
画面の全体
左が司令塔の Claude Code で、右が Orca の右サイドバーに出している「確認待ち」のパネルです。パネルは Orca のプラグインとして自作していて、エージェントの状態が変わるたびに読み直すので、司令塔が確認待ちを出すとすぐに並びます。
件名を押すと中身が開き、1行目に決めること、その下に判断に要る事実、最後に選択肢が並びます。詳しい経緯は PR やタスクのページにあり、必要があればそこを読みに行きます。
確認待ちができるまで
/coordinator で司令塔のスキルを起動すると、司令塔は GitHub と Notion のタスクを見比べて今抱えているものを組み立て直し、人間の判断が要るものを確認待ちに入れていきます。
- GitHub でレビュワーにアサインされた PR や、自分に割り当てられた Issue は、まず Notion のタスクにします。
- タスクの Next や前提のタスクを見て、着手できる条件がそろったものは作業役に渡し、設計の判断や本番への変更のように選択肢があるものは着手前の確認待ちにします。
- 着手する順番も司令塔が決めます。誰かが自分を待っているもの、期限の近いもの、ほかのタスクの前提になっているものの順です。
- 承認がそろってマージできる PR は、マージの確認待ちにします。
作業が始まってからのルールは、「人に見せる前」を意識して組みました。作業役の PR をほかのレビュワーに見せる前や、人の PR にレビューを投稿する前のように、自分以外の人の目に触れる手前で止まるようにしていて、そこまでは作業役と司令塔に任せています。ほかに、作業役が方針に迷ったときと、自分の手作業が要るときにも確認待ちが増えます。
番号で答える

Importantly, if AI is roughly doubling capabilities progress overall, it must be speeding up human researchers by much more than that.
Researchers work on improving algorithms and architectures; Anthropic has sometimes referred to these innovations as “compute multipliers.”5 Overall AI capabilities (“effective compute”) is the product of compute multipliers and training compute. Because the compute multipliers are only one input into capabilities, this means that if AI capabilities are advancing twice as fast overall because of software progress, the rate of growth in compute multipliers would need to be more than twice as fast: perhaps ~2.5-3x faster based on reasonable assumptions.6 Since there’s uncertainty about the size of speedup and how much of it comes from AI, I’ll go with ~2-3x.
Similarly, researcher labor is only one input to discovering these compute multipliers: they need to test their ideas, which requires compute for experiments. If we assume a very simple Cobb-Douglas model where experiment compute and labor are similarly important, that means the uplift to labor roughly needs to be the square of the acceleration in compute multipliers.7 This would imply that we would need a (~2-3x)^2 = ~4-9x speed up in labor to make overall AI capabilities go twice as fast.8

Each new compute multiplier takes more and more work to discover and implement (i.e., “ideas are getting harder to find”). Before there was much acceleration from AI, labor roughly grew at some roughly fixed exponential rate from hiring more humans. Combined with growth in compute, this compensated for diminishing returns enough to maintain the baseline rate of capabilities progress. libghostty-vt 1.0 is here. libghostty is a
portable, high-performance C library for terminal emulation, extracted
directly from the core of Ghostty. The 1.0 release means both the library

Today, the C API is a complete terminal emulator, it runs in production for millions of people across hundreds of products, both free and commercial, and it has a real, enforced ABI stability policy.
This post is about how we got here and what 1.0 actually means.1
Who Is Already Using It
Since starting the Ghostty project in 2022, the most common question I've been asked is "why?". I already answered this in the libghostty is coming post, so feel free to read that if you wish. Today, I'd rather answer this by showing the broad industry impact libghostty has already had. I believe this strongly validates its existence.
A year ago, I used a bug in JediTerm, the terminal emulator in JetBrains IDEs, as an example of why terminal emulation is hard to get right. A year later, the terminal in JetBrains IDEs now runs on libghostty. Every IntelliJ, PyCharm, GoLand, etc. user now has a libghostty-powered terminal. Based on a report by JetBrains, that's over 12.5 million active users.

replacing libvterm with libghostty-vt. Among other things, it closes a
10-year-old issue
about reflowing scrollback on resize. The maintainers are waiting on a
tagged release before merging so that distributions can package the
dependency separately, and the release today should enable that.
KDE developers are experimenting with a Konsole replacement built on it. Vercel's Turborepo uses it to render task output in its TUI. devenv uses it to drive shells. Antithesis used it to fuzz TUI programs and found real bugs in btop and others. Ghostel brings it to Emacs. ghostty-web is the WASM build with an Xterm.js-compatible API. There are community bindings for Rust, Go, JavaScript, Swift, Python, .NET, Elixir, Dart, Java, and more, and the awesome-libghostty list tracks well over a hundred projects.
More people today use a terminal powered by libghostty than use Ghostty the application, by a very large multiple. And libghostty is having a much larger impact than being "just" a terminal emulator.2
ABI Stability
1.0 means libghostty-vt follows semantic versioning and has strict
ABI compatibility
promises so that packagers across distributions and operating systems
can be confident packaging libghostty-vt and program developers can be
confident dynamically linking against it.
Beyond providing useful features, I believe the hallmark of a high-quality and enduring C library is ABI stability. So from the start, I took inspiration from C libraries I enjoyed working with and designed the API to have a strong, stable ABI that allows for future additions.
Every object is an opaque handle. The hundreds of values you might read or
write go through a small set of enum-keyed getters and setters, so we
can add new values easily without introducing a new symbol. Programs with
newer headers linked against an older libghostty get GHOSTTY_UNSUPPORTED
results instead of crashes or undefined behavior. The few non-opaque structs
we have carry their size so that fields can be appended later, or contain
reserved padding. Enums are pinned to int on every compiler, as much as
the C standard allows.
Our CI enforces our ABI policy. Every change is checked with libabigail against a committed baseline on Linux, and against golden type manifests on macOS and WebAssembly.
On ELF platforms, every exported symbol is also versioned, so the dynamic loader refuses to load a mismatched library by name rather than failing in some mysterious way later.

AWSでWebリクエストを受ける8パターンと「オリジンを裸にしない」設定プラクティス
はじめに
先日、X（旧Twitter）でこんな趣旨の話題が流れてきました。
- CloudFront + WAF → ALB の構成では、ALB の SG に CloudFront のプレフィックスリストを入れて直接アクセスを防ぐ
- ただし ALB のドメインが知られると、第三者が作った CloudFront 経由で WAF を迂回される。そのため秘密ヘッダーでの照合が必要
- さらに、CT Log が知られるようになってから、Host ヘッダー付きの攻撃が増えた
元の投稿はこちらです。
どちらも重要な指摘です。一方で、2024年11月に CloudFront VPC オリジン が登場してから、選べる構成はかなり変わっています。
この記事では、AWS で Web リクエストを受ける代表的な 8 パターンを、公式ドキュメントの根拠付きで、構成図と設定プラクティスにまとめます。
TL;DR
- 公式ドキュメントから読み取れる優先順位は 「VPC オリジン / OAC（マネージド）→ 使えない場合のみ プレフィックスリスト＋秘密ヘッダー」
- プレフィックスリストだけでは不十分です。他人の CloudFront も同じ IP 帯から来るため、本体は秘密ヘッダーの照合です
- CT Log にはオリジン用に取った証明書のホスト名が載るので、「ホスト名は知られる前提」で設計します
- 新規構築なら VPC オリジン＋CloudFront-VPCOrigins-Service-SG 限定 が第一候補です。名前を知られても、そもそも到達できません
- WAF は「中身を検査する層」、VPC オリジン / OAC / SG は「届く経路を絞る層」 です。役割が違うので両方必要で、WAF の主戦場はエッジ（CloudFront）です
以前のプラクティスと、いまのプラクティス
私自身、2015〜2017 年頃から「ELB（のちに ALB）をインターネットに公開し、その前に CloudFront を置く」構成を何度も作ってきました。当時はそれが一般的な作り方で、SG で CloudFront の IP に絞る、秘密ヘッダーで照合する、といった対策をプラクティスとして実装していました。
ALB をインターネットに公開する構成は今もよく見かけますし、それ自体が間違いというわけではありません。ただ、ここ数年でオリジンを閉じるためのマネージドな仕組みがそろい、同じ要件をよりセキュアに、しかも運用負荷を下げて作れるようになっています。
AWS 自身も、VPC オリジンの発表で「これまで VPC 内のオリジンはパブリックサブネットに置く必要があった」と書いています。つまり、10 年近く定番だった「ALB を公開して IP 制限と秘密ヘッダーで守る」方式は、今ではVPC オリジンが使えない場合のフォールバックという位置付けになりました。
この記事は、そうした変化を踏まえて「いま新しく作るなら、あるいは見直すなら、どう作るか」を整理したものです。
前提知識
プレフィックスリストだけではダメな理由
com.amazonaws.global.cloudfront.origin-facing は「CloudFront 全体」の IP 帯です。自社のディストリビューションに限った IP 帯ではありません。攻撃者が自分の AWS アカウントで CloudFront を作り、オリジンにあなたの ALB を指定すれば、SG は素通りします。WAF は「あなたの CloudFront」に付いているので、当然かかりません。
そのため公式ドキュメントでも、プレフィックスリストは Optional（追加の防御層） という位置付けです。本体は、カスタムヘッダーを ALB のリスナールールで照合する仕組みです。
CT Log（Certificate Transparency：証明書の透明性）とは
CT は、公的な CA（Certificate Authority：認証局）が発行した TLS 証明書を、誰でも検索できる公開ログにすべて記録する仕組みです。ブラウザが CT を必須にしているため、ACM で発行した証明書も必ず記録され、オプトアウトできません。
そのため crt.sh などで検索すれば、origin.example.com のように証明書を取ったホスト名を誰でも一覧できます。攻撃者はこれを偵察に使い、証明書の発行から数分でスキャンが来ることも観測されています。
DNS を公開していなくても、公的な証明書を取った時点でホスト名は知られる と考えておきましょう。ワイルドカード証明書で個別のホスト名を隠すことはできますが、それは推測しにくくするだけの隠蔽策です。本筋は「名前を知られても届かない」構成にすることです。
CA と CT の仕組み（構成・発行・検証・監視）は、図解付きで別の記事にまとめました。
選定フロー
DDoS 耐性のホワイトペーパーでは、CloudFront の背後に VPC 内のオリジンを置く場合、VPC オリジンが最新かつ推奨の方法 とされています。S3・AWS Elemental・Lambda 関数 URL については、引き続き OAC が推奨 です。
CloudFront の FAQ でも、マネージドな仕組みで要件を満たせない場合の代替として、カスタムオリジンヘッダーが挙げられています。
① CloudFront + VPC オリジン（内部 ALB）★第一候補
プライベートサブネットにある ALB / NLB / EC2 を、CloudFront のオリジンとして直接使えます。ALB にパブリック IP がないため、CT Log でホスト名を知られても、Host ヘッダーを付けても、インターネットから届く経路自体がありません。VPC オリジンの利用に追加料金はかかりません。
設定プラクティス
制約・注意点
- オリジンにできないもの：GWLB、TLS リスナーを持つ NLB。NLB には SG の付与が必須です
- 非対応の機能：gRPC、Lambda@Edge の origin request / origin response トリガー
- VPC Block Public Access を有効にすると、VPC オリジンの通信も止まります
- VPC オリジンで絞れるのは「自アカウント内で VPC オリジンを設定したディストリビューション」までです。同じアカウントに複数のディストリビューションがあり、特定のディストリビューションだけに限定したい場合は、カスタムヘッダーの検証も併用します（Origin cloaking）

- ポストプロセスが重い。
これ以外で、重い点が見つかるようであれば、まずその箇所の最適化を優先的に行います。
次のその最適化を施した状態でも重い場合は，非同期コンピュートに逃がすことを考え、処理時間を隠蔽すること考えます。
当時では、デカール処理などが若干重かったので、デカール処理時間を隠蔽するようにレンダリングパスの入れ替えなどを行い、ボトルネックの解消を行いました。
次に、モデル描画です。モデル描画は重いものの、まぁ許容できる処理時間ではあったのですが、GPUでオクルージョンカリングを行っており、そちらの方が処理時間を1,2ms程度喰っていて問題となっていました。そのため、GPUでオクルージョンカリングをやめて，CPUでオクルージョンカリングを実行する方針へと変更しました。
こちらのCPUオクルージョンカリングが入って、これでモデル描画はいったん解決としました。
続いては、ポストプロセスが重い問題です。
縮小バッファ対応などがすでにされているのであれば、あとはやることは決まっています。
「どのポストプロセスを残すか？」を決めるだけです。
基本的に絵作りに重要な要素は外せないと思うので，BloomやTAAは残します。
それ以外は基本的に不要と考え、SSAOやSSRなど縮小バッファで乗り切れるものは残し，DOFやモーションブラーなど乗り切れない機能は大胆に削るという判断をします。
当然、全部を切ってしまうと絵が残念になるだけなので、非同期コンピュートに逃がせるようなものは残しておくという形になります。
つぎに、ライティングが重い問題です。
これはやるべきことは2つ。
一つ目はコードレベルの最適化です。当初の実装が結構大味だったので、ループ先頭で早期リターンできる場合には早期リターンするなど、簡単なものからWave Intrinsicsを使った最適化まで出来る限りの最適化を行います。
コードの最適化をやっても、どうしても重い箇所が出てきます。これはもうしようもないのでアーティストにライトの重なりの調整や削減を依頼します。幸いにもライティング担当を兼ねていたテクニカルディレクターが今回は対応してくれたので、すんなりと調整が行えました。
以上の3点を解決することで、PC版 60FPS対応は行えました。
コンソール版もこの最適化の恩恵を得ることができ、PS5やXbox Series Xだったので60FPSに近いパフォーマンスが出るようになりました。
120FPS達成まで
60FPSは比較的に対応が簡単でした、…というのものそもそも最適化が全くされていなかったせいです。
ここからエンジニアとしてはハードモードに突入します。…というのもの60FPS達成である程度最適化できるところはしてしまったので、大きなボトルネックがもうない状態になっています。
120FPS達成するには、8.3ms以内，理想的には7ms台に抑える必要が必要があります。
モデル描画はスケールアップしないので，3ms程度，ポストプロセスも出力解像度依存になるので、1.5ms程度で抑える必要があります。この時点で4.5msかかります、余った時間で残りのすべての処理を済ませるという方針になります。
モデル描画についてはオクルージョンカリングなどできる限りの最適化は済ませている状態です。時間があればクラスターカリングを導入することで更なる処理改善が見込めましたが、マスターアップが迫ってきていて、片手で数える程度の時間しかありません。
…となると最終手段を講じる他ありません。その最終手段とは「モデルの表示数を削る」です。まず、Series S対応等もあったので、ゲーム進行に関係しない賑やかしで、効果があるものは積極的に削ってもらいます。
次に，PIX等のGPUデバッガやプロファイラを使って，シーン中においてボトルネックになっているモデルをいくつかピックアップして、パフォーマンスが最適になるようにモデル側を調整してもらいます。特に細長いポリゴン等は処理時間を喰いやすいので、ポリゴンの割り方を調整してもらったり、LODで下げるなどでアーティストに対応してもらいます。エンジニアができる限りのことをして、どうにもならないものだけをアーティストに仕方なく調整を依頼するという感じです。アーティスト側も120FPS対応は非常に大変だという認識があるので、このプロジェクトでは非常に積極的に対応していただけました。結構経験から、こういう時にアーティスト側がごねることが多いのですが、今回は120FPS対応という異次元なオーダーだったので、アーティスト側も覚悟を持っていただけていたようで、積極的に協力していただけました、本当にありがたかったです
あと、モデル描画についてエンジニア側でできる小手先の最適化も行っていきます。
まずはRe-Z対応ですね。対応できるものは片っ端から入れていきます。どのぐらい改善したかは具体的な数値は覚えていないですが、確実に効果があります。
頂点シェーダで頂点データ関連をバッファなどのSRVから読み取りしているのですが、モデル単位でデータを読み取るものは全頂点で同じデータにアクセスすることになるので，最初のレーンで読み取りすれば十分なはずです。
Wave Intrinsicsをつかって無駄に読み込まないように対応を行いました。これも微々たるものですが、高速化効果が得られたので、対応しました。
あとはやったのはアルファテストの対応ですかね。パイプラインとしてZ-PrepassやってG-Buffer描画を行うのですが、Z-PrepassとG-Bufferで同じようなピクセルシェーダを使用していました。このときにZ-PrepassとG-Bufferでそれぞれアルファテストを実行していたのですが、DEPTH_EQUALでどうせ弾くので、G-Bufferでのアルファテストは無意味になります。また、discardを実行すると遅くなるという問題があるので、Z-prepassのみでアルファテストを実行し，G-Bufferではアルファテストを実行しないように変更し，Early-Zなどで早期に棄却できる場合は早期棄却し，ピクセルシェーダが無駄に起動しないように抑制します。これも微々たるものですが、高速化効果が得られるので対応しました。
次に、頂点シェーダからの出力されるアトリビュート数の削減ですね。これが一番効果があります。頂点シェーダから出力されるアトリビュートの数は4だったかな、一定数を超える急激にパフォーマンスが遅くなるという傾向があります。これはPS4世代から知られている事実なので、今更知らないグラフィックスプログラマーはいないでしょうが、結構対応が面倒なので億劫で放置しがちです。これを頑張って数を減らします。オープンワールドゲームなどでもなかったし、120FPS対応しないいけないから仕方ないだろうと腹を括って、出力値を16bit精度に落とせるものは落として，1つのアトリビュートにできるだけパッキングします。例えばテクスチャでいえば
struct VSOutput
{
float4 Position : SV_POSITION;
float2 TexCoord0 : TEXCOORD0;
float2 TexCorod1 : TEXCOORD1;
float2 TexCoord2 : TEXCOROD2;
float2 TexCoord3 : TEXCOORD3;
};
みたいなものがあれば、
struct VSOutput
{
float4 Position : SV_POSITION;
float4 TexCoord0123 : TEXCOORD0;
};
のような構造体にして，TexCoord0123.x に input.TexCoord0.x　と input.TexCoord0.yを f32tof16()をつかって詰め込むという感じの実装です。こうした感じで，出力アトリビュートの数を減らして，ピクセルシェーダ側でf16tof32()を使って、データを復元し、復元したデータをマテリアル評価に流すという感じの実装に変更しています。
あとは、ハードウェア機能でポリゴン単位でカリングできるようなものがあったりするのですが、一律全部入れるみたいなことを試したら返って遅くなったので、この機能の採用は見送っています。会社さんによってはZ-prepassだけ採用すると早くなるという事例もあるようなので、いくつかのパターンで実験した方が良さそうです。当時はそこまでいろいろなことを試す時間は残されていませんでした。
あとはdxc(DirectX Shader Compiler)など、現在のシェーダコンパイラ世代ではdouble型がサポートされていたりします。そのため、1.0と1.0fは異なるデータ型になります。左はdouble型として判定され，右はfloat型として判定されます。1.0fのようなサフィックス付きにできる箇所は全部fのサフィックスを付けるように対応しました。もともとはdouble型をサポートしていないPCでも動作できるようにする対応の一環として行ったのですが、よくよく考えれば64bitなのでVGPRを無駄に喰っている可能性があったのかもしれないので、最適化になっているのかもしれません。…知らんけど。
あとできる地味な最適化としてはコンテキストロール対策ですね。シェーダが頻繁に切り替わるとコンテキストロールが発生して、ストールすることがあります。この対策としては同じシェーダはまとめて書き、無駄にシェーダが切り替わらないようにすればよいです。そのためには，シェーダバイナリに含まれるシェーダハッシュを使ってドローコールをソートして、まとめるみたいことをすればコンテキストロールを抑え込むことができます。特に半透明描画などはコンテキストロールで重くなりがちなので、ソートして問題ない箇所などは積極的にコンテキストロールが発生しないようにまとめると良いです。ちなみに別プロジェクトでもコンテキストロール対策してみました。このときはZ-prepassで前から順番に書いていたんですが、このときにコンテキストロールがかなり発生していてZ-prepassが非常に重かったので、思い切って前から順番に書かないようにして、コンテキストロールが発生しないようにソートするように変更してみたところ1ms-1.5ms程度の処理時間改善がありました。コ

全米工学アカデミー（NAE）は2026年9月8日、ホンダジェットの生みの親である藤野道格氏を、J・C・ハンサカー航空工学賞の受賞者に選んだと発表した。航空工学の分野で優れた業績を上げた人に贈られる賞で、授賞式は10月4日、ワシントンで開かれた。
同アカデミーは、藤野氏の功績として、エンジンを主翼の上に載せる配置において最適な位置を見つけ出し、実証したことを挙げている。空気抵抗を減らし、燃費を高め、客室の騒音を抑え、室内を広げる航空技術の革新だと称える。
2024年には、ライト兄弟のオーヴィル・ライトが最初の受賞者となった賞、ダニエル・グッゲンハイム・メダルも授与された。ホンダによると、日本人の受賞は藤野氏が初めてだったという。
だが、世界に認められたその設計は、かつて社内で酷評された。航空機の研究計画は一度打ち切られ、機体が世に出るまでには約30年を要している。
「こんな馬鹿な技術者は見たことがない」
ホンダジェットを、ほかの機体と見間違えることはないだろう。主翼の上面から支柱が伸び、その先にエンジンが載っている。
小型ビジネスジェットのエンジンは、ふつうなら胴体後部の左右に取り付けられる。翼の上に載せると空気抵抗が増え、揚力が減るからだ。開発当時の常識では、ありえない配置だった。
社内でも、この案は大いに物議を醸し、受け入れられなかった。ある会議の席上、上司は藤野氏にこう言い放ったという。
「こんな馬鹿な技術者は見たことがない。クビだ」

そもそもこの独特なエンジンの配置を着想するまでに、藤野氏は長い回り道をしている。
