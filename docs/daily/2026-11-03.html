We find that frontier LLMs are surprisingly good at natively reading and writing neural network weights, well past what we’d expect from humans or conventional algorithms. This might be a big deal for both optimization and interpretability.
Just by looking at the raw weights, GPT-6 Astra can tell what a network was trained to do. And without any environment feedback, it has no trouble writing, from scratch, small game-playing networks that outplay networks trained with PPO for 100 million steps.
Likewise, asked to make Qwen3.5-0.8B better at math without gradients, Astra identifies an issue in its weights causing reasoning loops that Qwen’s own model card warns about, and fixes this by natively editing 0.016% of the weights. With the same sampling settings, this weight correction raises MATH-500 from 7.9% to 48.1% and generalizes out of the box to instruction following, raising IFEval by 3x.
All of this is possible without allowing Astra to write training loops. It uses its reasoning to figure out what each part of a neural network computes, or should compute, and changes the weights accordingly. We call this Weight-Space Programming.
Throughout the history of deep learning, we encoded our simplistic inductive biases into tiny symbolic optimizers like Adam or Muon. This is changing: our neural network weights will soon be natively optimized by LLMs that deliberately reason about their weights.
If you were asked to handcraft a neural network that plays Go, what would you do? If you were handed raw neural network weights and asked to predict their behavior, where would you even start? For almost any human, this is practically impossible.
Today, weights are written by optimization, by custom networks trained to write them, or by compilers from formal programs. In this post, we find that the current generation of frontier LLMs, used natively in natural language, are starting to become eerily good at understanding and crafting neural network weights around natural-language goals.
For a few years now, we’ve all been using LLMs to optimize text artifacts like prompts and the programs built around them . More recently, we’ve started using them to optimize whole harnesses and the training code and hyperparameters that train ML models .
We often justified these methods by reference to the fact that we don’t know other principled ways to hill-climb on text artifacts, unlike for updating the weights of differentiable neural networks. After all, humans can “optimize” code by hand, for example, so it made sense to ask LLMs to do it, but they can’t “optimize” neural weights by hand, so those remained largely in the realm of symbolic algorithms.
In this post, we share very early results that allow us to argue that the paradigm of reasoning-driven optimization is now coming even for differentiable neural networks.
In Weight-Space Programming, a general-purpose LLM reads and writes a network’s weights directly (i.e., not through an optimizer, and in particular not with gradient descent) around some natural language spec, sometimes even with no environment feedback at all.
In natural language, it’s becoming possible to “just ask” an LLM to natively find a hidden trait or failure inside the weights of a neural network, to fix that failure, or to write a new network from scratch. The Cursor Marketplace serves extensions for the Cursor editor. Because extensions run with the permissions of the IDE and the user running it, a backdoored extension gets immediate access to local files, source code, and developer tooling as soon as its module is loaded.
Notably, Phorion has discovered a likely oversight in how the malware tries to turn on SSH. The setup logic assumes it can check the current Remote Login state without root privileges. When run as a standard user, systemsetup -getremotelogin prints an administrator-access error and exits with status 0 instead of returning Off. Because the script only tries to enable SSH if the output matches Off, it skips the enablement step entirely. On a Mac that doesn’t already have SSH running, that mistake breaks the inbound access path, even though the SSH keys and persistence still get dropped.
In this post, we’ll walk through how the backdoor works, why that macOS check fails, and what to look for across your fleet. It's the memory latency, stupid
Making GROUP BY faster by doing more (CPU!) work
When you see your databases CPU at 100%, what is it actually doing? We like to act as though CPUs run code linearly for simplicity's sake, but in truth CPUs are incredibly complex beasts; they can potentially do many instructions at once, or sometimes none at all (despite our console showing 100%). Because CPUs can do so many things, one CPU at 100% may be doing much less than another at 100%. A CPU is considered "idle" only if no task (Linux task) needs CPU time; this does not mean the CPU itself is being fully saturated. So why would a CPU not be fully utilized, even if it appears to be at 100%?
The answer is usually memory.
Memory accesses are orders of magnitude slower than internal CPU operations. To give a good picture of how much so, a modern CPU might be able to process somewhere in the realm of 4-8 instructions per nanosecond. A memory access to RAM can take somewhere in the realm of 50-100ns. To ease your mathing, that means a modern CPU can do around 400-800 instructions for every one memory access from RAM.
Given this, CPUs are built from the ground up to work their way around this. The most obvious way this is dealt with is CPU caches. CPU caches keep memory closer to the CPU than RAM, literally baked into the CPU chip. The closest cache (the L1 cache) takes around 1ns per memory operation- that's 50-100x faster than RAM! The "problem" here of course is that the CPU caches are fairly small; the L1 cache for a modern CPU is probably around ~64KB, while the farther caches max out at a few hundred MB for top end processors. A good database tries manipulating data in small "chunks" to take full advantage of caches, and you'll often hear cache utilization as being one of the top concerns of performance engineering.
Let's look at GROUP BY aggregations to get a better grip on cache utilization. In GROUP BY, we're looking to take a dataset, group it by a certain column (or more), and perform certain aggregations (for example, count, or sum on another column). The "naive" method might be to open a HashTable keyed by the group key that grows ever larger. For every new row, you would check if that key exists- if it does, go to it's corresponding aggregation and update the result. Simple, right? The problem is that if you have millions of unique groups, you're not utilizing your cache at all! Nearly every HashTable access will be a "cold" hit that goes to RAM. This means that although your CPU may /look/ like it's 100% utilized, in truth it'll constantly be waiting for cold memory accesses.

Why do our grids show a brief spike in electricity demand every minute? A team led by Dirk Witthaut from Forschungszentrum Jülich has now demonstrated that this is due to regular power checks carried out by large-scale battery storage systems. Tennet Germany, the largest transmission system operator in Germany, has observed over several years that the frequency in the European power grid dips briefly every 60 seconds. While these deviations were not critical to grid security, they were clearly measurable and unusually regular. The cause of this phenomenon was initially unclear.
A team at Forschungszentrum Jülich led by Dirk Witthaut—who is also a professor at the Institute for Theoretical Physics at the University of Cologne—joined forces with other researchers from the University of Cologne and the Karlsruhe Institute of Technology to search for an answer—and they found it: the cause appears to be the many large-scale battery storage systems that check their state of charge every minute. This leads to measurable fluctuations in electricity consumption, which can contribute to turbine wear and tear, for example. The battery storage systems ensure an uninterrupted power supply, and their numbers have increased significantly worldwide in recent years. The researchers found that this was not a European phenomenon, but a global one.

“It really was years of detective work,” says Witthaut. The grid frequency pattern is shaped by many different factors. Every Japanese law (法令) as git history. One commit is one amending law coming into
force: git log laws/act/415/415AC0000000057.md is the amendment history of the Personal
Information Protection Act, and git show <commit> is what one amendment changed.
Before v1.0, history may be rebuilt and force-pushed.
- laws/<law type>/<first 3 characters of the ID>/<e-Gov law ID>.md, with metadata in YAML
frontmatter. The first 3 characters are the era and year of promulgation (415 = 平成15年).
- Tables are HTML (merged cells kept). Figures and 様式 are links to the attachment on e-Gov,
on a line of their own, or as an HTML link inside a sentence or a table cell. About 3 in
10 figures have no attachment there and show （図：e-Gov に画像なし） instead.
- The table of contents (目次) is left out: it only repeats the headings.
- main: enforced revisions. upcoming: promulgated but not yet in force.
- Commit date = enforcement date (00:00 JST). Trailers: Amendment-Law-Id, Enforced;
for an amending Act, also Bill (the Diet bill), Bill-Submitter (who submitted it, e.g. 内閣 or 神谷宗幣君外四名) and Bill-Url (its text on the House of Representatives site,
where the bill's 理由 is). Skipped-Revision names a revision
e-Gov has no text for; the commit's diff covers it too.
git cannot record dates before 1970, so earlier ones are recorded as 1970-01-02; the real
date is in the Enforced trailer and the frontmatter.
- An amendment whose enforcement day is not fixed yet has enforced: "undetermined" and Enforced: undetermined, and is the last commit on upcoming (dated 2117-12-31, the
placeholder e-Gov uses). enforcement_comment in the frontmatter words the day as the
amending law does (e.g. 政令で定める日); with it, an upcoming date is e-Gov's estimate.
- A repealed law's file is deleted in the repealing law's commit; its history stays in
git log -- <file>.
- History starts around 2015, not at enactment. e-Gov's revision data ramps up from about 2015 (a few hundred commits a year before, about two thousand a year from 2019), so a time series of commit dates measures e-Gov's coverage as much as legislation.
- git blame dates the coverage, not the wording. A law's oldest commit holds every
line that existed before coverage began: most of 刑法 blames to its 2016 commit. Read it
as "already there by then".
- Many laws have little history. About a third of laws have a single commit.
- A law enters at its oldest e-Gov revision. Checking out an old date shows no file for a law e-Gov covers only later, not its older text: about 2,800 laws at 2010-01-01 against 9,000 now.
- Commit SHAs are not stable before v1.0. A rebuild keeps them only while the data
and the builder are unchanged; a builder change, or e-Gov adding a revision dated before
existing commits, rewrites every later SHA. Refer to a revision by its law_id and revision_id (both in the frontmatter) instead.
File names are e-Gov law IDs, which stay the same when a title changes. Search the frontmatter by title:
git grep -l '^title: "個人情報の保護に関する法律"' -- laws
Heading depth depends on the chapters around an article, so match any depth:
git log -L '/^##* *第十六条/,/^##* *第十七条/:laws/act/415/415AC0000000057.md'
This takes the first match, the main text. For an article of a 附則, start the range at
that 附則's heading, which names its amending law: /^## 附　則（令和二年/,/^## 附　則/.

ISUCONとは
ISUCONは「いい感じにスピードアップコンテスト」の略で、遅いWebサービスを決められたルールの中でどこまで速くできるかを、チームで競う大会です。
ミラティブはISUCON2026にGoの言語スポンサーとして協賛しました。
チーム
私とyamakuraはバックエンドエンジニア3年目で、2人ともISUCON14に続いて2回目の参加です。teruteruはバックエンドエンジニア5年目で、ISUCONは今回が初めてでした。言語はGoを選びました。
チームとしての事前の練習は、私に声をかける勇気がなく開催なし。当日は開始の1時間前に集まって雑談しつつ、teruteruがインフラまわり、私とyamakuraがアプリかなー、とふんわり決めて挑みました。
チームは全員Claude Opus 5.5を用いて取り組みました。
今年の題材
今年の題材は、決まった時間に写真を投稿しあうSNS「isureal」でした。BeRealをモチーフにしたような題材ですね。短い時間に画像のread/writeが集中することと、世界中にサーバーがある環境を模していることが特徴でした。
事前に用意されたサーバーは以下のとおりです。
利用者は国ごとに、ルーターでアプリのサーバー3台のどれかに振り分けられます。3台のアプリは、asia2のPostgreSQLを共有します。asia1からasia2までは往復で約1msですが、europe1・america1からは往復で約100msかかります。
以降は、asia1をアジアサーバー、europe1・america1を欧米サーバー、asia2をDBサーバーと呼びます。
サーバー同士の通信も、クライアント（ベンチマーカー）からの通信も、すべて運営が用意したルーターを通ります。参加者はこのルーターに触れません。リージョン間の遅延や帯域の制限はこのルーターが作っていて、海外のサーバーとの物理的な遠さを再現しています。
難しかったのは、次の条件が重なっていたところです。
- europeとamericaの利用者は、asiaの1.5倍のスコアになる
- ベンチマーカーは、リージョンをまたいでも、write直後のreadに結果が反映されていることを求めてくる
- リージョン間は往復で100msかかる
- 画像のやり取りが多い

プロファイリングツールをAI向けに準備（前日）
ISUCONでは、ベンチを回したらpprof、nginxのアクセスログ、スロークエリログを見てボトルネックを探すことが多いと思います。これをまとめて見られるのがpproteinです。ISUCON12で優勝したチームNaruseJunの皆さんが作って利用していたことで有名なツールです。私はISUCON14の時に利用させてもらいました。ISUCONにかなり寄せた作りという印象で、サーバーが複数台あっても各サーバーの計測をまとめて集めてくれるのが便利でした。
ただ、pproteinはAIが当たり前になる前に作られたツールなので、計測結果はブラウザの画面で人が見る前提でした。そこで前日に素振りしたついでにforkして、計測結果をMarkdownかJSONで、上位の行だけに絞って返すAPIを追加しました。あわせて、その使い方をコーディングエージェントのスキルにしておきました。当日の午前中には、スロークエリの収集がMySQLにしか対応していなかったので、PostgreSQL向けのパッチも当てました。
おかげで当日は、プロファイリングの結果をAIに聞くのがかなり楽でした。 後述のデプロイの仕組みと合わせて、結果を解析、根拠とともに修正、また結果を解析して修正、というループをコーディングエージェントだけで回せるようになったのがいい感じでした。
当日の動き（午前）
前日に素振りしていたのもあり、デプロイまわりの整備とプロファイリングツールの導入は私が担当しました。午前中の私は、主にデプロイまわりの整備をコーディングエージェントに指示しつつ、ルールを読んだり、SSEで実装されている通知のあたりを怪しみながら見ていました（通知は最後までボトルネックになりませんでした 😢）。

まず、コマンド一発でサーバー上のアプリのバイナリを入れ替えられるようにしました。少しあとに、競技サイトのAPIを叩いてベンチを始めるコマンドも作りました。どちらも開始と終了の通知がDiscordに飛ぶようにしました。地味に便利。

当日の動き（午後）
お昼ごろまでは、各自がpproteinの結果からボトルネックをAIに聞きつつ、DBとの往復を減らすなどの改善を進めていました。ただ、11時の計測の時点で、欧米サーバーはアジアサーバーの3〜15倍遅いことが見えていました。12時を過ぎたあたりから、レプリカを置くなど、リージョン間の遅延への対処に手を付け始めます。
まず同期レプリケーションにより欧米サーバーにDBのレプリカを配置し、readは手元のレプリカで行うようにしました。これで欧米サーバーは、DBを読むたびにアジアまで往復する無駄を解消できました。一方で、非同期レプリケーションにしてしまうと、write APIの直後のread APIに結果が見えず、ベンチマーカーがFAILとなりました。
つまりベンチマーカーはリージョン間での強整合性を求めて来ています。鬼だ。 強整合性を取るためには、write APIのたびに、欧米のレプリカへの反映をおよそ100ms待ってから応答を返す必要があります。この条件は変えずに、以下の最適化を行なって21万点に到達しました。当日のログをあさっても、まとめてデプロイしていたりして、どれが特に効いたのかはわかりませんでした...
- write APIのレプリケーション待ちを最適化
- 人気ユーザーのusersレコードへの書き込みがロック待ちで詰まっていたので、usersの行をロックするAPIでは、書き込みのトランザクションだけsynchronous_commitをoffにしてコミットすることでロックを解放し、レプリケーションは別の空のトランザクションで待つようにしました。ただ、この時点では、レプリケーションを待つあいだDBコネクションは保持したままでした
- 続けて、synchronous_commitをlocalにしてレプリケーションを待たずにコミットし、DBコネクションをすぐ解放するようにしました。レスポンスを返すまでにはレプリケーション完了を保証する必要があるので、APIの最後に空のwriteクエリを叩いて待つことでケアしました。この時のDBコネクションは、レプリケーション完了確認専用のプールから確保するようにしました。また、確認を待つリクエストの一覧をsync.Mutexで管理し、単一の空のwriteクエリで、並んでいる全リクエスト分のレプリケーション完了を確認するようにしました
- write APIの中でもアジアのユーザー同士の友達申請のようにレプリケーション遅延が影響しない場合は、レプリケーションを待たないようにしました
- 欧米サーバーのwrite APIのほとんどをアジアサーバーに転送してリージョン間往復の数を削減
- DBのコネクションプールの数を調整
最終的に、read系統はほぼ欧米、write系統はほぼアジアという構成になりました。以下の感じ。
- 欧米サーバーにレプリカを置く
- readは手元のレプリカで行う
- writeのAPIはnginxでアジアサーバーに転送する
- アジアサーバーのreadのAPIの一部を、欧米サーバーに転送する
- アジアサーバーにアクセスが集中しがちで、欧米サーバーには余裕があったため
細かく言うと誰がやったとかはあるのですが、差分を作るなどの実際の作業はコーディングエージェントがやるので、割と誰がやってもよかった気がします。次に何をしたら効きそうかを3人で話して、いいねとなったものを入れていく感じでした。
終盤

OpenAI、Google、Microsoftは2026年10月30日、robots.txtでWebコンテンツのAI学習利用を指定する新たな仕組みに対応する方針を発表した。サイト運営者は、__usage_ai-trainingという識別子を使い、対応する複数のAI事業者へ学習利用の許可・拒否をまとめて伝えられる。事業者ごとに設定を管理する負担を減らす狙いがある。
対応時期や、新しい指定と既存の設定を併用した場合の扱いは、事業者によって異なる。
- OpenAI：Making it easier for websites to express AI training preferences
- Google：Supporting a shared AI training control for websites
- Microsoft：Your content, your choice: clearer preferences for training and grounding
robots.txtで学習利用の許可・拒否を指定
OpenAI、Google、Microsoftが対応を予定する仕組みでは、クローラーへの指示を書くファイル、robots.txtを使う。
学習利用の可否を伝えるには、サイト運営者がrobots.txtのUser-Agent行に__usage_ai-trainingを書く。これは特定のクローラー名ではなく、学習利用についての指定であることを表す識別子。たとえば、サイト全体のコンテンツを生成AIの学習に使うことを拒否する場合は、次のように指定する。
User-Agent: __usage_ai-training
Disallow: /
Disallowは学習利用の拒否を、/はサイト全体を表す。特定のパスだけ学習利用を認める場合は、Allowを使う。たとえば、サイト全体では拒否し、/press-kit/以下のコンテンツだけ利用を認める場合は、次のように書く。
User-Agent: __usage_ai-training
Disallow: /
Allow: /press-kit/
これらの設定が伝えるのは、コンテンツを学習に使ってよいかどうか。クローラーがサイトを巡回してよいかどうかは、これまでのクローラー向けルールで別に指定する。[1]
この仕組みの基になるのは、IETFのAI Preferences（AIPREF）ワーキンググループでの議論を踏まえ、10月30日に公開された仕様案「Machine-Readable Training Preference Signal」。AnthropicのKevin Kelley氏が提出した草案で、IETFが承認した標準ではない。
各社が順次対応、Anthropicも実装を開始
OpenAIは今後数か月での実装を目指し、対応時に詳細を案内する。Googleは2027年初頭の対応を予定。Microsoftは2027年2月1日から、クロールで設定を読み取ったサイトやページへの適用を始める。
Anthropicについては、Kelley氏が10月30日のIETF公開メーリングリストへの投稿で実装を始めたと説明した。各サービスで対応するまでには時間がかかるとしており、完了時期には触れていない。[2]
OpenAIは既存のクローラー設定を継続
OpenAIでは、既存のクローラー向け設定も引き続き適用される。学習用のGPTBotと検索用のOAI-SearchBotへの指示は、現在も別々に設定でき、学習利用を拒否しつつChatGPTの検索結果への掲載を認められる。[3]
たとえば、学習用のGPTBotによる巡回を拒否し、検索用のOAI-SearchBotによる巡回を許可するには、robots.txtに次のように書く。
User-Agent: GPTBot
Disallow: /
User-Agent: OAI-SearchBot
Allow: /
Googleは学習とグラウンディングをまとめて制御
Googleでは、既存のGoogle-Extendedで、コンテンツの学習利用と、回答時に情報源として参照するグラウンディングへの利用をまとめて許可・拒否する。対象は、将来のGeminiモデルの学習と、GeminiアプリやVertex AIのGrounding with Google Searchでのグラウンディング。
Googleが__usage_ai-trainingによる指定を読み取るようになると、学習利用を拒否した場合の扱いは、Google-Extendedを個別に指定しているかどうかで変わる。
たとえば、robots.txtに次のように書き、Google-Extendedを個別に指定しなければ、GoogleはこれをGoogle-Extendedでの拒否として扱う。そのため、上記の学習とグラウンディングの両方が制限される。
User-Agent: __usage_ai-training
Disallow: /
一方、__usage_ai-trainingで学習利用を拒否していても、次のようにGoogle-Extendedで個別に許可すれば、Googleによる学習とグラウンディングへの利用をともに認められる。
User-Agent: __usage_ai-training
Disallow: /
User-Agent: Google-Extended
Allow: /
Googleの説明によると、Google-Extendedで利用を明示的に許可したサイトはGeminiアプリの回答で参照される対象になる。Google-Extendedの設定は、Google検索への掲載や検索順位には影響しない。
Microsoftは学習とグラウンディングを個別に設定
Microsoftは、クローラーで収集したWebコンテンツの学習利用と、回答時の情報源としての利用を別々に設定できるようにする。学習利用の設定はAI Training、回答時の参照の設定はAI Groundingと呼ぶ。
学習利用は、robots.txtの__usage_ai-trainingでサイト全体や特定のパスを対象に指定できる。ページごとのメタタグでも指定でき、メタタグでの指定はrobots.txtの設定より優先される。一方、グラウンディングへの利用はrobots.txtでは指定せず、ページごとのメタタグで指定する。[4]
たとえば、あるページの学習利用を拒否し、回答時の参照を認めるには、そのページのHTMLのhead要素内に次のメタタグを書く。name="Bingbot"は、MicrosoftのクローラーであるBingbotに向けた指定を表す。
<meta name="Bingbot" content="ai-training:disallow">
<meta name="Bingbot" content="ai-grounding:allow">
グラウンディングの指定をallowからdisallowextendedに変えると、CopilotやMicrosoft 365など同社が運営するサービスでの参照は認めつつ、同社が第三者に提供するグラウンディングサービスでの利用を拒否できる。
Microsoftでは、適用される設定がなければ、学習、グラウンディングともに許可する扱いとなる。これらの設定で学習やグラウンディングを拒否しても、通常のBing検索結果に掲載される対象からは外れない。
コラム：Microsoftの旧設定による制限を維持するには移行が必要
Microsoftはこれまで、ページのメタタグに書かれたNoArchiveやNoCacheの指定に応じて、そのページのコンテンツを学習やグラウンディングに利用する範囲を制限してきた。2027年3月1日以降は、これらの指定による利用制限を適用しなくなるため、制限を続けるには同日より前に新しい設定へ移行する必要がある。
ただし、Microsoftがサイト内で新しいAI TrainingまたはAI Groundingの設定を読み取ると、そのサイトでは3月1日を待たずに旧設定の適用が終わる。
ページに新しい設定を書いても、Microsoftが再クロールで読み取るまでは反映されないため、グラウンディングの制限を維持するにはBing Webmaster Toolsへの一時設定の登録も必要になる。一時設定の登録受付は2026年12月15日に始まり、同日時点でNoArchiveまたはNoCacheを使用しているサイトが対象となる。
Bing Webmaster Toolsに登録した一時設定は、各ページに書いた新しい設定が再クロールで読み取られるまで適用される。ただし、読み取られないままでも2027年9月30日には失効する。具体的な指定方法と移行条件は、Microsoftの移行ガイドで確認できる。

Just by looking at the raw weights, GPT-6 Astra can tell what a network was trained to do. And without any environment feedback, it has no trouble writing, from scratch, small game-playing networks that outplay networks trained with PPO for 100 million steps.

Throughout the history of deep learning, we encoded our simplistic inductive biases into tiny symbolic optimizers like Adam or Muon. This is changing: our neural network weights will soon be natively optimized by LLMs that deliberately reason about their weights.
If you were asked to handcraft a neural network that plays Go, what would you do? If you were handed raw neural network weights and asked to predict their behavior, where would you even start? For almost any human, this is practically impossible.

うまくいかなかったこと
ここからが本題であり、次に解決すべき課題点です。

何が問題だったのか
「AIに対して行った指示が正しいかどうか」を人間が見る、という元の方針自体は、今も正しいと思っています。AIが自律的に動き出している現在において、起点となった人間の意思や意図こそが、最重要の情報だと考えるからです。
では問題点はどこだったのか？
現在問題点だと感じているのは、ワークフロー内のどこにも、本人しか持っていない情報を要求する箇所がなかった という点ではないかと考えています。
コンセプトの4項目はコードを読めばAIが全て埋められるものです。埋められるものに関してはAIに埋めさせる。AIによって埋めたもの、すなわちコンセプト立案者の考えが入っていないものをレビューしたとしても、レビュー側が指摘することはほとんどありません。
なのであれば、「必ずコンセプト立案者の考えを入れる」ようなワークフローにすることで、コンセプトのレビューが機能すると考えています。

1. AIが下書きし、人には判断を聞く
コンセプトを作る順番を逆にします。
- 人は今まで通りやりたいタスクをAIに伝えます
- AIが調査した上で、コンセプトを下書きします
- AIは作成した下書きの中から「決まらなかった点」を0 ~ 4個取り出し、人間に聞きます

聞くのは例えば以下のようなことになる想定です。
- ユーザーから見える挙動が変わるが、いいか？
- 今回やらないと決めた範囲はなぜやらないのか？
- 後戻りしにくい変更をいま入れてもいいか？
絶対のルールとして、この「本人の判断」の欄はAIが勝手に埋めてはいけないことにします。これによって人間の言葉がそのまま記録されることになります。

robots.txtで学習利用の許可・拒否を指定
OpenAI、Google、Microsoftが対応を予定する仕組みでは、クローラーへの指示を書くファイル、robots.txtを使う。
学習利用の可否を伝えるには、サイト運営者がrobots.txtのUser-Agent行に__usage_ai-trainingを書く。これは特定のクローラー名ではなく、学習利用についての指定であることを表す識別子。たとえば、サイト全体のコンテンツを生成AIの学習に使うことを拒否する場合は、次のように指定する。
User-Agent: __usage_ai-training

Disallowは学習利用の拒否を、/はサイト全体を表す。特定のパスだけ学習利用を認める場合は、Allowを使う。たとえば、サイト全体では拒否し、/press-kit/以下のコンテンツだけ利用を認める場合は、次のように書く。
User-Agent: __usage_ai-training
Disallow: /
Allow: /press-kit/
これらの設定が伝えるのは、コンテンツを学習に使ってよいかどうか。クローラーがサイトを巡回してよいかどうかは、これまでのクローラー向けルールで別に指定する。[1]

We find that frontier LLMs are surprisingly good at natively reading and writing neural network weights, well past what we’d expect from humans or conventional algorithms. This might be a big deal for both optimization and interpretability.
Just by looking at the raw weights, GPT-6 Astra can tell what a network was trained to do. And without any environment feedback, it has no trouble writing, from scratch, small game-playing networks that outplay networks trained with PPO for 100 million steps.
Likewise, asked to make Qwen3.5-0.8B better at math without gradients, Astra identifies an issue in its weights causing reasoning loops that Qwen’s own model card warns about, and fixes this by natively editing 0.016% of the weights. With the same sampling settings, this weight correction raises MATH-500 from 7.9% to 48.1% and generalizes out of the box to instruction following, raising IFEval by 3x.
All of this is possible without allowing Astra to write training loops. It uses its reasoning to figure out what each part of a neural network computes, or should compute, and changes the weights accordingly. We call this Weight-Space Programming.
Throughout the history of deep learning, we encoded our simplistic inductive biases into tiny symbolic optimizers like Adam or Muon. This is changing: our neural network weights will soon be natively optimized by LLMs that deliberately reason about their weights.
If you were asked to handcraft a neural network that plays Go, what would you do? If you were handed raw neural network weights and asked to predict their behavior, where would you even start? For almost any human, this is practically impossible.
Today, weights are written by optimization, by custom networks trained to write them, or by compilers from formal programs. In this post, we find that the current generation of frontier LLMs, used natively in natural language, are starting to become eerily good at understanding and crafting neural network weights around natural-language goals.
For a few years now, we’ve all been using LLMs to optimize text artifacts like prompts and the programs built around them . More recently, we’ve started using them to optimize whole harnesses and the training code and hyperparameters that train ML models .

It's the memory latency, stupid
Making GROUP BY faster by doing more (CPU!) work
When you see your databases CPU at 100%, what is it actually doing? We like to act as though CPUs run code linearly for simplicity's sake, but in truth CPUs are incredibly complex beasts; they can potentially do many instructions at once, or sometimes none at all (despite our console showing 100%). Because CPUs can do so many things, one CPU at 100% may be doing much less than another at 100%. A CPU is considered "idle" only if no task (Linux task) needs CPU time; this does not mean the CPU itself is being fully saturated. So why would a CPU not be fully utilized, even if it appears to be at 100%?
The answer is usually memory.
Memory accesses are orders of magnitude slower than internal CPU operations. To give a good picture of how much so, a modern CPU might be able to process somewhere in the realm of 4-8 instructions per nanosecond. A memory access to RAM can take somewhere in the realm of 50-100ns. To ease your mathing, that means a modern CPU can do around 400-800 instructions for every one memory access from RAM.
Given this, CPUs are built from the ground up to work their way around this. The most obvious way this is dealt with is CPU caches. CPU caches keep memory closer to the CPU than RAM, literally baked into the CPU chip. The closest cache (the L1 cache) takes around 1ns per memory operation- that's 50-100x faster than RAM! The "problem" here of course is that the CPU caches are fairly small; the L1 cache for a modern CPU is probably around ~64KB, while the farther caches max out at a few hundred MB for top end processors. A good database tries manipulating data in small "chunks" to take full advantage of caches, and you'll often hear cache utilization as being one of the top concerns of performance engineering.
Let's look at GROUP BY aggregations to get a better grip on cache utilization. In GROUP BY, we're looking to take a dataset, group it by a certain column (or more), and perform certain aggregations (for example, count, or sum on another column). The "naive" method might be to open a HashTable keyed by the group key that grows ever larger. For every new row, you would check if that key exists- if it does, go to it's corresponding aggregation and update the result. Simple, right? The problem is that if you have millions of unique groups, you're not utilizing your cache at all! Nearly every HashTable access will be a "cold" hit that goes to RAM. This means that although your CPU may /look/ like it's 100% utilized, in truth it'll constantly be waiting for cold memory accesses.

Mystery of 60-Second Fluctuations in Power Grids Solved
30 October 2026
Why do our grids show a brief spike in electricity demand every minute? A team led by Dirk Witthaut from Forschungszentrum Jülich has now demonstrated that this is due to regular power checks carried out by large-scale battery storage systems. These findings could help to make our electricity supply more robust, as the team reports in an article published in Nature Energy.
Tennet Germany, the largest transmission system operator in Germany, has observed over several years that the frequency in the European power grid dips briefly every 60 seconds. While these deviations were not critical to grid security, they were clearly measurable and unusually regular. The cause of this phenomenon was initially unclear.
A team at Forschungszentrum Jülich led by Dirk Witthaut—who is also a professor at the Institute for Theoretical Physics at the University of Cologne—joined forces with other researchers from the University of Cologne and the Karlsruhe Institute of Technology to search for an answer—and they found it: the cause appears to be the many large-scale battery storage systems that check their state of charge every minute. This leads to measurable fluctuations in electricity consumption, which can contribute to turbine wear and tear, for example. The battery storage systems ensure an uninterrupted power supply, and their numbers have increased significantly worldwide in recent years. The researchers found that this was not a European phenomenon, but a global one.
Many devices, a common rhythm
“It really was years of detective work,” says Witthaut. The grid frequency pattern is shaped by many different factors. For example, it reveals the influence of electricity trading, with power stations being switched on and off abruptly, as well as the fluctuating feed-in from renewable energy sources, and various other disturbances.
Uns war schnell klar, dass es sich bei der Ursache um etwas handeln muss, das von der Uhr gesteuert wird
“It quickly became clear to us that the cause must be something controlled by the clock,” says Witthaut. There was no other way to explain the precise 60-second cycle. It was also clear that: “The observed effect can only be produced if many devices are consuming electricity at the same time.” A single consumer or generator could therefore be ruled out.
Measurements on campus provide the clue
But how do all these devices synchronize their consumption? The researchers finally found the crucial clues with the help of the Living Lab Energy Campus. This research infrastructure on the Jülich campus is primarily used to develop and test highly integrated energy supply systems. The team installed measuring points on end devices at a total of 80 locations – and sure enough, the same periodic pattern in electricity consumption was observed precisely at the locations where large-scale battery storage systems are designed to ensure an uninterrupted power supply. “We took a closer look at one of them and found a spike in electricity consumption at the start of every minute due to the power check,” explains Witthaut.
As there are no binding standards for such power checks, Witthaut suspects that most battery manufacturers assumed that a 60-second interval would be sensible. The start of every minute was simply chosen as the test time. “It is entirely possible, however, that battery storage systems are only part of the problem here,” says Witthaut. “It cannot be ruled out that other digitally controlled appliances – such as air-conditioning systems, heat pumps, washing machines, and dishwashers – may also exhibit similar patterns.”
Less synchronization, less wear and tear
The periodic fluctuations in electricity demand are already having an impact on hydroelectric power stations. The brief spikes in demand mean that the turbines slow down momentarily before accelerating back to their original rotational speed. This increases wear and tear. With the expansion of storage technologies, such problems could become even more prevalent. In Ireland, for example, where data centres with large-scale battery storage systems currently account for around a fifth of the country’s electricity demand, the amplitude of the 1-minute signal quadrupled between 2016 and 2021. The solution, however, would be simple: “You would simply have to distribute the checks randomly, rather than always starting them at the same time,” says Witthaut.

Every Japanese law (法令) as git history. One commit is one amending law coming into
force: git log laws/act/415/415AC0000000057.md is the amendment history of the Personal
Information Protection Act, and git show <commit> is what one amendment changed.
Before v1.0, history may be rebuilt and force-pushed.
- laws/<law type>/<first 3 characters of the ID>/<e-Gov law ID>.md, with metadata in YAML
frontmatter. The first 3 characters are the era and year of promulgation (415 = 平成15年).
- Tables are HTML (merged cells kept). Figures and 様式 are links to the attachment on e-Gov,
on a line of their own, or as an HTML link inside a sentence or a table cell. About 3 in
10 figures have no attachment there and show （図：e-Gov に画像なし） instead.
- The table of contents (目次) is left out: it only repeats the headings.
- main: enforced revisions. upcoming: promulgated but not yet in force.
- Commit date = enforcement date (00:00 JST). Trailers: Amendment-Law-Id, Enforced;
for an amending Act, also Bill (the Diet bill), Bill-Submitter (who submitted it, e.g. 内閣 or 神谷宗幣君外四名) and Bill-Url (its text on the House of Representatives site,
where the bill's 理由 is). Skipped-Revision names a revision
e-Gov has no text for; the commit's diff covers it too.
git cannot record dates before 1970, so earlier ones are recorded as 1970-01-02; the real
date is in the Enforced trailer and the frontmatter.
- An amendment whose enforcement day is not fixed yet has enforced: "undetermined" and Enforced: undetermined, and is the last commit on upcoming (dated 2117-12-31, the
placeholder e-Gov uses). enforcement_comment in the frontmatter words the day as the
amending law does (e.g. 政令で定める日); with it, an upcoming date is e-Gov's estimate.
- A repealed law's file is deleted in the repealing law's commit; its history stays in
git log -- <file>.
- History starts around 2015, not at enactment. e-Gov's revision data ramps up from about 2015 (a few hundred commits a year before, about two thousand a year from 2019), so a time series of commit dates measures e-Gov's coverage as much as legislation.
- git blame dates the coverage, not the wording. A law's oldest commit holds every
line that existed before coverage began: most of 刑法 blames to its 2016 commit. Read it
as "already there by then".
- Many laws have little history. About a third of laws have a single commit.
- A law enters at its oldest e-Gov revision. Checking out an old date shows no file for a law e-Gov covers only later, not its older text: about 2,800 laws at 2010-01-01 against 9,000 now.
- Commit SHAs are not stable before v1.0. A rebuild keeps them only while the data
and the builder are unchanged; a builder change, or e-Gov adding a revision dated before
existing commits, rewrites every later SHA. Refer to a revision by its law_id and revision_id (both in the frontmatter) instead.
File names are e-Gov law IDs, which stay the same when a title changes. Search the frontmatter by title:
git grep -l '^title: "個人情報の保護に関する法律"' -- laws
Heading depth depends on the chapters around an article, so match any depth:
git log -L '/^##* *第十六条/,/^##* *第十七条/:laws/act/415/415AC0000000057.md'
This takes the first match, the main text. For an article of a 附則, start the range at
that 附則's heading, which names its amending law: /^## 附　則（令和二年/,/^## 附　則/.
出典：e-Gov法令検索（https://laws.e-gov.go.jp/）、PDL1.0（https://www.digital.go.jp/resources/open_data/public_data_license_v1.0）
e-Gov法令検索の法令データ（法令API v2）を houritsu-builder（Kohei-Wada）が markdown に加工して作成。 条文の文字は変更していない（markdown のための見出し記号とエスケープ、図へのリンクを加えた）。正本は官報。改正履歴は e-Gov が提供する範囲に限る。
議案との対応：衆議院議案データベース（smartnews-smri、MIT）。議案番号と本文ページへのリンクのみ使用。

こんいす！ミラティブでバックエンドエンジニアをしているhamadaです。
ISUCON2026に、社内のバックエンドエンジニア3人で「Team Y3」として出てきました。結果は33位、213,540点でした。
前回のISUCON14から2年。そのあいだに、ソフトウェアエンジニアを取り巻く世界はずいぶん変わりましたね。ISUCON14のときは、まだGitHub CopilotやChatGPTを使っていたくらいで、コーディングエージェントは使っていなかった記憶があります。
今回はかなりコーディングエージェント頼みになるだろうと思いながら参加しました。実際、8時間で3人あわせて90本のPRをマージしています。
この記事は基本的にhamadaが書いていますが、途中にteruteruとyamakuraのパートがあります。2人には、競技中にやったことや感想をそれぞれ書いてもらっています。
ISUCONとは
ISUCONは「いい感じにスピードアップコンテスト」の略で、遅いWebサービスを決められたルールの中でどこまで速くできるかを、チームで競う大会です。
ミラティブはISUCON2026にGoの言語スポンサーとして協賛しました。
チーム
私とyamakuraはバックエンドエンジニア3年目で、2人ともISUCON14に続いて2回目の参加です。teruteruはバックエンドエンジニア5年目で、ISUCONは今回が初めてでした。言語はGoを選びました。
チームとしての事前の練習は、私に声をかける勇気がなく開催なし。当日は開始の1時間前に集まって雑談しつつ、teruteruがインフラまわり、私とyamakuraがアプリかなー、とふんわり決めて挑みました。
チームは全員Claude Opus 5.5を用いて取り組みました。
今年の題材
今年の題材は、決まった時間に写真を投稿しあうSNS「isureal」でした。BeRealをモチーフにしたような題材ですね。短い時間に画像のread/writeが集中することと、世界中にサーバーがある環境を模していることが特徴でした。
事前に用意されたサーバーは以下のとおりです。
利用者は国ごとに、ルーターでアプリのサーバー3台のどれかに振り分けられます。3台のアプリは、asia2のPostgreSQLを共有します。asia1からasia2までは往復で約1msですが、europe1・america1からは往復で約100msかかります。
以降は、asia1をアジアサーバー、europe1・america1を欧米サーバー、asia2をDBサーバーと呼びます。
サーバー同士の通信も、クライアント（ベンチマーカー）からの通信も、すべて運営が用意したルーターを通ります。参加者はこのルーターに触れません。リージョン間の遅延や帯域の制限はこのルーターが作っていて、海外のサーバーとの物理的な遠さを再現しています。
難しかったのは、次の条件が重なっていたところです。
- europeとamericaの利用者は、asiaの1.5倍のスコアになる
- ベンチマーカーは、リージョンをまたいでも、write直後のreadに結果が反映されていることを求めてくる
- リージョン間は往復で100msかかる
- 画像のやり取りが多い
スコアの推移
10:21の初回は3千点でした。13時台に9万点台、15時台に20万点台まで上がり、16:04に最高の21万点が出ました。 この辺りはスコアが調子よく伸びて、スクショを撮ってはチームの連絡用のDiscordに貼っていました。
16時ごろからは決定的な手が出てこなくてスコアをうまく伸ばせず、四苦八苦していました。 最終的には一番スコアが出た時の状態に戻して18時ギリギリまでベンチマークガチャを回していました。teruteruの引きが良く、21万点台で終了できました。感謝。
プロファイリングツールをAI向けに準備（前日）
ISUCONでは、ベンチを回したらpprof、nginxのアクセスログ、スロークエリログを見てボトルネックを探すことが多いと思います。これをまとめて見られるのがpproteinです。ISUCON12で優勝したチームNaruseJunの皆さんが作って利用していたことで有名なツールです。私はISUCON14の時に利用させてもらいました。ISUCONにかなり寄せた作りという印象で、サーバーが複数台あっても各サーバーの計測をまとめて集めてくれるのが便利でした。
ただ、pproteinはAIが当たり前になる前に作られたツールなので、計測結果はブラウザの画面で人が見る前提でした。そこで前日に素振りしたついでにforkして、計測結果をMarkdownかJSONで、上位の行だけに絞って返すAPIを追加しました。あわせて、その使い方をコーディングエージェントのスキルにしておきました。当日の午前中には、スロークエリの収集がMySQLにしか対応していなかったので、PostgreSQL向けのパッチも当てました。
おかげで当日は、プロファイリングの結果をAIに聞くのがかなり楽でした。 後述のデプロイの仕組みと合わせて、結果を解析、根拠とともに修正、また結果を解析して修正、というループをコーディングエージェントだけで回せるようになったのがいい感じでした。
当日の動き（午前）
前日に素振りしていたのもあり、デプロイまわりの整備とプロファイリングツールの導入は私が担当しました。午前中の私は、主にデプロイまわりの整備をコーディングエージェントに指示しつつ、ルールを読んだり、SSEで実装されている通知のあたりを怪しみながら見ていました（通知は最後までボトルネックになりませんでした 😢）。
デプロイとベンチをコマンド一発に
まず、コマンド一発でサーバー上のアプリのバイナリを入れ替えられるようにしました。少しあとに、競技サイトのAPIを叩いてベンチを始めるコマンドも作りました。どちらも開始と終了の通知がDiscordに飛ぶようにしました。地味に便利。
3人とそれぞれのコーディングエージェントが同時に動いていると、誰かのベンチ中に別の人がデプロイして、ベンチの結果がおかしくなることがあります。そこで、デプロイからベンチまでの流れが3人でかぶらないように、デプロイのコマンドは始める前に競技サイトを見て、走っているベンチがあればデプロイせずに止まるようにしました。
当日の動き（午後）
お昼ごろまでは、各自がpproteinの結果からボトルネックをAIに聞きつつ、DBとの往復を減らすなどの改善を進めていました。ただ、11時の計測の時点で、欧米サーバーはアジアサーバーの3〜15倍遅いことが見えていました。12時を過ぎたあたりから、レプリカを置くなど、リージョン間の遅延への対処に手を付け始めます。
まず同期レプリケーションにより欧米サーバーにDBのレプリカを配置し、readは手元のレプリカで行うようにしました。これで欧米サーバーは、DBを読むたびにアジアまで往復する無駄を解消できました。一方で、非同期レプリケーションにしてしまうと、write APIの直後のread APIに結果が見えず、ベンチマーカーがFAILとなりました。
つまりベンチマーカーはリージョン間での強整合性を求めて来ています。鬼だ。 強整合性を取るためには、write APIのたびに、欧米のレプリカへの反映をおよそ100ms待ってから応答を返す必要があります。この条件は変えずに、以下の最適化を行なって21万点に到達しました。当日のログをあさっても、まとめてデプロイしていたりして、どれが特に効いたのかはわかりませんでした...
- write APIのレプリケーション待ちを最適化
- 人気ユーザーのusersレコードへの書き込みがロック待ちで詰まっていたので、usersの行をロックするAPIでは、書き込みのトランザクションだけsynchronous_commitをoffにしてコミットすることでロックを解放し、レプリケーションは別の空のトランザクションで待つようにしました。ただ、この時点では、レプリケーションを待つあいだDBコネクションは保持したままでした
- 続けて、synchronous_commitをlocalにしてレプリケーションを待たずにコミットし、DBコネクションをすぐ解放するようにしました。レスポンスを返すまでにはレプリケーション完了を保証する必要があるので、APIの最後に空のwriteクエリを叩いて待つことでケアしました。この時のDBコネクションは、レプリケーション完了確認専用のプールから確保するようにしました。また、確認を待つリクエストの一覧をsync.Mutexで管理し、単一の空のwriteクエリで、並んでいる全リクエスト分のレプリケーション完了を確認するようにしました
- write APIの中でもアジアのユーザー同士の友達申請のようにレプリケーション遅延が影響しない場合は、レプリケーションを待たないようにしました
- 欧米サーバーのwrite APIのほとんどをアジアサーバーに転送してリージョン間往復の数を削減
- DBのコネクションプールの数を調整
最終的に、read系統はほぼ欧米、write系統はほぼアジアという構成になりました。以下の感じ。
- 欧米サーバーにレプリカを置く
- readは手元のレプリカで行う
- writeのAPIはnginxでアジアサーバーに転送する
- アジアサーバーのreadのAPIの一部を、欧米サーバーに転送する
- アジアサーバーにアクセスが集中しがちで、欧米サーバーには余裕があったため
細かく言うと誰がやったとかはあるのですが、差分を作るなどの実際の作業はコーディングエージェントがやるので、割と誰がやってもよかった気がします。次に何をしたら効きそうかを3人で話して、いいねとなったものを入れていく感じでした。
終盤
終盤はずっと初期データの画像に手こずっていました。 競技終了の1時間前にはコードフリーズして安全に過ごそうねという約束もあり、大きな構成変更に出られない状況でもありました。
アジアサーバーの画像の配信は、応答時間の12.6%を占めていました。 この時点で初期データの画像（約14GB）はDBに入っていて、DBのキャッシュが画像のせいで効かなくなるなどの問題がありました。ここを直せばスコアが上がるかも、と考えていました。
そこで、DBの中に格納されている画像データをアジアサーバー（アプリのサーバー）のディスクにコピーして、画像をそこから読むようにしました。画像のコピーは成功したのですが、17:12のベンチは10万点で、16:54の21万点から半分に落ちました。前から作ってあったキャッシュの仕組みに相乗りしたせいで、ディスクキャッシュのLRU自体が膨らみ、メモリが逼迫したのが原因でした。 LRUに載せない改善を入れたりもしたのですが、21万点を超えるスコアが出ることはなく、撤退を決めました。
終了30分前ぐらいに、超焦りながらyamakuraとteruteruに助けを求めつつrevert commitを入れる、という楽しい思い出になりました。
反省
データをどこに置くかを大局で考えられなかった
今回の問題で一番大事だったのは「どのデータを、どのリージョンに置くか」だったのかなと感じています。 私たちは、レプリカ、readの転送、writeの転送と、目の前の遅いところを1つずつ直していきました。どれも効果はありましたが、全体の設計をじっくり考える時間があっても良かったのかもしれません。 アクセスログを腰を据えて解析したり、デプロイツールをもう少し作り込んで、大胆なインフラ変更を何度も試せるようにしたりと、やれることは色々あったと思います。 「推測するな、計測せよ」とはありますが、要はバランスなのかもと感じました。
