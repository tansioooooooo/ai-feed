OpenCode 2.0
OpenCode 2.0 is a major overhaul. It draws on millions of daily users' experience to deliver a system that can flex to everything an agent needs to be. There are quite a lot of new features, performance improvements, and bug fixes but here are some of the more impactful user-facing changes.
The Service
From the beginning OpenCode adopted a client/server model. However, this was not something it took advantage of by default and was mostly used by power users.
In 2.0 this server now automatically runs as a single background process on your machine. When you open up a TUI, the web interface or the desktop app they're all talking to the same central process.
If you're using the programmatic client @opencode/client to make your own scripts, they will autodiscover the local service and just work. This is particularly useful for scheduled tasks. You can also call it via CLI by using opencode api commands.
You can expose it to other hosts and run /pair or opencode pair to connect it to other applications. We have native apps in the works that take advantage of this flow.
The API
The old API grew haphazardly as we and the world collectively learned what agents are and should be. It was bad.
We started from scratch and examined all the weird use cases across the millions of users who use OpenCode every day. It now supports nearly anything you need to be able to do.
OpenCode is also aware of its own API and will call it to do useful things like moving the current session into a git worktree when starting new work.
We've also shipped a new client package @opencode/client that contains clients for vanilla JavaScript as well as Effect.
Code Mode
The models love to write code and OpenCode 2.0 takes advantage of that more than any other coding agent. We've built a minimal JavaScript interpreter in the @opencode/codemode package.
This package ingests MCP servers or OpenAPI endpoints, converting them into functions that the agent can call in a script. It can run these scripts natively without the complexity of Node.js VMs or embedding complicated solutions like QuickJS.
This lets your agent write scripts that can do things like call a tool, map over the results and call another tool. Single round trip instead of calling them one at a time.
All MCP servers in 2.0 are opted into codemode by default. This means you can add a thousand of them with minimal context bloat and your agent will discover and compose them to get things done.
Background Tasks
The latest batch of models are incredibly good at orchestration and it is important for harnesses to let them express the full extent of that capability.
First, we've added background subagents. This allows the primary agent to kick off some work to another one while it continues.
This happens automatically but you can also trigger it manually - even with a different model. It lets you do things like “spawn a background fable subagent to review this code” while you keep prompting.
Second, we've added background shell commands. The shell tool can be invoked asynchronously so long-running work does not have to block the primary agent. It'll be notified when things are complete.
If any foreground shell command or subagent takes longer than you expect, you can hit a hotkey to move them to the background so you can keep prompting.
Plugins
Although OpenCode 1.0 had a plugin system, it never got the attention it needed. To correct that, we forced ourselves to implement nearly every OpenCode 2.0 feature as an internal plugin and there are now 80+ of them. This guarantees that the Plugin API stays well maintained.
We've also promoted TUI plugins from experimental to stable. Since it is all powered by OpenTUI, you can build nearly anything. Here is an example of something useless.
We also spent quite a lot of time ensuring everything in OpenCode 2.0 can be hot-reloaded. So it can write a plugin for itself mid-session and use it right away - we covered the design of this in a previous blogpost.
You can ask OpenCode to build whatever plugin you want and it knows how to. But if you do want to read the docs, they are available here.
The SDK
OpenCode can also now be used as a library with the @opencode/sdk package. This is the exact same code that powers our CLI.
This means you can strip it down and make your own flavor of OpenCode that runs on a server or in specialized environments like Durable Objects. And then you can connect to it from any OpenCode client since it speaks the standard OpenCode server protocol.
It also has an optional Effect-based API.
This one is still in development as things are shifting but you can already use it.
Upgrading
To upgrade the CLI, make sure you're on the latest 1.x release, then run opencode upgrade --major.
To upgrade your desktop app, download the latest here.

Server API is completely different
tui.json config is moved to json
There are a lot of other changes but they are backwards

Americans’ Social Activity Has Steeply Declined in the Past 30 Years
In recent years, there has been extensive discussion of a social decline in the United States, including a U.S. surgeon general advisory in 2023 that declared American loneliness to be an “epidemic.”
Various surveys have tracked America’s social decline over the past few decades. Tracking data from the American Time Use Survey shows that Americans are spending more time alone and less time with friends than they were two decades ago. Perhaps most notably, the American Perspectives Survey has found that from 1990 to 2021, the percentage of Americans with five or more close friends dropped by 25 points, from 63% to 38%.
But while extensive public tracking data show general declines in Americans’ socialization, little, if any, public data show what this looks like for the average American — how the day-to-day activities Americans participate in have changed over the past few decades.
In a new survey, Data for Progress surveyed 1,098 U.S. adults and asked them how many times they engaged in various specific social activities in the past 12 months. These questions directly replicate the DDB Needham Life Style surveys, which tracked Americans’ participation in various activities from 1975-1999 and were referenced in Robert Putnam’s 2000 book “Bowling Alone.” In this analysis, Data for Progress’ 2026 data is compared with the DDB Needham Life Style survey from 1995, which is the earliest year in which full data for all comparison questions was available.
This survey finds significant, double-digit declines in Americans’ participation in key social activities from 1995 to 2026.
The chart below compares the percentage of Americans who report participating in each tested activity at least one time in the past 12 months, between the 1995 and 2026 surveys. We find that Americans’ participation in various social activities has declined by double-digit margins, including attending a class or seminar (-22), entertaining people in your home (-21), attending church or a place of worship (-20), going on a picnic (-19), going to a club meeting (-19), playing cards (-19), going out to breakfast at a restaurant (-13), and doing volunteer work (-12).
A few activities have seen increased engagement: using the internet (+90), playing a home video game (+22), attending an exercise class (+14), going to a pop or rock concert (+13), and taking an airline trip for personal reasons (+5).
Methodology note: This analysis compares two surveys conducted using different methodologies, including differences in constructing sampling frames, modes, and weighting approaches. The findings below should be read as suggestive of trends, not a precise estimate of change. Please see the “Methodology” section below for more information.
One of the steepest declines in the survey is for “entertaining people in my home.” While in 1995, 88% of Americans reported entertaining others at home at least once in the past year, this number has declined to 67% in 2026.
Church attendance has dropped from 74% in 1995 to 54% in 2026.
The percentage of Americans who report having gone on a picnic in the past year has declined from 58% in 1995 to 39% in 2026.
There has also been a 19-point decline in attendance at club meetings, from 45% in 1995 to 26% in 2026.
This analysis adds to existing public data on America’s social decline. Previous reports have found that Americans are spending less time with others and reporting fewer close friends. This new analysis demonstrates that Americans are indeed spending less time in specific social settings, such as restaurants, churches, picnics, parties, bars, and social clubs.
Methodology
The DDB Needham survey was conducted by Market Facts using a stratified quota sampling procedure that begins with a sampling frame acquired from commercial list brokers. The sample oversamples by demographics such as race, gender, and marital status to oversample lower propensity respondents. Finally, the survey contacted individuals via mail.
In comparison, the Data for Progress adult sample was conducted through web panel suppliers and ensured national representativeness via quota fielding and post-stratification weighting.
There is plenty of research on the compositional differences that exist across survey collection modes, and this is likely to affect these results as questions about religiosity and loneliness tend to demonstrate modal differences and social desirability biases. We understand that these factors are at play in our comparison, but find that the magnitude and consistency in trends across measures is a substantial signal about trends in behaviors nonetheless.

Why is every rationalist blog post way too long?
For my piece on Catholic miracle apologetics, I read (correction: skimmed) a 25,000-word post by rationalist blogger Scott Alexander. My piece, which cited (but does not focus on) his, ended up being a cool 2,700 words. I don't think it would benefit from being longer, and it was the result of me cutting around 70% of the text I initially wrote.
Rationalist bloggers do not generally appear to have this impulse. Eliezer Yudkowsky's "sequences" are over one million words long. Nearly every blog post I have read in this ecosystem, even the rare one that contains some good ideas, is painfully long and extremely tedious. These bloggers tend to spend their time on precisely the wrong things, i.e. adding layers of detail and nuance rather than interrogating the one or two assumptions they make at the start or broadening their philosophical background beyond the collection of texts popular within their subculture.
It seems to me that, in this community, verbosity is a substitute for thoroughness: surely, if someone wrote a lot about something, and is able to demonstrate that by producing a large volume of text, they must have something worthwhile to say about it? Consider when blogger Gwern explained that nicotine, actually, is not addictive, and is good for you, as long as you don't smoke it, over the course of 9,000 words, with over 100 references. It turns out, actually, nicotine is addictive, and is bad for you even if you don't smoke it, as you probably already obviously knew.
In any case, what is missing from this endlessly verbose rationalist writing style is wisdom. Wisdom involves discretion: an intuition for what ideas are and are not worth seriously pursuing, and the ability to determine what does and does not need to be said. This community, broadly speaking, does not seem to value wisdom as a trait at all; the idea that something may be true, valuable, or good merely because it is common sense or inherited tradition is anathema to them. Instead, there is a heavy bias towards that which is unconventional and counterculture, with the amount of ink spilled for heterodox ideas taken as evidence in itself that these ideas are worth taking seriously.

JPMorgan, Morgan Stanley, SMBC and MUFG are quietly shopping pieces of the AI debt pile they helped build, a sign the lenders closest to the money have started hedging their own bet.
Six months ago, banks were racing each other to underwrite data center loans tied to Oracle, Meta and the rest of the AI buildout. Now some of the same banks are trying to get that debt off their books. JPMorgan, Morgan Stanley, SMBC and MUFG have been exploring significant risk transfers, according to a report from the Financial Times. These are deals that let a bank keep a loan on paper while shifting its riskiest slice to outside investors. The banks are doing this because they are bumping up against internal limits on how much AI-linked exposure any one lender can hold.
One case shows how stuck this has gotten. A group of banks including JPMorgan and MUFG has spent more than six months trying to distribute $38 billion in construction debt tied to a Texas and Wisconsin data center project leased to Oracle, Bloomberg has reported. Some lenders are now willing to sell pieces of it to non-bank buyers at a discount, just to move it. Six months is a long time to sit on debt nobody underwrote to hold forever.
Matthew Moniot, co-head of credit risk sharing at Man Group, told the Financial Times the deal sizes involved are "out of scale to anything we've thought about, ever." That is not a hedge-fund manager talking down a trade he wants no part of. It is someone whose job is pricing exactly this kind of risk, saying the numbers no longer fit any model he has used before.
Oracle is the clearest tell. Its five-year credit default swaps, the cost of insuring against the company defaulting, climbed to around 151 basis points in early October, levels last seen in 2009, according to market data cited by Bloomberg. S&P had already cut Oracle's credit rating to BBB-, a single notch above junk, back in July. The company is reportedly targeting more than $40 billion in additional debt and equity this fiscal year. That is on top of the $18 billion in bonds it sold in a single day last September, and the money is needed to keep funding its Texas, Wisconsin and New Mexico sites.
Oracle sued Wisconsin's Public Service Commission over a rule that could force it to post more than $7 billion in collateral for its Port Washington data center campus. The fight helped push S&P to cut Oracle's credit rating to BBB-, one notch above junk, as the company's AI spending outpaces its cash flow. - Oracle Wisconsin data center collateral dispute - utilities regulator $7 billion lawsuit
Demand for that paper has thinned out, too. Bonds from Alphabet, Amazon, Meta, Microsoft and Oracle now trade at a premium to similarly rated non-AI corporate debt. Order books for their offerings have shrunk from roughly five times the amount on sale back in February to under two times by July, Bloomberg has reported. That is the difference between a bond that sells itself and one a bank has to work to place.
None of this is happening in isolation. The 10-year Treasury yield hit 5.304% this month, its highest since 2002, after a $39 billion auction cleared at 5.30%, the highest auction yield since 2000. The Federal Reserve's own September meeting minutes named AI-related corporate borrowing as a contributor to that move. Capital Economics argues the bigger driver is plain old inflation and government deficits, not tech company bond sales. Whoever is right about the cause, the effect is the same for anyone trying to finance a data center right now: the risk-free rate they are borrowing against just got a lot more expensive.
Frankly, the mechanics here matter more than the headline number. Banks do not sell down debt they are confident in. They sell down debt when they are worried about concentration, which is exactly what "approaching internal limits" means in plain English: too much of this bank's balance sheet is now one bet on one sector holding up. Spreading $120 billion of AI infrastructure spending across special purpose vehicles was supposed to make that risk easier to swallow. That is the structure Oracle, Meta, xAI and CoreWeave have all used to keep debt off their own balance sheets. Instead the risk is turning up at the banks that financed the SPVs in the first place.
The investors who still want in have gotten pickier about where. Capital is rotating toward data centers leased to investment-grade hyperscalers like Microsoft and Google, and away from weaker credits, Bloomberg has reported. That is exactly why CoreWeave-leased paper prices at 7.00% to 9.875%, against the 5.70% to 7.875% that hyperscaler-leased bonds command, per bond market data compiled by CCIR. A smaller, less capitalized AI infrastructure company trying to raise debt next quarter is now competing for the same nervous pool of lenders as Oracle. Except without Oracle's balance sheet or its existing customer base to point to.

Our philosophy
A huge debate we’ve been having is on the balance between reliability and creativity.
To really care about the prod builders, we should be shipping models that meet our quality bar for intelligence and have been battle-tested to the limits of what we can do internally.
On the other hand, there’s no way that our team has a full understanding of what is needed to spark delight in the world and build sick sci-fi. We don’t want to impose our values of extreme reliability on those dreamers.
Our solution: share those dreamer-ready features under “danger zone” flags in our API headers. These are features that will be here to stay for future models, are (as far as we can tell) better than what exists out there, and will continue to get better by leaps and bounds. But as a warning, we think there is still way too much jaggedness for us to vouch for these for production use cases!
See these new capabilities as a continuation of what we’ve built over 2 years of stealth. They’re less ready for automation, but very fun to play with. They’re also an early glimpse into what we’re focused on making reliable enough to meet TypeSafe standards.
Composable Images
Not only are we enabling multimodality for future Jev models, we’re enabling it for the current Jev that you all know and love. Surprise: the Jev you all know and love (jev-1.13.0) was multimodal all along!
Image support is fully composable via a find-and-replace in assets. You can put them anywhere that our JSON interface supports: in the state, instructions, or even criteria! Play around with it, push the boundaries of technology, and let us know where Jev can improve.
As a warning, all models (Jev included) perform worse on multimodality over pure text. Breaking down questions into the simplest possible decompositions helps a lot.

有名企業や一流開発者のノウハウをそのまま持ち込める、Claude Codeスキル11選
こんにちは。くるしばです。
エラー監視サービスのSentry社が自社の開発チームで使っているコードレビューの基準を、明日から自分のプロジェクトにそのまま適用できるとしたら、ちょっと試してみたくならないでしょうか。
Claude Codeの「スキル」という仕組みを使うと、これが簡単に実現できます。決まった手順やルールをフォルダ/ファイルにまとめておくと、必要な場面でClaude Codeが自動的に読み込んでくれる、というものです。
面白いのは、そのファイルがGitHubで大量に公開されていることかなと思います。
こうしたものが、そのままみなさんのClaudeに読み込ませられる形で置いてあります。
これは、オープンソースのコードとよく似ているなと感じています。
世界中の優秀なエンジニアが自分のノウハウをスキルとして公開し、それを色んな人が実際に使ってフィードバックを返し、少しずつ改善されていく。ライブラリをインストールして使うのと同じ感覚で、こうしてスキル化された開発ナレッジを、自分の環境にそのまま持ち込めるわけです。
スキルの仕組み自体は2025年の10月に発表されたもので、同じ年の12月にはAIの種類を問わず使える共通仕様として公開されているので、特に目新しいものではありません。
ただ、この間に公開された数が増えすぎて、今はGitHubを覗いてもどれを入れればいいのか判断がつかない、というのが正直なところではないでしょうか。
そこで今回は、僕のほうで普段使っていておすすめのものを11個に絞ってまとめました。
選ぶときに基準にしたのは、他のスキルやClaude Code本体の機能では代わりがきかないところがあるかどうかです。それぞれのスキルについても、そのスキルにしかできないことを中心に紹介していきます。
1. Sentry社の実運用から生まれたフレームワーク特化のレビュー観点を持ち込める「getsentry/skills」
エラー監視サービスのSentry社が、自社の開発チームで実際に使っているスキルを公式に公開しているスキル集です。
個人開発をしていると、自分の書いたコードにセキュリティ上の穴やパフォーマンスの問題がないか、なかなか自分だけでは気づけないのではないでしょうか。
このスキル集ならではなのは、特定のフレームワークに踏み込んだレビュー観点を持っていることです。django-access-reviewはDjangoにおけるIDOR（本来アクセスできないはずのデータが権限の設定ミスで見えてしまう脆弱性）に、django-perf-reviewはN+1問題（データを1件ずつ取りに行くせいで、データベースへの問い合わせが大量に発生する問題）に絞ってチェックしてくれます。
Djangoで大規模なサービスを運用しているSentry社が、実際のレビューで見ているポイントがもとになっています。そのため、「この書き方だと他のユーザーのデータが見えてしまう」といった、画面上は普通に動いているので気づきにくい問題を拾ってくれるのが心強いところです。
ほかにも、ブランチの差分からロジックエラーや脆弱性を探すfind-bugs、Gitのコミットメッセージを一貫した形式で書くcommit、CIが通ってレビューの指摘が片付くまで修正を繰り返すiterate-prなども入っています。
だし、django系のスキルは名前の通りDjangoを前提にした内容なので、他のフレームワークではそのままでは使えません。
スキルの中身をOpusなどに任意のプログラミング言語で動くようにカスタマイズしてもらうなどするといいかなと思います。
2. 業界別の配色・スタイルのデータから、AIっぽくないUIの土台を決める「ui-ux-pro-max-skill」
デザイナーがいない状態でAIにUIを作らせると、どこかで見たようなテンプレート感のある配色になりがちですが、それを避けるための業界別スタイル・カラーパレット集です。
このスキルの特徴は、AIのセンスに任せるのではなく、スキル自体がデザインのデータベースを持っていることです。「フィンテックのダッシュボード」「医療系のLP」のように作るものを伝えると、業界ごとのルールに沿ってスタイル・配色・フォントの組み合わせを探し、その業界で避けるべきデザインまで含めて提案してくれます。
決まった内容はデザインシステムのファイルとしてプロジェクト内に書き出せるので、ページを追加するたびに配色がぶれる、ということも起きにくくなります。
無料版だけでも下記のようなボリュームがあります。
WCAG AA（アクセシビリティの達成基準の一つ）に準拠したコントラスト比の担保や、キーボード操作への配慮も自動で組み込まれます。
ただし、ロゴやオリジナルのビジュアル素材の生成までは無料版の範囲外で、そこは有料のプレミアム版が必要になります。
3. 「書く前に確かめる」行動規律をAIに常に守らせる「andrej-karpathy-skills」
AI研究者のAndrej Karpathy氏がLLM（大規模言語モデル）のコーディングにありがちな欠陥について指摘した内容をもとにまとめたものです。
指示が曖昧なまま実装を丸投げすると、AIが勝手な前提でコードを書き始めてしまい、後からやり直すことになった経験がある方は多いかなと思います。
このスキルの特徴は、コードを書き始める前の振る舞いを変えることにあります。書き終わったコードを後から整理するのではなく、そもそも推測で実装したり、頼んでいない箇所まで書き換えたりしないよう、次の4つの原則を最初から守らせます。
中身はCLAUDE.mdに書くルールが中心で、Cursor向けのルールファイルも同梱されています。Claude CodeとCursorを行き来していても、同じ規律でAIに作業させられるのは地味に便利なところです。
ただし、こうしたルールに従う分、タイポの修正のようなごく単純な作業でも確認のやり取りが増え、体感の速度は落ちたり、トークンの消費量は増えます。
大きめの変更や修正をする際に、明示的に使うようにするといいでしょう。
4. Chromeチーム発の基準で表示速度やアクセシビリティを実測・採点する「web-quality-skills」
GoogleのChromeチームに所属するAddy Osmani氏が公開している、Webサイトの表示速度やアクセシビリティをチェックするスキルです。
サービスを公開した後、モバイルでの表示が遅くて検索順位が上がらないけれど、何が原因か自分では特定できない、ということはよくあるのではないでしょうか。
このスキルが見るのは、「ちゃんと動くか」ではなく「速いか・誰にとっても使いやすいか」です。Performance・Accessibility・SEO・Best Practicesの4軸について、LCPやCLSといったCore Web Vitals（Googleが定めるサイトの表示品質の指標）を基準に採点してくれます。
しかも、コードを眺めて推測するだけではありません。ブラウザを操作できる環境があればLighthouse（Googleのサイト品質の計測ツール）で実際に計測し、「計測で確認できた問題」と「コードから推測される問題」を分けて報告してくれます。
目の不自由な人や色の見分けがつきにくい人にとって使いにくいなど、アクセシビリティ観点で問題のある箇所も見つけてくれます。たとえば、入力欄に「名前」「メールアドレス」といった説明が付いていない、背景と文字の色が近すぎて読みにくい、といった問題です。見つけるだけでなく、どう直せばいいかのコードまで提案してくれます。
5. トークンとコンテキストの消費を抑えて長い作業を持たせる「caveman」
Julius Brussee氏が公開している、AIの応答から挨拶や前置き、言い換えの繰り返しを削り、結論だけを短く返させることで、トークン（AIとのやり取りに使われる処理単位で、量に応じて費用がかかります）の消費を抑えるためのスキルです。AIの返答だけでなく、CLAUDE.mdのようにAIへ読み込ませるファイルを圧縮することもできます。
Claude Codeで長めの作業をしていると、途中でコンテキスト（AIが一度に覚えておける会話の量）がいっぱいになって会話が自動で圧縮されたり、利用上限に早く達してしまったりすることはないでしょうか。
その原因の一部は、AI自身の丁寧すぎる応答です。「確認しました。それでは〜について説明します」のような前置きや、同じ内容の言い換えも、すべてトークンとしてコンテキストに積み上がっていきます。
cavemanを入れると、この部分がばっさり削られます。ultraレベルにすると、たとえば「New object ref each render. Wrap in useMemo.」のように、結論と直す場所だけが1行で返ってくるようになります。
ここまでは「AIが返す文章」を短くする使い方ですが、cavemanにはもう1つ、「AIに読み込ませるファイル」のほうを短くする使い方があります。それが/caveman-compressです。
CLAUDE.mdのようなルールファイルは、会話を始めるたびに毎回Claudeに読み込まれます。つまり、ここに書いた文章が長いほど、何も作業していないうちからコンテキストを消費していることになります。
/caveman-compressにこうしたファイルを渡すと、ルールの中身はそのままに、文章だけを約46%圧縮した版に書き換えてくれます。一度圧縮しておけば、以降はセッションを始めるたびにその分のコンテキストが空いた状態でスタートできるので、応答を短くするモードと組み合わせると、入力と出力の両側から消費を抑えられます。
なお、/caveman-commitを使えば、コミットメッセージも50文字以内の簡潔な形で書いてくれます。
僕はエラーの原因だけをさっと知りたいときや、長時間の作業でコンテキストを温存したいときにultraを使い、設計をじっくり相談したいときは通常モードに戻す、という切り替え方をしています。
ただし、説明が削られる分、AIがなぜその修正を選んだのかといった背景は読み取りにくくなります。理解しながら進めたい場面では通常モードに戻し、手を動かす場面ではトークンを節約するためにcavemanを使う、という割り切りで使うとよいかなと思います。
6. 設計判断を記録に残しながら要件定義からレビューまで進める「mattpocock/skills」
TypeScript界隈で知られるMatt Pocock氏が公開している、要件定義・実装・テスト・レビューまでをカバーするスキル集です。
「なんとなくこんな機能が欲しい」という曖昧なアイデアのまま実装を進めてしまい、途中でAIが会話の文脈を見失って挙動が崩れる、というのはAIとの開発でよくある失敗パターンです。
このスキル集ならではなのは、設計時にドキュメントを作り、それを軸に設計からタスク分割、レビューまで一気通貫で進められることです。
まず/grill-with-docsを使うと、AIが設計上のトレードオフを質問してきて、決まったことをADR（設計の意思決定を記録したドキュメント）や用語をまとめたファイルに書き込んでくれます。
そこで固まった仕様は/to-ticketsで小さな作業単位に分割され、/code-reviewではその仕様に照らしてレビューが行われます。
このレビューは、「リポジトリの規約を守っているか」と「元の仕様どおりに実装されているか」を別々のサブエージェント（特定の作業だけを任せる子エージェント）が並行してチェックする仕組みです。バグがないかだけでなく、頼んだものが作られているかまで見てくれます。

PS5LMは脱獄したPS5のCPUでLLMを動作。現状の対応モデルは1.6GBまで
PS5LMは、PCで広く使われるLLM実行ソフトllama.cppを脱獄したPS5へ移植したもので、PS5のGPUで27BのQwen 3.8を1秒15トークン以上で動かすことを目標にしていました。派生版のPS5LM Plusは、この27Bを1秒あたり約20トークンで動かし、目標を上回ったとのことです。
この速さを出せたのは、PS5LM Plusをホーム画面から起動するアプリとして動かし、脱獄後に読み込んで動かすプログラム（ペイロード）では使えないGPUと約12GBのメモリを使えるようにしたためです。GPUは有志がPS5向けに移植したVulkanドライバーを使ってllama.cppを動かしており、メモリは約12GBのうち11.44GBをまとめてGPU用に確保しています。
Qwen 3.8は最も小さいモデルでも27Bあり、4bitに圧縮しても約15GBと、この11.44GBに収まらないため、2bitに圧縮した6.8〜9.2GBのデータで動かしています。そのため、長い回答でも速さはほとんど落ちず、7,775トークンを出し続けても1秒19.7トークンを保ったと報告されています。
また、モデルが小さければさらに速く、3BのLlama 3.2では1秒124トークンに達したとのことで実用にも耐えうる性能とのことです。なお、このPS5LM Plusはインストール用のファイルも配布されており、Redditなどでは実際に動作させた報告が相次いで投稿されています。

How to be more ambitious: A tutorial for humans with models
I work on Claude. It's an interesting experience: Every day I learn about yet another feat accomplished with or by Claude that I hadn't considered, didn't think possible, or simply lacked the curiosity and time to try. This month, it may have helped discover a new planet, I've seen the first AI music video that I really like, and we are discussing a new era of math.
Model capabilities don't grow uniformly. Models are, as Terence Tao puts it, "astounding in some directions, while inadequate in others". Some people manage to pilot the astounding capabilities and seem to be flying - it's addicting to watch people reach incredible heights with the products I've built. Many others are still struggling to get their new wings to work, wondering what they're good for beyond asking "What is the capital of France" or "Can you make this email sound less angry".
I frequently proclaim (together with other people working on AI) that we ought to be more ambitious when using it. It's become a rallying cry. Whenever we see something impressive, we repost and write "we're not ambitious enough". I understand how tricky it is to follow that advice, so here's a tutorial on being more ambitious.
I think of ambition in four types: Speed, Altitude, Depth, and Range.
- Speed: The same work in less time, the bread and butter for AI's economic value: If you need some code written, I'll do it faster with Claude. Well established and requires little creativity in how you approach AI, so I'll skip this one.
- Altitude: Going up in abstraction and considering the outcome rather than the individual task.
- Depth: Considering a task the way a field-leading expert would. Rather than operating at the task's layer, we go one level deeper and touch the underlying data, tools, and problems.
- Range: Drawing on multiple fields rather than just the one the task might need at the surface, using knowledge, tools, and techniques you normally wouldn't.
I primarily use Claude (duh) but my advice is not model-specific.
Altitude
We often flippantly call this "letting the model operate at a higher abstraction". When you give the model a task, it's executing your best guess at how to get the outcome you want. To be more ambitious in altitude, ask yourself - what do you want to happen next? What's the goal beyond the goal? At the beginning of last year, I still asked Claude to fix individual crashes for me. Eventually I asked Claude to simply keep our apps crash-free.
Let's consider an everyday (dare I say mundane?) office task. You're at Acme Inc, an imagined company, where you need to put together a deck for the quarterly business review (QBR). 株式会社ビットキーの高橋秀一郎（しゅういちろ）です。
20年ほどSIerでの実装から要件定義、役割としてはプロジェクトマネージャや組織の長を経験したのち、2024年にビットキーへ入社しました。現在は社内のエンジニアリングマネージャー（EM）を支援する立場から、組織開発や技術広報に携わっています。
チームの中にいるのではなく、外から見守る「支援者」として複数のチームに関わる役割です。複数チームのスクラムマスターというのが一番分かりやすいかもしれません。
この記事では、スクラムのイベントをきちんと回しているはずなのに、なぜ「雑談」が必要なのかについて書いていきます。かつて雑談に懐疑的だった私が、考えを変えるまでの話です。
スクラムのイベントがあるから「雑談は不要」と思っていた
アジャイル開発、特にスクラムを採用している現場には、対話のための枠組みがすでに用意されています。デイリースクラム、スプリントレトロスペクティブ、スプリントレビュー。チームの声を拾う仕掛けは、フレームワークの中に組み込まれています。それゆえ、わざわざ雑談の時間を設ける必要はないと私は考えていました。
前職でも「雑談したい人がオンラインで集まる」くらいの取り組みはありましたが、これは私が何かしたわけではなく自然発生的に行われていたもので、「話すのが好きな人が多いチームなんだろう」くらいに考えていました。
ところが、ビットキーに入社して実際に支援することになったチームと接して驚きました。このチームには金曜ランチなど「雑談会」といった意図的に雑談の時間を設ける文化が根付いていたのです。
私が支援することになった開発チームは、東京と福岡に分かれたハイブリッドワークの環境で働いていました。非同期と同期のコミュニケーションが入り混じるチームが、自分たちの意思で「定期雑談会」を続けていました。
会の成り立ちをチームのメンバーに聞いてみると、ハイブリッドワークで自然な立ち話が減ったことへの危機感がきっかけだったといいます。
オフィスで隣の席にいれば何気なく交わせていた会話が、リモートでは意図的に場をつくらないと生まれない。だから自分たちで「雑談の時間」を設けることにした。そしてその場から実際にチームの改善が生まれた経験を重ねるうちに、「この時間には意味がある」という実感がチームの中に根付いていったのです。
「わざわざ枠を確保して、そこまでやるのか」「業務に直接関係ない話に時間を使って、本当に意味があるのだろうか？」
そう思いながらも、チームがこれまで積み上げてきた経緯には敬意を持ちたかった。支援者として外からチームに関わる以上、既存の取り組みをいきなり否定するのは違う。だからまずは、自分も参加し続けることにしました。
参加するうちに、少しずつ見えてきたものがありました。何気ない会話の中に、チームが抱えている課題の兆しが混じっている。スクラムイベント、特にレトロスペクティブでは議題に上がらなかった小さな違和感が、雑談の場ではぽろっと言葉になるのです。
雑談が「センサー」となり、改善につながった例
まず、実際のエピソードから見ていきましょう。雑談がチームの課題を検知する「センサー」として働き、改善行動につながった事例を2つ紹介します。
【事例1】リモートだと発言しづらい
ある日の雑談で、こんな声が上がりました。
「会議でさ、リモートだとなかなか発言できなくてさ……」
ハイブリッドワーク環境では、オフィスにいるメンバー同士の会話が自然と盛り上がり、リモート参加のメンバーは会話に入るタイミングを掴みにくい。これは多くのハイブリッドチームが抱える構造的な問題です。普段から感じていた小さな困りごとが、雑談の場でこぼれた瞬間でした。
その声をきっかけに、「発言したいときはツールの挙手ボタンを使おう。押した人に発言権を渡そう」というルールがその場で決まりました。挙手ボタンはツールにもともとある機能でしたが、誰も使っていませんでした。雑談の場で出てきたからこそ、みんなが聞いていて、「やってみようか」がすぐに言えたのです。
面白いことに、このルールは徐々に社内の他のチームにも波及していきました。「小さな困りごと × すぐ試せる改善」。雑談が拾った声は、チームの枠を超えて広がっていったのです。
▼改善の詳細はこちら zenn.dev
【事例2】ファシリテーション、難しいよね
別の雑談の場では、こんなつぶやきがありました。
「最近、会議のファシリテーションがうまくできている気がしなくて……」
個人の悩みが、すっと漏れた瞬間でした。ファシリテーションの悩みは多くの人が抱えているものですが、チーム全体の改善を話し合うレトロスペクティブの場で、「ファシリテーションがうまくいっていない」と個人の悩みや課題を切り出すのはなかなか想像ができません。ファシリテーションというものの抽象度が高く、改善すべき課題として提示するには、まだ言葉が固まっていなかったのだと思います。
するとその場で、他のメンバーからも共感の声が上がりました。「分かる、私も悩んでる」「じゃあ、みんなで一回勉強しない？」という流れになりました。
個人の悩みが、チーム全体の学びへと変わった瞬間でした。誰かに指摘されたわけでもなく、チームが自発的に動いて見つけた学びですが、これは雑談という場だからこそ生まれた動きだと私は感じました。
事例1・事例2のどちらのエピソードにも共通しているのは、ふりかえりや1on1では出てこなかったであろう声が、雑談のゆるさの中で自然と表に出てきたということです。そしてその声が、チーム自身の手で改善へとつながっていった。
スクラムの文脈で言えば、これはスクラムの柱である検査と適応そのものです。ただし、スプリントレトロスペクティブのように構造化された場ではなく、雑談というゆるい場から生まれた検査と適応。雑談はこのサイクルを、思いがけない場所から回す仕組みだったのです。
なぜ1on1やスクラムのイベントでは拾えない声があるのか
スクラムのイベントや1on1では出てこなかった声が、なぜ雑談の場では自然と表に出てくるのか。チームにおける3つのコミュニケーションの場を並べてみると、その理由が見えてきます。
1on1は、1対1だからこそ話せる内容を共有する場です。
個人のキャリアや目の前のタスクだけでなく、「あの進め方には少し違和感がある」「実はこの仕事に不安がある」といった、チームの前では言いにくい本音が出てきます。視野は個人にフォーカスされ、「今困っていること」が話題の中心になります。
事例2の「ファシリテーションの悩み」も、1on1で出ていれば「個人のスキルの課題」としてマネージャーとの間で完結してしまい、チーム全体の学びには発展しなかったはずです。
スクラムのイベントはどうでしょうか。
例えば、デイリースクラムは、今日のタスクや阻害要因を短時間で同期する場です。 タイムボックスが限られているため、業務の進捗確認が中心となり、まだ言葉になっていない違和感を共有する余裕はありません。
また、レトロスペクティブは、テーマを絞り、構造化されたフォーマットのもとでチームの課題解決を図る場です。 KPT（Keep/Problem/Tryの略）やタイムラインなど、型があるからこそ振り返りが進みます。一方で、型があるがゆえに言葉にしやすいことが優先的に出てくるという性質も持っています。改善モードのスイッチが入った状態では、「なんとなく気になっている」程度の曖昧な感覚は、つい飲み込んでしまいがちで、明確に言葉にできるものが課題として摘出されます。
では雑談はどうでしょうか。
雑談には特定のテーマも構造もありません。議題もゴールも設定されていない。そのゆるさが、1on1やスクラムイベントでは拾いきれない、言語化される前の微細な違和感を包括的に拾うことを可能にします。
「そういえば最近ちょっと気になってたんだけど……」。そんな一言が出てくるのは、リラックスした空気の中だからです。構造がないことは弱さではなく、構造がないからこそ拾える声がある。それが雑談の固有の価値です。
扱う話題をベン図にすると、このようになると私は考えています。
1on1やスクラムイベントの話題と重なる領域、例えば「言語化しきれていない不安」や「ちょっとした違和感」がより自然に出てきやすいのが、雑談という場なのです。
雑談の雰囲気を守るために大事にしている4つのこと
雑談には大掛かりな仕掛けは要りません。ただし、場の雰囲気を守るための心がけはあった方が良いです。
私たちの経験から、ポイントを4つ共有します。
【ポイント1】機械的な雑談にしない
組織のトップダウンで「雑談チャンネル」を作っても、上長の投稿にスタンプを押すだけの一方通行になり、形骸化してしまうことがあります。
私自身、過去にそうした経験をしました。業務の進捗確認の延長になってしまう場も同様です。「雑談」という名前がついていても、実質的には報告会になっている。それでは本音は出てきません。
雑談は成果や答えを求めるものではありません。双方向に、気楽に話すこと自体に意味があります。
「この雑談で何か成果を出さなければ」と考えた瞬間、それはもう雑談ではなくなってしまいます。これは、私自身も大きな気づきでした。
盛り上がる日もあれば、静かな日もある。それでいいのです。
【ポイント2】「話題ボックス」できっかけをつくる
とはいえ、「何でも話していいよ」と言われると、逆に何を話せばいいか分からなくなります。これは多くの人が経験する感覚ではないでしょうか。
私たちのチームでは、事前に話したいネタを投稿しておく「話題ボックス」という仕組みを取り入れています。
仕事に関する話題から「2026年ベストバイ」のような趣味の話まで、幅広く受け付けています。思いついたネタをすぐ投稿できるようにして、定期雑談会の日までに話したい内容を忘れないようにする仕組みです。
お堅い日もあれば、気楽な日もある。そのメリハリが、雑談を持続可能なものにしているのだと思います。
ポイントは、話題を「強制」ではなく「きっかけ」として使うことです。話題ボックスに投稿されたネタはあくまで会話の入口であって、そこから脱線してもいい。むしろ脱線の中にこそ、思いがけない気づきが潜んでいることもあります。
【ポイント3】無理に改善プロセスを回さない
私たちはAI議事録で雑談の様子も記録していますが、雑談の改善のためには使用しません。どちらかというと、何を話したか思い出す程度です。
雑談に対して過度な改善を求めない「ゆるさ」が、息苦しさを防いでいます。
つい適応のために検査をしたくなりますが、雑談はそうした最適化の対象にしない方が良いです。全てを管理しようとしない姿勢が、雑談という場を守っているのだと思います。
【ポイント4】環境ごとにアプローチを変える
雑談のやり方は、チームの働き方によって変わります。
対面が中心のチームなら、立ち話や移動時間をそのまま活用すれば良いです。廊下での何気ない会話や、ランチに向かう途中のやりとりが、すでに雑談として機能しています。
リモートが中心のチームでは、放っておくと雑談が消えてしまいます。だからこそ、あえて場所を用意することが大切です。カレンダーに入れて、定期的に顔を合わせる時間をつくる。「わざわざ時間を設ける」ことに違和感があるかもしれませんが、リモート環境では意図しなければ生まれない会話があります。
ハイブリッド環境では、対面とリモートの間に生まれる温度差を埋める工夫が必要です。先ほどの事例1で触れたように、挙手ボタンやチャットを使って「発言のしやすさの差」を埋めるといったルールが有効です。
このように環境が違えば、雑談のかたちも変わります。大事なのは、自分たちのチームに合ったやり方を見つけることです。

- SSRF対策：外部URLの内容を取得するAPIでは、アクセス先を制限し、リダイレクト後の宛先も検証する。

Googleは13日、Google PlayやGeminiで今後利用可能になる予定の新機能について告知した。開発者アカウント不要の自作アプリ作成/共有機能や、AIによるゲームアプリの検索/比較機能を提供する。
自作アプリ作成機能では、Google AI Studioで作成したAndroidアプリを、Google Play経由で自分の端末上で利用可能となる。アプリは非公開で、公開ストアのカタログとは切り離される。通常のGoogleアカウントがあれば利用可能で、米国を含む一部の地域で18歳以上のユーザーを対象に順次展開予定。今後数カ月以内には、友人や家族間でのアプリ共有にも対応予定としている。一般向けに公開する場合は、開発者アカウントへの移行が必要となり、ほかの開発者と同じ審査や品質基準が適用される。
また、車載デバイス組み込みのGoogle built-inではインターフェイスのデザインを刷新。アプリへのより直感的なアクセスが可能になるという。
Google Playのゲームアプリ関連アップデートとしては、ユーザーの好みに合ったゲームを簡単に探せる「Game Finder」が利用可能になる。20億人以上のユーザーがこれまで遊んだゲームやプレイスタイルをもとに、好みのゲームを検索できる。ゲームのジャンルやシステムを指定した検索結果の絞り込み、ユーザーレビューの要約やトレンドの参照などが可能。当面は米国のみでの提供だが、近日中にそのほかの地域で提供を始める予定としている。
このほか特定のゲームアプリにおいて2～5人の少人数で短期間のお題に挑戦する「Sprints」、30秒程度のプレイバック録画やアプリについての質問など投稿が行なえるコミュニティ機能「Sidekick」、設定した年齢層に合致したアプリのみを表示するペアレンタルコントロール機能の強化などを予告した。
Geminiにおいては、Google Play上にあるゲームアプリの特徴やユーザーの感想を並べて比較できる「Ask Play」と、会話から直接ゲームを探せる「Play in Gemini」を提供予定としている。

OpenCode 2.0
OpenCode 2.0 is a major overhaul. It draws on millions of daily users' experience to deliver a system that can flex to everything an agent needs to be. There are quite a lot of new features, performance improvements, and bug fixes but here are some of the more impactful user-facing changes.
The Service
From the beginning OpenCode adopted a client/server model. However, this was not something it took advantage of by default and was mostly used by power users.
In 2.0 this server now automatically runs as a single background process on your machine. When you open up a TUI, the web interface or the desktop app they're all talking to the same central process.
If you're using the programmatic client @opencode/client to make your own scripts, they will autodiscover the local service and just work. This is particularly useful for scheduled tasks. You can also call it via CLI by using opencode api commands.
You can expose it to other hosts and run /pair or opencode pair to connect it to other applications. We have native apps in the works that take advantage of this flow.
The API
The old API grew haphazardly as we and the world collectively learned what agents are and should be. It was bad.
We started from scratch and examined all the weird use cases across the millions of users who use OpenCode every day. It now supports nearly anything you need to be able to do.
OpenCode is also aware of its own API and will call it to do useful things like moving the current session into a git worktree when starting new work.
We've also shipped a new client package @opencode/client that contains clients for vanilla JavaScript as well as Effect.
Code Mode
The models love to write code and OpenCode 2.0 takes advantage of that more than any other coding agent. We've built a minimal JavaScript interpreter in the @opencode/codemode package.
This package ingests MCP servers or OpenAPI endpoints, converting them into functions that the agent can call in a script. It can run these scripts natively without the complexity of Node.js VMs or embedding complicated solutions like QuickJS.
This lets your agent write scripts that can do things like call a tool, map over the results and call another tool. Single round trip instead of calling them one at a time.
All MCP servers in 2.0 are opted into codemode by default. This means you can add a thousand of them with minimal context bloat and your agent will discover and compose them to get things done.
Background Tasks
The latest batch of models are incredibly good at orchestration and it is important for harnesses to let them express the full extent of that capability.
First, we've added background subagents. This allows the primary agent to kick off some work to another one while it continues.
This happens automatically but you can also trigger it manually - even with a different model. It lets you do things like “spawn a background fable subagent to review this code” while you keep prompting.
Second, we've added background shell commands. The shell tool can be invoked asynchronously so long-running work does not have to block the primary agent. It'll be notified when things are complete.
If any foreground shell command or subagent takes longer than you expect, you can hit a hotkey to move them to the background so you can keep prompting.
Plugins
Although OpenCode 1.0 had a plugin system, it never got the attention it needed. To correct that, we forced ourselves to implement nearly every OpenCode 2.0 feature as an internal plugin and there are now 80+ of them. This guarantees that the Plugin API stays well maintained.
We've also promoted TUI plugins from experimental to stable. Since it is all powered by OpenTUI, you can build nearly anything. Here is an example of something useless.
We also spent quite a lot of time ensuring everything in OpenCode 2.0 can be hot-reloaded. So it can write a plugin for itself mid-session and use it right away - we covered the design of this in a previous blogpost.
You can ask OpenCode to build whatever plugin you want and it knows how to. But if you do want to read the docs, they are available here.
The SDK
OpenCode can also now be used as a library with the @opencode/sdk package. This is the exact same code that powers our CLI.
This means you can strip it down and make your own flavor of OpenCode that runs on a server or in specialized environments like Durable Objects. And then you can connect to it from any OpenCode client since it speaks the standard OpenCode server protocol.
It also has an optional Effect-based API.
This one is still in development as things are shifting but you can already use it.
Upgrading
To upgrade the CLI, make sure you're on the latest 1.x release, then run opencode upgrade --major.
To upgrade your desktop app, download the latest here.

I think the level of imitation goes well beyond having similar insights1. The fact that Sapling was only credited for “hard-won lessons”, and that Mononoke was not mentioned at all, borders on plagiarism. エラー監視サービスのSentry社が自社の開発チームで使っているコードレビューの基準を、明日から自分のプロジェクトにそのまま適用できるとしたら、ちょっと試してみたくならないでしょうか。

こうしたものが、そのままみなさんのClaudeに読み込ませられる形で置いてあります。
これは、オープンソースのコードとよく似ているなと感じています。

ただ、この間に公開された数が増えすぎて、今はGitHubを覗いてもどれを入れればいいのか判断がつかない、というのが正直なところではないでしょうか。

1. Sentry社の実運用から生まれたフレームワーク特化のレビュー観点を持ち込める「getsentry/skills」

Djangoで大規模なサービスを運用しているSentry社が、実際のレビューで見ているポイントがもとになっています。そのため、「この書き方だと他のユーザーのデータが見えてしまう」といった、画面上は普通に動いているので気づきにくい問題を拾ってくれるのが心強いところです。

だし、django系のスキルは名前の通りDjangoを前提にした内容なので、他のフレームワークではそのままでは使えません。

AI研究者のAndrej Karpathy氏がLLM（大規模言語モデル）のコーディングにありがちな欠陥について指摘した内容をもとにまとめたものです。

このスキルの特徴は、コードを書き始める前の振る舞いを変えることにあります。書き終わったコードを後から整理するのではなく、そもそも推測で実装したり、頼んでいない箇所まで書き換えたりしないよう、次の4つの原則を最初から守らせます。

5. トークンとコンテキストの消費を抑えて長い作業を持たせる「caveman」
Julius Brussee氏が公開している、AIの応答から挨拶や前置き、言い換えの繰り返しを削り、結論だけを短く返させることで、トークン（AIとのやり取りに使われる処理単位で、量に応じて費用がかかります）の消費を抑えるためのスキルです。AIの返答だけでなく、CLAUDE.mdのようにAIへ読み込ませるファイルを圧縮することもできます。
Claude Codeで長めの作業をしていると、途中でコンテキスト（AIが一度に覚えておける会話の量）がいっぱいになって会話が自動で圧縮されたり、利用上限に早く達してしまったりすることはないでしょうか。
その原因の一部は、AI自身の丁寧すぎる応答です。「確認しました。それでは〜について説明します」のような前置きや、同じ内容の言い換えも、すべてトークンとしてコンテキストに積み上がっていきます。
cavemanを入れると、この部分がばっさり削られます。ultraレベルにすると、たとえば「New object ref each render. Wrap in useMemo.」のように、結論と直す場所だけが1行で返ってくるようになります。
ここまでは「AIが返す文章」を短くする使い方ですが、cavemanにはもう1つ、「AIに読み込ませるファイル」のほうを短くする使い方があります。それが/caveman-compressです。
CLAUDE.mdのようなルールファイルは、会話を始めるたびに毎回Claudeに読み込まれます。つまり、ここに書いた文章が長いほど、何も作業していないうちからコンテキストを消費していることになります。
/caveman-compressにこうしたファイルを渡すと、ルールの中身はそのままに、文章だけを約46%圧縮した版に書き換えてくれます。一度圧縮しておけば、以降はセッションを始めるたびにその分のコンテキストが空いた状態でスタートできるので、応答を短くするモードと組み合わせると、入力と出力の両側から消費を抑えられます。
なお、/caveman-commitを使えば、コミットメッセージも50文字以内の簡潔な形で書いてくれます。
僕はエラーの原因だけをさっと知りたいときや、長時間の作業でコンテキストを温存したいときにultraを使い、設計をじっくり相談したいときは通常モードに戻す、という切り替え方をしています。
ただし、説明が削られる分、AIがなぜその修正を選んだのかといった背景は読み取りにくくなります。理解しながら進めたい場面では通常モードに戻し、手を動かす場面ではトークンを節約するためにcavemanを使う、という割り切りで使うとよいかなと思います。

I think of ambition in four types: Speed, Altitude, Depth, and Range.
- Speed: The same work in less time, the bread and butter for AI's economic value: If you need some code written, I'll do it faster with Claude. Well established and requires little creativity in how you approach AI, so I'll skip this one.
- Altitude: Going up in abstraction and considering the outcome rather than the individual task.
- Depth: Considering a task the way a field-leading expert would. Rather than operating at the task's layer, we go one level deeper and touch the underlying data, tools, and problems.
- Range: Drawing on multiple fields rather than just the one the task might need at the surface, using knowledge, tools, and techniques you normally wouldn't.
I primarily use Claude (duh) but my advice is not model-specific.
Altitude
We often flippantly call this "letting the model operate at a higher abstraction". When you give the model a task, it's executing your best guess at how to get the outcome you want. To be more ambitious in altitude, ask yourself - what do you want to happen next? What's the goal beyond the goal? At the beginning of last year, I still asked Claude to fix individual crashes for me. Eventually I asked Claude to simply keep our apps crash-free.
Let's consider an everyday (dare I say mundane?) office task. You're at Acme Inc, an imagined company, where you need to put together a deck for the quarterly business review (QBR). Given a bunch of data, Claude will happily make you some slides. Maybe you even have a template and it just needs to fill it in. That's hardly comparable to finding a new planet, so let's look at some concrete steps to make our approach more ambitious. We'll start basic and get a little bit more ambitious with each step:
- As input, most reviews want to know what changed this quarter, why, and what should be done about it. Resist the urge to just update whatever numbers are in the template - give the model too as much data as you can get your hands on so it can understand your business: "Tell me what changed this quarter, why, and what we should do about it."
- Meetings (the good kind, anyway) ideally end with some decisions. Ask Claude: "Work out which three decisions are most urgent in the face of everything you've learned, and start working on potential directions with for/against arguments."
- QBRs are from a time when good reviews required humans to carefully sift through data, figure out what the data means, and if the business should adjust. Ask Claude: "The review exists so leadership catches problems early and moves money and people to the right places. Design a better way to do that than a quarterly deck, show from our own history that it would have caught things sooner, and run it beside the current one for a quarter."
The altitude approach works best if you really are after some ultimate outcome; it works less well for creative endeavors. A good tell-tale sign that ambition in altitude is a good idea is if you're going to have meetings to discuss whatever you're working on. There are currently limits ("Claude, go make money" doesn't seem to work for most businesses by itself in 2026), but I generally see that models seem to be able to operate at higher levels of abstraction the more capable they become.

もう一つの止めどきは飽和。 違う探し方の2本（英語と日本語など）を並べ、挙がった資料の7割以上がすでに地図にあれば止める。 独立した2回の探索の重なりから全体の数を見積もる考え方（Kastner 2007）を借りた。 7割は試しながら決めた目安で、根拠はまだ弱い。
AI の検索は、方向がいくつもありうる段階で1つを選び、その後の検索が同じ道を強めて失敗する（Zhou ら 2026 HypoSearch）。 迷ったら別の仮説で検索役を2本並べ、戻ってから比べる。
塗り方や MIX のように論文がほとんど無い分野の知恵は、個人のブログや動画にある。 論文の参考文献をたどるのと同じ動きで、記事の中のリンクや「〇〇さんの記事を参考に」をたどる。 落とした原文には種類の印を付け、どれを信じるかは読む人に任せる。

- 〔観察〕他人の作品ややり方を見て、特徴を書き出したもの
- 〔まとめ〕他人の知見を集めた・言い換えた記事
- 〔公式〕道具や製品を作った側の文書

JPCERT/CCは、2026年10月8日に、国内の複数の組織で相次いで公表された不正アクセスによる個人情報などの漏えい被害に関する注意喚起を公開しました。 JPCERT/CCでは、複数の組織と連携し、攻撃に使用された可能性のあるインフラの調査を進めています。その過程で、攻撃者がAIを利用して、既知の脆弱性のスキャンやAPI経由での攻撃などを実施していたことを確認しました。 こうした攻撃元サーバーはインターネット上で複数確認されており、日本以外の地域向けのWebサービスに対しても攻撃を行っていました。

攻撃元サーバーの調査 その1

This survey finds significant, double-digit declines in Americans’ participation in key social activities from 1995 to 2026.

For my piece on Catholic miracle apologetics, I read (correction: skimmed) a 25,000-word post by rationalist blogger Scott Alexander. Rationalist bloggers do not generally appear to have this impulse. Eliezer Yudkowsky's "sequences" are over one million words long. These bloggers tend to spend their time on precisely the wrong things, i.e. adding layers of detail and nuance rather than interrogating the one or two assumptions they make at the start or broadening their philosophical background beyond the collection of texts popular within their subculture.
It seems to me that, in this community, verbosity is a substitute for thoroughness: surely, if someone wrote a lot about something, and is able to demonstrate that by producing a large volume of text, they must have something worthwhile to say about it? Consider when blogger Gwern explained that nicotine, actually, is not addictive, and is good for you, as long as you don't smoke it, over the course of 9,000 words, with over 100 references. In any case, what is missing from this endlessly verbose rationalist writing style is wisdom. Wisdom involves discretion: an intuition for what ideas are and are not worth seriously pursuing, and the ability to determine what does and does not need to be said. This community, broadly speaking, does not seem to value wisdom as a trait at all; the idea that something may be true, valuable, or good merely because it is common sense or inherited tradition is anathema to them. 株式会社ビットキーの高橋秀一郎（しゅういちろ）です。
20年ほどSIerでの実装から要件定義、役割としてはプロジェクトマネージャや組織の長を経験したのち、2024年にビットキーへ入社しました。現在は社内のエンジニアリングマネージャー（EM）を支援する立場から、組織開発や技術広報に携わっています。
チームの中にいるのではなく、外から見守る「支援者」として複数のチームに関わる役割です。複数チームのスクラムマスターというのが一番分かりやすいかもしれません。
この記事では、スクラムのイベントをきちんと回しているはずなのに、なぜ「雑談」が必要なのかについて書いていきます。かつて雑談に懐疑的だった私が、考えを変えるまでの話です。
スクラムのイベントがあるから「雑談は不要」と思っていた
アジャイル開発、特にスクラムを採用している現場には、対話のための枠組みがすでに用意されています。デイリースクラム、スプリントレトロスペクティブ、スプリントレビュー。チームの声を拾う仕掛けは、フレームワークの中に組み込まれています。それゆえ、わざわざ雑談の時間を設ける必要はないと私は考えていました。
前職でも「雑談したい人がオンラインで集まる」くらいの取り組みはありましたが、これは私が何かしたわけではなく自然発生的に行われていたもので、「話すのが好きな人が多いチームなんだろう」くらいに考えていました。
ところが、ビットキーに入社して実際に支援することになったチームと接して驚きました。このチームには金曜ランチなど「雑談会」といった意図的に雑談の時間を設ける文化が根付いていたのです。
私が支援することになった開発チームは、東京と福岡に分かれたハイブリッドワークの環境で働いていました。非同期と同期のコミュニケーションが入り混じるチームが、自分たちの意思で「定期雑談会」を続けていました。
会の成り立ちをチームのメンバーに聞いてみると、ハイブリッドワークで自然な立ち話が減ったことへの危機感がきっかけだったといいます。
オフィスで隣の席にいれば何気なく交わせていた会話が、リモートでは意図的に場をつくらないと生まれない。だから自分たちで「雑談の時間」を設けることにした。そしてその場から実際にチームの改善が生まれた経験を重ねるうちに、「この時間には意味がある」という実感がチームの中に根付いていったのです。
「わざわざ枠を確保して、そこまでやるのか」「業務に直接関係ない話に時間を使って、本当に意味があるのだろうか？」
そう思いながらも、チームがこれまで積み上げてきた経緯には敬意を持ちたかった。支援者として外からチームに関わる以上、既存の取り組みをいきなり否定するのは違う。だからまずは、自分も参加し続けることにしました。

【事例1】リモートだと発言しづらい

別の雑談の場では、こんなつぶやきがありました。
「最近、会議のファシリテーションがうまくできている気がしなくて……」
個人の悩みが、すっと漏れた瞬間でした。ファシリテーションの悩みは多くの人が抱えているものですが、チーム全体の改善を話し合うレトロスペクティブの場で、「ファシリテーションがうまくいっていない」と個人の悩みや課題を切り出すのはなかなか想像ができません。ファシリテーションというものの抽象度が高く、改善すべき課題として提示するには、まだ言葉が固まっていなかったのだと思います。
するとその場で、他のメンバーからも共感の声が上がりました。「分かる、私も悩んでる」「じゃあ、みんなで一回勉強しない？」という流れになりました。
個人の悩みが、チーム全体の学びへと変わった瞬間でした。誰かに指摘されたわけでもなく、チームが自発的に動いて見つけた学びですが、これは雑談という場だからこそ生まれた動きだと私は感じました。
事例1・事例2のどちらのエピソードにも共通しているのは、ふりかえりや1on1では出てこなかったであろう声が、雑談のゆるさの中で自然と表に出てきたということです。そしてその声が、チーム自身の手で改善へとつながっていった。
スクラムの文脈で言えば、これはスクラムの柱である検査と適応そのものです。ただし、スプリントレトロスペクティブのように構造化された場ではなく、雑談というゆるい場から生まれた検査と適応。雑談はこのサイクルを、思いがけない場所から回す仕組みだったのです。
なぜ1on1やスクラムのイベントでは拾えない声があるのか
スクラムのイベントや1on1では出てこなかった声が、なぜ雑談の場では自然と表に出てくるのか。チームにおける3つのコミュニケーションの場を並べてみると、その理由が見えてきます。
1on1は、1対1だからこそ話せる内容を共有する場です。
個人のキャリアや目の前のタスクだけでなく、「あの進め方には少し違和感がある」「実はこの仕事に不安がある」といった、チームの前では言いにくい本音が出てきます。視野は個人にフォーカスされ、「今困っていること」が話題の中心になります。
事例2の「ファシリテーションの悩み」も、1on1で出ていれば「個人のスキルの課題」としてマネージャーとの間で完結してしまい、チーム全体の学びには発展しなかったはずです。
スクラムのイベントはどうでしょうか。
例えば、デイリースクラムは、今日のタスクや阻害要因を短時間で同期する場です。 タイムボックスが限られているため、業務の進捗確認が中心となり、まだ言葉になっていない違和感を共有する余裕はありません。
また、レトロスペクティブは、テーマを絞り、構造化されたフォーマットのもとでチームの課題解決を図る場です。 KPT（Keep/Problem/Tryの略）やタイムラインなど、型があるからこそ振り返りが進みます。一方で、型があるがゆえに言葉にしやすいことが優先的に出てくるという性質も持っています。改善モードのスイッチが入った状態では、「なんとなく気になっている」程度の曖昧な感覚は、つい飲み込んでしまいがちで、明確に言葉にできるものが課題として摘出されます。
では雑談はどうでしょうか。
雑談には特定のテーマも構造もありません。議題もゴールも設定されていない。そのゆるさが、1on1やスクラムイベントでは拾いきれない、言語化される前の微細な違和感を包括的に拾うことを可能にします。
「そういえば最近ちょっと気になってたんだけど……」。そんな一言が出てくるのは、リラックスした空気の中だからです。構造がないことは弱さではなく、構造がないからこそ拾える声がある。それが雑談の固有の価値です。
扱う話題をベン図にすると、このようになると私は考えています。
1on1やスクラムイベントの話題と重なる領域、例えば「言語化しきれていない不安」や「ちょっとした違和感」がより自然に出てきやすいのが、雑談という場なのです。
雑談の雰囲気を守るために大事にしている4つのこと
雑談には大掛かりな仕掛けは要りません。ただし、場の雰囲気を守るための心がけはあった方が良いです。
私たちの経験から、ポイントを4つ共有します。
【ポイント1】機械的な雑談にしない
組織のトップダウンで「雑談チャンネル」を作っても、上長の投稿にスタンプを押すだけの一方通行になり、形骸化してしまうことがあります。
私自身、過去にそうした経験をしました。業務の進捗確認の延長になってしまう場も同様です。「雑談」という名前がついていても、実質的には報告会になっている。それでは本音は出てきません。
雑談は成果や答えを求めるものではありません。双方向に、気楽に話すこと自体に意味があります。
「この雑談で何か成果を出さなければ」と考えた瞬間、それはもう雑談ではなくなってしまいます。これは、私自身も大きな気づきでした。
盛り上がる日もあれば、静かな日もある。それでいいのです。
【ポイント2】「話題ボックス」できっかけをつくる
とはいえ、「何でも話していいよ」と言われると、逆に何を話せばいいか分からなくなります。これは多くの人が経験する感覚ではないでしょうか。
私たちのチームでは、事前に話したいネタを投稿しておく「話題ボックス」という仕組みを取り入れています。
仕事に関する話題から「2026年ベストバイ」のような趣味の話まで、幅広く受け付けています。思いついたネタをすぐ投稿できるようにして、定期雑談会の日までに話したい内容を忘れないようにする仕組みです。
お堅い日もあれば、気楽な日もある。そのメリハリが、雑談を持続可能なものにしているのだと思います。
ポイントは、話題を「強制」ではなく「きっかけ」として使うことです。話題ボックスに投稿されたネタはあくまで会話の入口であって、そこから脱線してもいい。むしろ脱線の中にこそ、思いがけない気づきが潜んでいることもあります。
【ポイント3】無理に改善プロセスを回さない
私たちはAI議事録で雑談の様子も記録していますが、雑談の改善のためには使用しません。どちらかというと、何を話したか思い出す程度です。
雑談に対して過度な改善を求めない「ゆるさ」が、息苦しさを防いでいます。
つい適応のために検査をしたくなりますが、雑談はそうした最適化の対象にしない方が良いです。全てを管理しようとしない姿勢が、雑談という場を守っているのだと思います。
【ポイント4】環境ごとにアプローチを変える
雑談のやり方は、チームの働き方によって変わります。
対面が中心のチームなら、立ち話や移動時間をそのまま活用すれば良いです。廊下での何気ない会話や、ランチに向かう途中のやりとりが、すでに雑談として機能しています。
リモートが中心のチームでは、放っておくと雑談が消えてしまいます。だからこそ、あえて場所を用意することが大切です。カレンダーに入れて、定期的に顔を合わせる時間をつくる。「わざわざ時間を設ける」ことに違和感があるかもしれませんが、リモート環境では意図しなければ生まれない会話があります。
ハイブリッド環境では、対面とリモートの間に生まれる温度差を埋める工夫が必要です。先ほどの事例1で触れたように、挙手ボタンやチャットを使って「発言のしやすさの差」を埋めるといったルールが有効です。
このように環境が違えば、雑談のかたちも変わります。大事なのは、自分たちのチームに合ったやり方を見つけることです。

京都大学白眉センター／人と社会の未来研究院 高木佐保 特定助教、麻布大学獣医学部 菊水健史 教授らの研究グループは、ネコ29匹とその飼い主19名を対象に、このうち尿試料が得られたネコ24匹について、1か月間にわたって両者の尿中のオキシトシンとコルチゾールを測定し、飼い主の気分や、家庭内でのネコと飼い主の距離との関係を調べました。その結果、飼い主のオキシトシン濃度が高いほどネコのオキシトシン濃度も高い、飼い主のコルチゾールが高いほどネコのオキシトシンが低いという関連が見られた一方で、コルチゾール同士には明確な関連は見られませんでした。また、オキシトシン濃度の高いネコの飼い主ほどネガティブな気分が低く、ネコと近くで過ごしている飼い主ほど活気が高いこともわかりました。ネコとヒトの生理的な結びつきは、コルチゾールよりもオキシトシンを中心としている可能性が示されました。

JPMorgan, Morgan Stanley, SMBC and MUFG are quietly shopping pieces of the AI debt pile they helped build, a sign the lenders closest to the money have started hedging their own bet.
Six months ago, banks were racing each other to underwrite data center loans tied to Oracle, Meta and the rest of the AI buildout. Now some of the same banks are trying to get that debt off their books. JPMorgan, Morgan Stanley, SMBC and MUFG have been exploring significant risk transfers, according to a report from the Financial Times. These are deals that let a bank keep a loan on paper while shifting its riskiest slice to outside investors. The banks are doing this because they are bumping up against internal limits on how much AI-linked exposure any one lender can hold.
One case shows how stuck this has gotten. A group of banks including JPMorgan and MUFG has spent more than six months trying to distribute $38 billion in construction debt tied to a Texas and Wisconsin data center project leased to Oracle, Bloomberg has reported. Some lenders are now willing to sell pieces of it to non-bank buyers at a discount, just to move it. Six months is a long time to sit on debt nobody underwrote to hold forever.
Matthew Moniot, co-head of credit risk sharing at Man Group, told the Financial Times the deal sizes involved are "out of scale to anything we've thought about, ever." That is not a hedge-fund manager talking down a trade he wants no part of. It is someone whose job is pricing exactly this kind of risk, saying the numbers no longer fit any model he has used before.
Oracle is the clearest tell. Its five-year credit default swaps, the cost of insuring against the company defaulting, climbed to around 151 basis points in early October, levels last seen in 2009, according to market data cited by Bloomberg. S&P had already cut Oracle's credit rating to BBB-, a single notch above junk, back in July. The company is reportedly targeting more than $40 billion in additional debt and equity this fiscal year. That is on top of the $18 billion in bonds it sold in a single day last September, and the money is needed to keep funding its Texas, Wisconsin and New Mexico sites.
Oracle sued Wisconsin's Public Service Commission over a rule that could force it to post more than $7 billion in collateral for its Port Washington data center campus. Order books for their offerings have shrunk from roughly five times the amount on sale back in February to under two times by July, Bloomberg has reported. That is the difference between a bond that sells itself and one a bank has to work to place.

The Federal Reserve's own September meeting minutes named AI-related corporate borrowing as a contributor to that move. Capital Economics argues the bigger driver is plain old inflation and government deficits, not tech company bond sales. Whoever is right about the cause, the effect is the same for anyone trying to finance a data center right now: the risk-free rate they are borrowing against just got a lot more expensive.
Frankly, the mechanics here matter more than the headline number. Banks do not sell down debt they are confident in. Spreading $120 billion of AI infrastructure spending across special purpose vehicles was supposed to make that risk easier to swallow. Capital is rotating toward data centers leased to investment-grade hyperscalers like Microsoft and Google, and away from weaker credits, Bloomberg has reported. 『RPGツクール』『ウディタ』『Bakin』『SRPG Studio』開発者が集結した濃厚対談。「ゲームを作るのは難しい」、その思い込みを壊したい
国内のノーコードゲーム制作ツールの開発者の方々にお声がけをし、座談会を企画。その内容をお届けする。
誰しも一度は「自分だけのゲームを作ってみたい」と思い立ったことがあるのではないだろうか。そんな野望の実現を助け、日本のインディゲーム・フリーゲーム文化を支え続けてきたのが、国産のノーコードゲーム制作ツールの存在だ。
弊誌AUTOMATONでは、国内のノーコードゲーム制作ツールの開発者の方々にお声がけをし、座談会を企画した。国内には多くのツールが存在するが、ゲーム開発者をそっと支えるツールの、さらにその中の人同士が話をする場面というのはなかなかない。海外製のさまざまなツールも存在するなかで、彼らはいまどういう思いで開発をしているのだろうか。
今回お招きしたのは、『RPGツクール』シリーズに長年携わり、最新作『RPGツクールU2U』ではプロデューサーを務める一之瀬裕之氏。『RPGツクール』を祖とし、独自のフルコマンド方式を展開した『WOLF RPGエディター（ウディタ）』の開発者であるSmokingWOLF氏。3D表現と2D表現を融合させた『RPG Developer Bakin』チームリーダーの長井伸樹氏。SRPG特化の制作ツール『SRPG Studio』のサファイアソフト氏だ。座談会では、よもやま話を多数うかがうことができた。本稿ではその様子をお届けする。
――自己紹介と、ご自身が関わっているツールのご紹介をお願いいたします。
長井伸樹氏（以下、長井氏）：
長井と申します。『RPG Developer Bakin』のチームリーダーとして、制作から宣伝やサポートメールまで、いろいろなことを担当しています。元々はゲーム業界でゲームを作っていたのですが、前の会社をやめてプラプラしていたところ、社長と飲みに行ったのがきっかけでスマイルブームに入りました。うちの会社では社是として「未来のクリエイターを作る」というものを掲げていまして、任天堂さんのコンシューマーハードで”SmileBASIC”という弊社独自に開発した言語でゲームプログラミングが楽しめる 『プチコン』シリーズだとか、『RPG Developer Bakin』の前身にあたる『SMILE GAME BUILDER』という3DRPG制作ツールみたいなものを作ってたんです。そこから、あれよあれよと『RPG Developer Bakin』のチームリーダーになりました。
『RPG Developer Bakin』は2Dから2.5D、3Dまで、様々なグラフィック表現を使ったゲームを作れるゲーム制作ツールです。2022年の10月に早期アクセスをスタートして、昨年の8月に正式版をリリースしました。自社製のコアエンジンを使っていまして、ポストエフェクトをかけて綺麗なグラフィックを作ったり、ゲームUIを作れるレイアウトツールを備えていたり、皆さんがゲーム作りを楽しんでいただけるようなツールを目指して作っています。制作ツールを作られているみなさんとの座談会、私が以前からやりたい！といろいろなところでお話ししていたので実現していただけてとてもうれしいです。AUTOMATONさん、ありがとうございます！
――長井さんのご提案がきっかけで座談会を実現できました。皆さまにもお集まりいただき感謝いたします。それでは次は一之瀬さん、お願いします。
一之瀬裕之氏（以下、一之瀬氏）：
Gotcha Gotcha Gamesの一之瀬です。『RPGツクールMV』から開発チームに参加して、最新作の『RPGツクールU2U』ではプロデューサーをしております。本日はよろしくお願いします。
『RPGツクール』シリーズは1992年に立ち上がったプロダクトで、最初の発売からはもう30年以上が経っています。『RPGツクールU2U』は、PC系の『RPGツクール』では初となる3Dを取り入れた制作ツールに挑戦しています。なかなか思い切ったことを考えたなと思っていて、いろんな方にご期待もいただいています。スクウェア・エニックスさんの「HD-2D」という素晴らしい作品群の影響はもちろんあるのですが、ツクール独自のUIやアセットの仕組みを生かしつつ、3Dの世界を広げたいというシンプルな発想のもとに鋭意開発中です。本日はよろしくお願いします。
SmokingWOLF氏：
SmokingWOLFと申します。『WOLF RPG Editor（ウディタ）』を開発しておりまして、自分でもそれで『片道勇者』などのゲームを作っております。自分はもともと熱心なツクラー（『RPGツクール』のユーザー）で、『ウディタ』は『RPGツクール』にかなり影響を受けているのですが、今回は一之瀬さんがいらっしゃっているのでとても緊張しております……（笑）
『ウディタ』は自作のデータベースと完全なコマンド方式でゲームを作れるフリーソフトです。プログラミングができない人からも「ゲームが作れた」というコメントをかなりいただいておりまして、理想はこのままフルコマンド式で突っ走るという考えでいます。とはいえ、スクリプトの導入に反抗したいわけではなくて、できればスクリプトなしでもやりたいことを実現したいという考えですね。
長井伸樹氏（以下、長井氏）：
うちのプログラマーは『ウディタ』を見てよく驚いてます。「あれを全部フルコマンドでやってるからすごい、とんでもない労力だ」って言ってますよ。メンテナンスとかも含めて大変なはずですよって。
SmokingWOLF氏：
実は、フルコマンドだからこそ、逆に移植性は上がるかなと思っているんですよね。特定の言語に依存するよりも、コマンド式の方がむしろ後から最適化しやすいんじゃないかなと。起動時にちょっとコンパイルチックなことをして処理を高速化できるようにするとか、色々アイデアを取り入れています。そうすることで、後から始める人でも高速化にあやかれる、という感じです。
――SmokingWOLFさんはもともと『RPGツクール』でゲームを制作されてましたよね。自分でツールを自作するようになった理由はあったのでしょうか。
SmokingWOLF氏：
単純にもっと自分にとって使いやすいツールが欲しかったんですよね。『RPGツクール』は当時のノーコードコンストラクションツールとして最強を更新し続けていたと思うんですけど、RPG以外のものを作ろうとすると大変なんですよ。だから、どんなゲームでもゼロから作れる自由なデータベースと完全なコマンド方式を備えた、自分向けのゲームエディターを作りたいなと思って……。結果として、うちでやってる「ウディコン」というゲームコンテストの作品は半分くらいがRPG以外なので、目的はだいぶ達成できたと思います。
あとは、自分が作ったゲームを長く維持できるようにしたかったからという理由もあります。自作のエンジンを作っておけば、遠い未来で普及しているOSがWindowsじゃなくなっても、画像処理とか音声処理といったWindows専用処理の部分を差し替えれば他の環境でも動かせるようになるんです。『ウディタ』の開発を開始した2006年ぐらいはUnityもあまり一般的じゃなかったので、自分のゲームを長く残したいなら自作エンジンが最も安全という判断になったんです。
サファイアソフト氏：
サファイアソフトです。『SRPG Studio』は、シミュレーションRPG制作ツールです。2Dマップとターン制の概念があり、自分のターンと相手のターンを順番に動かしていく……そういった流れのゲームを作るのに特化していて、プログラミングやイラストの知識がない方でもSRPGを作れるようにしたツールとなります。
長井氏：
僕が見ている界隈の特徴なのかもしれないんですが、SRPG自体が結構盛り上がってきているのは感じていますね。今年リリースされた『SRPG Studio』製のタイトルだと、『ユートラント戦記』とか『ユレイシア英雄戦記』とか。
SmokingWOLF氏：
フリーゲーム界隈でも『SRPG Studio』製のゲームはかなり流れてくるのを見るので、すごい影響力をお持ちだなと思います。
サファイアソフト氏：
本当ですか。フリーゲームといったら御三方のツールのシェアが大きいかなと思ってたので、なんだか恐縮です。
――イチから作るとなると大変なジャンルかと思いますので、専門のエディターがあるとありがたいですよね。制作のきっかけなどはあったのでしょうか。
サファイアソフト氏：
私が開発を始める前の日本のIT業界では、スタートアップとかシリコンバレーとかGAFAMとか、そういった言葉が流行していた時代だったんです。そのなかで「なんで日本の会社はGAFAMのような大企業に並んでいないんだ」とよく言われてた時代で、世間的にも「自分たちで何か大きなWebサービスを作ってみようぜ」という空気が強かったんですね。私も結構それに共感していたところがあって、じゃあ自分に何ができるのかと考えた時に、自分はWeb系はほとんど知識がなかったんですが、Windowsのプログラミングの知識は多少あったんです。それで世界と戦うまではいかずとも自分で何かできないかなと思ったときに、たどり着いたのがSRPGを作るツールだったんです。
――そこでSRPGというジャンルを選んだ理由はなにかあるのでしょうか。
サファイアソフト氏：
『RPGツクール』をはじめとしたシェアの大きいツールが存在するのは知っていたんですが、SRPGに特化したツールが当時は目立つものがなかったので、これなら使ってもらえるだろうなというか、自分の中でニーズは割とあるんじゃないかなと思っていたので選んだという感じですね。
SmokingWOLF氏：
市場の空いているところを見て作られているのが、すごくプロフェッショナルな発想だと感じます。 昔、Windows 95の時代に『シミュレーションRPGツクール95』というのがあったんですが、SRPG専門の制作ツールってあれ以来ほとんど出ていなかったんですよね。なのでその枠を埋められたのは素晴らしい着眼点だなと。
サファイアソフト氏：
恐縮ですね。需要の枠を埋められていたら嬉しいです。
――『RPGツクール』への参画は『RPGツクールMV』からとのことでしたが、一之瀬さんご自身としても、開発歴はかなり長いですよね。
一之瀬氏：
僕が一番最初に関わったタイトルは、1995年にエニックスから発売された『ミスティックアーク』ですね。同時期に『RPGツクール SUPER DANTE』が発売されて衝撃を受けたことを覚えています。それからずっとゲーム開発に関わっていたのですが、スパイクに在籍していた頃にエンターブレインさんとのつながりから『RPGツクール』の担当を探しているという話をされたのが、シリーズに関わるきっかけでした。

尾島さんはうちのプログラマーも「めちゃくちゃすごい方」と尊敬してますね。
SmokingWOLF氏：
私も偉大な人だと思っております。発想が2世代ぐらい早いんですよね。
