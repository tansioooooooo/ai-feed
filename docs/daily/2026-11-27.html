I’ve been self-hosting things for many years. There were times when I was quite enthusiastic about it, constantly trying out new software and tinkering with my infrastructure. But at some point, that enthusiasm faded a bit.

Over the last few months, however, I’ve found myself getting increasingly excited about self-hosting again. And, somewhat ironically, AI is a big reason for that.
Less friction
Most of my infrastructure configuration lives in Git repositories, mainly in the form of Docker Compose files, scripts, and other configuration files. This makes it possible to use AI coding agents to work on my infrastructure in much the same way as they would work on any other software project.
Whenever I want to try a new service, adjust an existing configuration, or automate something, I can now do so with considerably less effort.
In the past, I would sometimes put off certain changes simply because I didn’t feel like spending an evening reading changelogs and documentation or troubleshooting issues. It’s not that I couldn’t have done these things before. But often, the amount of effort required just wasn’t worth it to me.
Now, even relatively spontaneous ideas often end up becoming reality.
Trying things I always found interesting
There are also technologies that I’ve always found interesting but never felt knowledgeable enough about to really make use of them.

AI makes experimenting with unfamiliar technologies much more approachable. I don’t necessarily need to understand every little detail before I can get started. I can learn about things along the way, ask questions, and gradually improve my configurations.
Automating almost everything
Something I’ve also finally managed to do is automate most of the build, update, and deployment processes for my infrastructure.
A lot of the work involved in self-hosting isn’t particularly exciting. Keeping track of new releases, updating container image tags, building images, and deploying configuration changes are all things that need to be done regularly.
I still remember what updating a service used to look like: bumping the version and adjusting the Docker Compose file on my laptop, pushing the changes to the Git remote, SSHing into the server, pulling the changes, and finally deploying them. Minipg: 単一の実行ファイルで動くPostgreSQLMinipg: PostgreSQL as a Single Executable
11/26 03:00 · ▲ 289 · comments →
📄 本文を読む
minipg is PostgreSQL as one executable, ready to use, with no server to configure. A .pgdb directory is the database: its data, config, credentials, and Postgres version all live inside it, and minipg app.pgdb opens a psql shell on it. A server starts when a command needs one and stops on its own when it's idle.
minipg embeds Docker Hub's postgres:18-alpine image and runs it with h9, used as a Zig library. h9's Linux personality runs Alpine's own Postgres binaries directly on the host's hypervisor, with h9's Plan 9 kernel answering their system calls. There's no Linux kernel to boot, no VM image, and no Docker.
The demo downloads about 35 MB. It needs JavaScript Promise Integration, which Chrome and Edge have from version 137; other browsers are getting it. It can also be opened on its own page.
The demo runs minipg's Linux build, which runs inside the Postgres image itself. It starts Postgres as ordinary processes and serves on a unix socket, since a page has no TCP. New databases come from a template cluster made at build time, because initdb takes half a minute on v86.
minipg app.pgdb # psql shell (creates app.pgdb if missing)
minipg app.pgdb "select 1" # one statement
minipg url app.pgdb # postgres://postgres:...@127.0.0.1:54321/app
minipg serve app.pgdb # an explicit foreground server
minipg run app.pgdb -- npm start # your app, with DATABASE_URL set
minipg dump app.pgdb > dump.sql # and minipg restore app.pgdb dump.sql
A .pgdb holds minipg.toml (settings and the generated superuser password) and pgdata/, Postgres's data directory as plain files. A stopped one can be copied like any directory. New clusters use Postgres's builtin C.UTF-8 locale, which sorts the same on every platform.
In CI, the Linux binary is static and needs no privileges or devices: without /dev/kvm, h9 runs Postgres on its native backend. A test job can be as small as:
minipg init test.pgdb
minipg run test.pgdb -- go test ./...
The README lists every command, and the manual is the full guide.
Exactly one process runs Postgres for a .pgdb, enforced by a lock. It holds the server's h9 machine, whose Linux root is the unpacked image and whose writable working directory is the .pgdb. The image's docker-entrypoint.sh initializes the cluster on first start. Commands never host Postgres themselves. If no server is running, they start one in the background and use it. psql, pg_dump, and the other tools each run in their own short-lived h9 machine (about 90 ms to start) over the same root.
The source is on GitHub, under the MIT license. Building needs Zig 0.16, plus curl, jq, tar, and xz for the root:
git clone --recursive https://github.com/progrium/minipg
cd minipg
make build # pulls the root for this host's arch, builds ./minipg
make root ARCH=386
make web # this page's demo, in .zig-out/web
minipg is early, and h9's Linux personality is young. On h9's native backend, Postgres is about 2x slower than native for one client, and slower under load. Don't trust it with data you can't recreate yet.
Please report bugs and send questions through GitHub issues.

デジタル庁デザインシステムはプラットフォーム型であり、特定の組織のブランドやコミュニケーション方針を備えていません。そのため、使用するときは導入先のブランドやコミュニケーション方針（スタイルガイド）に合わせて、デザインシステムを定義し直す必要があります。
カラーや文字の大きさ、角の形状、余白などを導入先の方針に沿って定めると、UIコンポーネントの見た目が導入先のトーン＆マナーになります。このように導入先の方針で上書きしたデザインシステムを「ローカルデザインシステム」と呼びます。
上図のように、1つのデジタル庁デザインシステムから、各府省のブランドアセットに準じてローカルデザインシステムを作成し、導入先のサイトやサービスに適用します。
ローカルデザインシステムを作成する
ローカルデザインシステムを作成するには、デジタル庁デザインシステムを導入先に合わせて定義し直します。その作業の起点となるのが、デザイントークンの編集です。
デジタル庁デザインシステムでは、カラー、タイポグラフィ、余白、角の形状など、サイトやサービスの外観を定める視覚的な要素を「基本デザイン」としてまとめ、それらの値に名前を付けた「デザイントークン」として定義しています。
デジタル庁デザインシステムのデザインデータとコードスニペット（実装サンプルコード）には、初期値として、デジタル庁ウェブサイトをベースにしたデザイントークンが適用されています。
上図は、デジタル庁デザインシステムに初期値のデザイントークンが反映されている状態を示しています。この初期値は、コンポーネントの構造や状態の違いを具体的な形で示すためのものです。特定の外観を規定するものではなく、あくまで編集の起点という位置づけです。
ローカルデザインシステムを作成するときは、以下の項目を、必要に応じて導入先のデザイントークンに置き換える形で編集します。
- カラー：キーカラーの選択、ブランドカラーによる上書きなど
- タイポグラフィ：文字の大きさや行の高さの変更
- 余白：基準となる余白の単位と、その倍率によるルール
- 角の形状：コンポーネントごとの角丸の値
- ドロップシャドウとエレベーション（影などで表す、要素の重なりの高さ）：高さのレベルの種類と、その高低差
- リンクテキスト：リンクの色
- レイアウト：段組みと、ブレークポイント（画面幅に応じてレイアウトを切り替える境目）の数

ローカルデザインシステムでもアクセシビリティを確保する
デジタル庁デザインシステムは、アクセシビリティの確保を最優先に設計されたデザインシステムです。ローカルデザインシステムは、このアクセシビリティ確保の仕組みを理解したうえで、継承・維持するように作成しなければなりません。
基本デザインごとに、編集後も満たすことが必須の要件は次のとおりです。
- カラー：テキストと背景色のコントラスト比（明るさの比率）を4.5:1以上、枠線などテキスト以外の要素と背景色のコントラスト比を3:1以上にする。エラーや成功などの意味を表す色と、その意味の結びつきは変更しない
- タイポグラフィ：文字の大きさは16 CSS px以上を基準にする。読み物の本文の行の高さは、文字の大きさの1.5倍以上にする
- 余白：使用する余白の値に規則性を持たせる。ボタンなど操作できる要素のターゲットサイズ（押せる範囲の大きさ）を44×44 CSS px以上確保する
- ドロップシャドウとエレベーション：影の有無に関わらず要素の外周にボーダーを付けて3:1以上のコントラスト比を確保する
- リンクテキスト：色だけでなく、下線などの装飾と組み合わせる。青以外の色を使用する場合は、コントラストや色覚の多様性のほか、リンクであるとわかるように配慮する
- レイアウト：画面の幅に合わせて伸び縮みするリキッドレイアウトを採用する。見た目の配置と読み上げの順序をできるだけ一致させる
たとえば「ボタン」コンポーネントでは、キーカラー・角の形状・余白を変更できますが、いずれもアクセシビリティ要件を満たす範囲で調整しなければなりません。

SSH is a GUI framework
"One thing about which fish know exactly nothing is water." — Marshall McLuhan
SSH is a tool so ubiquitous that we've forgotten what it actually is: a multiplexed, encrypted byte stream accessible on a cross-platform rendering engine that ships on every laptop, server, and phone on earth. A number of terminal protocols have slowly added graphics, clipboard sharing (including images), notifications, mouse support, and more on top of SSH.
To see just how far you can push it, I've made a microVM with a desktop environment designed from the ground up to render natively over SSH. You can try it right now (no sign-up):
ssh zydra.sh
ssh -p 443 zydra.sh # if on an office network
ssh -t zydra.sh dino # SSH port of the Chromium T-Rex game, for fun. Terminal Protocols (and matching terminal support)
All terminal protocols work on data that can be passed through SSH, so typically, any terminal protocol will extend to SSH.
Perhaps the most ubiquitous new terminal protocol is the Kitty Graphics Protocol, which superseded the older Sixel and iTerm2 graphics protocols. It allows for compression, client-side graphical state (via VRAM), and even animations entirely on the terminal.
Graphics alone don't make a complete GUI, though. SSH has protocols that cover all other angles:
- Notifications: OSC 99 "Rich Notifications" allow image, text, and body. OSC 777 (our first fallback) allows only text and body, and OSC 9 (our last fallback) allows only a title.
We end up using a similar fallback for many things.
- Clipboard sharing: OSC 52 handles bidirectional clipboard sharing, and Kitty's OSC 5522 adds image and arbitrary MIME-type transfers on top of that.
- Mouse support: CSI ? 1000-1006 help track the mouse and give us its precise coordinates.
- Synchronized Output (Batched Rendering): CSI ? 2026 allows atomic rendering, preventing visual tearing and flickering.
- File upload (Kitty): The Kitty terminal uniquely supports a file upload feature, which zydra.sh uses to allow the upload of projects and related files to personal VMs.
SSH-native compositing: How I made it fast
A few tricks make compositing over SSH fast. Firstly, where possible, especially when streaming terminals, we simply stream them as text rather than unnecessarily streaming it via graphics. The compositor's UI framework itself cleverly overlays traditional text over carefully aligned graphics, saving bandwidth. In the case of zydra.sh, this allows us to efficiently stream the entire cloud computer's desktop UI over SSH.
Next, we optimize graphics by sending a sort of "grid" of pixels. Each cell has its own updates, where the previous frame is compared to the current frame to catch and send updates, avoiding having to constantly stream the full screen. Kitty also offers both RGB and RGBA, and so by removing transparency where it's not needed, we save another 25% in bandwidth. We also track ping and other factors to determine how well the client handles the stream: lowering the resolution in select cells, especially when scrolling, to relieve pressure. マキタ「ADP15」は、同社の 電動工具で用いられている専用バッテリに取り付け、スマホやノートPCの充電を可能にするアダプタだ 。USB Type-CとUSB Type-Aをそれぞれ1ポートずつ搭載しており、災害などの緊急時に、バッテリを有効活用できる一品だ。
USB PDによる最大100Wの充電に対応することから、ノートPCの充電にも余裕で対応できるこの製品。ポータブル電源やモバイルバッテリが使えない場合の電源確保に適している。実機を購入したので、使い方や性能についてチェックするとともに、用途についても考察していく。
電動工具のバッテリを用いてUSBでの充電が可能に
本製品は、同社の電動工具に使われるバッテリに取り付けて使うアダプタだ。バッテリと一体化させて使うことを前提としており、形状も完全な専用品となっている。同社の電動工具用バッテリのすべてに対応するわけではなく、一部製品に限定されるので注意が必要だ。詳しくは後述する。
USBポートは、 12W(5V/2.4A)までの出力に対応したUSB Type-Aポートと、最大105Wまで対応したUSB Type-Cポート、計2基が搭載されている 。105Wというのはあまり見ない値だが、PPSの値が5～21V/5Aであるためこのような表記になっているだけで、USB PDの規格上は最大100W(20V/5A)となる。いずれにしてもかなりパワフルで、ノートPCの充電にも余裕で対応できる。
今回は筆者の私物で、同社の電動工具に付属していた「18Vリチウムイオンバッテリ」(BL1830B、容量3,000mAh)との組み合わせで使用してみた。
装着方法は電動工具に取り付けるのと同様だ。レールに沿ってスライドさせると、カチリと音がしてロックされる。あとは本製品側に用意されたUSBポートにケーブルを差し込み、もう一端をデバイスにつなぎ、本体上部のボタンを押すことにより充電が開始される。
見た目こそやや特殊だが、使い方自体は一般的なモバイルバッテリと変わらない 。バッテリが着脱式になっているというだけの話だ。ちなみに残量表示は本製品側ではなく、バッテリ側にその機能があれば対応する。今回のBL1830Bでは4段階のゲージで確認できる。
最大105W、スマホはもちろんPCも余裕で充電可能
性能についてもう少し詳しく見ていこう。「USB Cable Checker3」のポートチェック機能を使って仕様を確認した。本体側面に記載されているのと同様、最大100W(20V/5A)までの対応に加えて、PPSで5～21V/5Aまで対応することが分かる。また別のケーブルチェッカーを見る限り、PPSに加えてAVS(Adjustable Voltage Supply、機器に応じて給電の電圧を調整する機能)にも対応しているようだ。なかなかの高機能である。
続いて実際にスマホおよびノートPCを充電し、出力および容量をチェックしてみた。まずスマホ(iPhone 17 Pro Max)については、 ピーク時でほぼ上限いっぱいとなる37W前後で充電が行なえていた 。なかなか優秀だ。
ノートPCはどうだろうか。今回はWindows PC(ThinkPad X1 Carbon Gen 9)で試してみた。このPCは最大65Wでの充電に対応するが、今回は ピーク時に60W前後で充電が行なえていたので、こちらもかなり優秀だ 。試用中に3Aを超えた形跡はなかったが、前述のポートチェックの結果からして、接続するデバイス次第で5Aで充電される場合もあるとみなして問題ないだろう。
ちなみに今回試用したバッテリ「BL1830B」は容量3,000mAhと控えめなため、前述のWindowsノートについては満充電に達する前、77%程度で充電が終了した。ただし、本製品に対応するバッテリには12,000mAhの大容量モデルもあるため、それらを使えば満充電も問題なく行なえる計算になる。このあたりは、手持ちのバッテリ次第ということになるだろう。
災害などの緊急時に最適。対応バッテリに注意
以上のように性能、使い勝手ともに問題のない本製品は、 普段使いよりも、災害など緊急時により適していると考えられる 。理由は大きく分けて2つある。
1つは、これらのバッテリを用いる電動工具が、災害時に使われるケースは極めて稀だと考えられることだ。出番のない電動工具のバッテリを、ポータブル電源やモバイルバッテリに代わって貴重な電力源として活用できるのであれば、それに越したことはない。
特に停電からの復旧の見通しが立たない状況下では、汎用性の高いポータブル電源やモバイルバッテリは、なるべく使わずに余力を残しておきたい。本製品があればこうした場合の先鋒として活用できるし、どちらも使える状況下であれば、スマホなどの充電は本製品が、それ以外の一般的な家電製品はポータブル電源が受け持つという、役割分担が成立しうる。
もう1つ、電動工具用のバッテリは交換用に複数を所有していることが多いため、1個あたりの容量はそれほど大きくなくても、複数個を交換しながら多くの製品を充電できる。さらにその性質上、充電が完了した状態でストックされている可能性が高いのも、充電できる見込みが立たない災害時には好都合だ。
一方で気を付けたいのは、本製品にはバッテリ自体を充電する機能がないことだ。つまり本製品を使って外部のデバイスを充電し、バッテリの残容量がゼロになってしまえば、バッテリを再充電するには元の電動工具側の充電器が必要となる。災害時であれば「それどころではない」可能性はあるが、充電器がない環境に持ち出す場合は注意したいところだ。
また本製品は「マキタ18V/14.4Vバッテリ」に対応する旨の記述があるが、実際には18V/14.4Vバッテリにも複数の形状があり、あらゆるモデルが対応するわけではない点には要注意だ。
たとえば筆者宅には今回試用したモデル以外に、電動ドリルやインパクトドライバーで使用する「BL1415G」なる14.4Vのバッテリがあるが、端子の形状が異なるので物理的に接続できない。 対応可否を確認するときは、電圧の表記だけで判断せず、型番ベースで確認することをおすすめする 。

技術スタックと選定の意図
今回は立ち上げ当初から、AIに実装を任せることを視野に入れて技術を選定しました。主な技術選定と、ふりかえって分かったことを整理します。
特に印象的だったのはNestJS + Clean Architectureです。Clean Architectureでは、業務処理（UseCase）とデータの読み書き（Repository）などを層に分けて実装します。「UseCaseはexecuteメソッドを1つだけ持つ」「Repositoryはインターフェースを介して注入する」といった層の規約が明確なので、AIに実装させても構造が崩れにくくなります。新しい機能を足すときも、既存のUseCaseやRepositoryを参照させるだけで同じパターンのコードが出てきます。
その反面、DI（依存性注入。クラスが使う部品を外から渡す仕組み）に起因する事故もありました。グローバルモジュール（アプリ全体から参照できる共通部品の置き場）に特定機能専用の実装を置いてしまい、バッチが起動しなくなったケースです。これは「動くが構造的に壊れている」変更で、差分だけを見ていると気づけません。再発防止として、モジュールの依存グラフを単体で組み立てられるかを検証するテストを追加しました。
幸い、ユーザーへの影響が出る前に気づけました。そのときは「よく気づけたな」という安堵と同時に、「AIを過信しすぎてはいけない」という戒めを強く感じたのを覚えています。

「AIに書かせる」だけでは品質は安定しません。今回のプロジェクトでは、品質を支える仕組みを整備しました。

ドキュメントを足場にしたAI実装
CLAUDE.mdに加えて、ARCHITECTURE・DATABASE・API_SPECといった設計ドキュメントを用意し、合計で約2,800行になりました。AIはこれらを読んでから実装に入るため、命名や層の分け方、エラーハンドリングの方針がぶれにくくなります。
実は、最初からこの量だったわけではありません。立ち上げ直後のドキュメントは今よりずっと大きく、主要4ファイルだけで3,323行ありました。当時私たちが使っていたモデルのコンテキストウィンドウ（AIが一度に扱える情報量）は20万トークンでした。そのため、AIがドキュメントを読むだけでコンテキストの60%ほどを使い切ってしまっていました。読んだ時点で余力がなく、何も作れないAIになってしまったのです。そこで3月に、ドキュメントの「ダイエット」を実施しました。コード例やディレクトリ構成など、コードを読めば分かる情報や重複を削り、957行まで約7割減らしています。4月にも別の設計ドキュメント7件を約46%圧縮しました。

AIに実装を依頼して、動くコードを書いてもらったとしても、そのコードが「わかった」とは限りません。理解を省略してしまうと、仕組みを説明することができなくなります。第5回となるこの記事では、実装が終わった後に、AIが書いたコードの仕組みを自分の言葉で説明できる状態にする方法を解説します。
「コードが動いた」で思考を止めない
AIにコードを書いてもらい、動作確認もできたので、「動くコード」は手に入りました。しかし、そのコードはまだ「動いただけのコード」であり、「わかるコード」とは限りません。
ここでいう「わかるコード」とは、自分がその機能の仕組みを説明できるコードのことです。具体的には、次の3つの観点について説明できる状態のコードを指します。
AIが書いたコードを「わかるコード」にするために必要な観点
- よくある失敗パターン
- 実装した機能にバグが見つかったが、処理の流れを理解しておらず、どこから調べればいいか見当がつかなかった
- コードレビューで「ここの処理はなぜ必要なの？」と聞かれ「AIが生成したコードなので…」としか答えられなかった
- 仕様変更の工数を聞かれたとき、どこをどれだけ変えればいいか見当もつかず、自分で実装したはずなのにコードを調べ直すことになった
これらは、「動いた」という結果だけで思考を止めてしまった典型的な例です。とりあえず動くだけのコードを積み上げ続けると、将来的に誰も変更できず、保守もできない「ブラックボックス」が生まれてしまいます。そうした「理解の負債」が蓄積すると、プロジェクト全体の生産性も下がっていきます。
ただし、常にすべてのコードに対して、自分の言葉で説明できるまで深掘りする必要はありません。納期が迫っているときや、緊急対応が必要なとき、あるいは一度だけ使うコードを書くときなどは、理解よりも動かすことを優先すべき場面もあります。
コードの理解が特に有効なのは、次のようなタイミングです。
- 「動いたけれど、なぜ動いているのかわからない」と感じたとき
- 実装が一段落して、コードレビューの前に振り返る時間があるとき
- 今後も修正やメンテナンスが発生するコードを書いたとき
重要なのは、AIが書いたコードを理解するプロセスを習慣化することです。
実装したコードを理解するための3つのステップ
動いたコードを自分の言葉で説明できるようにするために、次ページからの3つのステップで理解を深めていきます。

Ephyra is a new property-based testing library we are developing at Datadog Systems Research, designed from scratch for agentic property-based testing.
Briefly, Ephyra brings autoresearch style hill-climbing optimizations together with property-based testing; given a set of properties Ephyra first writes a simple valid test case generator, measures the code coverage, optimizes the generator to reach new regions of the code.
This process is similar to coverage-guided fuzzing (CGF) that favors inputs that increase the coverage of the testing space. However whereas CGF is deductive, mutating promising inputs; Ephyra is inductive, it rewrites the generator with the hypothesis of discovering promising inputs.
We have run Ephyra through popular targets for testing research, finding 70+ bugs in SQLite, 20 bugs in PostgreSQL, 25 bugs in Lean, several bugs in heavily fuzzing-guided developed systems such as FoundationDB and TigerBeetle. We present many more systems and bugs in the chart below.
The Ephyra library and Ephyra command line have their own respective documentation, mostly written in an information dense style targeting coding agents. Almost all of the code in this repository is experimental and subject to change, please let us know any issues you experience while using it.
Testing a project with an agent? Give your coding agent this prompt; it starts from STARTUP.md:
Let's test <my library> with ephyra
(https://github.com/datadog-labs/ephyra). Read its README and
STARTUP.md first, then autonomously start writing and optimizing
Ephyra tests until we find any bugs; validate, triage, and notify me.
[dev-dependencies]
ephyra = "0.0.1"
Write a property as a test:
use ephyra::prelude::*;
#[ephyra::test]
fn sorting_keeps_every_element(mut v: Vec<i32>) -> bool {
let mut expected = v.clone();
expected.sort();
v.sort();
v == expected
}
cargo test runs it. A failure prints the shrunk counterexample and an
EPHYRA_REPLAY=<seed>:<iteration> line that reruns exactly that case, and is
remembered in .ephyra/regressions/ so the next run tries it first. Settings
such as the number of tests (EPHYRA_TESTS), the seed (EPHYRA_SEED) or a
time budget (EPHYRA_BUDGET_MS) can be changed from the environment without
touching the code.
The ephyra command runs suites into one artifact directory, checks the
generators it finds in the source, and serves a local page for exploring the
results:
cargo install ephyra-cli
ephyra guide # how to write generators
ephyra test # run the suite; artifacts in .ephyra/
To see a failure report and the targeted search from a checkout:
cargo run -p ephyra --example bst -- --bug
cargo run -p ephyra --example sort_performance
Next: the library's README for generators, shrinkers and mutators, API.md for every generator, combinator and setting, the changelog for what changed in each release, and CONTRIBUTING.md to work on ephyra itself.

The name of the library is an homage to the most Sisyphean task in modern software development, testing; particularly random testing where we roll not one, but millions of rocks through a variety of software, and Ephyra is the home of all such efforts.

Title:Evolution Strategies at Scale: LLM Fine-Tuning Beyond Reinforcement Learning
View PDF HTML (experimental)
Abstract:Fine-tuning large language models (LLMs) for downstream tasks is an essential stage of modern AI deployment. Reinforcement learning (RL) has emerged as the dominant fine-tuning paradigm, underpinning many state-of-the-art LLMs. In contrast, evolution strategies (ES) has largely been overlooked due to the widespread belief that it does not scale to modern model sizes. This paper overturns this assumption by demonstrating the first successful application of ES to full-parameter fine-tuning of LLMs at the billion-parameter scale, without dimensionality reduction. ES can indeed search over extremely high-dimensional parameter spaces and outperform established RL implementations across multiple axes, including improved tolerance to long-horizon and delayed rewards, robustness across diverse base LLMs, reduced susceptibility to reward hacking, and improved training stability. These findings suggest that ES is not merely a viable alternative to RL, but a fundamentally different and powerful backpropagation-free post-training paradigm that opens a new direction for LLM fine-tuning beyond current RL-based approaches.

AI made self-hosting fun again
I’ve been self-hosting things for many years. There were times when I was quite enthusiastic about it, constantly trying out new software and tinkering with my infrastructure. But at some point, that enthusiasm faded a bit.
I never really stopped self-hosting, but I became less inclined to experiment with new things. Maintaining what I already had running was enough for me.
Over the last few months, however, I’ve found myself getting increasingly excited about self-hosting again. And, somewhat ironically, AI is a big reason for that.
Less friction
Most of my infrastructure configuration lives in Git repositories, mainly in the form of Docker Compose files, scripts, and other configuration files. This makes it possible to use AI coding agents to work on my infrastructure in much the same way as they would work on any other software project.
Whenever I want to try a new service, adjust an existing configuration, or automate something, I can now do so with considerably less effort.
In the past, I would sometimes put off certain changes simply because I didn’t feel like spending an evening reading changelogs and documentation or troubleshooting issues. It’s not that I couldn’t have done these things before. But often, the amount of effort required just wasn’t worth it to me.
Now, even relatively spontaneous ideas often end up becoming reality.
Trying things I always found interesting
There are also technologies that I’ve always found interesting but never felt knowledgeable enough about to really make use of them.
NixOS is a good example. I’ve always liked the idea of declaratively configuring an entire system; I even used it on my laptop during my Linux honeymoon phase. But getting everything configured the way I wanted was quite a hurdle. With the help of AI, I’m now making much more extensive use of NixOS on my home server.
For my VPS infrastructure, I’ve also started building my own Debian-based bootc image (after thinking about it for some time).
Having my entire operating system configuration defined in a Git repository and automatically building a bootable container image from it is something I find really cool. But it’s also something I probably wouldn’t have invested enough time in to get working on my own before. Even with the help of AI, it still took me half a day when I set it up a few months ago. Without AI, it would probably have taken me at least a week.
AI makes experimenting with unfamiliar technologies much more approachable. I don’t necessarily need to understand every little detail before I can get started. I can learn about things along the way, ask questions, and gradually improve my configurations.
Automating almost everything
Something I’ve also finally managed to do is automate most of the build, update, and deployment processes for my infrastructure.
A lot of the work involved in self-hosting isn’t particularly exciting. Keeping track of new releases, updating container image tags, building images, and deploying configuration changes are all things that need to be done regularly.
I still remember what updating a service used to look like: bumping the version and adjusting the Docker Compose file on my laptop, pushing the changes to the Git remote, SSHing into the server, pulling the changes, and finally deploying them. Now, a single Git push is enough. If a push is even necessary.
With Renovate, I no longer need to actively keep track of most software updates. It creates pull requests for me, and often, all I need to do is review and merge them. I can even do that on my phone while sitting on the sofa.
Pushing changes or merging a pull request triggers the corresponding GitHub Actions or Forgejo Actions workflows, which take care of building and deploying everything.

And the nice thing about automating these tasks is that the benefits extend well beyond the initial setup. I now have less tedious work to do every time I want to change something or update a service.

技術スタックと選定の意図
今回は立ち上げ当初から、AIに実装を任せることを視野に入れて技術を選定しました。主な技術選定と、ふりかえって分かったことを整理します。
特に印象的だったのはNestJS + Clean Architectureです。Clean Architectureでは、業務処理（UseCase）とデータの読み書き（Repository）などを層に分けて実装します。「UseCaseはexecuteメソッドを1つだけ持つ」「Repositoryはインターフェースを介して注入する」といった層の規約が明確なので、AIに実装させても構造が崩れにくくなります。新しい機能を足すときも、既存のUseCaseやRepositoryを参照させるだけで同じパターンのコードが出てきます。
その反面、DI（依存性注入。クラスが使う部品を外から渡す仕組み）に起因する事故もありました。グローバルモジュール（アプリ全体から参照できる共通部品の置き場）に特定機能専用の実装を置いてしまい、バッチが起動しなくなったケースです。これは「動くが構造的に壊れている」変更で、差分だけを見ていると気づけません。再発防止として、モジュールの依存グラフを単体で組み立てられるかを検証するテストを追加しました。
幸い、ユーザーへの影響が出る前に気づけました。そのときは「よく気づけたな」という安堵と同時に、「AIを過信しすぎてはいけない」という戒めを強く感じたのを覚えています。
フルAI開発を支えた仕組み
「AIに書かせる」だけでは品質は安定しません。今回のプロジェクトでは、品質を支える仕組みを整備しました。
全体像としては、ドキュメントを足場にAIが実装し、hookがセルフレビューの忘れを防ぎ、マージ後はdocs-botが設計判断をドキュメントに戻します。この循環によって、開発が進むほどAIの足場が厚くなる構造にしました。
なお、これらは最初からそろっていたわけではありません。失敗や手間に気づくたびに、少しずつ足していきました。ファイル編集時のhookやDevinのレビューは3月、PRテンプレートの検証hookは6月、docs-botは7月、セルフレビューを強制するhookは9月の導入です。
仕組みの前に、私が日々の使い方でこだわっていたことも書いておきます。1つは、いきなり実装させず、まずplan（実装方針）を出させることです。方針の段階でずれを直せば、手戻りは小さく済みます。もう1つは、何重にもセルフレビューさせて、できるだけ人間の手を煩わせないことです。人が見る前にAI自身に何度も粗を探させることで、人は判断が必要なところに集中できます。こうしたAIへの任せ方の考え方は、以前LTの内容をまとめた記事「AIをマイクロマネジメントしない勇気」でも紹介しています。以下で紹介する仕組みは、どれもこの2つを支えるためのものです。
ドキュメントを足場にしたAI実装
CLAUDE.mdに加えて、ARCHITECTURE・DATABASE・API_SPECといった設計ドキュメントを用意し、合計で約2,800行になりました。AIはこれらを読んでから実装に入るため、命名や層の分け方、エラーハンドリングの方針がぶれにくくなります。
実は、最初からこの量だったわけではありません。立ち上げ直後のドキュメントは今よりずっと大きく、主要4ファイルだけで3,323行ありました。当時私たちが使っていたモデルのコンテキストウィンドウ（AIが一度に扱える情報量）は20万トークンでした。そのため、AIがドキュメントを読むだけでコンテキストの60%ほどを使い切ってしまっていました。読んだ時点で余力がなく、何も作れないAIになってしまったのです。そこで3月に、ドキュメントの「ダイエット」を実施しました。コード例やディレクトリ構成など、コードを読めば分かる情報や重複を削り、957行まで約7割減らしています。4月にも別の設計ドキュメント7件を約46%圧縮しました。
そこから約2,800行まで育ったのは、次に紹介するdocs-botが設計判断を少しずつ追記していったためです。残す基準は「コードからは読み取れない、判断の理由と守るべきルール」に絞っています。
docs-botは、設計判断を記録するためのbotです。PRがマージされると、GitHub Actionsが差分とレビューコメントを生成AI（Amazon Bedrock）に渡し、設計判断を抽出します。抽出した判断は各ドキュメント末尾の「設計判断」セクションに追記され、元のPRの作成者をレビュアーとしたPRが自動で作られます。「なぜこう実装したのか」が自然と蓄積されるので、後から外部の点検や監査を受けた際も、根拠付きで回答できました。
ただし、過去の判断をAIが絶対のルールとして扱うと、前提が変わったときに古い判断を引きずってしまいます。そこでCLAUDE.mdには、設計判断の扱い方を次のように書いています（抜粋・一部省略）。
### 「設計判断」セクションの扱い方
各ドキュメント末尾の「## 設計判断」セクションは、
**過去のPRでの判断記録（参考情報）であり、絶対に従うべきルールではない**。
- 判断には当時の前提・文脈がある。新規開発では前提が変わっている可能性を常に考慮する
- 過去の判断を踏襲する場合: そのまま進めてよい（判断根拠として引用すると良い）
- 過去の判断と異なる方針を取りたい場合: **勝手に逸脱せず、該当エントリを提示して
「前提がこう変わっているので別方針を取りたい」とユーザーに確認してから進める**
- 過去の判断と矛盾する実装を求められた場合: 矛盾に気づいた時点で該当エントリを提示して確認する（黙って上書きしない）
hookによるセルフレビューの強制
9月からは、Claude Codeのhookを使ってPR作成前にセルフレビューを必ず通すようにしました。セルフレビューには、別モデルによる独立したレビューも含めています。設定は次のとおりです（抜粋）。

"matcher": "Bash",

PostToolUse（ツールの実行後に動くhook）では、PR作成後にマーカーを削除しています。マーカーが残り続けると、マーカーの使い回しでレビューなしのPRが作れてしまうためです。なお、この仕組みが防ぐのはあくまで「レビューのし忘れ」です。マーカーを手で書き換えれば通過できてしまうため、CLAUDE.mdで「レビューせずにマーカーだけを更新することは禁止」と明記しています。

今回のアップデートの中身
まず最初に、発表された内容をざっくりまとめておきます。
- Skills over MCP：MCP サーバーが、ツールと一緒に「スキル」も配れるようになりました（パブリックベータ）

どれも便利そうですが、個人的に一番グッときたのは Skills over MCP でした。
Skills over MCP とは
その前に、MCP とスキルの関係を軽くおさらいしておきます。
MCP は、Claude を外のサービスとつなぐための仕組みです。GitHub や Notion などにつなぐと、Claude がそこのデータを読んだり、操作したりできるようになります。
ただ、つながっただけでは「どう使えばいいか」まではわかりません。手がかりはツールの名前と説明くらいなので、細かいところは推測で動くことになります。
そこを補うのがスキルです。スキルは作業の手順やコツをまとめたマニュアルのようなもので、SKILL.md というファイルが中心になっています。
ここで困るのが、これまでスキルは自分で入れる必要があったことです。ファイルをダウンロードして、設定画面からアップロードして…と、地味に手間がかかります。そもそも「このサーバー用のスキルがある」と気づかないこともあったと思います。
Skills over MCP は、この部分を解決する仕組みです。MCP サーバーがスキルも一緒に配ってくれるので、サーバーにつなぐだけで使い方のマニュアルも付いてきます。
一番いいなと思ったところ
一番いいなと思ったのは、スキルがサーバー側で更新されるところです。
サービスに新しい機能が増えれば、マニュアルもそれに合わせて勝手に新しくなります。使う側は何もしなくて大丈夫です。
手元にスキルを置いておくやり方だと、どうしても古くなっていきます。サービスはどんどん変わっているのに、手元のマニュアルは昔のまま、ということが普通に起きるんですよね。
これを気にしなくてよくなるのは、結構大きいと思っています。
もう一つ、スキルは必要なときだけ読み込まれます。最初は名前と説明くらいしか見ないので、たくさんのサーバーにつないでいても、そのせいでコンテキストがいっぱいになることはありません。
使われている例
元記事では、こんな例が紹介されていました。
- Shopify：ネットショップの立ち上げや更新を、最初から最後まで手伝ってくれます
- HubSpot：顧客のオンボーディングや、Claude でのセットアップを手伝ってくれます
- Atlassian：組織の状況をふまえて、作業の分析をしてくれます
どれも「ツールはあるけど、どういう順番で使うかが大事」なタイプの作業ですね。こういう作業こそ、手順をまとめたスキルがあると助かりますね。
仕組みを少しだけ
中身は意外とシンプルです。
- スキルの形式は、これまでと同じ SKILL.md と補助ファイルの組み合わせ
- それを MCP の「リソース」として公開する
- クライアントは skills/list で一覧を取って、skills/get で個別のスキルを取ってくる
MCP 側はスキルの中身を特別扱いしておらず、ただのリソースとして運んでいるだけです。このあたりの割り切り方はいけてそうだなと思いました。
どこで使えるか
Claude と Claude Code で使えます。
最後に

AIに実装を依頼して、動くコードを書いてもらったとしても、そのコードが「わかった」とは限りません。理解を省略してしまうと、仕組みを説明することができなくなります。第5回となるこの記事では、実装が終わった後に、AIが書いたコードの仕組みを自分の言葉で説明できる状態にする方法を解説します。
「コードが動いた」で思考を止めない
AIにコードを書いてもらい、動作確認もできたので、「動くコード」は手に入りました。しかし、そのコードはまだ「動いただけのコード」であり、「わかるコード」とは限りません。
ここでいう「わかるコード」とは、自分がその機能の仕組みを説明できるコードのことです。具体的には、次の3つの観点について説明できる状態のコードを指します。
AIが書いたコードを「わかるコード」にするために必要な観点
- よくある失敗パターン
- 実装した機能にバグが見つかったが、処理の流れを理解しておらず、どこから調べればいいか見当がつかなかった
- コードレビューで「ここの処理はなぜ必要なの？」と聞かれ「AIが生成したコードなので…」としか答えられなかった
- 仕様変更の工数を聞かれたとき、どこをどれだけ変えればいいか見当もつかず、自分で実装したはずなのにコードを調べ直すことになった
これらは、「動いた」という結果だけで思考を止めてしまった典型的な例です。とりあえず動くだけのコードを積み上げ続けると、将来的に誰も変更できず、保守もできない「ブラックボックス」が生まれてしまいます。そうした「理解の負債」が蓄積すると、プロジェクト全体の生産性も下がっていきます。
ただし、常にすべてのコードに対して、自分の言葉で説明できるまで深掘りする必要はありません。納期が迫っているときや、緊急対応が必要なとき、あるいは一度だけ使うコードを書くときなどは、理解よりも動かすことを優先すべき場面もあります。
コードの理解が特に有効なのは、次のようなタイミングです。
- 「動いたけれど、なぜ動いているのかわからない」と感じたとき
- 実装が一段落して、コードレビューの前に振り返る時間があるとき
- 今後も修正やメンテナンスが発生するコードを書いたとき
重要なのは、AIが書いたコードを理解するプロセスを習慣化することです。
実装したコードを理解するための3つのステップ
動いたコードを自分の言葉で説明できるようにするために、次ページからの3つのステップで理解を深めていきます。
実践例：ユーザー検索機能のコードを読み解く
ユーザーを管理するための社内ツールを開発しており、AIを使って、そのユーザー一覧画面に「名前で検索できる機能」を実装しました。
AIが生成したコードの構造は以下の通りです。
UserList() ユーザー一覧ページ
├── users ユーザー一覧を保持する変数
├── searchQuery 検索キーワードを保持する変数
│
├── handleSearchChange(event) 入力値をsearchQueryに保持する
│
├── filterUsers(users, searchQuery) usersをsearchQueryで絞り込む
└── 描画()
├── SearchInput（検索入力欄）
│ └── onChange → handleSearchChange()を呼び出す
└── filteredUsers 絞り込み結果を一覧表示する
STEP 1 全体フローを把握する
実装した機能がどこから動き始め、どの処理を通って、どこで終わるのかという全体の流れを把握します。
- 問いかけ前の思考
実装した機能は正しく動いていそうだ。ただ、今の機能では入力から表示更新までにどの処理がどの順番で動いているのか、まだ自分の言葉で説明できない。入力欄に文字を打ってからユーザー一覧が切り替わるまでの、一連の処理の流れを正確に掴みたい。
- AIへの問いかけ
入力欄に文字を打ってから、検索機能によって絞り込まれたユーザー一覧が表示されるまでの処理の流れを、どの関数を通るかを含めて教えてください。 また、処理のフローがわかりやすいように、フローチャートの形式でも説明してください。
- AIの返答例
処理の流れは以下の通りです。
- SearchInputの入力欄でテキストが変更されると、変更イベントが実行される
- handleSearchChangeが呼ばれ、入力値をsearchQueryに保持する
- searchQueryが更新されると、filterUsersが呼ばれる
- filterUsersは、ユーザー一覧の各要素に対して名前に入力値を含むかを判定し、一致するものだけを集める
- 絞り込まれた結果がfilteredUsersに格納され、画面の一覧が更新される
処理の起点はSearchInputの変更イベント、終点はユーザー一覧の更新です。
絞り込みの中心は処理4のfilterUsersです。
- 返答後の思考
入力の変更イベントから始まり、入力値の保持、絞り込み、ユーザー一覧の更新へ進むという全体の流れは掴めた。どこから処理が始まり、どこで終わるのかを把握できたので、実際のコードも追いながら全体フローの理解を深めていけそうだ。
いきなり個々の処理を深掘りするのではなく、最初に実装全体の流れを把握しましょう。全体における個別の処理の位置づけがわかれば、なぜその処理が必要なのか、どんな役割を果たしているのかを理解しやすくなります。箇条書きだけでは流れが掴みにくい場合は、フローチャートやシーケンス図の形式でAIに整理してもらうのも有効です。
STEP 2 各処理の役割を理解する
フローの全体像が見えたら、次は実際のコードを追いながら、各処理がなぜ必要なのか考えます。自分なりに仮説を立てつつ、その理解が正しいかAIに確認しましょう。
- 問いかけ前の思考
全体フローの中に出てきた「入力値をsearchQueryに保持する」というのは、なぜ必要なんだ？もしかして保持しておかないと、絞り込みのタイミングで入力値を参照できなくなるのかな？
「入力値の保持は、絞り込み処理で参照するために必要な処理」という仮説が合っているか、AIにぶつけてみよう。
- AIへの問いかけ
検索機能の仕組みについて、自分の理解を確認してください。 「入力値をsearchQueryに保持しているのは、絞り込み処理のタイミングで参照するため」という理解は正しいですか？
もし他にも重要な役割があれば教えてください。
- AIの返答例
理解はおおむね正しいです。 入力値をsearchQueryに保持する理由は、おっしゃる通り後続の絞り込み処理で参照するためです。加えて、画面を再描画するときにも最新の入力値を参照する必要があるため、状態としても保持しています。
つまりsearchQueryは、「今どんなキーワードで検索しているか」を画面全体で共有するための値です。
- 返答後の思考
仮説の大枠は合っていたけど、見落としていた点もあった。入力値の保持は、単なる絞り込みのためだけでなく、再描画のタイミングでも使われるのか。「絞り込みのためだけ」と考えていたが、実際には画面全体で最新の検索キーワードを扱うためにも必要だということがわかった。
実際のコードを追いながら自分の仮説や理解をAIに確認することで、コードの構造や役割の理解をさらに深めることができます。「もしこの処理がなかったら何が起きるか」と仮説を立てて考えることで、各処理の役割がより明確になります。コードの文法や構文ではなく、各処理がどういう役割を果たしているか、という仕組みの部分に焦点を当てるのがポイントです。
STEP 3 仕組みを言語化して整理する
全体フローと各処理の役割が見えたら、ここまで理解した内容を言語化し、抜けや間違いがないかAIに確認します。余裕があれば、「もし仕様が変わったら、どこを変えることになりそうか」についても考えてみましょう。
- 問いかけ前の思考
全体フローと各処理の役割はわかった。ここまでの理解を自分の言葉でまとめて、AIにぶつけてみよう。説明に抜けや間違いがあれば、そこがまだ理解できていない箇所のはずだ。
- AIへの問いかけ
検索機能の仕組みについて、自分の理解を整理しました。
- 入力欄に文字を打つと変更イベントが実行されて、入力値が保持される。
- 保持された値をもとに絞り込み処理が走る。
- 絞り込み処理は、条件に合うユーザーだけを新しく取り出す。
この理解は正しいですか？抜けや間違いがあれば指摘してください。
- AIの返答例
大枠は正しく理解できています。補足すると、特に重要なのは、元のユーザー一覧と絞り込み結果を分けて考えている点です。 検索機能では、元のユーザー一覧そのものを書き換えるのではなく、searchQueryに合うユーザーだけを一時的な絞り込み結果として表示します。そのため、検索キーワードを変更したり削除したりしても、元のユーザー一覧をもとに再度絞り込むことができます。
- 返答後の思考
自分の理解はおおむね合っていた。元のユーザー一覧を直接書き換えるのではなく、検索条件に合うユーザーだけを絞り込み結果として表示している目的についても知ることができてよかった。
自分の言葉で説明できたなら、その仕組みは理解できているといえます。説明に抜けや間違いがあれば、そこがまだ曖昧になっている箇所なので、AIと確認しながら知識を補いましょう。さらに、仕様変更が来たときを想定し、どこを変更するかのイメージを持つことで、より理解が深まります。
まとめ
「動いた」は実装の終わりではなく理解の始まりです。動いた直後に思考を止めると、コードが増えても理解は積み上がりません。「全体フローの把握」「各処理の役割の考察」「自分の言葉での説明」という3つのステップを踏むことで、動いただけのコードを、自身で扱える「わかるコード」へと変えることができます。

Ephyra is a new property-based testing library we are developing at Datadog Systems Research, designed from scratch for agentic property-based testing.
Briefly, Ephyra brings autoresearch style hill-climbing optimizations together with property-based testing; given a set of properties Ephyra first writes a simple valid test case generator, measures the code coverage, optimizes the generator to reach new regions of the code.
This process is similar to coverage-guided fuzzing (CGF) that favors inputs that increase the coverage of the testing space. However whereas CGF is deductive, mutating promising inputs; Ephyra is inductive, it rewrites the generator with the hypothesis of discovering promising inputs.
We have run Ephyra through popular targets for testing research, finding 70+ bugs in SQLite, 20 bugs in PostgreSQL, 25 bugs in Lean, several bugs in heavily fuzzing-guided developed systems such as FoundationDB and TigerBeetle. We present many more systems and bugs in the chart below.
The Ephyra library and Ephyra command line have their own respective documentation, mostly written in an information dense style targeting coding agents. Almost all of the code in this repository is experimental and subject to change, please let us know any issues you experience while using it.

Title:Evolution Strategies at Scale: LLM Fine-Tuning Beyond Reinforcement Learning
View PDF HTML (experimental)
Abstract:Fine-tuning large language models (LLMs) for downstream tasks is an essential stage of modern AI deployment. Reinforcement learning (RL) has emerged as the dominant fine-tuning paradigm, underpinning many state-of-the-art LLMs. In contrast, evolution strategies (ES) has largely been overlooked due to the widespread belief that it does not scale to modern model sizes. This paper overturns this assumption by demonstrating the first successful application of ES to full-parameter fine-tuning of LLMs at the billion-parameter scale, without dimensionality reduction. ES can indeed search over extremely high-dimensional parameter spaces and outperform established RL implementations across multiple axes, including improved tolerance to long-horizon and delayed rewards, robustness across diverse base LLMs, reduced susceptibility to reward hacking, and improved training stability. These findings suggest that ES is not merely a viable alternative to RL, but a fundamentally different and powerful backpropagation-free post-training paradigm that opens a new direction for LLM fine-tuning beyond current RL-based approaches.

minipg is PostgreSQL as one executable, ready to use, with no server to configure. A .pgdb directory is the database: its data, config, credentials, and Postgres version all live inside it, and minipg app.pgdb opens a psql shell on it. A server starts when a command needs one and stops on its own when it's idle.
minipg embeds Docker Hub's postgres:18-alpine image and runs it with h9, used as a Zig library. h9's Linux personality runs Alpine's own Postgres binaries directly on the host's hypervisor, with h9's Plan 9 kernel answering their system calls. There's no Linux kernel to boot, no VM image, and no Docker.
The demo downloads about 35 MB. It needs JavaScript Promise Integration, which Chrome and Edge have from version 137; other browsers are getting it. It can also be opened on its own page.
The demo runs minipg's Linux build, which runs inside the Postgres image itself. It starts Postgres as ordinary processes and serves on a unix socket, since a page has no TCP. New databases come from a template cluster made at build time, because initdb takes half a minute on v86.
minipg app.pgdb # psql shell (creates app.pgdb if missing)
minipg app.pgdb "select 1" # one statement
minipg url app.pgdb # postgres://postgres:...@127.0.0.1:54321/app
minipg serve app.pgdb # an explicit foreground server
minipg run app.pgdb -- npm start # your app, with DATABASE_URL set
minipg dump app.pgdb > dump.sql # and minipg restore app.pgdb dump.sql
A .pgdb holds minipg.toml (settings and the generated superuser password) and pgdata/, Postgres's data directory as plain files. A stopped one can be copied like any directory. New clusters use Postgres's builtin C.UTF-8 locale, which sorts the same on every platform.
In CI, the Linux binary is static and needs no privileges or devices: without /dev/kvm, h9 runs Postgres on its native backend. A test job can be as small as:
minipg init test.pgdb
minipg run test.pgdb -- go test ./...
The README lists every command, and the manual is the full guide.
Exactly one process runs Postgres for a .pgdb, enforced by a lock. It holds the server's h9 machine, whose Linux root is the unpacked image and whose writable working directory is the .pgdb. The image's docker-entrypoint.sh initializes the cluster on first start. Commands never host Postgres themselves. If no server is running, they start one in the background and use it. psql, pg_dump, and the other tools each run in their own short-lived h9 machine (about 90 ms to start) over the same root.
The source is on GitHub, under the MIT license. Building needs Zig 0.16, plus curl, jq, tar, and xz for the root:
git clone --recursive https://github.com/progrium/minipg
cd minipg
make build # pulls the root for this host's arch, builds ./minipg
make root ARCH=386
make web # this page's demo, in .zig-out/web
minipg is early, and h9's Linux personality is young. On h9's native backend, Postgres is about 2x slower than native for one client, and slower under load. Don't trust it with data you can't recreate yet.
Please report bugs and send questions through GitHub issues.

デジタル庁デザインシステムとは「プラットフォーム型」
デザインシステムは、特定の企業のロゴや色などのブランドアセットを前提とした「企業型」と、特定のブランドを持たず、さまざまな組織が使用できるようにした「プラットフォーム型」の2種類に大きく分けられます。
デジタル庁デザインシステムはプラットフォーム型であり、特定の組織のブランドやコミュニケーション方針を備えていません。そのため、使用するときは導入先のブランドやコミュニケーション方針（スタイルガイド）に合わせて、デザインシステムを定義し直す必要があります。

SSH is a GUI framework
"One thing about which fish know exactly nothing is water." — Marshall McLuhan
SSH is a tool so ubiquitous that we've forgotten what it actually is: a multiplexed, encrypted byte stream accessible on a cross-platform rendering engine that ships on every laptop, server, and phone on earth. A number of terminal protocols have slowly added graphics, clipboard sharing (including images), notifications, mouse support, and more on top of SSH.
To see just how far you can push it, I've made a microVM with a desktop environment designed from the ground up to render natively over SSH. You can try it right now (no sign-up):
ssh zydra.sh
ssh -p 443 zydra.sh # if on an office network
ssh -t zydra.sh dino # SSH port of the Chromium T-Rex game, for fun. Terminal Protocols (and matching terminal support)
All terminal protocols work on data that can be passed through SSH, so typically, any terminal protocol will extend to SSH.
Perhaps the most ubiquitous new terminal protocol is the Kitty Graphics Protocol, which superseded the older Sixel and iTerm2 graphics protocols. It allows for compression, client-side graphical state (via VRAM), and even animations entirely on the terminal.
Graphics alone don't make a complete GUI, though. SSH has protocols that cover all other angles:
- Notifications: OSC 99 "Rich Notifications" allow image, text, and body. OSC 777 (our first fallback) allows only text and body, and OSC 9 (our last fallback) allows only a title.
We end up using a similar fallback for many things.
- Clipboard sharing: OSC 52 handles bidirectional clipboard sharing, and Kitty's OSC 5522 adds image and arbitrary MIME-type transfers on top of that.
- Mouse support: CSI ? 1000-1006 help track the mouse and give us its precise coordinates.
- Synchronized Output (Batched Rendering): CSI ? 2026 allows atomic rendering, preventing visual tearing and flickering.
- File upload (Kitty): The Kitty terminal uniquely supports a file upload feature, which zydra.sh uses to allow the upload of projects and related files to personal VMs.
SSH-native compositing: How I made it fast
A few tricks make compositing over SSH fast. Firstly, where possible, especially when streaming terminals, we simply stream them as text rather than unnecessarily streaming it via graphics. The compositor's UI framework itself cleverly overlays traditional text over carefully aligned graphics, saving bandwidth. In the case of zydra.sh, this allows us to efficiently stream the entire cloud computer's desktop UI over SSH.
Next, we optimize graphics by sending a sort of "grid" of pixels. Each cell has its own updates, where the previous frame is compared to the current frame to catch and send updates, avoiding having to constantly stream the full screen. Kitty also offers both RGB and RGBA, and so by removing transparency where it's not needed, we save another 25% in bandwidth. We also track ping and other factors to determine how well the client handles the stream: lowering the resolution in select cells, especially when scrolling, to relieve pressure. We also use Kitty's client-side state to hold graphics ahead-of-time before they're displayed on screen, as well as holding repeated UI components.
Backwards Compatibility
Not all terminals support all the latest terminal protocols, so the compositor must also fallback to older graphics protocols Sixel and iTerm2, and when necessary, fall back to pure textual streaming, using ASCII to replicate some UI. In the case of notifications and other protocols, multiple protocols similarly exist, which we also gracefully fallback to when needed.
Parsing terminal versions and querying capabilities allows us to get an idea of what the client supports. We also continually verify that features work as expected on the client as the session boots. The Kitty terminal itself I've found to have very reliable support for all graphics protocols zydra.sh relies on.
SSH often beats webapps and VNC at their own job
VNC is limited to sending pictures of the screen and diffing frames to find what changed. With zydra.sh's approach, apps directly tell the compositor what changed, and terminal text is sent as text you can select and copy natively. The browser is a WebKit build that delivers frames to the compositor as DMA-BUFs without a readback, which can be driven agentically via Playwright.
While webapps have advantages, especially in client-side state, WASM, and WebGPU, they don't really capture the universality and ease-of-use of an SSH session. SSH keys double as authentication, and -A allows you to SSH into servers from within a remote microVM itself. Webapps also can't be accessed from a pure TTY.
SSH also has sshfs, so you can mount your VM's filesystem locally:
sshfs zydra.sh: ~/zydra

工具のマキタバッテリがPCの電源に!? 最大100Wの純正アダプタを使ってみた
2026年11月27日 06:13
マキタ「ADP15」は、同社の 電動工具で用いられている専用バッテリに取り付け、スマホやノートPCの充電を可能にするアダプタだ 。USB Type-CとUSB Type-Aをそれぞれ1ポートずつ搭載しており、災害などの緊急時に、バッテリを有効活用できる一品だ。
USB PDによる最大100Wの充電に対応することから、ノートPCの充電にも余裕で対応できるこの製品。ポータブル電源やモバイルバッテリが使えない場合の電源確保に適している。実機を購入したので、使い方や性能についてチェックするとともに、用途についても考察していく。
電動工具のバッテリを用いてUSBでの充電が可能に
本製品は、同社の電動工具に使われるバッテリに取り付けて使うアダプタだ。バッテリと一体化させて使うことを前提としており、形状も完全な専用品となっている。同社の電動工具用バッテリのすべてに対応するわけではなく、一部製品に限定されるので注意が必要だ。詳しくは後述する。
USBポートは、 12W(5V/2.4A)までの出力に対応したUSB Type-Aポートと、最大105Wまで対応したUSB Type-Cポート、計2基が搭載されている 。105Wというのはあまり見ない値だが、PPSの値が5～21V/5Aであるためこのような表記になっているだけで、USB PDの規格上は最大100W(20V/5A)となる。いずれにしてもかなりパワフルで、ノートPCの充電にも余裕で対応できる。
今回は筆者の私物で、同社の電動工具に付属していた「18Vリチウムイオンバッテリ」(BL1830B、容量3,000mAh)との組み合わせで使用してみた。
装着方法は電動工具に取り付けるのと同様だ。レールに沿ってスライドさせると、カチリと音がしてロックされる。あとは本製品側に用意されたUSBポートにケーブルを差し込み、もう一端をデバイスにつなぎ、本体上部のボタンを押すことにより充電が開始される。
見た目こそやや特殊だが、使い方自体は一般的なモバイルバッテリと変わらない 。バッテリが着脱式になっているというだけの話だ。ちなみに残量表示は本製品側ではなく、バッテリ側にその機能があれば対応する。今回のBL1830Bでは4段階のゲージで確認できる。
最大105W、スマホはもちろんPCも余裕で充電可能
性能についてもう少し詳しく見ていこう。「USB Cable Checker3」のポートチェック機能を使って仕様を確認した。本体側面に記載されているのと同様、最大100W(20V/5A)までの対応に加えて、PPSで5～21V/5Aまで対応することが分かる。また別のケーブルチェッカーを見る限り、PPSに加えてAVS(Adjustable Voltage Supply、機器に応じて給電の電圧を調整する機能)にも対応しているようだ。なかなかの高機能である。
続いて実際にスマホおよびノートPCを充電し、出力および容量をチェックしてみた。まずスマホ(iPhone 17 Pro Max)については、 ピーク時でほぼ上限いっぱいとなる37W前後で充電が行なえていた 。なかなか優秀だ。
ノートPCはどうだろうか。今回はWindows PC(ThinkPad X1 Carbon Gen 9)で試してみた。このPCは最大65Wでの充電に対応するが、今回は ピーク時に60W前後で充電が行なえていたので、こちらもかなり優秀だ 。試用中に3Aを超えた形跡はなかったが、前述のポートチェックの結果からして、接続するデバイス次第で5Aで充電される場合もあるとみなして問題ないだろう。
ちなみに今回試用したバッテリ「BL1830B」は容量3,000mAhと控えめなため、前述のWindowsノートについては満充電に達する前、77%程度で充電が終了した。ただし、本製品に対応するバッテリには12,000mAhの大容量モデルもあるため、それらを使えば満充電も問題なく行なえる計算になる。このあたりは、手持ちのバッテリ次第ということになるだろう。
災害などの緊急時に最適。対応バッテリに注意
以上のように性能、使い勝手ともに問題のない本製品は、 普段使いよりも、災害など緊急時により適していると考えられる 。理由は大きく分けて2つある。
1つは、これらのバッテリを用いる電動工具が、災害時に使われるケースは極めて稀だと考えられることだ。出番のない電動工具のバッテリを、ポータブル電源やモバイルバッテリに代わって貴重な電力源として活用できるのであれば、それに越したことはない。
特に停電からの復旧の見通しが立たない状況下では、汎用性の高いポータブル電源やモバイルバッテリは、なるべく使わずに余力を残しておきたい。本製品があればこうした場合の先鋒として活用できるし、どちらも使える状況下であれば、スマホなどの充電は本製品が、それ以外の一般的な家電製品はポータブル電源が受け持つという、役割分担が成立しうる。
もう1つ、電動工具用のバッテリは交換用に複数を所有していることが多いため、1個あたりの容量はそれほど大きくなくても、複数個を交換しながら多くの製品を充電できる。さらにその性質上、充電が完了した状態でストックされている可能性が高いのも、充電できる見込みが立たない災害時には好都合だ。
一方で気を付けたいのは、本製品にはバッテリ自体を充電する機能がないことだ。つまり本製品を使って外部のデバイスを充電し、バッテリの残容量がゼロになってしまえば、バッテリを再充電するには元の電動工具側の充電器が必要となる。災害時であれば「それどころではない」可能性はあるが、充電器がない環境に持ち出す場合は注意したいところだ。
また本製品は「マキタ18V/14.4Vバッテリ」に対応する旨の記述があるが、実際には18V/14.4Vバッテリにも複数の形状があり、あらゆるモデルが対応するわけではない点には要注意だ。
たとえば筆者宅には今回試用したモデル以外に、電動ドリルやインパクトドライバーで使用する「BL1415G」なる14.4Vのバッテリがあるが、端子の形状が異なるので物理的に接続できない。 対応可否を確認するときは、電圧の表記だけで判断せず、型番ベースで確認することをおすすめする 。
いずれにしても、これまで同社の電動工具でしか使えなかった専用バッテリを、USB PD経由でほかの用途で使えるようになる画期的な製品で、7,000円前後という実売価格にも納得がいく。さすがにサイズや形状的に普段使いには向かない。ただ、対応するマキタの電動工具が自宅にある場合、災害用途で新たにモバイルバッテリを調達するなら、むしろ本製品を買って手持ちのバッテリを流用可能にしたほうがよい場合もありそうだ。
現状で入手にあたってネックになるのは、2026年春の新製品でもあるためか取り扱いが少なく、あってもかなりの品薄であること、また一部の販路では価格が跳ね上がっていることくらいだろうか。兄弟モデルとして40Vmaxバッテリに対応した「ADP002G」なるモデルもラインナップされているので、併せてチェックすることをおすすめしたい。
